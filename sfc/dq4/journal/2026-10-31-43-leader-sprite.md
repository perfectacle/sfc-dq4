# 2026-10-31-43: NDS 시트로 줄인 장 주인공과 장마다 그림 고르기

서장 주인공(천공의 용사)과 1장 라이언의 필드 그림을 NDS 인물 시트에서 줄여 넣고, 같은 그림 번호를 쓰는 두 주인공을 맵 그룹으로 갈라 그리게 했습니다. 규칙과 자리는 [스프라이트 규격의 「NDS 시트에서 줄인 서장·1장 인물」](../docs/dq4-sprite-format.md#nds-시트에서-줄인-서장1장-인물-dq4peoplepy)에 있습니다.

## 1. 만드는 방식부터

손으로 찍은 인물은 품질이 모자랐습니다([72번 일지](2026-10-25-72-sprite-drafts.md)). 세 가지를 시험했습니다.

- **다른 SFC 게임 인물 조립**: DQ6 필드 인물의 몸에 머리색·장식을 바꿔 붙이면 크기는 맞았지만, 원래 인물의 인상이 남았습니다.
- **이미지 생성 모델**: 공개 모델에 DQ6 필드 인물로 LoRA 를 학습시키고, NDS 그림을 입력으로 주는 편집 모델도 돌렸습니다. 큰 화면에 도트처럼 보이는 그림은 나왔지만 칸이 16×24 격자에 맞지 않아, 격자로 읽으면 색이 70~200개 섞이고 눈 같은 1~2픽셀이 사라졌습니다. 입력을 크게 넣으면 NDS 그림을 거의 그대로 베꼈습니다.
- **NDS 시트를 바로 줄이기**: NDS 프레임(24×32)을 세로 줄 수에 맞춰 BOX 축소하고 NDS 색으로 되돌리기만 한 것이 편집 모델의 결과보다 낫다는 판단을 받았습니다. 이것으로 정했습니다.

## 2. 크기

폭을 16칸에 맞추는 법은 세 가지를 견줬습니다: 가로만 눌러 줄이기, 24줄로 줄인 뒤 양끝 자르기, 비율을 지켜 키를 줄이기. 양끝 자르기가 원래 느낌에 가까웠습니다.

키는 처음 24줄(16×24 를 다 씀)로 넣었다가 「얘만 너무 크다」 는 평을 받았습니다. 저장소 규칙의 DQ5 주인공 실측(폭 14, 17~19줄)으로 19줄을 넣자 이번에는 DQ5 병사 옆에서 작고, 옆모습이 12칸으로 홀쭉했습니다. 병사(세트 `00`)를 덤프해 재니 네 방향 모두 불투명 상자가 16×22, 발이 21행이었습니다.

```
병사 상자(아래·왼·오·위) [(0, 0, 16, 22), (1, 0, 16, 22), (0, 0, 15, 22), (0, 0, 16, 22)]
```

22줄에 발을 21행으로 맞춘 것이 받아들여졌습니다. 21줄은 줄이는 칸이 얼굴 어두운 색에 걸려 얼굴이 뭉개졌습니다.

## 3. 걸음

NDS 시트는 방향마다 프레임이 셋입니다. 처음에는 첫 둘을 걸음 두 장으로 썼는데 팔만 휘저었습니다. 앞 줄에서 프레임끼리 다른 행을 세었습니다.

```
row 4 runs [(1, 23), (25, 47), (49, 71)] 0v1 diff rows (16, 24, 9) 0v2 (4, 24, 21)
```

둘째·셋째는 다리 행(25~)이 첫째와 같은 팔 동작이었습니다. 그래서 첫 프레임만 쓰고 둘째 장은 DQ5 처럼 다리만 바꿨습니다. DQ5 어린 주인공(세트 `82`)은 걸음 두 장이 16~21행만 다르고, 위 보기는 아래 8행이 좌우 반전이었습니다. 앞·뒤는 1장째 오른발, 2장째 왼발을 1칸 듭니다.

옆은 처음에 둘째 장만 다리 5행을 통째로 보는 쪽으로 밀었더니 「발 바꾸는 게 어색하다」 고 했습니다. 병사의 옆 두 장을 색 번호로 찍어 보니 몸통은 같고 발 줄만 앞뒤로 옮겼습니다.

```
right frame 0                right frame 1
..11111111111...             ..1111111111....
.......1111341..             ..1111341.......
```

발 3행을 1장째 보는 쪽, 2장째 반대쪽으로 1칸씩 옮기게 바꿨습니다.

## 4. 같은 그림 번호를 쓰는 두 주인공

1장 걷기 검사의 서장 구간(`dq4ch1walkcheck.py --until prologue`)으로 1장 왕좌의 방까지 간 상태에서 일행 그림 번호를 읽었습니다.

```
196F=2B 00 00 00 1967=01 2190=00 21BE=00 BC=36 BD=01
```

서장 주인공도 `2B` 입니다. `dq4ch1event.py` 에 적힌 대로 실내는 `02:CA5A` 가 `2B`, 바깥은 `05:D98F` 가 `2E` 로 둡니다. 그림 번호 → 세트를 읽는 `LDA $2586D0,X` 두 곳(`1F:CF45`, `03:D202`)을 훅으로 돌렸습니다.

처음에는 장 깃발 `CHAPTER1` 로 골랐습니다. 성 아래 마을(바깥)에는 라이언이 나왔지만 왕좌의 방에는 천공의 용사가 남았습니다. 왕좌의 방은 맵을 불러오며 주인공 그림을 올린 뒤에 장 제목 연출이 깃발을 켜기 때문입니다. 지금 맵 그룹 `$BC` 로 바꿨습니다. 서장 마을 `3C` 면 천공의 용사, 그 밖이면 라이언입니다. 다시 걸으니 왕좌의 방·성 아래 마을 모두 라이언, 서장 수련장은 천공의 용사였습니다.

## 5. 빌드에 붙이기

미리보기 롬의 BGM 이 이상하다는 말을 들었습니다. 작업 폴더가 `origin/main` 보다 141커밋 뒤였고, 곡 단계 전의 `dq4-ch1.sfc` 에 그림을 얹고 있었습니다. 최신으로 올려 곡 롬(`dq4-ch1-sound.sfc`) 위에 얹자, 쓰던 `3F:E300` 을 곡 롬의 다른 자료가 차지하고 있어 `apply_writes` 가 거부했습니다. 곡 롬의 0 끝 줄 안 `3E:E000`(타일)·`3D:EA00`(팔레트 표)·`3E:FC00`(훅)으로 옮겼습니다.

`dq4build.py` 는 곡 롬 다음에 `dq4leader.py` 를 불러 `dq4-ch1-full.sfc` 를 만듭니다. 손으로 얹어 검사한 롬과 빌드 결과가 바이트까지 같았습니다.

## 틀렸던 것들

- NDS 의 둘째·셋째 프레임을 걸음으로 봤다: 팔 동작이었다.
- 장 깃발로 주인공을 고를 수 있다고 봤다: 왕좌의 방은 깃발보다 그림을 먼저 올린다.
- 이상한 BGM 이 빌드 스크립트 문제라고 의심했다: 옛 브랜치의 곡 전 롬에 얹은 탓이었다.

## 남은 것

- 옆 걸음이 자연스러운지 사용자 확인.
- 2장 이후 주인공(맵 그룹 표에 줄 더하기), 다른 1장 인물로 넓히기. 공용 팔레트로 모으는 방식과 맵마다 OBJ VRAM 여유를 먼저 재야 합니다.
- 팔레트 6·7 이 1장 맵에서 다른 색으로 덮이지 않는지(`01:9A12` 맵 줄, `$1A0C` = `06`).
