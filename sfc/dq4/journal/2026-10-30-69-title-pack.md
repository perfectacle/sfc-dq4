# 2026-10-30-69: 타이틀 차분 자료를 한 벌씩 모아 36~39 비우기

타이틀의 용 차분 전송 자료가 `36:8000`~`39:821F` 를 차지하던 것을 `36:8000`~`36:9DBF` 로 줄였습니다. 화면에 보이는 프레임과 타이밍은 그대로입니다. 배치는 [타이틀 애니메이션](../docs/dq4-title-animation.md#차분-데이터-모으기)에 있습니다.

## 1. 무엇이 자리를 먹었나

`dq4titlelayers.pack_payload()` 의 `store()` 는 서술자마다 자료를 뒤에 덧붙였습니다. 기준 빌드의 자료를 세어 보았습니다.

```text
layer-payload.bin 98848
차분 198개 28,416바이트, 서로 다른 것 97개 14,080바이트
OAM 프레임 128개, 서로 다른 것 10개(544바이트씩)
최대 구간 9개 → 위상마다 256바이트 서술자 칸에서 최대 80바이트만 씀
```

OAM 프레임은 날갯짓 높낮이(`hover`)와 페이지 비트만 달라서 10가지뿐입니다. 차분 가운데 21개(2,912바이트)는 OBJ 초기 두 페이지(`34:8000`) 안에 이미 그대로 있습니다.

## 2. 한 벌만 두기

자료를 긴 것부터 놓으면서, 이미 롬에 있는 곳(초기 두 페이지, 앞 구름 OAM 표, 전경 CHR, 앞서 놓은 자료)에서 같은 바이트열을 찾으면 그 주소를 씁니다. 없으면 서술자 칸의 끝 표시 뒤 빈 곳에 가장 꼭 맞게 넣고, 어느 칸에도 들지 않는 OAM 프레임과 큰 차분만 `36:8000` 부터 둡니다. `Motion` 은 길이 0 인 서술자에서 멈추므로 칸의 나머지는 읽지 않습니다.

```text
33 서술자 칸 빈 곳   8,896바이트(남은 빈 곳 21,264바이트)
36:8000~36:9DBF     7,616바이트
```

`32:C3C0`~`32:FFFF` 는 전경 CHR 뒤 빈 곳이지만 1장 빌드의 새 맵 레코드 자리로 쓰기로 했고, `30`·`31` 의 빈 곳도 `dq4chapter1.RECORDS_AT` 이 쓰므로 비워 두었습니다.

## 3. 같은지 확인

런타임 코드는 바뀌지 않았고, 서술자와 OAM 포인터의 읽는 주소만 바뀝니다. 기준 롬과 새 롬의 다른 곳은 `31:EB00` OAM 포인터, `33` 서술자 칸, `36`~`39` 와 체크섬뿐입니다.

MesenCE 헤드리스에서 프레임 끝마다 화면 버퍼(`emu.getScreenBuffer`)를 남겨 견주었습니다. `--Snes.DisableFrameSkipping=true` 없이 `emu.takeScreenshot()` 으로 찍으면 같은 롬끼리도 1~3프레임 흔들려, 처음에는 669장이 다르게 나왔습니다.

```text
기준 롬 두 번       2400장 중 다름 0
대기 2400프레임     2400장 중 다름 0, 서로 다른 화면 421가지
A 600~601 누름      1000장 중 다름 0, 메뉴 복귀 00:A6F1 둘 다 680프레임
```

타이틀은 101프레임에 들어오므로 대기 실행은 카운터가 `0800` 에서 `0400` 으로 돌아가는 곳까지 덮습니다. 타이틀 자동 검사, 서곡·메뉴·1장 빌드도 통과했고 1장 롬은 기준과 타이틀 자료 자리에서만 다릅니다.

## 남은 것

- OAM 프레임 10개는 544바이트씩이라 서술자 칸에 들지 않습니다. 이것만 다른 곳으로 옮기면 `36` 도 비울 수 있습니다.
