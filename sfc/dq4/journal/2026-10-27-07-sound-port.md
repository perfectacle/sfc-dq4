# 2026-10-27-07: NDS 성 곡을 DQ5 엔진으로

NDS DQ4의 성 곡(왕궁의 미뉴에트)을 NDS 샘플과 함께 DQ5 사운드 드라이버로 옮겨, 실제 롬에서 울리고 귀로 들어 딸깍 소리가 없을 때까지 다듬었습니다. 맵 전환 페이드가 멈추던 원인도 찾았습니다. 결과는 [사운드 포팅](../docs/dq4-sound-port-format.md)에 정리했습니다.

## 1. 시퀀스가 SPC 메모리에 들어가지 않음

첫 삽입은 `SPC budget exceeded (48062/44195 bytes)`로 멈췄습니다. 변환한 성 곡 시퀀스가 15,217바이트로, DQ5에서 가장 큰 곡 `15`(4,595바이트)의 세 배가 넘었습니다. 명령별로 세어 보니 원인은 음표가 아니었습니다.

```
volume2 1967, tie 1595, rest 1298, note 1153, tempo 703, gate_preset 665
```

NDS 악보는 템포를 1 BPM 단위로 1,918번 바꾸고(115 → 128 → 123 …), 세기도 음마다 다릅니다(54~127). 그대로 옮기면 템포 경계와 CC 경계마다 음이 `tie`로 쪼개집니다.

- 템포: 원래 템포 경계마다 누적 시각 오차가 0.012초 이하가 되게 정수 템포 구간으로 합쳤습니다. 처음에는 원래 경계에서만 자르다가 일부 곡의 오차가 0.022초가 됐습니다. DQ5 템포가 정수라 긴 구간에서는 소수 템포만큼 밀리기 때문입니다. 박마다 나눌 자리를 더해 이웃 정수를 번갈아 쓰게 하자 50곡 모두 0.012초 이하가 됐습니다.
- 세기: 직전 값과 1dB 이내 차이는 새 `volume2`를 쓰지 않고, 음 중간 CC로 음을 자르는 것도 같은 기준으로 했습니다.

성 곡은 6,894바이트, 50곡 합계는 471,155바이트에서 243,156바이트가 됐습니다.

## 2. 롬에서 정말 그대로 울리는가

8kHz NDS 샘플 4개와 함께 빌드하고, 미리듣기 훅으로 타이틀 곡 자리에 틀어 전원부터 2,400프레임을 돌렸습니다. 기존 `dq5spc.py --check`는 `seq 02 DIFF`를 냈습니다. `dq5song.py --kon`도 프레임 오차 50~118로 나왔습니다. 둘 다 원래 자리 시퀀스와 템포 하나를 가정하기 때문이었습니다. 재배치 표를 따라가고 트랙 0의 템포 명령으로 시각을 계산하는 `dq4soundcheck.py`를 새로 썼습니다.

```
sequence_ok true, samples 26..29 ok
voice 0..5: KON 108/45/53/107/44/44 = 예상 음 수, wrong_srcn 0, interval_mismatches 0
speed_ratio 0.9987, max_frame_error 1.76
```

처음 비교에서는 오차가 시간에 비례해 0에서 4.2프레임까지 늘었습니다. 공칭 32kHz로 계산했는데 APU 발진기가 0.13% 빨랐기 때문입니다. 공통 속도 비를 맞추자 잔차가 2프레임 안에 들었습니다.

## 3. 맵 전환 페이드가 멈춤

`00:CEB1`(앞 곡 정리)을 「줄이기 `04` → 프레임 기다림 70번 → 정리」로 바꾼 훅은 맵에 들어가며 멈췄습니다. 앞 세션이 남긴 추적은 `71:8017 → 24:FE44 → 00:9506 → 00:969A → 2B:C473`에서 끊겨 있었습니다.

`00:969A`는 직접 페이지 `$19` bit0을 켜고 소리 일(`2B:C473` → `JML $0008EF`)로 넘어간 뒤, NMI가 그 비트를 지우기를 기다리는 협력 전환입니다. 그래서 그때 NMI가 켜져 있었는지를 쟀습니다.

```
f320 $2100=80
f320 $4200=01      ← NMI 끔
f321 hook 718000   ← 그 뒤 NMI 처리기 00:885D 실행 0번
```

맵을 불러오는 동안 NMI가 꺼져 있었습니다. 원래 게임은 이 자리에서 대기열에 넣기만 하고, 대기열은 불러오기가 끝난 뒤 처리됩니다. `$194B`(맵 곡)도 불러오기 안에서 정해지므로, 화면이 어두워질 때는 게임도 다음 곡을 모릅니다.

대기열을 보내는 `2B:C169`는 APU 포트만 폴링하고 프레임을 기다리지 않습니다. 그래서 훅이 같은 손잡기(`$08DC`·`$08DA`)로 SPC `04 지금곡 40`을 직접 보내, 검은 화면 동안 앞 곡이 줄게 했습니다. 새 곡은 `01` 대신 `03 n 30`으로 0부터 키웁니다. `01`과 `03`을 둘 다 넣으면 첫 음이 최대 음량으로 6프레임 울렸습니다. 성 → 필드에서 앞 곡은 455프레임(검은 화면 안)에 0이 됐고, 새 곡은 500프레임에 `01,01`에서 시작했습니다.

## 4. 「음정이 바뀔 때마다 스위치 소리」

첫 렌더를 들은 사용자가 「음정이 바뀔 때마다 똑딱하는 스위치 같은 소리, 노이즈」를 지적했습니다. 고역 에너지가 튀는 창은 KON 뒤 약 0.1초에 반복해서 나왔습니다(0.216 → 0.336초, 0.95 → 1.064초). 음마다 처음부터 재생되는 샘플 안의 같은 자리라는 뜻입니다.

인코더 `dq5brrenc`는 넘친 표본을 15비트로 자른다고 보고 니블을 고릅니다. S-DSP는 16비트로 자른 뒤 1비트 밀어 부호가 뒤집힙니다. 샘플을 `dq5brr.decode`(S-DSP와 같은 계산)로 풀어 원래 PCM과 비교했습니다.

```
26 SNR 38.72dB  튐 0
27 SNR 35.30dB  튐 0
28 SNR 13.67dB  튐 53  (첫 튐 0.095초, 두 계산 차이 최대 29,476)
29 SNR 17.12dB  튐 23
```

S-DSP와 같은 계산으로 오차를 재는 인코더 `encode_hw`를 dq4 도구에 두고 다시 만들자 튐이 0이 되고 SNR은 27.2~38.7dB가 됐습니다.

## 5. 음머리의 짧은 잡음

사용자는 딸깍이 「현저하게 줄었다」면서도 시작에 「팟」 하는 아주 짧은 잡음을 들었습니다. DQ5 원래 샘플 38개는 모두 무음 블록(`02 00 …`)으로 시작했지만, 새 샘플은 첫 블록부터 큰 값이었습니다. 16표본 무음 블록을 앞에 붙였습니다. 목소리별 렌더를 들은 뒤 사용자는 이 잡음이 곡 맨 처음 한 번뿐이라고 확인했습니다(남은 것).

## 6. 합치면 들리는 「똑딱」

목소리별 렌더는 깨끗하다는데, 합친 소리에서는 다시 들린다고 했습니다. 혼합은 목소리별 렌더의 합과 같았으므로(잔차 RMS 5.7) 섞을 때 생기는 소리는 아니었습니다. 드라이버 코드를 읽었습니다.

- `15E5`~`1629`: 음이 끝나기 1틱 전에 다음 트랙 바이트를 미리 봅니다. 다음이 음이면 KOF(`1A88`)로 약 8ms 만에 끊고, 쉼표면 걸지 않습니다.
- `1528` → `1A7F`: 게이트가 끝나면 ADSR2를 `$0393`(서스테인 레벨 | `DD` 속도)으로 바꾸는 소프트 릴리스입니다.

변환기는 같은 NDS 트랙을 같은 목소리에 붙였습니다. 그래서 775음이 앞 음 끝 12틱 안에 같은 목소리로 들어왔고, 앞 음은 최대의 40~65%로 울리다가 박마다 여러 목소리에서 동시에 끊겼습니다. 새 음은 12틱 이상 쉰 목소리에 먼저 넣어 앞 음이 자기 목소리에서 소프트 릴리스로 사라지게 했습니다(775 → 160). 릴리스는 `15`에서 `1C`로 빠르게 했습니다. 시퀀스는 8,667바이트, SPC 예산은 41,548/44,195바이트입니다. 사용자가 들어 보고 깨끗하다고 확인했습니다.

## 틀렸던 것들

- 「맵 페이드가 멈추는 것은 훅의 PLX 폭 문제」: 추적 때 D와 레지스터 폭은 정상이었습니다. 원인은 NMI가 꺼진 동안 프레임을 기다린 것이었습니다.
- 「`dq5brrenc`의 SNR 27~38dB면 샘플은 괜찮다」: 그 SNR은 인코더 자기 모형으로 잰 값이었습니다.
- 첫 S-DSP 디코드 비교에서 모든 샘플의 오차가 커 보였습니다. `dq5brr.decode`가 앞의 시드 2표본을 이미 빼고 돌려주는데 한 번 더 빼서 2표본 어긋났던 것입니다. 맞춘 뒤에는 `28`·`29`만 문제였습니다.
- 「키를 뗄 때 8ms 만에 끊기는 것은 DQ5 원곡에도 있으니 원인이 아니다」: 원곡 `05`에 급한 끊김이 더 많았지만, 이 곡은 같은 성부의 이어지는 음이 같은 목소리에서 박마다 동시에 끊기는 것이 문제였습니다.
- 「고쳐도 똑같다」는 청취: 렌더가 모두 `castle.wav`라는 같은 이름이었습니다. 같은 SPC의 20초 렌더는 깨끗하다고 했고, 150초 렌더의 앞 20초와 표본까지 같았습니다. 버전마다 다른 이름으로 다시 건네자 깨끗하다고 확인했습니다.
