# 2026-10-26-38: 자모를 조합해서 이름 넣기

모험의 서를 만들 때 한글 자모를 골라 이름을 조합하도록 입력기를 만들었습니다. 이름은 두 바이트씩 네 글자를 저장합니다. 구조와 재현 방법은 [조합형 이름 입력](../docs/dq4-name-entry-format.md)에 정리합니다.

## 1. 여덟 바이트에 네 글자

DQ5의 이름 버퍼는 여덟 바이트입니다. 호환 자모 51자와 KS X 1001 완성형 2,350자에 번호를 붙이고, 번호를 111로 나눈 몫과 나머지에 각각 `10`(16진수)을 더해 저장했습니다. 두 바이트 모두 기존 가나 범위에 들어가서 이름 끝 부호 `01`과 겹치지 않습니다.

「라이안」을 입력하고 새 게임을 시작한 뒤 이름 버퍼에서 `16 2F 1E 3C 1C 5A 01 01`을 확인했습니다. 다시 문자열로 풀면 「라이안」입니다. 다만 기존 출력기는 각 바이트를 가나로 읽으므로 저장만 바꿔서는 한글로 보이지 않습니다.

## 2. 조합 상태를 되돌리는 지우기

입력 중인 글자는 초성·중성·종성 상태를 스택에 쌓습니다. B나 「지우기」는 이 상태를 하나 되돌립니다. 받침 뒤 모음이 오면 받침을 다음 글자의 초성으로 옮기고, 겹받침이면 뒤 자음만 옮깁니다. 완성형 표에 없는 음절이나 다섯째 글자가 생기면 입력 직전 상태로 복원합니다.

Python 기준 구현의 테스트는 겹모음, 겹받침 이동, 네 글자 경계, 미수록 음절 거절과 저장 부호 전수 왕복을 확인합니다. 이 검사는 실제 65816 루틴과 화면 검증을 대신하지 않습니다.

## 3. 위아래 이동의 줄 폭

자모판을 그린 뒤 위아래 이동이 엇나갔습니다. 한 줄은 빈 칸까지 11칸인데 `$0AE3`은 7이었습니다. `04:C6E7`이 첫 줄에서 선택 항목 `FE`만 세고 빈 칸 `FC`는 세지 않았습니다.

첫 줄 끝에 `9F 00 FE`를 빈 칸 수만큼 더하고, 창 접두 훅에 열 수가 0이면 그리지 않는 처리를 넣었습니다. 그 뒤 `ㄷ → ㅇ → ㅊ → ㅇ → ㄷ → ㄸ` 순서로 이동하는 것을 확인했습니다. 화면 위치와 선택 색인이 같은 줄 폭을 쓰게 된 것입니다.

## 4. 저장은 맞고 목록은 가나

「라이안」을 저장한 기록을 다시 여니 목록에는 「きみそそ」가 보였습니다. 처음에는 창 레코드의 `C1`을 이름 자리라고 생각했지만, 이 처리기는 숫자를 그렸습니다. 이름은 `CF` 처리기 `04:B77A`를 거쳐 공통 루틴 `04:B79B`로 갔습니다.

이 루틴에 들어올 때 `$01`~`$08`을 기록하니 저장한 이름 바이트와 같았습니다. 따라서 저장 형식이나 SRAM 복사를 바꾸는 대신 메뉴에서 이름을 그리는 부분을 연결해야 했습니다. 이 공통 루틴은 게임 안 상태 창도 쓰므로 메뉴 표시를 확인해 한글 출력 범위를 제한합니다. 시작 메뉴에서 실제 열린 기록 목록은 창 `61`이었습니다. 앞 문서에서 적은 `70`과 구분해 명세를 바로잡습니다.

## 5. 이름마다 다른 타일

처음 목록 이름을 넣은 타일 `100`대에서는 배경이 반복 무늬로 덮였습니다. 이름 타일을 메뉴 문구 뒤의 `2D0`~`2E7`과 그 아래 줄 `3D0`~`3E7`로 옮겼습니다. 글자 아랫부분이 창 테두리와 겹쳤지만, 창 `61` 레코드의 높이를 늘려도 바뀌지 않았습니다. `04:A270`에서 기록 수에 따라 높이를 다시 계산하기 때문이었습니다. 메뉴에서만 이 계산에 한 줄을 더하고 타일 높이와 픽셀 높이를 함께 갱신하는 경로로 연결했습니다.

이름 하나가 여덟 열을 쓰므로 목록의 세 이름에는 각기 다른 타일을 줍니다. 「라이안·크리프트·미네아」 세 기록을 동시에 열어 서로 덮이지 않는 화면을 확인했습니다. 한 이름 그림을 세 행이 공유하면 마지막 이름으로 모두 바뀔 수 있으므로 슬롯을 나눕니다.

## 6. 완료 키는 Y

조합 상태 검사 뒤 실제 Start 버튼으로 완료하도록 연결하자 검사가 시간 초과로 끝났습니다. 처음에는 창 머리 `+4`의 `08`을 Start 허용 비트로 오해해 보존했지만, 이 값은 제목 위치이고 다음 바이트 `24`는 제목 번호였습니다. 새 자모판은 제목을 본문에 그리므로 `+4=00`이 맞습니다. 잘못된 변경과 그 가정으로 만든 테스트를 되돌리고 실제 버튼 처리 경로를 조사했습니다.

`00:9741` 이후 입력 변환에서 컨트롤러 Y 비트를 두 번 오른쪽으로 옮겨 `$24 & 10`으로 만듭니다. 물리 Start는 버립니다. 원본 이름 입력의 완료 키는 Y였고, 새 루틴의 주석과 검증 입력이 잘못됐던 것입니다. 「끝」을 A로 고르거나 Y를 누르는 원래 동작을 유지합니다.

최종 검증은 빈 이름 B·Y, 조합·삭제 13개와 Y 완료 직렬화·새 게임 이름 확인 2개를 모두 통과했습니다. 입력 칸 256바이트와 목록 이름별 256바이트가 생성한 글꼴과 차이 0이었습니다. Python 단위·실제 빌드 검사 22개도 생략 없이 통과했습니다.

## 틀렸던 것들

- 빈 칸도 줄 칸 수에 포함될 것으로 생각했지만 첫 줄의 `FE`만 세었습니다.
- 이전 실행의 화면 파일을 새 결과로 잘못 읽었습니다. 실행마다 새 출력 폴더를 써서 관찰 시점을 구분합니다.
- 기록 목록의 레코드 높이를 늘리면 테두리도 내려갈 것으로 생각했습니다. 실제 높이는 기록 수에 따라 다시 계산됐습니다.
- 이름 자리로 처음 조사한 `C1`은 숫자 출력이었습니다. 실제 호출과 이름 버퍼를 함께 기록해 `CF` 경로를 확인했습니다.

## 남은 것

- 게임 안 메시지·상태 창의 이름 한글화와 기존 가나 이름의 구분
- 메뉴 메시지 `1CE`·`1CF`·`1D0`의 한글화
- 사용자 시각 확인과 실제 SFC 기기 검증
