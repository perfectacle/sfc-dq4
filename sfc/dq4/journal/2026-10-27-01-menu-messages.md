# 2026-10-27-01: 모험의 서 지우기·기록 깨짐 메시지를 한글로

메뉴에 남은 일본어 메시지 셋(지우기 확인 `1CE`, 지운 뒤 `1CF`, 기록 깨짐 `1D0`)을 한글로 바꿨습니다. 보행 모드 메시지 3,200개를 새 허프만 트리로 다시 부호화해 빈 뱅크 `65`~ 로 옮기고, 비워진 원래 메시지 자리에 한글 2,401자를 넣었습니다. 결과는 [메뉴 한글화](../docs/dq4-menu-format.md#메뉴-메시지)에 반영합니다.

![MesenCE 화면의 메시지 창 셋. 위부터 지우기 확인, 지운 뒤, 기록 깨짐](../images/dq4-menu-messages.webp)

## 1. 원문과 제어 코드

DQ5 트랙의 `dq5text.py` 로 메뉴 롬에서 세 메시지를 풀었습니다.

```
1CE {1006}ぼうけんのしょ{1004}を　消します。\nいいですか？{end}
1CF {1006}ぼうけんのしょ{1004}を　消しました。{end}
1D0 {1006}まことに　ざんねんですが\nぼうけんのしょ{1004}は\n消えてしまいました。{end}
```

`{1004}` 는 칸 번호입니다. 1·2·3 은 「일을·이를·삼을」 처럼 조사가 바뀌므로, 「모험의 서 1번을」 처럼 「번」 을 붙여 조사를 하나로 정했습니다. FC DQ4 의 같은 문장(그룹 1 「なまえ のぼうけんのしょを けします。いいですか？」)도 함께 봤습니다.

## 2. 무엇이 어디에 있나

DQ5 트랙의 `retree` 는 2MB 롬의 뱅크 `30` 에 디코더 사본·트리·메시지를 두는 실험이었습니다. 지금 4MB 통합 롬의 뱅크 `30` 에는 타이틀·서곡·이름 입력 코드가 있어 그대로 쓸 수 없습니다. 빌드 롬을 32KB 마다 훑어 0 으로만 찬 뱅크를 찾았습니다.

```
40~5F, 65~6F, 71~7F 가 빔. 60 메뉴, 61 이름 표, 62~64 이름 글리프, 70 서곡 재배치 표
```

소리 이식 작업 트리가 `72`~`7D` 를 쓰므로 `65`~`69` 를 골랐습니다.

다음은 원래 메시지의 끝입니다. 마지막 메시지 `C7F` 를 끝까지 풀자 마지막 비트가 `0C:8020` 에 있었습니다. 전투 메시지 색인 `24:AECD` 는 `07:8000`~`07:97E3` 을 가리켜, 보행 메시지 자리 `07:D77C`~`0C:8020` 과 겹치지 않았습니다. 빌드 롬의 뱅크 `07`~`0C`·`24` 는 원본 DQ5 와 바이트째 같았습니다.

## 3. 디코더는 어느 뱅크에 둬도 되나

인계 메모에는 디코더와 트리를 낮은 WRAM 거울이 있는 뱅크(`00`~`3F`)에 둬야 한다고 적혀 있었습니다. `24:9E02`~`9E46` 을 디스어셈블하니 `PHK`·`PLB` 로 데이터 뱅크를 자기 뱅크로 두고, 직접 페이지 `$F0`~`$F4`(메시지 포인터·비트)와 자기 뱅크의 마스크·트리만 읽었습니다. 직접 페이지는 데이터 뱅크와 상관없이 뱅크 `00` 이므로 `65` 에 둬도 됩니다.

거울이 필요한 쪽은 글자 그림입니다. `24:A6C1`~ 은 묶음 주소에 비트 위치 >> 3 을 더한 24비트 값의 뱅크 바이트를 `PLB` 로 데이터 뱅크로 삼고, 그 상태로 `$0E29` 같은 낮은 WRAM 을 절대 주소로 읽습니다. 묶음 `+4` 의 뱅크가 `07` + 2비트인 것도 이 때문이라 보입니다.

## 4. 글자 묶음은 뱅크를 넘지 않게

같은 루틴은 더하기의 올림이 뱅크 바이트로 넘어가도 주소를 `8000` 으로 고치지 않습니다. 묶음이 뱅크 끝을 넘으면 다음 뱅크의 `0000`~ 를 읽게 됩니다. 그래서 묶음을 한 뱅크 안에 두고, 넘치면 다음 뱅크 `8000` 에서 새 묶음을 엽니다. 한 줄을 3바이트로 읽으므로 끝 뒤 2바이트도 같은 뱅크여야 합니다.

```
글자 묶음 628자 12×11 07D77C, 1775자 12×11 088000, 1자 4×11 08F268, 1자 6×11 08F26E
```

글자 번호는 이름 입력 글리프와 같게 `3DB` + n 으로 했습니다. 게임 안에서 이름을 찍을 때 같은 번호를 쓰려는 것입니다.

글자 높이는 묶음마다 다르고, 그리는 쪽이 `20 − 2×높이 − 6` 바이트만큼 내려 13줄 칸의 아래에 맞춥니다. 가나 ぼ 는 11줄, 한자 消 는 13줄이었습니다. Galmuri11 한글은 11줄이라 높이 11 묶음으로 두면 가나와 바닥이 같습니다.

## 5. 빌드와 다시 풀기

`dq4menumsg.py` 가 `dq4menupatch.py build` 의 마지막에 돕니다.

```
잎 1018, 노드 1017, 최장 부호 17비트, 메시지 141315바이트 658000~(머리 4415바이트)
```

빌드는 새 롬만으로 3,200개를 다시 풀어(디코더 사본의 표 주소, 새 색인, `OR 60`) 바꾸려던 셋을 뺀 나머지가 원래 코드와 같고 셋은 새 코드인지 확인합니다.

## 6. MesenCE 로 확인

칸 셋이 찬 SRAM 으로 메뉴에 들어가 「모험의 서를 지운다」 → 칸 1 → 예를 골랐습니다. 메시지 진입 `24:8BAF` 의 A 가 976프레임 `1CE`, 1,273프레임 `1CF` 였고 화면이 한글이었습니다. 「아니요」 를 고르면 `1CF` 없이 기록이 그대로였습니다. B 로 메시지를 닫은 뒤의 SRAM 머리와 칸 1 은 메시지 패치 전 빌드와 같았습니다.

칸 2 의 금화 바이트 하나를 뒤집은 SRAM 으로 켜자 695프레임에 `1D0` 이 「모험의 서 2번이」 로 떴습니다.

묶음 경계를 보려고 `1CE` 만 땝·땟(뱅크 `07` 끝)·땠(`08` 첫)·전각 공백(마지막)·`.`·`?` 로 바꾼 시험 빌드도 띄웠습니다. 모두 제 모양이었습니다.

회귀로는 선실 세이브스테이트의 파파스 대화(메시지 `742`) 화면 8장이 패치 전과 같았고, 이름 조합 검사와 커서 입력 52개 검사가 모두 통과했습니다.

## 틀렸던 것들

- 이어하기 화면을 패치 전과 견주다 1,120·1,140·1,600프레임이 달라 메시지 패치가 맵 페이드인을 늦춘다고 의심했습니다. 그 사이 디코더(`24:9E02`·`65:8000`)는 한 번도 불리지 않았고, 패치 전 롬끼리 두 번 돌려도 같은 프레임이 달랐습니다. 실행마다 달라지는 구간이었습니다.
- 처음에는 `1CF` 가 뜬 채로 `70:000E` 를 덤프해 지운 뒤에도 `07` 로 보였습니다. 같은 입력에 B 로 메시지를 닫는 입력을 더하자 패치 전·후 롬 모두 `06` 이 됐습니다. 기록은 메시지를 닫은 뒤에 지워집니다.

## 남은 것

- 원래 보행 메시지 자리를 색인 밖에서 읽는 코드가 있는지(실행한 장면에서는 없었음), 글자 그림 뒤 `08:F277`~`0C:8020` 의 쓰임
- 게임 안 메시지·상태 창의 한글 이름 표시와 기존 가나 이름의 구분
