# 2026-11-06-08: 2장 ルーラ 칸과 기록한 교회로 돌아가기

2장 마을 テンペ·フレノール·사막의 바자를 ルーラ 목록에 넣고, 2장 교회에서 기록하고 이어 하거나 전멸했을 때 그 교회로 돌아오게 했습니다. 넣다 보니 DQ5 엔진이 칸을 그룹으로만 알아서, 한 그룹을 나눠 쓰는 2장 마을이 모두 サントハイム·サラン 으로 가는 문제가 저장·전멸까지 이어져 있었습니다. 결과는 [그룹을 나눠 쓰는 칸](../docs/dq4-field-format.md#그룹을-나눠-쓰는-칸)과 [조우 「2장」](../docs/dq4-field-format.md#2장)에 있습니다.

## 1. 칸은 그룹이다

FC ルーラ 목적지 표(`dq4field.py places`)에서 2장 몫은 サントハイム(`02`)·エンドール(`05`)·사막의 바자(`0D`)·テンペ(`0F`)·フレノール(`10`)입니다. サラン 은 목적지가 아닙니다. 앞의 둘은 이미 칸이 있고, 나머지 셋은 각자 DQ5 그룹의 첫 FC 그룹이 아닙니다(テンペ·フレノール 은 `3D` 의 둘째·셋째, 바자는 `45` 의 둘째).

DQ5 코드를 읽으니 「칸 → 그룹」 이 일곱 곳에 있었습니다.

```
11:826A  JSL 1E:E54F   ; ルーラ·キメラ: 칸 → 목록 그룹 → 그 그룹 첫 입구 행에 내림
01:8EB2  JSL 06:D3ED   ; 맵에 들어설 때: 그룹이 앞 17칸에 있으면 그 칸 비트, 7E:2193 = 그룹
11:8CBF  JSL 23:E452   ; キメラのつばさ: 7E:2193 그룹 → 첫 칸
1E:E4AE  JSL 23:E452   ; ルーラ 뒤 배: 내린 그룹 → 첫 칸의 (dx, dy)
25:8365  LDA $BC ...   ; 저장: 지금 그룹 → 첫 칸을 7E:2033 에
25:82A9 / 01:89A3      ; 이어 하기·전멸: 칸 → 그룹 → 다시 시작 자리 표의 첫 항목
```

칸을 목록에 더하기만 하면 텐페를 골라도 サントハイム 에 내리고, 텐페에 들어가도 サントハイム 칸이 켜지고, 텐페 교회에서 기록해도 サントハイム 교회에서 이어 하게 됩니다. 그래서 칸 넷(12 テンペ, 13 フレノール, 14 바자, 15 サラン)을 목록 뒤에 붙이고, 일곱 곳을 표 셋(맵 → 칸, 칸 → 내리는 칸, 칸 → 교회 맵)으로 바꾸는 훅을 `5B:BC00` 에 넣었습니다(`dq4fieldtravel.hook_code`). キメラのつばさ 가 읽는 마지막 마을 `7E:2193` 에는 `80` + 칸을 씁니다. 이 바이트를 읽는 코드는 `11:8CBB` 하나이고, 그룹 번호에는 bit7 이 없습니다.

サラン 은 목적지가 아니지만 FC 귀환 자리 표(`1E:$A76D`)에 교회가 있습니다. DQ5 는 이어 할 자리를 칸 번호로 저장하므로, 다녀온 비트를 켜지 않는(목록에 나오지 않는) 칸을 줍니다. 탑·동굴은 칸 `FF` 로 두어 들어가도 サラン 칸이 켜지지 않게 했습니다.

새 칸은 FC 차례 사이에 끼우지 않았습니다. 칸 번호가 다녀온 비트이자 기록 속 `7E:2033` 이라, 앞 칸을 밀면 1장 배포판으로 한 기록이 다른 마을을 가리킵니다.

## 2. 해석기로 훅을 고정하고 게임에서 걷기

훅 여덟 개는 `w65816` 해석기가 빈 롬 위에서 돌리는 단위 테스트로 고정했습니다(`test_dq4fieldtravel.HookTest`). 예를 들어 `$BD` 의 위 3비트를 버리는지, 전멸 쪽이 칸 바이트의 밤 비트를 지우는지 봅니다.

2장 롬에서 `dq4fieldtravelcheck.py` 75장면이 통과했습니다.

```
ruler-12/13/14   (142,116) (192,82) (128,148)   FC 목적지 블록의 왼쪽 위 칸
visit-12/13/14   3D/03 3D/04 45/05  비트 001000 002000 004000, 7E:2193 8C 8D 8E
visit-15/2E/39   45/00 45/09 45/0D  비트 0, 7E:2193 그대로
ship-12          배 (98,109), 저어 나감
```

## 3. 전멸하면 어디로: FC·NDS 를 재다

1장 문서에는 「1장 롬은 마지막에 들어간 마을의 교회, FC 는 기록한 교회로 보이나 재지 않음」 이라고 남아 있었습니다. FC 를 쟀습니다. `fc/dq4/tools/lua/wipeplace.lua` 가 1장 필드 세이브스테이트에서 `$6290`(귀환 자리 번호)만 바꾸고 ライアン HP 를 1 로 두어 싸우게 합니다.

```
$6290 = 02 (그대로)  → 02/00 (05,16) バトランド 교회
$6290 = 0B           → 0E/00 (0C,19) テンペ 교회
$6290 = 12           → 16/00 (0E,06)
```

마지막에 들어간 곳과 상관없이 기록한 교회였습니다. NDS 도 desmume libretro 로 2장 프리셋 「テンペの村到着」·「サランの町到着」에서 さえずりの塔 으로 옮겨 전멸시키니, 둘 다 サラン 교회에 アリーナ 만 섰습니다(FC 2장 시작 귀환 자리 `10` 이 サラン). 마지막 마을로 가는 것은 DQ5 뿐이라, 사용자가 FC·NDS 쪽을 골랐습니다.

그래서 `01:899F`(그룹 `$195E` → 칸)를 기록한 칸 `7E:2033` 을 돌려주는 훅으로 바꿨습니다. 아직 기록하지 않은 새 게임 값 `16` 은 バトランド 칸(FC 1장 시작 귀환 자리)입니다. 1장 끝에서 2장으로 넘길 때는 `7E:2033` 을 サラン 칸으로 둡니다. 그러지 않으면 1장에서 기록한 イムル 칸이 남아, 2장에 전멸하면 1장 마을로 돌아갑니다.

`dq4fieldsavecheck.py` 결과입니다.

```
wipe  2033=0C → 3D/03 (24,51)   0D → 3D/04 (14,47)   0F → 45/02 (8,19)
      01 → 3D/00 (54,21)        07 → 37/00 (50,9)    16 → 36/00 (10,45)
transfer  1장 끝 2033=07 → 2장 시작 0F
continue  snes9x·bsnes, 칸 1·12·13·15, 2장 flag·크리프트·브라이 그대로, 422~440프레임
save      텐페 교회로 이어 한 뒤 2033=07 → 신부에게 기록 → 2033·기록 칸 0C
```

## 4. 조우와 몬스터

FC 구역 지도는 1·2·4장이 같고 장 안에서 바뀌지 않으므로, 2장 필드는 이미 옮긴 격자 그대로입니다. 2장 무대의 구역 `07`·`0A`·`0B`·`0C` 를 필드 조우 검사에, 탑·동굴을 던전 조우 검사에 더했습니다(2장 롬에서 39장면, 던전 여섯 장면 통과).

몬스터는 아직 DQ5 몬스터를 빌립니다. DQ4 몬스터를 옮길 때를 위해 FC 레코드를 DQ5 몬스터 표 비트 수와 견줬습니다(`dq4fieldencounter.monster_fit`). 195종 모두 들어가고, 수비 1023 인 메탈 셋은 DQ5 `1FF`(게임이 `7FF` 로 읽음)로 받습니다. 드롭 확률 등급은 FC·DQ5 가 같았습니다(1·8·16·32·64·128·256·4096 분의 1). 2장 몬스터 33종의 드롭 가운데 てつのつめ·はねぼうし·きんのかみかざり 는 DQ5 에 같은 이름의 물건이 없습니다.

## 틀렸던 것들

- 처음에는 キメラのつばさ 가 칸을 기억해야 해서 저장되는 빈 바이트를 찾으려 했습니다. 빈 자리가 없었고, `7E:2193` 을 읽는 곳이 하나뿐이라 bit7 표시로 끝냈습니다.
- 저장 장면을 MesenCE 로 텐페 신부 앞에 순간이동해 돌렸더니 명령 창 제목만 뜨고 기록이 되지 않았습니다. 1장 바트랜드 교회에서도 본 일이라, libretro 로 텐페 교회에 이어 한 뒤 기록하는 장면으로 바꿨습니다.
- 동굴 조우 장면을 위아래로 걸게 했더니, 도착 칸이 필드로 나가는 계단이라 드나들다 마지막 방문에 걸음이 없어 곡 검사가 실패했습니다. 좌우로 걷고 끝에 안쪽 걸음을 두었습니다.
