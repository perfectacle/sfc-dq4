# 2026-10-31-07: 게임 안 창에서 방향키 겹침 고치기

필드 명령 창에서 「작전」에 커서를 두고 위와 왼쪽을 함께 누르면 위로 두 칸, 왼쪽으로 한 칸을 움직였습니다. 원작 DQ5 도 그렇습니다. 이름 입력 자모판에만 걸어 둔 방향 처리를 모든 창으로 넓혀, 겹쳐 눌러도 한 칸씩만 움직이게 했습니다. 결과는 [조합형 이름 입력](../docs/dq4-name-entry-format.md#방향-처리)에 반영합니다.

## 1. 원래 선택 고리

창 선택 고리 `04:CB29` 는 입력 대기 `04:D1DE` 뒤에 위(`CB5A`)·아래(`CC0E`)·왼쪽(`CC2F`)·오른쪽(`CC5C`) 검사를 차례로 부릅니다. 각 검사는 `$24` 에 자기 방향 비트가 있으면 한 칸 움직이고, 반복 처리 `04:D222` 가 `$0B4C` 를 켜는 동안 되풀이합니다. `04:D222` 는 `$24` 가 조금이라도 바뀌면 새 입력으로 보고 `$0B4C` 를 켭니다.

그래서 위를 누른 채 왼쪽을 더하면 `$24` 가 `08` 에서 `0A` 로 바뀌고, 위 검사가 그 값을 다시 보아 한 칸 더 갑니다. 그 뒤 왼쪽 검사가 한 칸 움직입니다. 이름 입력 일지([2026-10-26-40](2026-10-26-40-name-cursor.md))에서 자모판만 고친 같은 문제였습니다. 도구 목록·하위 창과 수량 고르기(`04:CA0F`)도 같은 `D1DE`·`D222` 를 부릅니다.

## 2. 같은 처리를 모든 창으로

자모판 훅 `NePollHook`·`NeRepeatHook` 은 「메뉴 표시가 `A5` 이고 이름 입력 중」일 때만 새 처리로 갔습니다. 이 조건을 없애고, Start 로 「끝」에 가기와 자모판 이웃 표 이동만 그 조건에 남겼습니다.

입력 상태 여덟 바이트는 `7F:F073`~ 에 있었습니다. 게임 안에서는 `7F` 뱅크 아래 반을 세계 지도가 쓰고, 이 자리가 게임 안에서 비어 있는지 잰 적이 없습니다. DQ5 가 쓰지 않는다고 적어 둔 `7E:1BBE`~ 79바이트 가운데 `7E:1BE0`~`1BE7` 로 옮겼습니다. 앞쪽 `1BC0`~`1BCF` 는 조사·서장·1장 이벤트가 쓰고, `1BFF`~`1C0C` 는 DQ5 그룹 14 의 바위 자리(`03:8030`)입니다(리뷰에서 찾음). 훅은 DB = 04 라 짧은 주소로 낮은 WRAM 거울을 읽습니다.

원래 반복 대기는 `$0AEA` bit7 이면 한 프레임, bit6 이고 `$0A50` 이 `4`~`6` 이면 한 프레임, `7` 이상이면 세 프레임 줄입니다. 반복하면 `$0ADA` 를 `FF` 로 두는데, 좌우 끝에서 돌아가지 않는 창(`04:C9C4`)이 그 bit7 을 봅니다. 새 처리도 같게 했습니다. 첫 반복은 자모판처럼 16프레임이라 원래(17프레임)보다 한 프레임 빠릅니다.

## 3. 맨 윗줄에서 아래 끝으로 돌아감

넓힌 첫 빌드에서 위와 왼쪽을 30프레임 함께 누르니, 맨 윗줄에 닿은 뒤 8프레임 만에 아래 끝으로 돌아갔습니다.

```
원래   340: 5→3   357: 3→1
새 빌드 340: 5→3   356: 3→1   364: 1→7
```

위 이동 루틴 `04:D584` 는 맨 윗줄에 닿으면 `04:D1FA` 에서 방향이 바뀔 때까지 기다립니다. 이 고리는 걸러지지 않은 `$24`(`0A`)를 걸러 쓴 `$0ADB`(`08`)와 견주어 곧바로 빠져나갔습니다. 대기 고리 `04:D209` 도 같은 표본으로 돌렸습니다.

## 4. 끝 칸 대기에서 사라진 새 누름

그다음 「왼쪽을 누르고 2프레임 뒤 위」 사례에서 위가 움직이지 않았습니다. 왼쪽 끝 칸 대기가 위를 새 누름으로 보고 빠져나왔지만, 이어지는 반복 처리는 같은 프레임에 다시 표본을 떠 위를 「계속 누른 방향」으로 보았습니다. 대기에서 새 누름으로 빠져나올 때는 그 방향을 지난 패드 값에서 빼 두어, 반복 처리가 다시 새 누름으로 보게 했습니다.

## 5. 롬 자리

루틴이 늘어 1장 빌드가 「`0x182900`: 그룹 빌드 자리에 다른 자료가 있음」으로 멈췄습니다. `30:A900`~ 은 1장 레코드 자리입니다. 입력 상태를 긴 주소 대신 짧은 주소로 읽어 줄였고, 끝을 `30:A8F7` 까지로 맞췄습니다. 루틴의 `assert` 도 실제 한계 `30:A900` 으로 바꿨습니다.

## 6. 확인

`dq4menucursorcheck.py` 는 1장 롬을 전원부터 켜 명령 창 「작전」(색인 5, 행 × 2 + 열)에서 방향키를 누릅니다. 프레임은 첫 누름 기준입니다.

| 사례 | 원래 롬 | 새 롬 |
| --- | --- | --- |
| 위·왼쪽 동시 3프레임 | 3 | 3 |
| 위·왼쪽 동시 30프레임 | 3, 1(17) | 3, 1(16) |
| 위, 2프레임 뒤 왼쪽 | 3, 1, 0 | 3, 2 |
| 왼쪽, 2프레임 뒤 위 | 4, 2, 0 | 4, 2 |
| 위·왼쪽 동시, 위 먼저 뗌 | 3, 2 | 3 |
| 한 프레임씩 위·왼쪽 | 3, 2 | 3, 2 |
| 위 60프레임 | 3, 1(17) | 3, 1(16) |

새 롬은 10개 사례가 모두 통과했습니다. 도구 창과 「어떻게 할까」 하위 창에서도 원래 롬과 같은 위치로 움직였습니다. 자모판 방향·Start 52개, 조합·삭제·새 게임 이름 검사도 다시 통과했습니다.

## 7. 전투·상점 창

PR 뒤에 전투와 상점도 쟀습니다. 둘 다 같은 입력 대기 `04:D1DE` 를 지납니다.

- 상점: 1장 마을(36/00) 도구점 앞 칸(48,45)으로 `dq5warp.lua` 로 옮겨 말을 걸고 かう 로 품목 창 `3A`(약초·해독초·성수, 한 줄)를 열었습니다. `04:D1DE`·`D222`·`D209` 를 모두 지났습니다. 위+왼쪽은 맨 위에서 맨 아래로 한 칸, 아래+오른쪽은 맨 아래에서 맨 위로 한 칸, 위+왼쪽 30프레임은 맨 위에서 멈췄습니다.
- 전투: 필드 조우 검사(`dq4fieldencountercheck.py`)의 「성 근처 구역 + 조우율 FF」로 걸어 전투를 붙였습니다. 조우가 무작위라, 명령 창 `1B` 가 처음 `04:D1DE` 에 들어온 프레임부터 입력을 넣었습니다. 싸우기/도망 창에서 아래+오른쪽 → 1, 위+왼쪽 → 0, 아래+왼쪽 → 1, 위+왼쪽 40프레임 → 0 에서 멈춤. 「싸우기」 뒤 공격/방어/도구 창에서 아래+오른쪽 30프레임 → 1, 17프레임 뒤 2, 맨 아래에서 멈춤. 위+오른쪽·아래·위+왼쪽도 한 칸씩이었습니다.

이번에 연 전투·상점 창은 모두 한 줄이라, 원래 루틴도 좌우 검사(`04:CC2F`·`CC5C`)가 열 수 1 이면 건너뜁니다. 겹침으로 두 칸 가는 일은 두 줄 넘는 창(필드 명령 창 등)에서만 생깁니다. 이 실측은 넓힌 처리가 한 줄 창을 깨지 않는다는 확인입니다.

같은 프레임 안에서 `$0AD7` 이 `0→2→0→2` 처럼 여러 번 바뀌는 것은 이동 루틴이 빈칸을 찾으며 임시로 쓰는 값이고, 프레임 끝 값만 봤습니다.
