# 2026-11-03-05: 창 글자 패치가 깨던 BG3 타일맵과 전투 배경 고치기

[02번 일지](2026-11-03-02-song-bg3-checks.md)에서 BG3 자리 검사의 알려진 실패로 둔 다섯 맵을 고쳤습니다. 둘 다 창 글자 패치(`dq4windowname`)의 원인이었고, 1장 롬에서는 재현되지 않지만 같은 꼴의 맵을 옮기면 터지는 것이었습니다. `1E/00`·`20/06`·`32/00` 은 창 글자 변수가 DQ5 의 움직이는 타일 사본 자리에 있어 맵에 들어가자마자 덮였고, `00/0A`·`04/0B` 는 공통 NMI 입구에 건 받침이 전투 배경 그림 DMA 를 VBlank 밖으로 밀었습니다. 결과는 [창 글자 변수 자리](../docs/dq4-window-text-format.md#창-글자-변수-자리2026-11-03)와 [NMI 작업마다 걸기](../docs/dq4-window-text-format.md#nmi-작업마다-걸기2026-11-03)에 반영했습니다.

## 1. `1E/00` 에서 누가 `7E:3D14`~ 를 쓰나

창 이름 대기열(`7E:3EB0`~)과 그 변수(`7E:3D14`~`3E9F`)는 「11개 장면에서 접근 없음」 으로 고른 자리였습니다. `menu.sfc` 로 `1E/00` 에 순간이동하며 `7E:3D00`~`3FFF` 쓰기를 PC 별로 모았습니다(WRAM 오프셋에 건 쓰기 감시).

```text
03D3E1 map=1E/00 first=315 last=315 count=352 lo=7E3D14 hi=7E3E73
60D90A map=1E/00 first=400 ...                  (우리 코드)
```

`03:D3E1` 은 DQ5 의 [움직이는 타일](../../dq5/docs/dq5-graphics-format.md#실내-맵의-움직이는-타일)을 맵에 들어갈 때 채우는 루틴 안입니다. 종류 14 의 원본 자리(`03:D9A0` + 28)가 `7E:3D14`, 11칸 × 32 = 352바이트로 `7E:3D14`~`3E73` 과 딱 맞습니다. 대기열 항목 수(`7E:3D62`)와 읽을 자리(`7E:3D5C`)가 이 안이라, 명령 창을 열어 NMI 가 대기열을 보낼 때 덮인 값으로 엉뚱한 머리를 읽고 VRAM `3CB4` 에 썼습니다.

## 2. 원본 DQ5 도 같은 자리를 쓰나

원본 DQ5 롬과 원래 배 선실 상태로 같은 감시를 돌렸습니다.

```text
03D3E1 map=1E/00 first=325 last=325 count=352 lo=7E3D14 hi=7E3E73
```

원본도 같은 352바이트를 씁니다. 롬 표(`03:D82E` 맵 목록, `03:D806` 종류 마스크)로 종류 14 를 쓰는 맵을 세니 `1E/00`·`20/06`·`03/01`·`03/02`·`04/00`·`0D/00`·`31/00`·`32/00`·`34/00`·`35/03` 열이었습니다. 원본 DQ5 와 `menu.sfc` 의 표가 같습니다. 2장 이후 이 맵들을 옮기면 같은 일이 납니다.

## 3. 변수 옮기기

변수 블록(`7E:3D14`~`3E9F`, `!wn_stage` 포함 396바이트)을 `7E:A930`~`AABB` 로 옮겼습니다. `7E:A921`~`ABFF` 는 DQ5 장면 770개에서 원래 코드의 접근이 없던 자리이고, 앞의 `A5F1`~`A924` 는 전투 글 엔진이 씁니다. 대기열 `7E:3EB0`~ 와 `!wt_fixkeys`(`7E:3EA0`)는 사본 밖이라 두었습니다. 창 검사(`dq4windowcheck.py`)가 덤프하는 키·나이·가나 첫 칸은 이제 asm 의 정의를 읽습니다.

고친 롬에서 `7E:A925`~`ABFF` 쓰기를 여섯 맵(`00/0A`·`04/0B`·`1E/00`·`20/06`·`32/00`·`01/00`)에서 감시하니 모두 뱅크 `60`(창 글자 코드)이었습니다.

## 4. 전투 배경 검은 칸: WRAM 은 같은데 VRAM 만 다르다

`00/0A` 도착 뒤 전투에서 BG1 타일 `256`(VRAM 워드 `4560`~)으로 가는 DMA 를 찾았습니다. 두 롬 모두 487 프레임에 `00:FD6D` 가 `7E:6000` 에서 `0B00` 바이트를 VRAM `4000` 으로 보냈습니다. 그런데 보낸 뒤 VRAM 합이 달랐습니다.

거꾸로 원본을 따라갔습니다. `7E:6000` 은 `22:875B` 가 타일 풀 `7E:4000`~ 에서 MVN 으로 모으고, 풀은 `22:9C75` 등의 고리가 짭니다. 두 롬의 WRAM 을 프레임마다 견주니 487 프레임 끝에 `7E:6000`~`6AFF` 가 같았고, `22:9C75` 고리의 A·X·Y 차례(210번)도 같았습니다. WRAM 이 같으니 DMA 자체가 덜 간 것입니다.

`$420B` 쓰기에 주사선과 `hClock` 을 함께 적었습니다.

```text
overture.sfc  f487 sl=244 h=132  exec 00887C
              f487 sl=244 h=1112 dma ch7 vram=4000 size=0B00
              f487 sl=261 h=1270 exec 00FD6F
menu.sfc      f487 sl=244 h=120  exec 00887C
              f487 sl=244 h=646  exec 00FFA5
              f487 sl=245 h=222  dma ch7 vram=4000 size=0B00
              f487 sl=0   h=372  exec 00FD6F
```

공통 입구 `00:887C` 에서 받침을 지나 `JMP ($1944)` 로 가기까지 526 마스터 클럭이 들었습니다. 대기열이 비어 있어도 `JMP $FFA1` / `JML` / `JSR WhWith` / 다섯 바이트 확인을 느린 롬에서 돕니다. 원래는 주사선 261 의 1270 에 끝나 VBlank 끝까지 94 마스터 클럭 남는데, 그만큼 밀리자 끝이 다음 프레임 주사선 0 으로 넘어가 꼬리 약 46바이트가 버려졌습니다. `4000` 과 `4580` 으로 가는 두 NMI 의 꼬리가 타일 `256`·`257`·`2AF` 자리입니다.

원본 DQ5 도 같은 장면에서 261 / 1244~1264 에 끝났습니다. 원래부터 여유가 100 마스터 클럭 남짓이라, 공통 입구에는 바이트 하나를 읽는 확인(약 78 마스터 클럭)도 넣기 어렵습니다.

## 5. 작업마다 걸기

`$1944` 에 넣는 곳은 `00:87FA`(필드 `8926`·전투 `8952`)·`00:8809`(`FF9A`)·`00:8818`(카지노 슬롯 `FEDD`) 셋입니다. 공통 입구 `00:887C` 는 원래 `JMP ($1944)` 로 두고, 작업마다 게임 전송 앞에 `JSL WqNmiEntry` 를 넣었습니다.

| 작업 | 건 자리 |
| --- | --- |
| 필드 | `00:87F2` 가 `$1944` 에 넣는 값을 받침 `00:FF9E`(`JSL WqNmiEntry` / `JMP $8926`)로 |
| 전투 보통 길 | `00:896F` 를 `JSL WqNmiEntry` / `JSR $8C1E` / `BRA $8960`(뒤 셋 부름은 큰 그림 길과 같음) |
| 전투 큰 그림 길 | 걸지 않음. 이 NMI 는 게임 전송 목록·창 타일맵을 보내지 않음 |
| `FF9A` | `JML WqNmiFF9A` 로 통째로 |
| 카지노 | 첫 부름 `00:FF08` 의 두 명령을 `JSL WqNmiSlot` 으로 |

고친 롬은 같은 DMA 가 244 / 1112 에 시작해 261 / 1270 에 끝나 `overture.sfc` 와 같았습니다.

## 6. 고치기 전 롬과 고친 롬

`dq4bg3slotcheck.py` 를 `--known` 없이 다섯 맵에 돌렸습니다.

| 롬 | 결과 |
| --- | --- |
| 고치기 전 `menu.sfc` | 다섯 모두 실패. `00/0A`·`04/0B` 는 화면 VRAM `456E`~`457F`·`4AF0`~`4AFF`, `1E/00`·`20/06`·`32/00` 은 `vsbuf` 1155·1195·1024 |
| 고친 `menu.sfc` | 가드 15맵 모두 통과 |

가드 `dq4-bg3-slot` 의 `--known` 에서 다섯 맵을 뺐습니다.

## 7. 재발 방지

- `test_dq4windowname.py` `WramTest`: asm 의 창 글자 변수가 `7E:3D14`~`3E73`(종류 14 사본)에 들지 않음, 옮긴 블록이 전투 글 엔진 뒤 `7E:AC00` 앞에 있음. `NmiHookTest`: `00:887C` 와 `00:8952`~`896E`(큰 그림 길)에 `org` 가 없음. 고치기 전 asm 으로 돌리면 세 시험이 모두 실패합니다.
- `dq4windowname.py` 가 작업마다 건 자리의 원래 바이트(`NMI_SITES`)를 확인합니다.
- 가드 `dq4-bg3-slot` 은 알려진 실패 없이 15맵.

## 틀렸던 것들

- 받침을 처음에 `00:FFA1` 에 그대로 두려 했습니다. `00:FFA1` 은 `00:FF9E` 의 `JML $00888F` 의 뱅크 바이트였습니다. 옛 받침도 이 바이트를 `5C` 로 덮어 `FF9A` 작업이 `5C:888F` 로 뛰고 있었습니다. 원래 바이트가 `00` 이라 빈 자리 검사에 걸리지 않았습니다.
- 처음 고친 롬에서 순간이동 뒤 필드가 깨졌습니다(맵 `7C/03`). 그 롬에는 위 받침 자리 문제(`FF9A` 작업이 `22:888F` 로 뜀)와, `BRA $8960` 을 asar 가 `80 60`(거리 `60`, `00:89D8` 로 감)으로 낸 문제가 함께 있었습니다. 둘을 고치자 사라졌고, 어느 쪽이 그 장면을 깨뜨렸는지는 가르지 않았습니다. 이 asar 는 `BRA $주소` 를 거리로 바꾸지 않아 바이트로 씁니다.
- 전투 배경 그림을 짜는 고리의 실행 수가 191·192 로 달라 보였던 것은 프로브가 30 프레임마다만 기록을 덮어써 마지막 프레임을 빼먹은 탓이었습니다.

## 남은 것

- 종류 14 맵 열 가운데 실내 364맵 검사에서 셋만 깨진 까닭. 다른 일곱에서 그때 대기열이 비어 있었는지.
- `FF9A` 작업(`03:A211`)과 카지노 슬롯 작업을 실제로 띄워 걸린 받침 확인. `FF9A` 가 어느 장면인지.
- 전투 큰 그림 길의 NMI 에는 대기열을 보내지 않으므로, 전투 들어갈 때 대기열·가나 칸 되돌리기가 몇 NMI 늦어지는지.
