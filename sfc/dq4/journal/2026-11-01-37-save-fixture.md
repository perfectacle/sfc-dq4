# 2026-11-01-37: 저장 기록으로 검사 시작하기

장면 검사는 지금 서장부터 걷거나(약 1만8천 프레임) 걷기 검사가 남긴 세이브스테이트에서 시작합니다. 세이브스테이트는 에뮬레이터마다 형식이 다르고 롬이 바뀌면 다시 만들어야 합니다. 그래서 DQ5 의 저장 기록(SRAM)을 직접 만들어 넣고 「이어 하기」로 원하는 자리·상태에서 시작하는 `dq4savefixture.py` 를 만들었습니다. 형식은 [저장 기록으로 시작하는 검사](../docs/dq4-savefixture-format.md)에 있습니다.

## 1. 기록 칸을 고쳐도 되나

먼저 바트랜드 교회에서 실제로 기록한 SRAM 을 libretro snes9x 에서 이어 했습니다. 기록 칸은 [DQ5 SRAM 세이브](../../dq5/docs/dq5-data-format.md) 대로 WRAM `7E:2000`~`2A9F` 의 사본이고, 끝 워드가 체크섬입니다. 칸에서 금화·주인공 레벨·HP·셋째 칸 물건·이어 할 자리를 고치고 동료(호이민)와 합류 flag 를 넣은 뒤 체크섬을 다시 맞추자, 고친 값 그대로 이무르 교회 앞에서 시작했습니다. 체크섬을 맞추지 않은 칸은 지워졌습니다.

더 나아가 SRAM 을 맨바닥(0)에서 만들었습니다. 머리 「DRAGON QUEST V」 두 곳, 쓰는 칸 비트 `01`, 상태 `C0`, 칸 1 하나만 두어도 정상으로 이어 했습니다. 이러면 실제로 기록할 필요가 없습니다. 칸의 내용은 새 게임이 약 964프레임에 처음 쓰는 칸을 밑판으로 씁니다.

## 2. 어디에 서나

이어 할 자리는 `7E:2033` 입니다. 아래 7비트가 ルーラ 칸 번호이고, `25:85D5`[칸] 의 그룹을 다시 시작 자리 표 `25:8621` 에서 찾아 그 자리에 섭니다. bit7 은 밤입니다. 1장 롬의 칸 2·7·8 이 바트랜드·이무르·서장 마을이고, 표로 고른 자리에 432~445프레임에 섰습니다.

표에 그룹이 없는 칸(1장 롬의 11·16)은 예상과 달랐습니다. 전멸 뒤 다시 시작처럼 항목 0 으로 가리라 봤는데 필드에 섰습니다. 도구는 이런 칸을 고르면 오류를 냅니다.

## 3. 도착을 어떻게 알아보나

처음에는 불러온 `7E:2000` 블록이 기록 칸과 같아지는 때를 도착으로 봤습니다. 그런데 켤 때 `25:81CF` 가 칸을 맞춰 보며 WRAM 에 미리 불러, 아직 타이틀인 516프레임 무렵 블록이 거짓으로 같아졌습니다. 그래서 맵·주인공 칸(`7E:00BC`·`00BD`·`3020`·`3080`)이 표의 자리와 같아진 첫 프레임을 도착으로 봅니다.

맵에 선 뒤의 WRAM 은 기록 칸과 네 바이트만 달랐습니다. `2193`·`21C7` 은 도착 그룹이고, `21CB`·`21CC` 는 무엇인지 아직 모릅니다.

## 4. bsnes 에 SRAM 넣기

snes9x 는 `retro_get_memory_data(0)` 이 SRAM 포인터를 줍니다. bsnes 115 는 0 을 줍니다. 소스(`target-libretro/libretro.cpp`)를 보니 이 함수가 늘 nullptr 이고, 대신 저장 폴더의 `<롬 이름>.srm` 을 게임을 열 때 읽습니다. 그래서 코어를 열기 전에 파일을 두고, 읽을 때는 직렬화 상태에서 SRAM 이 나오는 오프셋 558 을 씁니다.

한 프로세스에서 bsnes 게임을 세 번째로 열자 넣은 SRAM 이 보이지 않았습니다. 같은 dylib 을 다시 열면 전역 상태를 나눠 쓰는데, 앞 게임을 내리지 않으면 앞 SRAM 이 남았습니다. 다음 코어를 열기 전에 `retro_unload_game` 을 부르자 고쳐졌습니다.

## 5. 확인

`dq4savefixture.py check` 가 두 코어에서 아래를 봅니다. 한 번에 약 6초입니다.

```text
bsnes  passed  도착 433, 밤 0190, 체크섬 틀린 칸 398프레임에 지워짐, WRAM 차이 0, 39/04 순간이동 788
snes9x passed  도착 432, 밤 0190, 체크섬 틀린 칸 398프레임에 지워짐, WRAM 차이 0, 39/04 순간이동 787
```

- (a) 고친 42바이트가 불러온 WRAM 과 같음. 밤 칸은 시각 `0190` 으로 섬
- (b) 체크섬을 1비트 틀린 칸은 타이틀을 넘겨 기록 목록을 고를 때 지워지고 새 게임이 시작함. 켜기만 하고 입력이 없으면 지워지지 않았습니다
- (c) 같은 SRAM·같은 입력 두 번의 WRAM 128KB 가 0바이트 다름
- (d) 이어 한 뒤 `dq4compatcheck.Walker.warp` 로 탑 `39/04` 에 순간이동, 일행·flag·금화 그대로

단위 테스트(`test_dq4savefixture.py`)는 롬 없이 체크섬·칸 배치·머리·금화·flag·자리 쓰기 위치를 합성 바이트로 보고, 1장 롬이 있으면 칸 표를 읽습니다.

## 틀렸던 것들

- 체크섬이 틀린 칸은 켤 때 지워진다고 봤습니다. 입력 없이 300프레임을 돌려도 남아 있었고, 이어 하기 입력으로 기록 목록에 들어갈 때(398프레임) 지워졌습니다.
- 새 게임 밑판을 「쓰는 칸 비트가 서면 기록됨」 으로 잡으면 켤 때 SRAM 에 남은 값 때문에 곧바로 멈춰 쓰인 칸이 없었습니다. 머리와 체크섬이 맞는 칸이 생길 때로 바꿨습니다.

## 남은 것

- MesenCE 에서 같은 SRAM 으로 이어 하기.
- 표에 없는 그룹의 칸으로 이어 했을 때 필드의 어느 칸에 서는지.
- `7E:21CB`·`21CC` 를 맵에 들어설 때 고쳐 쓰는 까닭.
- 기존 장면 검사를 이 기록으로 시작하게 옮기기.
