# 2026-11-02-07: 창이 뜬 프레임에 이름을 함께 올리기

[창 글자 깨짐 검사 76장면](2026-11-02-06-window-check-76.md)을 통과시킨 뒤에도 매 프레임 재면 남는 것이 둘 있었습니다. 목록 창 타일맵은 화면에 올라왔는데 넘친 이름 그림이 아직 오지 않아 목록 줄이 비는 프레임, 그리고 가게 「누가」 장면의 588·1585~1587프레임입니다. 둘 다 0으로 만들고, 깨짐 검사에 매 프레임 판정(`--every`)과 「빈칸」 규칙을 넣었습니다. 결과는 [창 글자 형식 문서](../docs/dq4-window-text-format.md#창-타일맵과-그림을-한-nmi-에)에 있습니다.

## 1. 매 프레임 검사

깨짐 검사(`dq4windowcheck.py`)는 30프레임마다 재므로 한두 프레임짜리 문제를 놓칩니다. `--every` 를 주면 넘친 이름을 묶음 버퍼로 보내는 세 장면(`talk02-full`·`shopwho`·`partyitems`)을 정한 구간에서 매 프레임 덤프합니다. 새 규칙 「빈칸」 은 필드에서 캔버스 안 슬롯이 화면에 보이는데(키 자리가 그 슬롯 첫 칸) 슬롯 칸 그림이 모두 메시지 캔버스 그대로인 프레임을 겁니다.

```text
고치기 전(main, c0296bd3)
talk02-full  324               빈칸 122
shopwho      588 가나 034, 1479 빈칸 122, 1585~1587 비침 0F0·122
partyitems   314~316, 551~555  빈칸
```

## 2. VBlank 가 239줄 모드였다

NMI 첫머리(`00:885D`)에서 주사선을 재니 늘 240 이었습니다. PPU 상태의 `overscanMode` 가 켜져 있어(화면 239줄) VBlank 는 240~261, 22줄뿐입니다. 그 안에 OAM 544바이트(3줄 남짓)와 게임의 창 타일맵 2KB(12줄)가 들어가고, 게임 타일맵 DMA 는 248 에 시작해 260 에 끝났습니다. 타일맵과 같은 NMI 에 이름 그림을 보낼 자리가 게임 순서대로는 없었습니다. 바뀐 타일맵 줄만 보내는 길도 재 봤지만, 목록 창이 뜨는 프레임에 바뀐 줄이 2~27줄이라 아낄 것이 거의 없었습니다.

## 3. 메시지 창이 없으면 묶지 않는다

`partyitems`(도구 목록)에는 메시지 창이 없습니다. 묶음 버퍼는 메시지 창에 비치지 않게 하려는 것이라, 화면에도 버퍼에도 메시지 창이 그 칸을 가리키지 않으면 묶지 않고 바로 대기열로 올리게 했습니다. 게임이 창 타일맵을 보낼 때마다 버퍼 18~26줄의 메시지 창 테두리를 보고 `7F:830A` 에 적습니다. 551~555 가 없어졌습니다.

처음에는 이 값을 묶음 버퍼 머리를 새로 만들 때 「모름 = 1」 로 두었더니 맵을 불러온 뒤 첫 목록(314~316)은 여전히 묶였습니다. 맵을 불러오면 7F 가 지워져 0 이 되고 창은 타일맵을 보내야 뜨므로, 머리와 상관없이 전송마다 적게 했습니다.

## 4. 타일맵과 그림을 한 NMI 에

메시지 창 위에 뜨는 목록(`talk02-full`·`shopwho`)은 그림을 먼저 보내면 옛 메시지 창에 비치므로 묶어야 합니다. 그래서 타일맵과 그림을 같은 NMI 에 보내되, 게임보다 앞에서 우리가 보내게 했습니다.

| 시도 | 결과 |
| --- | --- |
| 게이트에서 타일맵을 대신 보내고 항목마다 메시지 창이 가리키는지 재며 보냄 | 재는 데 두 줄이 들어 주사선 247 에 닿아 하지 못함 |
| 한 NMI 미루고 NMI 끝에서 미리 재 둔 수만큼 | 타일맵 246 → 257, 그 뒤 항목 하나만 들어감(뱅크 60 이 느린 롬이라 DMA 하나 설정에 700 마스터 클록 남짓) |
| 위 줄 항목을 쌓을 때 두 평면으로 늘리고 DMA 표를 미리 짜 NMI 첫머리에서 보냄 | 타일맵 245.4 → 257, 이름 둘(DMA 넷) 260.9 줄에 끝 |

마지막 판에서 할 일을 짜는 곳은 게임이 창 타일맵을 요청하는 `04:9D39`(`LDA #$0080 / STA $0BEC`)입니다. 게임은 요청한 뒤 바로 NMI 를 기다리므로 버퍼가 그대로입니다(`WhReq`). 여기서 메시지 창이 가리키지 않는 묶음 항목을 예산까지 골라 DMA 표를 짜고, 다음 NMI 첫머리(`WhWith`)가 30줄 타일맵(1920바이트, 화면 밖 30·31줄 빼고)과 그 표를 보냅니다. 미루는 프레임이 없어져 창도 한 프레임 일찍 뜹니다.

처음 이 훅을 `04:9D38` 에 걸었습니다. 그 바이트는 그 루틴의 `PHX` 였고, 여섯 바이트를 덮자 `STA $0BEC` 의 마지막 `0B` 가 `PHD` 로 실행되어 뒤의 `PLX` 가 0 을 받았습니다. 메시지 끝 ▼ 커서가 버퍼 첫 칸(`7E:5000`)에 그려져 화면 왼쪽 위에 타일 `124` 가 비쳤습니다(1478프레임부터). 빌드가 그 자리의 원래 바이트를 확인하게 했습니다(`WH_REQ_ORIG`).

## 5. 「누가」 창이 닫힐 때(1585~1587)

게임은 창을 아래 줄부터 두 줄씩 지우며 닫습니다. 「누가」 창의 「장비 불가」 는 캔버스 슬롯 `122`·`0F0` 에 그려졌는데, 이 슬롯 칸을 메시지 창이 가리키는 자리는 21·23줄이고 이름 줄은 20줄입니다. 그래서 창이 닫히는 동안 아직 보이는 이름과 같은 그림이 드러난 메시지 창 줄에도 보였습니다. 슬롯 표를 바꿔 피할 수는 없었습니다. 캔버스 슬롯은 모두 위 줄 칸 하나 이상이 메시지 창 21줄 아래에 있습니다.

그래서 `WhReq` 가 그림을 올린 캔버스 슬롯마다 메시지 창이 그 칸을 가리키는 버퍼 자리를 찾아(슬롯 키 두 줄은 빼고) 가림 표를 짜고, `WhWith` 가 타일맵 뒤에 VRAM 타일맵의 그 자리만 빈 바탕 칸 `001` 로 씁니다. 게임 버퍼는 그대로 둡니다. 가린 슬롯을 되돌리면(`WtRestoreSlot`·`WqClean`) 다음 NMI 에 버퍼를 다시 보내 가림을 걷습니다.

## 6. 크기가 바뀐 슬롯(588)

588프레임의 「가나」 는 화면이 깨진 것이 아니었습니다. 586~590프레임 동안 VRAM 의 그림과 타일맵은 바이트가 같았습니다. 가게 목록을 다시 그릴 때 같은 자리에 크기가 다른 문구가 오자 `WtAlloc` 이 옛 슬롯을 바로 비웠고, 새 타일맵이 가기 전 한 프레임 동안 화면의 「청동 갑옷」 이 빈 슬롯의 칸이 됐습니다. 그 칸을 다른 문구가 먼저 차지했다면 실제로 깨졌을 자리입니다. 화면에 보이는 슬롯은 남겨 두고 `WtVis` 가 안 보인다고 잰 뒤에 비우게 했습니다(같은 크기의 다른 문구와 같은 처리).

## 7. 결과

```text
매 프레임(--every)       고치기 전                         고친 뒤
talk02-full 60~700        빈칸 1(324)                       0
shopwho 100~1900          빈칸 1, 가나 1, 비침 3            0
partyitems 60~900         빈칸 8                            0
```

## 틀렸던 것들

- 게임 타일맵과 같은 NMI 에 그림을 넣을 VBlank 가 남아 있을 줄 알았습니다. 239줄 모드라 VBlank 가 22줄이고 게임 타일맵만으로 260 줄까지 찼습니다.
- 게이트에서 항목마다 메시지 창을 재면 될 줄 알았습니다. 느린 롬의 코드라 재기만 해도 두 줄이 들었습니다.
- 메시지 창 있음 표시를 모를 때 1 로 두면 안전할 줄 알았습니다. 맵을 불러온 뒤 첫 목록이 늘 묶여 빈칸이 남았습니다.
- 요청 훅을 `04:9D38` 에 걸었습니다. 한 바이트 앞의 `PHX` 를 덮었습니다.
- 588 을 깨짐으로 보았습니다. 화면은 같았고, 슬롯을 너무 일찍 비운 것이었습니다.

## 남은 것

- 위·아래 줄만 보내는 요청(`$40`, `04:9D5E`)에는 가림·함께 보내기를 하지 않음
- 예산을 넘는 묶음 항목은 다음 NMI 로(목록이 길면 그만큼 빈칸이 남을 수 있음), 넘는 가림은 하지 않음(비침이 남을 수 있음). 76장면에는 없었음
- 우리 대기열·캔버스 전송과 겹치거나 NMI 가 늦으면(주사선 245 이상) 함께 보내기를 쉬고 예전처럼 다음 NMI 에 보냄
