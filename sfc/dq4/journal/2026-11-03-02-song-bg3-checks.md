# 2026-11-03-02: 던전 곡과 BG3 자리 검사의 기대 고치기

[08번 일지](2026-11-02-08-fresh-states.md)에서 출발 상태를 옮긴 뒤에도 실패가 남은 검사 둘을 풀었습니다. 던전 조우 검사의 곡 `$1D8B` = `FF` 는 원본 DQ5 도 던전에 들어선 직후 같은 값을 읽어, 게임이 아니라 검사의 기대가 틀렸습니다. BG3 자리 검사는 menu 패치 전후 롬의 화면을 견주어 의도한 한글 창 글자까지 실패로 쳤고, 출발 맵 `17/00` 에는 도착을 알 수 없었습니다. 두 검사 모두 판정을 고쳐 가드로 올렸습니다. 결과는 [던전 조우와 곡](../docs/dq4-chapter1-format.md#들어선-직후의-ff2026-11-03)과 [BG3 타일맵 옮기기](../docs/dq4-window-text-format.md#패치-단계가-다른-롬과-화면을-견주지-않는-판정2026-11-03)에 반영했습니다.

## 1. 던전 곡의 `FF` 는 어디서 나오나

`dq4dungeonencountercheck.py` 에 `--scenes` 를 더해 곡 있는 1장 롬(`dq4-ch1-full.sfc`)의 필드 장면 셋만 돌렸습니다. 고치기 전 판정으로 `39-03-field`·`3A-00-field` 가 실패하고 `38-00-field` 는 통과했습니다. 걸음 기록(`00:82AF`)과 곡 요청(`00:CEA2`)을 순서대로 보면 `FF` 는 들어선 직후에만 있었습니다.

```text
39-03-field  331 곡 요청 0A   409·417·425 걸음 FF   433~545 걸음 0A
3A-00-field  330 곡 요청 09   411 걸음 FF   419~435 걸음 09
             579 곡 요청 09   652 걸음 FF   660 걸음 09   (나갔다 다시, 네 번 같은 꼴)
```

`$1D8B` 는 앞 곡을 정리하는 `1A` 가 `FF` 로 두고 새 곡이 시작할 때 그 번호가 됩니다([DQ5 소리 형식](../../dq5/docs/dq5-sound-format.md)). 필드 곡 `02` 를 정리하고 던전 곡을 보내는 사이의 걸음이 `FF` 를 읽은 것입니다. 곡이 시작한 뒤에 `FF` 로 돌아간 걸음은 없었습니다.

## 2. 원본 DQ5 는 어떤가

같은 기록 도구(`dq5warptrace.lua`, 검사와 같은 `TRACE`·`LOG`, 난수 고정)로 원본 DQ5 롬을 원본 롬으로 만든 선실 상태에서 필드로 옮겨, 곡 `0A`·`09` 를 쓰는 던전에 걸어 들어갔습니다. 입구는 `dq5fieldtables.dump` 의 입구 표에서 곡이 `09`·`0A` 인 그룹을 골랐습니다.

| 롬 | 들어간 곳(곡) | 곡 요청 → 곡 시작 | 시작 전 `FF` 걸음 | 시작 뒤 다른 값 |
| --- | --- | --- | --- | --- |
| 원본 DQ5 | 필드 (189,56) → 탑 `04/00`(`0A`) | 114프레임 | 4 | 0 |
| 원본 DQ5 | 필드 (414,46) → 동굴 `07/02`(`09`), 첫째 | 74프레임 | 0 | 0 |
| 원본 DQ5 | 같은 동굴, 나갔다 다시 | 58프레임 | 2 | 0 |
| 1장 롬 | 필드 → 탑 `39/03`(`0A`) | 102프레임 | 3 | 0 |
| 1장 롬 | 필드 → 동굴 `3A/00`(`09`), 다섯 번 드나듦 | 81~89프레임 | 1씩 | 0 |
| 1장 롬 | 필드 → 동굴 `38/00`(`09`) | 79프레임 | 0 | 0 |

원본 DQ5 도 탑에 들어선 뒤 네 걸음 동안 `FF` 였습니다. 1장 롬은 곡이 끊기지 않았고, 탑은 원본보다 12프레임 일찍 시작했습니다. `38-00-field` 가 통과한 것은 들어서서 첫 걸음까지 시간이 길어 곡이 먼저 시작했기 때문입니다.

## 3. 기대 고치기

검사는 던전 걸음의 곡이 모두 그 곡이기를 바랐습니다. 곡 요청마다 걸음을 나누고, 걸음의 곡이 `FF` 몇 개 뒤 그 곡으로 끝까지 이어지며 어느 걸음에서든 그 곡을 읽어야 통과하게 했습니다(`song_held`). 곡이 시작한 뒤의 `FF`, 다른 곡, 끝까지 `FF` 는 실패입니다. 고친 검사로 곡 있는 롬의 24장면이 모두 통과했습니다.

## 4. BG3 자리 검사가 무엇을 견주었나

`dq4bg3slotcheck.py` 는 원래 롬과 새 롬(지금은 `overture.sfc` 와 `menu.sfc`)의 명령 창 화면이 같기를 바랐습니다. 10맵(자리 `78`·`7C`·`3C`·`48`·`4C` 와 출발 맵 `17/00`)을 고치기 전 코드로 돌렸습니다.

```text
01/00 도착 다름 0725=7C shown=7C nz=1123 vsbuf=0 old=115
02/00 도착 다름 0725=3C shown=3C nz=342 vsbuf=0 old=660
17/00 못감 -    0725=3C …
10맵, 도착해서 화면이 다른 맵 9
```

`$0725` 는 모두 `dq4bg3slot.MAP_SLOTS` 대로였고, 보이는 타일맵과 게임 버퍼의 차이(`vsbuf`)도 0 이었습니다. 끝 화면을 나란히 놓으니 다른 곳은 명령 창 글자(はなす → 대화, じゅもん → 주문 …)와 상태 창 이름이었습니다. 둘 다 menu 패치가 일부러 바꾼 것이고, 옛 자리(`old`)가 0 이 아닌 것도 비운 BG3 칸 `180`~`1FF` 에 글리프가 올라간 것입니다. 패치 단계가 다른 롬끼리 화면을 견주는 판정은 이 검사의 목적(BG3 자리)과 맞지 않습니다. 단계가 같은 비교 롬은 만들 수 없었습니다. 상태 창 이름(`dq4windowname`)이 옮겨 비운 칸에 글리프를 쓰므로 자리 옮기기만 뺀 `menu.sfc` 는 그 자체로 깨집니다.

그래서 판정을 BG3 자리 동작으로 바꿨습니다. 도착, 끝의 `$0725` 가 그 맵의 자리, `$2109` 에 든 자리가 `$0725` 와 같음, 그 자리 타일맵이 비지 않고 버퍼와 같음입니다. 화면은 `--old` 를 줄 때 차이 영역만 적습니다.

| 롬 | 10맵 결과 |
| --- | --- |
| `menu.sfc` | 모두 통과 |
| `overture.sfc`(자리를 옮기기 전) | 모두 실패: `$0725=1C` |

## 5. `17/00` 에 도착하기

배 선실 상태에서 `17/00` 으로 순간이동하면 사다리 출구가 같은 맵을 다시 불러와 주인공이 (10,10) 에 섭니다. 끝 칸이 (10,9) 인 것은 `dq5warp.lua` 가 「배를 떠남」 을 기다리며 계속 위를 누른 탓입니다. 맵 번호가 바뀌어야 도착으로 보므로 못 감이 됩니다.

다른 맵에 먼저 가서 세이브스테이트를 남기고 거기서 「어디서나」(`ANYWHERE=1`)로 `17/00` 에 가게 했습니다. 들르는 맵은 자리가 `7C` 인 `01/01`(13,8)로, 돌아오며 자리를 `3C` 로 다시 골라야 합니다. `17/00` 이 통과했고 끝 화면에 한글 명령 창이 떴습니다.

## 6. 화면 차이에서 나온 다른 것

`00/0A` 는 도착 뒤 전투가 났고, 전투 배경 가운데에 8×8 검은 칸이 `menu.sfc` 에만 있었습니다. 같은 프레임의 OAM·BG3 타일맵·BG1 타일맵은 두 롬이 같았습니다. 전투 배경은 HDMA 로 BG1 세로 스크롤을 줄마다 `0100` 으로 두어, 그 칸은 BG1 타일맵 48째 줄 `1656`(타일 `256`)입니다. VRAM 을 견주니 BG1 타일 `256`·`257`·`2AF`·`356`·`3AE` 약 100바이트가 `menu.sfc` 에서 0 이었습니다.

`dq4menupatch.build` 의 한 단계씩 빼고 만든 롬으로 같은 장면을 돌렸습니다.

| 뺀 것 | 그 자리 픽셀 차이 |
| --- | --- |
| 없음(`menu.sfc`) | 65 |
| `dq4bg3slot` | 64 |
| `dq4namegame` | 65 |
| `dq4windowname` | 0 |

창 이름 코드가 전투 그림 전송을 막는 것으로 보입니다. BG3 자리와는 상관없어 이 검사가 잡지 않고, 고치지 않았습니다.

## 7. 실내 364맵

고친 판정으로 `menu.sfc` 의 실내 364맵을 돌렸더니 358맵이 통과했습니다. 실패 여섯 가운데 셋은 판정이 모자랐습니다.

| 맵 | 본 것 | 고친 것 |
| --- | --- | --- |
| `04/0B`·`04/0C` | 필드꼴 맵(`$BE` bit7 = 0, `dq5warp` 가 `field` 로 도착)이라 `$0725` = `78` | 필드로 도착하면 `78` 을 바람 |
| `04/0B` | 끝 기록만 `vsbuf` 1, 앞 기록은 0 | 끝 세 기록 가운데 하나가 0 이면 됨 |
| `33/01` | 도착하자마자 게임이 `33/00` 으로 옮김(`arrived map 33/00`) | 도착한 맵으로 판정 |

나머지 셋 `1E/00`·`20/06`·`32/00` 은 `menu.sfc` 에서만 명령 창을 열자 화면 전체가 깨진 타일로 덮였습니다(`overture.sfc` 는 `vsbuf` 0, 창이 온전함). 기록으로는 A 를 누른 뒤 480 프레임부터 `vsbuf` 가 1155 로 뛰었습니다. `$2116`·`$2117` 쓰기를 감시하니 479 프레임에 창 이름 코드의 전송 대기열(`60:D843`, `LDA $3EB0,Y` / `STA $2116`)이 VRAM 워드 `3CB4` 로 자료를 보냈고, 타일맵 `3CB4`~`3FFF` 가 `b4ff3cff…` 같은 타일 그림으로 바뀌었습니다. `dq4windowname` 을 뺀 롬에서는 세 맵 모두 통과했습니다. BG3 자리 표가 아니라 창 이름 코드의 문제여서 고치지 않았습니다. 가드에는 알려진 실패로 넣었습니다(8절).

## 8. 리뷰에서 고친 것

독립 리뷰에서 판정이 느슨한 곳을 짚었습니다.

| 짚은 것 | 고친 것 |
| --- | --- |
| `song_held` 가 곡을 듣지 못한 방문(`[09]` 뒤 `[FF, FF]`, 빈 방문)도 통과 | 방문마다 그 곡 걸음이 하나 이상 있어야 함. `FF` 는 첫 곡 걸음 앞에만 |
| `FF` 구간에 상한이 없음 | 곡 요청 뒤 150프레임(`SONG_START_FRAMES`) 안의 `FF` 만. 원본 DQ5 탑 곡이 114프레임에 시작한 것에 약 3분의 1 여유 |
| BG3 검사가 끝 세 기록 가운데 하나만 맞아도 통과 | 버퍼가 2프레임 멈춘 프레임에만 기록을 뜨고 끝 기록이 맞아야 통과 |
| 화면을 빼서 `00/0A` 의 BG1 손상을 아무것도 잡지 못함 | `--old` 와 같은 30프레임째 VRAM·OAM·PPU 상태로 화면에 쓰이는 BG1·BG2·OBJ 자료를 견줌 |
| 옛 자리 `old` 를 기록만 함 | 판정하지 않는 까닭(그 자리가 한글 글리프를 쓰는 BG3 글자 칸)을 도구 README 에 적음 |
| 알려진 실패를 가드에 드러내지 않음 | `--known` 의 맵은 실패해야 하고 통과하면 검사가 실패. 가드에 `00/0A`·`1E/00`·`20/06`·`32/00` |

곡을 듣지 못한 방문을 실패로 치자 `3A-00-field` 가 실패했습니다. 걷기가 필드에서 들어서는 순간 끝나 마지막 방문(1158 프레임 곡 요청)에 걸음이 없었습니다. 끝에 안쪽 걸음(`wait:90,down:16`)을 더하자 그 방문도 1263 프레임에 곡 `09` 를 읽었습니다.

VRAM 을 처음에는 BG3 글자 칸과 BG3 자리만 빼고 통째로 견주었습니다. 덤프가 있던 맵 열다섯이 모두 `7C00`~`7FFF` 같은 화면에 쓰이지 않는 자리에서 달랐습니다. 앞 장면이 남긴 자료가 롬마다 달랐던 것입니다. 그래서 PPU 상태로 BG1·BG2 타일맵과 그 칸이 가리키는 타일, 화면 안 OBJ 타일만 골라 견줍니다. 또 `VRAMAT=620` 한 프레임에서 덤프하니 `17/00`(들르는 길이라 일찍 끝남)은 그 프레임에 이르지 못해, 30프레임마다 덮어쓰고 두 롬의 같은 프레임을 견줍니다. 이 판정으로 `00/0A` 가 `456F`~`457F`·`4AF0`~`4AFF` 차이로 실패하고, 나머지 자리 맵은 통과했습니다.

리뷰 전 코드로 새 시험을 돌렸습니다. 리뷰 전 `song_held` 는 `test_every_visit_must_hear_the_song`·`test_gap_is_bounded` 를 통과하지 못했고, 리뷰 전 `judge` 는 끝 기록만 `vsbuf` 1 인 기록을 통과시켰습니다.

## 9. 재발 방지

- `test_dq4dungeonencountercheck.py`: 원본 DQ5 와 같은 `FF` 뒤 곡은 통과. 곡을 듣지 못한 방문, 시작 뒤 `FF`, 다른 곡, 상한을 넘은 `FF`, 곡 요청 없는 `FF` 는 실패.
- `test_dq4bg3slotcheck.py`: 맵마다 바라는 자리(필드꼴 맵은 `78`), 이어진 맵으로 판정, 끝 기록의 버퍼 차이·옮기지 않은 `1C`·보이는 자리 다름·빈 타일맵·도착 못 함은 실패, 화면이 쓰는 타일의 VRAM 차이만 잡음, 알려진 실패가 통과하면 검사 실패, 들르는 맵의 자리가 출발 맵과 다름.
- `guards.toml` 의 `dq4-dungeon-encounter`(1장 롬 24장면)와 `dq4-bg3-slot`(`menu.sfc` 15맵, `--old overture.sfc`, 알려진 실패 넷).

## 틀렸던 것들

- 들르는 맵을 처음에는 `01/00` (10,10) 으로 했습니다. 성벽 밖이라 걷지 못했고, `01/00` (32,57) 에서는 「어디서나」 가 누른 입력이 먹지 않아 맵을 떠나지 못했습니다. `01/01` (13,8) 에서 떠났습니다.
- `dq5warp.lua` 의 `SAVE` 에 절대 경로를 주었더니 `SHOT_DIR` 뒤에 붙어 상태가 남지 않았습니다. 파일 이름만 줍니다.

## 남은 것

- `menu.sfc` `00/0A` 전투 배경의 검은 칸: `dq4windowname` 의 어느 길이 전투 BG1 타일 전송을 막는지, 1장 롬 필드 전투에서도 나는지.
- `menu.sfc` `1E/00`·`20/06`·`32/00`: 창 이름 전송 대기열의 어느 항목이 VRAM `3CB4` 를 넣는지, `00/0A` 의 검은 칸과 같은 원인인지. 고치면 가드 `dq4-bg3-slot` 의 `--known` 에서 뺌.
- 가드는 실내 15맵만 돎(364맵은 약 25분, `--old` 를 주면 두 배).
- 화면 VRAM 판정은 모드 0·1 만 견줌(실내 맵·전투는 모드 1). 다른 모드면 실패로 적음.
