# 2026-10-25-52: 용의 날갯짓과 구름 이동

첫 DQ5 통합은 한 장의 그림에 페이드와 약한 광택을 적용했습니다. 정지 그림의 채택을 애니메이션 완성으로 판단해서는 안 됐습니다. 대기 중에도 눈에 보이는 날갯짓과 구름 이동이 필요하다는 피드백을 반영합니다. 규격은 [타이틀 애니메이션](../docs/dq4-title-animation.md)에 정리합니다.

## 1. 실제 움직임을 기준으로

NDS 실행 영상에서 구름은 왼쪽으로 초당 약 10~11픽셀 움직였고 날갯짓은 약 2.2~2.4초에 반복됐습니다. 정지 화면의 색만 바꾸는 대신 별도 용 자세와 구름 레이어를 사용합니다. 한글 로고·IV·부제는 기존 실제 크기 원본에서 가져와 고정합니다.

처음에는 네 자세를 만들었지만 각 자세가 약 0.53초 유지돼 날개가 끊겨 보일 수 있었습니다. 중간 자세를 포함한 여덟 자세로 늘리고 몸통 기준점을 맞췄습니다. 자세마다 바운딩 박스에 맞춰 크기를 바꾸면 용 전체 크기가 변하므로 같은 배율을 사용합니다. 날개를 올린 상태와 부유 범위까지 포함해 화면 위 여백을 확보했습니다.

구름은 고정된 성과 분리해 서로 다른 속도로 흐르게 합니다. 움직이는 그림에 기존 광택 팔레트를 다시 적용하지 않고 전체 순환 동안 같은 색을 사용합니다.

## 2. 전체 화면 전송의 한계

전체 896타일을 두 VRAM 영역에서 번갈아 사용하면 타일 전송량 때문에 화면 교체가 약 7.5fps에 그칩니다. 별도 날개 자세를 만들었어도 오래 멈춘 자세 사이를 바꾸는 것만으로는 부드러운 움직임이 되지 않았습니다.

실행 중 화면 아래쪽에 다른 프레임이 섞이는 문제도 발견했습니다. 어셈블러가 마스크 상수를 8비트 즉시값으로 해석했지만 CPU는 16비트 상태였고, 뒤의 carry 초기화 명령까지 즉시값으로 소비했습니다. 그 결과 일부 전송이 다음 ROM 뱅크를 읽었습니다. 명령의 폭을 명시하고 전체 화면을 연속 비교해 수정 여부를 확인했습니다. 전송이 귀선 시간 안에 끝난다는 사실만으로 올바른 프레임이 표시된다고 판단할 수는 없었습니다.

## 3. 화면 레이어 분리

로고와 성은 BG1, 하늘은 BG2, 용은 OBJ로 나눕니다. 구름은 하드웨어 스크롤로 이동시키고, 용은 고정 몸통과 별도 날개를 어깨 관절 기준으로 연속 변환합니다. 바뀐 스프라이트 타일만 전송하고 위치를 매 게임 프레임 갱신합니다.

표시용 VRAM을 재배치하므로 메뉴로 돌아갈 때는 암전 상태에서 원래 글꼴 초기화와 화면 설정을 복원합니다. 음악 데이터는 DQ5 원본이며, 타이틀부터 재생해 메뉴에서도 이어지는 동작을 유지합니다.

## 4. 하드웨어 표시 제한까지 확인

타일과 OAM 메모리가 기대한 데이터와 같아도 화면이 완전하다는 뜻은 아니었습니다. 미사용 32픽셀 스프라이트를 Y=240으로 숨기면 위쪽 16줄로 감기며 개수 제한을 소비해 날개 끝이 빠졌습니다. Y=224로 옮겨 가시 영역 밖에 두고 실제 화면까지 다시 비교합니다.

원래 로고에는 검정을 포함해 16색을 모두 쓰는 타일도 있습니다. BG1 4bpp에서 투명색을 추가하면 원래 색을 보존할 수 없어 Mode 3의 8bpp 전경을 사용합니다. 검정을 별도 불투명 색 번호로 옮겨 투명 배경과 구분합니다. 그림의 모양뿐 아니라 색 번호의 의미도 레이어 분리 때 달라질 수 있었습니다.

## 5. 최종 확인

최종 2MiB 롬에서 연속 화면 1,001장이 독립 합성 결과와 전체 픽셀 일치했고 구름 순환 경계도 포함했습니다. 연속 301프레임의 실제 VRAM·OAM으로 128개 위상이 매 프레임 진행하는 것을 확인했습니다. 전체 자동 검사 40개와 마지막 OAM 수정 관련 7개 회귀 검사를 통과했습니다. 실제 기기와 사용자 시각적 채택까지 완료한 것으로 해석하지 않습니다.

## 남은 것

- 애니메이션의 최종 시각적 채택은 사용자 확인과 구분합니다.
- 실제 SFC 기기와 게임 후반 전체의 동작은 별도 검증이 필요합니다.
