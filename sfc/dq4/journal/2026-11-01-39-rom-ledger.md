# 2026-11-01-39: 롬 쓰기 장부와 바이트 검사

사람 플레이 없이 검사만으로 1장 롬을 내보내려면, 에뮬레이터를 켜기 전에 롬 바이트만으로 잡을 수 있는 것부터 잡아야 합니다. 빌드 단계마다 바뀐 바이트를 장부에 적고, 장부와 결과 롬만으로 단계끼리 덮어쓴 곳, 원래 DQ5 롬을 크게 덮은 곳, 뱅크 경계를 넘는 쓰기, 표 불변식을 1초 남짓에 보는 검사를 만들었습니다. 지금 빌드에서는 의심스러운 덮어쓰기가 나오지 않았고, 걸린 것은 모두 근거를 찾아 허용 목록에 적었습니다. 명세는 [롬 쓰기 장부와 바이트 검사](../docs/dq4-rom-ledger-format.md)입니다.

## 1. 장부를 어디서 만드나

`dq4build.py` 는 단계마다 롬 파일을 하나씩 남깁니다(`title.sfc` → `overture.sfc` → `menu.sfc` → `dq4-ch1.sfc` → `dq4-ch1-sound.sfc` → `dq4-ch1-full.sfc`). 모듈 스무 개 남짓이 저마다 롬을 고치는데, 모듈마다 쓰기 목록을 내게 고치면 모듈을 더할 때마다 장부도 손봐야 합니다. 그래서 단계 롬을 바로 앞 단계 롬과 견주는 것으로 정했습니다. 견주는 일은 `dq4romledger.py` 가 하고, `dq4build.py` 는 단계가 끝날 때마다 바이트를 잡아 두었다가 마지막에 `ledger.json` 을 씁니다.

예외가 하나 있습니다. 칼 효과(`dq4sparfx.py`)는 곡 롬 파일을 그 자리에서 고쳐 쓰므로, 디스크에는 곡 묶음만 얹은 롬이 남지 않습니다. 고쳐 쓰기 전에 메모리에 잡아 두어 `sound` 와 `sparfx` 두 단계로 나눴습니다.

첫 단계는 원래 롬과 바로 견줄 수 없습니다. 타이틀 빌드가 롬을 4MB 로 늘리며 뱅크 `30`~`3F` 를 원본 `20`~`2F` 의 거울로 채우기 때문입니다(`dq4titlelayerpatch.py`). 같은 꼴로 늘린 원래 롬과 견주니 거울 512KB 가 「쓴 것」 으로 잡히지 않았습니다.

```text
title     범위  8,064   60,589바이트
overture  범위    185    2,611바이트
menu      범위 16,319  326,069바이트
chapter1  범위 27,080  566,515바이트
sound     범위 11,405  552,889바이트
sparfx    범위    519    2,301바이트
people    범위  3,019   38,526바이트
```

장부를 더해도 결과 롬은 그대로입니다(`c6cb51e6…`). 빌드 시간은 1분 남짓에서 달라지지 않았습니다.

## 2. 겹침: 처음에는 인물 그림이 1장 자료를 22KB 덮는 것처럼 보였다

바이트마다 마지막으로 쓴 단계를 들고 가며 뒤 단계가 다시 쓴 곳을 모았습니다. 체크섬 네 바이트(단계마다 다시 맞춤)를 빼고 처음 나온 것은 이렇습니다.

```text
title → overture   00:A70C, 30:801C~8021, 30:81AA~81AC
title → menu       30:829B~829D
overture → sound   2B:E676, 2B:E6EB~E7ED
chapter1 → people  3C:F050~FC0C, 3D:EA00~FD77 등 9곳, 22,431바이트
```

마지막 줄이 걱정스러웠습니다. 인물 그림 단계가 1장 빌드의 표 뱅크 `3C`~`3F` 를 덮는 것처럼 보였기 때문입니다. 덮인 바이트를 1장 롬에서 보니 모두 0 이었습니다. 1장 빌드는 그룹 패치를 얹기 전에 뱅크 `30`~`3F` 의 거울 바이트를 0 으로 둡니다([1장 문서](../docs/dq4-chapter1-format.md)). 그 0 은 자료가 아니라 「비운 자리」 이고, 인물 그림은 그 빈 자리에 들어간 것입니다(`work/ch1/leader/sprite*.dq5patch.json` 의 쓰기 주소와 같음).

그래서 장부에 `cleared` 를 더했습니다. 거울 그대로이던 바이트가 0 이 된 칸이 길게 이어지는 곳이고, 검사는 그 바이트의 주인을 비웁니다. 이렇게 하자 이 겹침은 사라졌고, 남은 다섯 곳은 모두 뒤 단계가 앞 단계 코드·표를 일부러 고친 것이었습니다.

- `00:A70C`: 타이틀은 메뉴 곡 `BRK 0F 10` 셋을 NOP 으로 막고, 서곡은 그 앞 `STA $2100` 과 첫 NOP 자리(`00:A709`~`A70C`)를 `JSL $70FF20` 으로 바꿉니다. 바이트로 보면 `8D 00 21 EA EA EA` → `22 20 FF 70 EA EA` 라 명령 경계가 맞습니다.
- `30:801C`·`30:81AA`: 서곡이 타이틀 코드의 곡 호출과 FadeOut 첫 명령을 스텁으로 돌립니다([서곡](../docs/dq4-overture-format.md)).
- `30:829B`: 메뉴가 타이틀 코드의 `JML $03FE5C` 대상을 바꿉니다(`dq4menupatch.FADEOUT_EXIT`).
- `2B:E676`~`E7ED`: 서곡이 곡 `10` 레코드를 늘린 곡 묶음 표를 곡 묶음 단계가 바꾼 곡 전부로 다시 씁니다([사운드 포팅](../docs/dq4-sound-port-format.md)).

## 3. 원래 롬 덮기: 어디까지를 실패로 볼까

원래 롬의 0 아닌 바이트를 덮은 곳을 16바이트 이하 틈은 이어 덩어리로 세었습니다. 364덩어리이고, 306덩어리가 64바이트 미만이었습니다. 작은 것은 거의 훅(`JSL`·`JML` 4바이트, 즉값 몇 바이트)과 표 칸 고치기입니다. 이것을 하나하나 허용 목록에 적으면 목록이 수백 줄이 되고, 훅 하나를 더할 때마다 목록을 고쳐야 합니다. 그래서 64바이트 미만은 단계마다 세어 보고만 하고, 훅은 아래 4절의 불변식으로 따로 봅니다.

64바이트 이상 58덩어리는 하나씩 어느 모듈이 무엇을 쓴 것인지 찾았습니다. 근거는 [DQ5 빌드 문서](../../dq5/docs/dq5-build-format.md)의 「1장 빌드가 원래 롬 안에서 고친 곳」 표, dq4 형식 문서, 인물 단계가 남기는 `work/ch1/leader/*.dq5patch.json` 의 `note` 입니다. 모두 표를 통째로 바꾸거나 자료를 제자리에 바꾼 것이라 20항목으로 묶어 적었습니다. 메뉴의 옛 보행 메시지 자리(`07:D77C`~`0C:8020`, 글자 그림), 1장의 출구 표(영역 이동 레코드를 옮겨 비운 `2A:D812`~), 인물의 세트 타일(`0C`~`0F`) 등입니다.

## 4. 표 불변식

형식 문서와 도구에서 롬만으로 읽을 수 있는 표를 찾았습니다. DQ5 트랙의 디코더가 원래 롬과 1장 롬을 같은 함수로 읽으므로 그것을 그대로 불렀습니다.

```text
checksum  체크섬 6FD5
vectors   COP 8F7F, BRK 8F80, NMI 885D, IRQ 8000, RESET 8639 …
shops     가게 3C:E000 목록 80개
inns      여관 3C:F000
exits     맵 464개, 출구 맵 446개, 영역 이동 맵 223개
messages  메시지 3760개, 글자 3430
people    목록 739개, scripts 1383, mismatch 0
brkscan   덩어리 4개
hooks     훅 109개
```

출구 목적지를 처음 봤을 때 원래 롬에서도 영역 이동 29곳이 「없는 맵」 으로 나왔습니다. 모두 목적지 그룹 `FF` 였고, 필드로 나가는 영역 이동입니다. 그룹 `FF` 를 받게 했습니다.

훅은 원래 롬 자리에 새로 쓴 덩어리의 첫 바이트가 `22`·`5C` 이고 피연산자가 그 덩어리 안일 때만 훅으로 봅니다. 첫 바이트가 원래와 같아 덩어리가 한 바이트 뒤에서 시작하는 훅(대상만 바꾼 `JSL`)도 있어 한 바이트 앞도 봅니다. 109개 모두 대상이 롬 안의 0 아닌 바이트였습니다.

## 5. 일부러 깨 본 롬

검사가 실제로 잡는지 보려고, 결과 롬에서 1장 사건 코드(`5E:D000`)를 NOP 여덟으로 덮고 가게 표 주소(`06:F4BA`)를 바꾼 롬을 마지막 단계로 붙였습니다. 겹침(`chapter1 → evil 5E:D000~D007`, `06:F4BB`), 체크섬, 가게 불변식(두 루틴의 표 주소가 다름)이 모두 실패로 나왔습니다.

## 6. 뱅크 넘기

쓴 덩어리가 뱅크 경계를 넘는 곳은 처음에 아홉 곳이었습니다. 메뉴의 보행 메시지 비트열 다섯(`64:F62A`~`65:818B` 등)은 디코더가 뱅크 끝에서 다음 뱅크 `8000` 으로 넘어가 읽는 자료라 허용 목록에 넣었습니다. 1장 롬의 `3B`~`3F` 뱅크 끝 네 곳은 뱅크 끝을 0 으로 비운 바이트와 다음 뱅크 첫 자료가 이어진 것이었습니다(`3C:FFEA`~`FFFF` 가 0, `3D:8000` 이 `09`). 뱅크 끝에 닿는 0 줄은 짧아도 지운 자리로 보게 하자 사라졌습니다(7절에서 거두고 한 곳만 허용 목록에 적음). 높은 뱅크 사건 코드 덩어리 넷(`dq4brkscan.blobs`)은 어느 것도 뱅크를 넘지 않습니다.

## 7. 허용 목록을 좁히고 빈 자리 재사용을 드러내기

리뷰에서 넷을 고쳤습니다.

- 지운 자리의 주인을 비우면, 앞 단계가 0 으로 채운 자료를 뒤 단계가 덮어도 보이지 않습니다. 지운 단계를 주인으로 두고, 뒤 단계가 그 자리를 쓰면 「비운 자리 다시 쓰기」로 따로 세어 `reuse = true` 항목만 받게 했습니다. 지금 빌드에서는 `chapter1` → `people` 다섯 자리 18,037바이트이고, 모두 `dq4people` 의 자리 상수(`TILE_AREAS`·`PALETTES_AT`·`MAP_PALETTES_AT`·`HOOK_AT`) 안입니다.
- 뱅크 끝 0 줄을 길이와 관계없이 지운 자리로 보던 것을 거두고, `3C:FFEB`~`3D:8000` 하나를 `[[cross]]` 에 `max = 32` 로 적었습니다.
- 메뉴의 옛 보행 메시지 자리 전체(`07:D77C`~`0C:8020`, 약 138KB)를 글자 그림이 실제로 쓰는 `07:D77C`~`07:FFFF`·`08:8000`~`08:F414` 둘로, 인물의 `0C`~`0F` 전체를 세트 19개의 원래 타일 자료 자리(`dq5sprite.set_tiles` 가 원래 롬에서 잰 끝)로 좁혔습니다. 원래 롬 덮기 덩어리는 뱅크 경계에서 자릅니다. 항목에 `max` 를 줄 수 있습니다.
- 자원 저장소 없이 빌드해 곡·인물 단계가 빠진 장부는 실패로 봅니다(`--allow-missing-stages` 로만 낮춤). 가드 `needs` 에 `DQ4_ASSETS` 를 넣고, 3.4GB 폴더를 캐시 키로 내용째 읽지 않도록 `tools/guards.py` 의 `hash_path` 가 폴더는 (상대 경로, 크기, mtime_ns) 목록, 64MB 넘는 파일은 (크기, mtime_ns) 로 보게 했습니다.

다시 깨 본 롬(사건 코드 `5E:D000`, 원래 롬 `05:9000` 100바이트, 인물 훅 표 `3E:FC10`)은 겹침 셋, 원래 롬 덮기, 체크섬으로 모두 실패했고, 좁힌 허용 목록으로 지금 빌드는 통과했습니다.

## 틀렸던 것들

- 지운 자리의 주인을 비워 두면 된다고 봤습니다. 그러면 앞 단계가 쓴 0 자료를 뒤 단계가 덮어도 보이지 않아, 지운 단계를 주인으로 두고 재사용을 따로 밝히게 바꿨습니다(7절).
- 「거울을 0 으로 바꾼 바이트는 모두 지운 자리」 로 처음 정했습니다. 1장 빌드가 거울 위에 새로 쓴 자료 속의 0 도 그렇게 잡혀, 뒤 단계가 그 0 을 덮어도 겹침으로 나오지 않게 됩니다. 0 줄이 32바이트 넘게 이어지거나 뱅크 끝에 닿을 때만 지운 자리로 보게 바꿨습니다. 그러자 이번에는 지운 자리가 거울에 원래 있던 0 에서 끊겨 짧은 줄로 쪼개졌고, 인물 그림 겹침이 다시 나왔습니다. 거울이 원래 0 인 칸도 줄에 잇게 해서 풀었습니다. 뱅크 끝 0 줄을 길이와 관계없이 지운 자리로 본 것도 거뒀습니다(7절).

## 남은 것

- 효과음 번호가 효과음 시퀀스 표 안인지(부르는 자리를 롬에서 모으는 길이 없음).
- 훅 대상이 쓴 덩어리의 진입점인지(지금은 0 이 아닌지만 봄).
- 앞 단계와 같은 값을 다시 쓴 바이트, 한 단계 안 모듈끼리의 덮어쓰기(단계마다 asar·도구가 쓴 구간 기록을 받는 길).
- [메뉴 문서](../docs/dq4-menu-format.md)의 글자 그림 끝(`08:F276`)이 지금 롬(`08:F414`)과 다름. 출구 표 끝도 DQ5 문서의 `2A:DE8E` 보다 길어져 `2A:DEA5`.
