# 2026-10-27-17: 시퀀스를 되풀이·부르기로 묶기

전투 곡이 원래보다 151프레임 늦게 시작하는 것을 줄이려고, 변환기가 시퀀스를 DQ5 드라이버의 되풀이(`F5`)와 깊이 3 부르기(`F8`)로 묶게 했습니다. 묶기 전후의 실행과 드라이버가 미리 보는 바이트가 같은지를 검산하고, 실제 DSP 쓰기로도 확인했습니다. 50곡 합은 272,041바이트에서 246,762바이트, 전투 곡은 8,902바이트에서 7,454바이트가 됐지만 전투 곡 시작은 158프레임에서 145프레임으로만 줄었습니다. 남은 지연은 전송 길의 한계였습니다. 결과는 [사운드 포팅](../docs/dq4-sound-port-format.md#시퀀스-묶기)에 정리했습니다.

## 1. 드라이버가 주는 흐름 명령

[DQ5 소리 형식](../../dq5/docs/dq5-sound-format.md)의 명령 표에 `F5`(횟수 되풀이)·`F4`·`DC`(두 바퀴)·`F8`·`F9`(부르기·돌아가기)가 있습니다. SPC RAM 덤프를 풀어 처리 루틴을 읽었습니다.

```
192E  CALL $19BD x2        ; 오프셋
1938  MOV A,$0240+X        ; 쌓은 깊이
193B  CMP A,#$06
193D  BCS $195C            ; 6 이상이면 점프하지 않고 돌아감
1907  MOV A,$0217+X        ; F5: 셈이 0 이면 횟수로, 1 을 빼 0 이 아니면 179B(점프)
1292  MOV $0217+X,A        ; 트랙을 켤 때 셈을 0 으로
```

부르기는 3단까지, 되풀이 셈은 트랙마다 하나라 되풀이 안에서 되풀이하면 셈이 엉킵니다. 그래서 되풀이는 목소리 본문 맨 위에만 두고, 서브루틴에는 되풀이를 넣지 않았습니다.

## 2. 미리 보기는 실제 자리의 바이트를 본다

음 경계를 다룬 [2026-10-27-07](2026-10-27-07-sound-port.md)에서 드라이버가 음이 끝나기 1틱 전에 다음 바이트를 본다는 것을 알았습니다. `15E5` 를 끝까지 읽어 보니 건너뛰는 것은 게이트(`A0`~`B5`·`EC`)·`F6`·`EB`·`F2`·`F3` 뿐이고, 그 밖의 바이트를 만나면 쉼(`00`·`50`)인지만 봅니다. 부르기·돌아가기는 따라가지 않습니다.

곧 음 바로 뒤에 `F8`·`F9` 를 두면, 실행상 다음이 쉼이어도 KOF 가 걸립니다. 이전 압축(깊이 1 서브루틴)으로 만든 시퀀스를 묶지 않은 것과 견주자, 두 바퀴 동안 성 곡 254번, 마을 617번, 전투 464번 미리 보기 결과가 달랐습니다. 이미 청취 승인한 빌드들이 쉼 앞의 음을 원래 뜻보다 일찍 끊고 있었습니다.

`execution_trace(peek=True)` 가 음표 사건마다 미리 본 것이 쉼인지를 붙이고, `convert` 는 묶기 전후가 같지 않으면 멈추게 했습니다. 처음 규칙(음표 뒤만 검사)으로는 50곡 중 18곡이 멈췄습니다. 쉼을 읽을 때도 `1583` 이 `$15` 를 0 으로 둬 미리 보기가 돌기 때문이었고, 쉼도 음표처럼 다루자 50곡이 모두 통과했습니다.

## 3. 묶는 방법

1. 목소리마다 주기 1~256줄로 바로 이어 같은 줄이 나오는 구간을 찾아, 아끼는 바이트가 큰 것부터 `Lrepeat: … loop n -> Lrepeat` 로 바꿉니다.
2. 모든 본문을 이어 접미사 배열을 만들고, LCP 구간마다 겹치지 않는 자리 수와 크기로 아끼는 바이트를 셉니다. 가장 큰 것 하나를 서브루틴으로 빼고 다시 셉니다. 서브루틴 높이가 3 을 넘는 것은 버립니다.
3. 미리 보기 규칙에 걸리는 자리는 뺍니다. 음으로 끝나는 프레이즈 뒤에 쉼이 오는 일이 많아, 끝을 쉼이 아닌 것 앞으로 당긴 토막과 처음을 쉼 뒤로 미룬 토막도 같은 자리 집합에서 함께 봅니다. 이것으로 전투 곡이 8,042 에서 7,370바이트가 됐습니다.

규칙을 지키지 않으면 전투 곡이 7,290바이트까지 줄지만 KOF 가 달라지므로 쓰지 않았습니다. 바이트의 약 46% 는 `instrument`·`pan`·`volume2` 입니다. NDS 트랙 12개(동시 발음 최대 15)를 일곱 목소리에 나눠 담아 목소리마다 트랙이 자주 바뀌는 탓이라, 정확히 같은 실행을 지키는 묶기로는 이 이상 줄기 어렵습니다.

## 4. 실제 드라이버에서 같은가

필드 곡 `05` 를 같은 샘플로 묶지 않은 시퀀스·이전 압축·새 압축으로 넣고 전원부터 2,400프레임을 돌려, 곡 시작 기준 DSP KON·KOF 를 목소리마다 견줬습니다.

```
묶지 않음  KON 337  KOF 334
새 압축    KON 337  KOF 334   목소리마다 시각 차 ±1프레임 안
이전 압축  KON 337  KOF 377
```

되풀이와 부르기를 쓴 전투 곡 미리듣기(`dq4soundcheck.py --song 17`)는 시퀀스·샘플 11개가 롬과 같고, 예상 음 1,270개에 SRCN·음 간격 오류 0, 잔차는 목소리 6 의 곡 첫 KON 하나만 2.81프레임이고 나머지는 1.81 이하였습니다. 마을 `06`(679음, 잔차 1.54)·필드 `02`(340음, 0.98)도 통과했고, 같은 롬으로 마을 `18/00` 워프(596프레임에 곡 `06`)와 필드(651프레임에 곡 `02`)에서 곡이 올랐습니다.

## 5. 샘플 예산이 따라 바뀌었다

새 압축으로 다시 빌드하자 마을 BRR 이 14,940 에서 17,073바이트로 늘었습니다. `dq4soundset` 은 시퀀스 크기를 빼고 남은 만큼을 샘플 예산으로 주므로, 시퀀스가 작아지자 샘플을 덜 줄였습니다. 청취 승인한 소리를 바꾸지 않으려고 `--budget` 을 더해 그때의 예산(`06=15967`·`02=20068`·`17=20791`)을 주었고, 세 곡의 샘플 보고서·곡 묶음 샘플 목록이 이전 빌드와 같았습니다.

같은 김에 `allocate` 가 저음 트랙을 고를 때 집합 순서를 따라, 중앙값이 같은 곡 `1C` 에서 실행마다 저음 트랙이 달라지던 것(`PYTHONHASHSEED` 에 따라 `track3`·`track7`)을 고쳤습니다. 롬에 넣은 곡에는 해당이 없었습니다.

## 6. 전투 곡 시작

선실 세이브스테이트에서 `FIELD="341,56" BATTLE="00:3"` 으로 같은 전투를 붙였습니다(`0C 17` 은 501프레임).

```
          곡이 오름  첫 목소리   도착 전 음
원래        505      508(7)
이전 k=4    658      659(158)    2
묶은 k=4    643      646(145)    2
묶은 k=2    631      633(132)    23
묶은 k=0    594      667(166)    102   ← 곡은 일찍 오르나 첫 샘플이 667 에 옴
```

시퀀스를 1,448바이트 줄인 만큼 13프레임만 줄었습니다. 프레임마다 전송의 남은 바이트(`$1D8D`)를 적자, 503프레임에 시퀀스를 보내기 시작해 505~560 은 전투 준비로 프레임당 0~150바이트(11프레임씩 멈춤), 562 부터는 프레임당 `0xC0`~`0xCF` 바이트였습니다. 2B 가 3바이트마다 부르는 대기열 훑기(`2B:C2E6 JSR $BED5`)를 지운 롬도 빠른 구간 속도가 같아, 빠른 구간의 한계는 SPC 가 대기 고리에서 3바이트씩 받는 쪽으로 보입니다.

전투 곡을 더 일찍 보낼 수 있는지도 봤습니다. 필드에서 걸어 실제 마주침을 내자 조우 판정 `23:E7C2` 와 `26:8F49` 의 `1A FF`·`0C 17` 이 같은 627프레임이었습니다. 판정 때 보내도 얻는 프레임이 없습니다. 필드에 있는 동안 미리 올리기는 필드 빌드에 남는 SPC 자리(약 5KB)가 묶은 전투 시퀀스(7,454바이트)보다 작아 들지 않습니다.

k 는 4 로 둡니다. k = 2 는 13프레임 빠르지만 첫 박 샘플 두 개가 늦어 23음이 빠지고, k = 0 은 곡이 일찍 올라도 샘플이 오기까지 소리가 없습니다. 들어 볼 파일은 묶은 k = 4 전원 미리듣기를 곡 뒤 샘플이 다 온 뒤 구운 `work/sound/listen/v8-battle-compact.wav`(150초)입니다.

## 틀렸던 것들

- 「서브루틴으로 묶어도 실행 순서와 시각만 같으면 소리가 같다」: 드라이버의 미리 보기는 실제 자리의 다음 바이트를 보므로, 음 뒤에 `F8`·`F9` 가 오면 원래 없던 KOF 가 납니다. 이전 압축은 필드 곡에서 43번 더 끊었습니다.
- 「미리 보기는 음 뒤에만 돈다」: 쉼을 읽으면 `$15` 가 0 이 되어 쉼 뒤에도 돕니다.
- 「전송은 2B 의 대기열 훑기가 느려서 프레임당 약 200바이트다」: 훑기를 지워도 같았습니다.
- 「시퀀스를 줄이면 전투 곡이 그만큼 일찍 시작한다」: 처음 약 2,400바이트는 전투 준비 중이라 느리게 가고, 시퀀스보다 곡 앞 샘플(8,847바이트)이 더 큽니다.

## 남은 것

- 전투 곡이 원래보다 138프레임 늦음. 전투 시퀀스를 늘 두는 길(다른 곡 예산에서 약 4.6KB, 또는 시퀀스를 원래 `17` 크기 2,874바이트 근처로)이나 곡 앞 샘플을 줄이는 편곡이 필요합니다
- 새 압축으로 쉼 앞 KOF 가 줄어든 마을·필드 다시 듣기, `v8-battle-compact.wav` 청취
- 목소리마다 NDS 트랙이 자주 바뀌는 성부 배분을 바꾸면 크게 줄 수 있으나 소리가 바뀌므로 청취와 함께 해야 합니다
