# 2026-10-27-32: つよさみる 에서 멈추던 주문 훅

에뮬레이터로 메뉴를 돌아다니던 중 「강함 보기」 에서 A 를 누르다 화면이 까맣게 멈췄습니다. 주문 목록 훅이 다른 길의 진입점을 덮고 있었습니다. 고친 내용은 [주문 목록](../docs/dq4-window-text-format.md#주문-목록)과 [전송](../docs/dq4-window-text-format.md#전송-게임-목록-대신-우리-대기열)에 있습니다.

## 1. 멈춘 상태

사용자가 남긴 세이브스테이트에서 낮은 WRAM `$0000`~`$01AA` 가 `22 22 25` 되풀이로 덮여 있었습니다. `$1D` = `A2`(화면 끔), `$1E` = `25`(NMI 끔)라 화면이 까맣게 멈춘 것입니다. 롬 밖 열린 버스에서 `JSL $222222` 를 끝없이 되풀이하며 복귀 주소 `22:2225` 를 쌓은 흔적으로 봤습니다.

## 2. 재현

세이브스테이트(09/00, 일행 3명)에서는 같은 입력으로 나오지 않았습니다. 사용자는 새 게임 직후 배 선실(맵 `17/00`, 주인공 혼자)이었습니다. `ship.mss` 는 BG3 타일맵이 옛 자리라, `$0725` 를 `3C` 로 넣고 시작하자 첫 타일맵 전송이 새 자리로 옮겨 정상 화면이 됐습니다. 이 상태에서 좌우까지 넣은 무작위 입력 8벌을 8000프레임씩 돌리자 2벌(씨앗 34·37)이 같은 무늬로 멈췄습니다.

## 3. 어디서 뛰었나

실행 PC 를 링 버퍼에 담는 Lua 로 롬 밖에 처음 들어간 순간을 잡았습니다. 게임의 바이트코드 해석기가 `FC` 를 명령 번호로 읽어 `21:8C43` 의 점프 표를 범위 밖으로 읽은 것이었습니다. 원인을 좁히려고 머지마다 롬을 빌드해 같은 씨앗을 돌렸습니다.

| 빌드 | 씨앗 34·37 |
| --- | --- |
| 기준 롬, #571·#573·#574·#575 | 정상 |
| #576(주문 목록) 이후 | 멈춤 |
| #576 에서 NMI 받침만 되돌림 | 멈춤 |
| #576 에서 `04:B8F2` 훅만 뺌 | 정상 |

뱅크 04 를 훑으니 `04:BD4F`·`04:BD9F` 가 스스로 `PHX` 를 한 뒤 `BRL $B8F3` 으로 `LDX #$0000` 부터 들어왔습니다. `04:B8F2` 에 넣은 4바이트 `JML` 이 이 자리를 덮어, 이 길로 오면 `JML` 피연산자를 명령으로 실행했습니다. つよさみる 둘째 쪽(「せんとうじゅもん」)이 이 길입니다. 훅을 `04:B8F3` 으로 옮기고, 두 입구 모두 `PHX` 를 한 상태로 받습니다. 새 자리와 뱅크 24 의 훅 셋에는 안으로 들어오는 분기가 없음을 확인했습니다.

## 4. 대기열이 찼을 때

조사하는 동안 대기열이 찼을 때의 길도 고쳤습니다. NMI 가 비워 주기를 기다리다 시간이 다 되면, 항목 수를 남긴 채 쓸 자리만 0 으로 되돌리고 있었습니다. 이제는 NMI 를 끈 채 VBlank 를 기다려 직접 보내고, 그 프레임의 게임 NMI 는 `$4210` 을 읽어 건너뜁니다.

| 시험 | 결과 |
| --- | --- |
| 선실 무작위 입력 8벌 × 8000프레임 | 모두 정상(`$1D`·`$1E` = `0F`·`81`) |
| 필드·전투 주문 목록, どうする 흐름 | 회귀 없음 |

## 틀렸던 것들

- 처음에는 대기열이 찼을 때 NMI 가 비워 주지 않는 길을 의심했습니다. 이 장면에서는 NMI 가 제대로 비웠고, 원인은 훅 자리였습니다.
- 우리가 쓰는 WRAM(`7E:3D14`~`3FFF`, `1C33`~`1D8B`)을 게임이 쓰는지도 접근 카운터로 쟀지만, 같은 입력의 기준 롬은 두 구간을 한 번도 건드리지 않았습니다.

## 남은 것

- 다른 훅 자리(`04:B808`·`04:B79B`·`04:ABCF` 등)는 뱅크 04 안의 분기만 훑었음. 다른 뱅크에서 `JML` 로 들어오는 길은 확인하지 않음
