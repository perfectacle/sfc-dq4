# 호환성 검사

MesenCE 에서만 우연히 도는 코드를 잡는 검사입니다. 분석·실험은 MesenCE 로 하지만([EMU-01](../../../.agents/skills/analysis/SKILL.md#emu-01--에뮬레이터는-mesence)), 패치는 다른 에뮬레이터와 카트에서도 돌아야 합니다. 서장 칼 여섯 합이 snes9x 에서 멈춘 일([11번 일지](../journal/2026-11-01-11-spar-brk-db.md))이 출발점입니다. 규칙은 [COMPAT-01](../../../.agents/skills/analysis/SKILL.md#compat-01--높은-뱅크-코드는-확인한-brk-만), 검사를 언제 돌리는지는 [`guards.toml`](../guards.toml)과 [GUARD-02](../../../.agents/skills/guards/SKILL.md#guard-02--걸린-실행-검사는-돌리고-결과를-적는다)가 정합니다.

## 무엇이 깨지나

DQ5 의 BRK 핸들러(`00:8F92`)는 DB 를 BRK 를 부른 코드의 뱅크로 둡니다. 스크립트 피연산자를 `LDA ($0B,S),Y` 로 읽으려면 그래야 합니다. 그런데 핸들러가 부르는 루틴 가운데 WRAM 을 DB 기준 절대 주소(`$1D91`, `$0A00` 등)로 읽고 쓰는 것이 있습니다. 뱅크 `00`~`3F` 에서 부르면 `xx:0000`~`1FFF` 가 WRAM 거울이라 상관없습니다. 우리가 코드를 두는 뱅크 `40` 이상에서 부르면 그 주소가 WRAM 이 아닙니다.

| 어디서 읽나 | MesenCE | bsnes 115 | snes9x 1.63 |
| --- | --- | --- | --- |
| `5E:1D91`(LoROM 4MB, 뱅크 `40`~`7D` 아래 절반) | 열린 버스(직전 피연산자 바이트 `1D`) | 재지 않음 | 롬 거울(`D0`) |

MesenCE 에서는 우연히 맞는 값이 읽혀 지나갔고, snes9x 에서는 끝나지 않는 고리가 됐습니다. 실기는 카트가 이 자리를 어떻게 잇느냐에 따릅니다(재지 않음).

## 가드 셋

| 가드 | 무엇을 | 언제 |
| --- | --- | --- |
| `dq4brkscan.py`(`test_dq4brkscan.py`) | 서장·1장 사건·2장 사건·장 상자 코드를 진입점부터 흐름을 따라 역어셈블해, 부르는 BRK 가 `ALLOWED` 안인지 | CI(롬 없음) |
| `dq4compatcheck.py probe` | MesenCE 1장 걷기 검사(`dq4ch1walkcheck`) 전체에 `lua/dq4openbus.lua` 를 붙여, 뱅크 `40`~`7D` 아래 절반 접근과 높은 뱅크가 부른 BRK 를 기록 | `guards.toml` 의 `dq4-openbus-probe` |
| `dq4compatcheck.py walk` | libretro bsnes·snes9x 에서 같은 구간(서장 → 1장 끝 리셋)을 이어 걷기 | `guards.toml` 의 `dq4-compat-walk` |

### BRK 허용 목록

`dq4brkscan.ALLOWED` 는 실측으로 만듭니다. MesenCE 1장 걷기 동안 BRK 핸들러 입구(`00:8F80`, 벡터 `00:FFE6`)에서 부른 뱅크와 명령 번호를 적고, 같은 걷기에 붙인 열린 버스 기록이 깨끗한 명령만 넣었습니다.

| 명령 | 피연산자 | 높은 뱅크에서 부르는 곳 |
| --- | --- | --- |
| `09` | 1 | 서장·장 상자·1장 사건(프레임 기다리기) |
| `88` | 1 | 1장 사건 4곳 |
| `89` | 2 | 1장 사건 1곳 |
| `8B` | 2 | 1장 사건 1곳 |
| `8D` | 2 | 1장 사건 7곳(걷기는 6곳을 지남) |

`16`(효과음 넣고 기다리기, `24:FE44` 가 대기열을 DB 기준으로 읽음)과 `95`(창 열기, `00:9085` 가 `STA $0A00`)은 `FORBIDDEN` 입니다. 새 명령을 높은 뱅크에서 부르려면 `dq4compatcheck.py probe` 가 깨끗한지 보고 `ALLOWED` 에 피연산자 길이와 함께 넣습니다. 정적 검사는 길이를 모르는 명령을 만나면 그 자리에서 멈추고 실패합니다.

### 열린 버스 프로브

기록 줄은 `R pc=24:FE52 bank=5E`(읽기)·`W …`(쓰기)·`BRK pc=5E:C260 op=16` 입니다. 낮은 뱅크(`00`~`3F`) 코드가 뱅크 `70`~`7D`(SRAM)를 읽고 쓰는 것은 DQ5 저장이라 괜찮고, 그 밖은 실패입니다. 뱅크 `00`~`3F` 의 다른 열린 버스 구역(`2000`~`20FF`, `4380`~`7FFF` 등)까지 콜백을 넓히면 MesenCE 가 느려져 걷기 검사가 구간 시간 제한에 걸립니다. 넓힌 기록을 한 번 따로 돌렸을 때(#907 직전 롬) 나온 것은 DQ5 원래 코드의 SRAM 접근뿐이었습니다.

### libretro 걷기

`dq4libretro.py` 가 코어를 ctypes 로 불러 입력·WRAM·화면·소리·상태 저장을 다룹니다. 코어 파일은 저장소에 두지 않고 `LIBRETRO_BSNES`·`LIBRETRO_SNES9X` 로 줍니다. 잰 코어는 libretro buildbot nightly(macOS arm64)의 bsnes 115 와 snes9x 1.63(`fae2fea`)입니다. mesen-s 코어는 이 프런트엔드에서 불러오다 segfault 가 나서 쓰지 않습니다.

MesenCE 판과 다른 점은 아래와 같습니다.

- 세이브스테이트 대신 코어 하나에서 처음부터 끝까지 이어 걷습니다(약 5만6천 프레임).
- 조우 끄기·보스 약하게 하기는 롬 파일에 미리 씁니다.
- 난수(`7E:075B`~`075D`)·시각(`075E`·`075F`)은 걷기 검사와 같이 구간 시작과 워프 도착 때 정한 값으로 둡니다.
- 워프(`dq5warp.lua` 의 「어디서나」)가 롬에 깔던 트리거·출구 레코드는 cheat(PAR 코드)로 쓰고, 워프가 끝나면 풉니다.
- 한 번만 쓰는 WRAM 값(트리거 목록 포인터 `7E:183A`~`183D`)은 poke 로 씁니다. bsnes 는 WRAM 을 API 로 주지 않아, 직렬화 상태의 오프셋 `8836` 에서 읽고 상태를 고쳐 다시 불러옵니다.
- 메시지 번호는 보지 않습니다. 끝(리셋)은 실행 추적 대신 타이틀 화면이 다시 뜨는지(화면 평균 밝기 60 이상)와 소리로 봅니다.

## 함정

- **bsnes cheat 를 풀면 옛 값이 돌아온다**: 한 번 쓰는 WRAM 값을 cheat 로 잠깐 켰다 끄면, bsnes 는 켜기 전 값을 되돌려 그 사이 맵 로더가 쓴 값을 덮습니다. 트리거 개수 `$183D` 가 0 이 되어, 왕에게 보고한 뒤 성 앞(`36/00`) 대신 필드로 나가는 가짜 실패가 났습니다. 같은 칸(32,72)에서 snes9x 는 `36/00` 으로 갔고, bsnes 의 `$183D` 는 0 이었습니다. poke 로 바꾸자 지나갔습니다.
- **bsnes 는 직렬화로 WRAM 을 읽는다**: 프레임마다 상태를 만들면 코어 스레드를 맞추느라 타이밍이 조금 바뀔 수 있습니다. 위 실패는 이 탓이 아니었습니다(WRAM 을 읽지 않고 같은 버튼을 다시 재생해도 같았음).
- **넓은 콜백은 느리다**: 프로브 범위를 넓히면 걷기 검사가 시간 제한에 걸려 실패합니다. 넓은 범위는 따로 돌립니다.

## 남은 것

- 걷기 검사가 지나지 않는 길(가게·저장과 이어 하기·일반 전투·2장)에서의 프로브와 libretro 확인.
- 정적 검사가 보는 것은 서장·사건·장 상자 코드뿐입니다. 뱅크 `40` 이상의 다른 코드(창 글자·전투 메시지·소리 등, asar 어셈블리 포함)는 프로브로만 봅니다.
- bsnes 에서 `5E:1D91` 을 읽은 값.
