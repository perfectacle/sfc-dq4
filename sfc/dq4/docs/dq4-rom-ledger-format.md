# 롬 쓰기 장부와 바이트 검사

사람이 플레이하지 않고 검사만으로 1장 롬을 내보내려면, 에뮬레이터를 켜기 전에 롬 바이트만 보고 잡을 수 있는 것을 먼저 잡아야 합니다. 이 문서는 그 첫 층의 명세입니다. 빌드가 단계마다 바꾼 바이트를 장부에 적고(`sfc/dq4/tools/dq4romledger.py`), 검사(`sfc/dq4/tools/dq4romledgercheck.py`)가 장부와 결과 롬만으로 단계끼리 덮어쓴 곳, 원래 DQ5 롬을 크게 덮은 곳, 뱅크 경계를 넘는 쓰기, 표 불변식을 봅니다. 에뮬레이터 없이 1초 남짓 걸립니다. 회귀 가드는 [`guards.toml`](../guards.toml) 의 `dq4-rom-ledger` 이고, 허용 목록은 [`ledger-allow.toml`](../ledger-allow.toml) 입니다.

일지: [2026-11-01-39: 롬 쓰기 장부와 바이트 검사](../journal/2026-11-01-39-rom-ledger.md)

```sh
uv run --locked python sfc/dq4/tools/dq4build.py --out work/ch1          # work/ch1/ledger.json 도 씀
uv run --locked python sfc/dq4/tools/dq4romledgercheck.py --ledger work/ch1/ledger.json --report work/ledgercheck/report.json
```

## 장부

`dq4build.py` 는 단계 롬을 만들 때마다 그 바이트를 잡아 두고, 끝에서 `--out` 폴더의 `ledger.json` 에 장부를 씁니다. 모듈마다 무엇을 썼는지 묻지 않고, 단계 롬을 바로 앞 단계 롬과 견줘 값이 바뀐 바이트를 범위로 적습니다. 그래서 모듈을 더하거나 고쳐도 장부 쪽은 고칠 것이 없습니다.

| 단계 | 견주는 롬 | 결과 파일 |
| --- | --- | --- |
| `title` | 원래 롬을 타이틀 빌드처럼 늘린 것: 원래 1.5MB 뒤에 원본 `20`~`2F` 의 거울(뱅크 `30`~`3F`), 그 뒤 0 으로 4MB | `title.sfc` |
| `overture` | `title.sfc` | `overture.sfc` |
| `menu` | `overture.sfc` | `menu.sfc` |
| `chapter1` | `menu.sfc` | `dq4-ch1.sfc` |
| `sound` | `dq4-ch1.sfc` | `dq4-ch1-sound.sfc`(곡 묶음만 얹은 때) |
| `sparfx` | 곡 묶음 롬 | `dq4-ch1-sound.sfc`(칼 효과와 체크섬을 얹은 때) |
| `people` | `dq4-ch1-sound.sfc` | `dq4-ch1-full.sfc` |

자원 저장소(`DQ4_ASSETS`)가 없으면 `chapter1` 에서, 인물 시트가 없으면 `sparfx` 에서 끝납니다. 검사는 이런 장부를 실패로 봅니다(아래). 칼 효과는 곡 롬 파일을 고쳐 쓰므로 `sound` 와 `sparfx` 는 같은 파일 이름이고, 디스크에 남는 것은 `sparfx` 쪽입니다. 장부는 단계 바이트를 메모리에 잡아 두었다가 견주므로 둘을 나눠 적습니다.

```json
{"format": "dq4romledger/1",
 "base": {"sha1": "1c47ed62…", "size": 1572864},
 "stages": [{"name": "title", "file": "title.sfc", "sha1": "…", "size": 4194304, "bytes": 60589,
             "ranges": [{"off": "001FD7", "end": "001FD7", "cpu": "03:FFD7~03:FFD7", "bytes": 1}, …],
             "cleared": […]}, …]}
```

- `ranges`: 바뀐 바이트의 범위. `off`·`end` 는 파일 오프셋(끝 포함), `cpu` 는 LoROM CPU 주소입니다. 파일 `3F0000`~ 은 뱅크 `FE`·`FF` 로만 보여 그렇게 적습니다([DQ5 늘린 롬](../../dq5/docs/dq5-build-format.md#늘린-롬)).
- `cleared`: `ranges` 가운데 뱅크 `30`~`3F` 의 거울을 0 으로 지운 곳. 1장 빌드는 그룹 패치를 얹기 전에 거울 바이트를 0 으로 둡니다([1장 문서](dq4-chapter1-format.md)). 거울 그대로이던 바이트가 0 이 된 칸이 32바이트(`CLEAR_MIN`) 넘게 이어지면 지운 자리로 봅니다. 뱅크 끝 0 줄도 이 길이를 넘어야 합니다. 거울이 원래 0 인 칸도 그 줄에 잇습니다. 새 자료 속의 0 은 짧게 끊겨 지운 자리로 보지 않습니다.
- 앞 단계와 같은 값을 다시 쓴 바이트는 바뀌지 않았으므로 장부에 없습니다. 검사는 이 한계를 출력과 보고(`limits`)에 늘 남깁니다.

## 검사

검사는 먼저 장부의 `base` 가 `rom/dq5.sfc` 와, 마지막 단계 SHA-1 이 결과 롬과 같은지, 장부에 단계 일곱(`dq4romledger.STAGES`)이 모두 있는지 봅니다. 곡·인물 단계가 빠진 장부(자원 저장소 없는 빌드)는 실패이고, `--allow-missing-stages` 를 줄 때만 경고로 낮춥니다. `--rom` 을 주지 않으면 장부와 같은 폴더의 마지막 단계 파일을 봅니다. 한 단계가 쓴 바이트는 `ranges` 에서 `cleared` 를 뺀 것입니다.

| 검사 | 보는 것 | 실패 |
| --- | --- | --- |
| 겹침 | 뒤 단계가 앞 단계가 쓴 바이트를 다시 씀. 바이트마다 마지막으로 쓴 단계를 들고 감. 지운 자리도 지운 단계가 주인이고, 뒤 단계가 쓰면 「비운 자리 다시 쓰기」로 따로 셈(지운 0 이 자료일 수 있어서) | `[[overlap]]` 에 없으면. 비운 자리 다시 쓰기는 `reuse = true` 항목만 받음 |
| 원래 롬 덮기 | 원래 롬(1.5MB)의 0 아닌 바이트를 덮은 곳을 16바이트(`GAP`) 이하 틈은 이어 덩어리로(뱅크 경계에서 자름). 64바이트(`BIG`) 이상인 덩어리 | `[[original]]` 에 없으면. 64바이트 미만(훅, 표 칸 고치기)은 단계마다 세어 보고만 함 |
| 뱅크 넘기 | 쓴 덩어리가 뱅크 경계(`xx:FFFF` → 다음 뱅크 `8000`)를 넘음 | `[[cross]]` 에 없으면. 높은 뱅크 사건 코드 덩어리(`dq4brkscan.blobs`)가 넘으면 늘 |
| 표 불변식 | 아래 표 | 하나라도 어기면 |

원래 롬의 빈 자리(뱅크 끝 0 줄, [DQ5 빈 자리 지도](../../dq5/docs/dq5-build-format.md#원래-롬))는 0 이라 원래 롬 덮기에 걸리지 않습니다. 옮긴 표가 떠난 원래 자리처럼 0 이 아닌데 비운 곳은 허용 목록에 그 까닭과 함께 적습니다. 원래 롬 덮기를 64바이트로 자른 까닭은 지금 빌드의 덮기 364곳 가운데 306곳이 64바이트 미만의 훅·표 칸이기 때문입니다(JSL·JML 훅은 아래 「훅」 불변식이 따로 봄). 큰 덮기는 표를 통째로 바꾸거나 그림·자료를 제자리에 바꾸는 것이라, 누가 무엇을 바꿨는지 허용 목록에 남깁니다.

### 허용 목록

`sfc/dq4/ledger-allow.toml` 은 dq4 트랙 파일입니다. 표는 셋입니다.

```toml
[[overlap]]
earlier = "title"          # 앞 단계, "*" 는 아무 단계
later = "overture"         # 뒤 단계
at = "30:801C~30:8021"     # 끝 포함. 한 바이트면 "30:801C"
why = "타이틀 코드의 LDA #$10 / JSL $24FE9A 를 서곡이 JSL $70FF00 으로 바꿈(…)"

[[original]]
stage = "people"
at = "0C:8000~0F:FFFF"
why = "…"

[[cross]]
stage = "menu"
at = "64:C400~69:FFFF"
why = "…"
```

- 겹침·덮기·넘기 덩어리는 한 항목의 `at` 안에 통째로 들어야 받습니다. 걸쳐 나가면 실패입니다.
- `max`(바이트)를 주면 그 항목이 받은 덩어리의 합이 그보다 크면 실패입니다. 넓은 자리를 적을 때 씁니다.
- `[[overlap]]` 의 `reuse = true` 는 앞 단계가 비운 자리를 뒤 단계가 쓰는 것만 받습니다. 없으면 보통 겹침만 받습니다.
- 자리는 실제로 쓰는 곳만큼 좁게 적습니다. 원래 자리를 그대로 바꾸는 자료는 그 원래 자료의 끝(예: 세트 타일은 `dq5sprite.set_tiles` 가 원래 롬에서 잰 끝)까지, 비운 자리를 쓰는 것은 그 도구가 정한 자리 상수(`dq4people.TILE_AREAS` 등)까지입니다.
- `why` 는 비우지 않습니다. 근거 문서나 도구 상수를 적습니다.
- 단계 이름은 `dq4romledger.STAGES` 에 있는 것이어야 합니다(자원 저장소 없이 빌드해 장부에 없는 단계도 받습니다).
- 맞는 쓰기가 없는 항목은 경고로 찍습니다. 경고가 나면 그 쓰기가 없어진 것이니 항목을 지웁니다.
- 의도를 모르는 덮어쓰기는 넣지 않습니다. 원인을 찾아 고치거나, 의도라면 근거를 찾아 적습니다.

### 표 불변식

| 이름 | 보는 것 | 읽는 법 |
| --- | --- | --- |
| `checksum` | 머리 체크섬(`00:FFDC`~`FFDF`)이 롬 합과 맞음 | `dq4romassets.set_checksum` 으로 다시 셈 |
| `vectors` | COP·BRK·NMI·IRQ·RESET 벡터(`00:FFE4`~`FFFE`)가 뱅크 `00` 의 `8000` 이상이고 첫 바이트가 `00`·`FF` 아님 | 롬 바이트 |
| `hooks` | 원래 롬 자리에 새로 쓴 JSL(`22`)·JML(`5C`)의 대상이 롬 안이고 0 바이트(BRK)가 아님 | 쓴 덩어리의 첫 바이트(첫 바이트가 원래와 같으면 한 바이트 앞)가 그 명령이고 피연산자 셋이 그 덩어리 안일 때만 훅으로 봄 |
| `shops` | 가게 목록: 키 찾기(`06:F4AE`)·품목 읽기(`06:F54E`)의 뱅크와 표 주소(`06:F4BA`·`06:F50D`)가 같고, 뱅크 `00`~`3F`, 종류 넷의 포인터가 앞으로 가고, `[키][품목…][FF]` 가 뱅크 안에서 끝나고, 품목이 물건 수(`D8`) 안 | [DQ5 상점](../../dq5/docs/dq5-build-format.md#성장조우상점-dq5progress1)과 같은 읽기 |
| `inns` | 여관 1인 값 표(`06:F568` 뱅크, `06:F56E` 주소)가 뱅크 `00`~`3F` 이고 앞 21항목이 원래 표(`04:FD6D`)와 같음 | `dq4shopport` 가 원래 표 뒤에 새 키를 더함 |
| `exits` | 출구·영역 이동 표가 엔진 순서로 끝까지 읽히고, 목적지가 있는 맵이거나 필드(그룹 `FF`) | `dq5exitreloc.parse`, `known_maps` |
| `messages` | 보행 메시지 전부가 옮긴 디코더·색인으로 풀리고 글자·제어 코드가 글자 묶음 표 안 | `dq5textwrite.base_package` |
| `people` | 인물 목록(그룹 포인터)과 인물마다 낮·밤 스크립트가 명령 길이대로 읽혀 길이 바이트와 맞음 | `dq5npc.all_lists`·`check_scripts` |
| `brkscan` | 높은 뱅크 사건 코드가 확인한 BRK 명령만 부름([호환성](dq4-compat-format.md)) | `dq4brkscan.scan` |

DQ5 디코더는 원래 롬과 지금 1장 롬 모두에서 같은 함수로 읽힙니다. 원래 롬에서 영역 이동 29곳의 목적지가 그룹 `FF`(필드)라 그 값을 받습니다.

## 남은 것
