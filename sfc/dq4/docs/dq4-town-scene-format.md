# 여관·교회·저장 칸 장면 검사

여관에서 묵기, 교회의 되살리기·해독·저주 풀기·계시·기도(저장), 타이틀의 기록 복사·지우기, 빈 SRAM 과 체크섬이 틀린 칸, 낮밤 경계를 장면 하나씩 libretro bsnes·snes9x 에서 돌려 WRAM·SRAM 값으로 판정합니다. 도구는 `sfc/dq4/tools/dq4townscene.py`, 회귀 가드는 [`guards.toml`](../guards.toml) 의 `dq4-town-scene` 입니다. 장면은 [저장 기록](dq4-savefixture-format.md)으로 이무르(`37/00`)에서 이어 해 시작합니다. 실측은 1장 롬(`dq4build.py` 출력 `dq4-ch1-full.sfc`, SHA-1 `c6cb51e6…`), snes9x 1.63 `fae2fea`·bsnes 115 `63ee22f7`([코어](dq4-compat-format.md#코어))로 했습니다.

## 고르기 창 알아보기

| 자리 | 내용 |
| --- | --- |
| `7E:0AD7` | 고르기 창의 커서 칸. 교회 메뉴(0~5), 예/아니요(0·1), 기록 목록(쓰인 칸 차례), 타이틀 메뉴(0~4)가 모두 씀 |
| `7E:0F20` | 여관 처리기가 도는 동안 `09`, 교회 처리기는 `0C`, 끝나면 `00` |
| `7E:0F28` | 여관이 셈한 값(1인 값 × 일행 수). 「하룻밤에 …골드」 쪽에서 쓰임 |
| `7E:00F6` | 계시가 셈한 남은 경험치(3바이트). 글자는 WRAM 에 그림(글리프)으로 그려져(`7E:5900`~ 근처가 값마다 다름) 숫자 칸을 바로 읽지 않고 화면으로 견줌 |

창이 떴는지를 알려 주는 WRAM 표지는 찾지 못했습니다. 교회 기도 대화 1,500프레임 동안 5프레임마다 WRAM 128KB 를 남기고, 그 프레임이 고르기 창이었는지(아래 프로브)와 견줘도 두 쪽을 가르는 바이트가 없었습니다. 그래서 5프레임마다 상태를 저장하고 아래(움직이지 않으면 위)를 눌러 `7E:0AD7` 이 바뀌는지 본 뒤 상태를 되돌립니다. 바뀌면 창이 입력을 기다리는 것이고, 정해 둔 칸까지 커서를 옮긴 뒤 A 를 누릅니다. 그 밖의 프레임에는 40프레임마다 A 로 글을 넘깁니다.

다음을 지켜야 했습니다.

- 필드 명령 창은 `7E:007F & 7` = 0 인 프레임에만 입력을 읽으므로 A 를 8프레임 누릅니다. 4프레임이면 명령 창의 「이야기하기」 가 빠져 다음 프로브가 같은 창을 또 봤습니다.
- 글 넘기기 A 를 누르고 있는 동안 창이 뜨면, 이어 누른 A 는 새 입력이 아니라서 먹히지 않습니다. 고르기 전에 12프레임 손을 뗍니다. 떼지 않았을 때 여관의 「예」 가 먹히지 않고 다음 창에서 B 가 눌려 묵지 않았습니다.
- 글 넘기기 A 가 막 뜨는 예/아니요를 기본값(예)으로 답해 버리는 일이 있었습니다. A 를 누르기 전에 16프레임 앞을 미리 돌려 보고(상태를 되돌림) 창이 뜰 거면 누르지 않습니다.
- 창이 막 뜬 프레임의 A 가 먹히지 않을 때가 있어(bsnes 해독의 예, snes9x 저주 풀기의 예), 고른 뒤에도 창이 그대로면 두 번까지 다시 누릅니다. 타이틀은 「모험을 한다」 뒤 기록 목록이 같은 커서로 바로 떠 다시 누른 A 가 목록을 고르므로 다시 누르지 않습니다.
- bsnes 는 소리 전송 중에 상태를 저장·되돌리면 손잡기가 풀리지 않아 멈췄습니다. 여관의 잠드는 연출(`7E:08D8`~ = `C0 00 00 00 00 00 7C C3 2B C0 01 06`)과 기도의 기록 징글에서 봤고, 같은 입력을 프로브 없이 넣으면 끝까지 갔으므로 검사의 탓입니다. 소리 대기열에 보낼 것이 남은 동안(`7E:1D91` ≠ `1D93`, `24:FE44` 와 같은 판정)은 프로브·미리 보기를 하지 않습니다. snes9x 는 멈추지 않았습니다.
- 정한 답을 다 쓴 뒤로는 프로브하지 않고 B 로 글을 넘깁니다(다시 뜬 메뉴는 B 가 닫음). 그래서 「멈춤」 을 판정하는 교회 장면은 멈춘 때에 상태 되돌리기가 섞이지 않습니다.
- 해독·저주 풀기는 일행이 주인공 하나면 「누구를」 창 없이 바로 값을 묻습니다. 처음에 「누구를」 답을 넣었더니 그 답이 다시 뜬 메뉴의 「기도하기」 를 골랐습니다.

장면마다 고르기 창이 정한 수만큼 떴고 창마다 정한 칸을 골랐는지도 판정합니다(`judge_choices`).

목록은 쓰인 칸만 차례로 보여 주므로, 칸 3 을 고를 때 칸 1·3 이 쓰여 있으면 커서 1 입니다.

### 기록과 이어 하기에서 본 것

- 기도로 칸 n 에 기록하면 그 칸의 상태가 `C0`, 앞서 `C0` 이던 칸은 `40` 이 됩니다(칸 2 에 기록: `40 C0 00`). 그래도 다음에 켜서 「모험을 한다」 를 고르면 기록 목록의 커서는 첫 쓰인 칸(칸 1)에 섰습니다. 원본 DQ5 도 같습니다. 칸 1·2 를 쓰고 칸 2 를 마지막 칸(`0F`~`11` = `00 C0 00`, 켠 뒤 `40 C0 00`)으로 둔 SRAM 으로 원본 `rom/dq5.sfc` 를 켜 「ぼうけんをする」 를 고르자 snes9x·bsnes 모두 기록 목록이 뜰 때 `7E:0AD7` = 0 이었고, 1장 롬도 snes9x 에서 0 이었습니다. 마지막 칸(bit7)으로 커서를 두는 `25:842E` 는 `04:CA9D` 에서 `$0A42` bit7 이 켜진 창의 항목이 `5D` 일 때만 불립니다(코드 읽기, 교회 기록 목록 쪽). 이어 하기 입력이 A 만 누르면 마지막 기록이 아니라 칸 1 로 이어 하므로, 검사는 칸을 직접 고릅니다.
- 빈 SRAM 에서 새 게임 입력을 넣으면 칸 2 를 씁니다(964프레임). 밑판 SRAM 을 만들 때와 같은 칸입니다.
- 기록 칸의 내용은 쓴 프레임의 WRAM 과 바이트까지 같았습니다(세 칸, 두 코어).
- 밑판(새 게임 첫 기록)은 맵 곡 건너뛰기 비트 `7E:21A5` bit6 이 켜진 채입니다. 이어 할 때 그 비트를 끄기 전의 롬에서는 이무르에서 이어 한 뒤에도 비트가 남아 곡이 없었고, 기도 기록에도 `40` 이 그대로 실려 그 기록으로 다시 이어 해도 곡이 없었습니다(snes9x). 지금 롬은 기도 기록이 `00` 이고, 다시 이어 하면 선 뒤 59~61프레임에 곡 `06` 이 울립니다(세 칸, 두 코어).

## 알려진 실패

`KNOWN` 에 둔 장면은 정확히 적어 둔 증상일 때만 `known` 으로 쳐 전체가 통과합니다. 항목마다 이슈 설명과 「고치면 이 항목을 지울 것」 을 적었습니다. 고쳐져 통과하거나 다른 증상이면 실패하므로, 고친 PR 이 그 항목을 지웁니다. `--no-known` 은 이 처리를 끕니다.

### 교회 치료 뒤 멈춤(고침)

소리를 넣은 롬에서 되살리기·해독·저주 풀기 뒤 「오오 신이시여! …주소서!」 에서 대화가 멈췄습니다(두 코어, 프로브 없이도, `7E:0F20` = `0C`). 소리를 넣기 전 롬은 끝까지 갔습니다.

교회 코드(`06:E03E`~, 원본 DQ5 와 바이트가 같음)는 세 치료 갈래에서 `LDA #$1E / JSL $25FD00`(`06:E17C`·`06:E29A`·`06:E308`)을 부릅니다. `25:FD00` 은 `1A`·`01 1E` 를 보낸 뒤 `24:FF0F` 에서 명령 `09 1E`(곡 `1E` 가 아직 울리는지)의 대답 `7E:08D2` 가 `7F` 가 될 때까지 돕니다. 소리 대응표가 이 자리에 되풀이하는 NDS 「コロシアム楽屋」(곡 `11`, 반복 시작 191틱)를 넣어 대답이 늘 `00` 이었습니다. 멈춘 끝에서 `7E:08D2` = `00`, `7E:1D8B` = `1E` 였습니다. 같은 롬의 세 자리를 `LDA #$25`(NDS 「教会治療」, 되풀이하지 않음)로만 바꾸자 세 장면이 두 코어 모두 1,742~1,863프레임에 끝났고 `7E:08D2` = `7F` 였습니다. 원본 DQ5 의 곡 `1E` 는 트랙 8개가 모두 `FF` 에서 끝납니다.

고친 것: 대응표에서 `1E` 에 NDS 「教会治療」(`28`)를 넣었습니다([사운드 포팅 「곡 끝을 기다리는 자리」](dq4-sound-port-format.md#곡-끝을-기다리는-자리2026-11-02)). 장면 결과에는 끝에서 읽은 `song_reply`(`7E:08D2`)·`song`(`7E:1D8B`)이 남습니다.

### 필드에서 시각 색이 바뀌지 않음(고침)

`dusk`·`dawn`·`cross` 가 두 코어 모두 낮 벌 그대로였던 것은 1장 롬의 문제였습니다. 아래 「낮밤 경계」 끝.

| `cross` | 붙들지 않고 `00EA` 에서 `00F3` 을, `01F9` 에서 `0003` 을 넘을 때까지 걷기 | 넘긴 뒤 버퍼가 표와 같고, 해 질 녘에 `7E:1AA1` 이 켜짐 |
| `town_edge` | 바트랜드에서 시각을 `00EF`(낮 끝)·`00F0`(밤 첫 값)에 붙든 채 이무르로 순간이동 | 인물 대화 번호 목록이 낮·밤으로 이어 한 이무르의 목록과 같고, 낮·밤 목록이 다름 |

기대 색은 검사할 롬이 아니라 원본 `rom/dq5.sfc`(`--dq5`)의 표에서 읽습니다. 포팅이 쓴 표를 그대로 기대값으로 삼으면 표가 틀려도 통과하기 때문입니다. 시각 표 읽기: `01:A16B` 의 `[하한 16비트][색인 × 2]` 항목 10개를 뒤에서부터 보아 하한이 시각 이하인 첫 항목의 색인으로 `01:A189` 의 벌 주소를 고릅니다. 색인 `0C` 이상이면 인물 줄은 `01:A422`(밤), 아니면 `01:A45E` 입니다. 1장 롬의 표·벌은 원본 DQ5 와 같습니다(`01:A199`·`A19A` 의 세계 1 벌만 다름). 필드는 이무르에서 이어 해 바트랜드 출구 앞 `36/00` (28,81)으로 순간이동한 뒤 아래로 걸어 나갑니다.

| 장면 | snes9x | bsnes |
| --- | --- | --- |
| `town_edge` | 통과: `00EF` 에 16명(낮, `006 94A 005 …`), `00F0` 에 10명(밤, `006 955 005 …`) | 같음 |
| `dusk` | 통과: `00ED`~`00F2` 가 1·17·8·8·8·8프레임 걸어 표 벌과 같아짐 | 같음(`00EE` 만 18) |
| `dawn` | 통과: `01FC`~`0002` 가 18·8·8·1·7·8·8프레임 | 같음(`01FC` 만 19) |
| `cross` | 통과: 해 질 녘 87프레임에 낮 → `EE` → `EF` → `F0` → `F1`(`7E:1AA1` 1) → 밤, 새벽 80프레임에 밤 → `F1` → `F0` → `EF` → `EE` → 낮 | 같음(해 질 녘 88) |

원인: 환경 훅 `wrap`(`15:F7D0` 을 부르는 `01:8F84`·`01:98FC`·`01:9FD6` 자리, [환경 문서](dq4-environment-format.md#물-애니메이션))이 바꾼 맵인지를 `$BC`/`$BD` 로만 보았습니다. 필드에서도 `$BC`/`$BD` 는 막 나온 마을(바트랜드 `36/00`)을 가리켜, 필드로 나갈 때(`01:9FD6`) 원래 고른 매 프레임 루틴 `02:AB33`(바다 타일과 시각 색 `02:AD2B` → `01:A055`)을 물 루틴 `3D:E620` 으로 덮었습니다. MesenCE 로 바트랜드에서 걸어 나가자 `wrap` 이 `15:F7D0` 에서 돌아온 직후 `7E:1AA6` = `02:AB33` 이었고 끝나면 `3D:E620` 이었습니다(그때 `$BE` = `00`). 필드에서 시각을 `0120` 에 붙든 채 600프레임 걸으니 `02:AD2B` 가 한 번도 돌지 않았고, 원본 DQ5 필드 상태(`work/state/field-free.mss`)는 같은 조작에 프레임마다 돌아 `01:A055` 를 75번 불렀습니다.

고친 것: `wrap` 이 `$BE` bit7 이 꺼져 있으면(필드) 원래 고른 루틴을 그대로 둡니다. 고친 롬을 MesenCE 로 같은 길로 걸어 나가 `0120` 에 붙들자 30프레임 안에 `7E:3956` = `4E60`, CGRAM 2번 줄 색 1 = `4E60`, 11번 줄 색 1 = `4A52`, `7E:1AA1` = 1 로 원본 DQ5 와 같은 값이 되었습니다. libretro 두 코어의 `daynight` 도 위 표처럼 통과해 `KNOWN` 에서 지웠습니다. 진입 방식(이어 하기·libretro)의 차이가 아니었습니다.

## 옛 롬의 기록(`oldsave`)

`DQ4_ASSETS`(비공개 에셋 저장소)의 이력에서 1장 IPS 를 꺼내(기본은 가장 오래된 커밋) 원본 DQ5 에 입히고, 그 롬의 새 게임 기록을 지금 롬으로 이어 한 결과를 `results.json` 에 남깁니다. 판정은 하지 않습니다.

| 옛 IPS | 옛 롬 | 결과 |
| --- | --- | --- |
| 에셋 `7045fb1`(sfc-dq4 `01fe3c9d`) | SHA-1 `61455fa0…` | 옛 롬의 새 게임 기록(칸 2)이 지금 롬의 것과 `AA0` 바이트가 같음. 지금 롬으로 이어 하면 두 코어 모두 `3C/01` (6,30)(snes9x 422, bsnes 423프레임)에 서고 칸 2 그대로, 기록 칸과 다른 바이트는 맵에 들어설 때 고치는 넷 밖에 3개 |

새 게임 기록만으로는 두 판의 형식 차이가 드러나지 않습니다. 옛 판에서 진행한 기록(flag·일행이 바뀐 칸)은 옛 롬을 걸어야 만들 수 있어 넣지 않았습니다.

## 사용법

```sh
uv run --locked python sfc/dq4/tools/dq4build.py --out work/ch1
uv run --locked python sfc/dq4/tools/dq4cores.py
uv run --locked python sfc/dq4/tools/dq4townscene.py check --rom work/ch1/dq4-ch1-full.sfc --out work/townscene --jobs 4
uv run --locked python sfc/dq4/tools/dq4townscene.py daynight --rom work/ch1/dq4-ch1-full.sfc --out work/townnight --jobs 4
DQ4_ASSETS=… uv run --locked python sfc/dq4/tools/dq4townscene.py oldsave --rom work/ch1/dq4-ch1-full.sfc --out work/oldsave
```

`--only 장면…` 으로 일부만, `--core bsnes|snes9x` 로 한 코어만, `--seeds 0,5` 로 난수 시드(`dq4ch1walkcheck.rng_for`)를 여럿 돌립니다. 장면마다 프로세스 하나가 코어 하나를 열고(같은 dylib 을 한 프로세스에서 여러 번 열지 않음), 결과는 `<out>/seed<시드>/<코어>/<장면>/result.json`·`end.png` 와 `<out>/results.json` 입니다. 여관 값의 기준은 FC 롬(`--dq4`, 기본 `rom/dq4.nes`)입니다.
