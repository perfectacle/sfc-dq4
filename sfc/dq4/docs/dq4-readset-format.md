# 읽은 롬 바이트 캐시

헤드리스 장면 검사의 MesenCE 실행 하나를 「그 실행이 실제로 읽은 롬 바이트」 단위로 캐시한다. 롬이 바뀌어도 장면이 읽은 바이트가 그대로면 다시 돌리지 않고 출력 파일을 펼친다. 도구는 `sfc/dq4/tools/dq4readset.py`(캐시), `sfc/dq4/tools/lua/dq4readset.lua`(머리말), `sfc/dq4/tools/dq4readsetcheck.py`(건전성 검사)다.

지금 이 캐시를 쓰는 곳:

- 창 글자 검사(`dq4windowcheck.py`)의 장면과 출발 상태(서장 시작·서장 걷기·순간이동).
- 필드 팻말 검사(`dq4signcheck.py`)의 순간이동 장면과 팻말 장면.
- 전투 메시지 검사(`dq4battlemsgcheck.py`)의 묶음 장면.
- `dq4groupcheck.scene`(순간이동 장면)을 거치는 검사 모두. 기본이 캐시를 거친다(`readset=False` 면 거치지 않음): 그룹 롬 장면(상자·필드·필드 조우·ルーラ), 문 열기·문 칸, 성문, 던전 조우, 우물 스위치, 그룹 연결.
- 상자 검사(`dq4chestcheck.py`)의 조사 장면, 우물 스위치 검사(`dq4wellresetcheck.py`)의 기록·리셋·이어 하기 장면, 보행 메시지 이름 검사(`dq4namegamecheck.py`).
- 서장 끝에서 걷는 검사: 주인공이 선 칸(`dq4heroblockcheck.py`), 환경 훅 wrap(`dq4wrapcheck.py`), 필드 OBJ 반투명(`dq4fieldmathcheck.py`)의 장면 모두. 전투 검사(`dq4battlecheck.py`)는 서장과 자리 잡기 구간만 거친다. 전투 실행은 같은 상태에서 여러 번 돌려 결과가 같은지 보고 화면을 견주므로 캐시를 거치지 않는다.
- 장면형 검사의 출발 상태(`dq4freshstate.make`): 서장 끝(서장 시작·서장 걷기)과 배 선실. 같은 롬 SHA-1 로 만든 상태 캐시가 없을 때 이 캐시로 걷기를 건너뛴다.

## 왜 건전한가

검사 장면은 결정적이다(난수·시각·입력 고정). 실행 한 걸음은 (기계 상태, 그 걸음에 읽은 롬 바이트, 입력)으로 정해진다. 출발 상태와 입력이 같고, 지난 실행이 읽은 오프셋의 바이트가 지금 롬에서도 모두 같으면, 새 롬에서도 같은 주소를 같은 차례로 읽는다. 처음으로 다른 주소를 읽으려면 그 전에 다른 값을 읽었어야 하는데, 그 전 읽기는 모두 기록된 오프셋이고 값이 같다. 그래서 키를 계산하려고 먼저 돌릴 필요가 없다. 지난 실행의 읽은 집합으로 지금 롬을 해시해 견주면 된다.

## 읽은 집합

머리말 Lua 가 장면 스크립트보다 먼저 돌며 다음 셋의 합집합을 `READSET_OUT` 에 「시작 길이」(16진) 줄로 쓴다.

| 출처 | 얻는 법 |
| --- | --- |
| CPU 데이터 읽기, DMA 원본 읽기, HDMA 표 읽기 | `emu.getAccessCounters(emu.memType.snesPrgRom, emu.counterType.readCount)`. 인자는 메모리 종류가 먼저다 |
| 실행한 명령(오퍼랜드 바이트 포함) | 같은 함수의 `execCount`. 실행 바이트는 readCount 에 잡히지 않는다 |
| Lua 의 `emu.read`·`readWord`·`read16`·`read32` | 카운터에 잡히지 않아 머리말이 감싸 따로 적는다. CPU 주소는 `emu.convertAddress` 로 롬 오프셋으로 바꾼다 |

- 카운터는 롬 파일 오프셋 단위라 LoROM 미러·뱅크를 따로 바꿀 필요가 없다.
- 첫 세이브스테이트를 불러올 때의 카운터를 밑값으로 두고, 그 뒤 늘어난 바이트만 센다. 상태가 기계 전체를 덮으므로 그 전의 읽기는 결과에 남지 않는다. 그보다 먼저 상태를 만든 적이 있으면 밑값을 두지 않는다.
- 장면이 `emu.resetAccessCounters` 를 부르면 지우기 전까지 읽은 것을 쌓아 둔다.
- `emu.stop` 뒤에도 프레임이 더 돈다. 몇 프레임인지는 실행마다 다르다. 그 사이 장면 콜백이 기록을 더 쓰면 출력이 실행마다 달라진다.
  - 캐시 없이 그룹 롬 필드 검사를 두 번 돌렸다. 254개 출력 가운데 `terrain-0A-right`·`w1-terrain-04-right` 의 `warp.txt`·`final.wram` 만 달랐다.
  - 한 번은 `dq5warp.lua` 가 멈춘 뒤 한 프레임 더 `finish()` 를 불러, 다른 걸음 결과(`moved=yes`)를 덧붙였다.
  - 그래서 머리말은 `emu.stop` 을 부른 뒤로 장면 콜백을 부르지 않는다. 읽은 집합도 `emu.stop` 때 한 번만 쓴다.
- 전제: 장면의 출력(기록 파일·덤프·세이브스테이트)은 모두 `emu.stop` 을 부르기 전에 쓴다. stop 뒤에 쓰는 출력은 남지 않는다. 세이브스테이트처럼 다음 명령에서 쓰이는 것은 다 쓴 뒤에 stop 을 부른다(`dq4walkstate.lua`, `dq5chestcheck.lua`).
- testrunner 에서는 `scriptEnded` 사건이 오지 않는다.
- `READSET_HDMA` 를 주면 HDMA 가 켜질 때 롬에 있는 표 첫 바이트가 읽은 집합에 들었는지 `.readset.txt.hdma` 에 적는다(건전성 검사용).

## 키

두 단계로 찾는다.

```text
index_key = SHA-256(판, 장면 스크립트 이름, Lua 코드, 에뮬레이터, 환경 변수, 출발 파일, 롬 모양)
work/cache/readset/index/<앞 2자>/<index_key>.json = [항목, …]   최근에 맞은 것부터 8개
항목 = {ranges(읽은 구간, zlib), digest(지금 롬의 그 구간 해시), files(출력 상대 경로 → blob SHA-256), returncode, when}
```

| 키 칸 | 내용 |
| --- | --- |
| Lua 코드 | `tools/lua`·`sfc/dq4/tools/lua`·`sfc/dq5/tools/lua`·`LIBDIR` 의 모든 `.lua`, 장면 스크립트, 머리말. 하나라도 바뀌면 모든 장면이 빗나간다 |
| 에뮬레이터 | MesenCE 실행 파일의 크기·mtime, 명령줄 인자, 고정 인자(`--Snes.RamPowerOnState=AllZeros --Snes.EnableRandomPowerOnState=false`), 사용자 `settings.json` 원 바이트의 해시. 고정 인자 없이 띄우면 이 머신 설정(`RamPowerOnState: Random`)으로는 전원을 켠 첫 프레임의 WRAM 이 무작위였다. 이 인자로 0, `AllOnes` 로 FF 가 되는 것을 실측했다 |
| 환경 변수 | 위 Lua 가 `os.getenv` 로 읽는 이름의 값만. 경로는 내용으로 바꾼다: 출력 폴더 안이면 상대 경로(아직 없는 출력 경로도), 파일이면 해시(세이브스테이트는 롬 이름을 지운 해시), Lua 폴더면 `code`, 그 밖의 폴더면 안 파일들의 해시. 상대 경로는 Lua 가 도는 작업 폴더 기준으로 본다. 출력 폴더 밖의 없는 절대 경로는 `absent:` 를 붙인다(나중에 그 자리에 파일이 생기면 빗나간다). `SHOT_DIR`·`READSET_*` 는 뺀다 |
| 출발 파일 | 돌리기 전에 출력 폴더에 있던 파일의 해시 |
| 롬 모양 | 롬 크기와 머리 `$7FB0~$7FFF` 가운데 체크섬 `$7FDC~$7FDF` 를 뺀 것. 전원·리셋 때 리셋 벡터(`$7FFC`)를 읽는 것은 카운터에 잡히지 않는다(실측: 그 두 바이트만 뒤집어도 서장 시작 상태가 달라짐). 에뮬레이터가 매핑을 정할 때 읽는 칸도 잡히지 않는다. 체크섬은 빌드마다 바뀌는데, 뒤집어도 결과가 같았다(건전성 검사가 늘 뒤집어 본다) |

키를 만든 롬 바이트는 실행 폴더에 사본(`.readset-rom.sfc`)으로 써서 그 사본으로 MesenCE 를 띄운다. 키를 만든 뒤 롬 파일이 바뀌어도 키와 실제로 돌린 롬이 같다. 사본은 실행 뒤 지우고 출력으로 치지 않는다.

찾을 때는 `index_key` 의 항목마다 지금 롬을 그 항목의 구간으로 해시해 `digest` 와 같은 항목을 최근 것부터 본다. 그 항목의 blob 을 모두 읽을 수 있으면 `files` 를 출력 폴더에 펼친다. 하나라도 없거나 깨졌으면 그 항목을 지우고 다음 맞는 항목을 본다. Python 이 출력으로 하는 판정은 캐시하지 않고 매번 돈다. 그래서 판정이 롬을 직접 읽어도 키에 넣지 않아도 된다. 장면 입력을 Python 이 롬에서 만들면(창 검사의 `SET`) 그 값이 환경 변수로 키에 들어간다.

## 세이브스테이트와 배터리 기록

- MesenCE 세이브스테이트 머리에는 띄운 롬 파일 이름이 들어 있다. `dq4mesen.unique_copy` 가 실행마다 이름을 다르게 지으므로 같은 실행이라도 상태 파일이 12바이트 다르다. 상태 해시는 이 이름 칸을 지우고 낸다(`state_hash`). 이름은 압축한 화면 그림 뒤에 와서 그림 크기에 따라 자리가 바뀐다(8KB 뒤에 온 상태도 있었다). 그래서 파일 전체에서 찾는다. 상태 안에 롬 SHA-1·CRC 는 없다. MesenCE 는 상태를 불러올 때 이 이름을 보지 않는다. 그룹 롬 선실 상태의 이름 칸만 같은 길이의 다른 이름으로 바꿔 불러도, 120프레임 뒤 WRAM 128KB 가 원래 상태와 같았다(두 번씩). 다른 상태를 불러오면 달랐다. 그래서 캐시에서 펼친 상태(첫 실행의 롬 사본 이름이 든 것)로 다음 장면을 출발해도 된다.
- MesenCE 는 롬 파일 이름으로 배터리 기록(`.srm`)을 읽는다. 롬을 같은 이름으로 띄우면 앞 실행의 SRAM 을 읽어 결과가 달라진다. 그래서 캐시 실행은 롬을 복사해 띄우는 `dq4mesen.run` 만 쓰고, 복사하지 않는 `dq4mesen.testrunner` 는 쓰지 않는다. `dq4mesen.clear_saves` 는 그 이름의 `.srm` 과 `Debugger/<이름>.cdl` 을 지운다. `.cdl` 은 롬 크기만 해서 실행마다 쌓이면 디스크를 채운다.

## 환경 변수

| 이름 | 뜻 |
| --- | --- |
| `DQ4_READSET=off` | 캐시를 읽지 않고 모두 돌린다(새 결과는 씀). `tools/guards.py --no-cache` 가 켠다. 배포 관문은 이것으로 돈다 |
| `DQ4_READSET_VERIFY` | 캐시가 맞은 장면 가운데 이 비율(기본 0.05)을 다시 돌려 출력을 견준다. 다르면 그 항목을 지우고 검사를 멈춘다(키에 빠진 입력이 있다는 뜻). 화면 찍기(`.png`)는 견주지 않고 다르면 알리기만 한다(아래) |
| `DQ4_READSET_CACHE` | 캐시 뿌리. 기본은 원래 체크아웃 `work/cache/readset`(워크트리끼리 함께 씀). 잠금(`.lock`)도 이 뿌리 안에 있어, 다른 뿌리를 준 실행과는 잠금을 함께 쓰지 않는다(뿌리가 다르면 같은 파일을 만지지 않으므로 그래도 된다) |
| `DQ4_READSET_MAX_GB` | 캐시 상한(기본 20). 넘으면 오래 안 맞은 index 부터 지우고 가리키는 곳이 없는 blob 을 지운다. 항목의 blob 과 index 는 한 잠금 안에서 쓰고(이미 있는 blob 도 풀어 내용 해시를 보고, 깨졌으면 다시 쓴다), 맞은 항목을 맨 앞으로 옮길 때 그 사이 지워진 항목은 되살리지 않는다. 읽으려는 blob 이 없거나 깨졌으면 그 항목을 지우고 빗나감으로 친다 |
| `DQ4_READSET_STATS` | 이 파일에 실행마다 JSON 한 줄(장면 스크립트, 출력 폴더, 맞았는가, 읽은 바이트 수, 종료 코드)을 덧붙인다. 적중률을 잴 때 쓴다 |

캐시는 `work/` 아래라 커밋되지 않는다. 롬·상태 파생물이므로 커밋하지 않는다(ROM-01).

## 건전성 검사

`dq4readsetcheck.py` 는 가벼운 장면 두 개(전원부터 서장 첫 장면까지, 그 상태에서 버튼을 눌러 걷고 창을 여는 것)마다 다음을 본다. `guards.toml` 의 `dq4-readset-soundness` 다.

- 결정성: 두 번 돌린 출력과 읽은 집합이 같다.
- 밖: 읽은 집합과 키에 든 머리 밖 바이트를 모두 뒤집은 롬(체크섬 포함)에서도 새로 돌린 출력·읽은 집합이 같다.
- 적중: 그 롬으로 캐시를 켜고 돌리면 맞고, 펼친 출력이 새로 돌린 출력과 같다.
- 입력(field): 캐시를 켠 채 환경 변수 값 하나, 에뮬레이터 명령줄 하나, 출발 상태 내용을 바꾸면 빗나간다. 출발 상태 파일을 다른 경로로 옮기기만 하면 맞는다.
- 안: 읽은 집합 안 바이트 하나를 바꾸면 캐시가 빗나간다.
- HDMA: 게임 장면의 HDMA 표 첫 바이트가 롬이면 읽은 집합에 들어 있다.
- 합성 장면(`lua/dq4readsetsynth.lua`): 창 글자 검사 76장면에는 롬을 표로 쓰는 HDMA 가 없다. 그래서 롬 `FE:8000` 에 다섯 바이트 표를 써 두고 채널 7 로 켜고, Lua 로 롬을 읽는다(`emu.read` 롬·CPU 주소, `emu.readWord`). 표 바이트와 Lua 가 읽은 바이트가 모두 읽은 집합에 들어야 한다. HDMA 표 읽기는 readCount 에 잡힌다.

- 오류 장면(`lua/dq4readseterr.lua`): 장면 Lua 가 맨 위·콜백 안·`emu.stop` 바로 뒤에서 오류를 내면 0 이 아닌 종료이고 캐시에 없다.
- 출력은 화면 찍기(`.png`)를 빼고 견준다(아래, 재검증과 같은 기준).

## 장면 Lua 의 오류

MesenCE `--testrunner` 는 장면 Lua 의 오류를 늘 0 이 아닌 종료로 알리지 않는다. 실측:

| 오류 자리 | 머리말이 없을 때 |
| --- | --- |
| 스크립트 맨 위 | 멈추지 않고 시간 초과까지 돈다 |
| 콜백 안(그 뒤 `emu.stop(0)`) | 오류를 삼키고 콜백이 다음 프레임에도 불려 0 으로 끝난다 |
| `emu.stop(0)` 바로 뒤 같은 콜백 | 0 으로 끝난다 |
| `emu.stop(0)` 다음 프레임 | 그 프레임이 돌지 않아 오류가 나지 않는다 |

로그(표준 출력)에도 아무것도 남지 않는다. 그래서 이렇게 막는다.

- 머리말은 자기 콜백을 걸기 전에 `emu.addEventCallback`·`emu.addMemoryCallback` 을 바꿔, 넘어온 함수를 `pcall` 로 감싼다. 반환값은 개수까지 그대로 넘기고, 오류는 다시 던져 동작은 그대로다.
- 오류가 나면 머리말은 읽은 집합 파일을 지우고, 표준 오류와 `READSET_OUT.err` 에 적는다. 그 뒤 쓰는 읽은 집합은 끝줄이 `LUAERROR` 다.
- 진입 파일은 장면 스크립트를 `pcall(dofile, …)` 로 불러, 맨 위 오류를 적은 뒤 `emu.stop(1)` 한다.
- Python 은 읽은 집합 끝줄이 `OK` 일 때만 캐시에 넣는다. `.err` 가 있거나 끝줄이 `OK` 가 아니면 종료 코드를 70(`LUA_ERROR`)으로 바꾼다. 그래서 `.err` 를 쓰지 못해도 캐시에 들지 않는다.

장면이 스스로 실패를 알면서 `emu.stop(0)` 으로 끝나는 경우도 캐시에 넣지 않아야 한다. 이 캐시를 쓰는 장면 Lua 를 훑은 결과는 이렇다.

| 장면 Lua | 실패를 아는 자리 | 처리 |
| --- | --- | --- |
| `dq5warp.lua`(순간이동, `dq4battlemsgswap.lua` 의 DRIVER) | `MAXF` 에 닿으면 「timeout phase=」 를 적고 `emu.stop(0)` | `run(accept=warp_finished)` 가 넣지 않는다(`dq4groupcheck.scene`, `dq4ch1walkcheck.run` 의 순간이동, 전투 메시지 검사). dq5 트랙 파일이라 Lua 는 고치지 않았다 |
| `dq4shipstate.lua` | 선실에 못 닿으면 `emu.stop(1)` | 종료 코드로 걸러진다 |
| `dq5msg.lua`, `dq5chestcheck.lua`, `dq5cdldump.lua`(NEXT=dq5msg), `dq4namegamecheck.lua`, `walk.lua`·`dq4walkstate.lua`, `mkstate.lua`(툴킷 boot.lua) | 없음: 정한 프레임에 기록을 쓰고 멈춘다 | 성공·실패는 Python 판정이 매번 기록을 보고 정한다. 결정적인 실행이라 캐시에서 펼친 기록도 같은 판정을 받는다 |

MesenCE 는 Lua 콜백 하나를 벽시계 시간 제한(사용자 설정 `Debug.ScriptWindow.ScriptTimeout`)으로 끊는다. 오류는 「Maximum execution time (N seconds) exceeded.」 다.
- 머신이 바쁠 때 그룹 롬 필드 검사의 순간이동 장면(`dq5warp.lua` 의 `finish()` 안)에서 나왔다.
- 같은 일(화면 찍기, WRAM 128KB 덤프, 머리말의 읽은 집합 쓰기)을 한가할 때 CPU 시간으로 재면 제한보다 한참 짧다. 제한은 벽시계로 재므로, 덤프를 빠르게 해도 바쁜 머신에서 스레드가 밀리는 것은 막지 못한다.
- MesenCE Lua API(실행 파일에 든 목록)에 메모리를 덩어리로 읽는 함수는 없다.
- 명령줄 `--Debug.ScriptWindow.ScriptTimeout=…` 으로는 늘어나지 않았다(제한보다 오래 도는 콜백이 그대로 끊김). 같은 꼴의 `--Snes.RamPowerOnState` 는 먹었다.
- 필요 조건: 헤드리스 검사를 돌리는 머신은 이 사용자 설정을 10초 이상으로 둔다(MesenCE 설정 화면, 또는 사용자 `settings.json` 의 `Debug.ScriptWindow.ScriptTimeout`). 1초 같은 짧은 값에서는 바쁜 머신에서 큰 덤프를 쓰는 콜백이 끊겨 그 검사가 종료 코드 71 로 실패한다. 설정 파일 해시는 읽은 바이트 캐시 키와 회귀 가드 캐시 키(`tools/guards.py`)에 함께 들어 있어, 바꾸면 두 캐시가 한 번 모두 빗나간다.
- 그래도 바쁜 머신에서 걸리면, 그 실행은 다시 돌리지 않는다. 종료 코드 71(`LUA_WATCHDOG`)과 「시간 제한으로 끊음」 알림으로 분명히 실패시키고, 캐시에 넣지 않는다.

시간이 초과된 실행은 끝줄 `OK` 를 썼어도 캐시에 넣지 않고, 「장면 Lua 오류」 가 아니라 시간 초과로 알린다. `dq4groupcheck.scene` 은 시간 초과, 0 이 아닌 종료, `dq5warp.lua` 가 MAXF 에 닿아 멈춘 장면을 판정에서도 `{"error": …}` 로 돌려준다(MAXF 에 닿아도 종료 코드는 0 이고 「end map」 이 찍힌다). 전투 메시지 검사는 멈춘 묶음을 남은 번호로 다시 돌리는 것이 판정이라 저장만 막는다. `dq5warp.lua` 는 도착하면(settle 단계에 들 때) 「arrived map」 을 찍고, 그 뒤 settle·test 단계에서 MAXF 에 닿으면 「timeout phase=」 도 찍는다. 그래서 「arrived map」 만 보는 판정은 MAXF 에 닿은 장면을 통과시킨다. `warp.txt` 를 읽는 판정은 `dq4readset.warp_timed_out` 으로 이것을 먼저 보고 실패(도착 못 함)로 친다: 걷기 검사의 순간이동 구간(`dq4ch1walkcheck.segment`), 주인공 칸 검사(`dq4heroblockcheck` 의 순간이동과 출발 상태), 환경 훅 검사(`dq4wrapcheck`), 환경 롬 검사(`dq4environmentromcheck.warp`, 문 연 성문 장면 포함), BG3 슬롯 검사(`dq4bg3slotcheck.arrival_of`), 저장 검사의 교회 순간이동(`dq4ch1savecheck.church`), 인물·상점 대화 검사(`dq4npccheck.run`). 걷기 구간의 판정은 「arrived map」 의 맵만 보고 칸은 보지 않는다.

감싸도 콜백을 지우는 데는 문제가 없다. MesenCE 의 `removeMemoryCallback`·`removeEventCallback` 은 add 가 돌려준 번호로 찾는다(실측: 머리말이 없을 때도 함수를 넘기면 지워지지 않고, 번호를 넘기면 머리말이 있어도 지워진다). 이 저장소의 Lua 는 모두 번호를 넘긴다. 반환값도 실측했다. 7E:0000~00FF 읽기 콜백이 아무것도 안 돌려줄 때, nil 일 때, 값 하나일 때, 값 둘일 때 모두 300프레임 뒤 WRAM 이 머리말 있음·없음 모두 같았다.

감싸기는 콜백마다 `pcall` 하나를 더한다. 명령마다 불리는 전 범위(00:0000~FF:FFFF) 실행 콜백을 오래 거는 장면은 눈에 띄게 느려진다. 지금 이 캐시를 쓰는 장면 Lua 의 메모리 콜백은 몇 PC·주소에만 걸리고, 전 범위 실행 콜백은 툴킷 `lib.lua` 가 세이브스테이트를 불러올 때 한 명령만 건다.

## 화면 찍기는 결정적이지 않다

같은 롬·같은 출발 상태로 같은 장면을 돌려도 `emu.takeScreenshot` 으로 찍은 화면은 다를 수 있다. 창 글자 검사의 `talk08` 장면을 캐시 없이 세 번 돌리자 메모리·VRAM 덤프(`msg.txt`, `v*.bin` 48개)는 세 번 모두 같았는데, 화면 49장 가운데 4장이 한 번씩 달랐다(그 가운데 하나는 메시지 창 안 112픽셀).

그래서 재검증과 건전성 검사는 `.png` 출력을 견주지 않는다. 다르면 표준 오류에 알리고 결과의 `screens_differ` 에 적기만 한다. 이 캐시를 쓰는 검사의 판정은 화면 찍기를 읽지 않는다(사람이 보는 모음 그림에만 쓴다). 단위 테스트가 `dq4readset` 을 import 하는 검사에서 PIL `Image.open` 이 `sheet*` 함수 밖에 있거나 화면 파일 이름을 직접 읽으면 실패한다. 화면으로 판정하는 검사를 옮길 때는 판정을 덤프로 바꾸거나 화면을 결정적으로 찍는 방법부터 정한다.

## libretro bsnes

libretro API 에는 메모리 읽기 훅이 없다. 그래서 `dq4cores.py` 가 bsnes 를 빌드할 때 패치(`sfc/dq4/tools/dq4cores-bsnes-romtrace.patch`)를 얹는다.

- 이 bsnes(63ee22f7)에서 카트리지 롬 읽기는 모두 `Bus::read` → 카트리지 롬 `ReadableMemory::read` 를 지난다. 명령 가져오기·데이터 읽기·DMA·HDMA 가 다 그렇다. 패치는 이 함수에 비트맵 한 줄을 넣는다. 포인터가 비어 있으면(기본) 아무것도 하지 않는다.
- 비트맵은 `retro_get_memory_data(0x5244)`·`retro_get_memory_size(0x5244)` 로 꺼낸다. 패치 전 이 코어는 모든 id 에 빈 값을 돌려줬다. `dq4libretro.Core(trace=True)`·`trace_ranges()` 가 이것을 쓴다.
- 비트맵은 코어를 연 바로 뒤에 켠다(`Core(trace=True)`, `dq4savefixture.open_core(..., trace=True)`). 켜기 전에 코어가 돈 몫은 비트맵에 들지 않는다. `retro_serialize` 도 코어를 동기 지점까지 돌린다.
  - 실측: 저장 기록을 맞춰 보는 직렬화 뒤에 켰더니, 읽은 집합 밖을 뒤집은 롬에서 이어 하기가 자리에 서지 못했다.
  - 열 때 켜자 같았다.
- 패치 해시는 코어 도장(`work/cores/bsnes.json` 의 `patch`)에 들어간다. 패치가 바뀌면 다시 빌드한다.
- 건전성 검사 `dq4libretroreadsetcheck.py`(`guards.toml` 의 `dq4-libretro-readset-soundness`)는 두 장면을 본다.
  - 장면: 전원부터 정한 입력 1500프레임, 그리고 저장 기록으로 이무르에서 이어 한 뒤 걷기.
  - 결정성: 두 번이 같다.
  - 밖: 읽은 집합과 머리 밖을 모두 뒤집은 롬(체크섬 포함)에서 화면·WRAM·읽은 집합이 같다.
  - 안: 안 바이트 하나로 읽은 바이트 해시가 달라진다.
- snes9x 는 패치하지 않는다. 명령 가져오기(`CPU.PCBase`)·`S9xGetByte` 의 메모리 맵·DMA 가 롬을 직접 포인터로 읽어, 고칠 자리가 여러 곳이고 빠뜨리기 쉽다. snes9x 장면은 캐시 없이 늘 돈다.
- 건전성 검사는 비트맵을 켜지 않은 실행도 견준다(「호환」). 같은 장면의 화면·WRAM 이 켠 실행과 같아야 한다. 패치가 에뮬레이션을 바꾸지 않는다는 근거다. 호환성 검사(compat-walk 등)도 이 패치한 코어로 돈다. `--original` 로 패치하지 않은 bsnes 를 주면 그 코어와도 견준다. 같은 커밋을 패치 없이 빌드한 코어(출력 SHA-256 은 원래 도장과 같음)와 두 장면 모두 화면·WRAM 이 같았다.
- **아직 키로 쓰지 않는다.** 이 비트맵으로 캐시를 켠 libretro 검사는 없다. 모든 libretro 장면 검사는 지금도 매번 돈다. 비트맵과 건전성 검사만 먼저 두었다.
- 장면 단위로 옮길 때의 설계(구현은 장면을 옮기는 단계에서 한다).
  - libretro 장면은 MesenCE 처럼 프로세스 하나가 아니라 파이썬 안의 `Core` 다. 드라이버(`dq4compatcheck.Walker`, 각 `*scene.py`)가 WRAM 을 읽어 다음 입력을 정한다. WRAM 은 에뮬레이션의 결과라 읽은 롬 바이트로 이미 덮인다.
  - 드라이버가 파이썬에서 롬 파일을 직접 읽어 입력이나 덮어쓸 값을 만드는 자리(이름 표, 출구 표, 장면 표 등)는 비트맵에 잡히지 않는다. 그래서 드라이버에는 롬 대신 `TrackedRom` 을 넘긴다. `TrackedRom` 은 `bytes` 처럼 동작하고 읽은 조각의 (시작, 길이) 를 적는다. 장면이 끝나면 그 구간을 코어 비트맵의 구간과 합쳐 키에 넣는다.
  - `TrackedRom` 을 거치지 않고 롬을 읽는 길(파일을 다시 열기, `Path.read_bytes()`)이 드라이버에 남지 않도록, 장면을 옮길 때마다 정적 시험을 둔다.
  - 키의 나머지는 MesenCE 와 같다: 코어 바이너리 해시(도장의 커밋·패치·SHA-256), 코어 설정, 출발 SRAM·상태의 해시, 드라이버 코드 해시, 장면 입력, 롬 크기·머리(체크섬 제외).
  - 판정은 매번 돈다. 재검증·실패 처리는 MesenCE 장면과 같다.
  - snes9x 장면은 캐시하지 않고 늘 돈다.

## 맞지 않는 경우

- 모든 장면이 지나는 코드(NMI, 공용 훅, 메인 루프)를 바꾸면 모두 다시 돈다.
- 코드가 자라 루틴 주소가 밀리면, 그 루틴을 부르는 훅의 JSL 오퍼랜드가 바뀐다. 그 훅을 지나는 장면은 모두 빗나간다.
- Lua 파일 하나, MesenCE, 사용자 MesenCE 설정이 바뀌면 모두 빗나간다.
