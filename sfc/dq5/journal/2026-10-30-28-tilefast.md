# 2026-10-30-28: 타일 늘리기 롬의 필드 불러오기 7프레임 없애기

[블록 훅 일지](2026-10-30-25-mblock.md)가 남긴 것 가운데 하나를 했습니다. 필드 타일을 512개 넘게 늘린 롬은 필드를 원본보다 7프레임 늦게 불러왔습니다. 타일 늘리기가 바꾸는 루틴 둘(블록 표 읽기 `00:BC6D`, 타일에 팔레트 비트를 붙이는 `00:BBAC`)을 훅으로 빼지 않고 제자리에서 더 짧게 바꿨습니다. 이제 타일만 늘린 롬도, 블록 번호를 10·11비트로 늘린 롬과 함께 넣은 롬도 세 세계에서 원본과 같은 프레임에 필드를 불러옵니다. 형식은 [쓰기 형식의 「필드 그림」](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)과 [블록 훅 속도·빛 칸·세계 지도 실측](../docs/dq5-build-format.md#블록-훅-속도빛-칸세계-지도-실측)에 있습니다.

## 1. 다시 재기

앞 일지와 같이 `dq5warp.lua` 로 배 선실 세이브스테이트에서 필드에 내리며 프레임마다 `$7F`·`$BE` 를 적고, 둘 다 그대로인 프레임을 멈춘 구간으로 셌습니다. 롬은 다섯입니다.

- 타일: `dq5fieldgfxwrite --worlds-at 34:8000 --extra-at 60:8000` 으로 타일을 1,024개로 늘림(새 타일 = 원래 타일 XOR FF, 니블 bit0 반전, 속성 그대로). 블록 표는 그대로라 화면은 원본과 같아야 합니다.
- 블록 10·11비트: `dq5blockgrowcheck.py` 의 same 롬.
- 타일 + 블록 10·11비트: 타일 롬으로 만든 같은 블록 표·지도 패치를 함께 넣은 롬.

```
                    세계 0     세계 1     세계 2     세계 2 첫걸음
원본                462~492   453~483   451~481   822
타일                462~499   453~489   451~487   820
블록 10·11비트       461~492   453~483   451~481   822
타일 + 블록 10·11비트 462~496   453~487   451~485   826
```

같은 실행에서 마스터 클록(`emu.getState()` 의 `masterClock`)을 더하면 `00:BBF7`~`BC46` 한 번이 원본 1,901, 타일 롬 2,675 였고, `00:BBAC`~`BBF6` 한 번이 원본 717, 타일 롬 1,789 였습니다. 두 루틴은 칸마다 한 번씩(세계 0 에서 1,090·1,088번) 불립니다.

- 블록 표 읽기: 타일 늘리기는 `00:BC80`·`BC8D` 의 `LDA $2AA330,X / AND $BC9C,Y / BEQ / LDA #1 / STA $95`(13바이트)를 `JSL` 훅과 `STA $95` 뒤 `NOP` 일곱으로 바꿨습니다. 훅은 9번째·10번째 비트를 마스크 둘로 따로 읽어 `ROL` 로 모읍니다. `JSL`·`RTL` 과 `NOP` 일곱이 층마다 붙습니다.
- 팔레트 비트: 니블을 읽는 네 자리를 세계마다 512바이트 표를 읽는 `JSL` 훅으로 바꿨습니다. 훅은 X·A 윗바이트를 스택에 지키고 세계 번호로 주소를 셈합니다. 한 번에 두 자리를 거칩니다.

타일과 블록을 함께 늘린 롬은 `00:BBF7` 이 1,931 로 블록 롬과 같았습니다. 지도의 칸이 모두 512 이상이라 빠른 훅이 옮긴 표를 읽고 `00:BC6D` 를 거의 거치지 않기 때문입니다. 그래서 4프레임은 모두 `00:BBAC` 몫입니다.

## 2. 블록 표 읽기를 제자리에서

`00:BC6D`~`BC9B`(47바이트)는 `PHB / PHK / PLB` 로 DB 를 `00` 에 두고 두 층 타일 하위 8비트를 읽은 뒤, 상위 비트 바이트를 마스크로 `AND` 해 `$95`·`$97` 을 0·1 로 둡니다. 빠른 훅의 칸 비트 표(`칸 × 256 + 상위 비트 바이트` → 그 칸의 9·10번째 비트, 1,024바이트)를 여기서도 쓰면 층마다 읽기 한 번으로 끝납니다. 칸 q 는 Y 에 있으므로 `TYA / XBA` 로 A 윗바이트에 두고, 상위 비트 바이트를 8비트로 읽어 `TAX` 하면 16비트 X 가 곧 표의 색인입니다.

```
00:BC6D  SEP #$20 / LDA $2AA32C,X / STA $94 / LDA $2AAD27,X / STA $96 / TYA / XBA
00:BC7D  LDX $02 / LDA $2AA330,X / TAX / LDA 칸비트표,X / STA $95
00:BC8A  LDX $02 / LDA $2AAD2B,X / TAX / LDA 칸비트표,X / STA $97 / RTS
```

43바이트라 원래 자리에 들어갑니다. 긴 주소로만 읽어 DB 를 바꾸지 않습니다. 나갈 때 X 가 원래(`$02`)와 다르지만, 부른 곳은 모두 X 를 다시 둔 뒤에 읽습니다(`00:BB9F`·`00:D00D` 다음 `00:BBAC` 의 `TAX`, `00:BCAE` 다음 `00:BCBA` 의 `TAX`, 코드 읽기). 빠른 훅의 511 이상 갈래도 X 를 같은 식으로 남깁니다. 디코더(`dq5field.wide_tiles`)는 `00:BC6D` 가 `SEP #$20`(`E2`)이면 10번째 비트를 읽습니다.

타일 롬의 `00:BBF7` 한 번이 2,675 에서 1,852 로, 원본보다 49 짧아졌습니다.

## 3. 팔레트 비트 붙이기

처음에는 `00:BBAC` 를 원래와 같은 사이클로 맞추려 했습니다. 원래 루틴은 `LDA $96 / LSR / TAX` 로 니블 자리를 고른 뒤 `XBA / ORA $96` 으로 팔레트를 붙이는데, 그 사이 A 윗바이트 `(타일 >> 1) >> 8` 이 타일맵 워드 아랫바이트에 섞입니다. 원본은 타일이 512 미만이라 늘 0 이었고, 늘린 훅은 이를 0 으로 돌려주려고 길어졌습니다. `TAX` 뒤에 `TDC`(D = 0 이면 A = 0)를 넣고 `ADC #8` 앞 `CLC` 를 빼면(니블을 `LSR` 둘·`ASL` 둘 하면 밀려 나가는 비트가 늘 0) 길이도 사이클도 원래와 같습니다. 세계마다 니블이 같으면 표 하나만 읽으면 됩니다.

이 롬은 `00:BBAC` 한 번이 717.3 으로 원본과 같았는데도 세 세계 모두 한 프레임 늦었습니다(493·484·482, 첫걸음 823). 실행된 자리를 프레임마다 세 보니, 필드를 불러올 때 `00:A771` 이 460프레임에 화면 다시 그리기 `01:B4D5` 를 부르고, `01:B4D5` 는 462프레임에 들어가 4,772,680마스터 클록 뒤에 돌아옵니다. `00:BBF7` 1,090번은 461~475프레임에 돕니다. 타일 늘리기는 `01:B4D5` 를 훅으로 바꿔 늘린 타일 16KB 를 DMA 로 다시 보내는데(전투 뒤 다시 보내려고 둔 것), 이 훅이 한 번에 136,286마스터 클록을 씁니다. `00:BBF7` 에서 덜어 낸 5만 남짓으로는 이것을 메우지 못합니다.

그래서 `00:BBAC` 를 원래보다 짧게 바꿨습니다. `(니블 × 4 + 8)` 을 타일마다 1바이트로 미리 셈한 표를 위층(니블 4비트)·아래층(3비트) 둘(1,024바이트씩) 두고, 타일 번호로 바로 읽어 `$97`·`$95` 에 `ORA` 합니다. 짝·홀 갈래와 `LSR`·`XBA` 가 없어지고 A 윗바이트 문제도 생기지 않습니다.

```
00:BBAC  LDA $96 / TAX / SEP #$20 / LDA 위층표,X / ORA $97 / STA $97 / REP #$20 / LDA $96 / ORA $C6 / STA $96
00:BBC1  LDA $94 / TAX / SEP #$20 / LDA 아래층표,X / ORA $95 / STA $95 / REP #$20 / LDA $94 / RTS
```

나갈 때 A 를 `$94` 로 둔 것은 `00:B769`·`B7B5`(화면 끝 줄을 그림)가 돌아오자마자 A 를 그대로 타일맵 버퍼에 쓰기 때문입니다. X 는 원래(타일 >> 1)와 달리 타일 번호이지만, 부른 곳은 X 를 다시 둔 뒤에 씁니다(`00:B76C`·`B7B8` 의 `LDX $84`, `00:D018` → `00:A588` 의 `LDX $0759`, 코드 읽기). `$96`·`$94` 의 윗바이트는 칸 비트 표나 옮긴 블록 표에서 온 타일 번호 8·9비트(0~3)뿐이라 X 는 1,023 을 넘지 않습니다. 디코더(`dq5field.tile_word`)는 `00:BBAE` 가 `TAX`(`AA`)이면 이 두 표로 타일맵 워드를 냅니다.

```
                    00:BBF7   00:BBAC   세계 0     세계 1     세계 2     세계 2 첫걸음
원본                1,901     717       462~492   453~483   451~481   822
타일                1,852     500       462~492   453~483   451~481   822
블록 10·11비트       1,931     717       461~492   453~483   451~481   822
타일 + 블록 10·11비트 1,931     499       462~492   453~483   451~481   822
```

다섯 롬 모두 마지막 멈춘 구간의 끝과 첫걸음이 원본과 같습니다. `01:B4D5` 에 들어가 돌아오기까지도 타일 롬이 원본보다 153,440마스터 클록 짧습니다(DMA 를 넣고도). [블록 훅 일지](2026-10-30-25-mblock.md) 7절의 타일 1,024개·블록 2,047개 지도 롬도 지금 도구로 다시 만들자 461~496 이 461~492, 세계 1·2 도 483·481, 첫걸음 822 가 되었습니다.

세 세계의 니블이 다르면(`worlds` 로 세계 1·2 의 니블을 따로 주면) 표 하나로 읽을 수 없어 니블 훅을 그대로 씁니다. 세계 1 의 니블만 다르게 둔 타일 롬은 462~496·453~487·451~485, 첫걸음 826 으로 4프레임 늦습니다(블록 표 읽기는 고친 것이라 `00:BBF7` 은 1,853).

## 4. 화면과 검사

원본과 세 롬(타일, 타일 + 블록 10·11비트)과 블록 10비트 롬을 같은 장면에서 덤프해 VRAM `0000`~`7FFF`(타일맵과 원래 타일 512개)·CGRAM 을 바이트마다 견주었습니다. 세계 0 (341,56)·세계 1·2 (50,28) 에 서서 700·900프레임, 세계 0 에서 네 방향으로 32프레임씩 걸으며 700~960프레임 여섯 번, 세계 2 바다 (62,64) 에서 왼쪽 해안까지 밀며 700~900프레임 세 번이 모두 같았고, 걸은 뒤 좌표·지형 `$1AA0` 도 같았습니다. 프레임까지 같은 덤프가 바이트마다 같다는 것은 불러오기뿐 아니라 걷는 동안의 타이밍도 같다는 뜻입니다.

- `dq5gfxlimitcheck.py` 23건(늘린 타일을 쓰는 블록의 타일맵·니블, 전투 뒤·メニュー·キメラのつばさ·ルーラ·융단, 속성 표로 막히는 걸음): 통과.
- `dq5fieldgrowcheck.py` 44건(세계마다 타일 벌, 니블 훅 갈래 포함): 통과.
- `dq5blockgrowcheck.py` 10비트 13건, 11비트 21건: 통과.
- 원본 롬 `dq5fieldgfxwrite.py check`(내보낸 그대로 patch 쓰기 0개)·`dq5fieldtables.py check`·`dq5fieldwrite.py check`: 통과.
- 타일 롬의 `fgw.current` 가 돌려준 타일·니블이 입력과 같고, 디코더 `tile_word` 가 타일 1,024개 두 층 모두 입력 니블로 셈한 값과 같았습니다.

## 틀렸던 것들

- 사이클이 원래와 같으면 프레임도 같으리라 보았습니다. 불러오기 안에서 `01:B4D5` 의 다시 그리기 훅이 16KB DMA 를 더 하므로, 칸마다 도는 두 루틴이 원래보다 짧아야 했습니다. 이 판은 D = 0 이라는 가정(`TDC`)에도 기대고 있었는데, 실측하지 않은 채 버렸습니다.
- 타일과 블록을 함께 늘린 롬의 4프레임을 블록 표 읽기 훅 몫으로 보았습니다. same 롬의 칸은 모두 512 이상이라 그 롬에서는 `00:BC6D` 가 거의 돌지 않고, 4프레임은 모두 니블 훅 몫이었습니다.

## 남은 것

- 세계마다 니블이 다른 타일 늘리기 롬은 니블 훅을 그대로 써서 4프레임 늦습니다. 세계별 팔레트 표(세계마다 2KB)를 두고 `$1949` 로 고르는 판은 만들지 않았습니다.
- 세계 지도 화면의 점은 블록을 늘린 롬에서 여전히 15프레임 늦습니다. `00:BDC5` 의 빠른 훅 한 번이 1,086(원본 915)마스터 클록이라 원본보다 짧게 하려면 반 바이트 평면 읽기와 세계 고르기를 다시 짜야 해서 하지 않았습니다. 타일 늘리기는 이 경로를 바꾸지 않습니다.
- 블록 2,047개 지도 롬은 멈춘 구간만 다시 쟀고, 화면을 디코더로 다시 견주지는 않았습니다.
- 늘린 타일을 `01:B4D5` 마다 다시 보내는 것은 그대로 둡니다. 덮지 않은 때는 보내지 않게 하려면 VRAM 이 덮였는지 알 길이 필요합니다.
