# 2026-10-30-14: 맵 OBJ 물체·탈것·배의 칸 배치 쓰기와 새 물체

[타일 쓰기](2026-10-27-56-objtiles.md)에 이어, 타일을 어디에 어떤 반전으로 늘어놓는지(칸 배치)를 쓰는 `dq5objlayout.py` 를 만들고 맵 OBJ 물체를 새로 더했습니다. 배의 칸 배치를 바꾸고 04/06 에 새 물체를 둔 롬을 게임에서 덤프해, OAM 과 화면이 예상과 같은 것을 확인했습니다. 형식은 [쓰기 형식](../docs/dq5-build-format.md#맵-obj-물체탈것세트-칸-배치-dq5objlayout1)과 [그래픽 형식의 「탈것」](../docs/dq5-graphics-format.md#탈것-01c4be-16f7dd-00fc08)에 있습니다.

## 1. 칸 배치는 어디에 있나

세 가지가 같은 꼴(칸 바이트 bit7 = 좌우 반전, bit0-6 = 첫 타일에서 센 번호)이지만 자리를 정하는 곳이 다릅니다.

- 맵 OBJ 물체: `16:F862` 의 9바이트 항목이 가로·세로 칸 수와 칸 바이트 주소를 가집니다. `16:F60D` 를 리스팅하자 표를 읽는 명령이 모두 `LDA $F862+k,Y`(스무 곳)이고, 앞에서 `PHK`·`PLB` 로 데이터 뱅크를 16 으로 둡니다. 칸 바이트도 16비트 주소라 표와 칸은 16 뱅크를 벗어날 수 없습니다.
- 탈것: `16:F7DD` 를 부르는 곳을 찾으니 `16:F7D9`(`JSR F7DD` / `RTL`)를 `01:BDBC`·`BDCF`·`BDE2`(양탄자), `01:C4A5`·`C4B7`(天空城), `01:C101`·`C114`(マスタードラゴン)가 불렀습니다. 그 앞에 `LDY #칸 표`·`STX $00`(속성)·`STA $06` 이 있고, 가로·세로 칸 수와 간격은 같은 루틴이 슬롯마다 즉값으로 씁니다.
- 배: 필드에서 배에 탄 채 시작한 장면(`FIELD=328,39 SET=21BF|10`)을 덤프하자, 흰 돛단배는 주인공 슬롯 0 의 그림 `4A`(세트 `68`)였습니다. 칸 배치는 세트 레코드의 칸 48개이고, 자리는 6타일 배치(`00:F071`)가 정합니다.

```
슬롯 00 그림 4A 세트 68 타일 102~: VRAM 35/35, 칸 48/48, OAM (120,104) down0 179px
```

## 2. 칸 표의 블록 수와 天空城

`16:F7DD` 는 가로 × 세로 칸을 `$06` + 1 번 옮깁니다. 이 수가 `00:FC08` 이 고를 수 있는 블록 수보다 늘 많았습니다(양탄자 부분 2 는 11블록을 옮기고 8블록을 그림, 코드 읽기). 그래서 칸 표가 겹쳐 보여도 그리는 범위만 보면 부분끼리 겹치지 않는다고 보았습니다(코드 읽기). 天空城 은 뒤 [일지 2026-10-30-15](2026-10-30-17-objlayout-low.md)에서 실측했습니다.

天空城 부분 1 은 `LDY #$96B6` 이었습니다. 지금까지 적은 `04:9634` 는 앞 16바이트(`00`~`0F`)가 같은 다른 자리라 덤프 비교로는 가려지지 않았습니다. 디코더(`dq5sprite.py`)의 주소를 `96B6` 으로 고쳤고, 그린 그림은 같습니다.

## 3. 표를 늘리는 자리

표는 `16:F862`~`FAFC`(74항목과 `FF`), 바로 뒤 `16:FAFD`~`FDFE` 가 칸 바이트이고, 이 구역의 바이트는 `FDFF` 하나 빼고 모두 어느 항목인가가 가리킵니다. 같은 칸 바이트를 여러 항목이 나눠 쓰고(`16:FB87` 을 다섯 항목), 앞부분만 나눠 쓰기도 합니다.

16 뱅크에 남은 빈 자리는 `16:FE10`~`FFFF`(496바이트)뿐이라 표 전체(676바이트)를 옮길 수 없습니다. 그래서 표는 제자리에서 뒤로 늘리고, 늘어난 표에 덮이는 칸 바이트만 옮깁니다. 바꾸지 않은 항목은 원래 주소를 그대로 두고, 바꾸거나 덮인 칸 바이트는 남은 구역에서 같은 바이트를 찾아 가리키거나 `--at` 에 둡니다. 원본을 `dump` 해 다시 넣으면 쓰기가 0개입니다.

```
원본: 물체 74개, 탈것 부분 7개, 세트 147개, 다시 넣어 쓰기 0개
```

## 4. 게임에서

`dq5objlayoutcheck.py` 로 세 가지를 바꾼 롬을 만들었습니다.

- 배(세트 `68`)의 `down0`·`down1` 을 `left0`·`left1` 칸으로.
- 04/06 에 물체 `0C`(석상 2×4, (39,9))를 좌우로 뒤집은 새 물체를 (36,9) 에. 표가 9바이트 늘어 52/50·53/52 의 물체 다섯이 가리키던 칸 바이트 세 덩어리가 `16:FE10` 으로 옮겨졌습니다.
- 양탄자 부분 2 의 아래 방향 두 프레임을 좌우로 뒤집기.

```
16:F862 676 맵 OBJ 물체 표 75항목
16:FE10 28 맵 OBJ 물체 칸 바이트 28바이트
04:94CF 72 탈것 80-2 칸 72개
1F:ECAA 48 세트 68 칸 48개
```

처음 돌렸을 때는 새 물체가 예상한 (80,80) 이 아니라 (104,80) 에 나왔습니다. 물체 X·Y 를 16픽셀 칸으로 본 것이 틀렸고, 8픽셀 셀이었습니다(셀 3개 = 24픽셀). 원래 물체 `0C` 도 주인공 (38,11) 보다 8픽셀 오른쪽이었습니다.

화면 비교도 처음에는 픽셀이 10% 남짓만 맞았습니다. 덤프한 프레임의 OAM 을 같은 프레임 스크린샷과 견준 것과, 스크린샷이 위 8줄을 잘라 낸다는 것을 빼먹은 탓이었습니다. 다음 프레임 스크린샷과 8줄 위로 견주자 원래 물체 `0C` 의 3픽셀만 남았고, 그 3픽셀은 주인공 머리(앞 OAM 슬롯)에 가린 자리였습니다.

```
original-ship f700: {'frame': 'down0', 'at': (120, 104), 'screen': (179, 179)}
edited-ship f700: {'frame': 'down0', 'at': (120, 104), 'screen': (165, 165)}
edited-ship f800: {'frame': 'down1', 'at': (120, 104), 'screen': (168, 168)}
edited-map f700: {12: {'xy': (39, 9), 'slot': 8, 'at': (128, 80), 'screen': (391, 391)},
                  74: {'xy': (36, 9), 'slot': 9, 'at': (104, 80), 'screen': (394, 394)}}
edited-carpet f700: {'80-1': [1, 1], '80-2': [1, 1], '80-3': [1, 1]}
검사 5개 통과
```

- 배는 칸 목록 48칸이 고친 레코드와 같았고, 아래를 볼 때 OAM 6장이 왼쪽 방향 그림의 칸(자리·타일·반전)으로 놓여 화면 픽셀까지 같았습니다.
- 새 물체는 슬롯 9 에 만들어져 OAM 8장이 표대로 놓였고, 자리 (104,80) 이 물체 `0C` 의 (128,80) 에서 −3 셀만큼 옮긴 자리였습니다.
- 양탄자는 부분 2 의 OAM 묶음이 고친 롬에서 그린 프레임과 맞았습니다.

## 틀렸던 것들

- 天空城 부분 1 의 칸 표를 `04:9634` 로 보았습니다. 부르는 곳의 `LDY #` 는 `96B6` 이었습니다.
- 맵 OBJ 물체의 X·Y 를 16픽셀 칸으로 보았습니다. 8픽셀 셀입니다.
- `+4` bit7 을 이야기 조건으로 적었습니다. `21:8000` 은 `7E:075E` >= `F0`(밤)을 보는 루틴이라 낮·밤 조건입니다(코드 읽기).

## 남은 것

- 탈것의 가로·세로 칸 수·프레임 수 바꾸기와 새 탈것. 칸 수와 간격은 같은 `LDA #` 를 두 칸이 나눠 쓰는 곳(양탄자 부분 2 의 가로·세로)이 있고, 프레임 수는 `7E:32A0`(양탄자 `81`, マスタードラゴン `82`) 쪽으로 보이지만 재지 않았습니다.
- 옮긴 칸 바이트를 쓰는 52/50·53/52 물체의 게임 실측. 이번에는 빌드한 롬을 다시 읽어 칸 바이트가 같은 것까지만 봤습니다.
- 새 물체가 맵의 인물 슬롯(최대 `20`)을 넘기는지는 도구가 보지 않습니다.
- 天空城·マスタードラゴン 칸 쓰기의 게임 실측(양탄자만 확인).
