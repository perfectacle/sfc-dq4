# 2026-10-25-32: 필드 인물 스프라이트

나중에 DQ4 인물을 그릴 때 원작 인물을 옆에 펴 놓고 보려고, 마을·필드를 걷는 인물 스프라이트가 롬 어디에 있는지 찾아 모두 꺼냈습니다.
그림 번호 → 세트(147개) → 52바이트 레코드 → 런 길이 압축 타일이고, 장면 25곳의 덤프 578개에서 VRAM 타일과 OAM 이 모두 디코더와 같았습니다.
결과는 [dq5-graphics-format.md 「필드 인물 스프라이트」](../docs/dq5-graphics-format.md#필드-인물-스프라이트-1fcf1e) 에, 도구는 `sfc/dq5/tools/dq5sprite.py` 에 있습니다.

## 1. 걷는 동안에는 OBJ 를 올리지 않는다

먼저 배 선실 세이브스테이트에서 주인공을 걷게 하며 DMA 를 모두 적었습니다. VRAM 쪽은 BG 스크롤 줄뿐이었고 OBJ 영역(`$6000`~)으로 가는 것이 하나도 없었습니다.
OAM 을 보면 주인공은 타일 `000`·`001`·`006`·`007`·`014`~`017` 의 OBJ 8개였고, 파파스는 같은 타일 `09A` 를 좌우 반전으로 두 번 썼습니다.
그러니 맵을 불러올 때 인물마다 프레임 전부를 VRAM 에 올려 두고, 걸을 때는 OAM 타일 번호만 바꾸는 것으로 보았습니다.

## 2. 맵을 불러올 때의 VRAM 쓰기

`dq5warp.lua` 로 19/00 에 가면서 프레임마다 DMA 를 적자 321~407프레임이 통째로 비었습니다. `$420B` 쓰기만 감시한 것이 문제였습니다.
`$2118`·`$2119` 쓰기를 PC 별로 모으자 OBJ 영역에 쓰는 곳이 나왔습니다.

```
1F:D326 2118 first=393 n=2666 va=6000-7FDF
1F:D307 2119 first=393 n=3071 va=6006-7FDC
```

이 둘은 `STA $420B` 바로 뒤 주소였습니다. `1F:D2DB` 가 자료 뱅크를 DB 로 둔 채(`PHA PLB`) DMA 를 걸어서, 쓰기가 `1F:420B` 로 가 `00:420B` 감시에 안 걸렸던 것입니다.
392~400프레임의 실행 커버리지로 리스팅을 만들어 흐름을 읽었습니다. `1F:CF1E` 가 A 의 그림 번호로 `25:86D0` 에서 세트 번호를 얻고, `1F:D63D` 포인터로 레코드를 찾아 칸 48개를 `7E:8060-` 에 옮긴 뒤, `1F:D200` 이 낮은 바이트와 높은 바이트를 따로 DMA 합니다.
부르는 곳은 롬을 `22 1E CF 1F`·`22 14 CF 1F` 로 찾았습니다. 인물은 `1E:DC8C`, 주인공은 `00:E232` 이고 일행이 `00:E3D4` 근처입니다.

## 3. 압축과 레코드

`1F:D2DB` 는 바이트 하나로 「뒤 n 바이트를 그대로」·「한 바이트를 n 번」·「다음 뱅크로」·「끝」을 고르는 런 길이 압축이었습니다. 이것을 옮겨 19/00 덤프와 맞추었습니다.

```
slot 00 gfx 2E set 82 list 8060 base 000 tiles 34(n=34 lo=544 hi=544) match 34
slot 08 gfx 08 set 03 list 8180 base 090 tiles 38(n=38 lo=608 hi=608) match 38
slot 0B gfx 09 set 8D list 8240 base 0D2 tiles 39(n=39 lo=624 hi=624) match 39
```

모든 세트를 풀자 자료가 `0C:8000` 부터 `0F:8ABC` 까지 세트 순서로 빈틈없이 이어졌고, 레코드 `+51` 의 타일 수와 풀린 타일 수가 147개 모두 같았습니다.

## 4. 프레임 배치

칸 48개를 화면에 놓는 쪽은 `7E:8000-` 을 읽는 곳을 감시해 찾았습니다. 그리는 루틴이 둘이었습니다.

- `00:F071`: 칸 6개를 16x24 로. 방향마다 12칸, 프레임마다 6칸(`00:EE5C`).
- `00:F7AA`: 머리 칸 4개(방향마다, 프레임과 상관없음)를 위에, 몸 칸 4개(방향 × 프레임)를 8픽셀 아래에 겹침(`00:EE8C`).

어느 쪽인지는 레코드를 부른 뒤 돌려받는 `$00`(→ `7E:32A0`)이 정하고, 그 값은 세트 번호 bit7 로 정해집니다. 주인공·파파스가 OBJ 8개였던 까닭이 이것입니다.
처음 비교는 화면 전체에서 프레임을 찾았는데, 주인공 다리가 바로 아래 인물에게 가려 「없음」이 나왔습니다. 세트 타일 범위의 이어진 OAM 슬롯만 묶어 다시 그리도록 바꾸자 맞았습니다.

## 5. 장면 25곳 비교

`dq5npc.py` 의 인물 목록으로 세트가 가장 많이 모이는 실내 맵을 골라, 맵마다 인물이 모인 자리 셋으로 순간이동해 4방향으로 걸으며 10프레임마다 덤프했습니다(`sfc/dq5/tools/lua/dq5sprdump.lua`). 8개를 동시에 돌려 27곳이 30초에 끝났습니다.

```
덤프 578개, OBJ 팔레트 0~2 가 ROM 과 같은 덤프 578개, 팔레트 3 까지 같은 덤프 410개
세트 60개, VRAM 타일 138848/138848 같음
OAM 묶음 2778개 중 2778개가 디코더 프레임과 픽셀째로 같음, 서로 다른 (세트, 방향, 프레임) 132개
```

17/01 은 순간이동이 안 됐고, 세 곳(03/01·1D/04·1F/01 의 한 자리씩)은 도착하자 전투가 붙어 뺐습니다.
롬에서 그린 어린 주인공(세트 `82`)의 아래 방향 행렬은, dq4 트랙이 VRAM 덤프에서 되돌린 [dq4-sprite-format.md](../../../docs/dq4-sprite-format.md) 의 행렬과 같았습니다.

## 6. 맵 OBJ 타일

필드 덤프의 OBJ 타일 `$090` 이후에 세트에 없는 타일이 82개 있었습니다. 인물을 다 놓은 뒤 부르는 `1F:D4AF` 가 `1F:D59A` 의 맵별 항목 27개 중 맞는 것을 올린 것이었습니다.
필드 세계 0 은 82/82, 02/07·04/06·07/00·1D/04·1D/0F 도 그 맵의 `7E:1997` 자리에 모두 그대로 있었습니다. 이 타일을 어떻게 늘어놓는지는 아직 모릅니다.
이 항목이 있는 맵에서는 OBJ 팔레트 3 이 `04:96D6` 과 달랐고, 그 색은 `01:9BDC`·`01:9C68`·`01:9EDE` 에서 찾았습니다.

## 틀렸던 것들

- 맵을 불러오는 동안 VRAM DMA 가 없다고 보았습니다. `$420B` 를 뱅크 `00` 주소로만 감시한 탓이었습니다. DB 를 롬 뱅크로 두고 쓰는 DMA 는 `$2118`·`$2119` 쓰기로 감시해야 보입니다.
- 「Y-1」로 알던 인물 엔트리 기타 bit7(`7E:31C0`)이 이 루틴에서는 B 로 넘어가 다른 압축 풀기(`1F:D39F`)와 칸 표를 고릅니다. 세로를 한 칸 올리는 값만은 아니고 누운 모양으로 보입니다(남은 것).
- 처음 덤프 셋 중 OBJ 팔레트 0 이 다른 곳이 있어 맵마다 팔레트가 바뀐다고 의심했는데, 화면을 보니 전투 중이었습니다. 전투가 아닌 덤프에서는 팔레트 0~2 가 모두 같았습니다.

## 남은 것

- 누운 인물 모양(`1F:D39F`·`1F:D413` 전치, `1F:D0AC`·`1F:D1B3` 칸 표, `00:EC9B`·`00:F3CE`)을 디코더에 넣고 덤프와 맞추기.
- 동료 몬스터가 일행으로 걸을 때의 그림 번호 표, 탈것과 맵 OBJ 타일의 배치, 팔레트 3 을 고르는 곳.
- 덤프에 나오지 않은 세트 87개의 실측, 그림 번호 `9A`·세트 `63`·`6C`·`7E:21D1` bit6 예외.
