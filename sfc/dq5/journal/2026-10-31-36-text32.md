# 2026-10-31-36: 인라인 `32`, 1장 대화 창의 `over` 메시지, 진행 시험의 `7E:1ABC` 감시

텍스트 쪽 남은 것 넷을 닫았습니다. 인라인 `32` 가 A 를 기다렸다 창을 닫는 것을 화면과 PC 로 쟀습니다. 통합 빌드의 `text`(`over`)로 고친 메시지가 DQ4 1장 게임의 대화 창에 뜨는 것도 봤는데, 그 과정에서 통합 빌드가 1장 롬의 IRQ 벡터를 잃는 것을 찾아 고쳤습니다. DQ4 1장 진행 시험 전체에서는 `7E:1ABC`~`1BB0` 에 닿은 PC 를 셌습니다. [#827](https://github.com/perfectacle/sfc-dq4/pull/827) 리뷰의 LOW 둘(따로 둔 색인의 끝, 글자 묶음 표의 끝)도 교차 검사로 막았습니다. 결과는 [3200 이상 덧붙이기](../docs/dq5-build-format.md#3200-이상-덧붙이기), [통합 포팅 빌드](../docs/dq5-build-format.md#통합-포팅-빌드-dq5portbuild1), [인물 스크립트 명령](../docs/dq5-map-format.md), [실측으로 닫기: 접근 카운터](../docs/dq5-hangul-format.md#실측으로-닫기-접근-카운터)에 옮겼습니다.

## 1. 인라인 `32`

[2026-10-31-08](2026-10-31-08-msgextra.md)에서는 1,000프레임 화면에 `32` 의 창이 없다는 것만 봤습니다. 이번에는 `dq5inlinecheck.py` 를 만들어, 17/00 인물 스크립트를 셋으로 바꾼 롬을 돌렸습니다.

```
21      21 29 01             창을 열어 띄우고 A 를 기다렸다 닫음(대조)
32      32 29 01
30-32   30 29 01 / 32 2A 01  30 이 연 창에 32 가 이어 띄움
```

롬마다 부딪친 뒤 A 를 400프레임과 200프레임에 누르는 두 번을 돌렸습니다. 처리기 첫 명령, `BRK 0E`(기다림), `BRK 95 FF`(닫기)의 PC 를 실행한 프레임과 A 를 누른 프레임을 남기고, 화면 아래 창 자리(y 128~215)를 닫은 뒤 화면과 견줬습니다.

```
   21-400: 시작 f353 기다림 f371 A f691 닫기 f691 기다리는 동안 창 있음 message 0129
   21-200: 시작 f353 기다림 f371 A f491 닫기 f491 기다리는 동안 창 있음 message 0129
   32-400: 시작 f353 기다림 f369 A f691 닫기 f691 기다리는 동안 창 없음 message 0129
   32-200: 시작 f353 기다림 f369 A f491 닫기 f491 기다리는 동안 창 없음 message 0129
30-32-400: 시작 f379 기다림 f416 A f691 닫기 f691 기다리는 동안 창 있음 message 0129 message 012A
30-32-200: 시작 f379 기다림 f416 A f491 닫기 f491 기다리는 동안 창 있음 message 0129 message 012A
통과
```

`32` 도 `21` 처럼 A 를 누른 바로 그 프레임에 닫기를 실행하고, A 를 200프레임 당기면 닫기도 따라옵니다. 다른 점은 창을 열지 않는 것입니다. 홀로 쓰면 메시지를 띄워도 화면에는 아무것도 없이 A 를 기다리고, `30` 이 연 창이 있으면 그 창에 이어 찍습니다.

## 2. 1장 게임의 대화 창

[2026-10-31-12](2026-10-31-12-textover.md)에서는 dq5 의 배 선실 세이브스테이트로 디코더만 돌렸습니다. 이번에는 `dq4build.py` 로 만든 1장 롬(`dq4-ch1-full.sfc`)을 고정 롬으로 두고, 서장 첫 대사 `CA8` 을 도구점 인사(메시지 `000`)의 코드로 바꾼 `text`(`over`) 하나만 넣어 통합 빌드를 했습니다.

DQ4 서장 검사와 같은 부팅·길로 돌리자 통합 빌드 롬은 켜도 화면이 까만 채였습니다. 1장 롬과 바이트로 견주니 텍스트 자리 말고 머리가 달랐습니다.

```
1장 롬     … 00:FFEE = 00 80
통합 빌드  … 00:FFEE = 7F 8F   (원래 롬과 같음)
```

1장 롬의 [소리 이식](../../dq4/docs/dq4-sound-port-format.md)은 IRQ 벡터 `00:FFEE` 를 `00:8000`(`JML 71:8600`)으로 바꿉니다. 빌더는 머리 `7FB0`~`7FFF` 전체를 자기 몫으로 두어 패치가 쓰지 못하게 했고, `fixed_mask` 도 고정 롬의 머리를 견주지 않았습니다. 그래서 벡터가 원래 값으로 돌아갔습니다. 빌더 몫을 이름·크기·체크섬이 있는 `7FB0`~`7FDF` 로 줄이고, 벡터 `7FE0`~`7FFF` 는 원래 롬 자리처럼 `orig` 를 단 쓰기로 받게 했습니다. 고정 패치에 `00:FFEE` 쓰기가 들어가고, 다시 빌드한 롬은 정상으로 켜졌습니다.

`dq5textovercheck.py` 는 두 롬을 같은 길로 돌려 메시지가 불린 프레임과 그 뒤 창 자리를 견줍니다.

```
{"message": "CA8", "called_at": 650, "window_differs": [670, …, 740, 970, …, 1040], "side": "f0740"}
```

두 롬 모두 f650 에 `CA8` 을 불렀고(f949 에 한 번 더), 그 두 번의 창만 달랐습니다. 나란히 붙인 화면에서 1장 롬은 「용사님 용사님……」, 통합 빌드는 「어서 오세요! 여기는 / 도구점이에요. 무엇을 / 도와드릴까요?」였습니다. f1240 까지 다른 장은 이 둘뿐이었고, 뒤 메시지(`CA9`~`0129`)가 불린 프레임도 두 롬이 같았습니다.

## 3. 진행 시험의 `7E:1ABC`~`1BB0`

[2026-10-27-46](2026-10-27-46-wramfree.md)은 장면 841개에서 원래 코드의 접근이 0 인 것을 봤고, 패치 뒤 처음부터 끝까지 진행할 때도 재라고 남겼습니다. 지금 있는 가장 긴 진행 시험은 dq4 트랙의 `dq4ch1walkcheck.py`(새 게임 ~ 2장 제목 상자, 27구간)입니다. 이 도구는 고치지 않고, `dq5wramwatch.py` 가 `dq4mesen.run`·`Runner` 를 감싸 띄우는 스크립트 앞에 감시를 끼웠습니다. 감시는 범위의 읽기·쓰기를 (CPU 주소, PC) 마다 세어 60프레임마다 씁니다.

처음 돌렸을 때는 `hoimin` 구간이 「세이브스테이트 없음」으로 멈췄습니다. 메모리 콜백 때문에 에뮬레이션이 느려져, 구간마다 주는 시간 제한(`maxf // 40 + 120` 초) 안에 끝나지 못했습니다. 감싼 실행의 시간 제한을 4배로 늘리자 27구간이 모두 통과했습니다.

```
r 00865E 245회 245곳 1ABC~1BB0            (00:8667·8670·8679 도 같음)
r 049C52 16회 3곳 41AC0~41AEC             (04:9F91 ~ 04:C6EA 21곳, 41AC0~41BAF)
r 30A670 13회 1곳 7E1BB0~7E1BB0           (30:A008·A6E0, 60:C13E 도 1BB0)
r 60830D 23854회 2곳 7E1ABC~7E1ABD
w 00864C 245회 245곳 1ABC~1BB0
w 608213 241회 241곳 7E1AC0~7E1BB0
w 608253 6266회 241곳 7E1AC0~7E1BB0
w 6083D9 26회 1곳 7E1ABC~7E1ABC
```

원래 코드가 쓴 것은 전원을 켤 때의 0 채우기(`00:864C`)뿐입니다. 원래 코드가 읽은 것은 그 0 채우기와, 뱅크 `04` 의 창 코드가 낮은 WRAM 거울(`04:1AC0`~)로 옮긴 창 레코드를 읽는 것입니다. DQ4 메뉴가 레코드를 `7E:1AC0` 으로 옮긴 것이 [메뉴 문서](../../dq4/docs/dq4-menu-format.md)의 설계이고, 창 코드는 DQ4 메뉴 변수 `1ABC`~`1ABF` 를 읽지 않았습니다. 나머지는 늘린 뱅크(`30`·`60`)의 패치 코드입니다.

## 4. #827 의 LOW 둘

- 따로 둔 색인 표(`59:8000`)는 항목이 앞으로 가는 동안을 표로 셉니다. 색인 뒤에 0 이 아니고 앞으로 가는 다른 자료가 오면 메시지 수를 넘게 셉니다. 메시지는 비트로 이어 붙으므로, 센 항목마다 앞 묶음 16개를 실제로 풀어 끝 비트가 다음 항목과 같은지 보게 했습니다(`contiguous_groups`). 시험에서 색인 뒤에 앞으로 가는 항목 넷을 붙여도 원래 묶음 수에서 멈춥니다.
- 따로 둔 글자 묶음 표(`5A:9991`)는 0 이 아닌 5바이트 항목이 이어지는 데까지를 표로 보고, 글자 수의 아래 한도(`3DB`)만 봤습니다. 그 뒤 0 인 항목이 뱅크 안에 있어야 하고, 메시지가 쓰는 가장 큰 글자 코드가 표의 글자 수보다 작아야 한다는 검사를 더했습니다. 시험은 표 뒤를 뱅크 끝까지 0 이 아닌 값으로 채운 롬과, 표의 글자 수를 메시지가 쓰는 글자보다 작게 줄인 롬을 거부합니다.

## 틀렸던 것들

- `hoimin` 구간이 멈춘 것을 감시가 게임을 바꾼 것으로 의심했습니다. 실행 기록은 프레임을 다 돌았는데 세이브스테이트만 없었고, 시간 제한을 늘리자 같은 구간이 통과했습니다.
- 감시 실행의 첫 시도는 `LIBDIR` 를 빈 값으로 넘겨 부팅 상태부터 만들지 못했습니다. `krpatch` 는 `uv run` 안에서만 길에 있습니다.

## 남은 것

- `7E:1ABC`~`1BB0` 감시는 DQ4 1장 진행까지입니다. 2장 이후와 DQ5 이야기 장면은 그 장의 진행 시험이 생기면 같은 `dq5wramwatch.py` 로 겁니다.
- `dq5textovercheck.py` 는 서장 길(5,000프레임 안)에서 불리는 메시지만 견줍니다.
