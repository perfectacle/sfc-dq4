# 2026-10-30-35: 블록을 늘린 롬의 지형 루틴 03:CB1B 와 움직이지 않던 융단

[세계 지도 점 일지](2026-10-30-34-mapdots.md)가 남긴 것 둘을 했습니다. 하나는 블록 번호를 10·11비트로 늘린 롬에서 `00:BDC5` 의 빠른 훅 한 번이 원본보다 165·249마스터 클록(세계 0·1) 긴 것이 세계 지도 화면 말고 다른 장면을 늦추는지였고, 다른 하나는 점 훅 주석에 「코드 읽기」 로 적은 `AND #$01FF` 가 실제로 도는지였습니다. 재 보니 늦는 장면은 없었습니다. 대신 늘린 롬에서는 마법 융단이 한 칸도 움직이지 못했습니다. 지형 루틴 `03:CB1B` 를 빠른 훅으로 바꿔 융단을 고쳤고, 이제 `03:CB1B` 한 번이 모든 장면에서 원본보다 짧습니다. 형식은 [쓰기 형식의 「필드 세계 지도」](../docs/dq5-build-format.md#필드-세계-지도)와 [블록 훅 속도·빛 칸·세계 지도 실측](../docs/dq5-build-format.md#블록-훅-속도빛-칸세계-지도-실측)에 있습니다.

## 1. 누가 00:BDC5 를 부르나

롬에서 `JSR $BDC5` 는 `00:BDC1` 하나이고, `JSL $00BDC1` 은 `03:CB20` 하나입니다. `03:CB20` 은 지형 루틴 `03:CB1B` 안이고, `JSL $03CB1B` 는 `01:81D6`·`01:84E0`·`01:BE8E`·`03:CB11` 넷입니다. 그래서 `00:BDC5` 의 시간은 곧 `03:CB1B` 를 부르는 곳의 시간입니다.

새 프로브 `lua/dq5bdc5.lua` 는 `03:CB1B` 에 들어올 때 스택에서 돌아갈 자리를 읽어 부른 곳을 정하고, `03:CB1B` 에서 부른 곳 + 4 까지와 `00:BDC5` 에서 `00:BE16`(`RTS`)까지의 마스터 클록을 부른 곳마다 더합니다. 프레임마다 화면 버퍼(`emu.getScreenBuffer`) 해시도 적어, 같은 입력의 두 롬이 몇 프레임째부터 어긋나는지 봅니다. 장면은 배 선실 세이브스테이트에서 `dq5warp.lua` 로 갔고, 시험 롬은 `dq5blockgrowcheck.py` 와 같이 만든 10비트·11비트 same 롬(모든 칸 512 이상, 블록 512+b 는 블록 b 그대로)입니다.

| 장면 | 만든 법 | 불린 곳 |
| --- | --- | --- |
| 세계 0 걷기(무작위 전투까지) | `FIELD=341,56`, 왼쪽·오른쪽 64프레임씩 | `01:84E0` 걸음마다(8프레임) |
| 이벤트 전투 | `FIELD=341,56 BATTLE=00:1` | 없음 |
| 해안의 배에 올라 저음 | `FIELD=328,39 SET="21B5\|80;21CD=48;21CE=01;21CF=25;21D0=00"` | `01:84E0` 걸음마다 |
| 天空城·マスタードラゴン | `FIELD=310,60 LATESET=1954=81`(`82`), 날다가 A | `01:BE8E` A 를 누를 때 |
| 마법 융단 | `FIELD=310,60 SET=2056=CC`, どうぐ → つかう 뒤 세 방향 | `01:BE8E` 펴고 내릴 때, `01:81D6` 4프레임마다 |
| 세계 1·2 걷기 | `FIELD=50,28 POKE=7E1949=01`, `FIELD=62,64 POKE=7E1949=02` | `01:84E0` 걸음마다 |

`01:84E0` 은 걸음마다 주인공 칸의 지형을 `$1AA0` 에 둡니다(조우와 전투 배경이 이 값을 씀). `01:81D6` 은 다음 칸의 지형으로 `01:81FD` 표를 읽는 곳으로 보입니다(코드 읽기: `01:81AD` 가 `$1954 & 7F` 가 0 일 때 이리로 옴). 걷기(`$1954` = `00`)에서는 불리지 않았고 융단(`80`)에서만 불렸습니다. `01:BE8E` 는 지금 칸의 지형을 X 가 가리키는 `FF` 로 끝나는 목록과 견주는 곳으로 보입니다(코드 읽기: `01:BE95` 의 `LDA $0000,X / BMI / CMP $00`). 天空城 이 물 위에서 「ここでは 降りられない。」 를 띄울 때와 マスタードラゴン 이 내려앉을 때 불렸습니다. 이벤트 전투는 `03:CB1B` 를 부르지 않았고, 무작위 전투의 배경은 `01:84E0` 이 둔 `$1AA0` 을 읽습니다([`dq5battlebg.py`](../tools/dq5battlebg.py)).

## 2. 늦는 장면이 있나

고치기 전 롬은 `03:CB1B` 한 번이 원본보다 163~278마스터 클록 깁니다(4절 표). 한 프레임은 357,368마스터 클록이고 `03:CB1B` 는 많아야 4프레임에 한 번이라, 프레임이 밀리려면 그 장면이 프레임 끝에 거의 붙어 있어야 합니다. 화면 해시를 견주니 고치기 전 롬(10·11비트 같음)은 다음과 같았습니다.

```
장면         견준 프레임  다른 프레임  어긋남
세계 0 걷기  1~2,300       0
이벤트 전투  1~2,090       0
세계 1 걷기  1~900         0
세계 2 걷기  1~900         0
マスタードラゴン 1~1,800   0
天空城       1~1,800       467          478~953 이 모두 원본 게임의 다음 프레임 화면
배           1~1,100       375          478~1,099 가 모두 원본 게임의 다음 프레임 화면
마법 융단    1~1,600       440          1,161 부터 다름(앞뒤 20프레임 안에 같은 화면 없음)
```

天空城·배의 차이는 필드 불러오기가 한 프레임 일찍 끝나서이고(`03:CB1B` 가 처음 불리는 824프레임보다 앞), [일지 34](2026-10-30-34-mapdots.md)의 「세계 0 461~492(원본 462~492)」 와 같은 앞당김입니다. 원본보다 늦은 프레임은 어느 장면에도 없었습니다. 남은 것은 융단입니다.

## 3. 융단이 움직이지 않는다

융단 장면의 `warp.txt` 는 원본이 `field 310,60 -> field 312,71 moved=yes`, 늘린 롬이 `field 310,60 -> field 310,60 moved=no` 였습니다. 융단을 펴는 데까지는 같고 걷기만 막혔습니다. `01:81D6` 앞뒤의 레지스터를 찍었습니다.

```
            01:81D6 JSL 앞      01:81DA 돌아옴   01:81E1 RTS
원본        A=0000 X=0135       A=0006           X=0006
늘린 롬     A=0000 X=0135       A=0106           X=0106  A=01D0
```

`01:81D4` 는 `REP #$30 / JSL $03CB1B / TAX / SEP #$20 / LDA $0181FD,X / RTS` 입니다. `03:CB1B` 는 번호를 `LSR / TAX` 한 뒤 `SEP #$20 / LDA 지형표,X` 로 니블을 읽어, A 아랫바이트만 바꾸고 윗바이트에는 번호 >> 9 를 남깁니다. 원래 번호는 511 이하라 이 윗바이트가 늘 0 이었습니다. 블록 514(= 2 + 512)를 받은 늘린 롬은 `0106` 을 돌려주고, `01:81DA` 의 16비트 `TAX` 가 `01:81FD + 106` 을 읽어 걸을 수 없는 칸이 됩니다. `01:84E0` 은 `TAX` 뒤 `SEP #$30` 이고 `01:BE8E` 는 M 8비트로 `STA $00` 하므로 윗바이트를 쓰지 않습니다. 셋 가운데 `01:81D6` 만 깨졌습니다.

`dq5blockgrowcheck.py` 는 걷기만 보았고, `dq5gfxlimitcheck.py` 의 융단 장면은 블록을 늘리지 않은 타일 롬이라 지나쳤습니다.

## 4. 03:CB1B 를 훅으로

빠른 훅 몸통을 더 줄이지 않고, 일지 34 의 `03:CB07` 처럼 부르는 쪽에서 들고 나기를 덜었습니다. `03:CB1B` 의 `PHP` 뒤 `REP #$30 / PHX / PHY`(`03:CB1C`, `C2 30 DA 5A`)를 빠른 훅 넷째 몸통으로 가는 `JML` 로 바꿉니다.

- 머리: `REP #$30 / PHX / PHY` 하고 부른 곳이 둔 `$90`·`$92` 로 `03:CB07` 몸통과 같은 번호 셈(`dq5fieldwrite.fast_hook` 의 `number`)을 합니다. 좌표 `0200` 이상이면 원래 루틴처럼 번호 0 이 됩니다.
- 꼬리: `REP #$30 / LSR / TAX / LDA #$0000 / SEP #$20 / LDA 지형표,X` 뒤 홀수 번호면 `AND #$0F`, 짝수면 `LSR` 넷을 하고 `PLY / PLX / PLP / RTL` 합니다. `LDA #$0000` 이 윗바이트를 0 으로 두고, C(번호가 홀수인지)는 건드리지 않습니다.
- `00:BDC5` 는 이제 부르는 곳이 없지만 `00:BDC9` 몸통은 그대로 둡니다.

넷째 몸통이 붙어 빠른 훅이 159바이트 늘었습니다(세 세계, 10·11비트 모두). 블록 표를 늘리지 않은 롬은 빠른 훅을 넣지 않으므로 이 훅도 넣지 않습니다. 해석기(`w65816`)로 돌리는 `test_dq5blockgrow` 에 01:81D4 처럼 M·X 16비트로 A = `FFFF` 를 채운 채 `03:CB1B` 를 `JSL` 하는 시험을 더해, 세계 0·1·넷째 세계와 좌표 아홉 곳에서 A 가 `dq5field.terrain` 과 같고(윗바이트 0) X·Y·스택·DB 가 그대로인지 봅니다. `LDA #$0000` 을 뺀 판은 「세계 0 (37,300)」 에서 A = `0103` 으로 실패했습니다.

`03:CB1B` 한 번(들어와서 부른 곳 + 4 로 돌아가기까지)은 이렇게 바뀌었습니다. 10비트·11비트 롬은 같은 값이고, 괄호 안은 그 가운데 `00:BDC5` 몸통입니다.

## 5. 세계 지도 화면의 AND #$01FF

`03:CB07` 몸통의 좌표 `0200` 이상 갈래가 세계 지도 화면에서 돌지 않는다는 주석은 코드만 읽고 적은 것이었습니다. 같은 프로브의 `EXEC` 로 `03:C8D2`·`C932`·`C93E`·`CB68`·`CB73`·`CAC2` 의 실행 횟수를, `03:CB07` 에 들어올 때 `$CE`·`$D0` 의 가장 큰 값을 적었습니다. たびびとのちず(`B6`) 장면은 일지 34 와 같습니다.

```
            C8D2  C932  C93E  CB68    CB73    CAC2    최대 $CE·$D0
세계 0      1     0     0     15,360  15,360  15,360  01FC·01EC
세계 1      1     1     1     15,360  15,360  15,360  01FF·01FF
```

원본·10비트·11비트 롬 모두 같았습니다. 첫 값은 세계 0 에서는 `03:C8D2` 의 즉값(`STX $D0 / LDX #$0000 / STX $CE`)만 두고, 세계 1 에서는 그 뒤 `03:C932`·`C93E` 의 `AND #$01FF` 가 한 번씩 다시 둡니다. 점마다 `03:CB68`·`CB73` 의 `AND #$01FF` 가 돌아 `01FF` 를 넘지 않습니다. `dq5fieldwrite.py` 의 주석을 이 실행 기록으로 고쳤습니다.

## 6. 검사

- 블록 표를 늘리지 않은 롬의 지도 패치(원본 롬에 세계 0·1 원래 지도, 블록 표만 늘린 롬에 원래 지도)는 고치기 전 도구와 바이트마다 같았습니다. 원본 롬 SHA-1 은 그대로입니다.

## 틀렸던 것들
