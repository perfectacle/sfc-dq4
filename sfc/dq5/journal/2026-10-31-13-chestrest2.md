# 2026-10-31-13: 상자 번호 16비트 훅의 남은 것, 2238 읽기, 집은 뒤 빛 블록

[상자 번호 16비트 일지](2026-10-30-23-chest16rest.md)가 남긴 것들을 쟀습니다. 넘길 마스크 `7E:291B` 를 남긴 뒤 다른 상자를 열 때, 상자를 연 뒤 실제로 맵을 떠났다 돌아올 때, `FFFE` 상자 몬스터, 전멸 뒤 교회 기록의 SRAM 과 그 기록을 불러온 뒤입니다. 앞선 [상자 일지](2026-10-29-05-chestgrow.md)부터 남아 있던 셋도 풀었습니다. `BRK 0C`·`0D` 꼴 넷이 무엇인지, 전투 `0C` 의 `7E:2238` 읽기, 필드 조사 보상을 집은 뒤 빛 블록을 되돌리는 곳입니다. 마지막 것은 필드 조사 쓰기가 빠뜨린 조각이어서 `dq5chestwrite.py` 를 고쳤습니다. 결과는 [쓰기 형식 「상자 257개 이상」](../docs/dq5-build-format.md#상자-257개-이상---wide-at)·[「조사 보상」](../docs/dq5-build-format.md#보물상자조사-보상-dq5chest1)과 [맵 형식 「필드」](../docs/dq5-map-format.md#필드-12e5a2)에 넣었습니다.

## 1. 걸어 나갈 수 있는 상자 256

지금까지 256 이상 상자는 19/00 의 (12,45) 하나로 쟀습니다. 계산대 안 (11,46) 에 서서 여는 상자라 어느 쪽으로도 걸어 나갈 수 없었습니다. 그래서 「다른 상자 열기」도 「떠났다 돌아오기」도 못 했습니다.

상자 576개 롬(`widenum575`)의 맵 연결 표를 `dq5chestreloc.py dump` 로 다시 읽고 맵마다 번호 범위를 셌습니다.

```
01/02 2 256
16/00 344 483
...
19/00 571 575
```

01/02 는 맵 연결 `count` 의 끝인 255개를 갖고, 마지막 칸 (5,31)(블록 (4,30))이 상자 256(`28F3 & 80`)입니다. 이 칸은 (4,33) 에서 위를 보고 엽니다. 그 자리에서는 `dq5warp.lua` 가 아래로 걸어 나갈 수 있었습니다. `dq5chestcheck.py` 에 이 칸을 쓰는 `edge_*` 사례를 더했습니다. 내용물은 놓은 차례대로 938G 이고, 잠긴 상자·물건 `33` 으로 바꾼 빌드도 둡니다.

## 2. 떠났다 돌아오기

`edge_leave` 는 상자 256 을 열고, 그 끝 세이브스테이트에서 19/00 으로 걸어 나간 뒤 다시 01/02 (4,33) 으로 들어옵니다. 들어온 장면의 WRAM 을 연 앞의 것과 견줍니다.

```
open   reward 04AA(938G)  set index=00 mask=00 pend=80 ret=F51C   끝 28F3=80 291B=00
away   19/00 cell 5,47
back   01/02 cell 4,34
look   28F3=80, 열린 상자 타일 워드 4개
```

게임이 연 상태 그대로 다른 맵을 거쳐 돌아와도 `1F:FDD0` 훅이 상자 256 자리 넷을 열린 상자 타일로 그렸습니다.

## 3. 남은 마스크 뒤 다른 상자

`edgelock_other`·`edgefull_other` 는 상자 256 을 잠긴 상자(`FFFC`)·가방이 가득 찬 물건 `33` 으로 두고 한 번 엽니다. 둘 다 `12:F839` 에 가지 않아 `291B` 에 `80` 이 남습니다. 19/00 을 거쳐 01/02 의 원래 상자 (35,29)(256 미만, 물건 `33`)를 엽니다.

```
edgelock_other  open pend=00 → 142·14E                       끝 28F3=00 291B=80
                (19/00 → 01/02, 들어선 장면 291B=80)
                open pend=80 → count pend=00 → set index=9C mask=40 pend=00   끝 291B=00
edgefull_other  open pend=00 → 131·12E·14A·13D·14B            끝 291B=80
                open pend=80 → count pend=00 → 12E·14A·13D(set 없음)        끝 291B=00
```

다른 상자를 열 때도 열기 훅 첫머리가 지웠습니다. 맵을 두 번 오가는 동안 `291B` 는 그대로였습니다. 가방이 그대로 가득한 쪽은 다른 상자의 물건도 받지 못했지만, 그 상자가 256 미만이라 `291B` 에 아무것도 남지 않았습니다.

## 4. FFFE 상자 몬스터와 전멸 뒤 기록

상자 300 을 `FFFE` 로 둔 빌드 `widemon2` 를 더했습니다. 이기는 쪽은 무리 `0C` 의 몬스터 칸을 スライム 로 바꿉니다. 이벤트 전투 무리는 `23:D757 + 무리 × 13` 이고 `+1` 이 첫 몬스터라, 무리 `0C` 는 `23:D7F4`(파일 `11D7F4`, `5D`)입니다.

```
widemon2_win   reward FFFE → message 13A → battle group=0C → back pend=08 → set index=05 mask=00 pend=08 ret=F4AA
widemon2_lose  reward FFFE → message 13A → battle group=0C → B7·7E·82·8A·84·86·88    끝 28F8=00 291B=08, 금화 100 → 50
```

`FFFD` 와 메시지(`139` 대신 `13A`)와 무리만 다르고 길은 같았습니다.

전멸 사례는 끝에 SRAM 도 남기게 했습니다. `dq5chestcheck.lua` 에 `SRAM=1` 이면 `70:0000`~`1FFF` 를 `after.sram` 에 쓰는 갈래를 더했습니다. 교회에서 칸 1 에 기록했으므로 `70:0012 + (주소 − 2000)` 을 봅니다. 먼저 금화 세 바이트(`70:002B`~)가 WRAM 과 같은지로 그 칸이 맞는지 봤습니다.

```
widemon_lose   SRAM 70:090A(28F8)=00  70:092D(291B)=08
widemon2_lose  SRAM 70:090A(28F8)=00  70:092D(291B)=08
```

이어서 그 기록을 불러왔습니다. `dq5chestcheck.lua` 에 `RESETAT` 을 더해 20프레임째에 리셋하고, `dq5cdlsweep.py` 의 church-save-load 와 같은 누름(`start` 셋, `A` 열둘)으로 타이틀에서 칸 1 을 고른 뒤 `B` 로 남은 창을 닫았습니다.

```
load    메시지 B6·B7·7E·88   맵 19/00, 금화 50, 28F8=00 291B=08
reopen  01/02 (35,29): open pend=08 → count pend=00 → set index=8E mask=08 pend=00   끝 291B=00
```

불러온 WRAM 에도 `291B` = `08` 이 들어오고, 다음 열기가 지웠습니다. 앞 일지의 전멸 사례는 기록만 한 채로 상자를 열었는데, 이제 리셋해 불러온 뒤에 엽니다.

## 5. BRK 0C·0D 꼴 넷

`BRK 0B`·`0C`·`0D mask idx` 는 `7E:2190 + idx` 비트를 보고·켜고·끄는 명령이고, `idx` `80`~`94` 이면 상자 비트 `2210`~`2224` 입니다. 바이트 검색으로 나온 넷이 실제 명령인지 770장면의 CDL([상자 16비트 일지](2026-10-30-16-chest16.md)의 `dq5cdlsweep.py` 출력)로 봤습니다. 바이트마다 bit0 이 코드, bit1 이 자료, bit4·5 가 그때의 X·M 8비트입니다.

```
01:B60E 01 01 01 01 21 21 21 …   (B612 부터 코드, M 8비트·X 16비트)
0F:8630 02 02 02 02 02 02 02 …   자료만
2A:9630 02 02 …                  자료만
12:B9A6 02 02 …                  자료만
```

`01:B612` 는 `A2 00 0C`(`LDX #$0C00`)로 X 16비트일 때 실행되었습니다. `01:B613` 의 `00 0C 86 88` 은 이 즉시값과 다음 `STX $88` 이 겹쳐 보인 것입니다. 나머지 셋은 읽히기만 하고 실행된 적이 없습니다. 넷 모두 상자 비트를 다루는 명령이 아닙니다.

## 6. 전투 0C 의 7E:2238 읽기

`dq5warp.lua` 로 필드에서 몬스터 `0C` 하나와의 전투를 붙이고(`BATTLE=0C:1`), `21:8C2D` 에서 포인터 `$3A`~`$3C`·`Y`·`$38`·`$39` 를 기록했습니다. `2238` 을 읽는 것은 한 갈래뿐이었습니다.

```
f=608 ptr=7E2238 Y=00 len=01 $38=2B $39=0C stack=18 8B …
```

그 순간 앞 400명령을 고리 버퍼로 남겨 길을 거슬러 올랐습니다. `04:BD0C`~`BD21` 이 무리마다 `$42` = `7E:1001 + X`(몬스터 번호), `$43` = `04` 로 두고 `BRK 88 2B` 를 부릅니다. `BRK` 처리(`00:8F80`)가 `21:8AF8` 로 갑니다. 이 처리는 먼저 `21:8B82` 에서 항목 `2B` 의 설명을 읽습니다. `21:8D96` 의 `2B` 번째는 `00`, `21:8C86` 의 0번째는 `01 00` 으로, 종류 0(`21:8D6A` 의 `7E:2040`, 간격 `21:8D8B` 의 `2A` = 42)의 `+0` 한 바이트입니다. 그래서 `2040 + $39 × 42` = `2238` 을 `$46` 에 읽습니다(`21:8C2F`).

그 다음 `21:8C3A` 가 항목 번호로 처리를 고르고, `2B` 는 `21:94F8` 입니다. 이 처리는 `$43` 이 `0`(일행)일 때만 `$46` 으로 주인공·동료 이름을 고르고, `04` 이면 `21:955D` 로 가서 `21:959B` 의 이름 표에서 `$42` 번째 이름을 베낍니다. 적 이름을 쓰는데 공통 읽기가 몬스터 번호를 일행 레코드 번호로 써서 곁으로 읽는 것이고, 읽은 값은 쓰지 않습니다.

확인으로 `7E:2238` 을 `00`·`FF`·`5A` 로 매 프레임 고정하고 같은 전투를 700프레임까지 돌렸습니다.

```
end.png md5   셋 모두 5ff00449…
final.wram    다른 바이트는 7E:2238 하나
```

몬스터 `0D`·`0E`·`35`~`37` 에서 `2262`·`228C`·`28F2`·`291C`·`2946` 이 읽히는 것도 같은 꼴입니다. `dq5chestreloc.py` 는 `2238` 을 표 밖 코드가 보는 비트로 계속 예약해 둡니다. 읽은 값이 버려지므로 풀어도 되지만, 이번에는 까닭만 문서에 적었습니다.

## 7. 집은 뒤 빛 블록을 되돌리는 곳

원래 롬에서 (22,166) 의 ルラムーンそう 를 집으면 빛 블록 `A7` 이 `CA` 로 돌아가고, 금화로 바꾸면 남았습니다. 세계 지도 버퍼의 그 칸(`7F:530B` 과 9번째 비트 `7E:EA61`)에 쓰기 감시를 걸고 같은 장면을 돌렸습니다.

```
f=458   00:CF50 ← 01:A011(밤, 빛을 놓음)   7F:530B = A7
f=1408  00:CF50 ← 스택 D1 EF 12          7F:530B = CA   21B3 = 10
```

돌아갈 주소 `12:EFD1` 앞은 이렇습니다.

```
12:EFB2: JSR $F43B / BCS 끝
12:EFB7: REP #$20 / LDA $1E73 / CMP #$00CA / BNE 끝
         LDA #$0016 → $90 / LDA #$00A6 → $92 / LDA #$00CA / JSL $00CF50
```

이 코드는 칸이 아니라 보상 값만 봅니다. `12:EF92` 는 조사 종류 표 `12:E4A7` 의 1번입니다. `dq5chestcheck.lua` 에 종류(`12:E4A3` 의 A)와 `12:EFB9` 진입을 기록하게 하고 여섯 사례를 돌리자 종류는 이랬습니다.

```
chest 00   search 03   ahead 0F   lower 10   field 01   foot(패치, 선실 (3,5)) 01
```

발밑 조사도 종류 1 이라, 선실의 발밑 보상을 `CA` 로 둔 롬을 만들어 주웠습니다.

```
kind 01 → reward 00CA map=17/00 → set … ret=EFB4 → light reward=00CA      7F:530B 00 → CA
```

실내에서도 빛 칸 자리의 맵 버퍼가 덮였습니다. 선실은 작아서 화면에는 보이지 않습니다.

`dq5chestwrite.py` 의 필드 조사 쓰기는 이 넷째 조각을 몰라서 보상만 바꾸면 비교값 `CA` 가 남았습니다. 그래서 금화로 바꾸면 빛이 남았습니다. 칸을 옮기고 보상을 `CA` 로 두면 빛은 새 칸에 놓이는데 집은 뒤에는 원래 칸 (22,166) 에 `CA` 를 그리는 코드입니다(이 조합은 코드 읽기). 조각 `12:EFB9`(`AD 73 1E C9 r0 r1 D0 11 A9 x0 x1 85 90 A9 y0 y1 85 92 A9 b0 b1 22 50 CF 00`)를 템플릿에 더해 보상·칸·블록을 함께 쓰게 했습니다. 발밑 보상이 필드 조사 보상과 같으면 실내에서 맵 버퍼를 덮으므로, `dq5chestwrite.py`·`dq5chestreloc.py` 가 거부합니다. 필드 조사 코드를 다른 패치가 바꾼 롬이면 비교할 값을 모르므로 보지 않습니다. 테스트 픽스처의 발밑 보상은 필드 조사 보상(`A1`)과 같았어서 `A2` 로 바꿨습니다.

세계 지도 쓰기(`dq5fieldwrite.py`)는 `00:CF50` 이 블록을 바꾸는 칸을 롬의 즉값에서 읽는데, `12:EFC1` 의 꼴에 블록 `CA` 를 고정해 두었습니다. 이제 상자 쓰기가 그 블록을 칸의 세계 0 블록으로 바꾸므로, 그 두 바이트는 보지 않게 했습니다. 칸을 (24,168) 로 옮긴 롬에서 `changed_cells` 의 첫 둘(`01:A01B`·`12:EFC1`)이 모두 (12,84) 였습니다. 전에는 `12:EFC1` 이 원래 칸 (11,83) 그대로였습니다.

게임에서는 `field`·`field_move`·`field_world1` 의 기대값을 바꿔 다시 돌렸습니다.

```
field         876G   12:EFB9 reward=046C   (11,83)  원본 CA, 패치 CA(전에는 A7 이 남음)
field_move    876G   (24,168)               (12,84)  원본 178, 패치 178(전에는 A7 이 남음), (11,83) 은 CA
field_world1  876G                          (11,83)  CA
```

## 틀렸던 것들

- 다른 상자로 바로 왼쪽의 상자 255 (3,31) 를 골라, 19/00 을 거쳐 `dq5warp.lua` 로 (2,33) 에 들어가 열려 했습니다. 선실이 아닌 곳에서 온 순간이동은 한 칸 아래 (2,34) 에 섰고, 거기서 위로 걷지 못해 12B·12C(찾지 못함)만 나왔습니다. 앞 일지의 전멸 사례처럼 (34,32) 에 서서 위로 한 칸 걸어 원래 상자 (35,29) 를 열게 바꿨습니다.
- 가득 찬 가방 사례에서 다른 상자도 원래 길로 켜질 줄 알았습니다. 가방이 그대로라 그 물건도 받지 못해 `12:F839` 에 가지 않았습니다. 기대를 「켜지 않고 `291B` 는 `00`」 으로 고쳤습니다.
- 필드 조사 빛을 되돌리는 곳이 「물건 보상」 갈래라고 봤습니다. 실제로는 물건·금화가 아니라 `$1E73` = `00CA` 하나를 비교하는 코드였습니다.

## 남은 것

- 동료 칸이 찬 실제 진행 세이브나 처음부터 끝까지 진행했을 때 `7E:28F3`~`291B` 에 다른 코드가 닿는지.
- `dq5chestreloc.py` 의 `2238` 예약을 풀지. 읽은 값이 버려지는 것은 몬스터 `0C` 전투 하나와 코드 읽기로 확인했습니다.
