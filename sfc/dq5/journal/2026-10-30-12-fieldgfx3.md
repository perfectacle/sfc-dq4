# 2026-10-30-12: 필드 블록 1,024개와 세계 1·2 의 시간대 벌

[필드 타일 늘리기](2026-10-30-07-gfxlimit.md)가 남긴 한도 둘을 늘렸습니다. 필드 블록 번호는 512개에서 1,024개로, 세계 1·2 의 2·3번 줄 벌은 한 벌에서 128벌까지 씁니다. 쓰기 형식은 [필드 세계 지도](../docs/dq5-build-format.md#필드-세계-지도)·[필드 블록 표](../docs/dq5-build-format.md#필드-블록입구-표-dq5fieldtables1)·[필드 그림](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)에 있고, 구조는 [필드 형식 「블록」](../docs/dq5-field-format.md#블록-00bbf7-00bc4e)과 [「팔레트」](../docs/dq5-field-format.md#팔레트-01a04b)에 있습니다.

## 1. 블록 번호를 쓰는 곳

롬 전체에서 `7F:0000`·`7E:E000` 의 긴 주소를 찾으니 뱅크 00 에 셋이 나왔습니다. 칸의 번호를 모으는 `00:BBF7`, 같은 꼴로 번호만 돌려주는 `00:BDC5`, 칸의 번호를 바꾸는 `00:CF73`(`00:CF50` 안)입니다. 다른 뱅크의 일치는 모두 자료나 다른 명령의 중간이었습니다.

- `00:BBF7` 은 타일맵 워드(`00:BB85` → `00:BBAC`)와 타일 속성(`00:BCA8`)이 부릅니다. 속성은 타일 번호로 `2A:D512` 를 읽으므로 걸음·충돌은 블록 번호를 직접 보지 않습니다.
- `00:BDC5` 는 지형 `03:CB1B` 하나가 부릅니다. 지형은 `03:CC48 + 번호/2` 의 니블이고, 블록 512개 몫 256바이트입니다. 전투 배경·조우·天空城 착륙·세계 지도 화면이 이 값을 씁니다.
- `00:CF50` 을 부르는 곳은 `01:A025`·`03:BB49`·`05:EF2C`·`12:EFCE` 넷이고, 모두 칸과 번호를 즉값으로 줍니다(번호 `A7`·`71`·`02`·`CA`).

`00:BC48` 입구(`00:D009` 의 `JSL`)는 `00:CF50` 이 칸을 바꾼 뒤 네 칸을 다시 그리는 `00:CFD0` 안에 있습니다. `$04` 는 `00:CFD5` 가 넘겨받은 번호를 그대로 둔 것이고, 사이에 부르는 `00:D2B1` 은 `$04` 를 쓰지 않습니다. 그래서 이 입구로 오는 번호는 위 넷뿐이고 모두 256 미만입니다.

## 2. 10번째 비트를 어디에 두나

9번째 비트는 `7E:E000` 의 8KB 비트 평면입니다. 같은 꼴의 평면을 하나 더 두려면 8KB 가 필요한데 WRAM 에 자리가 없었습니다. `7F` 뱅크는 지도 64KB 가 다 쓰고, `7E:C000`~`DFFF` 는 [앞 일지](2026-10-29-01-fieldgrow.md)에서 잰 대로 `CE00`~`D3FF` 를 움직이는 타일 16벌이 씁니다. 남는 `D400`~`DFFF` 는 3KB 입니다.

그래서 10번째 비트는 롬에 둡니다. 세계마다 압축하지 않은 8KB 평면을 두고, `00:BC33`·`00:BE06` 의 9번째 비트 읽기를 평면도 함께 읽는 `JSL` 훅으로 바꿨습니다. 평면이 롬이라 `00:CF50` 은 10번째 비트를 바꾸지 못합니다. 그 칸들(블록 좌표 (0B,53)·(11,7C)·(E2,75)~(E2,77))에 512 이상을 두면 `dq5fieldwrite.py` 가 거부합니다.

블록 표는 `00:BC4E` 를 `JML` 훅으로 바꿨습니다. 번호가 511 미만이면 원래처럼 `STA $00` 뒤 `00:BC52` 로 돌아가고, 511 이상이면 옮긴 표에서 `$94`~`$97` 을 채운 뒤 `00:BC47` 의 `RTS` 로 돌아갑니다. 원래 표의 읽기 넷(`00:BC72`·`BC78`·`BC80`·`BC8D`)은 건드리지 않습니다. 그래서 타일 늘리기 훅(`00:BC80`·`BC8D`)과 바이트가 겹치지 않고, 원래 표에서 위층 0번과 겹치던 511 도 옮긴 표의 첫 항목으로 씁니다. 지형 표는 512바이트로 옮기고 `03:CB2A`·`CB36` 의 피연산자를 바꿨습니다.

## 3. 처음 만든 훅이 칸을 엉뚱하게 그렸다

블록 512+b 를 블록 b 와 똑같이 두고 지도의 모든 칸을 b+512 로 바꾼 롬을 만들었습니다. 원본 게임과 같아야 하는데, 필드 화면에 없는 개울과 모래가 생기고 산 몇 개가 사라졌습니다. 타일맵 워드 270개가 달랐습니다.

해석기(`w65816`)로 같은 WRAM 에서 `00:BBF7` 을 돌리니 두 롬의 `$94`~`$97` 이 40×32칸 모두 같았습니다. 게임과 해석기가 다르게 도는 명령을 찾다가 `00:BC32` 의 `TAY` 를 보았습니다.

```
00:BC2C  XBA          ; A 윗바이트 = 칸의 하위 8비트
00:BC2E  LDA $02 / AND #$07
00:BC32  TAY          ; M 8비트·X 16비트: Y = 윗바이트:아랫바이트
00:BC37  SEP #$10     ; Y 윗바이트를 지움
00:BC39  TYX
00:BC3A  AND $00BCA0,X
```

X 가 16비트면 `TAY` 는 A 의 윗바이트까지 옮깁니다. 원래 루틴은 `SEP #$10` 으로 지운 뒤 `TYX` 하는데, 훅은 평면을 읽으려고 X 를 16비트로 둔 채 `TYX` 했습니다. 그래서 마스크를 `00:BCA0 + 하위 8비트 × 256 + 칸` 에서 읽었습니다. 해석기의 시작 상태가 그 바이트를 0 으로 두어 같은 값이 나왔던 것입니다. 훅이 평면과 `7E:E000` 을 먼저 읽고 `SEP #$10` 뒤에 `TYX` 하게 고치자 타일맵 4,096워드가 모두 원본 게임과 같았습니다. 단위 시험은 Y 윗바이트에 값을 넣고 돌립니다.

## 4. 세계 1·2 는 시간대를 늘 0 으로 둔다

세계 1·2 의 2·3번 줄은 세 곳이 정합니다(코드 읽기).

```
01:9F86  LDX #$0000 / STX $075E      ; 세계 1. 세계 2 는 01:9FA0
         LDX #$A199 / STX $A5 / LDA #$01 / STA $A7 / JSR $A6A3
02:AD38  LDA $1949 / BNE +4 / JSL $01A055   ; 몇 프레임마다 2·3번 줄을 다시 옮김
00:82C6  LDA $1949 / BNE …           ; 걸음마다 $075E 를 1 올리는 시계
```

들어갈 때 `$075E` 를 0 으로 두고, 시계도 다시 옮기기도 세계 0 에서만 돕니다. [보물상자 일지](2026-10-29-05-chestgrow.md)에서 본 「세계 1·2 에서 밤이 오지 않는다」(`$075E` = `0000`)가 이 세 곳 때문입니다. 벌을 늘리는 일과 얽히는 것은 둘째·셋째 줄입니다. 시간대로 벌을 고르게 해도 시간대가 늘 0 이면 첫 벌만 보입니다.

벌을 늘린 롬은 불러오기의 두 즉값을 시간대 표 첫 항목(하한 0)의 벌로 바꾸고, `02:AD38` 을 훅으로 바꿉니다. 훅은 세계 0 이면 원래처럼 `01:A055` 를 부르고, 세계 1·2 는 `$075E` 로 그 세계의 시간대 표를 뒤에서부터 찾아 벌을 `7E:3956`·`3976` 에 `MVN` 으로 옮깁니다. `01:A055` 를 그대로 세계 1·2 에서 부르지 않은 것은, 그 안의 밤에 빛나는 풀(`01:A05D`~)이 세계 0 의 칸 (0B,53) 을 `00:CF50` 으로 바꾸고 인물 팔레트(11·12번 줄)도 덮기 때문입니다. 시간대를 0 으로 두는 것과 시계는 원래대로 두었습니다. 그래서 벌은 이벤트처럼 `$075E` 를 바꾸는 쪽이 있을 때만 바뀝니다.

## 5. 게임에서 확인

`dq5blockgrowcheck.py` 로 13건이 통과했습니다. 표는 [실측](../docs/dq5-build-format.md#블록-1024개세계-12-벌-실측)에 있습니다.

- same 롬은 세계 0 (341,56)·세계 1·2 (50,28) 에서 BG1·2 타일맵 4,096워드와 VRAM 필드 타일이 원본 게임과 같았습니다. 네 방향으로 걸은 뒤 자리 (340,56) 과 지형 `02` 도 같았습니다. 주인공 칸의 블록은 520 이었습니다.
- swap 롬(새 블록의 왼쪽·오른쪽 칸을 맞바꿈)은 세 세계 모두 채운 칸이 원본 게임의 블록마다 좌우를 바꾼 워드와 같았습니다. 걸은 뒤 지형은 새 블록에 준 `0D` 였습니다. 지형은 `00:BDC5` → `03:CB1B` 로 읽으므로, 두 번째 훅과 옮긴 지형 표를 읽는다는 뜻입니다.
- 새 블록의 아래층만, 또는 위층만 속성 `80` 타일로 바꾼 두 롬은 (341,56) 에서 한 칸도 걷지 못했습니다. 두 층 모두 옮긴 표에서 읽습니다.
- 세계 1 에 벌 셋, 세계 2 에 벌 둘을 둔 롬에서 `$075E` 를 매 프레임 고정하고 서자, 2·3번 줄 색 26개가 시간대 표대로 고른 벌과 같았습니다. 원본 롬은 같은 장면에서 모두 원래 벌이었습니다.

`dq5gfxlimitcheck.py`(23건)·`dq5fieldgrowcheck.py`·`dq5fieldgfxcheck.py`(13건)도 고친 도구로 다시 돌려 모두 통과했습니다.

## 틀렸던 것들

- 10번째 비트 훅이 `TAY` 가 옮긴 Y 윗바이트를 지우지 않았습니다(3절). 해석기가 같은 값을 내어 게임에서만 드러났습니다.
- swap 검사는 처음에 타일맵을 64칸 줄로 보고 `i ^ 1` 로 짝을 지었습니다. 64×32 타일맵은 32×32 화면 둘이 나란히 놓인 꼴이고, 세계 1·2 의 장면은 블록이 홀수 열에서 시작했습니다. 화면 둘을 이어 열을 세고, 짝수·홀수 가운데 맞는 쪽으로 짝을 짓게 고쳤습니다.
- 세계 1·2 의 시간대 시험은 처음에 `LATESET` 으로 `$075E` 를 한 번 바꿨는데 서 있을 때 0 이었습니다. 필드에 선 뒤에도 0 으로 돌아가, `POKE` 로 매 프레임 고정했습니다. 어느 코드가 되돌렸는지는 보지 않았습니다.

## 남은 것

- 블록 번호 11비트 이상. 같은 꼴의 평면을 하나 더 두면 되지만 블록 표 1,024개 × 2층이 한 뱅크의 3분의 1 이고, 지금은 필요한 곳이 없어 하지 않았습니다.
- 세계 지도 화면(`03:C8B3`)의 점이 옮긴 지형 표를 읽는지는 코드 읽기로만 봤습니다. 같은 `00:BDC1` 을 쓰는 지형(`$1AA0`)은 게임에서 확인했습니다.
- `00:CF50` 이 칸을 바꾸는 네 장면(밤에 빛나는 풀 `01:A025` 등)을 늘린 롬에서 돌려 보지 않았습니다. 그 칸들은 512 미만만 받습니다.
- 디코더 `dq5battlebg.py`·`dq5encounter.py` 의 지형 계산은 원래 지형 표와 9비트 번호를 씁니다. 늘린 롬은 `dq5field.terrain`·`world_blocks` 로 봅니다.
- 세계 1·2 의 시계와 `$075E` 를 0 으로 두는 것은 바꾸지 않았습니다. 세계 1·2 에서 밤을 돌리려면 `00:82C6`·`01:9F86`·`9FA0` 을 고쳐야 하고, 그 뒤 밤에 빛나는 풀처럼 세계 0 을 가정한 코드가 따라옵니다([쓰기 형식의 필드 조사](../docs/dq5-build-format.md#입력과-고정-한도)).
- `LATESET` 으로 바꾼 `$075E` 가 세계 1·2 필드에 선 뒤 0 으로 돌아간 까닭.
