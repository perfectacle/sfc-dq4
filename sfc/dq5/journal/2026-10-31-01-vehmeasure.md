# 2026-10-31-01: 탈것을 타고 내리는 장면과 세계 1·2 의 탈것, 52/50·53/52 물체 실측

앞 일지들([탈것 칸 수](2026-10-30-22-vehiclelayout.md), [マスタードラゴン 장면 블록](2026-10-30-30-dragonlayout.md), [지형 루틴](2026-10-30-35-bdc5.md))이 남긴 탈것 장면을 쟀습니다. マスタードラゴン 을 세우는 `01:BB7C` 의 나머지 두 부르는 곳(`03:8F1F`·`12:8BE9`)과 てんくうのベル 의 이륙(`11:8E18`), 융단을 펴고 내리는 장면, 天空城 이 실제로 내려앉는 장면, 세계 1·2 의 융단과 탈것 내리기, 칸 바이트가 옮겨진 52/50·53/52 물체, マスタードラゴン 칸을 제자리에서 고친 롬입니다. 재는 동안 원본과 다르게 움직이는 롬은 없었습니다. 결과는 [그래픽 형식의 「탈것」](../docs/dq5-graphics-format.md#탈것-01c4be-16f7dd-00fc08), [쓰기 형식의 블록 훅 실측](../docs/dq5-build-format.md#블록-훅-속도빛-칸세계-지도-실측)과 [맵 OBJ 물체](../docs/dq5-build-format.md#맵-obj-물체탈것세트-칸-배치-dq5objlayout1)에 있습니다.

## 1. 프로브 하나로 모으기

블록 프로브(`dq5vehicleblocks.lua`)와 지형 루틴 프로브(`dq5bdc5.lua`)는 둘 다 드라이버를 `dofile` 하므로 겹쳐 쓸 수 없습니다. 새 프로브 `lua/dq5vehscene.lua` 가 한 번에 모읍니다.

- `00:FC60` 에서 탈것 슬롯이 그린 블록(앞 프로브와 같은 줄)
- `03:CB1B` 를 부른 곳마다 횟수와 돌려준 A
- `EXEC` 주소의 실행 횟수와 처음·마지막 프레임
- `$1954`·맵·세계·필드 좌표가 바뀐 프레임
- 블록을 처음 그린 프레임 + 2(`SHOTLAG`)의 WRAM·OAM

`dq5vehscenecheck.py` 가 이 프로브로 장면을 돌립니다. 롬은 원본, `dq5blockgrowcheck.py` 의 same 롬 10·11비트(이번에 `make_roms(only=...)` 로 same 만 만들게 함), 4프레임 マスタードラゴン 롬(`dq5vehiclecheck.py` 의 dragon4)입니다.

## 2. 융단을 펴고 내리기

세계 0 (310,60) 에서 まほうのじゅうたん 을 どうぐ → つかう 로 폈습니다. 847프레임에 `01:BBD4` 가 돌고 `01:BE8E` 가 네 번 불렸고, 메시지 「ああああは まほうのじゅうたんを ひろげた!」 가 닫힌 900프레임에 `$1954` 가 `80` 이 되었습니다. 펴는 그림은 따로 없었습니다. 탈것 슬롯은 902프레임부터 걷기 블록 4·5(아래 방향)를 그렸습니다. 세 방향으로 걸은 뒤 A 를 누르자 1,356프레임에 `01:BE8E` 가 다시 네 번 불렸고, 1,357프레임에 `$1954` 가 `00` 이 되었습니다.

```
carpet0-original: 1954 00 → 80 → 00, 01:BE8E 8번(0006), 01:81D6 30번(0006 22·0007 8)
                  그린 블록 80-1·80-2·80-3 모두 0~7
```

펴기·걷기·내리기 모두 세 부분이 걷기 블록(방향 4 × 프레임 2)만 그렸습니다. 옮기기만 하는 블록(8·8~10·8)은 이 장면에서도 그려지지 않습니다.

`01:BBD4` 는 `$BE` bit7(실내)이 꺼지고 `$1949` = 0 일 때만 `01:C1A5` 로 (x,y−1)·(x+1,y−1)·(x,y)·(x+1,y) 의 지형이 목록 `01:BE7A`(`01`·`06`)에 있는지 봅니다(코드 읽기, 위 네 번이 그 네 칸).

## 3. 세계 1·2 에서 융단을 펼 수 없는 까닭

[앞 일지](2026-10-30-35-bdc5.md)는 세계 1·2 에서 융단을 펴는 입력이 맞지 않았다고 적었습니다. 화면을 찍어 보니 입력은 맞았고, 둘 다 「ここでは ひろげられない!」 였습니다. `01:BE8E` 는 한 번도 불리지 않았습니다. `7E:1949` 읽기를 감시하자 847프레임에 `01:BBDE`(`LDA $1949 / BNE`)가 읽었습니다. 게임이 세계 0 밖에서는 지형을 보지 않고 거절합니다. てんくうのベル 의 검사 `01:BBF0` 도 같은 꼴입니다.

그래서 세계 1·2 의 탈것은 `$1954` 를 두어 만들었습니다(`LATESET=1954=80`·`81`·`82`).

## 4. 날아다니는 탈것의 A

天空城·マスタードラゴン 을 세계 1·2 에 두고 A 를 눌렀는데, 내려앉을 때와 그냥 날아가 버릴 때가 섞였습니다. 프레임마다 `7E:007F`·`7E:007E`·`$B8` 을 찍었습니다.

```
452~484  7F=00 7E=00  B8=14       (서 있음, 이 동안 누른 A 는 무시)
485      7F=02 7E=02               (マスタードラゴン 은 7F 가 2씩)
488      7F=08 7E=00  B8=15        (& 7 = 0 인 프레임에 입력을 읽고 한 칸 감)
```

날아다니는 탈것은 서 있다가 30프레임쯤 뒤 바라보는 쪽으로 저절로 나아갑니다. 서 있는 동안 누른 A 는 받지 않았고, 움직이는 동안은 입력을 4·8프레임에 한 번 읽습니다. 드라이버의 고정 프레임 입력은 이 창을 자주 비껴갔습니다. 프로브에 `APRESS` 를 두어 `7F & 7` 이 6 이상인 프레임에 A 를 3프레임 누르고, `01:BC3F`(`00:8127` 이 부르는 탈것 A 처리)가 돌면 멈추게 했습니다. 이렇게 하자 天空城·マスタードラゴン 모두 세 세계에서 한 번에 내렸습니다.

## 5. 天空城 이 내려앉는 장면

앞 측정은 두 번 다 「ここでは 降りられない。」 였습니다. A 는 `01:BC3F` → `01:C30A` → `01:C375` 로 가고, `01:C375` 는 `01:C3AB` 를 줄마다 네 번, 세 줄 부릅니다. 곧 (x−1~x+2, y−1~y+1) 의 4x3 칸이 모두 지형 `01`·`06` 이어야 합니다(코드 읽기). 처음에는 3x3 으로 셈해 세계 1 (74,32) 를 골랐는데, 게임은 넷째 칸에서 `0003` 을 돌려주고 거절했습니다. (76,31) 의 지형이 3 이었습니다. 4x3 으로 다시 셈해 고른 자리입니다.

```
tenkuu0 (306,40): 01:BE8E 12번(0006 11·0001 1) → 01:C319, 73프레임 뒤 1954 = 00, 06/08 (24,11)
tenkuu1 (60,14):  01:BE8E 12번(0006)           → 같음, 06/08
tenkuu2 (46,13):  01:BE8E 12번(0006)           → 같음, 06/08
그린 블록: 81-1 블록 0, 81-2 블록 0
```

내려앉은 뒤 天空城 안(06/08)으로 들어갑니다. 天空城 은 이 장면에서도 블록 0 만 그렸습니다.

## 6. マスタードラゴン 의 남은 장면 셋

**てんくうのベル.** 필드 (341,56) 은 산 사이라 「私を よぶのなら もっと広い場所が 必要だ。」 였고, (310,60) 에서 불렀습니다. `11:8E0F` 가 `01:BBF0` 을, `11:8E18` 이 `01:BEA9` 를 부르고 `01:BF47` → `01:BF7C` 로 이륙했습니다. 그 뒤 A 로 착륙(`01:C200`)했습니다.

**스크립트 41.** `03:8F1F` 는 스크립트 41(`15:F60B`)의 네이티브 호출 `03:8EC7` 안에 있습니다. 06:B68D 의 대화가 부르고 메시지 442「わが名は　マスタードラゴン。」 를 띄우므로, プサン 이 マスタードラゴン 의 모습을 드러내는 장면으로 보입니다. [이벤트 형식](../docs/dq5-event-format.md)처럼 06/00 에 들어선 뒤 `$19B3`~`$19B5` 에 `15:F60B` 를 넣고 `$19AE` bit7 을 켜서 걸었습니다. `7E:2190` bit7 을 끄면 06/00 이 51/00 필드로 내보내므로 켠 채로 했습니다. 그래서 맵 루틴이 378프레임에 한 번, 스크립트가 716프레임에 한 번 `01:BB7C` 를 부릅니다. 원 모양으로 화면을 닫았다가 여는 효과 뒤, 같은 자리 (36,51) 에 같은 값(`37C7` = `80`·`32A7` = `83`)을 두었습니다. 그 뒤로는 프레임이 0 에 머물러 블록 12 만 그렸습니다.

**`12:8BE9`.** 앞 일지는 맵을 불러올 때 닿는다고 보았습니다. 다른 맵으로 옮겨도, 06/00 을 다시 불러와도 닿지 않았습니다. `$1A0C` 를 지우는 곳을 찾자 `2B:80E5`(`STZ $1A0C`)가 맵을 불러올 때마다 돌았습니다. `12:8B82` 를 부르는 곳은 `01:8AA4` 하나이고, 그 루틴(`01:8A7F`·`01:8A87`)을 부르는 곳을 거슬러 가니 `01:8677`(`JSL $208001`, 전투) 뒤의 `01:867C` 였습니다. 이 길은 코드 읽기이고, 실행 기록으로는 아래처럼 전투(`20:8001`) 뒤 `01:867B`·`01:872B`·`12:8BBC`·`12:8BE9` 가 차례로 돌았습니다. 06/00·06/05 는 조우 구역이 `FF` 라 전투가 없어, `dq5encounterwrite.py` 로 06/00 에 구역 `01` 을 달고 조우 계수를 `FF` 로 덮은 롬에서 걸었습니다. 전투는 프로브의 `FLEE=1` 로 にげる 를 골라 끝냈습니다(전투 중 `$1001` 은 0 이라 `20:8001`~`01:867B` 로 가림).

```
battle0600: 1294 20:8001 → 2027 12:8BE9 → 01:BB7C, 2B:80E5 는 다시 돌지 않음
            슬롯 7 칸 목록 8360 → 83C0, 37C7 = 80·32A7 = 83, 블록 12~15
```

`$1A0C` 는 맵을 불러오면 지워지고 전투로는 지워지지 않아, 전투 뒤 화면을 다시 세우는 길이 マスタードラゴン 을 다시 둡니다.

세 장면을 4프레임 롬에서도 돌렸습니다. 두 롬 모두 그린 블록이 도구가 둔 자리였고, 두 프레임 뒤 OAM 에 칸 표 그대로 놓였습니다(착륙 둘째 블록은 원본처럼 나오지 않음).

```
bell-original:     37C7 60 32A7 87  그린 장면 블록 15·16  OAM 16: 921
bell-dragon4:      37C7 80 32A7 85  그린 장면 블록 16·17  OAM 17: 921
script41-original: 37C7 80 32A7 83  블록 12   OAM 760·900·1000
script41-dragon4:  37C7 C0 32A7 83  블록 18   OAM 760·900·1000
battle0600-original-enc: 블록 12~15  OAM 2037·2072·2088·2104
battle0600-dragon4-enc:  블록 18~21  OAM 2036·2071·2087·2103
```

## 7. 세계 1·2 의 탈것과 블록을 늘린 롬

장면 열하나(세계 0 융단, 세계 1·2 융단 쓰기, 세계 1·2 융단 타고 걷고 내리기, 天空城 셋, マスタードラゴン 셋)를 원본과 10·11비트 same 롬에서 같은 입력으로 돌렸습니다. 장면마다 `03:CB1B` 를 부른 곳·횟수·돌려준 A, `$1954` 가 거친 값, 끝난 맵·좌표를 견줬고 22건 모두 같았습니다. 일이 일어난 프레임은 세 장면에서 1~3프레임 어긋났습니다(天空城·マスタードラゴン 세계 0 의 착륙은 늘린 롬이 1프레임 이르고, 세계 2 융단은 걷기가 3프레임 이르고 내리기가 1프레임 늦음). [지형 루틴 일지](2026-10-30-35-bdc5.md)의 훅을 고친 뒤라 돌려준 A 의 윗바이트도 모두 0 이었습니다.

```
ride1-original: 01:81D6 48번(0006 16·0007 2·0009 8·0000 22), 01:BE8E 4번(0006), 끝 (62,14), 1954 00 → 80 → 00
ride2-original: 01:81D6 48번(0006 8·0009 10·0000 30),         01:BE8E 4번(0006), 끝 (46,13)
dragon1-original: 01:BE8E 4번(0006) → 01:C200 → 01:BF7C, 블록 15·16
```

## 8. 52/50·53/52 물체와 マスタードラゴン 제자리 칸 쓰기

`dq5objlayoutcheck.py` 의 고친 롬은 04/06 에 물체를 더해, 52/50 의 물체 18·19·21 과 53/52 의 24·25 가 가리키던 칸 바이트가 `16:FE10` 으로 옮겨집니다. 두 맵에 들어가는 장면을 더했습니다(`TO=52/50,22,18`, `TO=53/52,40,27`). 처음 53/52 를 (30,21) 에서 쟀을 때는 8x2 물체 26 이 화면 오른쪽 밖이라 OAM 묶음을 찾지 못해 (40,27) 로 옮겼습니다.

```
52/50: 물체 18·19·20·21 이 슬롯 9~14, OAM (88,80)·(120,80)·(168,80)·(216,80), 화면 86/86·273/273·185/185·86/86
53/52: 물체 24·25·26, 화면 22/86·86/86·306/365(우선순위가 낮아 BG 에 가림)
두 롬의 결과가 덤프마다 같음, 검사 9개 통과
```

물체를 잡는 슬롯은 700·800프레임 덤프에서 서로 바뀌었습니다. `03:83D8`·`03:8421` 이 8프레임마다 슬롯의 그림 번호를 맞바꾸기 때문입니다([맵 형식](../docs/dq5-map-format.md)). 53/52 의 물체 24·25 는 칸으로 찾으면 덤프마다 자리가 맞바뀌어 나옵니다. 화면 픽셀이 다 맞지 않는 것은 원본도 같아서, 53/52 는 두 롬의 결과가 같은지로 봅니다.

マスタードラゴン 칸 쓰기는 [앞 일지](2026-10-30-30-dragonlayout.md)에서 칸 표를 옮기는 롬만 쟀습니다. 칸 수·프레임 수를 그대로 두고 두 부분의 `up1`·`down1` 과 부분 1 의 `land0`·`tenkuu1` 을 좌우로 뒤집은 롬을 만들었습니다(제자리 쓰기 1개, `land1`·`tenkuu3` 은 같은 블록 15 라 두었음). `dq5vehiclecheck.py` 의 `dragon_runs` 를 그대로 불러 걷기 블록·덤프 20개와 장면 넷을 돌렸고 11개 검사가 모두 통과했습니다. 뒤집은 `land0`(블록 16)은 749프레임, `tenkuu1`(블록 13)은 419·1,269프레임 OAM 에 칸 표 그대로 나와 화면 픽셀이 같았습니다.

## 9. 검사

```
MESENCE=… uv run --locked python sfc/dq5/tools/dq5vehscenecheck.py rom/dq5.sfc --state work/state/ship.mss
MESENCE=… uv run --locked python sfc/dq5/tools/dq5objlayoutcheck.py rom/dq5.sfc --state work/state/ship.mss
```

`dq5vehscenecheck.py` 는 장면 검사 40개와 제자리 칸 쓰기 11개, `dq5objlayoutcheck.py` 는 9개가 통과했습니다. MesenCE 테스트 러너가 가끔 첫 프레임에 255 로 끝나 `dq5vehscenecheck.py` 는 한 번 더 돌립니다.

## 틀렸던 것들

- 세계 1·2 에서 융단을 펴지 못한 것을 입력 탓으로 보았습니다. `01:BBDE` 가 `$1949` ≠ 0 이면 거절합니다.
- 天空城 의 착륙 검사를 3x3 칸으로 보았습니다. `01:C375` 는 줄마다 네 칸, 4x3 칸을 봅니다.
- `12:8BE9` 가 맵을 불러올 때 닿는다고 보았습니다. 맵을 불러오면 `2B:80E5` 가 `$1A0C` 를 지우고, `12:8B82` 는 전투 뒤에만 돕니다.
- 전투 중 `$1001` 로 전투를 가리려 했습니다. 이 전투에서 `$1001` 은 0 이었습니다.
- 날아다니는 탈것이 서 있을 때 누른 A 가 받힐 것으로 보았습니다. 움직이기 시작한 뒤 입력을 읽는 프레임에만 받습니다.

## 남은 것

- 天空城(06/00·06/05)에서 실제로 전투가 일어나는 길(대화 전투 `06:D620`·이벤트 전투 `02:A126`·`02:A782`)이 있는지. 이번 `12:8BE9` 는 조우 구역을 단 롬으로만 닿았습니다.
