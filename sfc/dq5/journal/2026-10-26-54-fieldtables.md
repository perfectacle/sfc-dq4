# 2026-10-26-54: 필드 블록·입구 표 쓰기와 자료 뱅크 제한

필드 블록 양층, 일반·보조 입구, 그룹별 도착 표를 JSON으로 고치는 `dq5fieldtables.py`를 만들었습니다. 형식은 [쓰기 도구 문서](../docs/dq5-build-format.md#필드-블록입구-표-dq5fieldtables1)에 있습니다. 함께 확인한 블록 표의 끝과 필드 자료 배치 제한도 고쳤습니다.

## 1. 9비트 번호와 정의 표 크기는 다릅니다

블록 번호는 9비트지만 정의 표에는 511개만 있었습니다.

| 표 | 시작~끝 | 크기 |
| --- | --- | --- |
| 아래층 | `2A:A32C`~`AD26` | 511×5바이트 |
| 위층 | `2A:AD27`~`B721` | 511×5바이트 |
| 일반 입구 | `04:FD97`~`FE81` | 47×5바이트, `FE82`의 `FF`로 끝 |
| 보조 입구 | `04:FE83`~`FEC8` | 14×5바이트, `FEC9`의 `FF`로 끝 |
| 그룹 도착 | `0F:EA97`~`EBA4` | 54×5바이트, 다음은 실행 코드 |

아래층 511번을 계산하면 위층 0번 자리가 나오고, 위층 511번은 세계 1 압축 지도 시작 `2A:B722`입니다. 세 세계의 65,536칸씩을 풀어 보니 최대 번호는 510·497·508이고 511은 한 번도 쓰이지 않았습니다. 블록 쓰기와 지도 입력은 0~510만 허용하고, 갤러리에서도 잘못 읽던 마지막 블록을 뺐습니다. 블록 안에 적는 타일 번호는 그대로 0~511입니다.

## 2. 원본 바이트를 보존하는 고정 표 쓰기

블록은 두 층의 타일 네 칸을 따로 고칩니다. 다섯째 바이트의 상위 네 비트가 타일 번호의 9번째 비트이고, 뜻을 확인하지 못한 하위 니블은 원본에서 보존합니다.

입구는 같은 그룹이 여러 항목에 있으므로 그룹이 아닌 목록 안의 인덱스로 고칩니다. 도착 표의 세계 값도 세계 번호로 바꾸어 내보내지 않고 원시 `world_code` 0~3으로 둡니다. 원본 그룹 05·27에는 0이 있어 이것도 그대로 왕복해야 합니다.

```text
블록 511개 × 2층, 입구 61개, 도착 54개
5,685바이트: 원본과 다른 항목 0개
내보낸 JSON 그대로 패치: 쓰기 0개
필드 표·지도 경계 합성 검사 10개: 통과
```

실제 롬의 블록 양층·일반/보조 입구·도착 항목을 고친 패치를 빌더에 넣고 기존 읽기 도구로 다시 확인했습니다. 합성 검사에서는 뜻 모르는 니블에 0이 아닌 값을 넣어 보존을 확인하고, 마지막 항목을 고쳐도 다음 표·압축 지도·종료자·실행 코드가 바뀌지 않는지 봤습니다.

## 3. 필드 압축 자료를 아무 확장 뱅크에나 놓을 수는 없습니다

앞서 쓰던 기본 `34:8000` 대신 `60:8000`에 세 세계를 다시 압축해 놓자 화면이 꺼진 채 멈췄고 WRAM 지도도 달랐습니다. 배치 주소만 `34:8000`으로 바꾸자 세 세계 모두 일치했습니다.

```text
세계 0: 지도 65,536 + 상위 비트 8,192바이트, 차이 0
세계 1: 지도 65,536 + 상위 비트 8,192바이트, 차이 0
세계 2: 지도 65,536 + 상위 비트 8,192바이트, 차이 0
```

실행 커버리지로 원인을 확인했습니다. `01:A5D1`의 `PLB`로 자료 뱅크를 DB에 넣은 뒤, `01:A668`·`A673`이 `$00A5`를 읽고 쓰고 `01:A656`·`A660`·`A66C`이 DMA 레지스터 `$4371`·`4375`·`4372`를 씁니다. `01:A67D`도 `$420B`를 씁니다. 뱅크 `60`에는 이 낮은 주소의 WRAM·I/O 미러가 없습니다.

필드 지도 쓰기 도구는 이제 확장 뱅크 `30`~`3F`만 받습니다. 덩어리가 뱅크를 넘어 다음 뱅크로 옮겨지는 경우도 다시 검사하며, `3F` 끝을 넘으면 오류입니다. 기존 한글 재압축 도구도 이 영역을 쓰므로 함께 빌드할 때는 서로 겹치지 않게 `--at`을 정해야 합니다.

## 4. 블록과 입구를 게임에서 바꾸기

블록 8의 아래층 타일을 `[1,257,2,258]`, 위층을 `[3,259,4,260]`으로 바꿨습니다. 같은 필드 자리에서 원본과 패치 롬을 실행하고 BG1·BG2 타일맵을 비교했습니다. 화면 버퍼에 있는 전체 블록 61개와 오른쪽 반블록 2개에 해당하는 변경을 예측하자, 타일맵 전체 8,192바이트에서 차이가 0이었습니다. 원본에서 바뀐 바이트는 748개입니다. 위층에는 게임이 붙이는 우선순위 비트 `2000`도 포함했습니다.

일반 입구 첫 항목의 그룹을 4로 바꾸고, 그룹 4 도착을 (27,73)·층 1·오른쪽 방향으로 고쳤습니다. 원래 입구 아래에서 위로 걸어 `04/00 (27,73)`에 도착했습니다. 보조 입구 첫 항목도 필드 (341,57)·그룹 4로 고쳐 아래로 한 칸 걸으니 같은 자리에 들어갔습니다. 도착 WRAM의 층과 방향도 맞았습니다.

일반 입구의 그룹 1 항목 좌표를 (341,56)으로 고친 롬에서는 마을에서 실제로 걸어 나와 그 필드 좌표에 섰습니다. 세 세계 재압축 검사를 합쳐 8개 장면에서 7개 비교를 통과했습니다.

## 5. 다시 확인하기

`$MESENCE`와 조작 가능한 배 선실 세이브스테이트를 준비합니다. 새 실행 폴더에 입력 JSON·패치·롬·IPS·덤프·화면과 `results.json`을 남깁니다. 원본과 세이브스테이트는 바꾸지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc check
uv run --locked python -m unittest discover -s sfc/dq5/tools/tests -p 'test_dq5field*.py'
uv run --locked python sfc/dq5/tools/dq5fieldtablecheck.py rom/dq5.sfc --state work/state/ship.mss --out work/fieldtablecheck
```

## 틀렸던 것들

블록 번호가 9비트이므로 정의 표도 512개라고 적었지만, 표 사이 실제 간격과 세 세계 전수 결과는 511개였습니다. 쓰기 도구를 만들면서 마지막 항목이 다음 자료를 덮는다는 것을 확인했습니다.

또한 압축 덩어리가 한 뱅크에 들어가면 어느 확장 뱅크나 쓸 수 있다고 보았지만, 필드 불러오기는 자료 뱅크를 DB로 쓰며 WRAM과 DMA 레지스터도 접근했습니다. 이벤트 스크립트에서 통과한 뱅크 `60`을 필드 자료에 그대로 적용할 수 없었습니다.

## 남은 것

필드 표의 항목 수를 늘리거나 표 자체를 옮기는 기능은 없습니다. 그룹 `50`~`54`와 일부 좌표의 특수 도착 코드는 그대로입니다. 다음 쓰기 도구는 성장·조우 구역·상점 목록이며, 보행 대사 일괄 쓰기와 인물 목록 재배치도 이어서 다룹니다.
