# 2026-10-30-30: マスタードラゴン 칸 수·프레임 수 바꾸기와 착륙·天空城 장면 블록 옮기기

[앞 일지](2026-10-30-22-vehiclelayout.md)는 マスタードラゴン 의 칸 수·프레임 수 바꾸기를 모두 거부했습니다. 착륙·이륙(`01:BF7C`)과 天空城 장면(`01:BB7C`)이 부분 1 의 블록 12~16 을 즉값이 아닌 고정값으로 그렸기 때문입니다. 이번에는 두 루틴의 고정값을 즉값처럼 고쳐 장면 블록을 새 칸 표로 옮기게 했고, 그림자 상하 반전 표를 옮겨 늘릴 수 있게 했습니다. 4프레임 롬과 부분 1 을 5x5 로 바꾼 롬을 만들어 걷기와 장면 넷을 게임에서 쟀습니다. 결과는 [그래픽 형식의 「탈것」](../docs/dq5-graphics-format.md#탈것-01c4be-16f7dd-00fc08)과 [쓰기 형식](../docs/dq5-build-format.md#맵-obj-물체탈것세트-칸-배치-dq5objlayout1)에 있습니다.

## 1. 장면이 읽는 값 찾기

`01:BF7C` 와 `01:BB7C` 를 다시 디스어셈블했습니다. 고칠 수 있는 즉값은 넷입니다.

```
01:BF80  a9 87     LDA #$87      ; 32A7(마지막 프레임)   ← 착륙·이륙
01:BF85  a9 07     LDA #$07      ; 3287(프레임)
01:BF92  a9 20     LDA #$20      ; 31E7
01:BBB3  a9 80     LDA #$80      ; 37C7(방향 간격)       ← 天空城 06/00·06/05
01:BBB8  a9 83     LDA #$83      ; 32A7
01:BBCD  a9 20     LDA #$20      ; 31E7
```

앞 일지는 두 장면이 「방향 3 자리」에서 그린다고만 적었습니다. 그 3 은 방향이 아니라 `31E7` = `20` 에서 옵니다. `00:FC2F` 는 `3240` bit7 이 꺼져 있을 때 `31E0` 위 4비트가 0 이 아니면 그 값을 `00:EE7C` 의 색인으로 쓰고, `EE7C[2]` 가 `03` 입니다(bit7 이 켜져 있으면 `00:FC2A` 가 `3240` 아래 4비트를 `EE7C` 의 색인으로 씀). 그래서 오른쪽으로 돌든 왼쪽으로 돌든 같은 블록이었습니다. 착륙·이륙은 `37C7`·`37E7` 을 건드리지 않아 걷기 간격 그대로이고, 天空城 은 `37C7` 만 바꿉니다. `01:BB7C` 가 그 앞에 부르는 `12:8CFD`·`12:8CBE` 는 자리(`3020`·`3080` 등)만 씁니다(코드 읽기). 그러면 첫 칸은 이렇습니다.

```
착륙·이륙: (3 × 방향 간격 + X × 프레임 간격) / 2   X = 3287, 한 번 세어 X − 1 로 내림
天空城   : (3 × S + 프레임 × 프레임 간격) / 2      S = 37C7, 프레임 0~3(32A7 = 83)
```

원본 값(방향 간격 `60`, 프레임 간격 `20`, X = 7, S = `80`)을 넣으면 블록 16·15 와 12~15 로, 앞 일지의 측정과 같습니다.

## 2. 장면 블록을 둘 자리

칸 수·프레임 수를 바꾸면 걷기 블록은 0 ~ 4 × 프레임 수 − 1 입니다. 장면 블록은 이와 겹치지 않아야 하고, 착륙은 3 × 프레임 수 + X 와 그 앞, 天空城 은 3 × S / (칸 수 × 2) 부터 넷입니다. 고칠 수 있는 범위는 X 가 1~15(`32A7` 아래 4비트), S 가 칸 수 × 2 의 배수로 255 이하입니다. 이 안에서 세 무리가 겹치지 않고 블록 수가 가장 적은 X·S 를 차례로 찾게 했습니다(`scene_layout`).

```
4프레임 4x4: 걷기 0~15, 착륙 17·16(X = 5), 天空城 18~21(S = C0)  → 22블록
3프레임 5x5: 걷기 0~11, 착륙 17·16(X = 8), 天空城 12~15(S = C8)  → 18블록
4프레임 5x5: 天空城 을 걷기 뒤에 두려면 S = 6 × 50 = 300 → 거부
```

원본은 `land1`(착륙 프레임 6)과 天空城 프레임 3 이 같은 블록 15 를 씁니다. 옮길 때는 둘을 나눕니다. 그래서 문서에도 장면 블록을 따로 두었습니다. `82-1` 의 `cells` 에 `land0`(먼저 그리는 블록)·`land1`·`tenkuu0`~`tenkuu3` 열쇠가 생겼습니다. 칸 수가 그대로일 때 두 열쇠가 같은 바이트를 다른 값으로 쓰거나, 문서에 없는 열쇠가 그리는 칸을 바꾸게 되면 거부합니다. 원래 롬에서 그리는 칸이 겹치는 곳은 이 블록 15 하나뿐이었습니다(부분 일곱의 모든 열쇠를 견줌).

## 3. 상하 반전 표

그림자의 상하 반전 표는 `01:C132`(マスタードラゴン, 24칸)·`01:C40D`(天空城, 8칸)가 `LDA long,X` 로 읽습니다. 뱅크까지 피연산자에 있어 표를 어디에 두어도 됩니다. 원래 표에 들어가면 제자리에 쓰고, 길면 칸 표 뒤에 두고 피연산자(`01:C133`·`01:C40E`)를 고치게 했습니다. 4프레임 マスタードラゴン 그림자는 상하 반전이 32칸이라 옮깁니다.

4프레임 롬은 칸 표 352 + 64 바이트에 표 33바이트로 449바이트라, `04:FEE0`(288바이트)에 들어가지 않았습니다. 칸 표는 데이터 뱅크(`01:C0EE` `LDA #$04`)로 읽으므로 다른 뱅크도 됩니다. 원래 롬에서 가장 큰 빈 자리 `0B:FBB0`(1,104바이트)에 두었습니다.

```
0B:FBB0 탈것 82 칸 표      01:BF86 탈것 82-1 착륙 프레임 05    01:BBB4 탈것 82-1 天空城 간격 c0
01:BF81 착륙 마지막 프레임 85   01:C09A 82-1 dir 80   01:C0F7 82-1 count 15
01:C0C8 82-2 dir 20   01:C10E 82-2 count 0f   01:C133 82-2 상하 반전 표 주소 50 fd 0b   01:C0AA 프레임 수 83 …
```

`dq5objlayout.py rom/dq5.sfc check` 는 그대로 쓰기 0개였습니다.

## 4. 게임에서 재기

`dq5vehiclecheck.py` 에 고친 マスタードラゴン 두 벌을 더했습니다. 4프레임 롬은 프레임 3 을 프레임 1 을 좌우로 뒤집은 칸으로, 5x5 롬은 줄마다 첫 칸을 더하고 마지막 줄을 한 번 더 두었습니다. 원본 롬과 함께 같은 검사를 거칩니다. 필드 (310,60) 에서 네 방향으로 걷고, 앞 일지의 장면 넷(착륙 오른쪽·왼쪽, 이륙, 天空城 06/00)을 돌립니다.

처음에는 장면 블록을 처음 그린 프레임과 그 뒤 두 프레임에서 덤프해 OAM 을 보았는데, 장면 넷 모두 불일치였습니다. 원본 착륙을 744~762 프레임마다 덤프해 보았습니다.

```
744~748: 블록 3(right0)   749~756: 블록 16(land0)   757~762: 블록 6(down0)
748: 3287=07 31E7=20 … 756: 3287=00 31E7=40
```

`dq5vehicleblocks.lua` 가 블록 16 을 센 셀 프레임은 747 이고, OAM 덤프에는 749 에 나왔습니다. 블록 프로브의 번호는 끝난 프레임 수라 그 프레임 안의 그리기보다 하나 작고, 그린 칸이 다음 프레임 OAM 으로 가는 것으로 보입니다. 天空城 블록 13~15 도 센 프레임 + 2 에 처음 나와(417 → 419 등) 두 프레임 차이는 같았습니다. 블록 15(`land1`)는 `00:FC60` 이 한 번 그리지만 OAM 에는 한 번도 나오지 않았습니다. 755 에 세고 757 은 이미 블록 6 이었습니다. `01:BFB1` 이 프레임을 6 으로 내리고 그린 뒤, 같은 프레임 안에 `01:BFC1`~`BFCD` 가 `31E7` = `40`·프레임 0 으로 되돌려 다시 그린 것으로 보입니다(추측, 코드 읽기·덤프). 天空城 은 처음 그린 프레임 + 2(388)가 페이드 안이라 화면 픽셀이 0/645 였습니다.

그래서 블록마다 처음·마지막으로 센 셀 프레임 + 2 를 덤프하고, 슬롯 7 의 칸 목록이 칸 표와 같은지와 그 블록의 칸이 OAM·화면에 그대로 있는지 보게 했습니다. 화면에 나와야 하는 블록은 `land0` 과 `tenkuu0`~`3` 입니다. 결과입니다.

- 걷기: 세 롬 모두 그린 블록이 방향 4 × 프레임 수였고 `32A0` 은 `82`·`83`·`82` 였습니다. 덤프 20개마다 두 부분의 슬롯 칸 목록이 칸 표(그림자는 옮긴 상하 반전 표까지)와 같았고, 부분 1 은 OAM 블록의 픽셀이 다음 프레임 화면과 모두 같았습니다. 새 프레임 3 도 네 방향 모두 OAM 에 나왔습니다.
- 장면: 슬롯 7 이 4프레임 롬은 `37C0` = `80`·`32A0` = `85`(착륙·이륙)와 `C0`·`83`(天空城), 5x5 롬은 `96`·`88` 과 `C8`·`83` 이었고, 그린 블록이 도구가 둔 자리와 같았습니다. `land0` 과 天空城 네 블록은 OAM·화면에 칸 표 그대로 나왔고, `land1` 은 원본처럼 나오지 않았습니다.
- 고친 롬의 착륙·이륙은 원본보다 한 프레임 늦었습니다(749 → 750, 987 → 988). 天空城 은 같은 프레임이었습니다.

## 5. 재지 않은 부르는 곳

`01:BB7C` 를 부르는 `03:8F1F`·`12:8BE9` 와 `01:BEA9` 를 부르는 `11:8E18` 은 이번에도 재지 못했습니다. 셋 다 고친 루틴을 그대로 부르므로 같은 즉값을 씁니다(코드 읽기). `12:8BE9` 는 `01:8AA4` 가 맵을 불러오는 차례에 부르는 `12:8B82` 안에 있고, `$BE` bit7 이고 `$1A0C` 가 `05` 일 때 갑니다. `$1A0C` = `05` 는 `01:BB7C` 가 스스로 두는 값이라, 天空城 장면 뒤에 맵을 다시 불러오면 같은 장면을 다시 세우는 것으로 보입니다. 06/00 에서 메뉴를 열고 닫는 입력으로 실행 기록을 걸었으나 `01:BB7C` 는 맵 루틴에서 한 번만 불렸고 `12:8BBC` 에는 닿지 않았습니다.

## 틀렸던 것들

- 장면 블록이 「방향 3」 에서 그려진다고 보았습니다. 방향과 상관없이 `31E7` = `20` 이 `00:EE7C[2]` = 3 을 고릅니다.
- 처음 그린 프레임 뒤 세 프레임에서 OAM 을 보면 된다고 보았습니다. OAM 에는 두 프레임 늦게 나오고, 天空城 의 첫 프레임은 페이드 안이었으며, 착륙 둘째 블록은 OAM 에 나오지 않았습니다.
- OAM 에서 찾은 블록을 열쇠 이름으로 견주었습니다. 원본 칸을 그대로 둔 롬에서는 `land1` 과 `tenkuu3` 의 칸이 같아 天空城 프레임 3 이 `land1` 로 잡혔습니다. 블록 번호의 칸으로 찾게 고쳤습니다.

## 남은 것

- `03:8F1F`·`12:8BE9`(`$1A0C` = `05`)·`11:8E18` 장면의 실측(위 5절).
- 착륙 둘째 블록(`land1`)이 OAM 에 나오지 않는 까닭. 같은 프레임 안에서 다시 그려지는 것은 코드 읽기와 덤프로 본 추측이고, 그 프레임의 OAM 버퍼 쓰기는 재지 않았습니다.
- 고친 롬의 착륙·이륙이 한 프레임 늦은 까닭.
- 슬롯 칸 목록(`7E:8060`~)과 OAM 의 한도. 이번에는 マスタードラゴン 부분 1 을 288칸에서 352칸(4프레임)·450칸(5x5)으로 늘린 것까지만 확인했습니다.
- 4프레임 5x5 처럼 天空城 간격이 한 바이트를 넘는 배치는 거부합니다. 넘기려면 `01:BB7C` 가 `37E7` 도 두게 루틴을 고쳐야 합니다.
