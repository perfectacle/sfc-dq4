# 2026-10-25-195: 옮긴 레코드 자리의 접근 카운터, BG3 타일맵을 쓰는 곳 전부

[2026-10-25-173](2026-10-25-173-hangul6.md)에서 두 가지가 남았습니다. 하나는 긴 명령 창 레코드를 옮긴 `7E:1ABC`~`1BB1` 이 간접·직접 페이지 접근까지 비어 있는지, 다른 하나는 BG3 타일맵을 `1C00` 에 쓰는 나머지 곳입니다. 둘 다 근거만 모으고 어느 길로 갈지는 정하지 않았습니다. 결과는 [dq5-hangul-format.md 「옮긴 레코드 자리」·「VRAM 배치와 BG3 칸을 넓히는 길」](../docs/dq5-hangul-format.md#vram-배치와-bg3-칸을-넓히는-길)에 있습니다.

## 1. 커버리지 대신 접근 카운터

실행 콜백으로 PC 를 모으는 `COVER` 는 300프레임만 넘어도 테스트 러너의 시간 제한(약 100초)에 걸렸습니다. MesenCE 에는 메모리 바이트마다 읽기·쓰기·실행 횟수를 세어 두는 접근 카운터가 있고, Lua 의 `emu.getAccessCounters(memType, counterType)` 로 한 번에 꺼낼 수 있습니다. 콜백이 없어서 12,000프레임 필드 실행도 몇 초면 끝납니다. `dq5msg.lua` 에 `ACCESS="1ABC-1BB1"` 을 더해 마지막 프레임에 WRAM 범위의 읽기·쓰기 횟수와 롬의 실행된 바이트를 적게 했습니다.

처음 돌린 결과는 한 바이트씩 밀려 있었습니다. 카운터 배열이 Lua 관례와 달리 0부터 시작하는데 `+1` 을 붙였기 때문입니다. 전원 켤 때 `00:864A STZ $00,X` 고리의 실행 횟수 8,192가 `00:8649` 에 찍힌 것을 보고 알았습니다.

장면 아홉(새 게임 오프닝 10,700프레임, 이어하기, 선실 무기점·교회·`36EB=06`, 무작위 전투, 필드 걷기와 명령 창, 사건 대화, 동료가 있는 일행)에서 `1ABC`~`1BB1` 에 쓴 것은 전원 켤 때의 0 채우기 한 번뿐이었습니다. 읽기는 0 채우기를 나머지 WRAM 으로 퍼뜨리는 `MVN`, 그리고 억지로 무기점으로 바꾼 실행 하나의 `06:F534` 였습니다. 이 고리는 `LDA ($00),Y` 로 상점 표를 훑습니다. `SET 36EB=01` 로 만든 상점 번호가 표에 없어 Y 가 뱅크 04 끝을 넘었고, `05:1ABC`(낮은 WRAM 거울)까지 12만 번 읽었습니다. 쓰지는 않습니다.

## 2. 실행된 바이트에서 연산자 찾기

같은 아홉 실행의 실행된 롬 바이트 84,848개에서 2바이트 연산자가 범위 안인 자리를 뽑으니 32곳이었습니다. 실행 카운터는 연산자 바이트도 세므로, 명령의 시작인지는 따로 봐야 합니다. `COVER` 가 쉼표로 여러 범위를 받게 고치고 32곳의 앞뒤 16바이트만 걸어 아홉 장면을 다시 돌렸습니다. 범위가 좁으면 콜백이 드물어 긴 실행도 됩니다. 32곳 모두 다른 명령의 중간이었습니다(`22:AD00 LDA $0D1E` 뒤의 `0D F0 1A` 처럼).

뱅크 00 의 네 곳은 처음에 앞뒤가 비어 보였는데, 판정 스크립트가 16진 문자열 비교를 잘못한 탓이었습니다. 리스팅을 직접 보니 그 넷도 중간 바이트였습니다. 직접 페이지는 장면 여섯의 짧은 전 범위 커버리지에서 D 값을 모았습니다(`dregs.txt`). 나온 값은 `0000` 뿐이었고, 실행된 `TCD` 는 모두 `LDA #$0000` 바로 뒤였습니다.

## 3. VMADD 를 쓰는 곳

처음 `WW=002116` 으로 선실에서 감시했을 때는 아무것도 잡히지 않았습니다. 선실 세이브스테이트는 창이 이미 떠 있는 상태라, 입력을 넣어도 새 창을 그리지 않았던 것입니다. 필드에서 A 로 명령 창을 열자 `00:8E1F` 가 잡혔습니다. 앞선 시도에서 빠진 곳이 이것이었습니다. `00:8E13 LDA #$1C00` 바로 뒤에 `BRK 0B 20 2F`(플래그 `21BF.5` 시험)가 있고, 켜져 있으면 `LDA #$4C00` 으로 갑니다.

`dq5msg.lua` 에 `VMADD=1` 을 더해 VMADD 쓰기(PC·값)와 MDMAEN 때 켠 채널의 B 버스·원본·길이를 모으게 하고 아홉 장면을 돌렸습니다. `1C00`~`1FFF` 를 가리킨 곳은 여섯입니다.

- 즉값: `00:8E13`·`8E52`·`8E72`, 전투의 `22:8B4D`·`8B6F`·`8BC6`(`$0F5E` 를 거쳐 `00:FDA1`), 전원 켤 때 지우기 `00:A436`
- 변수: 전송 목록 레코드 주소를 넣는 `00:B44F`(`$27`)와 `02:FEF7`(`$1F18`). 타이틀·이어하기에서만 봤습니다.

## 4. 3C00 으로 바꿔 보기

즉값 일곱 곳(앞의 여섯과 `$0725` 를 두는 `2B:82BD`)을 바꾸는 `dq5hangul.py bg3move` 를 만들었습니다. 그런데 이 롬에 `$0725` 만 고정하자 타일맵은 `3C00` 에 써졌는데도 창이 화면에서 사라졌습니다. NMI 의 `00:8A43` 은 매 프레임 PPU 레지스터를 다시 쓰지 않아서, 세이브스테이트의 BG3SC 가 `1C` 로 남아 있었습니다. `POKE` 로 `$2109` 에도 `3C` 를 쓰자 창이 돌아왔습니다.

필드 명령 창에서는 VRAM `3C00`~`3FFF` 1,024워드가 원래 롬의 `1C00`~`1FFF` 와 같았고, 그 밖의 VRAM 은 한 워드도 다르지 않았습니다. 전투에서도 VMADD 가 `3C00`·`3CE0`·`3EA0` 으로 옮겨졌고, 세 프레임 화면이 원래 롬과 같았습니다. 다만 `3C00`~`3FFF` 는 BG1·BG2 글자 칸 `1C0`~`1FF` 자리라, 선실·필드의 VRAM 에서는 그림이 있는 칸이었습니다. 이 두 장면 화면에서 깨진 곳은 보이지 않았습니다.

`21BF.5` 를 켜고 필드에서 명령 창을 열어 보았습니다. 창 타일맵이 `4C00` 으로 갔고 BG3SC 는 그대로라 창이 보이지 않았습니다. `4C00`(글자 칸 `2C0`~`2FF`)은 선실·필드 모두 0 인 칸이었습니다.

## 5. 맵마다 남는 글자 칸

`dq5hangul.py slots` 가 dq5map 의 슬롯 할당대로 실내 맵 364개의 슬롯 끝을 셉니다. 슬롯 끝은 `BF`~`235` 였고, 슬롯이 `1C0` 을 넘는 맵이 아홉입니다. 선실은 맵 슬롯 끝 `179` 뒤에도 `1BF` 까지 그림이 있는 칸이 있었는데, 앞 맵에서 남은 것인지는 아직 모릅니다.
