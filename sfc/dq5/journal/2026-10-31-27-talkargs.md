# 2026-10-31-27: 대화 명령 01·12 를 받는 규칙, 01/04 에서 00:BCC3 으로 걷기

[앞 일지](2026-10-31-24-worldrest.md)가 남긴 둘을 풀었습니다. 하나는 대화 스크립트의 명령 `01`·`12` 를 쓰기 도구가 받을 수 있는 인자 규칙입니다. 다른 하나는 01/04 를 셀 읽기 루틴 `00:BCC3` 으로 읽을 때 걷기가 어떻게 바뀌는지입니다. `01` 은 `call` 의 `args`, `12` 는 새 명령 `service` 로 받게 했습니다. 결과는 [쓰기 형식의 대화 스크립트](../docs/dq5-build-format.md#대화-스크립트-dq5talk1)·[맵별 루틴 표](../docs/dq5-build-format.md#맵별-루틴-표-dq5maphook1)와 [텍스트 형식의 대화 스크립트](../docs/dq5-text-format.md#대화-스크립트-06aef8)에 넣었습니다.

## 1. 두 건너뛰기가 01·12 를 세는 법

스크립트를 건너뛰는 코드는 둘입니다.

```
06:B23F  갈리지 않은 분기: 17·18·19·00 = 3, 12 = 2, 0B·07 = 1, 01 = 5, bit6 = 2
06:AFA9  스크립트 찾기:   17~1C·00 = 3, bit6 = 2, 3F = 끝, 나머지(01·12 포함) = 1
```

`06:B23F` 는 두 명령의 길이를 바르게 압니다. 그래서 갈리지 않은 블록 안에 두어도 어긋나지 않습니다. `06:AFA9` 는 `01`·`12` 를 1바이트로 세고, 그 뒤 인자 바이트를 명령처럼 따로 셉니다. 그런데 스크립트 찾기는 앞 스크립트의 끝 `3F` 다음을 찾을 뿐입니다. 그래서 도중에 어긋나도 끝에서 바로 `3F` 를 만나면 됩니다. 쓰기 도구는 이미 스크립트마다 이 규칙으로 끝을 다시 세어(`skip_length`) 맞지 않으면 거부합니다. 이 검사가 그대로 `01`·`12` 의 규칙입니다.

```
01 A0 B3 5A A5 61 29 3F   01·A0·B3 = 1, 5A(bit6) = 2(5A A5), 61 = 2, 3F   → 받음
12 00 61 29 3F            12 = 1, 00 = 3(00 61 29), 3F                    → 받음
12 00 3F                  00 = 3 이 3F 를 삼킴                              → 거부
01 A0 B3 3F 00 …          3F 를 끝으로 읽음                                 → 거부
```

`service` 의 인자는 `06:DBD2` 가 뛰는 `06:DBDB` 표(17칸, 대화 번호 `000`~`010` 의 처리기) 번호라 `00`~`10` 만 받습니다.

## 2. 게임에서 보기

`dq5talkcheck.py` 에 도구로 쓴 롬 둘을 더했습니다.

```
args     012: if 7E:2191&01 then [call B3A0 args 11 22, service 01, msg 16B] else [msg 129, call B3A0 args 5A A5, msg 742]
  012    129 1CC 742   묶음 FE10   7E:0F30·0F31 = 5A A5
  013    743 (원본 743)   015    747 (원본 747)
service  012: service 01
  012    002 006 013
```

선실에서는 조건이 거짓이라 `01`·`12` 가 든 then 블록을 `06:B23F` 가 건너뛰고, else 블록의 `01` 이 인자를 둔 채 돌았습니다. 같은 묶음의 `013`·`015` 가 원본과 같은 메시지였습니다. 그래서 `06:AFA9` 도 012 를 바르게 건너뛰었습니다. 앞 일지의 바이트로 덮은 장면까지 26장면이 통과했습니다(아래 `9C` 둘을 더해 28).

같은 검사의 사례에 「모르는 명령 갈래(`06:B10F`)를 지나는가」 기대를 필드로 두었습니다. 지금은 `c16-skip` 하나만 지납니다. bit7 로 뒤집은 `1C`(`9C`)도 바이트로 덮어 봤습니다. `07 9C 01 00 …` 은 `7E:2191` = 0 에서 `16B`(뒤집혀 참)였습니다. 갈리지 않은 블록 안에 둔 `9C` 도 `129` 로 바르게 건너뛰었습니다. 길이 표 `06:B27E` 는 조건 바이트를 `& 3F` 해서 찾습니다(28장면 통과).

## 3. 01/04 를 00:BCC3 으로 읽으며 걷기

`dq5maphookcheck.py` 의 `cells` 롬(01/04 → `00:BCC3`)과 원본에서 01/04 (32,5) 부터 네 방향으로 따로 걸었습니다. 처음 64프레임으로 걷자 왼쪽만 원본 (25,5)·`cells` (26,5) 로 갈렸습니다. 프레임마다 칸을 적었습니다.

```
원본    548 31,5  556 30,5  564 29,5 … 596 25,5
cells   550 31,5  558 30,5  566 29,5 … 590 26,5
```

첫 칸이 2프레임 늦었을 뿐, 그 뒤는 둘 다 8프레임마다 한 칸이었습니다. 160프레임으로 늘리자 네 방향 모두 같았습니다. 왼쪽은 01/06 (75,67) 로 나갔고, 아래 (32,7)·오른쪽 (36,5)·위 (32,4) 에서 멈췄습니다. 그래서 `walk-*` 여덟 장면은 160프레임으로 둡니다. 앞 일지의 장면까지 36장면이 통과했습니다. 앞 일지의 `hall-select` 는 맵을 푼 뒤 루틴도 `02:94C1` 로 기대하게 했습니다(문서·일지에 적은 값). `00:BCC3` 은 `JSL 21:8000`(낮밤)과 `7E:2190` bit2·`7E:21A6` bit5·`7E:2192` bit7, 주인공 좌표로 갈래를 고릅니다(코드 읽기). 이 실측은 선실 상태(낮, 세 비트 꺼짐)의 갈래뿐입니다.

## 틀렸던 것들

- 64프레임 걷기에서 왼쪽 끝 칸이 갈려 `00:BCC3` 이 통행을 바꾼다고 봤습니다. 프레임마다 보니 첫 칸이 2프레임 늦은 것이었습니다.

## 남은 것

- `00:BCC3` 의 밤 갈래와 세 플래그가 켜진 갈래에서 01/04 를 걸을 때.
- 첫 칸이 2프레임 늦는 까닭.
- `service` 는 처리기 `00`~`10` 을 모두 받지만 게임에서 본 것은 `01`(무기점)뿐입니다. 말 거는 인물 문맥이 필요한 여관·교회 등 나머지 처리기는 재지 않았습니다.
