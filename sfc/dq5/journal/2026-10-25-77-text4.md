# 2026-10-25-77: 창 제목, 전투 글자, 인물 그림 어긋남, 늘린 롬의 SRAM

[2026-10-25-66](2026-10-25-66-hangul.md) 까지 남긴 것 가운데 창 머리 `+4`·`+5`, 전투 메시지 글자를 그리는 곳, 인물 표 `7E:3000`·`3180` 의 단위, 늘린 롬의 SRAM 을 풀었습니다.
결과는 [dq5-text-format.md](../docs/dq5-text-format.md) 의 「창 레코드 머리」·「몸짓 코드」 와 [dq5-hangul-format.md](../docs/dq5-hangul-format.md) 의 「롬 확장」·「1바이트 부호」 에 있습니다.

## 1. 머리 +4 가 0 이 아닌 창

명령 창 → さくせん 을 고르면(일행 혼자) 「さくせん」 제목 아래 「ならびかえをする」 한 줄인 창이 뜹니다. 창 레코드를 훑어 이 문자열이 든 창 `5A`(`06 08 0B 65 03 05 01 FE …`)를 찾고 `+4`~`+6` 을 바꿔 열었습니다.

```sh
PRE="b:4,wait:40,down:3,wait:20,a:4,wait:40,right:4,wait:15,down:4,wait:15,down:4,wait:15,a:4,wait:60"
STATE=$PWD/work/state/ship.mss PRE=$PRE MAXF=200 ROMPATCH="273FC=04" \
  SHOT_DIR=$PWD/work/win5a/5-04 "$MESENCE" --testrunner "$PWD/rom/dq5.sfc" "$PWD/sfc/dq5/tools/lua/dq5msg.lua"
```

`+5` 를 `04`·`01`·`06` 으로 하자 제목이 「どこへ」·「どうぐ」·「さくせんをねる」 로 바뀌었고, `+6` 을 `02` 로 하면 줄이 하나 더(엉뚱한 줄), `00` 이면 창이 열리지 않았습니다. `+4` 는 `01`·`02`·`04` 로 바꿔도 같았습니다.
제목 문자열을 롬에서 찾으니 `04:AD78` 부터 `FF` 로 나뉜 목록이었고, `04:ACC8` 이 번호만큼 `FF` 를 건너뜁니다. 탁점 접두는 창 항목과 달리 `92`·`93` 이었습니다.

```
00 コマンド  01 どうぐ  02 どうする  03 だれに  04 どこへ？  05 さくせん  06 さくせんをねる  07 そうび …
```

명령 창에서 `+4` 아래 비트를 켜면 깨지던 것은, 제목이 있는 창으로 보고 머리를 한 바이트 더 읽기 때문입니다. `dq5text.py --window` 가 머리(X·Y·너비·높이·줄 수·제목)를 풀어 찍게 했습니다.

## 2. 전투 메시지 글자

슬라임·ドラキー 전투 세이브스테이트에서 A 를 누르며 `dq5vramlog.lua` 로 VRAM 쓰기를 기록했습니다.

```
136  pc 00:8E90 ch0 B=18 src 7E5000 size 0800 vram 1C00
 11  pc 00:8E90 ch0 B=18 src 7E5540 size 0240 vram 1EA0
 11  pc 00:8E70 ch0 B=18 src 7E5000 size 01C0 vram 1C00
```

메시지가 뜨는 동안 VRAM 으로 가는 것은 BG3 타일맵(`7E:5000` → 워드 `1C00`)뿐이었습니다. 버퍼 `7E:5000`~`57FF` 쓰기를 155프레임부터 기록하자(`dq5msg.lua` 에 `WWFROM` 을 더함) `24:A5F0` 이 8,268번 썼고, 그 루틴 `24:A5D9` 는 `7E:1DD5` 의 26바이트 줄을 `7E:5546` 에 바이트 그대로 옮깁니다.
전투 글자도 창과 같이 바이트가 BG3 타일 번호입니다.

창·전투 글자 타일 `01`~`8A` 는 전원을 켤 때 `04:E17D` 가 `04:E528` 의 1bpp 138자를 올린 것입니다([dq5-graphics-format.md](../docs/dq5-graphics-format.md#창메뉴-타일-04e17d)). 타일 `29`(は) 자리 8바이트(파일 오프셋 `26668`)를 상자 모양으로 바꾸고 전원을 켜자 이름 입력 창의 「は」 가 상자로 나왔습니다.

## 3. 인물 그림 어긋남의 단위

파파스 슬롯의 `7E:300B` 와 `7E:318B` 를 값마다 고정하고 30프레임째 OAM 을 덤프해 원래와 견줬습니다.

```
300B=08,10: 그대로   20: X+1   40: X+2   80: X+4
318B=FC: Y+4
```

`7E:3000` 은 위 3비트가 가로 점 수이고, `7E:3180` 은 뺄수록 아래로 갑니다. `1112` 의 떨림은 1점 오른쪽으로 갔다 돌아오는 것, `1114`(`FF`)는 1점 아래, `1118`(`01`)은 1점 위입니다.

## 4. 늘린 롬의 SRAM

원래 롬이 쓰는 SRAM(모험의 서가 든 것)을 4MB 롬과 `retree` 롬 이름으로 복사해 두고 전원을 켰습니다. 1,400·3,000프레임 화면(모험의 서를 불러 성 안)이 원래 롬과 같아 불러오기가 됩니다. 이 실행에서는 게임이 SRAM 을 쓰지 않아 파일이 그대로였고, 교회 저장은 남겼습니다.

## 틀렸던 것들

- `+4` 아래 비트가 머리 길이 자체라고 보았다: 값이 `01`~`04` 어느 것이든 같고, 0 이냐 아니냐로 제목 바이트가 끼는지가 갈린다.
- 전투 메시지도 보행 모드 폰트로 그린다고 보았다: 바이트를 타일 번호로 바로 쓴다.
- `1114` 의 `FF` 를 「1점 위」 로 짐작했다: OAM 으로 재 보니 `3180` 은 뺄수록 아래다.

## 남은 것

- `+4` 아래 4비트 값의 뜻, `+6` bit7 인 창의 머리
- BG3 타일 `96` 이후(보행 모드 글자 칸)를 창·전투 글자에 나눠 쓸 수 있는지
- 늘린 롬에서 교회 저장
