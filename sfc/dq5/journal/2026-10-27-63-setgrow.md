# 2026-10-27-63: 8타일 새 세트와 세트 표 늘리기

새 인물 그림을 6타일 세트로는 `70`~`7F` 에 더할 수 있었지만, 8타일 세트는 더할 번호가 없었습니다. 세트 번호 bit7 이 8타일 배치를 고르는데 `80`~`A4` 가 모두 차 있었기 때문입니다. 세트 포인터 표를 256칸으로 늘려 옮기는 `dq5spritewrite.py --sets-at` 을 만들어 `A5`~`FF` 를 열었습니다. 형식은 [쓰기 형식](../docs/dq5-build-format.md#인물-세트-표-늘리기-dq5spritewritepy---sets-at)에 있습니다.

## 1. 표를 읽는 곳

세트 포인터 표 `1F:D63D` 는 2바이트 포인터 `A5`칸이고, 바로 뒤 `1F:D787` 부터 레코드가 이어집니다. 그래서 칸을 늘리려면 표를 옮겨야 합니다. 롬에서 `3D D6 1F` 바이트열을 찾으니 `1F:CFB6`·`1F:D0E9`·`03:D20B` 의 `LDA $1FD63D,X` 셋뿐이었습니다. 셋 모두 바로 뒤에서 `LDA #$1F` / `STA` 로 레코드 포인터의 뱅크를 정합니다. 표는 24비트로 읽으니 어디에 두어도 되지만, 레코드 포인터는 16비트라 레코드는 한 뱅크에 모아야 합니다. 그래서 표 512바이트 뒤에 원래 레코드 149개와 새 레코드를 모두 옮기고, 피연산자 여섯 곳(주소 셋, 뱅크 셋)을 고칩니다.

세트 번호는 두 곳에서 `AND #$00FF`, 한 곳에서 앞의 `TDC` 로 8비트가 되니 `00`~`FF` 를 다 쓸 수 있습니다.

## 2. 세트 캐시

세트를 VRAM 에 올린 뒤 `1F:CF9E` 가 `7E:AC00 + 세트 × 2` 에 칸 목록 번호를 적어 둡니다. 원래 표 크기만큼(`AC00`~`AD49`)만 잡혀 있다면 `A5` 이상 세트가 그 뒤 WRAM 을 덮게 됩니다. `dq5freesweep.py` 에 범위와 접근을 고르는 `--ranges`·`--access` 를 더해 `7E:AD4A`~`ADFF` 의 읽기·쓰기를 필드 세 장면에서 감시했습니다. 잡힌 것은 첫 PC `00:E995` 하나였습니다. 맵을 불러올 때 `7E:AC00`~`AFFF` 를 지우는 루프(`00:E98F`)이고, 256세트 몫이 원래부터 비어 있었습니다.

## 3. 옛 표를 읽는 다른 곳

코드에서 찾지 못한 읽기가 있으면 옮긴 롬에서 옛 표나 옛 레코드가 읽힐 것입니다. 옮긴 롬으로 실내 맵 346곳과 필드 세 장면을 돌며 `1F:D63D`~`F5CA` 읽기를 감시했습니다.

```
옮긴 롬, 옛 표·레코드: maps 346개·field 3개, 읽힌 것 0줄
원래 롬, 같은 범위: field world0~2 n=770 first pc=1FD0ED
옮긴 롬, 새 표·레코드 3B:8000~A0AB: field world0~2 n=770 first pc=1FD0ED
```

원래 롬에서 같은 감시가 읽기를 잡고, 옮긴 롬에서는 같은 횟수가 새 자리로 옮겨 갔습니다.

## 4. 게임에서 새 8타일 세트

`dq5spritewritecheck.py` 에 표를 옮긴 롬(grown)을 더했습니다. 02/06 의 인물 그림 `29` 를 세트 `84` 대신 새 세트 `FF`(세트 `91` 의 그림, 팔레트 2)로 잇고, 6타일 세트 `04` 와 새 세트 `70` 은 다른 시험과 같게 두었습니다.

```
grown: 덤프 4개, 세트 04 164/164 70 128/128 82 136/136 FF 108/108, OAM 묶음 16/16(레코드와 다른 팔레트 0), 프레임 04 down0 70 right1 82 down0 FF down0
```

세트 `FF` 인물이 VRAM 타일과 8타일 배치의 OAM 픽셀까지 디코더와 같았고, 레코드의 팔레트 2 로 그려졌습니다.

## 5. 이미 옮긴 롬을 다시 고치기

리뷰에서 구멍이 나왔습니다. 표를 옮긴 롬에 `--sets-at` 없이 새 세트 `70`~`7F` 를 더하면, 도구는 옛 표 `1F:D63D` 와 `1F:FE30` 에 썼습니다. 엔진은 옮긴 표를 읽으니 그 세트의 포인터는 `FFFF` 그대로입니다. 그래서 옮긴 롬에서 새 세트를 더할 때 `--sets-at` 이 없으면 거부하고, `--sets-at` 을 주면 표와 레코드를 다시 놓게 했습니다. 기존 세트를 고치는 쓰기는 옮긴 레코드 자리에 떨어집니다. 함께 고친 곳은 셋입니다.

- `dq5objpalette.py`·`dq5picturegrow.py` 도 옮긴 표를 읽게 했습니다.
- 세트를 도는 루프가 `range(SET_COUNT)` 라 `A5` 이상을 건너뛰었습니다. 이 루프는 `set_numbers` 로 바꿨습니다.
- 같은 빌드에서 `dq5objpalette.py` 의 세트 팔레트가 죽은 옛 레코드에 써지는 일도 이제 문서만으로 막지 않습니다. 세트 팔레트를 쓰면 표 주소 피연산자 `1F:CFB7` 을 같은 값으로 다시 써 두므로, `--sets-at` 패치와 함께 빌드하면 `dq5build.py` 가 `겹침 1F:CFB7~1F:CFB9` 로 멈춥니다.

`dq5spritewritecheck.py` 에 grown 롬을 다시 고친 regrown 롬을 더했습니다. 먼저 grown 롬에 `--sets-at` 없이 새 세트 `71` 을 더해 거부되는지 봅니다. 그다음 `--sets-at 3C:8000` 으로 표를 다시 옮기며 그림 `2B` 를 `71` 에 잇습니다.

```
regrown: 덤프 4개, 세트 04 164/164 71 128/128 82 136/136 FF 108/108, OAM 묶음 16/16(레코드와 다른 팔레트 0), 프레임 04 down0 71 right1 82 down0 FF down0
검사 7개 통과
```

다시 옮긴 표에서 새 세트 `71` 과 앞서 더한 `FF` 가 모두 디코더와 같았습니다.

두 번째 리뷰에서 구멍이 하나 더 나왔습니다. 표를 옮긴 롬을 다시 고칠 때 `--sets-at` 을 앞서 `--at` 으로 쓴 자리(`3A:8000`)에 주어도 도구가 받았습니다. 그러면 세트 `A5` 의 타일 자료가 표에 덮여, 디코더가 자료 끝을 찾지 못했습니다. 이제 `--sets-at` 의 표·레코드와 `--at` 에 옮기는 타일 자료가 지금 엔진이 읽는 세트 자료와 겹치면 거부합니다. 세트 자료는 표, 모든 레코드, 모든 세트의 압축 타일 자료입니다. `dq5picturegrow.py --new-sets` 의 `A5`~`FF` 는 표를 옮긴 롬이거나 `--sets-grown` 으로 밝혔을 때만 받습니다.

## 남은 것

- 세트마다 고유한 팔레트. 레코드의 팔레트 칸이 2비트라 OBJ 팔레트 0~3 만 고릅니다. 필드에서 팔레트 4~7 을 무엇이 쓰는지 재고, 세트마다 CGRAM 에 색을 올리는 코드를 따로 만들어야 합니다.
- `sfc/dq4/tools/dq4romassets.py` 도 세트를 `range` 로 돌아 `A5` 이상을 건너뜁니다. dq4 트랙 파일이라 [todo](../../../docs/todo.md#dq4)에 요청만 남겼습니다.
- `A5` 이상 세트를 여러 맵에 두었을 때의 OBJ VRAM 여유.
