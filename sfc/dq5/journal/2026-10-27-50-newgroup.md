# 2026-10-27-50: 새 그룹 번호와 맵 표 덩어리 옮기기

[지난 일지](2026-10-27-39-newmap.md)에서는 기존 그룹 끝에 맵을 더했습니다. 그때 남은 셋을 풀었습니다. 새 그룹 번호, 그룹 `$50` 이상의 새 맵, 그리고 같은 뱅크에서 늘릴 수 있는 한도(맵 포인터 36개, 맵 속성 18개)를 넘는 증설입니다. 먼저 맵 번호를 읽는 코드 조사를 전투·메뉴·대화로 넓혔습니다. 결과는 [쓰기 형식의 새 맵 번호](../docs/dq5-build-format.md#새-맵-번호-dq5newmap1)에 있습니다.

## 1. 전투·메뉴·대화에서는 맵 번호를 거의 읽지 않음

지난번 조사는 맵에 들어가 걷는 세 장면뿐이었습니다. 기존 도구들의 장면 입력을 빌려 열 장면으로 넓혔습니다. 실내 조우, 파파스와의 대화, 필드 주문 메뉴, 필드 전투를 걸어 끝까지 싸우기, 전투 주문, 그룹 `$50` 이상 맵을 더했습니다. `lua/dq5mapidscan.lua` 가 장면 드라이버를 감싸 `$BC`·`$BD` 를 읽은 PC 를 모으고, `dq5mapidscan.py` 가 읽은 값을 쓰는 다음 명령으로 나눕니다.

```
장면 10개, PC 112곳: 색인 7, 견줌 91, 살핌 14
```

새로 넣은 장면에서 나온 PC 는 거의 없었습니다. 대화 중에는 `00:D8F0` 의 `CMP #$51` 이 매 프레임 읽고, 전투와 주문 메뉴는 맵 번호를 읽지 않았습니다. 「살핌」 14곳은 들어가는 곳 표(`$BC`×5), 고층 포인터, 그룹 번호를 목록에서 찾는 루틴(`25:8046`, `06:D3ED` 의 `25:85D5` 목록, `BRK 8A`), 문 표, 맵 번호를 남기는 곳이었습니다. `2B:C293` 은 소리 코드가 직접 페이지 `$BC` 를 제 변수로 읽는 자리였습니다.

그룹 번호를 범위로 견주는 곳은 모두 `CMP #$50` 이었습니다. 그래서 `36`~`4F` 는 보통 실내 맵으로 다뤄집니다.

## 2. 새 그룹에 필요한 표

새 그룹은 그룹 번호로 곧장 색인하는 표마다 항목이 하나씩 더 필요합니다.

| 표 | 원본에 없는 그룹이면 |
| --- | --- |
| 맵 포인터·맵 속성 그룹 표 | 표 뒤 바이트를 포인터로 읽음 |
| 들어가는 곳 `0F:EA97`(그룹마다 5바이트) | 표 밖을 읽음 |
| 인물 그룹 포인터 `05:D4B2` | `05:D51E` 의 코드 바이트 `20 42` 를 읽어 `05:4220`(MMIO 영역)을 목록으로 봄 |
| 출구 표 | 그룹 머리를 찾지 못해 출구 없음 |

맵 포인터·속성은 지난번처럼 그룹 표를 옮기면서 항목을 하나 더 붙입니다. 옮긴 표의 끝을 알아야 하므로, 끝 표시 뒤에 `0000` 을 하나 더 두는 꼴로 바꿨습니다. 그룹 수는 `0000` 앞까지 세고, 목록 시작 주소는 늘 `8000` 이상이라 헷갈리지 않습니다.

들어가는 곳 표는 `LDA $0FEA97,X` 꼴의 긴 주소로 읽습니다(`2A:F393` 등 여덟 곳, `+0`~`+4`). 그래서 피연산자만 바꾸면 어느 뱅크로든 옮기고 늘릴 수 있습니다. 출구 쪽은 `dq5exitreloc.py` 의 그룹 수 54 고정을 맵 목록에서 세게 바꾸어, 새 그룹이면 출구 표에 그룹 덩어리를 더합니다.

인물 그룹 포인터는 인물 도구 담당에게 요청했고, 그사이 `dq5npcrelocate.py --new-map` 이 새 그룹도 받게 되었습니다. 그 도구 없이 빌드한 첫 실측에서도 36/00 에 인물은 놓이지 않았지만(`$1983` = `08`) MMIO 영역을 읽은 결과라 믿을 수 없습니다. 실측 롬 `g` 는 인물 도구로 그룹 36 의 포인터와 빈 목록을 두고 빌드해, 같은 슬롯 `08` 을 기대값으로 확인합니다.

## 3. 그룹 `$50` 이상

고층 맵 포인터(`1F:CEB6`, `01:934E`)는 보통 맵과 같은 꼴입니다. 같은 방법으로 늘리되, 옛 표 자리가 10바이트뿐이라 같은 뱅크에서는 세 개까지입니다. 고층 속성은 꼴이 다릅니다. `23:FDD6` 의 `[BC][목록]` 을 찾고, 목록에서 `[BD]`+6바이트를 찾습니다. 처음에는 맵을 더한 그룹의 목록만 뱅크 23 빈 자리로 옮겼는데, 같은 목록을 조우 도구(`dq5encounterwrite.py --high-at`)가 이미 통째로 옮겨 쓰고 있었습니다. 두 도구가 같은 자료를 쓰면 빌드에서 겹치고, 한쪽이 옮긴 목록을 다른 쪽이 읽지 못합니다. 그래서 고층 새 맵의 속성은 조우 도구에 맡기고, 이 도구는 포인터만 씁니다. 조우 도구 문서에 따르면 목록에 없는 고층 맵은 스택이 어긋나 엉뚱한 곳으로 돌아가므로, 새 고층 맵은 반드시 함께 넣어야 합니다.

영역 이동은 코드(`01:94B4`)가 고릅니다. 50·52 는 그룹 전체가 한 목록, 53 은 53/51 과 나머지입니다. 51·54 는 `$BD` 마다 견줍니다. 맞는 것이 없으면 54 는 `01:962A` 로 빠져 `$183D` 를 그대로 두고, 51 은 `01:95C6` 에서 `01:94C9` 로 가서 A(`$BD`)를 레코드 뱅크 `$183C` 에 넣고 개수 `$183D` 는 그대로 둡니다. 둘 다 앞 맵의 영역 이동 개수가 남으므로 새 맵은 50·52·53 에만 받습니다(코드 읽기). 그룹 `$50` 이상은 인물 기본 목록을 읽지 않고(`12:801C`), 출구 표에도 없습니다.

## 4. 문 표

독립 리뷰가 문 표를 짚었습니다. 지난 일지에서는 문 표(`01:D2FC`)를 찾기 목록으로 적었는데, 읽는 루틴(`01:F3F9`)은 `$BC` 번 동안 `C0` 이상 바이트를, 이어 `$BD` 번 동안 `80` 이상 바이트를 건너뜁니다. 인물 기본 목록과 같은 건너뛰기입니다. 원본 54그룹 모두 `80` 이 맵 수−1개라, 그룹은 `[맵0][80]…[마지막 맵][C0]` 꼴입니다.

그래서 새 맵은 다음 그룹 맵의 문 목록을 읽습니다. 0D/05 는 0E 첫 목록이 비어 있어 괜찮았던 것이고, 0D/07 은 0E 그룹 맵의 문 하나(`01:D514`)를 읽습니다. 새 그룹 36 은 표 끝 `01:D8C2` 뒤의 코드 바이트를 읽습니다. 표는 1,478바이트로 바로 뒤가 코드이고, 뱅크 01 의 빈 자리는 304바이트뿐이며, 루틴은 `PHK`·`PLB` 로 DB 를 01 로 둡니다. 다른 뱅크로 옮기려면 그 자리와 문 루틴 전체의 DB 를 봐야 해서 이번에는 늘리지 않았습니다. 대신 엔진과 같은 건너뛰기로 새 맵이 읽게 될 목록을 계산해, 비어 있지 않거나 표 밖이면 거부하고 `--allow-door-readthrough` 로만 만들게 했습니다.

## 5. 다른 뱅크로 덩어리째

같은 뱅크에서는 옛 그룹 표 자리만큼만 늘어납니다. 더 늘리려면 목록과 그룹 표를 다른 뱅크로 옮기고, 로더가 DB 를 그 뱅크로 두게 해야 합니다(`01:92F1` `LDA #$0F`, `01:83ED` `LDA #$23`, `01:9326` `LDA #$1F`). DB 를 바꾸면 그 동안의 abs 접근이 모두 새 뱅크로 갑니다. 출구 표 때 만든 DB 창 감사에 창을 여는 PC 를 고르는 `AUDITOPEN` 을 더해 네 창(`01:92F4`·`83F0`·`9329`·`847D`)을 원본 8장면에서 돌렸습니다.

```
DB 창 명령 151개, DB 기준 접근 29곳 (abs 8000~ 6곳)
  01:9316 LDY $8ED7,X   … 0F:8ED9~0F:8F2C
  01:92F6 STA $1823     …
  01:84B9 STA $4202     …
```

`8000` 이상 abs 는 표 읽기 여섯 곳뿐이고, 나머지는 WRAM 과 MMIO 곱셈이었습니다. 출구 표 때와 같은 결론으로, 뱅크 `00`~`3F` 면 됩니다. `01:84C9` 의 롬 읽기는 조우 구역 레코드를 긴 주소로 읽는 것이라 상관없습니다.

`dq5map.group_spans` 는 이제 표 주소 피연산자와 DB 즉값을 함께 읽습니다. 맵 포인터를 읽던 도구들(`map_pointer`·`all_maps`·`pointer_addr`·`dq5gfx`·조우 도구)은 고정 뱅크 대신 그 뱅크를 씁니다.

## 6. 밟아서 확인

`dq5newmapcheck.py` 의 롬을 네 벌로 늘렸습니다.

| 롬 | 바꾼 것 |
| --- | --- |
| `m` | 0D 에 스무 개(0D/05~0D/18). 맵 포인터 덩어리 `3E:8000`, 맵 속성 덩어리 `3E:A000`. 0D/01 계단 → 0D/18 |
| `g` | 새 그룹 36/00(0D/02 복사). 들어가는 곳은 0D 복사로 `3E:C000`, 인물 그룹 포인터·빈 목록은 `dq5npcrelocate.py --new-map`. 0D/01 계단과 다른 그룹 출구로 서로 이음 |
| `h` | 50/52(50/51 레코드 복사). 고층 그룹 표 `1F:FE30`. 속성은 조우 도구로 50/51 과 같은 값, `--high-at 3D:8000` |

```
many-enter: 0D/18 (14, 11) 층 01 1A98=FF 1AA0=80 194D=01 194B=09 1983=08
group-enter: 36/00 (14, 11) 층 01 1A98=FF 1AA0=80 194D=01 194B=09 1983=08
group-leave: 0D/01 (14, 11) …
high-stay: 50/52 (31, 17) 층 01 1A98=FF 1AA0=80 194D=0A 194B=0D 1983=08
high-new: 05/01 (33, 47) …
25개 장면 통과
```

0D/01 의 계단으로 0D/18 과 36/00 에 들어갔고, 그 계단으로 0D/01 에 돌아왔습니다. 50/52 에 서 있으면 맵 속성 WRAM 이 50/51 과 같았고, (31,17) 에서 아래로 가면 50/* 공유 목록대로 05/01 에 섰습니다. 목록이 밀린 뒤 그룹의 21/02 출구와 앞 그룹 01/00 출구도 원본과 같았습니다. 출구 쪽 44장면도 다시 돌려 모두 맞았습니다.

36/00 의 화면은 0D 의 같은 방과 같았습니다. 그룹 36 은 팔레트 세트 표(`10:DEBC`)에 없어서, 앞 맵(0D/01)의 팔레트가 남은 것인지는 확인하지 않았습니다.

## 틀렸던 것들

- 지난 일지에서 문 표를 `[BC][BD]` 찾기 목록으로 분류했습니다. `$BC`·`$BD` 를 `$00`·`$02` 에 옮기기만 하는 곳이라 다음 명령으로는 가를 수 없었고, 루틴을 끝까지 읽어야 건너뛰기인 것이 보였습니다.
- 고층 속성 목록을 이 도구가 직접 옮겼는데, 조우 도구가 같은 목록을 이미 맡고 있었습니다. 조우 도구에 맡겼습니다.

- 새 그룹을 받는 입력을 만든 뒤 `check` 가 다시 패치하는 단계에서 「새 그룹은 37 부터」 로 실패했습니다. 이미 그룹 36 이 있는 롬에 같은 입력을 주면 새 그룹이 아니라 기존 그룹입니다. `groups` 에 기존 그룹을 적으면 들어가는 곳만 고치게 했습니다.
- 처음 만든 50/52 장면은 (31,17) 에서 아래로 걸어 05/01 에 선 뒤의 속성을 견주었습니다. 그건 05/01 의 속성입니다. 50/52 에 머무는 장면을 따로 두었습니다.
- 다른 세션이 같은 스크래치 폴더의 디스어셈블 도구를 덮어써 분석이 한 번 비었습니다. 워크트리 `work/` 에 따로 두었습니다.
