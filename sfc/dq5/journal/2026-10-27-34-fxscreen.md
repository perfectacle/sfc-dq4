# 2026-10-27-34: 연출 OBJ·BG3 겹침은 색 더하기가 아니라 우선순위였다

[2026-10-25-182](2026-10-25-182-fxframes.md)에서 연출 층 그림과 화면이 맞지 않은 다섯 벌(`02`·`03`·`06`·`1F`·`20`)을 「색 더하기로 보임」 으로 남겨 두었습니다. 화면 전체를 그려 MesenCE 화면 버퍼와 같은 프레임끼리 견주자, 까닭은 색 더하기 하나가 아니라 BG3 우선순위와 HDMA 였습니다. 결과는 [dq5-graphics-format.md 「연출 층과 화면 전체」](../docs/dq5-graphics-format.md#연출-층과-화면-전체-dq5fxscreenpy)에 있습니다.

## 1. 화면 전체를 같은 프레임으로

앞 대조는 PNG 화면을 찍어 견줬는데, 찍는 프레임이 1~3프레임 흔들려서 4프레임 동안 그대로인 덤프만 썼습니다. 이번에는 프레임 끝마다 화면 버퍼(`emu.getScreenBuffer`)와 PPU·DMA 상태를 함께 남기고, 타이틀에서 쓰던 `dq5ppu.py` 로 화면 전체를 그렸습니다.

`02` メラミ 는 첫 프레임부터 거의 맞았습니다. 72프레임 내내 `ppu.colorMathEnabled` 가 0 이라 색 계산은 꺼져 있었습니다. 다른 점은 166줄 한 줄뿐이었고, 그 줄의 화면에는 OBJ 불꽃이 없었습니다. HDMA 채널 4 가 롬 표 `22:E471`(`36 07 70 17 49 07 01 17`)로 `$212C` 를 바꿔 OBJ 를 56~166줄에만 켜기 때문이었습니다. 렌더러가 롬에 있는 HDMA 표와 `$212C`·`$212D` 를 따르게 하자 72/72프레임이 같았습니다.

그렇다면 연출 층이 어긋난 것은 무엇 때문일까요. 전투는 모드 1 에 BG3 우선(`$2105` bit3)이 켜져 있어, 우선순위 비트가 선 BG3 타일은 모든 OBJ 위에 옵니다. 연출 층 그림(`dq5fx.render_frame`)은 OBJ 를 늘 BG3 위에 그렸습니다. BG3 를 우선순위 비트로 둘로 나눠 OBJ 아래·위에 그리자, 같은 72프레임의 56~159줄 불투명 점이 1,637개 다르던 것에서 44,139개 모두 같아졌습니다.

## 2. HDMA 고정색과 CGRAM

`03` メラゾーマ·`06` ベギラゴン 은 색 계산이 BG1~3 에 켜져 있었습니다. HDMA 채널(간접, `$2132`, 롬 표 `22:E26C`, 자료 `7E:5C00`~)이 줄마다 고정색을 바꿉니다. 렌더러에 `$2132` HDMA 를 넣자 대부분 맞았고, `06` 은 두 가지가 더 있었습니다.

- 서브 화면 층(`$212D`, 롬 표 `22:E184`)도 HDMA 로 56~166줄에 OBJ 를 켭니다.
- 반으로 나누기를 31 로 자른 뒤에 하고 있었습니다. 한 점을 따라가 보니 BG3 색 (31,21,0) 과 서브 화면 OBJ 색 (10,17,21) 의 결과가 화면에서 (20,19,10) 이었습니다. 합을 자르기 전에 반으로 나눠야 합니다.

`1F`·`20` ルカニ·ルカナン 은 HDMA 채널(꼴 3, `$2121`·`$2121`·`$2122`·`$2122`, 롬 표 `22:E6CD`)이 144~158줄에서 슬라임의 색을 파랗게 바꿉니다. 프레임 끝 CGRAM 에는 바뀐 색이 이미 들어 있어서, 프레임 첫머리(`startFrame`)의 CGRAM 에 줄마다 HDMA 쓰기를 더해 그렸습니다.

## 3. 화면을 그리는 동안의 쓰기

`03` 에는 첫머리 WRAM 으로 그리면 맞고 끝 WRAM 으로 그리면 틀린 프레임과, 그 반대인 프레임이 섞여 있었습니다. 고정색 표 `7E:5C00` 에 쓰기 감시를 걸고 줄(`ppu.scanline`)과 줄 안 자리(`memoryManager.hClock`)를 적었습니다.

```
12프레임  33줄 240  7E5C00 = 22    → 끝 WRAM 이 맞음
16프레임  59줄 1316 7E5C00 = 24    → 첫머리 WRAM 이 맞음
```

`7E:5C00` 을 읽는 HDMA 는 54줄입니다(표 `36 03 5C | 82 00 5C | …`). 줄 i 의 HDMA 보다 앞선 쓰기만 보게 하자 둘 다 맞았습니다.

남은 두 가지도 같은 방식으로 풀었습니다.

- `09` イオナズン: 색 창(`$2130` = `20`)으로 창 0 의 좌우 범위 안에서만 고정색을 뺍니다. `$2130` 은 MesenCE 상태 키에 없어 쓰기 감시로 받았습니다.
- `0B` ヒャダルコ 48프레임: CPU 가 33줄 마스터 주기 210 에 `$2131` = `00` 을 썼고, 그 줄의 x 30 까지만 색 계산이 남았습니다. 점 x 의 자리를 88 + 4x 로 두었습니다.

PPU 레지스터 쓰기 감시에는 HDMA 쓰기도 걸립니다. HDMA 채널이 쓰는 레지스터이고 줄 안 자리가 1100 이후인 쓰기는 HDMA 로 보고 뺐습니다. 이 실행에서 그렇게 나뉘지 않는 쓰기는 없었습니다.

## 4. 전부

이것을 `lua/dq5fxscreen.lua`(덤프)와 `dq5fxscreen.py`(비교)로 묶고, [2026-10-27-11](2026-10-27-11-fxclock.md)의 전투 실행 91벌을 떠서 견줬습니다. 몬스터 쪽 실행은 주인공의 たたかう(`73`)가 먼저 돌아서, `ONLY` 로 그 행동의 연출을 골랐습니다.

```
연출 84가지(01~20 중 26, 39~65 45, 6F·70·73, 8E~94 7, 9E·A4·A6)  4,355프레임  다른 프레임 0
연출이 없던 실행: m6F(슬라임이 がったいだ 를 고르지 않음. 6F 는 n6F 에서 견줌)
```

타이틀은 `title-opening-rom.gif` 가 바이트째 그대로였고, 세이브스테이트에서 돌린 1,297프레임도 모두 같았습니다. 연출 층 그림(`gfx/effects/frames`)은 BG3 우선순위를 따르게 되어 24벌이 바뀌었습니다.

## 틀렸던 것들

- 다섯 벌이 어긋난 것을 색 더하기로 보았습니다. `02` 는 색 계산이 꺼져 있었고 BG3 우선순위 문제였습니다. 색 계산이 실제로 있던 `03`·`06` 도 OBJ 가 아니라 BG1~3 에 HDMA 고정색을 더한 것이었습니다.
- 처음에는 프레임 끝 상태 하나로 그렸습니다. HDMA 표·CGRAM·레지스터가 프레임 도중에 바뀌는 장면은 첫머리 상태와 그 프레임의 쓰기 기록이 있어야 맞았습니다.
