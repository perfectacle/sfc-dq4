# 2026-10-31-08: 덧붙인 스크립트 끝 뒤의 대화 번호와 인라인 30·31·32

[3200 이상 덧붙이기 일지](2026-10-30-27-msggrow.md)에 남은 것이 둘 있었습니다. 대화 번호 `900` 이상에 스크립트를 덧붙인 롬(`dq5talkwrite.py --extra-at`)에서 스크립트 끝 뒤의 대화 번호가 원래처럼 메시지 `T + 3C6` 으로 가는지, 그리고 인물 인라인 `30`·`31`·`32` 가 `21` 처럼 덧붙인 메시지를 띄우는지입니다. 둘 다 코드로만 읽었던 것이라, `dq5textgrowcheck.py` 에 장면을 더해 게임에서 쟀습니다. 결과는 [메시지 번호의 한도](../docs/dq5-text-format.md#메시지-번호의-한도)와 [3200 이상 덧붙이기](../docs/dq5-build-format.md#3200-이상-덧붙이기)에 옮겼습니다.

## 1. 코드로 본 길

말을 걸면 `06:AFF4` 가 `06:AF62`(갈래 고르기)와 `06:B044`(실행 갈래)를 차례로 부릅니다. 덧붙인 스크립트 루틴은 이 가운데 `06:AF7B`·`06:B04F` 의 `CMP #$024F` 를 `JSR` 로 바꾼 것입니다.

```
lookup  CMP #$0900 / BCC +5 / CMP #end / BCC 덧붙인 갈래 / CMP #$024F / RTS
run     CMP #$0900 / BCC +6 / CMP #end / BCS +1 / RTS / CMP #$024F / RTS
06:B029 24F ≤ T < 26D(묻기)      06:B34F 를 부른 뒤 복귀 주소를 버려 06:AFFB 로 가지 않음
06:B04F JSR run / BCC $B058       C = 0(T < 24F 이거나 덧붙인 스크립트): 06:B05D 부터 스크립트 실행
        C = 1(T ≥ 26D, 끝 뒤 포함)  06:B054 BRK #$95 뒤 06:AFFB 로 돌아가 메시지 T + 3C6(코드는 T - 24F + 615)
```

끝 이상이면 두 루틴 모두 원래 비교만 하고 돌아가므로, `T ≥ 26D` 는 원래대로 `06:AFFB` 로 갑니다. 걸리는 곳이 하나 있었습니다. `06:B05D` 의 데이터 뱅크 루틴은 `7E:0F1A`(대화 번호 위 바이트)가 `09` 이상이면 스크립트 뱅크를 고르는데, 끝 뒤 `922`·`FFF` 도 위 바이트가 `09` 이상입니다. 그러나 `06:B05D` 는 `06:B04F` 가 C = 0(스크립트)일 때만 닿고 메시지 갈래는 `06:B054` 에서 `06:AFFB` 로 돌아가므로 지나지 않습니다(코드 읽기). 이것을 게임에서 확인하는 것이 이번 일입니다.

## 2. 두 패치를 함께 빌드하기

메시지 패치는 지난번처럼 3200~`1FFF` 를 `38:8000` 에 덧붙이고, `CE8`(= `922 + 3C6`)에도 「なにぬねの」 를 넣었습니다. 스크립트 패치는 원본 롬에서 따로 대화 `900`~`921`(34개, 묶음 둘)을 `3F:8000`, 루틴을 `06:FE10` 에 둡니다. `900` 은 `msg C80`, `921` 은 `msg 1FFF`, 나머지는 `msg 129` 입니다. 덧붙인 스크립트가 덧붙인 메시지를 부르는 길도 함께 보려는 것입니다.

```
walk-text   38:8000~3B:FFFF, 3C:8000 19,051바이트(3C:CA6A 까지), 24:8BC3·24:9E02·24:9E07·24:8BD7
talk-extra  06:AF7B·06:B04F·06:B05D·06:B137, 06:FE10 84바이트, 3F:8000 106바이트
```

두 패치는 자리가 겹치지 않아 `dq5build.py` 가 그대로 받았습니다. 일부러 `--extra-at 3C:C000` 으로 메시지 자리 안에 두면 빌더가 `겹침 3C:C000~3C:C069` 로 거부합니다. 도구를 고칠 것은 없었고, `--extra-at` 을 메시지 자리 밖에 두라는 줄을 쓰기 형식 문서에 더했습니다.

## 3. 게임에서 띄우기

대화 번호 갈래는 선실 파파스의 대화 번호를 `POKE` 로 바꿔 말을 걸고, 인라인 갈래는 17/00 인물(`05:A84F`) 스크립트를 `30 80 0C`·`31 C5 0C`·`32 FF 1F` 하나로 바꿔 걸어갑니다. 프로브는 지난번 `dq5textgrowcheck.lua` 그대로이고, `24:8BAF` 가 받은 번호와 `24:8B98` 이 푼 첫 64코드를 입력과 견줍니다.

도구 출력(25줄 가운데 이번에 더한 8줄과 마지막 줄). 꼴은 「장면: 스트림 앞 코드」 입니다.

```
인물 인라인 30 C80: 3CBE1F 1006 327 398 2FD 328 329 1001
인물 인라인 31 CC5: 3CBE50 1006 32A 2E5 2FE 32B 34C 1001
인물 인라인 32 1FFF: 3CCA64 1006 32E 2E7 354 3C3 302 1001
덧붙인 스크립트 롬 대화 번호 900: 3CBE1F 1006 327 398 2FD 328 329 1001
덧붙인 스크립트 롬 대화 번호 921: 3CCA64 1006 32E 2E7 354 3C3 302 1001
덧붙인 스크립트 롬 대화 번호 922: 3CBE6B 1006 330 3C6 3B9 314 399 1001
덧붙인 스크립트 롬 대화 번호 FFF: 3CC2BA 1006 2FF 300 32C 32D 2E6 1001
덧붙인 스크립트 롬 대화 번호 8FF: 3CBE50 1006 32A 2E5 2FE 32B 34C 1001
25개 검사 통과
```

장면마다 `24:8BAF` 가 받은 번호는 실행 폴더의 `decoded.txt` 첫 칸에 남습니다. 위 여덟 장면은 차례로 `0C80`·`0CC5`·`1FFF`·`0C80`·`1FFF`·`0CE8`·`13C5`·`0CC5` 한 줄씩이었습니다.

실행마다 디코더가 받은 번호는 하나뿐이었습니다. `900` 은 덧붙인 스크립트가 없으면 메시지 `CC6`(빈 `{1001}`)인데 `C80` 이 나와 스크립트가 돈 것이고, 바로 뒤 `922` 는 메시지 `CE8` 로 갔습니다. `FFF` 도 덧붙인 스크립트가 없는 롬과 같은 `13C5` 였고, `900` 앞 `8FF` 도 그대로입니다.

인라인 셋은 모두 `21` 과 같이 입력대로 풀었습니다. 1,000프레임 화면에서 `30` 은 「あいうえお」 가 든 창이 남아 있고, `31` 은 메시지 창이 없었습니다. [인라인 표](../docs/dq5-map-format.md)에 적힌 「`30` 은 창이 남음, `31` 은 창 없이」 와 맞습니다.

메시지 `CE8` 에 글자를 넣어 그 뒤 메시지 자리가 다섯 글자만큼 밀렸습니다. 그래서 `13C5`·`1FFF` 의 스트림 주소가 지난 일지(`3C:C2B5`·`3C:CA5F`)와 다르고(`3C:C2BA`·`3C:CA64`), 문서 표도 새 주소로 고쳤습니다.

## 틀렸던 것들

- 처음 돌릴 때 다른 MesenCE 빌드를 `MESENCE` 로 주었더니, 선실 상태를 읽지 못하고 새 게임 이름 넣기 화면에서 1,000프레임을 보내 25건 모두 디코더 기록이 비었습니다. 원본 롬 대조까지 빈 것을 보고 롬 탓이 아니라 에뮬레이터 탓임을 알았습니다. 상태를 만든 빌드로 바꾸자 모두 통과했습니다.

## 남은 것

- 인라인 `32` 가 A 를 기다렸다 창을 닫는 것은 화면으로 따로 보지 않았습니다. 1,000프레임 화면에 창이 없었지만, 그 사이 무엇이 창을 닫았는지는 재지 않았습니다.
