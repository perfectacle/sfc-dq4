# 2026-10-30-16: 상자 번호를 16비트로, 257번째 상자부터의 비트 자리

[상자 일지](2026-10-29-05-chestgrow.md)와 [걸음 루틴 일지](2026-10-30-04-maprest.md)가 남긴 상자 257개 이상을 풀었습니다. 상자 번호를 16비트로 바꾸는 훅 셋을 `dq5chestreloc.py --wide-at` 으로 넣고, 257번째부터의 열림 비트를 기록 범위 안의 빈 틈 `7E:28F3`~`291A` 에 둡니다. 상자 301개 롬에서 상자 300 을 열고, 들어가고, 기록·불러오기까지 확인했습니다. 결과는 [쓰기 형식 「상자 257개 이상」](../docs/dq5-build-format.md#상자-257개-이상---wide-at)에 넣었습니다.

## 1. 기록 범위의 빈 바이트

비트를 어디에 둘지부터 정했습니다. 세이브 칸은 `7E:2000`~`2A9F` 를 그대로 옮기므로(`25:83CE`) 이 안이어야 하고, SRAM 8KB 는 칸 셋이 다 채웁니다. [빈 자리 일지](2026-10-27-46-wramfree.md)와 같이 접근 카운터로 쟀습니다.

```
dq5cdlsweep.py rom/dq5.sfc work/state/ship.mss work/acc2000 --kinds maps,battles,field,extra,effects --acc 2000-2A9F
실행 770, cdl.bin 을 남긴 실행 770
2000-2A9F 접근: 주소 2720곳, acc.txt 없는 실행 0
교회 기록·불러오기의 바이트마다 (읽기, 쓰기): (10, 8) 2646곳, (11, 8)·(10, 9) 14곳씩, (12, 8) 7곳
```

교회 장면 말고는 아무 장면도 닿지 않고 교회 장면의 횟수도 (10, 8) 인 바이트가 2007곳이었습니다. 그런데 대부분은 맡긴 물건(`2250 + 물건 번호`)·맡긴 동료(`2332` 부터 26바이트 × 56)·사람 동료(`294A`) 칸이었습니다. 이 장면들에서 비어 있었을 뿐 게임을 하면 차는 자리입니다. 그래서 측정에 더해 구조로도 쓰이지 않는 틈을 찾았습니다.

첫 후보는 물건이 없는 번호의 맡긴 개수 `2328`~`2331`(물건 `D8`~`E1`)이었습니다. 물건 표는 216개(`00`~`D7`)입니다. 맡긴 물건 목록을 보니 물건 번호를 `00`~`40`·`41`~`99`·`9A`~`DF` 세 갈래로 훑어 0 이 아닌 칸을 셉니다(`21:A689`~`A6A8`, 끝 `$4A` = `E0`). 여기에 비트를 두면 없는 물건이 목록에 잡히므로 버렸습니다. 남는 `2330`~`2331` 은 2바이트뿐입니다.

둘째 후보는 맡긴 동료 칸이 끝나는 `28E2` 부터 사람 동료 칸 `294A` 앞까지 104바이트입니다. 롬에서 `7E:28C0`~`294A` 를 롱 주소로 다루는 명령은 `294A`(사람 동료 칸 시작) 여덟 곳뿐이었습니다. 770장면에서는 세 바이트만 읽혔습니다.

```
28F2 {'battles/35': (18, 0), 'effects/35': (2, 0)}
291C {'battles/36': (18, 0), 'effects/36': (2, 0)}
2946 {'battles/37': (9, 0), 'effects/37': (2, 0)}
2238 {'battles/0C': (18, 0)}   2262 {'battles/0D': (18, 0)}   228C {'battles/0E': (18, 0)}   2334 {'battles/12': (18, 0)}
```

몬스터가 하나 늘 때마다 42바이트(일행 레코드 간격)씩 뒤를 읽습니다. [상자 일지](2026-10-29-05-chestgrow.md)가 남긴 `21:8C2F` 의 `2238` 읽기가 이 꼴의 하나였습니다. 전투 코드가 `2040 + 몬스터 × 42` 를 읽는 것으로 보이지만 무엇인지는 보지 않았습니다. 이 셋을 피해 `28F3`~`291B`(41바이트)를 골랐습니다. 40바이트가 상자 256~575 의 비트, 마지막 `291B` 는 아래 3절의 넘길 마스크 칸입니다.

## 2. 8비트인 곳

원래 코드를 다시 풀어, 번호가 지나는 길을 따라갔습니다.

```
12:E66C  JSR $FE91 / JSL $25FAB0 / BCS 없음(E669)      ; 25:FAB0 이 A = n(8비트)
12:E675  STA $07 / AND #$07 / … / LDA $7E2210,X / AND $25FAE9,X / BEQ E691
12:E68B  LDY #$01 / TDC / PLP / CLC / RTS              ; 이미 열림
12:E691  $1E80 = n>>3 | 80, $1E81 = 마스크
12:E6A7  REP #$30 / TYA / ASL / TAX / LDA $1EEE4E,X     ; 내용물
12:F839  LDX $1E80 / LDA $7E2190,X / ORA $1E81 / STA $7E2190,X / CLC / RTS
1F:FC6B  JSR $FDD0                                     ; 맵에 들어갈 때 칸마다, A = 맵 안 순서
```

`25:FAB0` 을 부르는 곳은 `12:E66F` 하나, `1F:FDD0` 은 `1F:FC6B` 하나였습니다(바이트 검색). `12:F839` 는 `12:F1CF`·`F4A8`·`F51A` 셋이 부릅니다. 맵 안 순서를 세는 `2A:F224`(→`2A:FBCD`)는 DP `$00`·`$01`(= `$1E71`)만 받고 A 는 쓰지 않습니다. `12:E6A7` 은 `REP #$30` 뒤 `TYA` 라, Y 에 16비트 번호를 두고 들어가면 내용물 색인이 그대로 늘어납니다.

## 3. 훅 셋

256 미만은 원래 루틴과 원래 비트를 그대로 쓰게 했습니다. 기존 세이브와 다른 표의 비트가 바뀌지 않습니다.

- 열기: `12:E66F` 의 `JSL $25FAB0` 을 `JML 훅` 으로 바꿨습니다. 훅은 맵 연결 표를 긴 주소로 읽어 맵 앞 개수를 16비트로 더하고(스택에 쌓음), `2A:F224` 로 맵 안 순서를 더합니다. 256 미만이면 A = n 으로 `12:E675` 에 돌아갑니다. 256 이상이면 `28F3 + (n − 256)/8` 을 보고, 열렸으면 `12:E68B`, 아니면 `$1E80`·`$1E81`·`291B` 를 두고 Y = n 으로 `12:E6A7` 에 돌아갑니다.
- 켜기: `$1E80` 은 1바이트라 `2190`~`228F` 밖을 가리킬 수 없습니다. 그래서 `12:F839` 를 `JSL 훅 / RTS` 로 바꿨습니다. 상자 256 이상이면 `$1E80` 에 바이트 번호, `$1E81` 에 `00`, `291B` 에 마스크를 둡니다. 훅은 `$1E81` 이 `00` 이고 `291B` 가 `00` 이 아닐 때만 `28F3 + $1E80` 에 그 마스크를 OR 하고 `291B` 를 지웁니다. 서랍·발밑·필드 조사 등은 마스크가 `00` 이 아니므로 원래 길로 갑니다. 뱅크 01 의 `01:DF34`·`DFB9`·`F138` 은 `$1E80` 을 `7E:21C2` 기준으로 따로 쓰고 `12:F839` 를 거치지 않습니다.
- 들어갈 때: `1F:FDD0` 을 `JSL 훅 / RTS` 로 바꿨습니다. A·X 를 지키고 열렸으면 C 를 켭니다. 원래 `FDD5` 뒤와 `25:FAB0` 의 DB 즉값·abs 자리는 남겨 두고 도구가 같은 표로 고칩니다.

`dq5chestreloc.py` 는 `--wide-at` 이 있으면 훅 코드를 그 자리에 두고 세 자리를 덮습니다. `locate` 는 `12:E66F` 가 JML 이면 그 코드를 같은 표 자리로 다시 만들어 바이트째 같은지 보고, 훅의 표 자리도 다른 자리와 같아야 받습니다. 상자 수 한도는 576, 256 이상의 비트는 `28F3`~`291A` 만 받고, 다른 표의 비트는 여전히 `2210`~`224F` 안이어야 합니다. `dq5chestplace.py` 도 같은 옵션을 받습니다. `dq5chestwrite.py` 는 상자 수가 161 로 고정이고 비트가 `2210`~`224F`(필드 조사는 `2190`~`228F`) 안이라 바꿀 것이 없었습니다. 훅만 넣은 롬에서도 같은 표를 읽고 쓰는 것을 단위 테스트로 봤습니다.

해석기 테스트(`test_dq5chestwide.py`)는 원본 롬에 훅과 합성 표(01/02 200, 03/00 100, 19/00 60)를 붙이고 `2A:F224` 를 `LDA #순서 / RTL` 로 바꿔 돌립니다. 19/00 의 순서 4(상자 304)는 `12:E6A7` 에 Y = `0130`, `$1E80` = 6, `291B` = `80` 으로, 같은 비트를 켜 두면 `12:E68B` 로 갑니다. 03/00 의 55(255)는 원래 `12:E675` 에 A = `FF` 로, 56(256)은 훅 길로 갑니다. 스택은 모든 갈래에서 들어올 때와 같았습니다.

## 4. 상자 301개 롬

[상자 256개 롬](2026-10-29-05-chestgrow.md)(`full_*`)에 01/02 의 (16~90, 8)·(16~28, 10) 블록 45개를 더 놓았습니다. 자리는 `dq5chestplace.plan` 이 받는 곳을 하나씩 더해 골랐습니다. 상자는 301개이고 19/00 의 첫 칸이 상자 296, 마지막 칸 (12,45) 가 상자 300(`28F8 & 08`)입니다. 300 의 아래 8비트는 44 라, 번호를 8비트로 다뤘다면 원래 상자 44(`2215 & 08`)를 봅니다.

```
dq5chestcheck.py rom/dq5.sfc --state work/state/ship.mss
35쌍/70실행 통과: 보상·금화·새 열림 비트·기존 비트 보존·들어갈 때 열린 상자, 기록·불러오기 2실행 통과
wide_open  patched: 금화 100 → 400, 7E:28F8 = 08, 7E:291B = 00, 기록 범위에서 바뀐 바이트 2019·201A·28F8
wide_alias patched: 2210 = 40 → 40, 2215 = 08 → 08, 28F8 = 00 → 08, 300G
wide_entry 열린 상자 타일 4
wide_save  2600:70090A = 08, 2600:7E28F8 = 08, 2710:7E28F8 = 00, 6400:7E28F8 = 08
```

기존 사례(`--env` 가 필요한 `blocks_*` 는 뺌)도 모두 그대로 통과했습니다.

- `wide_open`: 19/00 (11,46) 에서 위를 조사하자 메시지 131 과 300G 를 얻고 `28F8 & 08` 만 켜졌습니다. 원본 롬은 19/00 이 표에 없어 12B·12C 였습니다.
- `wide_alias`: 상자 1(`2210 & 40`)과 상자 44(`2215 & 08`)를 켠 채로 열어도 상자 300 은 닫힌 상자로 보여 300G 를 주었고, `2210`·`2215` 는 그대로였습니다.
- `wide_entry`: `28F8 & 08` 을 켜고 19/00 에 들어가자 상자 300 자리 넷이 열린 상자 타일(`9E`·`9F`)이 되었습니다. 원본은 그대로였습니다. 떠났다 돌아오는 것과 같은 길(`1F:FC50`)입니다.
- `wide_save`: `28F8 & 08` 을 켜고 교회에 기록하자 SRAM 칸 1 의 `70:090A`(= `0012 + 08F8`)가 `08` 이 되었고, 리셋 뒤 `00` 이던 WRAM 이 불러온 뒤 `08` 로 돌아왔습니다. 체크섬이 맞아 불러오기도 됐습니다.

## 남은 것

- 상자 300 밖의 번호(256~575)는 해석기 테스트와 코드 읽기입니다. 게임에서는 300 하나입니다.
- `7E:28F3`~`291B` 는 770장면과 구조(칸 표의 끝)로 골랐습니다. 훅을 넣은 롬으로 이야기를 처음부터 끝까지 진행하며 같은 카운터를 걸어 두어야 합니다.
- 전투에서 `2040 + 몬스터 × 42` 를 읽는 코드(`21:8C2F`)가 무엇을 읽는지.
