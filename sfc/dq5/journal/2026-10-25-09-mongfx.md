# 2026-10-25-09: 전투 몬스터 그림

전투 화면의 몬스터 그림을 롬에서 풀었습니다. 몬스터 번호 → 레코드(그림 번호·색) → 그림 머리 → 조각·타일 순으로 읽어 OBJ 로 그리고, 그림 107개를 모두 게임 버퍼·화면과 비교했습니다. 형식은 [dq5-graphics-format.md](../docs/dq5-graphics-format.md) 에 정리했습니다.

## 1. 그림이 VRAM 에 들어가는 곳

[핸드오프](../handoff.md) 의 이벤트 전투(배 선실에서 사다리를 덮어 슬라임 셋과 싸움)를 그대로 쓰고, 전투가 시작되는 850프레임부터 DMA(`$420B`) 기록을 남겼습니다.
OBJ 이름 기준인 VRAM `$6000` 으로 가는 DMA 는 889프레임에 `00:FD6D` 에서 나왔고, 원본은 WRAM `7E:4000` 부터 한 줄(`$200` 바이트)씩이었습니다. 다음 프레임에는 `00:FDE3` 이 `7E:2D00` 512바이트를 CGRAM 으로 보냈습니다.

```
889 ch7 ctl=01 B=2118 src=7E4000 n=0040 vaddr=6000 pc=00:FD6D
889 ch7 ctl=01 B=2118 src=7E4200 n=0040 vaddr=6100 pc=00:FD6D
890 ch7 ctl=00 B=2122 src=7E2D00 n=0200 vaddr=6120 pc=00:FDE3
```

그 버퍼를 채우는 곳을 거슬러 올라가니 `22:8FF8` 이 몬스터 번호(`$0D14`)로 `27:E5DC` 표에서 27 뱅크 레코드를 찾고, 첫 바이트(그림 번호)를 `57`·`2A` 와 비교해 세 뱅크의 머리 포인터 표(`27:82E4`, `26:8F99`, `25:8C45`) 중 하나를 고릅니다.
머리를 읽어 타일을 푸는 것은 `22:9822`, 타일 하나는 `22:992A` 입니다.

## 2. 형식 읽기와 디코더

`22:9822` 를 읽은 결과, 그림은 8픽셀 칸 상자(머리 `+5` 의 두 니블)와 칸 비트맵, 조각마다 니블 하나, 그리고 조각 자료로 되어 있습니다.
니블 bit1 은 16x16(타일 4개), bit2·bit3 은 「앞 조각을 좌우 반전해 다시 씀」이고, 타일은 모드 바이트의 bit0~3 으로 비트평면 유무, bit7 로 마스크 압축을 고릅니다. 자세한 표는 형식 문서에 있습니다.

`sfc/dq5/tools/dq5mongfx.py` 로 옮기고 먼저 경계를 봤습니다. 그림 번호 `00`~`71` 의 머리는 104곳이고(`00`·`11`·`29` 처럼 같은 머리를 가리키는 번호가 있음), 주소 순으로 놓으면 그림마다 디코더가 읽은 끝이 다음 머리와 같았습니다.
맞지 않는 것은 그림 `15`(다음 머리까지 3바이트 `81 80 FC` 가 남음)와 뱅크 마지막 그림 `28`·`56`·`71` 뿐이었습니다. `28` 뒤는 바로 코드, `56` 뒤는 `00` 채움, `71` 뒤는 레코드 포인터 표입니다.

```sh
uv run --locked python sfc/dq5/tools/dq5mongfx.py rom/dq5.sfc            # 236마리 목록
uv run --locked python sfc/dq5/tools/dq5mongfx.py rom/dq5.sfc 60 --png work/60.png --scale 2
```

```
00 그림 02 머리 259177-2591D1 2x2칸 조각 1(16x16 1, 반전 0) 색 6
60 그림 15 머리 25C1F6-25C4E9 9x6칸 조각 22(16x16 5, 반전 3) 색 12
```

## 3. 그림 107개를 게임과 비교

이벤트 전투의 첫 무리 몬스터(`7E:1001`)와 마릿수(`7E:1005`)를 매 프레임 고정하면 아무 몬스터 한 마리와 싸울 수 있습니다. 몬스터 236마리가 쓰는 그림 번호 107개마다 대표 몬스터 하나를 골라 107번 전투를 붙였습니다.
`sfc/dq5/tools/lua/dq5battledump.lua` 가 그림을 다 푼 직후(`22:90DC` 실행)의 WRAM 과, 1000프레임의 화면·OAM·VRAM 을 덤프합니다.

```sh
export LIBDIR=$(tools/lua/seqlib.sh "$(uv run --locked krpatch sfc lua)" work/walklib walk.lua)
m=60
STATE=$PWD/work/state/ship.mss PRE="b:4,wait:40,b:4,wait:40" ROMPATCH="156FF5=E0253C0103" \
  WAYPOINTS="3,11;3,24;7,24;7,22;37,66;37,72;down:90" CHANGES=2 AFTER=400 MAXF=1100 POKE="7E1001=$m;7E1005=1" \
  DUMPF=1000 FROM=850 TO=0 AT=2290DC SHOT_DIR=$PWD/work/all/t$m \
  "$MESENCE" --testrunner "$PWD/rom/dq5.sfc" "$PWD/sfc/dq5/tools/lua/dq5battledump.lua"
uv run --locked python sfc/dq5/tools/dq5mongfx.py rom/dq5.sfc $m --compare work/all/t$m/at.bin \
  --shot work/all/t$m/s01000.png --oam work/all/t$m/o01000.oam work/all/t$m/v01000.vram
```

```
60 그림 15 머리 25C1F6-25C4E9 9x6칸 조각 22(16x16 5, 반전 3) 색 12 버퍼 31/31 화면 1721/1726 @(91,105) OBJ 1726/1726 @(91,113)
```

- `--compare`: 디코더가 푼 타일이 게임 버퍼 `7E:4000-5FFF` 에 32바이트째로 있는지. 107번 모두 빠짐없이 있었습니다(합계 3,623/3,623).
- `--shot`: 레코드 색으로 칠한 그림을 화면에서 가장 잘 맞는 자리에 놓고 RGB 를 비교합니다. `E4`·`EA` 를 뺀 105번에서 152,426/152,899 픽셀이 맞았고, 틀린 473픽셀은 모두 스크린샷 y=152 한 줄이었습니다. 그림 맨 아랫줄이 창 테두리에 가려진 것입니다.
- `--oam`: OAM·VRAM 으로 OBJ 만 다시 그려 색 번호로 비교합니다. 창에 가려지지 않으므로 맨 아랫줄까지 맞습니다.

색이 RGB 까지 맞으니 레코드의 색이 OBJ 팔레트 1번 색부터 들어가는 것, 반전 복사 조각(bit2 가 0 이면 1픽셀 왼쪽)의 자리도 함께 확인한 셈입니다. 반전 조각이 있는 그림(`09`·`0E`·`26`·`65` 등)도 맨 아랫줄 말고는 다 맞았습니다.

## 4. 화면과 맞지 않던 둘: ブオーン, ミルドラース

`E4`(ブオーン)는 1000프레임 화면에서 한 픽셀도 맞지 않았습니다(0/5,522). 등장 연출이 길어 아직 그려지지 않은 것으로, `MAXF=1500 DUMPF=1450` 으로 다시 찍으니 5,522/5,522 맞았습니다.

`EA`(이름 표에서는 `E8`~`EB` 넷 다 ミルドラース)는 버퍼는 91/91 맞는데 화면은 0/7,332 였습니다. 덤프를 보니 게임이 둘째 무리(`7E:1002`)에 `EB` 를 1마리(`7E:1006`) 더해, 그림 `70`(윗몸)과 `71`(아랫몸)을 겹쳐 그리고 있었고, OBJ 팔레트를 바꾸는 연출 때문에 화면 색이 레코드 색과 달랐습니다.
색 번호로 비교하는 `--oam` 을 만들어 1950프레임 덤프와 비교하니 두 그림이 같은 자리 (51,58) 에서 모두 맞았습니다.

```
EA 그림 70 머리 27D45D-27DEAA 19x8칸 조각 44(16x16 34, 반전 16) 색 15 OBJ 7332/7332 @(51,58)
EB 그림 71 머리 27DEAA-27E5DC 19x13칸 조각 31(16x16 14, 반전 2) 색 15 OBJ 3401/3401 @(51,58)
```

`EB` 만 넣은 전투는 1000프레임 화면과 3,401/3,401 맞았습니다.

## 틀렸던 것들

- 처음에는 그림 번호 107개가 모두 따로 있는 줄 알고 「107개가 모두 다음 그림에서 끝난다」고 세었습니다. 실제로는 머리가 104곳이고, 안 쓰는 번호(`2D`·`35`·`37`·`38`·`57`·`5F`·`66`)는 뱅크 첫 그림을 가리킵니다. 뱅크 마지막 그림 셋도 「다음 그림」이 없으니 경계 검사에서 따로 봐야 했습니다.
- 화면 비교의 틀린 픽셀을 처음에는 디코더 오류로 의심했지만, 모두 같은 스크린샷 줄이었고 OAM 으로 다시 그리면 맞았습니다. 창 테두리가 OBJ 위에 그려지는 것입니다.

## 남은 것

- 머리 `+0` 플래그와 `+1`~`+4`(`7E:0C2E`·`0C33`·`0C51`·`0C56`)의 뜻.
- 여러 마리·여러 무리일 때 화면 위치를 정하는 규칙, `7E:5800` 조각 목록에서 OAM 을 만드는 루틴.
- 그림 `15` 뒤의 3바이트 `81 80 FC`, 그림 `11`·`29`·`5E` 처럼 같은 머리를 가리키는 번호가 따로 있는 이유.
- `EA` 에 `EB` 를 더하는 곳, 다른 보스도 그림을 나눠 쓰는지. 전투 배경.
