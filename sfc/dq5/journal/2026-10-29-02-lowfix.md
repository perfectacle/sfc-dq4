# 2026-10-29-02: 문 표 패치와 dq4 환경 맵 패치를 함께 쓰기, 검사 도구 정리 둘

[문 표 늘리기](2026-10-27-66-doortable.md)는 스텁을 뱅크 01 끝 `01:FED0` 에 두었습니다. dq4 트랙의 환경 맵 패치도 같은 자리를 써서 두 패치를 함께 빌드할 수 없었습니다. 이번에는 스텁을 뱅크 01 밖으로 옮겼고, 함께 빌드한 롬을 MesenCE 로 돌려 보았습니다. 검사 도구 두 곳도 정리했습니다. `dq5newmapcheck.py` 가 `dq5exitcheck.py` 의 전역을 바꾸던 것과, `dq5chestplace.py` 의 아래층 상자 검사가 엔진과 맞지 않던 것입니다. 결과는 [쓰기 형식의 dq4 환경 맵과 함께 쓰기](../docs/dq5-build-format.md#dq4-환경-맵과-함께-쓰기)와 [보물상자 놓기](../docs/dq5-build-format.md#보물상자-놓기-dq5chestplace1)에 있습니다.

## 1. 뱅크 01 에는 자리가 없음

dq4 패치(`sfc/dq4/tools/dq4environmentrom.py --out …`)를 만들어 보니 뱅크 01 끝에 295바이트를 씁니다(`report.json` 의 `bank01_bytes`). 빈 자리 304바이트 가운데 9바이트만 남아, 66바이트 스텁은 뱅크 01 어디에도 들어가지 않습니다. 그 295바이트의 대부분은 바꾼 맵의 문 물체 항목이고, `01:F42D` 훅이 Y 를 그 항목으로 바꾼 뒤 `01:F43F` 의 `LDA $D2FC,Y` 가 DB 로 읽습니다. 문 표를 늘리면 이 읽기도 복사본에서 일어납니다. 그러니 뱅크 01 끝은 비워 두고, 복사본에 그대로 들어가야 합니다.

## 2. 스텁을 뱅크 01 밖으로

다섯 입구의 스텁은 `JML 입구+4` 로 돌아가므로 어느 뱅크에 있어도 됩니다. 걸리는 것은 `01:F3C9`(`PHB PHK PLB JSR $F3D1 PLB RTL`)뿐이었습니다. 스텁이 `JSR $F3D1` 을 맡으면 `F3D1` 이 같은 뱅크에 있어야 합니다. 그런데 입구의 첫 4바이트만 `JML` 로 덮으므로 `01:F3CF` 의 `PLB RTL` 은 남습니다. `JSR` 이 쌓을 복귀 주소 `F3CE` 를 `PEA` 로 쌓고 `JML $01F3D1` 하면, `F3D1` 끝의 `PLA PLY PLX PLP RTS` 가 `F3CF` 로 돌아옵니다. 스택에 쌓이는 바이트는 `JSR` 과 같습니다.

```
01:F3C9 몫: 8B F4 BB BB AB AB F4 CE F3 5C D1 F3 01   PHB / PEA $BBBB / PLB / PLB / PEA $F3CE / JML $01F3D1
```

기본 자리는 원래 롬 빈 자리 가운데 아무 도구도 쓰지 않는 `22:FF30`(208바이트)으로 했습니다. 스텁은 모두 68바이트입니다. `dq5map.door_table` 은 스텁이 어느 뱅크에 있든 읽고, 옛 꼴(`JSR` 스텁)은 받지 않습니다.

복사본을 견주는 구간도 `F037`~`FEB6` 에서 `F037`~`FFFF` 로 넓혔습니다. 문 표 패치를 만든 뒤 다른 패치가 뱅크 01 끝에 문 항목을 두면 복사본에 없기 때문입니다. 스텁을 `--door-stub-at` 으로 뱅크 01 에 둔 롬은 그 자리를 빼고 견줍니다.

## 3. 4MB 롬에서 만들기

dq4 패치를 넣은 4MB 롬(`env.sfc`)에서 `--door-bank 3C` 로 만들려 하자 두 가지가 막았습니다.

- 「뱅크 01 을 복사할 뱅크가 비어 있지 않음」: `dq5build.py` 가 늘린 뱅크마다 머리 8바이트에 `DQ5X`+뱅크 표지를 씁니다(`3C:8000` = `44 51 35 58 3C 00 00 00`). 이 표지만 있으면 빈 뱅크로 보게 했습니다.
- `check` 의 「negative count」: 늘린 자리의 맨 위 뱅크(`3C`)로 롬 크기를 2MB 로 정하고, 4MB 롬을 2MB 로 늘리려다 깨졌습니다. 입력 롬보다 작게 정하지 않게 했습니다.

새 맵은 처음에 그룹 01 에 더했습니다. 이러면 같은 뱅크에서 밀린 맵 포인터 목록(`0F:8B17`~)이 dq4 의 `03/00` 포인터 쓰기(`0F:8B38`)와 겹쳐 빌드가 거부됩니다. dq4 가 포인터를 고치는 마지막 그룹 `19` 뒤인 1A 에 1A/05(1A/00 복사)를 더해 원래 롬에서 한 번에 빌드했습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc build work/lowfix/env/dq4-environment.dq5patch.json --size 4 -o work/lowfix/env.sfc --ips work/lowfix/env.ips
uv run --locked python sfc/dq5/tools/dq5newmap.py work/lowfix/env.sfc patch work/lowfix/doors.json -o work/lowfix/doors.dq5patch.json --door-bank 3C
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc build work/lowfix/env/dq4-environment.dq5patch.json work/lowfix/doors.dq5patch.json --size 4 -o work/lowfix/both.sfc --ips work/lowfix/both.ips
uv run --locked python sfc/dq5/tools/dq5newmap.py work/lowfix/both.sfc check work/lowfix/doors.json
```

```
맵 365개 → 365개(새 없음); 그룹 54 → 54개; 표 0F:FF50·23:FF20·1F:CEB6·들어가는 곳 0F:EA97; 쓰기 0개 검사 통과
```

순서를 거꾸로 해 문 표 패치를 원래 롬에서 만들면(`wrong.sfc`) 빌드는 되지만, 그 롬의 `check` 가 「뱅크 3C 복사본의 F42D 가 뱅크 01 과 다름」으로 거부합니다. `--door-stub-at 01:FED0` 은 「문 표 뱅크 밖의 빈 자리 68바이트가 필요함」, `--door-bank 3D` 는 「비어 있지 않음」으로 거부합니다.

## 4. MesenCE 로 돌려 보기

`--testrunner` 로만 돌렸습니다. 장면은 `dq5exitcheck.run` 에 `dq5newmapcheck.py` 의 문 장면 입력을 그대로 넣었고, 옛 문 표 `01:D2FC`~`D8C1` 읽기를 감시했습니다.

- `dq4environmentromcheck.py --rom both.sfc`: 통과했습니다. 바꾼 맵 46곳의 픽셀 차이 0, 걷는 층 불일치 0, 문 물체 54/54, 03/00 성문은 열린 상태로 18행까지 지나갔고, 대조 맵 01/03 의 셀 버퍼·블록 표가 원본과 같았습니다. 맵을 불러올 때마다 새 꼴 `01:F3C9` 스텁을 지납니다.
- 03/00 에 들어갈 때 물체 항목 구간의 읽기를 셌습니다. `env` 는 `01:F43F` 가 `01:FEE9` 부터 13번 읽었고 `3C:FEE8`~ 은 0번이었습니다. `both` 는 같은 13번을 `3C:FEE9` 부터 읽었고 `01:FEE8`~ 은 0번이었습니다. `wrong` 은 `3C:FEE9` 부터 336번 읽었습니다. 복사본의 그 자리가 0 이라 끝 표시(`80` 이상)가 나올 때까지 읽은 것입니다.
- 03/00 (70,44) 에서 위로 걸으면 `env`·`both` 는 문 (70,43) 에 막혔습니다(셀 `01 91 D8 18 00 10 38 3B`). `wrong` 은 문 물체가 없어 (70,43) 으로 들어갔고 메시지 `186` 이 나왔습니다.
- 01/04 잠긴 문(`187`), 열쇠(`1A2`, 셀 `01 31 F4 08 00 14 11 3D`), 01/00 성문 이벤트 `C4`·`C5`, 01/03 방 문은 `both` 와 원본의 셀·메시지가 같았습니다. 새 맵 1A/05 의 (36,27) 은 빈 문 목록대로 문 물체가 없었습니다. 옛 문 표 읽기는 모든 문 장면에서 0번이었습니다.

## 5. 사라진 종류 3F·40 문

1A/00 (36,27)(종류 3F)·19/00 (32,47)(종류 40)은 `both` 에서 문 물체가 없었습니다. 처음에는 문 표 패치를 의심했습니다. 롬을 나눠 보니 문 표 패치만 넣은 `dbonly` 는 원본과 같고, dq4 패치만 넣은 `env` 가 `both` 와 같았습니다.

| 롬 | 1A/00 (36,27) | 19/00 (32,47) | 01/03 (14,7) |
| --- | --- | --- | --- |
| 원본·`dbonly` | `00 19 91 0D 00 2E 34 3F` | `00 11 32 0D 00 34 34 40` | `01 19 E6 0C 00 0C 38 3B` |
| `env`·`both` | `00 09 91 0D 00 00 00 00` | `00 01 32 0D 00 00 00 00` | 같음 |

dq4 훅 네 곳을 하나씩 원래 바이트로 되돌리자 `01:F42D` 만 원본과 같아졌습니다. 훅 루틴은 `PHP REP #$30 PHA PHX` 뒤 바꾼 맵을 찾는 루틴을 부르는데, 그 루틴 첫머리의 `SEP #$30` 이 X 플래그를 켜며 Y 상위 바이트를 지웁니다. 훅은 Y 를 저장하지 않으므로, 바꾸지 않은 맵에서는 문 목록 자리 Y 가 `100` 미만으로 잘립니다. 01/xx 는 표 앞쪽이라 걸리지 않았습니다. `work/` 에서만 그 호출을 `PHY / JSL / PLY` 로 감싼 롬을 만들자 `env`·`both` 모두 세 셀이 원본과 같았습니다. 그 `both` 에서 두 문에 `C4` 를 걸어 연 셀(`00 31 2A 09 00 91 0D 00`·`00 31 1A 09 00 32 0D 00`)도 원본과 같았습니다. dq4 트랙 파일이라 고치지 않았습니다.

## 6. 출구 실측 도구의 감시 구간

`dq5newmapcheck.py` 는 import 할 때 `dq5exitcheck.STALE['doors'] = …` 로 남의 모듈 전역을 바꿨습니다. `dq5exitcheck.run` 이 감시 구간을 `stale` 인자로 받게 하고(기본은 그 모듈의 `STALE`), `dq5newmapcheck.py` 는 자기 `STALE` 을 넘깁니다. `dq5exitcheck.py` 자신의 호출은 그대로입니다. 테스트는 import 뒤 `dq5exitcheck.STALE` 이 바뀌지 않는지와, 넘긴 구간이 MesenCE 환경 변수 `STALE` 로 가는지 봅니다(MesenCE 는 흉내만 냄).

## 7. 아래층 상자 검사

`dq5chestplace.py` 는 놓은 블록이 발밑·두 칸 앞·아래층 상자 항목의 좌표를 덮으면 거부합니다. 아래층 상자 표 11항목은 모두 그룹 `51`·`53`·`54` 이고 이 도구는 그룹 `00`~`35` 만 받으니, 아래층 검사는 걸릴 일이 없어 보였습니다. 그런데 표를 찾는 `12:ED62` 는 이렇게 시작합니다.

```
12:ED65  a5 bc        LDA $BC
12:ED67  c9 32        CMP #$32
12:ED69  90 2b        BCC $12ED96
```

그룹 `32` 이상에서 찾으므로 그룹 `32`~`35` 는 도구 범위와 겹칩니다. `dq5chestwrite.py` 는 아래층 항목을 아무 맵으로나 옮길 수 있습니다. 그래서 검사를 빼지 않고 그룹 `32` 이상에서만 보게 했습니다. 그룹 `32` 미만에서는 항목이 있어도 엔진이 읽지 않으니 덮어도 묻히는 것이 없습니다. 테스트는 아래층 첫 항목을 32/00 (2,2) 로 옮긴 롬에서 그 칸을 덮는 상자를 거부하고, 01/02 (36,26) 으로 옮긴 롬에서는 받는지 봅니다. 고치기 전 코드는 뒤쪽에서 「기존 조사 항목 [('lower', 36, 26)]」 로 거부했습니다.

## 틀렸던 것들

- 1A/00·19/00 문이 사라진 것을 처음에는 문 표 패치 탓으로 보았습니다. `dbonly` 와 `env` 를 따로 돌려 보고 dq4 훅 쪽임을 알았습니다.
- 아래층 상자 검사는 쓸모없는 줄 알았습니다. `12:ED62` 의 `CMP #$32` 를 보고, 그룹 `32`~`35` 에서는 엔진이 읽는다는 것을 알았습니다.

## 남은 것

- dq4 환경 맵 패치의 `01:F42D` 훅이 Y 상위 바이트를 지워, 바꾸지 않은 맵 가운데 문 목록이 표 시작에서 `100` 바이트 넘게 떨어진 맵의 문이 사라집니다. 물 루틴 호출 훅도 Y 를 저장하지 않고 같은 루틴을 부릅니다(코드 읽기). 셀 바이트는 1A/00 (36,27) 원본 `00 19 91 0D 00 2E 34 3F` → dq4 패치 뒤 `00 09 91 0D 00 00 00 00`, 19/00 (32,47) `00 11 32 0D 00 34 34 40` → `00 01 32 0D 00 00 00 00` 입니다. 두 훅의 호출을 `PHY / JSL find / PLY` 로 감싸면 됩니다(obj 훅은 `work/` 의 실험 롬에서 원본과 같아짐을 확인). dq4 트랙에서 고쳐야 하며, [docs/todo.md](../../../docs/todo.md) 의 dq4 절에 요청으로 적었습니다.
- 새 맵을 그룹 `19` 보다 앞에 더하는 문 표 패치는 원래 롬에서 dq4 패치와 한 번에 빌드할 수 없습니다(맵 포인터 목록 겹침). 통합 빌드에서 dq4 패치를 넣은 롬을 바탕으로 빌드하는 순서를 정해야 합니다.
- 문 루틴 DB 감사(명령 수·DB 기준 접근 곳)는 스텁을 `01:FED0` 에 둘 때 잰 것입니다. 다섯 입구의 스텁 바이트는 같지만, 새 꼴 `01:F3C9` 스텁으로 감사를 다시 재지는 않았습니다.
- 순서를 거꾸로 한 `wrong.sfc` 의 `dq4environmentromcheck.py` 는 `rosaryhill-01` 의 덤프 파일이 없어 중간에 멈췄습니다. 다시 돌리지 않았습니다.
- 입구 `01:D92E` 는 여전히 런타임에서 지나는 장면을 찾지 못했습니다.
