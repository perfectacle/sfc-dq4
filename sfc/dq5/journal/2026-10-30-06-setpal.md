# 2026-10-30-06: 세트마다 OBJ 팔레트 4~7 고르기와 맵 팔레트 줄 늘리기

[OBJ 팔레트 쓰기](2026-10-27-51-objpalette.md)는 세트를 팔레트 0~3 중 하나로만 다시 배정했습니다. 레코드의 팔레트 칸이 2비트라서입니다. 이번에는 세트 번호로 찾는 팔레트 표를 두어 세트마다 OBJ 팔레트 0~7 을 고르게 했고, 맵마다 OBJ 줄을 덮는 `01:9A12` 표를 옮겨 새 항목을 더할 수 있게 했습니다. 실내 맵 346곳을 모두 들어가, 맵마다 인물 수·남는 OBJ 팔레트 줄·OBJ VRAM 끝도 쟀습니다. 형식은 [쓰기 형식의 「OBJ 팔레트·세트 팔레트 배정」](../docs/dq5-build-format.md#obj-팔레트세트-팔레트-배정-dq5objpalette1)과 [그래픽 형식의 「팔레트」·「맵마다 남는 OBJ 팔레트 줄과 VRAM」](../docs/dq5-graphics-format.md#팔레트)에 있습니다.

## 1. 팔레트 비트는 칸 목록에 들어 있다

`1F:CF1E` 를 읽으면 팔레트를 정하는 곳은 6타일(`1F:CFA9`)과 8타일(`1F:D0DC`)에 하나씩 있습니다. 둘 다 같은 13바이트입니다.

```
1F:CFC8  a0 02        LDY #$02
1F:CFCA  b7 09        LDA [$09],Y      ; 레코드 +2
1F:CFCC  29 c0        AND #$C0
1F:CFCE  4a ×5        LSR A            ; bit6-7 → bit1-2
1F:CFD3  85 01        STA $01
```

그 뒤 칸 48개마다 `세트 안 타일 + $1995 | $00` 을 칸 목록(`7E:8060-`)에 씁니다. 칸 워드의 위 바이트가 그대로 OAM 속성이고, 그리는 쪽(`00:F129`~`F138`)은 `($AE),Y` 의 위 바이트에 우선순위만 ORA 합니다. 그래서 `$01` 에 세 비트를 다 두면 팔레트 4~7 도 OAM 까지 갑니다. 레코드 형식을 바꿀 필요가 없습니다.

롬에서 `29 C0 4A 4A 4A 4A 4A` 를 찾자 이 둘과 전투 쪽 `21:FF50`(6번 밀어 0~3 을 만듦, 다른 것)이 나왔습니다. 그림을 그 자리에서 바꾸는 `03:D1FE` 는 `AND` 없이 `LDA [$00],Y` / `LSR` ×5 / `STA $08` 이었습니다. 레코드 `+2` 의 아래 6비트는 자료 뱅크이므로, 이 길에서는 뱅크 `20`~`3F` 의 bit5 가 `$08` bit0(OAM 타일 bit8)으로 갑니다. 원본 세트는 모두 뱅크 `0C`~`0F` 라 드러나지 않습니다.

## 2. 세트 팔레트 표

세 곳을 `JSL` 로 바꾸고, `--at` 에 루틴 둘과 256칸 표를 둡니다.

- 1F 루틴: `LDY #$02` / `LDX $0C`(세트) / `LDA 표,X`. 값이 `FF` 면 원래 명령을 그대로 하고, 아니면 `ASL` 해 `$01` 에 둡니다. 표를 처음 놓을 때 바꾸지 않은 세트는 모두 `FF` 라 레코드 팔레트를 그대로 씁니다. 나중에 `dq5spritewrite.py` 가 더하는 세트도 레코드를 따릅니다.
- 03 루틴: 세트 번호가 남아 있지 않아(`03:D206` 의 `PHA` 를 `D222` 에서 빼고, 그 자리를 `D23B` 의 `PHX` 가 덮음) `7E:1EC0` 의 그림 번호를 그림 번호 표로 다시 세트로 바꿉니다. 그림 번호 표는 실행 중에 `03:D202` 의 피연산자로 찾습니다(아래 「틀렸던 것들」). `dq5picturegrow.py` 를 먼저 넣든 나중에 넣든, 원본에서 만든 두 패치를 한 빌드에 넣든 늘린 그림 `18`·`A9` 의 세트 팔레트가 맞았습니다.

표를 세트 레코드가 아니라 세트 번호로 찾게 했으므로, `dq5spritewrite.py --sets-at` 이 세트 표와 레코드를 옮겨도 표는 그대로 맞습니다. 레코드 칸에 쓸 때만 원래처럼 세트 표 주소를 그대로 다시 써 겹침을 막습니다.

## 3. 맵 팔레트 줄 옮기기

`01:996A` 는 `PHK` / `PLB` 로 DB 를 01 로 두고 `01:9A12` 표를 `abs,X` 로 일곱 곳에서 읽습니다. 루틴을 통째로 옮기면 `JSL` 로 들어간 뱅크가 그대로 DB 가 되므로, 고칠 것은 피연산자 일곱, 루틴 안 `JMP` 둘, 끝 `RTS` 뿐입니다. `$1949` 도 `abs` 로 읽으므로 옮길 뱅크는 `00`~`3F` 여야 합니다.

옮기기 전에 롬 전체에서 이 루틴 안으로 들어오는 분기를 찾았습니다. `01:9954` 가 `LDA #$3B14` 로 다른 CGRAM 사본을 고른 뒤 `BRA $9976` 으로 루틴 중간에 들어갔습니다. 이 입구는 DB 를 부르는 `01:994A` 에 맡깁니다. 그래서 옮긴 자리에 이 입구도 두되 `PHK` / `PLB` 를 넣고, `01:9954` 도 `JSL` / `RTS` 로 바꿨습니다. `01:9FB2`·`03:A6DB` 가 `JSL` 로 부르는 `01:9960` 은 `JSR $996A`, `03:A74D` 가 부르는 `01:994A` 는 `JSR $9954` 라 그대로 둡니다.

## 4. 롬 코드로 확인

`check` 는 [`w65816.py`](../tools/w65816.py) 로 롬 코드를 그대로 돌립니다. 세트마다 `1F:CFA9`·`1F:D0DC`, 그림 번호마다 `03:D24D`, 실내 맵마다와 필드 세계 셋에서 `01:996A`·`01:9954` 를 원본·만든 롬 모두 돌려 예측과 견줍니다.

```
$ dq5objpalette.py rom/dq5.sfc check
OBJ 팔레트 8개, 맵 팔레트 36→36개, 세트 147개 검사 통과; 칸 목록 147세트·그림 바꾸기 169그림·맵 367곳을 롬 코드로 확인; 쓰기 0개
$ dq5objpalette.py rom/dq5.sfc check work/setpal/doc.json --at 3B:8000
OBJ 팔레트 8개, 맵 팔레트 36→38개, 세트 147개 검사 통과; 칸 목록 147세트·그림 바꾸기 169그림·맵 367곳을 롬 코드로 확인; 쓰기 7개
```

두 번째 문서는 세트 `04` → 5, `84` → 6, `82` → 2 와 새 항목 둘(02/06 줄 `0E`, 필드 세계 0 줄 `0D` 의 조건 항목), 기존 13번 항목의 색을 담았습니다. 단위 테스트는 새 루틴 둘을 해석기로 돌려 `$01`·`$08`·Y·X 를 보고, 가짜 롬에서 맵 루틴 옮기기의 피연산자와 거부, CLI 의 `--at` 없음 오류를 봅니다.

## 5. 게임에서

`dq5setpalettecheck.py` 는 [앞 검사](2026-10-27-51-objpalette.md)의 02/06 롬에 세트 `04`(6타일) → 5, `84`(8타일) → 6, 주인공 `82` → 7 을 주고, 팔레트 5·6·7 의 색, 02/06 의 새 줄 `0F`, 04/06 의 기존 13번 항목 색을 바꿉니다. 슬롯마다 그 세트 타일을 쓰는 OAM 의 팔레트를 셌습니다.

```
original-0206 f00780: CGRAM OBJ 줄 0~7 예측과 같음 8/8, OAM 묶음 4/4, 슬롯 세트의 OAM 팔레트 00 0×6, 04 1×6, 82 0×8, 84 0×16
edited-0206 f00780: CGRAM OBJ 줄 0~7 예측과 같음 8/8, OAM 묶음 4/4, 슬롯 세트의 OAM 팔레트 00 0×6, 04 5×6, 82 7×8, 84 6×16
edited-0406 f00780: CGRAM OBJ 줄 0~7 예측과 같음 8/8, OAM 묶음 1/1, 슬롯 세트의 OAM 팔레트 82 7×8
```

세 세트가 모두 표의 팔레트로 그려졌고, 표에 넣지 않은 세트 `00` 은 레코드의 팔레트 0 이었습니다. 02/06 의 CGRAM 줄 `0F` 는 새 항목의 색, 04/06 의 줄 `0B` 는 옮긴 표의 13번 항목 색이었습니다. 덤프 620·700·780프레임이 모두 같았습니다.

## 6. 맵마다 남는 줄과 VRAM

`dq5objsweep.py` 는 실내 맵 346곳에 들어가 걷는 동안 매 프레임 보이는 OAM 의 팔레트, 인물 슬롯, `$1995` 를 셉니다(`lua/dq5objsweep.lua`). 여섯 개를 함께 돌려 2분 반 걸렸습니다.

```
맵 346곳 중 346곳 도착, 못 간 곳 0:
인물 슬롯 최대 24(03/05), 맵에 나온 세트 종류(센 프레임 합집합) 최대 14(02/01)
OBJ 팔레트 4: OAM 에 보인 맵 7, 01:9A12 가 덮는 맵 5, 끝 CGRAM 이 04:96D6 과 다른 맵 18 (04/01 04/03 12/09 1B/00 2B/00 2B/02 31/0B)
OBJ 팔레트 5: OAM 에 보인 맵 0, 01:9A12 가 덮는 맵 0, 끝 CGRAM 이 04:96D6 과 다른 맵 12
OBJ 팔레트 6: OAM 에 보인 맵 0, 01:9A12 가 덮는 맵 0, 끝 CGRAM 이 04:96D6 과 다른 맵 9
OBJ 팔레트 7: OAM 에 보인 맵 1, 01:9A12 가 덮는 맵 3, 끝 CGRAM 이 04:96D6 과 다른 맵 11 (2A/00)
$1995 최대 1FE(19/00) → 탈것 180 까지 -126타일, 최소 090(00/08)
```

CGRAM 이 다른 맵을 들여다보니 04/00·12/02 등 8곳은 OBJ 팔레트 4~7 이 0~3 과 같은 색이었습니다. 원본 `04:96D6` 의 팔레트 4~7 은 색이 모두 0 입니다. 롬에서 `3A94` 를 피연산자로 쓰는 곳을 찾자 `12:8C43` 이 `7E:3A14` 를 `3A94` 로 베끼고, 이를 부르는 `12:8C9F` 가 색 연산을 켜고 `$1A0C` 를 `06` 으로 두었습니다. 맵마다 끝 WRAM 의 `$1A0C` 를 보니 이 8곳만 `06` 이었습니다. 색 연산은 OBJ 팔레트 4~7 에만 걸리므로, 반투명 인물을 그리는 장치로 보입니다. 이 맵들에서는 세트에 준 팔레트 4~7 의 색이 0~3 의 색으로 바뀝니다.

나머지는 03/02(`$1A0C` = `04`)와 2B/00·2B/02 의 회색 띠, 17/04 의 흰색, 맵 줄 항목이 있는 맵이었습니다. 346곳 중 322곳은 OBJ 팔레트 4~7 을 OAM 이 쓰지도 않고 색도 바뀌지 않았습니다. 팔레트 6 은 어느 맵의 OAM 에도 나오지 않았습니다.

인물 슬롯은 300곳이 6개 이하였고 맵에서 센 프레임 전체에 나온 세트 종류는 02/01·19/00·20/00 이 14개로 가장 많았습니다. OBJ 줄은 여덟뿐이므로, 한 맵에서 세트마다 다른 색을 줄 수 있는 것은 그 맵에서 남는 줄 수까지입니다. 세트에 줄 팔레트는 6·7·5 순서로 덜 겹치고, 필드 세계 0 에서는 낮밤 루틴이 3·4 를, 탈것 그림자가 5 를 씁니다.

`$1995` 는 21곳이 탈것 자리 `180` 을 넘었습니다. 실내에는 탈것 타일이 올라오지 않으므로 끝은 512타일입니다. 19/00 은 2타일, 가운데 값은 338타일이 남습니다.

## 틀렸던 것들

- 처음 훑기에서는 세 맵 모두 인물 슬롯이 24개이고 세트도 똑같이 나왔습니다. 슬롯 `00`~`1F` 를 모두 세었고, 맵 번호가 바뀐 직후의 프레임까지 세서 선실의 슬롯이 남아 있었던 것입니다. 다음 빈 슬롯 `$1983` 앞만 세고, 맵 번호가 바뀌고 60프레임 뒤부터 세도록 고쳤습니다.
- `$1A0C` 맵의 팔레트 4~7 을 덮는 곳을 쓰기 감시로 찾으려 했습니다. 04/00 에 서 있기만 한 실행에서는 `7E:3A94`~`3B13` 에 맵을 불러올 때의 DMA 말고는 쓰기가 없었고, `$1A0C` 도 0 이었습니다. 훑기는 걸어 다녔기 때문에 `06` 이 된 것입니다. 그래서 「이 맵에 들어가면」 이 아니라 「걷는 동안 `06` 이 된 맵」 으로 적었습니다.

- 처음에는 03 루틴이 그림 번호 표 주소를 품게 하고, `03:D202` 를 그대로 다시 써 `dq5picturegrow.py` 와 한 빌드에 넣지 못하게 막았습니다. 리뷰에서 순서를 바꾼 경우가 드러났습니다. 세트 팔레트를 먼저 넣고 그 롬에 그림 표를 옮기면, 루틴은 옛 `25:86D0` 을 읽어 그림 `18`(세트 `0A`)의 `$08` 이 `00` 이었고 두 도구의 `check` 는 모두 통과했습니다. 또 「그림 표를 옮긴 롬에서 돌린다」 로 만든 패치는 `03:D202` 의 `orig` 가 원래 롬과 달라 원본 빌드에 합칠 수 없었습니다. 이 도구의 `check`·`dump` 도 고정된 그림 수(169)와 `25:86D0` 을 써서 늘린 그림을 보지 않았습니다. 지금은 루틴이 피연산자를 실행 중에 읽고, `check`·`dump` 는 `dq5picturegrow.layout` 을 따릅니다.
- 첫 훑기의 「세트 종류」 는 인물 슬롯이 가장 많았던 프레임의 세트만 셌습니다. 맵에서 센 프레임 전체의 합집합으로 고쳤습니다.
