# 2026-10-30-24: 필드 블록 훅의 남은 3프레임 없애기와 DB·빛 칸·타일 한도 실측

[11비트 훅 줄이기](2026-10-30-18-block2k-low.md)가 남긴 넷을 했습니다. 블록을 늘린 롬이 필드를 3프레임 늦게 불러오던 것을 블록 번호 루틴의 몸통 전체를 바꾸는 빠른 훅으로 없앴고, 다른 장면의 DB, 칸을 바꾸는 장면, 세계 지도 화면을 늘린 롬에서 쟀습니다. 타일 1,024개로 블록 2,047개를 채운 지도도 게임에서 걸었습니다. 형식은 [쓰기 형식의 「필드 세계 지도」](../docs/dq5-build-format.md#필드-세계-지도)·[「필드 블록·입구 표」](../docs/dq5-build-format.md#필드-블록입구-표-dq5fieldtables1)와 [블록 훅 속도·빛 칸·세계 지도 실측](../docs/dq5-build-format.md#블록-훅-속도빛-칸세계-지도-실측)에 있습니다.

## 1. 늦어지는 몫 나누기

앞 일지처럼 `dq5warp.lua` 를 돌리며 프레임마다 `$7F`·`$BE` 를 적고, 둘 다 그대로인 프레임을 멈춘 구간으로 셌습니다. 같은 실행에서 `00:BBF7` 에 들어와 `00:BC46` 에 닿기까지의 마스터 클록(`emu.getState()` 의 `masterClock`)도 더했습니다. 롬은 원본, 블록 표 훅만 넣은 롬(블록을 늘리고 지도는 그대로), 9번째 비트 훅만 넣은 롬(평면은 모두 0), 두 시험 롬입니다.

```
                         한 번(마스터 클록)  세계 0     세계 1     세계 2     세계 2 첫걸음
원본                        1,901          462~492   453~483   451~481   822
블록 표 훅만                 2,031          462~493   453~484   451~481   822
9번째 비트 훅만              2,398          462~494   453~485   451~483   824
10비트 시험 롬               2,928          461~495   453~486   451~484   825
```

세계 0 에서 `00:BBF7` 1,090번이 모두 마지막 구간 안에 들었고, 31프레임 가운데 5.8프레임을 썼습니다. 그래서 칸마다 늘어난 사이클이 거의 그대로 프레임이 됩니다. 얼마까지 늘어도 되는지 보려고 `00:BC4E` 를 `JML` 로 빼서 `REP / STA` 뒤 `NOP` k 개를 두고 돌아오는 롬을 만들었습니다. k = 0(칸마다 66마스터 클록 더)은 세 세계 모두 원본과 같았고, k = 2(95)·4(124)는 세계 0 만 한 프레임 늦었습니다. 세계 0 의 여유가 칸마다 66~95마스터 클록뿐이라, 10번째 비트 평면 한 바이트를 긴 주소로 읽는 데(40)와 세계 고르기(48)만 해도 거의 다 씁니다.

## 2. 블록 표 훅 줄이기

블록 표 훅의 511 미만 갈래는 `JML` 로 들어가 `CMP #$01FF / BCS` 를 하고 원래 `STA $00` 뒤 `00:BC52` 로 돌아갔습니다. 들고 나는 `JML` 둘이 64마스터 클록입니다. 그 뒤의 원래 셈 `00:BC50`~`BC6C`(번호 × 5 + 칸)를 훅 안에서 더 짧게 하고 `00:BC6D` 로 돌아가게 바꿨습니다. 칸 번호는 `$90 & 1`·`$92 & 1` 을 따로 마스크해 `ORA` 하던 것을 `LDA $90 / LSR` 이 남긴 C 와 `LDA $92 / AND #1 / ROL` 로 모읍니다. 번호 × 4 와 `ROL` 이 넘치지 않아 `CLC` 도 없앴습니다.

블록만 늘린 롬의 한 번이 2,031 에서 1,926 이 되어(원본보다 25 더) 세 세계 모두 멈춘 구간과 첫걸음이 원본과 같아졌습니다.

## 3. 블록 번호 루틴 전체를 빠른 훅으로

9번째 비트 훅은 비트마다 평면 바이트를 읽고 `00:BCA0` 의 마스크로 `AND` 해 모읍니다. 10번째 비트 하나에 평면 읽기·저장·마스크·분기가 붙어 120마스터 클록 남짓이고, 11번째 비트면 두 배입니다. 위의 여유로는 어떻게 줄여도 들어가지 않습니다. 그래서 원래 루틴의 다른 곳에서 덜어 메우기로 하고, `00:BBF7` 의 `PHP` 뒤 `00:BBF8` 부터 몸통 전체를 빠른 훅으로 바꿨습니다.

- 10·11번째 비트를 세계마다 32KB 의 반 바이트 평면에 함께 둡니다. 칸 둘에 1바이트이고 짝수 칸은 아래 니블, 홀수 칸은 위 니블에 `(번호 >> 8) & 6` 을 둡니다. 인덱스가 칸 >> 1(0~7FFF)이라 뱅크 `8000` 에서 시작해 한 뱅크를 다 씁니다. 읽기 한 번에 `AND #$06`(홀수 칸은 `LSR` 넷 뒤)이면 두 비트가 번호 윗바이트 자리에 섭니다. 9번째 비트만 원래처럼 `7E:E000` 에서 읽습니다(`00:CF50` 이 바꿈).
- 칸의 비트 자리(`$90 >> 1 & 7`)는 `$90` 아랫바이트로 바로 고르는 256바이트 마스크 표로 읽어 `AND #7 / TAY / TYX` 를 덜었습니다. 범위 검사 둘은 `LDA $90 / ORA $92 / CMP #$0200` 한 번입니다.
- 번호가 511 미만이면 2절과 같은 셈 뒤 `PEA $BC45` 로 `00:BC6D` 에 들어가 원래 표를 읽고, `00:BC9B` 의 `RTS` 가 `00:BC46`(`PLP / RTS`)으로 옵니다. 511 이상은 옮긴 표에서 `$94`~`$97` 을 채우고 `00:BC46` 으로 `JML` 합니다. 원래 루틴의 `JSR $BC4E`·`PHB / PHK / PLB` 가 빠지고, 칸 타일의 9·10번째 비트는 `칸 × 256 + 상위 비트 바이트` 로 고르는 1,024바이트 표에서 한 번에 읽습니다.
- 세계는 원래 훅처럼 세계 0 만 분기 없이 잇고 나머지는 `JMP` 로 합칩니다. 칸이 홀수인지를 C 에 둔 채 세계를 가르므로 `CMP` 대신 `DEC / BEQ` 로 가릅니다.

```
                         한 번(마스터 클록)  세계 0     세계 1     세계 2     세계 2 첫걸음
10비트·11비트 시험 롬(지금)  1,931          461~492   453~483   451~481   822
```

두 시험 롬 모두 멈춘 구간의 끝과 첫걸음이 원본과 같아졌습니다. `dq5blockgrowcheck.py` 는 10비트 13건, 11비트 21건이 통과했고 900·700프레임 VRAM 필드 타일이 모두 원본 게임과 같았습니다. 빠른 훅이 있으면 9번째 비트 훅(`00:BC33`·`00:BE06`)은 한 번도 실행되지 않았습니다. 디코더가 그 훅 머리에서 평면 자리를 읽으므로 그대로 둡니다.

세계 0 의 앞 구간은 441~460 이 441~459 로 한 프레임 일찍 끝납니다. 원래 지도를 `dq5fieldwrite.py dump` 한 그대로 다시 `patch` 한 롬만 넣어도 같아서, 훅이 아니라 다시 싼 RLE 때문입니다.

## 4. 세계 지도 화면도

たびびとのちず(`B6`)를 쓰면 `03:CAC2` 가 점마다 `00:BDC5` 를 15,360번 부릅니다. 9번째 비트 훅 롬은 점을 다 만드는 프레임이 원본 1,239 에서 1,269 로 30프레임 늦었습니다. `00:BDC5` 도 같은 바이트(`00:BDC9` 의 `LDA $90 / CMP #$0200`)에서 빠른 훅으로 들어가 번호를 들고 `00:BE14`(`PLB / PLP / RTS`)로 돌아가게 했습니다. 원래 루틴은 `00:BDE1` 에서 DB 를 `00` 으로 두는데 빠른 훅은 그러지 않으므로 세계를 `$7E1949` 긴 주소로 읽습니다. 한 번이 915 → 1,086마스터 클록이고, 점을 다 만드는 프레임은 1,254(세계 1 은 원본 1,231, 지금 1,246)입니다.

## 5. 블록 번호를 읽을 때의 DB

`00:BBF7`·`00:BDC5` 에 들어올 때와 `00:BCA8` 을 부르는 여섯 자리의 DB 를 실행 콜백으로 셌습니다. 탈것 장면은 [필드 형식의 「탈것」](../docs/dq5-field-format.md#탈것-01bc10)의 법으로 만들었습니다.

```
장면                                         00:BBF7    01:8192   2B:81E9·81F6  00:E32E·C82C·C83B
세계 0·1·2 걷기·배 오르기·배·융단·天空城·용·마차   00·7E      00·7E     7E            -
마을 입구 (414,46)·(236,56) 에 들어섬           00·7E      00        7E            7E
```

`00:E32E` 는 `00:C797` 이 DB 를 `7E` 로 둔 채, 주인공이 선 칸의 속성이 `45` 이면 그 아래 칸을 볼 때 돕니다. `00:C82C`·`C83B` 는 이어서 마을 입구에 들어설 때 돕니다. `00:BDC5` 는 융단 장면에서 DB `01` 로도 들어왔지만 원래 루틴이 `00:BDE1` 에서 DB 를 바꾸고, 빠른 훅은 긴 주소로 읽습니다. 그래서 `00:BBF7` 쪽의 짧은 `$1949` 는 재 본 장면에서 모두 WRAM 을 읽어, 바꾸지 않았습니다.

## 6. 칸을 바꾸는 장면

`00:CF50` 을 부르는 넷과 [상자 일지](2026-10-29-05-chestgrow.md)의 밤에 빛나는 풀을 원본과 두 시험 롬에서 돌렸습니다. 600~2,000프레임 사이 덤프마다 BG 타일맵·필드 타일·바뀌는 칸 다섯의 `7F` 바이트와 9번째 비트·지형 `$1AA0` 이 모두 원본 게임과 같았습니다.

- 밤 `01:A025`(풀이 `A7`), 낮으로 되돌림 `01:A02B`(`CA`, 다시 그리기 `00:CFD0` → `00:BC48` 네 번), 풀을 집음 `12:EFCE`(`CA`, 다시 그리기).
- `05:EF2C`: 필드에 들어설 때 `01:9FEF` 의 `BRK 0B 40 52`(`21E2.6`)가 켜져 있으면 `05:EF00` 이 블록 (E2,75)~(E2,77) 을 `02` 로 세 번 바꿉니다. `FIELD=452,242 SET="21E2|40"`.
- `03:BB49`: 수문 (34,250) 에서 위를 보고 とびら 를 고르면 `01:DA0A` 가 부릅니다. ビアンカ 가 일행에 있어야 열리고(`BRK 8A DB`, A = 3), 없으면 「水門は ビクともしない！」 입니다. 470프레임에 일행 레코드 1 을 인물 표의 ビアンカ 로 채우고 はい 를 고르자 블록 (11,7C) 이 `71` 로 바뀌고 다시 그려졌습니다.
- 수문을 연 뒤 필드에 들어서면 `01:9FE5` 가 `$1948` ≠ 0·`21BA.1` 일 때 `03:BB6C` 를 부릅니다. 이 루틴은 `00:CF50` 을 거치지 않고 `LDA #$71 / STA $7F7C11` 과 `7E:EF82` bit6 끄기로 칸을 직접 씁니다. [블록 1,024개 일지](2026-10-30-12-fieldgfx3.md)가 블록 번호를 쓰는 곳을 `7F0000`·`7EE000` 의 긴 주소로 찾았기 때문에 걸리지 않았던 곳입니다. 칸이 `03:BB49` 와 같아 지도 쓰기의 512 미만 제한으로 함께 막힙니다. `SET="21BA|02;1948=02"` 로 들어서자 같은 칸이 원본 게임과 같았습니다.

세계 지도 화면은 세계 0 (341,56)·세계 1 (50,28) 에서 VRAM `0000`~`7FFF`(모드 7 타일맵과 점) 16,384워드가 same 롬과 원본 게임에서 모두 같았습니다. swap 롬(새 블록 지형 `0D`)은 점 15,360개가 모두 `2D` 였고, 세계 0 에서 하나만 `23`(블록 512 미만으로 둔 `00:CF50` 칸) 이었습니다.

## 7. 타일 1,024개로 블록 2,047개

원본 블록 511개는 타일 449개를 쓰고, 아래층 네 칸 묶음은 368가지, 위층은 165가지(비어 있는 것 포함)입니다. 위층이 빈 블록(땅)이 250개, 비지 않은 위층(물체)이 164가지라 땅과 물체의 짝만 41,000가지이고 그 가운데 40,872가지는 원본에 없습니다. 새 그림 없이 짝을 바꾸는 것만으로 번호 한도를 넘습니다.

`dq5fieldgfxwrite` 로 타일을 1,024개로 늘리고(새 타일 512개 = 원래 타일 XOR FF, 팔레트 n^1, 속성 그대로) 블록을 이렇게 두었습니다.

- 1024+b: 블록 b 의 아래층을 새 타일로, 위층 그대로(색만 바꾼 땅 위에 같은 물체).
- 511~1023·1535~2046: 땅 × 물체 가운데 원본에 없는 짝.

블록 2,047개(두 층이 서로 다른 짝 2,011개)가 타일 727개(원래 449개 + 새 278개)를 썼습니다. 세계 0 지도는 주인공 블록 (170,28) 둘레 ±4 블록을 1024+b 로, 둘레 64×40 블록의 나머지 칸에 남은 번호를 차례로 두어 서로 다른 블록 1,976개(새 번호 1,536개 모두)를 썼습니다.

화면은 디코더(`dq5field.block_tiles`·`tile_word`)로 칸마다 두 층의 타일맵 워드를 셈해 VRAM 과 견주었습니다. 타일맵 열·줄을 칸 좌표에 맞추는 어긋남은 원본 롬의 같은 장면에서 찾았고(아래층은 BG2, 위층은 BG1, 위층이 없는 칸은 타일 0 워드), 원본 롬도 같은 방법으로 24×20칸이 모두 맞았습니다.

```
장면                                  덤프 프레임       보이는 블록           두 층 워드
(341,56) 에서 네 방향으로 걸음          700·1000·1150   44~75개, 모두 1024 이상  480/480칸씩
(340,22) 에 섬                         700·1000·1150   97개, 96개가 511~1023    480/480칸씩
```

주인공 칸은 블록 1032 였고, 걸어서 (339,53)·(338,56) 을 지났습니다. 늘린 타일 자리(VRAM `8000`~`BFFF`)는 움직이는 타일 10개를 빼고 502개가 원래 타일 XOR FF 와 같았습니다. 새 블록마다 새 그림을 그리면 원본 비율(블록 511개에 타일 449개)로 1,165개쯤에서 타일이 먼저 바닥나지만, 층 묶음을 다시 쓰면 번호 한도 2,047개까지 채울 수 있습니다.

이 롬은 필드 불러오기가 461~496 으로 4프레임 늦었습니다. 블록은 늘리지 않고 타일만 1,024개로 늘린 롬도 462~499 로 7프레임 늦고 `00:BBF7` 한 번이 2,675마스터 클록이어서, 타일 늘리기의 훅(`00:BC80`·`BC8D` 의 `JSL` 과 니블 훅) 몫입니다.

## 틀렸던 것들

- 앞 일지는 늦음이 사이클에 비례하지 않고 불러오기 단계가 프레임 경계를 넘느냐로 정해진다고 보았습니다. 마지막 구간에서 `00:BBF7` 이 5.8프레임을 쓰고 세계 0 의 여유가 칸마다 66~95마스터 클록이라, 훅을 조금 줄여서는 경계를 넘지 못했던 것입니다. 경계가 있는 것은 맞지만 남은 3프레임은 늘어난 사이클(칸마다 1,000마스터 클록 남짓)이 그대로 쌓인 것이었습니다.
- 빠른 훅을 처음 넣은 11비트 롬은 서 있을 때는 화면이 같았지만 걷자 필드 좌표가 (9506,8738) 이 되며 멈췄습니다. 9번째 비트 훅 뒤에 빠른 훅을 붙인 뒤에 둘째 몸통 자리(`bit11_entries`)를 셈해, `00:BE06` 의 `JML` 이 엉뚱한 곳을 가리켰습니다. 자리를 붙이기 전에 셈하게 고쳤습니다.

## 남은 것

- 타일을 512개 넘게 늘린 롬의 필드 불러오기 7프레임(타일 늘리기 훅 몫). 블록 번호 쪽 빠른 훅처럼 `00:BC80`·`BC8D`·니블 훅을 덜 수 있는지는 보지 않았습니다.
- 세계 지도 화면의 점은 여전히 원본보다 15프레임 늦게 다 만들어집니다.
- 빠른 훅이 있는 롬은 1비트 평면과 9번째 비트 훅을 디코더용으로만 둡니다(세계마다 8KB·16KB 와 훅 400바이트). 디코더가 반 바이트 평면을 읽게 하면 뺄 수 있습니다.
- DB 는 위 장면에서만 쟀습니다. 이벤트가 인물을 움직이며 타일 속성을 묻는 장면 등 다른 곳은 재지 않았습니다.
- 블록 2,047개 지도에서 걸은 것은 주인공 둘레의 1024+b 블록뿐입니다. 땅 × 물체 블록 위의 걸음·충돌은 속성이 원래 위층 타일 그대로라 따로 걷지 않았습니다.
