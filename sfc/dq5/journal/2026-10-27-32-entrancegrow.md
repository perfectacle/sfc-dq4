# 2026-10-27-32: 필드 입구 표 옮기기와 늘리기

DQ4 의 마을·동굴은 DQ5 보다 많아서, 필드 입구 표에 항목을 더할 수 있어야 합니다. 입구 표 둘을 새 길이로 다른 자리에 옮기고, 표를 읽는 곳을 모두 바꾸는 쓰기를 `dq5fieldtables.py` 에 더했습니다. 새 입구를 걸어 새 맵에 들어가는 것을 원래 롬과 견줘 확인했습니다. 결과는 [쓰기 형식](../docs/dq5-build-format.md#입구-표-옮기기늘리기)에 있습니다.

## 1. 표를 읽는 곳 세기

입구 표는 일반 `04:FD97`(47항목)과 보조 `04:FE83`(14항목) 두 개이고, 항목은 `[그룹][X 16비트][Y 16비트]` 5바이트, 끝은 `FF` 입니다. 롬 전체에서 두 표의 주소와 그 +1~+4 를 24비트로 찾았습니다.

```text
일반 표  1E:E56C·E581·E58A  2A:F24F·F259·F263·F26B  2A:F42D·F458·F45E      LDA/CMP long,X
보조 표  1E:E59B·E5AC·E5B5  2A:F443·F468·F46E       2A:FE11·FE1B·FE25·FE32
포인터   03:C880 = 97 FD 04 83 FE 04   (03:C811 이 LDY $C880,X / LDA $C882,X 로 읽음)
```

긴 주소 읽기가 20곳이고, 마지막 줄은 명령 사이에 끼인 6바이트 자료입니다. 바로 앞이 `RTS` 라 처음에는 우연히 같은 바이트로 보았습니다. `03:C826`·`03:C82B` 가 이 자리를 X 로 읽고 `[$00],Y` 로 표를 훑어 지금 그룹의 필드 자리를 `$1EC4`·`$1EC6` 에 둡니다. 세계 지도에서 주인공 자리를 찍는 데 쓰는 것으로 보입니다.

두 표의 주소와 +1~+4 를 담은 다른 4곳(`0C:F418`·`0D:9E6B`·`04:8493`·`27:C477`)은 앞 바이트가 긴 주소 읽기가 아니었습니다. 16비트로 `FD97`·`FE83` 을 읽는 7곳 가운데 `01:DE7F`·`01:DEC0`·`01:F496` 은 니블(0~15)을 X 로 써서 뱅크 01 의 다른 표를 읽는 명령이었고, 나머지는 자료 한가운데였습니다.

읽기는 X 를 0 부터 5씩 올리고 항목 수를 세는 상수가 없습니다. 긴 주소라 데이터 뱅크도 보지 않으므로, 표는 한 뱅크 안이면 어디든 둘 수 있습니다. 대부분의 루프는 `FF` 에서 멈추지만, ルーラ 의 보조 표 루프(`1E:E59B`~`E5A8`)는 `FF` 를 보지 않고 그룹을 찾을 때까지 돕니다. 원래 롬에서는 ルーラ 행선지 그룹 22개(`25:85D5`)가 두 표 가운데 하나에 늘 있어서 문제가 없었습니다. 옮길 때 이 22개가 새 표에 모두 있는지 검사합니다.

## 2. 쓰기

`entrance_tables` 에 표 전체를 적고 `--entrances-at` 으로 자리를 주면, `[일반][FF][보조][FF]` 를 그 자리에 쓰고 20곳의 주소와 포인터 둘을 바꿉니다. 바꾸기 전에 20곳이 원래 명령(`BF`·`DF` + 원래 주소)인지 보고, 다른 도구가 먼저 고쳤으면 거부합니다. 옮긴 표에는 원래 롬 안의 자리라도 `orig` 를 붙이지 않습니다. 처음에는 원래 바이트를 `orig` 로 붙였는데, 그러면 빌더가 빈 자리 검사를 건너뛰어 `01:8000` 같은 코드 자리도 덮을 수 있었습니다. 원래 자리의 두 표는 그대로 남고 더는 읽히지 않습니다. 기본 자리는 두지 않았습니다. 원래 롬의 빈 자리와 늘린 뱅크는 상점 목록 옮기기나 DQ4 타이틀·메뉴도 쓰기 때문에, 쓰는 사람이 겹치지 않는 곳을 고르고 빌더가 겹침을 거부합니다.

## 3. 어느 표에 새 입구를 둘까

처음에는 일반 표 끝에 (345,56) → 그룹 `02` 를 더했습니다. 필드 341,56 세이브스테이트에서 오른쪽으로 걸었지만 들어가지 않았습니다. 원래 롬에서 두 표의 읽기를 모두 감시하자, 걷는 동안 읽힌 것은 보조 표(`2A:FE15`·`FE1F`) 2,322번뿐이고 일반 표는 0번이었습니다. 일반 표로 들어가는 `2A:F247` 은 `00:C7DD` → `2A:F230` 으로 불리는데, 그냥 걷는 칸에서는 불리지 않았습니다. 보조 표를 보는 `2A:FDCB` 는 지형을 보지 않고 좌표만 견주므로 새 입구를 보조 표에 두었습니다.

## 4. 원래 롬과 견주기

두 표를 `68:8000` 으로 옮기고 보조 표에 (345,56) → `02` 를 더한 롬을 만들었습니다.

```text
필드 341,56 에서 오른쪽으로 40프레임
  원래 롬  필드 346,56 ($BE = 00), 04:FE83~ 를 읽음
  고친 롬  345,56 에서 02/00 ($BE = 80), 04:FE83~ 은 읽지 않고 68:80EC~ 를 읽음
01/00 에서 필드로 나오기(장면 이동 도구가 원래 자리 04:FDC9 의 그룹 01 입구를 341,56 으로 덮음)
  원래 롬  341,56
  고친 롬  331,67 (옮긴 표의 그룹 01 입구 그대로)
```

나오는 자리는 일반 표를 읽으므로, 원래 자리를 덮어도 고친 롬이 옮긴 표만 읽는 것을 이 장면으로 봅니다. `dq5entrancecheck.py` 가 이 4회 실행과 단언을 다시 돌립니다.

```sh
MESENCE=… uv run --locked python sfc/dq5/tools/dq5entrancecheck.py rom/dq5.sfc \
  --state work/state/ship.mss --field-state work/state/field-free.mss
```

## 틀렸던 것들

옮긴 표에 `orig` 를 붙이면 원래 롬 어디에나 쓸 수 있어, 리뷰에서 코드 자리를 덮는 경우가 나왔습니다. `orig` 를 빼서 빌더의 빈 자리 검사를 받게 했습니다. 처음에는 모든 루프가 `FF` 에서 멈춘다고 적었는데, ルーラ 의 보조 표 루프는 그렇지 않았습니다.

일반 표 끝에 둔 입구를 걸어서 밟으면 들어갈 줄 알았습니다. 걷는 동안 입구를 보는 것은 보조 표였습니다. `03:C880` 의 6바이트도 `RTS` 바로 뒤라 처음에는 우연히 같은 바이트로 보았지만, 실제로 읽는 포인터 표였습니다.

## 남은 것

일반 표로 들어가기(`2A:F24F`~`F26B`), 보조 표의 나올 자리(`2A:F443`·`F468`·`F46E`), ルーラ 행선지(`1E:E56C`~), 세계 지도(`03:C880`)는 주소만 바꿨고 게임에서는 보지 않았습니다. `2A:F247` 이 어떤 칸에서 불리는지 확인해야 일반 표에 더한 입구가 언제 쓰이는지 알 수 있습니다. 블록 표와 도착 표는 늘리지 않았습니다. 블록 표는 블록 번호를 읽는 `00:BC4E` 가 번호를 얼마까지 받는지 모르고, 도착 표는 새 맵 그룹을 만드는 다른 표들과 함께 늘려야 합니다.
