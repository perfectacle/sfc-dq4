# 2026-10-30-08: 다시 불러오기 실행 기록·마법 융단 검사, 빌드한 롬의 블록 한도, 그림 표 순서 합성 시험

[필드 타일 늘리기](2026-10-30-07-gfxlimit.md)와 [세트 팔레트 표](2026-10-30-06-setpal.md)의 검사에 빈틈이 다섯 군데 있었습니다. 다시 불러오기 시험은 아무 일도 일어나지 않아도 통과했고, 마법 융단은 검사 도구로 다시 확인할 수 없었습니다. 블록 표는 빌드한 롬에서 다시 검사하지 않았고, 그림 표 순서 시험은 롬이 있어야 돌았습니다. 그림 표를 읽는 루틴의 뱅크 제약도 적혀 있지 않았습니다. 다섯 군데를 모두 메웠습니다. 결과는 [쓰기 형식의 실측](../docs/dq5-build-format.md#필드-타일세계-0-벌실내-세트-늘리기-실측)과 [필드 그림](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)에 있습니다.

## 1. 다시 불러오기 시험에 실행 기록

`dq5gfxlimitcheck.py` 의 キメラのつばさ·ルーラ 사례는 앞뒤 세 프레임의 VRAM 이 늘린 타일과 같은지만 보았습니다. 물건이나 주문이 실패해 필드를 다시 불러오지 않아도 VRAM 은 그대로라 통과합니다. 다시 그리기 시험처럼 `lua/dq5vramwipe.lua` 를 앞에 붙이고 `EXECLOG='01A4A7'` 로 실행 프레임을 적게 했습니다. 이 사례는 지우지 않으므로 `WIPEF` 를 주지 않으면 지우지 않게 바꿨습니다. 검사는 첫 덤프와 마지막 덤프 사이에 `01:A4A7` 이 돌았어야 통과합니다.

```
reload-chimera  frames 900,1000,1300  reloaded_at [960]
reload-rula     frames 1000,1100,1300 reloaded_at [1047]
```

대조로 첫 칸을 `00` 으로 두고 같은 입력을 넣는 사례(`reload-empty`)도 넣었습니다. 쓸 물건이 없어 필드를 다시 불러오지 않습니다. 이 사례에 「다시 불러옴」 검사를 하면 「900~1300프레임에 01:A4A7 이 돌지 않음」으로 실패해야 통과합니다. 실행 기록에 잘린 줄이 있으면 따로 실패합니다.

## 2. 마법 융단

앞 일지에는 마법 융단 장면을 확인했다고 적었지만, 그 확인을 검사 도구로 다시 할 수 없었습니다. [핸드오프](../handoff.md)의 요령대로 (310,60) 에서 첫 칸에 `CC` 를 넣고 どうぐ → つかう 로 융단을 폈습니다. 그 뒤 300프레임을 기다렸다가 융단에 탄 채 왼쪽·위·오른쪽으로 32프레임씩 걸었습니다. 처음에는 덤프를 900·1300·1600프레임에 두었습니다. 그런데 900프레임에 이미 `$1954` = `80` 이었고, 입력이 1,545프레임에 끝나 1600프레임 덤프가 없었습니다. 그래서 펴기 전·편 뒤·걸은 뒤인 700·1100·1500프레임으로 옮겼습니다.

```
reload-carpet  $1954 00 → 80  field 310,60 -> field 312,56 moved=yes  reloaded_at []
```

세 프레임 모두 늘린 타일 512개가 VRAM 워드 `4000`~ 과 같았습니다. 융단은 필드를 다시 불러오지 않았고, `01:A4A7` 기록이 있으면 실패하게 했습니다. 검사 도구 전체는 23건이 통과했습니다.

## 3. 빌드한 롬에서 블록 한도

`dq5fieldtables.py patch` 는 입력 롬의 세계 타일 수로 블록 칸 타일을 막고, `dq5fieldgfxwrite.py patch` 는 입력 롬의 블록 표로 막습니다. 둘 다 패치를 만들 때만 검사합니다. 그래서 블록 패치를 만든 뒤 그림 쪽에서 세계 타일 수를 줄여 다시 빌드하면 어느 도구도 이를 다시 보지 않습니다. 이제 `dq5fieldtables.py check` 가 롬의 블록 표를 모두 읽고 타일이 가장 적은 세계의 타일 수와 견줘, 넘는 칸이 있으면 실패합니다.

검사 도구가 만든 tiles 롬(세 세계 1,024개)은 통과했습니다. 같은 블록 패치에 세계 1 만 600개로 줄인 그림 패치를 넣어 빌드한 롬은 실패했습니다.

```
블록 칸 960개가 타일이 가장 적은 세계의 타일 수(600개)를 넘음(처음: 블록 1 upper 타일 878). 그림 쪽 타일 수를 바꿨으면 dq5fieldtables 패치를 다시 만들 것
```

롬 없이 도는 단위 시험도 더했습니다. 가짜 롬에 타일 늘리기 훅과 세계별 타일 수 표를 두고 블록 하나를 타일 700 으로 놓아, 세계 1 이 812개면 통과하고 600개면 실패하는지 봅니다.

## 4. 그림 표 순서를 롬 없이

세트 팔레트 표와 `dq5picturegrow.py` 를 어느 순서로 넣어도 `03:D24D` 루틴이 늘린 그림 표를 보는지는, 롬이 있어야 도는 시험만 확인했습니다. 롬이 없는 CI 에서는 건너뜁니다. 그래서 두 도구가 보는 자리만 채운 합성 롬을 만들었습니다. 원래 그림 표에서는 그림 29 가 세트 84(표의 팔레트 6)입니다. 그림 패치로 29 를 세트 04(레코드의 팔레트 1)로 바꾸고 새 그림 A9 를 세트 84 로 더했습니다. 세 순서(세트 팔레트 먼저, 그림 먼저, 둘 다 원래 롬에서 만들어 한 롬에)마다 루틴을 해석기로 돌렸습니다. 셋 모두 29 → 팔레트 1, A9 → 6 이 나왔고, `03:D202` 의 피연산자는 옮긴 표를 가리켰습니다.

## 5. 그림 표 루틴의 16비트 덧셈

이 루틴은 `03:D202` 의 표 주소에 그림 번호를 16비트 `ADC` 로 더해 X 로 씁니다. 원래 명령 `LDA long,X` 는 뱅크를 넘어 읽지만, 이 덧셈은 FFFF 를 넘으면 올림을 잃습니다. 원래 표 `25:86D0` 은 `+ FF` 까지 뱅크 안입니다. `dq5picturegrow.py` 는 그림 표 뒤에 물체 표 256바이트를 붙이고, `--at` 에서 이 묶음이 뱅크를 넘으면 거부합니다. 그래서 옮긴 표도 `+ FF` 까지 뱅크 안이므로 따로 거부하는 검사를 더하지 않았습니다. 대신 `swap_routine` 에 이 제약을 주석으로 적었습니다.
