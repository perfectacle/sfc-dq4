# 2026-10-30-14: 필드 블록 2,048개

[필드 블록 1,024개](2026-10-30-12-fieldgfx3.md)가 남긴 「블록 11비트 이상」을 했습니다. 필드 블록 번호를 11비트로 넓혀 2,048개까지 씁니다. 쓰기 형식은 [필드 세계 지도](../docs/dq5-build-format.md#필드-세계-지도)·[필드 블록 표](../docs/dq5-build-format.md#필드-블록입구-표-dq5fieldtables1)에 있고, 구조는 [필드 형식 「블록 512개 넘기기」](../docs/dq5-field-format.md#블록-512개-넘기기)에 있습니다.

## 1. 늘릴 만한가

먼저 블록 표·지형 표·타일 수가 11비트를 막는지 봤습니다.

- 블록 번호를 받는 곳은 `00:BC4E` 훅과 지형 `03:CB1B` 둘입니다. 둘 다 16비트로 셈합니다. 블록 훅은 `CMP #$01FF`·`SBC #$01FF` 뒤 5를 곱하므로 2,047 이면 7,680 으로 16비트 안입니다. 지형은 `LSR A / TAX` 를 16비트 X 로 하므로 번호 >> 1 이 1,023 까지 갑니다.
- 블록 2,047개면 옮긴 표 둘이 (2,047 − 511) × 5 × 2 = 15,360바이트, 지형 표가 1,024바이트, 훅까지 16.5KB 남짓입니다. 한 뱅크(32KB)에 들어갑니다.
- 타일은 1,024개가 한도입니다. 블록은 아래층·위층 타일 넷씩을 묶은 것이라, 블록 수가 타일 수를 넘어도 됩니다. 원본 블록 511개는 타일 449개를 씁니다. 아래층 네 칸 묶음은 368가지, 위층은 165가지이고 그 짝이 505가지입니다. 원본의 비율이면 타일 1,024개에 블록 1,100개쯤이고, 2,048개를 다 채우려면 아래층·위층 묶음을 더 많이 다시 써야 합니다. 같은 땅 위에 다른 것을 얹은 블록이 그런 경우입니다. 그래서 늘린 몫은 쓸 수 있지만, 타일이 먼저 바닥나는 지도도 있습니다.

## 2. 평면을 하나 더 두나, 칸마다 2비트로 넓히나

10번째 비트는 WRAM 에 자리가 없어 롬의 8KB 평면으로 두었습니다([앞 일지](2026-10-30-12-fieldgfx3.md) 2절). 11번째 비트도 칸마다 1비트면 세계마다 8KB 입니다. 남은 WRAM `7E:D400`~`DFFF` 3KB 에는 들어가지 않으므로 이것도 롬에 둡니다. 롬에 두면 VRAM·WRAM 은 쓰지 않습니다.

롬 안에서는 두 방법의 크기가 같습니다(세계마다 16KB). 평면을 따로 두는 쪽을 골랐습니다. 10번째 비트 평면의 꼴이 그대로이고, 11번째 비트를 쓰지 않는 세계는 평면을 두지 않아도 됩니다. 칸마다 2비트로 넓히면 10번째 비트만 쓰는 세계도 16KB 를 씁니다.

훅 머리는 `[세계 0·1·2 의 10번째 비트 평면][세계 0·1·2 의 11번째 비트 평면]` 18바이트입니다. 10번째 비트만 읽던 훅은 머리가 9바이트이고, 둘은 첫 `BRA` 의 거리(`12`·`09`)로 가릅니다. 디코더 `dq5field.bit9_planes` 는 두 꼴을 모두 읽습니다.

## 3. 세 바이트를 스택에 쌓는 훅

10비트 훅은 평면 바이트를 A 에 받은 뒤 `CMP #1`·`PHP`·`ROL` 로 비트 둘을 모았습니다. 비트가 셋이면 바이트 셋을 한꺼번에 들고 있어야 하는데, A 의 윗바이트에는 번호 하위 8비트가 있어 쓸 수 없습니다. 그래서 훅은 들어오자마자 `7E:E000` 바이트를 쌓고, 세계 갈래에서 10번째·11번째 비트 평면 바이트를 차례로 쌓습니다. 그 뒤 `SEP #$10 / TYX` 로 칸의 비트 자리를 X 에 두고, 위에서부터 꺼냅니다.

```
PLA / AND $00BCA0,X / CMP #$01   ; C = 그 비트
TYA / ROL A / TAY                ; Y 에 모음(M·X 8비트라 A 윗바이트는 그대로)
… 세 번(11번째, 10번째, 9번째 비트)
TXY / XBA / RTL                  ; Y 를 원래처럼 칸의 비트 자리로
```

나갈 때 A 는 원래 루틴의 `XBA` 뒤와 같고, X·Y 는 원래처럼 칸의 비트 자리입니다. 해석기(`w65816`)로 세계 0·1·2·3 과 비트 조합 여섯을 돌려 A·X·Y·S 를 확인했습니다.

## 4. 게임에서 확인

`dq5blockgrowcheck.py --bits 11` 로 21건이 통과했습니다. 시험 롬은 원본에서 만듭니다. 블록 511~2,046 을 더하고, 블록 1024+b 와 1536+b 는 블록 b 를 따릅니다. 지도의 칸 b 는 칸 좌표 x+y 가 짝수면 b+1024(11번째 비트만), 홀수면 b+1536(10·11번째 비트)으로 바꿉니다. `00:CF50` 이 바꾸는 칸만 그대로 둡니다. 표는 [실측](../docs/dq5-build-format.md#블록-2048개-실측)에 있습니다.

- same 롬은 세계 0 (341,56)·세계 1·2 (50,28) 에 선 900프레임과 세 세계의 걷기 앞 700프레임에 BG1·2 타일맵 4,096워드가 원본 게임과 같았습니다. 주인공 칸 블록은 1032·1539·1960 입니다.
- swap 롬(새 블록의 왼쪽·오른쪽 칸을 맞바꿈, 지형 `0D`)은 세 세계 모두 채운 칸이 원본 게임의 블록마다 좌우를 바꾼 워드와 같았습니다.
- 걷기: 세계 0 은 (341,56) 에서 네 방향, 세계 1 은 (50,28) 에서 네 방향, 세계 2 는 바다 (62,64) 에서 왼쪽으로 해안까지 밀었습니다. 같은 자리 (340,56)·(46,29)·(52,64) 에 섰고, 지형은 same 이 원본 게임과 같고 swap 은 `0D` 였습니다. 선 칸의 블록은 1032·1730·1314 입니다. 세계 2 의 해안에서 멈춘 것은 1,024 이상 번호의 뭍 블록 충돌을 읽었다는 뜻입니다.
- 새 블록의 아래층만, 또는 위층만 속성 `80` 타일로 바꾼 두 롬은 세 세계 모두 한 칸도 걷지 못했습니다.

10비트 시험(`--bits` 없이)도 다시 돌려 13건이 통과했습니다.

## 틀렸던 것들

- 처음에는 11번째 비트가 없는 지도에도 늘 11비트 훅을 냈습니다. 그러자 10비트 시험이 통과는 했지만, 세계 0 의 VRAM 필드 타일이 원본 게임과 달라졌습니다. 다른 타일은 움직이는 타일 10개(4·5·20·21·454~459)뿐이었습니다. 같은 시험을 고치기 전 도구로 돌리면 같았습니다. 해석기로 세니 훅 명령이 22개에서 35개로 늘어 있었습니다. 지금은 11번째 비트 평면이 없으면 10비트 훅을 그대로 냅니다. 10비트 시험의 VRAM 필드 타일은 다시 원본 게임과 같아졌습니다.
- 세계 2 걷기는 처음에 세계 1 과 같이 (50,28) 에서 했습니다. 원본 게임도 한 칸도 움직이지 않았습니다. 세이브스테이트가 배를 탄 상태이고 그 자리는 뭍입니다. 바다 블록 08 이 모인 (62,64) 로 옮겼습니다.
- (62,64) 에서 왼쪽·위로 32프레임씩 걷자 원본 게임은 (59,60), 블록을 늘린 롬은 (60,60) 이었습니다. 지나는 칸의 블록을 디코더로 견주니 두 롬의 타일·지형이 모두 같았습니다. 매 프레임 자리를 찍으니 늘린 롬이 한 걸음(8프레임) 늦게 떠났고, 그 뒤 걸음 간격과 위로 간 칸 수는 같았습니다. 충돌이 아니라 출발이 늦은 것이라, 걸음 수 대신 해안에 막히는 자리로 견주게 바꿨습니다.

## 남은 것

- 11비트 훅이 세계 0 의 움직이는 타일 위상과 세계 2 의 첫걸음을 늦추는 까닭. 훅이 길어진 것과 맞물리지만, 지도를 불러올 때 멈춘 프레임이 생기는지는 재지 않았습니다. 걸음 속도·충돌·화면은 같았습니다.
- 타일 1,024개로 블록 2,048개를 실제 지도에 채울 수 있는지. 원본의 비율이면 1,100개쯤에서 타일이 먼저 바닥납니다.
- `00:CF50` 이 칸을 바꾸는 네 장면과 세계 지도 화면(`03:C8B3`)의 점은 앞 일지처럼 블록을 늘린 롬에서 돌려 보지 않았습니다.
