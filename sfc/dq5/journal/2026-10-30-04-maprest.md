# 2026-10-30-04: 걸음 루틴 표 늘리기, 층 2 새 맵의 가장자리 출구, 상자 번호 16비트 조사

[새 그룹 일지](2026-10-29-04-newgroup-field.md)에서 남긴 둘을 풀었습니다. 하나는 걸음마다 부르는 루틴 표 `00:C689` 를 늘리는 것이고, 다른 하나는 층 2 맵을 복사한 새 그룹 맵의 가장자리 출구입니다. [상자 일지](2026-10-29-05-chestgrow.md)가 남긴 상자 257개 이상도 정적으로 조사했습니다. 그리고 머지된 PR 의 LOW 둘(DB 창 감사의 BRK 돌아오는 자리, 세계 1·2 필드 그림의 타일)을 고쳤습니다. 결과는 [쓰기 형식 「걸음 루틴 표」](../docs/dq5-build-format.md#걸음-루틴-표-dq5step1)·[「새 그룹을 필드와 잇기」](../docs/dq5-build-format.md#새-그룹을-필드와-잇기)·[「맵별 루틴 표」](../docs/dq5-build-format.md#맵별-루틴-표-dq5maphook1)·[「표 옮기기」](../docs/dq5-build-format.md#보물상자조사-보상-표-옮기기-dq5chesttables1)에 넣었습니다.

## 1. 걸음 루틴 찾기는 `00:C652` 부터

형식 문서에는 찾기가 `00:C650` 으로 적혀 있었습니다. 바이트를 풀어 보니 `00:C64E`~`C651` 은 `JSL $02860B` 이고, 찾기는 `00:C652` 의 `PHP` 부터입니다. 부르는 곳도 `01:8F89` 의 `JSL $00C652` 하나였습니다(24비트 정적 검색).

```
00:C652  PHP / PHB / PHK / PLB / SEP #$30
00:C658  LDA $BE / BPL 기본          ; 필드면 기본
00:C65E  LDX #$00
00:C660  LDA $C689,X / BMI 기본 / CMP $BC / BEQ 찾음 / INX ×3 / BRA
00:C66E  찾음: $C68A,X·$C68B,X → $1AAD·$1AAE
00:C67A  기본: #$87·#$C6 → $1AAD·$1AAE   ; 00:C687 = CLC / RTS
00:C684  PLB / PLP / RTL
```

표를 읽는 명령은 `00:C660`·`C66C`·`C672` 셋뿐이고, 표 바로 뒤 `00:C6B7` 은 코드입니다. `$1AAD` 는 `00:C357` 의 `JMP ($1AAD)` 가 부르므로 루틴은 뱅크 00 에 있어야 합니다.

그래서 팔레트 세트 표처럼 찾기를 통째로 다른 뱅크로 보냈습니다. `00:C652` 4바이트를 `JML 루틴` 으로 바꾸고, 루틴은 같은 차례로 표를 긴 주소로 읽습니다. 원래 찾기가 `RTL` 로 끝나므로 루틴도 `RTL` 로 끝냅니다. DB 를 바꾸지 않으니 `$1AAD` 도 긴 주소(`$00:1AAD`)로 씁니다. 색인 X 는 8비트 그대로입니다. 끝 `FF` 를 X ≤ 255 에서 읽어야 하므로 85그룹까지입니다(85그룹이면 끝 `FF` 가 X = 255). 이것이 새 도구 `dq5stepwrite.py` 입니다.

단위 테스트는 합성 롬의 원래 찾기와 옮긴 찾기를 65816 해석기(`w65816.py`)로 `JSL` 해서 `$1AAD` 를 견줍니다. 원본 롬에서 내보낸 표를 그대로 넣으면 쓰기가 0개였고, 그룹 36 을 더하면 `3C:A000` 에 루틴과 16그룹 표를 둡니다.

## 2. 층 2 새 맵의 가장자리 출구

지난번 01/00 을 복사한 새 맵이 아래 가장자리에서 멈춘 것은 `$182F` 때문이었습니다. 01/00 의 맵별 루틴 `02:B1DF` 를 풀어 보면 뒤쪽이 바로 그 일을 합니다.

```
02:B1DF  JSL $1EF207
02:B1E3  LDA #$02 / STA $182F / RTL
```

`02:B1E3` 은 03/0D 항목도 쓰는 자리라 `dq5maphook.py` 가 이미 받는 루틴입니다. 막힌 것은 맵 고르기였습니다. 도구가 롬의 맵 목록에 없는 맵을 거부해서, 새 그룹 맵은 항목에 쓸 수 없었습니다. 그래서 다른 도구처럼 `--new-map GG/MM` 을 받게 했습니다. 그룹 `50` 미만이고 롬에 아직 없는 맵만 받습니다. 표는 162개를 꽉 채우고 있어서, 항목을 더하려면 `rewrite --at 3B:8000 --stub-at 15:FF80` 으로 뱅크 15 밖에 옮깁니다. 이때 로더 DB 가 `3B` 가 되지만 `STA $182F` 는 낮은 WRAM 거울로 갑니다.

## 3. 밟아서 확인

`dq5newgroupcheck.py` 에 36/01(01/00 의 레코드·속성 복사)을 더했습니다. 롬 `g` 에는 36/01 의 맵별 루틴 항목(`02:B1E3`)과 그룹 36 의 걸음 루틴(그룹 01 과 같은 `00:C385`)을 넣었고, `p` 는 둘 다 뺐습니다. 맵을 떠나면 `$1AAD` 가 바뀌지 않으므로, 걸음 루틴은 맵 안에서 걸은 뒤의 `$1AAD` 로 봅니다.

```
edge: {'map': '36/01', 'BE': 0, '182F': 2, 'field': [345, 57]}
edge-none: {'map': '36/01', 'BE': 128, '182F': 1, 'cell': [32, 92]}
step: {'map': '36/01', 'BE': 128, '1AAD': 'C385', 'cell': [41, 84]}
step-none: {'map': '36/01', 'BE': 128, '1AAD': 'C687', 'cell': [41, 84]}
step-01: {'map': '01/00', 'BE': 128, '1AAD': 'C385', 'cell': [41, 84]}
12회 실행, 새 그룹 검사 12개 통과
```

- 36/01 (32,90) 층 2 에서 아래로 걸으면 (32,92) 를 지나 필드 (345,57) 에 나왔습니다. 맵 안에 있을 때 `$182F` 는 2 였습니다. 항목이 없는 `p` 롬에서는 (32,92) 에서 멈추고 `$182F` 가 1 이었습니다.
- 36/01 에서 좌우로 걸은 뒤 `$1AAD` 가 `g` 롬은 `C385`, `p` 롬은 기본 `C687` 이었습니다.
- 같은 `g` 롬에서 01/00 은 원래 항목 그대로 `C385`, 03/00 은 `C565` 였습니다. 옮긴 표가 원래 15그룹을 지켰습니다.
- 지난번 일곱 장면도 같은 롬에서 모두 그대로 통과했습니다.

## 4. 상자 257개 이상

상자 번호와 열림 비트를 16비트로 바꿀 곳을 정적으로 모았습니다.

- 번호 덧셈: `25:FAB0`(열 때)과 `1F:FDD0`(들어갈 때)은 M 8비트로 `ADC $EF90,X` 해 맵 앞의 개수를 더합니다. 맵 안의 순서도 8비트로 더합니다. 표의 개수 칸도 1바이트입니다.
- 열림 비트 읽기: `12:E675`~`E690`·`1F:FDF7`~`FE0B` 가 `n >> 3` 을 X 8비트로 써서 `LDA $7E2210,X` 합니다.
- 켜기: `12:E691` 이 `$1E80` 에 `n >> 3 | 80` 1바이트를 두고, `12:F839` 가 `LDX $1E80` 로 `7E:2190,X` 를 켭니다. `$1E80` 은 서랍·발밑·두 칸 앞·아래층 상자·필드 조사도 같은 꼴로 씁니다. 뱅크 01 의 `01:DE8A`·`DECB` 가 쓰고 `01:DF34`·`DFB9`·`F138` 이 읽는 곳도 있습니다.
- 내용물 색인 `n * 2` 는 `12:E6A7` 의 `REP #$30` 뒤라 16비트로 늘어납니다.

비트를 둘 자리가 더 큰 문제였습니다. 256개면 `2210`~`222F` 를 다 씁니다. 그 뒤 `2230`~`224F` 는 다른 표의 비트이고, `2250` 부터는 맡긴 물건입니다. 기록되는 WRAM 은 `7E:2000`~`2A9F` 이고, SRAM 8KB 는 칸 셋이 다 채웁니다(`dq5sram.py`). 그래서 기록 범위 안에서 아무 코드도 쓰지 않는 바이트부터 찾아야 합니다. 덧셈 둘·읽기 둘·`$1E80` 꼴·비트 자리를 함께 바꾸는 일이라 이번에는 구현하지 않고 「남은 것」에 두었습니다.

## 5. DB 창 감사의 BRK 돌아오는 자리

`lua/dq5dbread.lua` 는 창 안에서 `BRK` 를 만나면 늘 4바이트 뒤(인자 둘)를 돌아오는 자리로 보았습니다. 그런데 `BRK` 의 인자 수는 서비스마다 다릅니다(`dq5talk.brk_args`, `80`~`93` 은 롬 표). 처리기 `00:8F80` 은 스택에 쌓인 PC 를 인자만큼 옮긴 뒤 `RTI` 합니다. 그래서 인자 수 표를 루아에 옮기지 않고 처리기의 `RTI` 를 기다리게 했습니다.

`BRK` 를 실행할 때의 SP 에서 4를 뺀 값을 열쇠로 둡니다. 그 SP 에서 도는 `RTI` 가 꺼내는 PC 를 돌아오는 자리로 봅니다. `RTI` 후보는 뱅크 00 의 `40` 바이트마다 실행 콜백을 걸어 잡습니다. 명령 중간의 `40` 은 실행되지 않으니 걸어도 됩니다. 이 롬은 SlowROM 이라 BRK 벡터가 처리기 `00:8F80` 으로 가므로 뱅크 00 의 `8000`~`FFFF` 만 봅니다. 같은 SP 에서 도는 다른 `RTI`(인터럽트 등)를 잘못 받지 않게, 꺼낸 PC 가 BRK 와 같은 뱅크의 BRK + 2 ~ + 4 일 때만 받습니다. 돌아온 자리는 `dbbrk.txt` 에 남깁니다.

`dq5chestcheck.py --audit` 는 전과 같이 명령 310개였습니다. DB 로 롬을 읽는 명령 9개도 모두 표 자리였습니다. 그 창 안의 `BRK` 는 인자 둘인 `1F:FCCA`(`0B`)·`FCD0`(`0D`)뿐이라 전에도 맞았습니다. 인자가 다른 `BRK` 를 보려고 01/02 에서 상자를 여는 장면을 `DBWIN=12E680` 으로 따로 돌렸습니다.

```
BRK 95 05:D56A → D56D   BRK 95 12:EDE6 → EDE9   BRK 98 12:EDEE → EDF1   BRK 98 12:F44A → F44D
BRK 8E 12:F6F9 → F6FC   BRK 98 12:F709 → F70C   BRK 0E 12:FE72 → FE74   BRK 19 25:FBDF → FBE3
BRK 08 25:FC27 → FC29
```

9개 모두 `brk_args` 로 낸 자리와 같았습니다. 옛 「늘 4바이트」로 맞는 것은 `BRK 19` 하나뿐이었습니다.

## 6. 세계 1·2 필드 그림의 타일

`dq5gfx.export_field` 는 세계 셋을 모두 `field_tiles(rom)`(세계 0 의 타일 벌)로 그렸습니다. 그래서 `dq5fieldgfxwrite.py --worlds-at` 롬에서는 세계 1·2 의 니블만 그 세계 것이고 타일 모양은 세계 0 것이었습니다. `field_tiles(rom, world)` 가 세계 1·2 는 `dq5fieldgfxwrite.current(rom)['worlds']` 의 타일을 읽게 했습니다. 훅이 없는 롬에서는 세 세계 모두 같은 자리를 읽습니다. 단위 테스트는 세계 1 의 타일 63 만 바꾼 롬에서 세계 1 그림의 타일 63 이 바뀐 것과, 세계 0·2 가 그대로인 것을 봅니다.

## 틀렸던 것들

- 걸음 루틴 찾기를 `00:C650` 부터로 보고 원래 바이트를 견주는 검사를 썼다가, 원본 롬을 거부했습니다. `00:C650` 은 앞 명령 `JSL $02860B` 의 끝이었습니다.

- DB 창이 닫힐 때 기다리던 BRK 를 비우게 했더니, 상자 여는 장면의 BRK 가 9개에서 2개로 줄었습니다. 메시지 BRK(`95`·`98`·`8E`·`0E`)는 처리 중 DB 가 바뀌어 창이 닫힌 뒤에 돌아옵니다. 그래서 비우지 않고 위 범위 검사로만 거릅니다.
