# 2026-10-30-36: 세계마다 타일맵 워드 표의 넷째 세계 줄이기와 세계를 오갈 때의 화면

[세계마다 니블 일지](2026-10-30-33-nibfast.md)가 남긴 둘을 했습니다. 첫째, 필드 세계 `$1949` 에 쓰는 곳을 모두 찾아 필드에서 `$1949 & 3` 이 3 이 되는 길이 없음을 확인하고, 세계마다 타일맵 워드 표를 16KB 에서 14KB 로 줄였습니다. 둘째, 세계마다 니블이 다른 롬으로 ルーラ 와 걸어 나가기로 세계를 옮긴 뒤의 화면을 쟀습니다. 내린 세계의 니블로 늘린 타일 칸의 팔레트가 붙었고, 타일 번호·CGRAM·프레임은 같은 니블 롬과 같았습니다. 형식은 [쓰기 형식의 「필드 그림」](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)과 [필드 형식의 「세계 셋」](../docs/dq5-field-format.md#세계-셋-019f40)에 있습니다.

## 1. `$1949` 에 쓰는 곳

롬 전체에서 `$1949` 를 고치는 명령 모양을 찾았습니다. `STA`·`STZ`·`STX`·`STY`·`INC`·`DEC`·`TSB`·`TRB`·시프트의 절대 주소와 `7E:1949` 긴 주소, 그리고 16비트로 쓰면 `$1949` 에 닿는 `$1948` 쓰기입니다. `$1949` 에 쓰는 곳은 다섯이었고, `$1948` 쓰기 다섯은 모두 8비트(`LDA #` 가 2바이트이거나 `STZ`)라 `$1949` 를 건드려도 0 입니다.

| 곳 | 쓰는 값 | 언제(부르는 곳) |
| --- | --- | --- |
| `2A:FEEC` | 나가는 그룹의 세계 | 실내에서 필드로 나갈 때(`2A:F475` → `2A:FEE4`) |
| `11:819A` | 내릴 그룹 `$BC`(`54` 는 `15` 로 바꿈)의 세계 | ルーラ·キメラのつばさ 로 내릴 때(`23:E0B3` → `11:8176` → `11:8180`) |
| `03:C684` | 지금 그룹의 세계. `$BE` bit7 이 꺼져 있으면(필드) 쓰지 않음 | `03:C688`(たびびとのちず 처리 `11:8DF1`, 스크립트 `06:FAE4`, `00:8155`, `12:EBE1`)·`03:C6AF` |
| `02:9779` | 0 (`STZ`) | `$C1` = `18`, `$C2` = `08`·`09` 인 장면 뒤 `$1954` = `81` |
| `02:B9D8` | 0 (`STZ`) | 필드 (399,387) 과 `7E:21DB`·`21DD` 를 두는 장면 |

「그룹의 세계」는 모두 `2A:FEF5` 가 셉니다(코드 읽기). 그룹 `50` 이상은 0(`54` 만 2), 그룹 `05` 는 0, 나머지는 `0F:EA97 + 그룹 × 5` 의 bit5-6 에서 1 을 뺀 값입니다. 맵 포인터 표에 있는 그룹 `00`~`35` 를 모두 셈하니 bit5-6 이 0 이라 `FF` 가 나오는 그룹은 `05`(위에서 따로 0)와 `27` 둘뿐이었습니다. `36`~`4F` 는 맵이 없는 번호입니다. ルーラ 목적지 목록 `25:85D5` 의 22개는 모두 0~2 입니다.

그러니 `FF` 는 그룹 `27` 의 맵 27/00(배 안, 출구 하나가 17/01 로 감)에서 `03:C684` 가 쓸 때만 나옵니다. 이것은 실내에서만 쓰고, 필드로 나가는 길은 다시 씁니다. 27/00 에서 필드로 바로 나가는 출구는 없고, 출구를 다른 맵으로 돌리는 `2A:F52A` 표에도 그룹 27 이 없습니다.

## 2. 실측

`lua/dq5worldlog.lua` 를 새로 썼습니다. WRAM 오프셋 `1949` 에 쓰기 콜백을 걸어(거울 주소와 DMA 도 잡힘) PC·값을, `00:BBAC` 에 들어갈 때의 `$1949` 값을 모읍니다. 배 선실 세이브스테이트에서 `dq5warp.lua` 로 장면을 만들었습니다. 원본 게임 기록입니다.

```
장면                                      $1949 쓰기(PC 값 프레임)           00:BBAC 의 $1949(첫 프레임 횟수)
27/00 에 서기                             없음                               부르지 않음
27/00 에서 たびびとのちず                 없음(「ここでは 何も おこらなかった」)  부르지 않음
22/00 에 서기                             없음                               부르지 않음
1C/00 에서 걸어 나가기                    2AFEEF 02 490                      02 518 1088
30/00 에서 걸어 나가기                    2AFEEF 02 513                      02 541 1088
ルーラ 세계 0 → 22(세계 1)                2AFEEF 00 422, 11819D 01 1056      00 462 1088, 01 1087 1088
ルーラ 세계 0 → 1C(세계 2)                2AFEEF 00 422, 11819D 02 1056      00 462 1088, 02 1084 1088
ルーラ 세계 0 → 15(세계 2)                2AFEEF 00 422, 11819D 02 1056      00 462 1088, 02 1084 1088
ルーラ 세계 0 → 22 → 01(세계 0)           …, 11819D 01 1056, 11819D 00 1964  00 462 2176, 01 1087 1088
```

쓰는 PC 는 앞 표의 `2A:FEEC`·`11:819A` 다음 명령 자리입니다. `00:BBAC` 는 실내에서 한 번도 돌지 않았고, 필드에서는 늘 그 세계 값(0~2)이었습니다. 27/00 의 たびびとのちず 는 `03:C688` 앞에서 막혀 `FF` 를 쓰지 않았습니다. `03:C688` 을 부르는 나머지 셋(스크립트·`00:8155`·`12:EBE1`)이 27/00 에서 도는 장면은 찾지 못했습니다.

원본도 필드에서 `$1949` 가 0·1 이 아니면 세계 2 지도를 고릅니다(`01:9F49` 의 `LDA $1949 / BNE` → `CMP #$01 / BNE`). 필드에서 `FF` 가 되면 원본부터 화면이 어긋나는 셈이라, 게임이 그 길을 두지 않았다고 보았습니다.

## 3. 표를 줄이는 배치

`00:BBAC` 는 색인 `($1949 & 3) << 11 | 타일 << 1` 로 위층 표와 아래층 표를 따로 읽습니다. 넷째 칸을 그냥 빼면 & 3 = 3 일 때 표 밖을 읽습니다. 두 층 모두 넷째 칸을 표 안에 두려면 표가 몇 KB 여야 하는지 셈했습니다. 세계 0·1·2 의 표 여섯(2KB 씩)은 서로 다르니 겹칠 수 있는 것은 넷째 칸뿐입니다. 위층 넷째 칸이 아래층 j 번째 표와, 아래층 넷째 칸이 위층 i 번째 표와 겹치려면 위층 시작 + 6KB = 아래층 시작 + 2j KB, 아래층 시작 + 6KB = 위층 시작 + 2i KB 라 i + j = 6 이어야 하는데, i·j 는 2 이하입니다. 그래서 12KB 로는 한 층의 넷째 칸이 표 밖으로 나가고, 둘 다 표 안이려면 14KB 가 필요합니다.

14KB 로 했습니다. 위층 세계 0·1·2(6KB) 바로 뒤에 아래층 세계 0·1·2·0(8KB)을 두면, 위층 넷째 칸은 아래층 세계 0 표를 읽습니다. & 3 = 3 이 되어도 두 층 모두 세계 0 의 타일 번호이고, 위층 팔레트만 니블 3비트로 읽습니다. 아래층 표는 지금까지의 아래층 표와 바이트가 같고 자리만 2KB 앞으로 옵니다.

- `dq5fieldgfxwrite.py` 의 `palette_world_words` 가 세계 셋의 니블로 14KB 한 덩어리를 내고, `00:BBCB` 의 아래층 표 주소는 표 + `WORD_LOWER`(`1800`)입니다.
- 코드 38바이트는 아래층 표 주소 한 바이트만 다릅니다. `LDA long,X` 는 주소에 따라 사이클이 바뀌지 않으므로 `00:BBAC` 의 사이클도 같습니다.
- 디코더(`dq5field.tile_word`)는 `00:BBBA`·`BBCB` 의 피연산자를 읽으므로 그대로 맞습니다.

`dq5gfxlimitcheck.py` 의 시험 롬을 고치기 전·후 도구로 만들어 견주었습니다. nibs 롬만 3,585바이트가 달랐습니다. `00:BBCD`(아래층 표 주소 `E0` → `D8`) 1바이트, 체크섬 4바이트, `60:E000`~`F7FF` 1,536바이트(아래층 표가 2KB 앞으로 옴. `60:D800`~`DFFF` 는 위층 넷째 칸이던 세계 0 위층 표가 이 롬에서 아래층 세계 0 표와 바이트가 같아 차이 없음), 쓰지 않게 된 `60:F800`~`FFFF` 2,044바이트입니다. 고친 뒤 `60:D800`~`F7FF` 는 고치기 전 `60:E000`~`FFFF` 와 같고, `60:C000`~`D7FF` 도 같습니다. 같은 니블인 tiles 롬과 다른 시험 롬 열 개는 바이트마다 같았습니다.

## 4. 세계를 오간 뒤의 화면

nibs 롬(세계 1·2 의 늘린 타일 니블만 bit1·bit2 를 더 뒤집음), 같은 니블인 tiles 롬, 원본 게임에서 다섯 장면을 같은 입력으로 돌렸습니다. ルーラ 목적지는 `7E:2030`~`2032` 의 비트로 고릅니다. `FIELD` 로 01/00 을 지나면 bit0(ラインハット)이 켜지므로 한 비트만 더 켜고 목록 둘째를 골랐습니다(덤프의 `7E:2030`~ = `01 20 00`·`01 80 00`).

```
장면                      덤프   세계   늘린 타일 칸   그 세계 니블과 같음   다른 세계 니블과 다름   tiles 롬과 팔레트가 다른 칸
ルーラ 0 → 22             1600   1      1,285          1,285                 1,285·1,285            1,285
ルーラ 0 → 1C             1600   2      1,415          1,415                 1,415·1,415            1,415
1C/00 에서 걸어 나가기    1400   2      1,413          1,413                 1,413·1,413            1,413
30/00 에서 걸어 나가기    1400   2      1,346          1,346                 1,346·1,346            1,346
ルーラ 0 → 22 → 01        1600   1      1,285          1,285                 1,285·1,285            1,285
                          2500   0      1,184          1,184                 1,184·1,184            0
```

팔레트 비트는 [앞 일지](2026-10-30-33-nibfast.md)와 같이 디코더를 거치지 않고 입력 니블로 셈했습니다. 세 롬 모두 타일맵의 채운 칸이 디코더 워드와 같고, tiles·nibs 롬의 칸은 같은 자리 원본 게임 칸의 타일 + 512 였습니다. nibs 롬은 tiles 롬과 타일 번호가 모두 같고 CGRAM 도 같았으며, 팔레트가 다른 칸은 세계 1·2 에서 늘린 타일 칸 수와 같고 세계 0 에서 0 이었습니다.

프레임도 견주었습니다. 다섯 장면 모두 nibs·tiles 롬의 `$1949` 쓰기와 `00:BBAC` 호출 기록(PC·값·첫 프레임·횟수)이 같았고, 걸은 결과(내린 좌표, 1,433·1,635·2,543프레임)는 세 롬이 같았습니다. 원본 게임과 견주면 두 롬 모두 필드를 불러올 때 첫 `00:BBAC` 가 한 프레임 늦습니다(462 → 463, 518 → 519 등). 늘린 타일을 먼저 보내는 불러오기 훅 때문으로 보이고, 같은 니블 롬에도 있는 것이라 이번 변경과는 따로입니다. 호출 횟수와 뒤 프레임은 같았습니다.

이 다섯 장면은 `dq5gfxlimitcheck.py` 에 넣었습니다.

## 틀렸던 것들

- 그룹 `27` 에 들어가면 `$1949` 가 `FF` 가 될 것으로 보았습니다. 맵에 들어갈 때 `2A:FEF5` 는 세계를 견주기만 하고 쓰지 않아, 27/00 에 들어가도 `$1949` 는 0 그대로였습니다.
- 처음 ルーラ 장면은 목적지 비트를 하나만 켜고 목록 첫째를 골라 ラインハット 로 날았습니다. 01/00 을 지나며 bit0 이 켜지기 때문입니다.
