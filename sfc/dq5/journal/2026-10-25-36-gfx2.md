# 2026-10-25-36: 창 타일과 움직이는 타일

[그래픽 내보내기](2026-10-25-28-gfx.md) 에 남은 창·메뉴 그림, 타이틀 화면, 움직이는 타일을 찾아 `sfc/dq5/tools/dq5gfx.py` 의 `ui`·`anim` 묶음으로 더했습니다.
결과는 [dq5-graphics-format.md 「창·메뉴 타일」](../docs/dq5-graphics-format.md#창메뉴-타일-04e17d) 과 [dq5-field-format.md 「타일 그래픽과 팔레트」](../docs/dq5-field-format.md#타일-그래픽과-팔레트) 에 있습니다.

## 1. 창 타일은 롬에 그대로 없었다

배 선실 덤프의 BG3 CHR(VRAM 워드 `$1000`)을 펴 보니 타일 1~95 가 숫자·가나·기호·창 테두리였고, 96 부터는 그때 띄운 글자였습니다.
창은 BG3 타일맵에 8C(모서리)·8D(위)·8E(옆)·8F·90(가로줄)을 늘어놓고 다른 모서리는 반전으로 씁니다. 그런데 타일 1~95 의 16바이트를 롬에서 찾으면 149개 중 하나만 나왔습니다.

## 2. 언제 누가 올리는지

전원을 켜고 이름 입력까지 가는 입력(`PERIOD=40 TAP=a`)으로 프레임마다 VRAM 을 덤프해, 타일이 232~236프레임 사이에 들어오는 것을 잡았습니다(`sfc/dq5/tools/lua/dq5gfxdump.lua` 의 `EVERY`).
그 구간의 DMA(`$420B`)를 적었지만(아래 프로브의 `dma.txt`) 해당 VRAM 으로 가는 것이 없었습니다. `$2118`·`$2119` 쓰기 감시도 처음에는 아무것도 잡지 못했는데, 감시를 뱅크 `00` 에만 걸었기 때문이었습니다. 레지스터 미러가 있는 뱅크 `00`~`3F`·`80`~`BF` 에 모두 걸자 나왔습니다. 이 감시를 `sfc/dq5/tools/lua/dq5vramlog.lua` 로 남겼습니다.

```sh
LIBDIR=$(uv run --locked krpatch sfc lua) FROM=200 STOPF=240 MAXF=242 VLO=1000 VHI=14FF PERIOD=40 TAP=a \
  SHOT_DIR=$PWD/work/vl "$MESENCE" --testrunner "$PWD/rom/dq5.sfc" "$PWD/sfc/dq5/tools/lua/dq5vramlog.lua"
```

```
04:E1C6 f233 vram 1008 count 1104
04:E1E0 f234 vram 1458 count 88
24:8100 f234 vram 14B0 count 80
```

적히는 PC 는 쓰기 명령 바로 다음 명령의 주소라, 쓰는 명령은 `04:E1C3`(`STA $2118`)과 `04:E1DD` 입니다.

`04:E17D` 는 `04:E528` 의 1bpp 8바이트를 평면 0 에, `FF` 를 평면 1 에 써서 타일 138개를 만들고, 이어서 2bpp 11개(평면 0 여덟 줄 뒤 평면 1 여덟 줄)를 씁니다. 처음 VRAM 워드 상위는 플래그 검사(`BRK #$0B`) 결과에 따라 `$10` 이나 `$40` 입니다.
CGRAM 0번 줄은 `04:9870` 이 `04:98D7` 의 32바이트를 씁니다. 롬으로 만든 타일이 배 선실과 필드 덤프의 VRAM 2,384바이트와 같았고, 팔레트도 두 덤프의 0번 줄과 같았습니다.

## 3. 타이틀 화면

입력 없이 4,000프레임을 100프레임마다 찍어 보니 「ENIX PRESENTS」「ARMOR PROJECT」「BIRD STUDIO」「KOICHI SUGIYAMA」「CHUN SOFT」「IN」「DRAGON QUEST V」가 차례로 뜨고 바로 모험의 서 창이 나왔습니다.
1600프레임 덤프의 BG3 CHR 은 워드 `$4000`(위의 `$40` 길)이고 타일맵은 `21A1`~ 만 썼습니다. 폰트 글자를 그려 넣은 것이라, 따로 뽑을 로고 그림은 없습니다.

## 4. 필드의 움직이는 타일

다른 일지에서 필드 타일 454~459 가 `7E:C800` 의 8벌로, 타일 4·5·20·21 이 `7E:C400-` 으로 바뀐다는 것을 확인해 두었습니다. 장면 이동 도구로 필드에 나가며 그 WRAM 쓰기를 감시했습니다.

```
7EC800-7EC8FF pc=2B8063 first=459 n=253
7EC400-7EC43F pc=01C7AC first=458 n=32
```

`2B:8000` 은 `1E:D0FF` 를 필드 RLE(`01:A64F` 와 같은 꼴)로 WRAM 포트에 DMA 로 풉니다. `dq5field.rle` 로 풀자 1,536바이트가 나왔고 필드 덤프의 `7E:C800-CDFF` 와 같았습니다.
`01:C790` 은 롬 타일 두 개를 이어 줄마다 16비트로 보고 한 픽셀 돌립니다(세계 0 은 오른쪽). 덤프의 `C400-C47F` 는 타일 4·5 와 20·21 모두 오른쪽으로 9픽셀 돌린 값과 같았습니다.

## 5. 실내 맵의 움직이는 타일

01/01 세이브스테이트에서 4프레임마다 32번 VRAM 을 덤프해 바뀐 타일을 세니 VRAM 바이트 `57C0`~ 의 10타일, 곧 맵 CHR 슬롯 `BE`~`C7` 뿐이었습니다. 매 프레임 `00:8F74` 가 `7E:2D00` 의 `$140` 바이트를 DMA 하고, `7E:2D00` 에는 `03:D777`·`03:D77A` 가 씁니다.
실내 맵을 그릴 때 물 타일이 VRAM 에 없던 까닭이 이것입니다. 원본 타일과 맵마다 고르는 곳은 아직 찾지 않았습니다.

## 틀렸던 것들

- VRAM 쓰기를 `emu.memType.snesVideoRam` 의 메모리 콜백으로 잡으려 했는데 아무것도 걸리지 않았습니다. CPU 주소 `$2118` 쓰기를 감시하는 쪽으로 바꿨습니다.
- 레지스터 쓰기 감시를 뱅크 `00` 에만 걸어 `04:E17D` 를 놓쳤습니다. 이 게임은 레지스터를 다른 뱅크 미러로도 씁니다.

## 남은 것

- 실내 맵 움직이는 타일의 원본 타일과 맵마다 고르는 표(`03:D5B8`·`03:D6A0` 근처), 닫힌 문을 덮는 곳.
- 움직이는 타일이 다음 벌·다음 픽셀로 넘어가는 간격.
