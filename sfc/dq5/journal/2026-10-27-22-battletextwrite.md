# 2026-10-27-22: 전투 메시지와 이름 문자열 표 쓰기

전투 모드 메시지 432개를 1바이트 부호 목록으로 고쳐 허프만 트리와 함께 다시 넣는 `dq5battletextwrite.py`, 인물·주문·몬스터·물건 등의 이름 문자열 표 아홉 개를 길이를 바꿔 다시 채우거나 옮기는 `dq5namewrite.py` 를 만들었습니다. 입력과 배치는 [전투 메시지 일괄 쓰기](../docs/dq5-build-format.md#전투-메시지-일괄-쓰기-dq5battletext1)와 [이름 문자열 표 쓰기](../docs/dq5-build-format.md#이름-문자열-표-쓰기-dq5names1)에 있습니다. 새 한글 글꼴과 2바이트 부호는 다루지 않고 원래 글꼴의 부호만 받습니다.

## 1. 전투 디코더를 다시 읽기

보행 쓰기([일지 56](2026-10-26-56-textwrite.md))처럼 디코더를 늘린 뱅크로 옮기려면, 전투 디코더 `24:9E47` 이 어떤 주소에 묶여 있는지부터 알아야 했습니다. 디스어셈블한 결과는 이렇습니다.

```text
24:9E49  PHK / PLB                데이터 뱅크 = 디코더 뱅크
24:9E51  LDX #$00E8               뿌리
24:9E5A  AND $9E8C,Y              비트 마스크(보행 디코더와 같은 표)
24:9E61  LDA $9C2E,X / $9D18,X    트리 1·0
24:9E7F  AND #$00FF / ASL / TAX   가지: 다음 노드 번호는 8비트
24:9E8B  RTS
```

부르는 곳은 `24:8C29`(메시지 풀기)와 `24:8C6D`(앞 메시지 건너뛰기) 두 곳뿐이었고, 둘 다 `JSR $9E47` 입니다. 그래서 보행과 같이 `24:9E47` 에 `JSL 사본 / RTS` 를 두고, 사본의 피연산자 넷과 끝 `RTL` 만 바꾸면 됩니다. 다만 마스크 `24:9E8C` 는 보행 디코더도 읽으므로 덮지 않고 사본 쪽에 마스크를 따로 둡니다.

`24:8C39` 를 따라가니 색인 풀기는 보행과 같은 `24:8C8D`(`24:8C60` 에서 부름)였습니다. 3바이트 값을 3비트 밀어 주소로 쓰므로 뱅크 `1F` 까지만 가리킵니다. 보행 쓰기가 그랬듯 루틴 안은 두고 전투 쪽 `JSR` 만 비운 디코더 자리 `24:9E4C` 의 훅으로 돌렸습니다. 훅이 OR 하는 값은 `--at` 뱅크 & `E0` 이라, `30`~`3F` 면 `20`, `40`~`5F` 면 `40`, `60`~`7D` 면 `60` 입니다.

메시지를 부르는 쪽(`24:8691`~`869A`)은 `8C39`(찾기) → `8C21`(128바이트 풀기) → `86A5`(한 바이트씩 처리)입니다. 푸는 것은 한 번뿐이라 메시지 하나는 끝 부호까지 128바이트를 넘으면 안 됩니다. 원본에서 가장 긴 메시지는 99바이트입니다.

## 2. 전투 메시지 쓰기

원본 432개를 1바이트 부호 목록(`dq5battletext/1`)으로 내보내고, 바꾼 항목만 반영해 트리를 다시 만듭니다. 원본은 118종 부호·트리 117노드였습니다. 다시 만든 트리는 노드를 앞에서부터 번호 매기므로 뿌리가 `E8` 이 아니라 `00` 입니다.

`--at` 은 반드시 받게 했습니다. 기본값으로 쓸 만한 `30`·`32`·`34`·`38`·`60:8000` 이 DQ4 타이틀·메뉴와 다른 쓰기 도구에 이미 잡혀 있어, 빈 자리라고 단정할 수 없기 때문입니다.

```text
check --at 3B:8000   전투 메시지 432개, 부호 8910개, 다른 메시지 0개
check --at 60:8000   전투 메시지 432개, 부호 8910개, 다른 메시지 0개
```

보행 쓰기(`38:8000`), 전투 쓰기(`4F:FD00`), 이름 표 옮기기(`4E:8000`)를 한 롬으로 빌드해도 빌더가 겹침을 찾지 않았습니다. 세 디코더·표 모두 원본과 같게 풀렸습니다. 처음에는 전투를 `3D:8000` 에 두고 검사했으나, `3D` 는 DQ4 환경 그림이 쓰는 뱅크라 예시에서 뺐습니다.

`check` 는 새 디코더 사본이 원래 `24:9E47`~`9E8B` 와 피연산자 넷·끝 `RTL` 말고는 같은지, 사본의 마스크가 `01`~`80` 인지도 봅니다. 트리·색인만 따라 푸는 비교로는 마스크 피연산자나 `RTL` 이 틀려도 잡히지 않기 때문입니다.

## 3. 이름 문자열 표

`21:955D` 는 `21:959B` + 표 × 3 의 24비트 주소에서 [길이][바이트…] 를 n 번 건너뛰어 n 번째 이름을 찾습니다. 건너뛸 때 `$3A` 에 길이 + 1 을 더하고 올림이 나면 `$3B` 만 올리므로, 표가 뱅크 끝을 넘으면 같은 뱅크 `0000` 을 읽습니다. 한 표는 한 뱅크 안에 둬야 합니다.

표 시작 주소를 롬 전체에서 찾았습니다. 24비트로 나온 곳은 `21:959B` 포인터 표뿐이었고, 표 8·9 의 `23:D6A1` 은 `21:A1D7` 이 `JSL` 하는 코드였습니다. 그래서 표 8·9 는 쓰지 않습니다. 남은 표의 경계를 세어 보니 표 `0A`·`0`·`1`·`2`·`4`·`5`·`6`·`0B` 가 `23:C242`~`D6A0` 에 빈틈 없이 이어져 있고, 표 3 은 `22:8000`~`841E` 하나였습니다. 원본 이름은 854개, 가장 긴 것은 12바이트(몬스터 이름)입니다.

쓰기 도구는 두 길을 둡니다.

- 제자리: 두 자리 안에서 표를 다시 채우고, 바뀐 바이트 범위와 시작이 달라진 표의 포인터만 씁니다. 원래 자리에 남는 바이트가 없어서, 이름 하나를 늘리면 같은 자리의 다른 이름을 그만큼 줄여야 합니다. 원본 그대로면 쓰기가 0개입니다.
- 옮기기(`--at`): 아홉 표를 늘린 뱅크로 옮기고 포인터 아홉 개를 고칩니다. 뱅크 끝에 들어가지 않는 표는 다음 뱅크 `8000` 에서 시작합니다.

이름 길이는 12바이트까지만 받습니다. `21:9589` 는 [길이][바이트…] 를 직접 페이지 `$00` 부터 복사하므로, 길이가 `39` 를 넘으면 복사하는 도중에 표 포인터 `$3A` 를 덮습니다. 그보다 짧더라도 `$0D` 뒤 직접 페이지를 부른 쪽이 쓰는지는 보지 않았습니다. 그래서 원본의 최대 길이를 넘기지 않습니다.

## 4. 전투에서 확인하기

선실 세이브스테이트에서 `dq5warp.lua` 로 スライム 하나와 전투를 붙이고 A 를 15번 눌렀습니다. `24:8C39` 의 메시지 번호, `24:8C21` 에 들어올 때 비트 위치, 푼 뒤 버퍼 `7E:0E4B` 128바이트, 40프레임 뒤 글자 격자 `7E:1DD5` 를 적었습니다.

```text
경우      푼 버퍼   05E 스트림   격자의 몬스터 공격 줄
original  8개 같음  07:84EB     4E684362 2801191218167A        スライムの　こうげき！
repacked  8개 같음  3B:870C     4E684362 2801191218167A
edited    8개 같음  3B:870C     544E554E684362 2801544E55191218167A   テストスライムの　テストこうげき！
moved     8개 같음  50:840C     544E554E684362 2801544E55191218167A
```

- `repacked` 는 원문을 `3B:8000` 에 다시 넣고 이름 표는 원본 그대로(쓰기 0개)입니다.
- `edited` 는 메시지 `05E` 「{F7}の　こうげき！」에 テスト 를 넣었습니다. 몬스터 0 スライム 을 テストスライム 으로 늘리고, 그만큼 물건 0 ひのきのぼう 를 ひのき 로 줄여 제자리에 넣었습니다.
- `moved` 는 같은 메시지를 `4F:FD00` 에 두었습니다. 사본·트리 545바이트 뒤 스트림이 뱅크 `50` 으로 넘어가고, 훅이 `ORA #$40` 입니다. 이름 표는 `4E:8000` 으로 옮겼습니다. 처음 실행에서는 `3C:8000` 으로 옮겨 같은 결과였고, 낮은 WRAM 거울이 없는 뱅크 `40` 이상에서도 되는지 보려고 바꿨습니다.

푼 버퍼는 그 메시지부터 이어지는 기대 부호 128바이트(다음 메시지까지 넘어감)와 바이트째 같았습니다. 격자에는 이름과 메시지 바이트가 그대로 이어져 있었고, 화면에도 「テストスライムの　テストこうげき！」가 떴습니다. 몬스터 이름이 옮긴 표에서 나왔으므로, 전투의 몬스터 이름은 `21:959B` 포인터를 따라 읽습니다. 전투가 무작위라 `edited`·`moved` 에서는 `002`(도망) 대신 `063` 이 나왔습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5battletextcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/battletextcheck
```

- 전투 창(크기·자리) 쓰기와 문자열 번역 편집, 새 한글 글꼴·2바이트 부호. 2바이트 부호는 사람이 고를 일입니다.
