# 2026-10-31-12: 따로 둔 머리·색인·메시지를 `over` 로 읽기

[앞 일지](2026-10-31-09-dq4ranges2.md)에서 통합 빌드의 `text` 작업 `over` 가 지금 dq4 메뉴 롬을 읽지 못하는 것을 찾았습니다. 이번에 `dq5textwrite.base_package` 가 dq4 메뉴처럼 머리(`5A:8000`)·색인(`59:8000`)·메시지(`64:C400`~)를 따로 둔 롬을 읽게 했습니다. `over` 가 고정 패치에서 빼는 자리도 세 구간으로 나눴습니다. 그 뒤 지금 1장 롬을 고정 롬으로 두고 통합 빌드를 돌렸습니다. 형식은 [보행 대사](../docs/dq5-build-format.md#보행-대사-일괄-쓰기-dq5text1)와 [고정 롬이 차지하는 자리](../docs/dq5-build-format.md#고정-롬이-차지하는-자리)에 있습니다.

## 1. 색인 표의 끝

`index_table` 은 색인 표가 머리 안(트리 뒤, 글자 묶음 표 앞)에 있다고 보고, 표 끝을 글자 묶음 표나 메시지 0 으로 셉니다. dq4 메뉴는 색인을 디코더와 다른 뱅크 `59` 에 두므로 그 뒤에 끝을 알려 주는 자료가 없습니다. 색인 표가 디코더와 다른 뱅크에 있으면 항목(묶음마다 21비트 비트 주소)이 앞으로 가는 동안을 세게 했습니다. `59` 는 표 뒤가 0 이라 거기서 멈춥니다.

```
menu.sfc  227항목 → 3,632개
```

## 2. 글자 묶음 표와 묶음 자리

다음은 글자 묶음 표에서 멈췄습니다. 지금까지는 표가 메시지 0 바로 앞에서 끝난다고 봤는데, dq4 메뉴는 표 `5A:9991` 이 머리 끝이고 메시지는 `64:C400` 에 있습니다. 표가 디코더와 같은 뱅크에 있고 메시지 0 앞이 아니면, 0 이 아닌 5바이트 항목이 이어지는 데까지를 표로 보게 했습니다. 글자 수가 원래 `3DB` 보다 적으면 거부합니다.

`base_package` 는 이제 묶음 자리를 구간 목록으로 돌려줍니다. 두 롬에서 이렇게 나왔습니다.

```
옛 메뉴 dq4-menu.sfc(e102f29…)  3200개  표 270바이트  ['65:8000~69:B941']
지금 메뉴 menu.sfc              3632개  표 460바이트  ['5A:8000~5A:9B5C', '59:8000~59:82A8', '64:C400~69:CD9A']
```

세 구간은 [앞 일지](2026-10-31-09-dq4ranges2.md)에서 바이트 비교로 잰 `dq4menumsg` 의 쓰기와 같습니다. 사이의 메뉴 자료 `60:8000`~`64:C209` 는 들어가지 않습니다.

## 3. 조사 코드

표를 지나자 메시지 검사에서 멈췄습니다.

```
ValueError: 지원하지 않는 글자·제어 코드: 4126
```

`4126` 은 `101E` 이고, dq4 의 [조사 코드](../../dq4/docs/dq4-josa-format.md)(`101E`~`1024`)입니다. 1장 빌드가 `24:81D1` 에 훅을 걸어 처리합니다. 메뉴 롬에는 그 훅이 아직 없지만 메시지는 이미 이 코드를 씁니다. 그래서 훅을 보고 판단하지 않고, 기준 롬의 메시지가 쓰는 `101E`~`10FF` 를 그 롬이 처리하는 코드로 받게 했습니다(`base_package` 의 다섯째 값 `controls`). 입력 `codes` 에도 같은 코드만 받습니다. 지금 기준 롬이 쓰는 것은 `101E`·`101F`·`1020`·`1024` 입니다.

```
dq5textwrite.py rom/dq5.sfc check --at 70:8000 --base work/ch1/dq4-ch1.sfc
보행 메시지 3632개, 코드 184381개, 다른 메시지 0개
```

## 4. 통합 빌드

`dq4build.py --no-sound` 로 만든 1장 롬(`b8634d80…`)을 고정 롬으로 두었습니다. 옛 통합 빌드 실측의 보행 메시지 둘(`297`·`3184`)을 고친 `text`(`over`)와 이벤트 하나를 넣었습니다.

```
오류: 고정 패치 dq4-ch1: 차지한 바이트 10개가 결과 롬에서 다름
bad ['37:8000 fixed=00 got=44', … '39:8004 fixed=00 got=39']
```

`37`·`39` 는 1장 빌드가 거울을 0 으로 지워 다음 장 레코드 자리로 비운 뱅크입니다. `fixed_mask` 는 모두 0 인 늘린 뱅크를 「표지만 다른 빈 뱅크」로 보고 쓰기에서 뺍니다. 그런데 거울 추정은 이 뱅크가 거울과 달라 예약합니다. 그래서 결과 롬에는 늘리기 표지 `DQ5X` 가 남고 검사가 멈췄습니다. 타이틀 거울 안에서는 이 규칙을 쓰지 않고, 표지 자리를 0 으로 쓰게 했습니다.

```
text              173978바이트  창 high 64:C406~69:EB9F
events                 6바이트  창 high 64:C400~64:C405
port.sfc sha1=c79fb95f… IPS 793478바이트(다시 붙여 같음)
```

`text` 는 자기가 비운 옛 메시지 자리에 놓였습니다. 결과 롬을 1장 롬과 견줬습니다.

- 메시지 3,632개가 기준 롬의 메시지에 고친 둘을 더한 것과 같습니다.
- 1장 롬과 다른 곳은 다음뿐입니다. 사이의 메뉴 자료와 조사 훅 `24:81D1` 은 그대로입니다.
  - 텍스트 훅(`24:8BC4`·`9E03`·`A63C`·`A660`·`A6C2`)
  - 이벤트 `23:E33A`
  - 비운 `59`·`5A`
  - 새 묶음 `64:C400`~`69:EB9F`
  - 비운 거울 자리
  - 빈 뱅크 표지

헤드리스 MesenCE 로 디코더도 돌렸습니다.

```
dq5portcheck.py rom/dq5.sfc work/tp/new/report.json --state …/ship.mss --only text
text: 3건 통과  text-129 6580DF · text-C70 69968E · text-742 6791E1 (64코드씩 같음)
```

옛 메뉴 롬으로 같은 빌드를 하면 `origin/main` 의 도구(압축본으로 꺼낸 것)와 바이트까지 같은 롬이 나왔고(`5f414e22…`), `--only text` 도 3건 통과했습니다.

## 틀렸던 것들

- 조사 코드를 받을지 `24:81D1` 훅이 있는지로 고르려 했습니다. 메뉴 롬에는 훅이 없는데 메시지는 이미 조사 코드를 써서, 메뉴 롬을 기준으로 삼으면 계속 막혔습니다.

## 남은 것

- 1장 롬은 DQ4 게임이라 dq5 의 배 선실 세이브스테이트로는 디코더만 돌렸습니다. 고친 메시지가 1장 게임 안의 대화 창에 뜨는지는 재지 않았습니다.
- 기준 롬이 쓰지 않는 조사 코드(`1021`~`1023`)는 `codes` 에 받지 않습니다.
