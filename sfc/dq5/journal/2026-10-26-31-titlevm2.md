# 2026-10-26-31: 타이틀 끝내기 14장과 HDMA 가 멈추는 CPU 시간, 전투 연출에 같은 주기 모형

[2026-10-26-24](2026-10-26-24-titlevm.md)에서 롬 코드로 그린 타이틀이 에셋 GIF 342장 가운데 328장과 같았고, A 로 타이틀이 끝나는 마지막 14장이 남았습니다. 그 14장을 맞췄습니다. 결과는 [dq5-graphics-format.md 「롬 코드로 그린 타이틀」](../docs/dq5-graphics-format.md#롬-코드로-그린-타이틀-dq5titlevmpy)에 있습니다.

## 1. 처음 갈리는 바이트

전원부터 실행의 6,740~6,800프레임을 덤프하고 해석기와 WRAM 을 견줬습니다. 늘 다른 자리를 빼자 6,759프레임에 `7E:0978` 하나가 먼저 갈렸습니다(해석기 `00`, 게임 `40`). 이 자리에 쓰는 것을 감시하자 NMI 처리기 첫머리 `00:8861`~`8864` 였습니다. 스택이고, `40` 은 NMI 가 쌓은 P 레지스터입니다. 게임에서는 이 프레임에 처리 도중 NMI 가 들어온 것입니다.

기다림이 불린 프레임을 견주자 게임은 6,759·6,761·6,763·6,765·6,767프레임에 기다림이 없었고, 해석기는 앞의 둘만 그랬습니다. 지연이 셋 모자라 팔레트가 두 배 빠르게 어두워졌습니다.

## 2. 얼마나 모자란가

NMI 와 기다림에서 MesenCE 의 `ppu.scanline` 을 적었습니다.

```
6761 N 240   6762 N 240   6762 W 261     (프레임 번호 줄 번호, N = NMI, W = 기다림)
6763 N 240   6764 N 240   6764 W 255
6767 N 240   6768 N 240   6768 W 247
```

NMI 는 240줄(겹쳐 보기 모드)에 들어오고, 이 프레임들은 다음 프레임 247~261줄에 기다림에 닿았습니다. 262줄을 겨우 넘긴 것입니다. 줄 수 × 1364 를 해석기의 마스터 주기 셈과 견주자, 타이틀 고리의 보통 프레임에서도 해석기가 0.94배쯤만 셌습니다.

CPU 주기 수(`cpu.cycleCount`)로 문턱을 두는 방법도 해 봤지만, 문턱을 43,300~43,700 으로 바꿔도 로고 밝히기 동안의 지연과 기다림이 42~45프레임 어긋났습니다.

## 3. HDMA

6% 는 HDMA 와 맞았습니다. HDMA 는 보이는 줄마다 CPU 를 멈추고 18 + 채널마다 8 + 바이트마다 8 마스터 주기를 씁니다. 타이틀은 채널 5·6·7 이 2바이트씩이라 줄마다 90, 240줄이면 21,600 입니다. NMI 뒤 셈이 줄 경계를 넘을 때마다 보이는 줄이면 이 값을 더하게 했습니다.

- 해석기의 비율이 0.97 이 됐고, 스냅숏 뒤 1,232프레임의 지연·기다림 순서가 게임과 하나도 다르지 않았습니다.
- 에셋 GIF 342장이 모두 같았습니다.
- `--out` 으로 같은 규칙(2프레임마다, 검은 화면 사이)의 GIF 를 쓰자 `title-opening.gif` 와 바이트째 같았습니다.

A 입력은 boot.lua 의 SEQ(`a@6759:4` 등)를 그대로 스냅숏 프레임 + NMI 수에 맞춰 `$4218` 로 넣었습니다. 앞 일지에서 입력을 몇 프레임 옮겨야 가까워 보였던 것은, 입력이 아니라 지연이 빠졌기 때문이었습니다.

## 4. 전투 연출에 같은 모형

`dq5fxvm.py` 에 `--clock` 을 더해 같은 해석기로 돌렸습니다. 처음에는 전투의 보이는 줄을 225줄로 두었는데, 연출 중 NMI 처리기에서 `ppu.scanline` 을 적으니 전투도 240줄(겹쳐 보기)이었습니다. 139벌 가운데 그림이 같은 것이 133벌에서 135벌이 됐습니다(`02`·`03`).

`6F` 는 처리 도중 NMI 가 여섯 번 연달아 드는 구간에서, 게임과 해석기가 모두 여섯 번이지만 끼어든 명령이 달랐습니다. 기다림에 닿은 줄도 게임 101줄, 해석기 148줄이었습니다. 스택 상대 주소(`d,S`)의 내부 주기를 더해도 바뀌지 않았습니다. `0C` 와 함께 남겼습니다.

## 5. F01F 와 DDDC

`F01F` 는 メガンテ 스크립트 안이라고 적었었습니다. 연출 포인터 표 `22:D7AA` 를 끝까지 보니 마지막 칸 `22:D8FC`(연출 `A9`)가 `F086` 을 가리켰고, 앞의 훑기는 `94` 까지만 봤습니다. 연출 `A9` 로 바꿔 띄우자 `F01F` 가 불려 OBJ 두 칸(OAM 버퍼 `03A0`~`03A5`)의 자리를 몬스터 표로 두었습니다.

`DDDC` 는 トラマナ 스크립트에서 변수 5(기준 칸 X)가 0 이 아니어야 닿습니다. 입구에서 `$9E78` 을 써 넣어도 닿지 않았습니다.

## 틀렸던 것들

- `F01F` 를 メガンテ(`15`) 안으로 봤습니다. メガンテ 는 `F085` 의 `3F` 에서 끝나고, `F086`~ 은 연출 `A9` 입니다.
- 전투의 NMI 줄을 225 로 봤습니다. 240 입니다.

- 끝 14장은 입력 시점이 어긋나서라고 봤습니다. 입력은 그대로였고, HDMA 가 멈추는 CPU 시간이 빠져 지연 셋이 없었습니다.

## 남은 것

- 스냅숏 없이 전원부터 롬 코드로: 소리 칩과 주고받는 부분과 SRAM.
- 전투 연출 `0C`·`6F`(처리 도중 NMI 가 끼는 명령), `DDDC` 를 부르는 장면.
