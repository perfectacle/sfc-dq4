# 2026-10-31-19: 통합 롬에서 인물 레코드·`patch` 작업 재기, `30`~`3F` 다시 재기

[통합 포팅 빌드](2026-10-27-26-portbuild.md)에서 게임 실측하지 않은 두 가지를 헤드리스 MesenCE 로 쟀습니다. `npc` 작업의 `records`(인물 레코드)와 `patch` 작업입니다. `dq5portcheck.py` 에 둘을 보는 검사를 더했고, 함께 [dq4 구간](2026-10-31-09-dq4ranges2.md)의 `30`~`3F` 표를 2장 맵이 들어간 지금 롬으로 다시 쟀습니다. 결과는 [통합 포팅 빌드의 검사](../docs/dq5-build-format.md#검사)와 [1장 빌드가 더 쓰는 자리](../docs/dq5-build-format.md#1장-빌드가-더-쓰는-자리)에 있습니다.

## 1. 통합 롬

`origin/main` `0b511c93` 에서 `dq4build.py --no-sound` 로 만든 메뉴 롬(`menu.sfc`)을 고정 롬으로 두었습니다. 1장 롬은 DQ4 게임이라 dq5 의 배 선실 세이브스테이트 장면(02/06 등)이 그대로 있지 않으므로 메뉴 롬을 썼습니다.

작업 둘은 각 도구의 검사가 쓰는 입력을 그대로 가져왔습니다.

- `npc`: 스크립트를 바꾸지 않는 `dq5npcrelocate/1` 에 `records` 로 `dq5npcrecordcheck.py` 의 문서를 줌. 02/06 의 밤 인물을 낮으로 옮겨 (24,12)에 그림 `18`·대화 `300` 으로 세우고, 다른 인물은 그림만 바꿈
- `patch`: `dq5tables.py patch` 결과 하나. `dq5tablecheck.py` 의 고친 값 가운데 서로의 장면을 바꾸지 않는 둘(`slot`: 물건 06 칸 1, `amount`: 피해량 01 바탕 40·폭 1)을 함께 넣음

```
npc.base           20173바이트  창 low  30:A937~30:F803
npc.alt            23986바이트  창 low  36:9DC0~36:FB71
port.sfc sha1=1305f9c7… IPS 506215바이트(다시 붙여 같음)
```

인물 목록은 타이틀 거울에서 비운 자리에 놓였습니다(`mirror_freed_overwritten` 44,159바이트). 그래서 `title` 검사도 돌렸고, 대기 16표본·A 입력 뒤 7표본의 덤프가 고정 롬과 모두 같았습니다.

## 2. 인물 레코드

먼저 있던 `npc` 검사를 그대로 돌리니 멈췄습니다.

```
오류: 02-06-day: 재배치 09/3220, 재배치 09/32A0
```

`dq5npcrelocatecheck.compare_case` 는 결과 롬의 인물 표를 원래 롬으로 예측합니다. 레코드를 고친 롬은 02/06 낮에 인물 하나가 늘고 그림이 바뀌므로 예측과 다릅니다. 예측할 롬(`model`)을 따로 받게 고쳤습니다. 원래 롬 장면은 지금처럼 원래 롬으로 견주고, 결과 롬은 「원래 롬에 레코드 패치만 넣은 롬」으로 견줍니다. 스크립트 포인터는 옮긴 자리(`layout`)로 봅니다.

레코드 문서가 `dq5npcrecordcheck.py` 의 것이면 그 도구의 장면도 결과 롬에서 돌리게 했습니다. 02/06 낮에 위로 걸어 말을 걸고(`TALK_TEST`), 밤에는 목록만 봅니다.

```
npc: 9건 통과
records  moved 058D34  cell [24, 12, 24, 0, 3]  messages ['1D1', '6C6']  night ['058D2C']
```

옮긴 인물이 (24,12)에 그림 `18`·대화 `300` 으로 섰고, 말을 걸자 메시지 `6C6`(`300 + 3C6`)이 떴습니다. 밤 목록에는 원래 밤 인물 하나만 남았습니다. 선실·02/06·01/05 낮밤과 대체 목록 8장면의 인물 표·포인터도 모두 맞았습니다.

## 3. `patch` 작업

`patch` 묶음은 먼저 패치의 쓰기가 결과 롬에 바이트까지 그대로 있는지 봅니다. 그다음 `dq5tablecheck.EDITS` 의 `slot`·`amount` 를 원래 롬으로 다시 만들어, 그 쓰기가 작업 패치 안에 모두 들어 있으면 그 장면을 결과 롬에서 돌립니다.

```
patch: 1건 통과
tables  writes 2  table_edits ['slot', 'amount']  slot {'read': '23B237=01', 'shown': 16}  amount [[[1, 40]], [[2, 40]]]
```

상점에서 どうのつるぎ 를 고르면 칸 표 `23:B237` 을 `01` 로 읽고 비교 창의 새 능력치가 16 이었습니다(원래 롬은 `00`·24). パパス 의 メラ 는 두 번 모두 한 마리에 40 이었고, `27:8073` 을 `28` 로 읽었습니다.

## 4. `30`~`3F` 다시 재기

2장 맵이 들어간 지금 1장 롬(`8d0fe4c8…`)으로 앞 일지의 표를 다시 쟀습니다. 묶음 경계는 앞 롬(`b8634d80…`)과 같았고 안의 값이 바뀌었습니다.

```
36:9E00~36:FFFF nonzero 17415 last nz 36:E339 zeroed 7214 new nonzero 17316
3E:8000~3E:FFFF nonzero 21972 last nz 3E:D6F3 zeroed 9787 new nonzero 21883
3F:8000~3F:FFFF nonzero 25864 last nz 3F:EAB9 zeroed 6077 new nonzero 25754
```

- `36:9E00`~`E339`: 그룹 빌드의 `newmap-6` 패치가 새 맵 레코드 18개를 둡니다(앞 롬은 4개, `36:AD6A` 까지).
- `3E`: 환경 맵 레코드가 30개로 줄어 `3E:D6F3` 에서 끝납니다.
- `3F`: 기본 인물 목록이 `3F:8000`~`EABD` 입니다.

dq4 1장 문서의 「두는 자리」 표는 아직 4장까지의 값(`36:AD6A`)입니다. 거울 추정으로 센 `30`~`3F` 의 빈 자리는 앞 롬과 같은 5,937바이트였습니다.

## 남은 것

- `patch` 의 게임 장면은 `dq5tablecheck.py` 의 `slot`·`amount` 둘만 봅니다. 다른 쓰기 도구의 결과는 바이트가 그대로 있는지만 봅니다.
- 고정 롬을 1장 롬으로 두면 dq5 장면 대부분이 DQ4 맵으로 바뀌어 있어 이 검사들을 그대로 쓸 수 없습니다.
