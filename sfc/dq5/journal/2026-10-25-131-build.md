# 2026-10-25-131: 패치 빌드 길과 빈 자리 지도

이제 읽기 분석보다 롬에 써 넣는 쪽으로 갑니다. 여러 세션이 따로 만드는 쓰기 도구의 결과를 한 롬으로 모으는 길을 먼저 깔았습니다. 형식과 결과는 [dq5-build-format.md](../docs/dq5-build-format.md) 에 있습니다.

## 1. 입력 형식부터

쓰기 도구는 저마다 `dq5patch/1` JSON 을 냅니다. 쓰는 자리(`BB:AAAA` 나 파일 위치), 바이트, 원래 롬이었던 바이트(`orig`)를 적습니다. 빌더는 그 목록들을 모아 한 바이트라도 겹치면 거부하고, 원래 롬을 쓰는데 `orig` 가 없거나 원래 롬과 다르면 거부합니다. 다른 세션이 먼저 고친 자리를 덮어쓰는 일을 빌드할 때 잡으려는 것입니다.

이미 롬 전체를 내는 도구(`dq5hangul.py retree`)는 `fromrom` 으로 바꿉니다. retree 롬을 목록으로 바꾸자 쓰기 13개, 146,209바이트였습니다. 그것만 넣어 다시 만든 롬은 retree 롬과 바이트까지 같았습니다.

## 2. 원래 롬은 거의 꽉 차 있다

뱅크마다 0 이나 FF 가 64바이트 넘게 이어지는 곳을 찾으니 32곳이었습니다. 여기에 읽기·실행 감시를 걸고 전원부터 8,000프레임, 선실 세이브스테이트에서 다섯 장면을 돌렸습니다. 뱅크 가운데 0 줄은 모두 읽혔습니다. 필드 맵 자료(`2A:ADC4` 등)와 `04:9750` 의 표입니다. 남은 것은 뱅크 끝의 0 줄뿐이었습니다.

뱅크 끝에서 읽힌 것은 `2F:FF86` 한 바이트였습니다. `2B:C2C7` 이 소리 자료를 `$2143` 으로 보내다 끝을 한 바이트 넘겨 읽는 자리입니다. 그래서 뱅크 끝 0 줄의 시작에서 16바이트를 띄워 22곳, 5,680바이트를 빈 자리로 잡았습니다. 다시 감시해도 읽히지 않았고, 22곳을 `55` 로 채운 롬도 부팅 시험을 통과했습니다.

## 3. 늘린 롬의 끝 두 뱅크

4MB 로 늘린 롬에서 `40`~`7D` 는 이미 재어 두었습니다. 파일 `3F0000`~ 은 어디로 보이는지 몰랐습니다. 표지를 쓴 롬을 켜 읽어 보니 `FE:8000`·`FF:8000` 이 표지 `7E`·`7F` 였습니다. `7E`·`7F` 는 WRAM 이라 이 64KB 는 `FE`·`FF` 로만 씁니다.

## 4. 같은 롬이 다른 화면을 낸다

부팅 시험을 처음 짤 때는 원래 롬끼리 견주어도 화면 해시가 달랐습니다. 까닭은 둘이었습니다.

- MesenCE 설정이 전원을 켤 때 RAM 을 무작위로 채웁니다(`Snes.RamPowerOnState` = `Random`). 인자 `--Snes.RamPowerOnState=AllZeros` 로 그 실행만 0 으로 켜자 첫 프레임 WRAM 이 모두 0 이었습니다.
- 그래도 PNG 가 달랐습니다. 같은 세이브스테이트에서 네 번 돌리며 600프레임마다 VRAM·CGRAM·OAM·WRAM 해시와 PNG 를 함께 남겼습니다. 메모리 해시는 네 번 모두 같은데, PNG 는 여섯 장 가운데 네 장이 실행마다 달랐습니다. 커서가 깜빡이는 때나 글자가 반쯤 찍힌 때처럼 한 프레임 앞뒤 화면이었습니다. 찍는 프레임이 흔들리는 것이라 메모리 해시를 견주기로 했습니다.

이렇게 맞춘 뒤 아무것도 넣지 않은 4MB 롬과 빈 자리를 채운 4MB 롬은 해시 11개가 원래 롬과 같았고, 둘 다 6,500프레임에 배 선실(17/00)에 닿았습니다.

## 남은 것

- 곡 자료 뱅크 끝의 빈 자리를 들어 보지 않은 곡이 읽는지
- 첫 장면 뒤 장면(필드·전투·메뉴)까지 보는 시험
