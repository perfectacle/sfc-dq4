# 2026-10-25-143: 곡 시퀀스 형식과 효과음

[SPC 드라이버 명령표와 곡 자료](2026-10-25-133-sound4.md) 에서 찾은 시퀀스 0x47개의 속을 풀었습니다. SPC 드라이버의 시퀀스 해석 루틴을 읽어 바이트마다 뜻과 인자 수를 정했습니다. 그 표로 디코더 [dq5song.py](../tools/dq5song.py) 를 쓰고, 디코더가 낸 음표를 DSP 에 실제로 쓰인 KON·피치와 프레임 단위로 견줬습니다. 결과는 [dq5-sound-format.md](../docs/dq5-sound-format.md) 「시퀀스 형식」「효과음과 스크립트」에 있습니다. 소리 자료와 덤프는 커밋하지 않았습니다.

## 1. 해석 루틴 찾기

드라이버를 `spc700.py` 로 `0800` 부터 6000줄 풀었습니다. 명령 바이트끼리 견주는 `CMP A,#$A0`·`#$B6`·`#$FE` 가 모인 곳이 `154E` 였습니다.

```
155C  3f bd 19  CALL $19BD      ; 트랙 바이트 하나
155F  68 a0     CMP A,#$A0
1561  b0 5b     BCS $15BE
1563  68 50     CMP A,#$50
1565  90 0d     BCC $1574
1567  2d        PUSH A
1568  3f bd 19  CALL $19BD      ; 50~9F 는 길이가 따라옴
...
15BE  68 b6     CMP A,#$B6
15C0  b0 03     BCS $15C5
15C2  5f c3 17  JMP $17C3       ; A0~B5 게이트 표
15C5  68 ff     CMP A,#$FF
15C7  f0 64     BEQ $162D       ; 트랙 끝
15C9  80        SETC
15CA  a8 db     SBC A,#$DB
15CC  90 13     BCC $15E1       ; B6~DA 는 건너뜀
15CF  1c        ASL A
15D0  5d        MOV X,A
15D1  f5 95 07  MOV A,$0795+X   ; 명령 처리 루틴 표
15D4  c5 df 15  MOV $15DF,A     ; 아래 CALL 의 대상을 고쳐 씀
```

명령 처리 루틴의 주소를 `CALL` 명령의 바이트에 써 넣고 부르는 방식이라, 첫 디스어셈블에서 `JMP [abs+X]` 를 찾을 때는 보이지 않았습니다. 표 `0795` 의 36개 주소를 하나씩 읽어, 루틴이 `19BD`(바이트 읽기)를 몇 번 부르는지로 인자 수를 정했습니다. 다음 음표를 미리 훑는 `15E5` 가 `EC`·`F6`·`EB` 는 2바이트, `F2`·`F3`·`A0`~`B5` 는 1바이트씩 건너뛰는 것도 이 인자 수와 맞았습니다.

머리는 곡을 시작하는 `11CA` 에 있었습니다. 첫 바이트를 템포(`03B7`)로, 둘째를 트랙 수로 읽고, 2바이트 오프셋을 시퀀스 시작에 더해 트랙마다 읽는 자리로 둡니다. 시퀀스 `02` 의 `71 05 0C 00 A9 00 55 01 0C 01 D7 01` 이 템포 `71`, 트랙 다섯입니다.

## 2. 모든 시퀀스를 끝까지 풀기

처음 `--check` 에서는 141개의 점프가 시퀀스 밖으로 나갔습니다. 모두 `F5` 였고, `191C` 를 다시 보니 `F5` 는 [횟수][오프셋 2] 순서였습니다. 고치자 0 이 되었습니다.

그다음은 닿지 않는 바이트였습니다. 시퀀스 `0D` 는 1820바이트 중 1095바이트가 남았습니다. 트랙 1 이 `F9`(돌아가기)로 끝나 거기서 멈췄기 때문입니다. `1970` 은 쌓인 돌아올 자리가 없으면 아무것도 하지 않고 지나갑니다. 부르기 스택을 들고 흐름을 따라가게 바꾸자, 남는 것은 네 시퀀스의 끝 1~2바이트뿐이었습니다.

```
$ uv run --locked python sfc/dq5/tools/dq5song.py rom/dq5.sfc --check
00: tempo FA tracks 1 bytes    5 unread   0
01: tempo 60 tracks 7 bytes 1209 unread   0
...
37: tempo 78 tracks 1 bytes  415 unread   1
...
71 sequences, 0 problems
```

## 3. KON 과 견주기

DSP 레지스터를 프레임마다 읽는 것으로는 KON 이 잘 안 잡혀, SPC 쪽 `$F2`·`$F3` 쓰기에 콜백을 거는 [lua/dq5dspw.lua](../tools/lua/dq5dspw.lua) 를 만들었습니다. MesenCE 의 `emu.addMemoryCallback` 에 `emu.cpuType.spc`·`emu.memType.spcMemory` 를 주면 SPC 의 쓰기도 잡힙니다.

필드 곡 `02` 의 목소리 2 는 512 프레임부터 피치 1716·2041·2291·2571 로 울렸습니다. 디코더의 트랙 2 는 음 `22`·`25`·`27`·`29` 였습니다. 피치 비가 2^(3/12)·2^(5/12)·2^(7/12) 로 음 차이와 같았고, 틱 24·48 간격이 프레임 16·32 간격이었습니다.

처음에는 트랙 1·3 이 길이 0 으로 무한히 돌았습니다. 둘 다 머리에 `F2` 가 있고 길이 없는 음표만 있었습니다. `F2` 가 켜는 `02CB` bit0 을 `1C64` 에서 찾아보니, 음표마다 바로 앞 트랙의 `0203`(길이)·`0204`(비율)를 복사하는 「앞 트랙 따르기」였습니다. 그래서 디코더의 재생기를 트랙 0 부터 틱마다 차례로 도는 드라이버 순서대로 바꿨습니다.

```
$ uv run --locked python sfc/dq5/tools/dq5song.py rom/dq5.sfc 02 --kon work/snd/k02/dspw.txt --start 500
track 0: 12 notes, 0.6635 frame/tick, max frame error 0.8, pitch mismatches 0
track 1: 12 notes, 0.6638 frame/tick, max frame error 0.7, pitch mismatches 0
track 2: 12 notes, 0.6611 frame/tick, max frame error 1.9, pitch mismatches 0
...
```

배 곡 `04` 는 트랙 여섯의 음이 틀렸습니다. 트랙 3 의 첫머리가 `E0 0C 00 01` 이었습니다. 곡 변수(`03E7`)가 1 이면 다른 자리로 가는 명령입니다. 배에 오를 때 APU 포트를 보니 `0C 04 01` 이 나갔고, `0C` 처리기 끝(`0C82`)은 X 번 스크립트를 돌렸습니다. 스크립트 표 `0801` 의 `01` 번은 `05 01`, 곧 곡 변수 = 1 이었습니다. `--flag 1` 로 풀자 일곱 트랙이 모두 맞았습니다.

마법 융단 곡의 트랙 5 는 악기를 `00` 에서 `04` 로 바꾼 뒤부터 첫 음과의 차이가 7.87반음 어긋났습니다. 샘플마다 음높이 값이 달라서이므로, 음 차이는 악기가 같은 이웃 음끼리만 보게 했습니다.

| 곡 | 트랙 | 최대 시각 차 | 음 틀림 |
| --- | --- | --- | --- |
| `02` 필드 | 5 | 1.9 | 0 |
| `03` 마법 융단 | 7 | 2.6 | 0 |
| `04` 배 | 7 | 1.9 | 0 |
| `0D` 天空城 | 7 | 1.7 | 0 |
| `17` 전투 | 6 | 3.5 | 0 |

틱당 프레임 x 템포는 다섯 곡 모두 약 75 였습니다.

## 4. 효과음

효과음 `33`·`34`·`37` 도 같은 형식이었습니다. 머리의 `E0` 여러 개로 X 에 따라 갈라지고, 목소리 7 에서 울렸습니다. 전투에서 맞을 때의 `0C 37` 은 X 가 `07`·`04`·`02`·`03` 이었습니다. `04`·`03` 갈래는 `E3`(잡음)이라 피치 대신 FLG 하위 5비트에 음 번호가 들어갔습니다(`1B46`). 프로브에 FLG 를 더하고 견주자 네 갈래 모두 맞았습니다.

## 5. 곡 묶음 둘째 바이트와 $0F1B

`2B:C3F2` 를 보니 곡 묶음 둘째 바이트 k 는 곡을 틀기 전에 보낼 샘플 수였습니다. 나머지는 곡이 시작한 뒤 `2B:C1DB` 가 보냅니다. 앞 일지의 전송 기록(곡 `02`: `03`·`00` 뒤에 `04`, 곡 `03`: 넷 뒤에 넷)과 같았습니다.

`$0F1B` bit6 을 켜는 `06:BDC8`·`06:C29C` 는 `dq5talk.py --calls` 로 보니 특수 기능 `06:BD99`·`06:BDB5`(플래그를 보고 여관 `06:E384` 를 부름)와 장면 `06:C297` 안이었습니다. 그 장면은 만들지 못했습니다.

## 틀렸던 것들

- `F5` 의 인자를 [오프셋][횟수] 로 보았습니다. [횟수][오프셋] 이었습니다.
- `F1`·`F2` 를 이음(슬러)으로 보았습니다. 앞 트랙의 길이를 따르는 명령이었습니다.
- `F9` 를 트랙의 끝처럼 다뤘습니다. 부르기 밖에서는 아무것도 하지 않습니다.

## 남은 것

- 시퀀스 명령 `E2`·`E6` 의 뜻과 `E5`·`E7`·`E8`·`FB` 의 세부, 스크립트 연산 `03`·`04`·`11`~`17`.
- `$0F1B` bit6 장면에서의 실측과 `02`·`03`·`04` 의 나머지 부르는 곳.
- 장면으로 정해지지 않은 곡의 이름.
