# 2026-10-30-22: 상자 256~575 의 다른 번호, 상자 몬스터 전멸, 비트 자리 다시 재기

[상자 번호 16비트 일지](2026-10-30-16-chest16.md)와 [남은 마스크 일지](2026-10-30-19-chest16fix.md)·[게임 검사 일지](2026-10-30-21-chest16stale.md)가 남긴 셋을 쟀습니다. 게임에서 연 상자는 300 하나뿐이었고, 상자 몬스터에게 전멸하면 어떻게 되는지 몰랐고, 비트 자리 `7E:28F3`~`291B` 는 훅이 없는 원본 롬으로만 골랐습니다. 상자 576개 롬에서 상자 256·263·264·421·575 를 열고, 상자 300 을 상자 몬스터로 바꿔 이기고 져 보고, 훅을 넣은 롬으로 접근 카운터를 다시 돌렸습니다. 결과는 [쓰기 형식 「상자 257개 이상」](../docs/dq5-build-format.md#상자-257개-이상---wide-at)에 넣었습니다.

## 1. 상자 576개 롬

상자 301개 롬은 01/02 에 블록 114개를 놓아 19/00 의 마지막 칸 (12,45) 를 상자 300 으로 만듭니다. 맵 연결 표에서 19/00 은 맨 끝이고, 그 앞 맵의 상자 수가 하나 늘 때마다 (12,45) 의 번호도 하나 늡니다. 그래서 블록 K 개를 놓으면 (12,45) 가 상자 186 + K 입니다. 575 까지 가려면 블록 389개가 필요합니다.

01/02 는 맵 연결 `count` 가 1바이트라 상자 255개(블록 253개)까지입니다. 나머지는 19/00 보다 앞에 있는 다른 맵 16/00(128×80)에 놓았습니다. 자리는 `dq5chestplace.plan` 에 행 하나를 통째로 넣고, 거부하는 블록을 빼 가며 골랐습니다.

```
01/02 (0~90, 24~38) 중 앞 139개, 16/00 (0~126, 30~34) 중 앞 136개
drop 01/02 [34, 28]    블록 안에 새 상자 칸이 0개(원래 상자 (35,29))
drop 01/02 [38, 28]    〃(원래 상자 (39,29))
ok 576 [('01/02', 255), ('16/00', 140)]   맵 연결 끝은 19/00
```

`dq5chestcheck.py` 의 `number_build(n)` 은 이 목록의 앞 n − 186 개만 놓고 (12,45) 의 내용물을 금화 n 으로 둡니다. 번호 다섯은 비트 자리의 경계를 고루 고른 것입니다.

| n | 비트 | 8비트로 읽었다면 |
| --- | --- | --- |
| 256 | `28F3 & 80` (첫 비트) | 상자 0 `2210 & 80` |
| 263 | `28F3 & 01` (바이트 끝) | 상자 7 `2210 & 01` |
| 264 | `28F4 & 80` (다음 바이트) | 상자 8 `2211 & 80` |
| 421 | `2907 & 04` (가운데) | 상자 165 `2224 & 04` |
| 575 | `291A & 01` (마지막 비트, 바로 뒤가 `291B`) | 상자 63 `2217 & 01` |

`test_dq5chestplace.py` 에 다섯 빌드의 표 끝이 19/00(5개)이고 상자 n 의 내용물이 금화 n 인지 보는 테스트를 더했습니다.

## 2. 다섯 번호를 열기

사례 `widenum_*` 은 선실에서 19/00 (11,46) 으로 가면서 8비트 번호의 원래 비트를 켜 두고, 상자를 엽니다. 연 뒤 기록 범위 `7E:2000`~`2A9F` 에서 바뀐 바이트를 모두 봤습니다.

```
dq5chestcheck.py rom/dq5.sfc --state work/state/ship.mss --case widenum_256 … --case widenum_575
widenum_256  7E:28F3 = 80  바뀐 것 201A·28F3       12:F839 index=00 mask=00 pend=80 ret=F51C  열린 상자 타일 4
widenum_263  7E:28F3 = 01  바뀐 것 2019·201A·28F3  index=00 pend=01                          4
widenum_264  7E:28F4 = 80  바뀐 것 2019·201A·28F4  index=01 pend=80                          4
widenum_421  7E:2907 = 04  바뀐 것 2019·201A·2907  index=14 pend=04                          4
widenum_575  7E:291A = 01  바뀐 것 2019·201A·291A  index=27 pend=01                          4
통과, 상자 번호 5개 열기·다시 들어오기 통과
```

다섯 모두 금화 n 을 얻고, 그 상자의 비트 하나만 켜졌고, `291B` 는 `00` 으로 돌아왔습니다. 미리 켠 8비트 번호의 비트는 그대로였고 상자를 이미 열린 것으로 보지 않았습니다. 256 은 금화가 100 → 356(`0164`)이라 아래 바이트 `2019` 가 `64` 그대로여서 바뀐 것이 둘입니다. 처음에는 바뀐 바이트를 `2019`·`201A`·비트로 고정해 256 에서 실패했고, 금화 바이트는 값에서 계산하게 고쳤습니다.

다시 들어갈 때 그리기는 처음에 연 상태에서 01/02 로 갔다가 돌아오려 했습니다. 그런데 `dq5warp.lua` 의 어디서나 방식이 아래 칸을 영역 이동 칸으로 덮고 아래로 걷는데, (11,46) 은 아래가 계산대, 위가 연 상자, 왼쪽이 가게 주인, 오른쪽이 벽이라 2500프레임 동안 움직이지 못했습니다. 그래서 연 뒤의 WRAM 에서 그 바이트 값을 읽어 선실에서 켜고 19/00 에 들어갔습니다([`wide_entry`](2026-10-30-16-chest16.md#4-상자-301개-롬)와 같은 길). 다섯 모두 연 상자 자리 넷이 열린 상자 타일(`9E`·`9F`)이 되었습니다. 비교한 장면은 같은 8비트 번호 비트를 켜고 들어간, 상자를 열기 전의 19/00 입니다.

## 3. 상자 몬스터

상자 300 의 보상을 `FFFD` 로 둔 롬(`widemon`)입니다. `FFFD` 는 상자에서 이벤트 전투 무리 `0D`(ひとくいばこ 하나)입니다. `lua/dq5chestcheck.lua` 에 `12:F4A4`(`JSL $01868B`, A = 무리)와 `12:F4A8`(돌아온 뒤 `JSR $F839`) 실행 기록을 더했습니다.

선실 상태의 주인공(Lv1, HP 24)은 ひとくいばこ 를 이기지 못합니다. 이기는 경우는 만든 롬에서 무리 `0D` 의 몬스터 칸 `23:D801`(파일 `11D801`, `36`)을 スライム(`00`)으로 바꿨습니다. 상자를 열고 전투를 거는 길은 같습니다.

```
widemon_win   reward FFFD → message 139 → battle group=0D → back pend=08
              → set index=05 mask=00 pend=08 ret=F4AA        끝 28F8=08 291B=00, 금화 100 → 101
widemon_lose  reward FFFD → message 139 → battle group=0D → (back·set 없음)
              → B7 → 7E → 82 → 8A → 84 → 86 → 88            끝 28F8=00 291B=08 $1E80=05 $1E81=00, 금화 100 → 50
```

이기면 전투에서 `12:F4A8` 로 돌아와 상자 300 의 비트를 켰습니다. 전멸하면 `12:F4A8` 로 돌아오지 않고, 같은 마을(19/00)의 교회에서 되살아났습니다. 비트는 꺼진 채이고 `291B` 에 `08` 이 남았습니다.

되살아난 뒤 신부는 「記録しても よろしいかな?」(82)를 묻고, いいえ 를 고르면 「前の記録まで もどっても よろしいのじゃな?」(8F)를 물어 둘 중 하나를 고르게 합니다. 처음에는 B 로 거절하며 빠져나가려 했는데 82 와 8F 를 번갈아 물었습니다. A 를 거듭 눌러 1번 칸에 기록하자(8A·84) 「おお神よ!」(88) 뒤에 움직일 수 있었습니다. `291B` 는 기록 범위 안이므로 이때 SRAM 에 `08` 로 들어갔을 것입니다(재지 않음).

그 상태에서 01/02 (34,31) 로 가서 상자 2(256 미만, 물건 `33`)를 열었습니다.

```
open f=243 pend=08 → count pend=00 → reward 0033 → set index=8E mask=08 pend=00 ret=EE25    끝 291B=00
```

열기 훅이 첫머리에서 남은 `08` 을 지웠고, 상자 2 는 `$1E81` = `08` 로 원래 길을 지났습니다. 잠긴 상자·가득 찬 가방에서는 같은 상자 300 을 다시 열어 봤는데, 여기서는 다른 상자(256 미만)를 연 것입니다.

전멸 뒤 입력이 끝난 장면을 다음 단계의 세이브로 쓰려고 `dq5chestcheck.lua` 에 `SAVE` 를 더했습니다. 처음에는 저장하자마자 `emu.stop` 해 파일이 생기지 않았습니다. 툴킷의 `saveState` 는 다음 프레임에 쓰므로 세 프레임 뒤에 멈추게 했습니다.

## 4. 비트 자리를 훅을 넣은 롬으로 다시 재기

원래 상자 표에 `--wide-at 3F:E000` 만 넣은 롬(2MB, 쓰기 10개)으로 같은 770장면을 돌리고, `28F3`~`291B` 를 둘러싼 틈 `28E2`~`2949` 를 셌습니다.

```
dq5chestreloc.py rom/dq5.sfc patch tables.json -o hook.dq5patch.json --wide-at 3F:E000
dq5cdlsweep.py hook.sfc work/state/ship.mss OUT --kinds maps,battles,field,extra,effects --acc 28E2-2949 --jobs 10
실행 770, cdl.bin 을 남긴 실행 770
28E2-2949 접근: 주소 104곳, acc.txt 없는 실행 0
  28E2~2949 의 104곳 모두  extra/church-save-load 읽기 10 쓰기 8
  28F2  battles/35 읽기 18, effects/35 읽기 2
  291C  battles/36 읽기 18, effects/36 읽기 2
  2946  battles/37 읽기 9,  effects/37 읽기 2
```

원본 롬으로 잰 것과 같습니다. `28F3`~`291B` 에 닿은 것은 교회 기록·불러오기의 복사·체크섬·지우기뿐입니다.

이야기를 진행한 장면도 보려고 `dq5cdlsweep.py` 에 `saves` 종류를 더했습니다. `--saves` 로 준 세이브스테이트마다 `tools/lua/walk.lua` 로 네 방향을 걷고, 명령 창 여덟 칸(4행 2열)을 하나씩 골라 A 세 번·B 네 번을 누릅니다. 필드는 8프레임에 한 번 입력을 읽으므로(`00:8185`) 처음에 4프레임으로 누른 것은 명령 창이 열리지 않아, 8프레임으로 고쳤습니다(코드 바이트 40,851 → 52,671, 루이다 세이브 9실행).

```
dq5cdlsweep.py hook.sfc work/state/ship.mss OUT --kinds saves --saves work/state/dq5-*.mss(타이틀 빼고 16개) work/state/party4-wagon.mss --acc 28E2-2949
실행 153, cdl.bin 을 남긴 실행 152
28E2-2949 접근: 주소 0곳, acc.txt 없는 실행 0
```

세이브는 노예·석상·루이다·그란바니아·결혼식·교회·아내 등 이야기 단계의 맵 16곳과 동료 몬스터 둘을 데린 마차 필드입니다. 다만 화면을 보니 이 세이브들은 선실에서 이벤트 플래그를 켜고 순간이동해 만든 장면이라 주인공은 Lv1, HP 24 그대로였고 동료 칸·맡긴 칸이 차 있지 않습니다. 실제로 이야기를 진행해 쌓인 동료 몬스터·사람 동료 칸을 다루는 코드는 이 측정에 들어 있지 않습니다.

## 틀렸던 것들

- 상자를 연 뒤 01/02 로 갔다가 돌아오는 「실제 다시 들어가기」를 하려 했습니다. (11,46) 에서는 어느 쪽으로도 걸을 수 없어 `dq5warp.lua` 가 2500프레임 동안 떠나지 못했습니다(2절).
- 전멸 뒤 신부의 물음을 B 로 거절하며 빠져나가려 했습니다. 82(기록)와 8F(앞 기록으로 돌아감)를 번갈아 물어 둘 중 하나를 골라야 했습니다(3절).
- 바뀐 바이트를 금화 두 바이트와 비트로 고정했습니다. 금화 356 은 아래 바이트가 100 과 같아 256 에서 틀렸습니다(2절).

## 남은 것

- 상자를 연 자리에서 실제로 맵을 떠났다가 돌아오는 다시 들어가기. 계산대 안 (12,45) 대신 걸어 나갈 수 있는 상자 칸으로 번호를 맞춰야 합니다.
- `FFFE`(ミミック, 무리 `0C`)는 재지 않았습니다. 같은 `12:F4A4` 로 가는 코드 읽기입니다.
- 전멸 뒤 교회 기록에 `291B` = `08` 이 들어가는지(SRAM 덤프), 그 세이브를 불러와 상자를 열 때 지우는지.
- 실제로 이야기를 진행한 세이브(동료 몬스터·맡긴 동료·사람 동료 칸이 찬 것)에서 `28E2`~`2949` 접근. 지금 세이브들은 선실에서 만든 장면이라 Lv1 주인공이고, 처음부터 끝까지 진행한 측정은 없습니다.
