# 2026-10-30-07: 필드 타일 1,024개·세계 0 의 2·3번 줄 벌·실내 BG 팔레트 세트 늘리기

[그림 쓰기](2026-10-27-47-gfxwrite.md)와 [필드 그림 늘리기](2026-10-29-01-fieldgrow.md)가 남긴 한도 셋을 늘렸습니다. 필드 타일은 512개에서 1,024개로, 세계 0 의 2·3번 줄 벌은 8벌에서 128벌까지, 실내 BG 팔레트 세트는 69개에서 256개까지 씁니다. 늘린 타일의 속성 표(`2A:D512`)도 함께 늘렸습니다. 이 표는 그동안 문서에 없던 것입니다. 쓰기 형식은 [필드 그림](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)·[실내 맵 그림](../docs/dq5-build-format.md#실내-맵-그림-dq5mapgfx1)에 있고, 구조는 [필드 형식 「타일 512개 넘기기」](../docs/dq5-field-format.md#타일-512개-넘기기)에 있습니다.

## 1. 타일 512개 뒤의 VRAM 자리

블록 번호가 9비트(`00:BBF7`)인 것과 타일 번호가 9비트인 것은 따로 따져야 합니다. 이번에 늘린 것은 타일 번호입니다. 먼저 VRAM 에 자리가 있는지 봤습니다. 필드 (341,56) 의 PPU 상태는 이렇습니다.

```
BG1 chr 2000 tilemap 0800 (64x32)   BG2 chr 2000 tilemap 0000 (64x32)
BG3 chr 1000 tilemap 1C00           OBJ 6000
```

BG1·2 의 타일맵 워드는 타일 번호가 10비트라, 타일 512~1023 은 워드 `4000`~`5FFF` 에 놓입니다. 이 자리를 쓰는 곳을 찾으려고, VRAM 쓰기 카운터를 10프레임마다 `0x100` 워드 칸으로 나눠 적는 프로브를 세 장면에 돌렸습니다.

```
걷기·명령 창   (기록 없음)
이벤트 전투    f00570 4000~5FFF 전부 512  (전투 들어감)
배·무작위 전투 f01390 4000~4500, 5000~5FFF  f01400 4500~4FFF
```

필드에 선 동안에는 아무도 쓰지 않았고, 전투가 들어갈 때만 전투 그림으로 덮었습니다. 전투에서 돌아올 때 VRAM 에 무엇을 다시 쓰는지 `dq5vramlog.lua` 로 보니, BG3 창 글자(`14B0`)·OBJ(`6000`~)·타일맵(`01:B79B`·`B7AA`)뿐이었습니다. 필드 타일 `2000`~`3FFF` 는 전투가 건드리지 않아 그대로 둡니다. 타일맵을 쓰는 `01:B79B` 에서 스택을 따라가면 `01:8715` → `01:8A87` 이고, 그 안의 `JSL $01B4D5`(`01:8AA8`)가 화면을 끈 채 타일맵을 CPU 로 씁니다.

그래서 늘린 타일은 두 번 보냅니다. 필드에 들어갈 때는 세계 훅 자리인 `01:A4A7` 에서 보냅니다. RLE 를 풀기 전이지만 화면은 이미 꺼져 있습니다. 전투 뒤에는 `01:B4D5` 자체를 훅으로 바꿔 `$BE` bit7 이 0(필드)일 때만 보냅니다. 처음에는 `01:8AA8` 의 `JSL $01B4D5` 를 바꿨는데, 독립 리뷰에서 `01:B4D5` 를 부르는 곳이 하나 더 있다는 지적을 받았습니다(7절). 압축은 하지 않고 롬에서 DMA 채널 7 로 바로 보냅니다. `7E:C000`~ 는 필드가 쓰는 자리라 풀어 둘 곳이 없기 때문입니다. 풀기 루틴 `01:A64F` 는 `$4370`·`4371`·`4372`·`4375` 를 스스로 정하고, `$4376` 은 앞 DMA 가 0 으로 끝내므로 채널을 같이 써도 됩니다.

## 2. 타일 번호가 9비트라는 가정

번호를 읽는 곳을 롬에서 긴 주소로 찾았습니다. 블록 표는 `00:BC72`·`BC78`·`BC80`·`BC8D`, 니블 표는 `00:BBB4`·`BBBE`·`BBDA`·`BBE4` 뿐입니다.

블록 `+4` 바이트는 위 니블이 칸마다 9번째 비트(`80 >> 칸`)이고, 아래 니블은 원본 1,022항목에서 모두 0 이었습니다. 이 아래 니블을 10번째 비트로 씁니다. `00:BCA4` 에 마침 `08 04 02 01` 마스크가 있어(세계 지도 9번째 비트용 `00:BCA0` 표의 뒤 절반), 훅은 `AND $BCA4,Y` 와 `AND $BC9C,Y` 를 차례로 하고 `A = 비트9 << 1 | 비트8` 을 돌려줍니다.

니블 표는 타일 2개에 한 바이트라 1,024개면 512바이트가 필요합니다. 세계 훅의 니블 읽기가 `세계 × 256` 이던 것을 `CLC` 자리에 `ASL A` 를 넣어 `세계 × 512` 로 바꿨습니다. 디코더 `dq5field.nibble_table` 은 이 한 바이트로 간격을 가립니다.

## 3. 처음 돌린 롬의 칸이 한 칸씩 밀렸다

타일 512~1023 을 0~511 의 비트 반전으로 두고, 블록 두 층의 모든 칸 타일에 512 를 더한 롬을 만들었습니다. 처음 검사는 타일맵 칸마다 「그 칸의 워드가 그 타일 번호의 디코더 워드와 같은가」만 봤는데, 세계 0·1·2 모두 통과했습니다. 세계 1 의 칸 하나만 팔레트가 맞지 않았습니다.

그 칸을 따라가 보니 원본 게임은 타일 `1A2`, 고친 롬은 `3A3` 이었습니다. `1A2 + 512` 라면 `3A2` 여야 합니다. 같은 자리 원본 칸과 견주는 검사로 바꾸자 칸 2,176개 가운데 1,111개가 원본 타일 + 513 이었습니다. 짝수 타일에서 bit0 이 켜진 것입니다.

원인은 `00:BBAC` 입니다.

```
00:BBD2  LDA $94      ; 16비트, 아래층 타일 번호
00:BBD4  LSR A
00:BBD5  TAX          ; 니블 자리
00:BBD6  SEP #$20     ; A 의 윗바이트는 (타일 >> 1) >> 8 그대로
00:BBDA  LDA $2AD712,X
  …
00:BBEF  REP #$20
00:BBF1  XBA          ; 그 윗바이트가 아랫바이트로
00:BBF2  ORA $94
```

타일이 512 미만이면 `(타일 >> 1) >> 8` 이 늘 0 이라 아무 일이 없습니다. 512 이상이면 1 이 되어 OR 로 bit0 이 켜집니다. 위층도 같은 꼴입니다. 넓은 니블 훅이 돌아갈 때 A 의 윗바이트를 0 으로 두게 고치자, 같은 자리 비교에서 모든 칸이 원본 타일 + 512 가 되었습니다.

## 4. 타일 속성 표 `2A:D512`

움직임 시험에서 고친 롬의 주인공이 위로 걷지 못했습니다(원본은 (338,52), 고친 롬은 (338,56)). 블록 표를 읽는 곳을 다시 보다가 `00:BCA8` 을 찾았습니다.

```
00:BCAB  JSR $BBF7          ; 그 칸의 블록 → $94(아래층)·$96(위층) 타일 번호
00:BCAE  LDA $96
00:BCB0  AND #$01FF
00:BCB3  BNE $BCBA          ; 위층 타일이 0 이 아니면 위층
00:BCB5  LDA $94
00:BCB7  AND #$01FF
00:BCBA  TAX
00:BCBD  LDA $2AD512,X      ; 타일마다 1바이트
```

니블 표 바로 앞의 512바이트가 타일 속성 표였습니다. `00:C82C`·`C83B`·`E32E`·`01:8192`·`2B:81E9`·`81F6` 이 부르고, 값을 `45` 와 견주는 곳(`00:C844`)이 있습니다. 시험 롬은 위층 타일 0 까지 512 로 바꿔서, 「위층 없음」이던 칸이 위층 타일 512 의 속성(타일 0 의 것)을 읽었던 것입니다. 시험 롬에서 위층 0 은 그대로 두었습니다.

늘린 타일이 제 속성을 가지게 `AND` 둘을 `#$03FF` 로, 표 읽기를 1,024바이트 표로 바꿨습니다. 늘린 타일 512개의 속성을 한 값으로 채운 롬 다섯과 원래 속성 그대로인 롬으로 (341,56) 에서 왼쪽·위·오른쪽·아래로 32프레임씩 걸어 봤습니다(`dq5gfxlimitcheck.py` 의 `move-*`).

| 늘린 타일 속성 | 끝 자리 |
| --- | --- |
| 원래 속성(타일 − 512 의 값) | (340,56) |
| `45`·`00` | (342,56) |
| `80`·`82`·`95` | (341,56), 한 칸도 못 감 |

늘린 표를 읽는다는 것이 확인되었습니다. 값마다의 뜻은 보지 않았습니다.

## 5. 세계 0 의 2·3번 줄 벌

`01:A132` 는 `$075E` 이상인 시간대 항목을 뒤에서부터 찾아 색인(벌 × 2)을 X 에 두고, `01:A166` 에서 `01:A189` 포인터를 읽습니다. 벌·포인터·세계 1·2 벌이 `01:A16B`~`A3F0` 에 붙어 있고 바로 뒤가 코드라 제자리에서 늘릴 수 없습니다. 벌을 옮기는 `01:A090` 의 DMA 뱅크는 `01:A0B1` 즉값인데, 같은 DMA 가 `$4374` 를 바꾸지 않은 채 물결 색(`01:A0E3` 의 `ADC #$A0F6`)도 옮깁니다. 그래서 벌을 옮길 때 물결 표도 같은 뱅크로 옮겼습니다.

찾기는 `JSL` 훅으로(X 는 8비트라 `CMP long,X`), 포인터 읽기는 `LDA long,X / TAY / RTL` 로 바꿨습니다. 밤 인물 팔레트는 색인을 `01:A145` 의 `CPX #$0C` 와 견주므로 밤 시작 벌도 고칠 수 있게 했습니다.

시험 롬은 벌 12개(8~11 이 새 색), 시간대 12항목, 밤 시작 벌 10 입니다. `$075E` 를 여섯 값으로 두고 (341,56) 에 서서 덤프했습니다.

| `$075E` | 벌 | 11·12번 줄 | 원본 게임과 |
| --- | --- | --- | --- |
| `0000` | 8 | 낮 | 다름 |
| `0001` | 9 | 낮 | 다름 |
| `0050` | 2 | 낮 | 같음 |
| `00F1` | 6 | 낮 | 다름(원본은 밤) |
| `0120` | 10 | 밤 | 다름 |
| `01A0` | 11 | 밤 | 다름 |

2·3번 줄 색 26개가 모두 표대로 고른 벌과 같았습니다.

## 6. 실내 BG 팔레트 세트

`10:DE56` 의 `LDA $DFE4,X` 가 세트 표를 읽고, 그 포인터로 `LDA ($00),Y`(DB = 10)가 목록을 읽습니다. 세트 표 뒤가 목록, 목록 뒤가 줄이라 뱅크 10 에 자리가 없습니다. 원래 롬의 빈 자리 `10:FFE8` 에 스텁을 두었습니다. 스텁은 옮긴 세트 표를 긴 주소로 읽고 DB 를 그 뱅크로 바꿉니다. 그 뒤 `LDA $1EAE` 가 DB 로 읽으므로 WRAM 거울이 있는 `30`~`3F` 에만 둡니다. 줄 읽기 `LDA $E5C8,Y` 도 DB 를 따르게 되므로, 줄을 옮기지 않았어도 `10:FFE0` 스텁이 원래 줄을 긴 주소로 읽게 합니다. 돌아갈 때는 부른 쪽의 `PLB` 가 DB 를 되돌립니다. 이 읽기로 들어오는 입구는 셋입니다. 맵 팔레트 `10:DDDD`, 플래그 팔레트 세트 `10:DDCF`, 그리고 `10:DDB2` 입니다. `10:DDB2` 는 옮길 곳을 `7E:3B14`(`$1EAE`·`$1EB0`)로 두고 `10:DE55` 로 들어가는데, `02:D828`·`1E:E03F`·`E056`·`E07E` 가 JSL 합니다. 세 입구 모두 `PHB / PHK / PLB` 로 시작해 `PLB` 로 끝나므로 스텁이 바꾼 DB 는 돌아갈 때 돌아옵니다(코드 읽기).

세트를 70개로 늘리고 새 세트 69 의 낮 목록을 새 목록으로 둔 롬에서, `dq5palsetwrite.py` 로 01/01 을 세트 69 로 바꿨습니다. 01/01 에 서자 BG 1~7번 줄이 새 목록의 줄과 같았고 원본 게임과 달랐습니다. 세트를 바꾸지 않은 01/00(46)·02/00(6)·21/02(5)는 원본 게임과 같았습니다.

## 7. 화면 다시 그리기도 `01:B4D5` 를 부른다

`01:B4D5` 를 긴 주소로 부르는 곳은 `01:8AA8` 말고 `00:A788` 이 있습니다. `00:A771` 은 화면을 다시 그리는 루틴이고 `00:A766` 을 거쳐 `00:A79E`·`C705`·`C78D`·`CBA7`·`CBC7`·`CC4B` 가 부릅니다. `C705`·`C78D` 는 `JSL $2AF22C` 바로 뒤라 맵을 바꾸는 길입니다. 부른 곳마다 실행을 적어 보니 필드로 걸어 나올 때 이 차례였습니다.

```
f00383 00:A788   (01/00 에 들어감, $BE bit7 = 1)
f00439 01:A4A7   (필드 타일 올리기)
f00462 00:A788   (CC4B 에서, 필드)
f01756 01:8AA8   (이벤트 전투 뒤)
```

필드에 선 채 `4000`~`5FFF` 를 덮은 뒤 `00:A771` 만 도는 장면은 찾지 못했습니다. 그래서 그 자리를 439프레임 뒤·462프레임 앞인 450프레임에 Lua 로 지워 보았습니다. 훅을 `01:8AA8` 에 둔 롬은 470프레임에도 비어 있었고, `01:B4D5` 에 둔 롬은 470프레임에 늘린 타일이 돌아와 있었습니다. 검사 도구에는 대조로 `01:B4D5` 만 원본 4바이트로 되돌린 롬을 넣었습니다. 이 롬은 470프레임에도 비어 있고, 두 롬 모두 450~469프레임에 돈 것은 `00:A788` 뿐(`01:A4A7` 없음)이었습니다.

`01:B4D5` 는 `JSR $B50A / RTL` 4바이트입니다. 처음 만든 훅은 `JML` 로 바꾸고 끝에서 `PEA $B4D7 / JML $01B50A` 로 원래 일을 하게 했는데, 01/00 을 불러오다 멈췄습니다. 4바이트 `JML` 이 `01:B4D8` 의 `RTL` 까지 덮어, `B50A` 의 `RTS` 가 그 자리(훅 주소의 마지막 바이트)로 돌아갔기 때문입니다. 돌아올 자리를 뱅크 01 의 다른 `RTL`(`01:8A87` 의 끝 `01:8ABA`)로 바꾸자 맞았습니다.

## 8. 게임에서 확인

`dq5gfxlimitcheck.py` 로 21건이 통과했습니다. 늘린 타일은 tiles 롬이 `60:8000`, 속성 시험 롬이 `35:8000` 에 두고, 두 자리 모두 VRAM 워드 `4000`~ 과 같았습니다. 결과 표는 [실측](../docs/dq5-build-format.md#필드-타일세계-0-벌실내-세트-늘리기-실측)에 있습니다. 앞선 검사 `dq5fieldgfxcheck.py`(13건)·`dq5fieldgrowcheck.py`(44건)·`dq5gfxwritecheck.py`(11건)도 고친 도구로 다시 돌려 모두 통과했습니다.

## 틀렸던 것들

- 처음 타일맵 검사는 칸마다 「그 워드가 그 타일 번호의 올바른 워드인가」만 봐서, 타일 번호가 1 밀려도 팔레트까지 그 번호대로면 통과했습니다. 세계 1 의 칸 하나가 짝 타일의 팔레트를 들고 있어 드러났습니다. 같은 장면을 원본 롬으로 돌려 같은 자리 칸과 견주게 바꿨습니다.
- 다시 보내는 훅을 처음에는 부르는 곳 `01:8AA8` 에 두어, 같은 루틴을 부르는 `00:A788`(화면 다시 그리기) 길이 빠졌습니다(독립 리뷰). 루틴 `01:B4D5` 자체로 옮겼습니다. 그때 `JML` 이 루틴 끝 `RTL` 까지 덮는 것을 놓쳐 한 번 멈췄습니다(7절).
- 니블 훅은 [필드 그림 늘리기](2026-10-29-01-fieldgrow.md) 때 「A 의 윗바이트를 지킨다」고 만들었습니다. 원본에서는 그 윗바이트가 늘 0 이라 지키는 것과 0 으로 두는 것이 같았습니다. 512 이상에서는 0 으로 두어야 합니다.
- 걷기 시험이 오래 걸어 무작위 전투가 붙자, 전투 그림이 늘린 타일 자리를 덮어 「걷기만 해도 덮인다」로 보였습니다. 짧게 걷고 덤프 때 `$1001` = 0 을 보게 했습니다.
- 시험 롬에서 위층 타일 0 에 512 를 더해 걷기가 원본과 달라졌습니다. `00:BCA8` 이 위층 0 을 「위층 없음」으로 보기 때문입니다(4절).

## 남은 것

- 늘린 타일을 다시 보내는 곳은 필드에 들어갈 때와 `01:B4D5`(전투 뒤, 화면 다시 그리기) 둘입니다. 걷기·명령 창, 이벤트 전투, 배에서 붙은 무작위 전투, キメラのつばさ·ルーラ(필드를 다시 불러옴), 마법 융단으로 확인했습니다(다시 불러오기 실행 기록과 융단 사례는 [뒤 일지](2026-10-30-08-lowfix2.md)에서 검사 도구에 넣음). キメラのつばさ·ルーラ 에서는 5프레임마다 VRAM 쓰기 카운터를 보니 `4000`~`5FFF` 에 쓴 것이 두 훅의 DMA 뿐이었고, 원래 롬은 이 자리에 아무것도 쓰지 않았습니다. 그래서 `00:A788` 앞에서 게임이 이 자리를 덮는 장면은 아직 찾지 못했고, `00:A771` 길의 다시 보내기는 Lua 로 지운 장면으로만 확인했습니다. 세계를 오가는 이벤트, ベネット 의 지도처럼 큰 그림을 띄우는 장면은 헤드리스로 재현하지 못해 보지 않았습니다.
- 늘린 타일을 보내는 DMA 는 VRAM 주소를 둔 바로 뒤에 시작하지만, 그 사이에 NMI 가 VRAM 주소를 바꾸면 어긋납니다. 원래 타일을 올리는 루프도 같은 조건이고 실측에서는 어긋나지 않았습니다.
- 타일 속성 값의 뜻(`45`·`80`·`82` 등)과 부르는 곳 여섯이 각각 무엇을 정하는지.
- 블록 번호 512개 넘기기(세계 지도 9번째 비트, `00:BBF7`)와 블록 표 옮기기는 하지 않았습니다.
- 세계 1·2 의 시간대 벌. 두 세계는 `01:9F4A` 가 시간대 경로를 건너뛰어 한 벌만 씁니다. 늘린 세계 0 벌을 ラナルータ·여관 뒤에 고르는지도 보지 않았습니다.
- 실내 새 세트의 밤 목록(`JSL $218000` 이 밤으로 돌려줄 때)과, 맵 → 세트 표 말고 플래그 팔레트 세트(`10:DDCF`)·`10:DDB2`(`7E:3B14` 로 옮김, `02:D828`·`1E:E03F`·`E056`·`E07E`)로 새 세트를 고르는 장면은 실측하지 않았습니다. `10:FFE8` 스텁은 원래 롬의 빈 자리라 다른 트랙의 패치가 같은 자리를 쓰면 겹칩니다(빌더가 겹침을 거부).
