# 2026-10-30-32: 전투 메시지 창 넓히기와 높이기

[일지 29](2026-10-30-29-msgwindow.md)에서 전투 메시지 창 18·25 는 X 만 옮길 수 있게 하고, 너비·Y·높이는 글자 격자 `7E:1DD5` 뒤의 필드 변수와 BG3 7~20줄 효과 층 때문에 막아 두었습니다. 이번에는 글자 격자를 빈 WRAM 으로 옮기고 격자 루틴을 새 코드로 돌려, 너비 28~31(글자 26~29칸)과 높이 7~13(글자 3~6줄)을 쓸 수 있게 했습니다. 창을 21줄보다 위로 올리면 효과 층 전송을 창 위까지로 줄여 창이 효과에 지워지지 않게 했습니다. 다만 그만큼 효과와 몬스터가 창에 가려집니다. 형식은 [창 자리·크기](../docs/dq5-build-format.md#창-자리크기-dq5windows1)에 있습니다.

## 1. 격자를 만지는 곳

슬라임 전투에서 `7E:1DD5`~`1E90` 읽기·쓰기를 PC 마다 모으고, 뱅크 24 실행 커버리지로 리스팅을 만들었습니다. 쓰는 곳은 `24:8140`·`814B`(모두 지우기), `24:87CE`·`87E0`·`87ED`(줄 지우기), `24:A4E0`·`A4EB`(글자 하나), 읽는 곳은 `24:A5E9`(격자 → 버퍼)였습니다. 줄 올리기 `24:A569`·`A5C5` 의 접근은 처음 감시에 걸리지 않았는데, 커버리지에는 52번씩 실행되어 있었습니다. 감시를 건 뱅크(`24`·`A4`·`00`·`80`·`04`·`20`·`7E`)가 아닌 데이터 뱅크로 낮은 WRAM 거울에 닿은 것으로 보입니다.

격자 크기를 박은 상수는 루틴 안의 즉값입니다. `9B`(156 - 1), `19`(26 - 1), `34`(두 줄), `1A`·`0C`(한 줄 26칸, 버퍼 줄 나머지), `68`(네 줄), `9C`, `1E57`(마지막 줄)입니다. 줄 수 3 은 `24:A4FA` 말고도 세 곳에 더 있었습니다. 줄 바꾸기 제어 코드 `24:85FA`, 둘째 줄부터 지우기 `24:864C`, 남은 줄 지우기 `24:8677` 의 `CMP #$03` 과, 모두 지우기 `24:8613` 의 `LDA #$02`(마지막 줄부터 지움)입니다.

`$0F0E` 를 읽는 다른 곳은 필드 메시지 길이었습니다. 배 선실에서 파파스에게 말을 걸자 `24:8181`(줄 3 이면 `24:A3EF` 로 줄 올리기)과 `24:82A1`·`9E94`(글자를 점 단위로 그림)가 돌았고 격자 루틴은 돌지 않았습니다. `24:8359`·`83E9` 도 `24:A3EF` 를 부르고, `24:841F` 의 ▼ 자리 표 `24:84AB`(20·23·25·27줄 15칸)도 이 길의 것입니다(코드 읽기).

## 2. 빈 WRAM

격자 루틴은 데이터 뱅크 `24` 나 부른 쪽 뱅크에서 `$1DD5,X` 로 닿으므로, 같은 꼴로 두려면 낮은 WRAM 이어야 합니다. 일지 [2026-10-27-46](2026-10-27-46-wramfree.md)의 장면 모음으로 `dq5cdlsweep.py --acc 1800-1EFF` 를 돌렸습니다.

```text
실행 770(실내 맵 346, 몬스터 236, 세계 3, 행동 171, 그 밖 14), acc.txt 없는 실행 0
접근 없음: 1800-181F(32) 1A86-1A97(18) 1ABC-1AF8(61) 1B68-1BB0(73) 1C9F-1CF8(90) 1D68-1D8A(35) 1E71-1E81(17)
```

156바이트 격자도 들어갈 자리가 없었고, 그나마 큰 `1C9F`~`1CF8` 과 `1D68`~ 는 DQ4 메뉴 빌드(`dq4windowname.asm` 의 `!wn_*`)가 씁니다. 그래서 격자 루틴을 새 코드로 다시 쓰고 격자를 높은 WRAM 에 두기로 했습니다. 같은 770개를 `--acc A000-FFFF` 로 다시 돌리자 `7E:A5F1`~`A91F`(815바이트)와 `7E:A921`~`ABFF` 가 접근이 없었습니다. `7E:A920` 은 연출 `0C`·`26` 에서 읽기만 있었습니다. 격자는 `7E:A600`~`A7FF` 에 둡니다.

## 3. 새 코드

`dq5windowwrite.py` 는 너비·높이를 바꾸면 `--message-at` 자리에 루틴 여섯(`24:8133` 의 채우기, `87AA`, `A4A4`, `A569`·`A5C5`, `A5D9`)을 옮긴 코드를 두고, 원래 자리 앞을 `JSL` / `RTS` 로 덮습니다. `24:8133` 은 롱 호출 24곳(바이트 검색)이 그대로 들어오도록 그 안의 채우기(`24:813B`)만 `JSL fill` / `BRA $8151` 로 바꿨습니다. 루틴은 격자를 만지는 동안만 데이터 뱅크를 `7E` 로 두고, `04:991D`(프레임 기다림)·`00:950E` 는 부른 쪽 데이터 뱅크로 부릅니다. `7E` 뱅크에는 I/O 거울이 없어, 그대로 부르면 그 루틴의 `$21xx`·`$42xx` 쓰기가 WRAM 으로 갈 수 있기 때문입니다(코드 읽기).

새 코드는 원래 롬 없이 시험했습니다. 도구의 65C816 해석기(`w65816.py`)로 채우기·글자·탁점·줄 지우기·줄 올리기를 돌려 격자와 버퍼 칸을 보는 단위 시험을 더했습니다.

## 4. 효과 층

창을 21줄 위로 올리면 [일지 29](2026-10-30-29-msgwindow.md)처럼 공격 효과가 창을 지웁니다. `00:FD75` 가 `7E:8A1D` 0x380 바이트를 `$0F5E` 의 VRAM 에 올리는데, 이 루틴은 NMI 표(`00:FCE4`)의 `$0DF3` = `08`·`0C` 로 불립니다. `08` 은 `22:8B4A`·`8B5F`·`8B6C`·`8B84` 가 두고, `22:891A`·`892E`·`894D`·`8978` 이 `$0F5E` 를 `0CC0`·`04C0`·`05C0`·`0DC0`(BG1·BG2 타일맵)으로 두고 `22:8B5F` 로 같은 버퍼를 올립니다(코드 읽기). 그래서 크기 상수를 바로 줄이지 않고, `00:FD92` 의 `LDA #$0380` / `STA $4375` 를 `JSL eff` 로 바꿔 `$0F5E` 가 `1CE0` 일 때만 `(Y - 7) × 64` 를 둡니다. `8B84` 의 `18E0` 은 BG3 글자 자리(캔버스)라 건드리지 않습니다. 부분 전송(`00:8E72`·`8E79`·`8E81`)은 창 맨 위 줄부터 29줄까지로 넓힙니다.

효과가 어느 줄에 그려지는지 쟀습니다. 행동 171개를 쓰는 전투(`dq5effectgif.py` 의 틀)에서 `00:FDA1` 의 `1CE0` 전송마다 `7E:8A1D` 에서 그림이 있는 줄을 연출 번호(`22:D73C` 의 A)별로 셌습니다.

```text
연출 44개, BG3 효과 층에 그린 것 24개
가장 아래 줄: 19줄 10개, 20줄 14개
가장 위 줄:   7줄 7개, 8 2, 10 3, 11 1, 12 2, 13 1, 14 1, 15 1, 16 1, 17줄 5개
보통 공격 73: 17줄 299, 18줄 856, 19줄 856, 20줄 299 번(전송 1,417번)
```

BG3 효과는 모두 19줄이나 20줄까지 내려옵니다. 높이 9(Y 19)부터 모든 효과의 아래쪽이, 높이 11(Y 17)부터 보통 공격 효과 전체가 창에 가려집니다. スライム 전투 화면에서는 높이 11·13 창이 몬스터도 가렸습니다. 효과 층을 줄이는 것은 되지만, 메시지 창을 올리는 값은 화면에서 효과와 몬스터를 덮는 것입니다.

## 5. 실측

`dq5msgwindowcheck.py` 에 경우 셋(wide (0,21) 31 × 7, tall (2,17) 28 × 11, both (1,15) 31 × 13)과 field 장면을 더했습니다. 프레임마다 VRAM BG3 타일맵과 창 버퍼 `7E:5000` 을 함께 남깁니다.

처음에는 버퍼와 VRAM 이 두 칸 넘게 다르면 틀린 것으로 보았는데, 원래 롬도 메시지 `118` 에서 다섯 덤프 내리 달랐습니다. 글자를 한 프레임에 예닐곱 칸씩 찍는 동안 부분 전송이 네 프레임에 한 번이라, VRAM 이 네 프레임 전 버퍼와 같았습니다. 그래서 VRAM 창이 앞 여덟 프레임 가운데 한 프레임의 버퍼와 같은지 봅니다. 원래 롬은 one 1,826·four 2,284 프레임에서 다른 프레임이 0 이었습니다. 대조로 tall 롬의 `00:FD92` 만 원래 바이트로 되돌리자 1234프레임부터 19프레임 동안 VRAM 창이 어느 버퍼와도 달랐습니다.

```text
one  wide 창 1826 다름 0  같은 메시지 24 중 글자까지 23  효과 전송 20  새 격자 쓰기 7768  옛 격자 0
one  tall 창 2085 다름 0  15 중 5(여섯째 피해 수 08·06)    효과 28     10411            0
one  both 창 1835 다름 0  17 중 15                          효과 23     13610            0
four wide·tall·both 창 2284·2271·2272 다름 0, 글자까지 같은 메시지 42·30·30, 옛 격자 0
one·four X 0·4  워드 다름 0, 화면 87·87·68·99
field 다섯 롬 모두 f1955 01/00 (341,56), 7E:1E71~1EFF 143바이트 원래 롬과 같음, 그 구간 쓰기 5,990번 같음
```

줄을 늘린 롬은 줄 올리기 기다림이 줄어 난수가 갈립니다. one 의 tall 은 여섯째 메시지(피해)부터 수가 달라 다섯 메시지까지만 글자째 같았습니다. 모든 글자의 줄·칸은 새 격자 안이었습니다.

## 틀렸던 것들

- 줄 수 3 을 `24:A4FA` 한 곳으로 보았습니다. 제어 코드 쪽 `24:85FA`·`8613`·`864C`·`8677` 에도 있었습니다.
- 넓힌 창의 너비를 32 로 잡았습니다. 레코드 너비는 5비트라 31 까지입니다.
- X 만 옮긴 롬의 화면 비교가 one 1920프레임에서 어긋났습니다. 기록은 같았고 화면만 한 글자 늦게 찍혀 있었습니다. 두 롬 모두 창이 세 프레임 내리 같은 때만 화면을 견주게 했습니다.
- field 장면의 끝(4200프레임)을 필드로 보았지만 다음 전투 안이었습니다. `dq5warp.lua` 의 끝 좌표는 전투 중에도 필드 좌표를 적습니다. 파파스의 필드 메시지 글자로 필드에 돌아온 때를 잡게 바꿨습니다.

## 남은 것

- 이벤트 전투(ジャミ 등)·동료가 있는 전투·주문 효과를 넓히거나 높인 창으로 돌리지 않았습니다.
- 글자는 줄을 저절로 바꾸지 않으므로 넓힌 칸은 메시지 쪽이 줄을 끊어 채워야 합니다. 원래 메시지는 왼쪽 26칸에 그대로 찍힙니다.
- DQ4 메뉴 빌드의 `WnBattleCell`(`24:A5E9`)은 격자 `$1DD5,Y` 와 버퍼 `7E:5546`·`5547` 을 박아 둡니다. 너비·높이를 바꾸려면 이 훅을 새 코드의 격자 옮기기 안으로 옮겨야 합니다(코드 읽기).
- `7E:A600`~`A7FF` 는 770개 장면에서 접근이 없던 자리이고 증명은 아닙니다.
