# 2026-10-27-26: DQ4 타이틀·메뉴와 함께 빌드하는 통합 포팅 빌드

[도구 점검](../docs/dq5-port-tool-audit.md#기본-배치-다섯-조합이-충돌합니다)에서 DQ4 타이틀·메뉴와 DQ5 쓰기 도구의 기본 배치가 다섯 조합 모두 겹쳤습니다. 고정 롬을 예약 영역으로 두고 작업마다 뱅크 창 안의 빈 자리에서 `--at` 을 고르는 통합 빌드 `dq5portbuild.py` 와, 결과 롬을 게임에서 확인하는 `dq5portcheck.py` 를 만들었습니다. 형식은 [통합 포팅 빌드](../docs/dq5-build-format.md#통합-포팅-빌드-dq5portbuild1)에 있습니다.

맵 54개·인물 목록·세 세계 필드·보행 대사·이벤트 둘을 DQ4 타이틀·서곡·메뉴 롬과 합친 4MB 롬이 겹침 없이 만들어졌고, 타이틀·메뉴·이름 입력과 작업마다의 장면이 게임에서 기대대로 돌았습니다.

## 1. 고정 롬을 다시 만들기

DQ4 트랙의 재현 절차대로 타이틀과 서곡을 만들었습니다. 두 SHA-1 은 [구름 변형 일지](../../dq4/journal/2026-10-26-39-title-cloud-variation.md)의 채택본과 같았습니다.

| 단계 | SHA-1 |
| --- | --- |
| 타이틀 `dq4titlelayerpatch.py` | `dd7adb546d7c00e10cc3a6cf39f42ce7a9216318` |
| 서곡 `dq4overture.py build` | `ccfebebc25407cdc502ba6a90eabb928ce0a3968` |
| 메뉴·이름 입력 `dq4menupatch.py build` | `e102f295ba3e8171bb5d6c6d445b1759dc0a9eb0` |

메뉴 빌드는 그대로는 멈췄습니다. `dq4menupatch.py` 가 입력 서곡 롬의 SHA-1 을 이전 서곡 `ed46db6…` 와 견주기 때문입니다.

```
work/overture/dq4-title-overture.sfc: 서곡 채택본(ed46db6d9e8113191de124949f7d50a375adc410)이 아님
```

DQ4 트랙 파일이라 고치지 않고, 모듈을 불러 `BASE_SHA1` 만 지금 서곡 값으로 바꿔 `main()` 을 돌렸습니다. 결과 `e102f29…` 는 DQ4 핸드오프의 `9d8d2be…` 와 다릅니다. 그 뒤 머지된 지우기·기록 깨짐 메시지와 게임 안 이름 표시(`dq4menumsg.py`·`dq4namegame.py`)가 들어간 빌드라, 이 값을 적은 문서는 아직 없습니다. 메뉴 롬에서 `dq4nameentrycheck.py` 15건이 통과해 이 롬을 고정 롬으로 썼습니다.

```sh
export ASAR=… DQ4_GALMURI="$PWD/work/galmuri" DQ4_NAMEENTRY_SYMBOLS="$PWD/work/menu/name-entry.sym"
uv run --locked python -c "import sys; sys.path.insert(0, 'sfc/dq4/tools'); \
sys.argv = ['dq4menupatch.py', 'build', '--rom', 'work/overture/dq4-title-overture.sfc', '--out', 'work/menu/dq4-menu.sfc']; \
import dq4menupatch as m; m.BASE_SHA1 = 'ccfebebc25407cdc502ba6a90eabb928ce0a3968'; m.main()"
```

## 2. 고정 롬이 실제로 차지하는 자리

`dq5build.py fromrom` 처럼 늘린 원래 롬과 다른 바이트를 모두 예약하면 `30`~`3F` 가 거의 다 찹니다. 타이틀 빌드가 2MB 로 늘릴 때 `30`~`3F` 를 원래 롬 `20`~`2F` 의 복사본(거울)으로 채우기 때문입니다. 뱅크마다 거울과 같은 바이트를 세자 `3A`~`3F` 는 32,768바이트 모두 거울이었습니다.

처음에는 타이틀이 선언한 자리(`dq4titlelayerpatch.PLACEMENTS` 와 코드 `30:8000`~`8FFF`) 밖은 모두 거울일 것으로 보고, 다르면 멈추게 했습니다. 실제로 멈췄습니다.

```
오류: 30:A000: 타이틀 선언 자리 밖인데 확장 거울과 다름
```

단계별 롬을 견주니 선언 밖에서 거울과 다른 바이트는 서곡이 `30:FF00` 에 21바이트, 메뉴가 `30:A000`~ 에 2,272바이트를 썼습니다. `dq4overture.py` 의 주석대로 서곡은 타이틀의 페이드 루틴에서 `30:FF00` 으로 뛰고, 이름 입력 어셈블리는 `org $30A000` 입니다. 이 바이트가 우연히 거울과 같은 끝 바이트를 놓치지 않도록, 64바이트 안쪽 틈을 이은 묶음을 앞뒤 64바이트 넓혀 예약했습니다. 나머지 거울 272,252바이트는 빈 자리로 돌렸습니다.

`30`~`3F` 밖에서는 바이트 단위 예약이 위험했습니다. 메뉴의 `60`~`64`·`65`~`69` 와 서곡의 `70` 안에도 0 바이트가 많고, 0 은 롬을 늘린 0 과 구별되지 않습니다. 그래서 다른 바이트가 하나라도 있는 뱅크는 뱅크 전체를 차지한 것으로 봅니다. 반대로 메뉴 롬의 `40`~`5F`·`6A`~`6F`·`71`~ 은 모두 0 이라 `dq5build` 의 뱅크 첫 8바이트 표지만 달랐습니다. 이런 뱅크는 비어 있는 것으로 봤습니다.

| 고정 롬이 차지한 늘린 뱅크 | 바이트 |
| --- | ---: |
| `30` 코드·서곡·이름 입력 | 6,654 |
| `31` | 21,248 |
| `32` | 17,856 |
| `33`~`38` | 각 32,768(`34` 는 16,384) |
| `39` | 544 |
| `60`~`64`, `70` | 각 32,768 |

`dq5portbuild.py` 의 [config](../docs/dq5-build-format.md#통합-포팅-빌드-dq5portbuild1) `reserve` 로 소리 이식 몫 `72`~`7D` 를 더 비웠습니다. [메뉴 형식](../../dq4/docs/dq4-menu-format.md#배치)이 그 작업이 잡아 둔 자리라고 적은 범위입니다.

## 3. 보행 대사는 메뉴가 이미 옮겼다

점검의 다섯 충돌 가운데 대사는 `38:8000` 이 타이틀 자리라서였습니다. 그런데 메뉴 롬은 지우기 확인 메시지를 한글로 쓰려고 **보행 메시지 3,200개 전체**를 다시 부호화해 `65:8000`~`69:B941` 에 두고, 색인 `24:AF1E`·디코더 호출 `24:9E02`·색인 훅 `24:9E07`·글자 묶음 표 피연산자 넷을 이미 바꿨습니다. `dq5textwrite.py` 는 같은 자리를 원래 롬 기준으로 씁니다. 자리를 옮겨도 두 패치가 같은 색인·훅을 쓰는 것은 그대로입니다.

그래서 `dq5textwrite.py` 에 `--base 롬` 을 더했습니다. 기준 롬의 디코더·색인으로 3,200개를 읽어 입력에 적은 것만 바꾸고, 머리 끝의 늘린 글자 묶음 표(270바이트, 글자 `000`~`D3F`)를 새 머리 끝에 옮겨 표 피연산자도 씁니다. 메뉴의 한글 글꼴 코드 `3DB`~ 를 대사에 쓸 수 있게 됩니다. 메뉴 롬을 기준으로 아무것도 바꾸지 않고 다시 싸면 3,200개가 모두 같았고, 끝도 `69:B942` 로 메뉴와 같았습니다.

메뉴의 디코더 사본은 `65:8000` 에서 돕니다. 디코더 사본이 `PHK`·`PLB` 로 자기 뱅크의 표만 읽기 때문입니다. 색인 훅이 OR 하는 값만 `20` 에서 `60` 으로 바꾸면 `60`~`7D` 창도 쓸 수 있어, `dq5textwrite.py` 가 두 창을 받게 했습니다. 통합 빌드는 `over` 를 준 대사 작업에 `60`~`7D` 를 먼저 시도하고, 옛 묶음 자리와 원본 자리를 고정 패치에서 뺍니다.

## 4. 배치

작업마다 쓰기 도구를 한 번 시험 자리에 돌려 크기를 잽니다. 쓰기 도구의 배치 규칙(이어 놓기, 덩어리가 뱅크를 넘으면 다음 뱅크로, 머리는 시작 뱅크 안)대로 구간을 계산해 빈 자리에 맞춥니다. 실제로 돌린 쓰기 도구가 늘린 자리에 쓴 구간이 계산과 다르면 멈춥니다.

이번 작업 묶음은 DQ4 1장 정도의 크기를 생각했습니다. 그룹 `01`~`04` 의 맵 54개(01/05 에는 [맵 쓰기 일지](2026-10-26-41-mapwrite.md)의 블록 넷을 더함), 긴 스크립트 셋을 넣은 인물 목록(`dq5npcrelocatecheck.py --mutations` 의 입력), 세 세계 필드(세계 0 의 (172~176, 25~28) 을 언덕 블록 307 로), 메시지 `129`·`C70` 을 한글 「안녕하세요 산타로즈」·「인도받은 자들」로 바꾼 대사, 번호 `07`·이벤트 `8` 스크립트입니다.

| 조각 | 바이트 | 창 | 자리 |
| --- | ---: | --- | --- |
| maps | 42,243 | `30`~`3F` | `39:8220`~`3A:A722` |
| npc.base | 20,218 | `30`~`3F` | `30:A929`~`30:F822` |
| npc.alt | 24,022 | `30`~`3F` | `3C:8000`~`3C:DDD5` |
| field0 | 31,581 | `30`~`3F` | `3A:A723`~`3B:E56E` |
| field1 | 3,597 | `30`~`3F` | `30:9000`~`30:9E0C` |
| field2 | 4,091 | `30`~`3F` | `31:B760`~`31:C75A` |
| text | 145,787 | `60`~`7D` | `65:800C`~`69:B986` |
| events | 12 | `60`~`7D` | `65:8000`~`65:800B` |

`30`~`3F` 는 빈 자리 297,762바이트 가운데 125,752바이트를 썼고 172,010바이트가 남았습니다. 이 125,752바이트는 모두 비운 거울 자리였습니다. 거울과 같은 바이트로만 이뤄진 다른 단계의 자료가 있으면 이 규칙으로는 못 찾으므로, 그 자리를 고정 롬이 읽지 않는지는 6절의 타이틀·DQ4 검사로 봤습니다. 타이틀 코드 뒤 `30:9000`, 하늘 CHR 뒤 `31:B760` 처럼 타이틀 에셋 사이의 틈에도 들어갔습니다.

## 5. 빌드

배치한 `--at` 으로 쓰기 도구를 돌리고, 고정 패치(대신한 자리를 뺀 것)와 함께 `dq5build.py check`·`build` 에 넣었습니다.

```
목록 8개, 쓰기 37181개 474701바이트, 겹침 없음
work/port/build/port.sfc sha1=f1e0ccff2606fa22888fb79e7b09bd4a3611052b IPS 573839바이트(다시 붙여 같음)
```

빌드 끝에 고정 롬이 쓴 원래 롬 자리와 늘린 자리에서 차지한 구간 463,291바이트가 결과 롬과 같은 것, 결과 롬의 새 디코더로 푼 3,200개가 입력과 같은 것을 확인했습니다.

## 6. 게임에서 확인

`dq5portcheck.py` 로 MesenCE 에서 돌렸습니다.

| 묶음 | 결과 |
| --- | --- |
| 타이틀 대기 | 프레임 320~1280(64 간격) 16표본의 VRAM·OAM·CGRAM 48개가 고정 롬과 바이트까지 같음. 프레임 101 에 `30:8000` 진입 |
| 메뉴 복귀 | 프레임 420 에 A, 580~700(20 간격) 7표본 21개가 같음. 두 롬 모두 프레임 500 에 `00:A6F1` |
| DQ4 이름 입력 | `dq4nameentrycheck.py` 15건과 이름 칸 VRAM 256바이트 차이 0, `dq4namecursorcheck.py` 52건, `dq4namegamecheck.py` 7건 통과 |
| 대사 | `129`(`65:ABB8`)·`C70`(`69:B3CC`)·고치지 않은 `742`(`67:B2F1`)의 디코더 반환 64코드가 결과 롬과 같음 |
| 필드 | 세계 0·1·2 의 WRAM 지도 73,728바이트가 입력 지도와 차이 0 |
| 인물 | 선실·02/06·01/05 낮밤과 대체 목록 2건의 인물 표·포인터, 긴 스크립트 5건이 (5,13) 에 멈춤(포인터 `30:CBD7`·`30:AE98`·`3C:9176`) |
| 맵 | 01/05(`39:9B12`)의 `01:BA4C` 셀 버퍼 32,640바이트가 결과 롬 디코더와 차이 0, 원본과 다른 셀 28칸 |
| 이벤트 | 번호 표·이벤트 표 조회로 `65:8000`·`65:8006` 의 스크립트가 돌아 플래그 `7E:220F` 에 `40`, 주인공 (11,11) |

타이틀 비교가 차이를 잡는지 보려고, 결과 롬의 BG 팔레트 한 바이트(파일 `18E802`)를 뒤집은 롬도 돌렸습니다. 16표본의 CGRAM 16개가 고정 롬과 달랐습니다.

```sh
MESENCE=… uv run --locked python sfc/dq5/tools/dq5portcheck.py rom/dq5.sfc work/port/build/report.json \
  --state work/state/ship.mss --symbols work/menu/name-entry.sym --out work/port/check
```

## 7. 자리가 모자랄 때

맵 364개 전체를 넣은 설정으로 `plan` 을 돌리면 배치기가 거부합니다.

```
오류: 배치 실패
maps 233794바이트(stream, 창 low)를 놓을 자리가 없음.
  창 low(30~3F): 아직 못 놓은 작업 중 이 창만 쓰는 것 317303바이트 + 다른 창도 쓰는 것 145787바이트, 빈 자리 297762바이트(가장 긴 연속 228832바이트)
```

맵 하나의 덩어리가 가장 긴 빈 자리보다 크고, 맵·인물·필드 합계도 빈 자리보다 19,541바이트 큽니다. 맵을 여러 작업으로 나눠도 합계가 넘습니다. 이만큼을 넣으려면 타이틀 에셋을 상위 뱅크로 옮겨야 하고, 이는 DQ4 트랙 작업입니다([todo](../todo.md)). 이번 작업 묶음에서는 대사를 `60`~ 으로 보내 타이틀을 옮기지 않아도 들어갔습니다.

## 틀렸던 것들

- 고정 롬의 「써야 하는 바이트」를 그대로 「차지한 자리」로 썼습니다. 메뉴 묶음 안의 0 이 빈 자리로 보여, 작은 조각이 그 사이에 들어갈 수 있었습니다. 늘린 자리는 뱅크 단위로 잡게 고쳤습니다.
- 타이틀 거울 안은 타이틀만 쓴다고 봤습니다. 서곡과 이름 입력 코드가 거울 안에 있었습니다(2절).
- 메뉴 롬의 빈 뱅크도 표지 8바이트가 달라 뱅크 전체가 찬 것으로 잡혀, 높은 창의 빈 자리가 163,840바이트로 나왔습니다. 모두 0 인 뱅크를 빼자 393,216바이트였습니다.
- 인물 목록은 덩어리가 뱅크를 넘으면 다음 뱅크로 민 자리에 놓아야 하는데, 민 앞의 후보 주소를 `--base` 로 넘겨 쓰기 도구가 「한 뱅크를 넘음」 으로 거부했습니다. 민 뒤의 첫 덩어리 자리를 넘기게 고쳤습니다.

## 남은 것

- 맵 364개 전체와 인물·필드를 함께 넣는 배치(타이틀 에셋 재배치, DQ4 트랙).
- 메뉴 빌드의 입력 SHA-1 검사가 이전 서곡 값이라 문서 절차가 그대로는 멈춤(DQ4 트랙).
- 고정 롬 단계들이 쓴 구간 목록이 있으면 거울 추정이 필요 없음(DQ4 트랙).
- 거울 안에 거울과 같은 바이트로만 이뤄진 DQ4 단계 자료가 있는지는 단계별 쓰기 목록 없이는 알 수 없습니다. 이번 롬에서는 비운 거울 125,752바이트를 덮고도 타이틀·메뉴·이름 입력 검사가 같았습니다.
- `npc` 작업의 `records`, 제자리 쓰기 결과를 넣는 `patch` 작업은 통합 롬에서 게임 실측하지 않았습니다.
- 실제 SFC 기기, 새 게임 → 장 진행 → 저장·재개.
