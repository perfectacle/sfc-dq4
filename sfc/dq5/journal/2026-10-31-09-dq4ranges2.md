# 2026-10-31-09: 지금 dq4 빌드로 dq4 구간 다시 견주기

[앞 일지](2026-10-30-10-dq4ranges.md)는 dq4 트랙이 알려 준 롬·WRAM 구간을 2026-10-27 에 만든 옛 고정 롬과 견줬습니다. 이번에는 지금 `origin/main`(`6d7a49a8`)의 dq4 절차로 롬을 새로 만들어 같은 비교를 했습니다. 1장·곡 묶음 단계와 그 롬에서 통합 빌드가 쓸 수 있는 자리도 셌습니다. 결과는 [통합 포팅 빌드](../docs/dq5-build-format.md#dq4-트랙이-쓰는-롬wram-구간)의 표에 있습니다.

## 1. 롬 만들기

dq4 의 한 줄 빌드를 그대로 돌렸습니다. 도구·입력이 바뀌지 않은 단계는 원래 체크아웃의 공유 캐시에서 나왔고, 곡 묶음은 자원 저장소(`DQ4_ASSETS`)에서 만들었습니다.

```sh
ASAR=… DQ4_GALMURI=… DQ4_ASSETS=… uv run --locked python sfc/dq4/tools/dq4build.py --out work/ch1
```

```
work/ch1/dq4-ch1-sound.sfc sha1=c474743a4bb2678b68ffecaee0f3ca4b0f689792
real	1m23.374s
```

중간 롬은 타이틀 `0a5c8716…`(2MB), 서곡 `2948bf10…`, 메뉴 `526b4b8f…`, 1장 `b8634d80…` 입니다. 단계마다 바로 앞 단계와 견주는 방법은 앞 일지와 같습니다(타이틀은 원래 롬 + `20`~`2F`, 서곡은 4MB 로 늘린 타이틀에서 뱅크 첫 8바이트 표지를 뺌, 16바이트 안쪽 틈은 이음). 묶음 수는 타이틀 18, 서곡 11, 메뉴 170, 1장 877, 곡 묶음 62 입니다.

## 2. 남은 확인 넷

앞 일지가 남긴 대상부터 봤습니다.

- **뱅크 `58`**: `58:8200`~`F87B` 안의 묶음 열여덟이고, 가장 큰 것은 `58:9200`~`F87B` 26,236바이트입니다. 메뉴 단계 안의 `dq4windowname` 이 씁니다.
- **사운드 포팅 자리**: 곡 묶음 단계가 `6A:8000`~`6F:FFE5`, `72:8000`~`7D:BAA5`, `70:8104`~`8539` 의 셋, `71:8200`~`8817` 의 여덟, `2B:B741`~`EAF7` 안의 묶음을 씁니다. 목록에 없던 `00:8000`·`88E3`·`9676`·`9691`·`CD40`·`CD5C`·`CEA3`·`FFEE`, `01:C214`, `2A:FFE6` 도 바뀌었는데, 모두 [사운드 포팅 문서](../../dq4/docs/dq4-sound-port-format.md)에 적힌 훅입니다. 훅 첫 바이트가 원래와 같아 한 바이트 뒤(`88E2` → `88E3` 등)에서 시작하는 것이 다섯입니다.

## 3. 창 레코드 뒤의 다리 코드

`dq4menupatch.window_addr` 로 서곡 롬의 창 표 `04:EB48` 을 읽어, 두 구간이 어느 레코드 안에 있는지 봤습니다.

```
old rec ['5E'] 04:F43B~F44F
old rec ['5F'] 04:F450~F477
old rec ['60'] 04:F478~F4BB (끝80 at F4BB)
old rec ['63'] 04:F4D6~F513
...
old rec ['6A'] 04:F5AA~F5D4 (끝80 at F5D4)
```

메뉴는 한글 레코드가 짧으면 남은 자리에 `place()` 로 코드를 둡니다. 목록 끝 뒤의 바이트는 그 다리입니다.

```
04:F4B3  20 35 9D 6B   JSR $9D35 / RTL   (wait)
04:F4B7  20 B9 D1 6B   JSR $D1B9 / RTL   (erase)
04:F5D0  20 19 D3 6B   JSR $D319 / RTL   (row)
```

옛 롬도 같은 끝이었으니 바뀐 것이 아니라 목록이 다리를 빼고 적은 것입니다. 이 둘은 원래 레코드 끝(`F4BB`·`F5D4`)까지 쓰는 자리로 문서에 적었습니다.

## 4. 1장 빌드가 `30`~`3F` 에 둔 것

1장 단계의 `30`~`3F` 차이는 큰 묶음 몇 개로 이어집니다(`3B:8000`~`3C:EE54`, `3C:EE8E`~`3F:FF85` 등). 1장 빌드가 그룹 패치를 얹기 전에 거울을 0 으로 지우기(`dq4chapter1.clear_mirror`) 때문입니다. 그래서 바뀐 바이트를 「0 아닌 새 값」과 「0 으로 지운 거울」로 나눠 셌습니다.

```
36:9E00~36:FFFF nonzero 3897 last nz 36:AD6A zeroed 20110 new nonzero 3872
37:8000~37:FFFF nonzero 0 last nz - zeroed 30915 new nonzero 0
38:8000~38:FFFF nonzero 29967 last nz 38:FFED zeroed 1648 new nonzero 26999
39:8000~39:FFFF nonzero 0 last nz - zeroed 31187 new nonzero 0
3A:8000~3A:FFFF nonzero 31746 last nz 3A:FE25 zeroed 890 new nonzero 31565
3F:8000~3F:FFFF nonzero 25316 last nz 3F:E88A zeroed 6485 new nonzero 25200
```

[1장 문서](../../dq4/docs/dq4-chapter1-format.md)의 레코드 자리 표(`30:9FF6`·`30:DD8A`·`31:C9B2`·`31:FD0F`·`32:FF5B`·`36:AD6A`·`3A:FE25` 까지, `37`·`39` 비어 있음)와 대체 목록 `38:8000`~`F184`, 기본 목록 `3F:8000`~`E88B` 이 0 아닌 끝과 맞았습니다. 앞 일지가 물었던 자리는 이렇게 됐습니다.

- `34:8000`: 그룹 빌드만 쓰는 자리입니다. 1장 빌드는 새 맵 레코드를 `3A:8000` 으로 돌리고, `34` 에는 타이틀 뒤 `34:C000`~ 에 필드 지도를 둡니다.
- `35:8000`: 1장 단계는 바꾸지 않았습니다. 대사 패치는 얹지 않고, 대사는 메뉴 빌드가 다시 만듭니다.
- `39:9000`: 대체 목록이 `38:8000` 으로 옮겨 갔고, `39` 는 0 으로 비운 레코드 자리입니다.
- `3B`·`3C`: 문 표 복사본과 입구·도착·포인터·속성 표입니다.
- `3F:9C00`: 기본 인물 목록이 `3F:8000` 에서 시작합니다(4장 맵을 빌린 자리에서 빼 환경 맵이 `3E` 에서 끝나서).

타이틀도 줄었습니다. 거울과 다른 곳이 `36:9DBF` 에서 끝나(옛 롬은 `39:821F`) 메뉴 롬까지는 `37`~`3F` 가 거울 그대로입니다. 그 자리를 1장 빌드가 씁니다.

## 5. 통합 빌드에 남은 자리

`dq5portbuild.fixed_mask`·`occupied` 로 메뉴·1장·곡 묶음 롬을 고정 롬으로 두었을 때의 빈 자리를 셌습니다.

```
== menu: freed mirror 356172, low free 782708, high(60~7D) free 622592
== dq4-ch1: freed mirror 4615, low free 5937, high(60~7D) free 622592
   low 30:F908 30:FEBF 1464
   low 31:E9A0 31:EAFF 352
   low 38:F1C5 38:FFC0 3580
== dq4-ch1-sound: freed mirror 4615, low free 5937, high(60~7D) free 0
```

위 출력은 256바이트 넘는 조각만 찍었습니다. 1장 롬의 셋(5,396바이트) 말고 뱅크 끝 조각 다섯 `30:FF55`~`FFFF`(171), `32:FF9C`~`FFFF`(100), `34:FF45`~`FFFF`(187), `39:FFA7`~`FFBF`(25), `3F:FFC6`~`FFFF`(58), 541바이트가 더 있습니다. 메뉴 롬에도 `30:FF55`~`FFFF` 가 있습니다.

1장 롬을 고정 롬으로 두면 `map`·`field`·`npc` 작업이 쓰는 `30`~`3F` 창에 5,937바이트만 남습니다. 곡 묶음까지 얹으면 `60`~`7D` 창도 다 찹니다.

## 6. `over` 가 지금 메뉴 롬을 읽지 못함

빈 자리를 세면서 `text` 작업의 `over` 가 빼는 메시지 묶음 자리도 보려고 `dq5textwrite.base_package` 를 메뉴 롬에 불렀더니 멈췄습니다.

```
ValueError: 옮긴 보행 색인 표의 끝을 찾지 못함
```

```
decoder 5A8000 mask 60 index 598000
first msg 64C400 table 5A9991
size to first 377856 to table 39313
```

`index_table` 은 색인 표가 머리 안에 있다고 보고, 끝을 글자 묶음 표나 메시지 0 으로 셉니다. 지금 dq4 메뉴는 색인(`59:8000`), 머리(`5A:8000`), 메시지(`64:C400`)를 따로 둡니다([메뉴](../../dq4/docs/dq4-menu-format.md)). 그래서 색인부터 글자 묶음 표까지 39,313바이트가 잡혀 3의 배수도 아니고 한도도 넘습니다. `base_package` 가 돌려주는 묶음 자리 하나(디코더~마지막 메시지)도 이 배치에서는 `5A:8000`~`69:CD9A` 가 되어, 사이의 메뉴 자료 `60`~`64` 까지 덮게 됩니다. 이번에는 고치지 않고 [todo](../todo.md)에 남겼습니다.

## 틀렸던 것들

- `04:F43D`~`F4BA` 가 목록보다 긴 것을 옛 롬과 지금 롬의 차이로 봤습니다. 지금 롬도 같은 끝이었고, 창 레코드 남은 자리에 둔 다리 코드였습니다.
- `37`·`39` 의 차이를 1장 빌드가 쓴 자료로 읽었습니다. 0 아닌 바이트가 하나도 없었고, 모두 0 으로 지운 거울이었습니다.
- `24:AF1E` 를 메뉴가 늘 고치는 색인 자리로 봤습니다. 지금 메뉴는 색인을 `59:8000` 으로 옮겨 이 자리를 그대로 둡니다. 바로 앞에서 끝나는 `24:AECD`~`AF1D` 는 `dq4windowname` 이 씁니다.

## 남은 것

- `dq5textwrite.base_package`·`index_table` 이 색인·머리·메시지를 따로 둔 dq4 메뉴 롬을 읽게 하고, `over` 가 빼는 자리를 셋으로 나누기.
- 1장 단계가 원래 롬 안(`00`~`2B`)에서 고친 훅·표를 dq4 문서와 하나씩 맞춰 보기.
- `3E` 의 0 아닌 끝 `3E:D93E` 가 dq4 문서의 환경 맵 끝 `3E:D934` 보다 10바이트 뒤인 까닭.
- WRAM 구간은 롬 비교로 볼 수 없어 여전히 알려 준 것입니다.
