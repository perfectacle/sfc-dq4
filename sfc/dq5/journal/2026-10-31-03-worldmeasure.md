# 2026-10-31-03: 세계 1·2 의 시계, 실내 새 세트의 밤·플래그 팔레트, 세계를 오가는 장면의 화면과 움직이는 타일

[그림 쓰기](2026-10-27-47-gfxwrite.md) 항목에 남아 있던 세계·시계·이동 쪽 실측을 했습니다. 세계 1·2 에 들어가면 `$075E` 가 0 이 되고 걷거나 ラナルータ 를 외워도 그대로라 밤이 오지 않으며, 세계 0 으로 돌아오면 아침부터 다시 갑니다. 실내 새 팔레트 세트는 밤 목록과 플래그 팔레트 세트(`2A:8690` → `10:DDCF`)로도 골라졌습니다. 세계마다 니블이 다른 롬으로 ルーラ 1 → 2, キメラのつばさ, 天空城 이륙(`02:9779`), 52/50 석상 이벤트, 27/00 에서 `$1949` = `FF` 를 쓴 뒤의 길을 쟀고, 모두 내린 세계의 니블대로였습니다. 다만 엔딩 비행(`02:B9D8`)에서는 스태프 롤이 늘린 필드 타일 자리 VRAM 워드 `4000`~`5FFF` 를 지워, 블록이 늘린 타일을 쓰는 롬은 땅이 검게 보였습니다. 움직이는 타일 16벌과 `7E:CE00`~`D3FF` 는 세계를 옮기는 장면·융단·天空城 에서도 맞았습니다. 결과는 [필드 형식](../docs/dq5-field-format.md#낮밤-0082d3)·[세계 셋](../docs/dq5-field-format.md#세계-셋-019f40)·[타일 512개 넘기기](../docs/dq5-field-format.md#타일-512개-넘기기), [맵 형식의 플래그 팔레트 세트](../docs/dq5-map-format.md#플래그로-바꾸는-팔레트-세트-019771), [쓰기 형식](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)에 넣었습니다.

## 1. 도구

- `lua/dq5worldlog.lua` 에 `WATCHW="075E,075F"` 를 더했습니다. `$1949` 처럼 그 WRAM 오프셋에 쓰는 PC·값을 `wXXXX` 줄로 모읍니다. `READPC` 로 ラナルータ 처리기 `11:826F`·`11:829B` 에 들어갈 때의 `$1949` 도 함께 봅니다.
- `lua/dq5rangewatch.lua` 에 `RWLOG=1` 을 더했습니다. 원래 `rw.txt` 는 PC 마다 한 줄로 합쳐 필드를 여러 번 불러오는 장면에서 차례가 사라지므로, 프레임마다 닿은 PC 를 `rwlog.txt` 에 남깁니다.
- `lua/dq5gfxdump.lua` 는 `dq5warp.lua` 의 `TO`(맵 목적지)와 `EVERY` 끝 프레임 `TO` 가 겹쳐 실내에서 시작하는 장면에서 `EVERY` 를 쓰면 프레임 콜백이 멈췄습니다. 끝 프레임을 `EVERYTO` 로도 줄 수 있게 하고, 숫자가 아닌 `TO` 는 끝이 없는 것으로 읽습니다.
- `dq5map.set_cgram(rom, 세트, 밤)` 을 `map_cgram` 에서 떼었습니다. 맵 → 세트 표를 거치지 않고 세트를 고르는 장면의 기대값입니다.

## 2. 세계 1·2 의 시계

`dq5gfxlimitcheck.py` 의 clock 장면입니다. 세계 0 에서 `$075E` = `0120`(밤), 시간 멈춤(`7E:2190` bit1)을 끈 채 ルーラ 로 세계 1(22)·세계 2(1C) 에 내려 네 방향으로 64프레임씩 걷고 ラナルータ 를 외운 뒤, ルーラ 로 ラインハット 에 돌아와 걷고 다시 ラナルータ 를 외웠습니다. ラナルータ 는 주인공 필드 주문 목록 다섯째 칸(파일 오프셋 `11BE2C`)을 `37` 로 바꿔 외우게 했고, 걷는 동안 무작위 전투가 붙지 않게 조우 판정 `23:E7C2` 를 `CLC / RTL` 로 두었습니다(시계 `00:82C6` 은 그 뒤라 그대로 돎). 100프레임마다 덤프했습니다.

```
                      $075E 쓰기(PC 값)                      ラナルータ(11:826F 에 들어간 세계 / 11:829B)   세계 0 의 $075E
세계 1                019F8C 00, 0082DF 01~, 1182A7 0190     1·0 / 0                                          0120 → 0000 → 0008 → 000E → 0190
세계 2                019FA6 00, 0082DF 01~, 1182A7 0190     2·0 / 0                                          0120 → 0000 → 0008 → 000E → 0190
```

세계 1·2 에서 서 있거나 걸은 덤프 20장(자리 넷)은 모두 `$075E` = 0 이고 2·3번 줄 색 1~13 이 그 세계 한 벌(`01:A199`·`01:A3B5`)이었습니다. 세계 0 덤프는 `$075E` 로 시간대 표가 고르는 벌과 같았습니다. ラナルータ 는 세계 1·2 에서 「ラナルータを となえた！」 뒤 `11:829B` 에 닿지 않았고, 세계 0 에서는 `11:82A7` 이 `0190` 을 썼습니다. nibs 롬의 `$075E` 쓰기 기록은 원본과 같았습니다.

곧 세계 1·2 에 밤이 오지 않는 조건은 셋입니다. 불러올 때 `01:9F86`·`9FA0` 이 0 을 쓰고, 시계 `00:82C6` 이 `$1949` ≠ 0 이면 건너뛰고, ラナルータ 의 `11:826F` 가 `$1949` ≠ 0 이면 거절합니다. 세계 1·2 를 다녀오면 세계 0 의 시간도 0(아침)이 됩니다.

## 3. 실내 새 세트의 밤 목록과 플래그 팔레트 세트

indoor 롬(세트 70개, 01/01 을 새 세트 69(`45`) 로, 69 의 밤 목록은 세트 0 의 것)과 원본으로 견주었습니다. 세트 번호는 10진이고 괄호가 16진입니다(롬 표의 바이트는 16진).

```
장면                                   BG 1~7번 줄       원본 게임과
01/01, $075E = 0120                    세트 69(45) 의 밤 목록  다름(원본은 세트 37(25), 낮밤 목록이 같음)
06/00, 7E:21D4 bit2                    세트 36(24) 의 낮 목록  같음(맵 표의 세트 35(23) 와는 다름)
06/00, 항목의 세트를 69(45) 로(ROMPATCH)  세트 69(45) 의 낮 목록  다름
위와 같고 $075E = 0120                  세트 69(45) 의 밤 목록
```

플래그 팔레트 세트 표의 06/00 항목은 `06 00 44 04 24` 이고 플래그 번호 `44` 는 `7E:2190 + 44` = `7E:21D4` 입니다. 맵 형식에 `7E:2194` 로 적혀 있던 것을 고쳤습니다. `21D4` bit2 를 끄면 세트 35(`23`) 였습니다.

`10:DDB2`(옮길 곳 `7E:3B14`)를 부르는 넷은 세트 × 4(+2 면 밤)를 즉값으로 넘겨(`02:D828` 은 `009C`, `1E:E03F`·`E056`·`E07E` 는 `0106`·`0108`·`0104`) 맵 표와 상관없이 세트 39·65·66(`27`·`41`·`42`) 을 고릅니다(코드 읽기). 새 세트를 고르려면 그 즉값을 바꿔야 하고, 그 장면은 찾지 않았습니다.

```

castle-0608       700(0)                          02977C 0                       1,394
statue-5250       3900(2)                         2AFEEF 2                       1,316
ship27-ff         2000(1)                         03C687 FF, 11819D 1           1,285
walk-1C00-ff      1400(2)                         2AFEEF 2                       1,413
```

모든 장면에서 늘린 타일 칸의 팔레트가 그 세계 입력 니블과 같고 다른 두 세계 니블과는 모두 달랐으며, 타일 번호·CGRAM 은 tiles 롬과 같았습니다. `00:BBAC` 가 읽은 `$1949` 는 늘 0~2 였고, `FF` 를 쓴 장면도 필드에 내리기 전에 다시 쓰였습니다. 늘린 롬의 첫 `00:BBAC` 가 원본보다 한 프레임 늦은 것은 앞 일지와 같습니다.

## 6. 엔딩 비행과 늘린 타일

엔딩 장면을 같은 세 롬으로 돌리자 tiles 롬은 1,000프레임에 天空城 만 보이고 땅이 검었습니다. VRAM 쓰기(`lua/dq5vramlog.lua`)를 보니 528프레임에 `01:A4A7` 의 훅(`34:80A6`)이 늘린 타일을 `4000` 에 보낸 뒤, 610프레임에 `02:FAAF`(`02:FA86` 의 DMA, 고정 원본)가 `$CE` 의 VRAM 주소부터 지웠습니다. 그때 PPU 의 BG3 글자 기준은 `4000` 이었습니다. 스태프 롤 글자(BG3 2bpp)가 `4000`~`5FFF` 를 쓰는 것입니다. 원본은 이 자리를 필드에서 쓰지 않아 늘 비어 있고, tiles 롬은 블록이 늘린 타일을 쓰는 칸 1,285개가 빈 타일을 가리켰습니다.

필드 타일 1,024개와 OBJ·타일맵·BG3 창 글자로 VRAM 이 다 차 있어 스태프 롤 글자를 둘 다른 자리가 없습니다. 그래서 고치지 않고, 엔딩 비행에서 늘린 타일을 쓰지 않거나 스태프 롤 글자를 다른 자리로 옮기는 일을 남겼습니다. `dq5gfxlimitcheck.py` 의 ending 검사는 이 충돌(원본 0칸, tiles 롬 1,285칸, BG3 글자 기준 `4000`, `4000`~`5FFF` 가 빔)을 그대로 확인합니다.
