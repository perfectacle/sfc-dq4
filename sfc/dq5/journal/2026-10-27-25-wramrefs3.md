# 2026-10-27-25: CDL 을 늘려 옮긴 레코드 자리 후보 줄이기, 쓰이던 `7E:1BB1`

[2026-10-26-50](2026-10-26-50-wramrefs2.md)이 남긴 직접 피연산자 569곳(과 값을 모르는 `TCD`·`PLD`·`MVN`·`MVP`)을 더 나눴습니다. 장면을 늘려 MesenCE CDL 을 쌓고, 롬의 자료 구조와 리스팅으로 나머지를 가렸습니다. 그러다 옮긴 레코드 자리의 끝 바이트 `7E:1BB1` 을 실제로 쓰고 읽는 코드를 찾았습니다. 결과는 [dq5-hangul-format.md 「CDL 을 늘려 다시 나누기」](../docs/dq5-hangul-format.md#cdl-을-늘려-다시-나누기)에 있습니다.

## 1. CDL 의 비트와 정렬

필드 세이브스테이트에서 `getCdlData` 를 받아 값의 분포를 보니 `01`·`02` 말고 `11`·`21`·`31`·`15`·`39` 같은 값이 있었습니다. 알려진 코드 `00:891E REP #$30` 의 바이트가 `15`·`11`, 그 뒤가 `01` 인 것으로 bit4·bit5 가 실행 때의 X·M 8비트임을 맞췄습니다. bit2 는 점프 대상, bit3 은 서브루틴 입구입니다.

그래서 코드 표시가 이어진 구간마다 첫 바이트부터 그 바이트의 폭으로 명령 길이를 따라가면 명령 시작 자리를 얻습니다(`dq5wramrefs.py --align`). 구간 끝을 넘은 구간과, 점프 대상인데 명령 시작이 아닌 자리는 0개였습니다. BRK 의 인자 바이트는 CDL 이 자료로 표시하므로 구간이 거기서 끊깁니다.

앞 일지에서 정렬된 디스어셈블로 하나씩 보던 「CDL 이 코드라 한 후보」 는 이것으로 한꺼번에 명령 시작·명령 중간으로 갈립니다.

## 2. 함께 돈 실행의 CDL 이 사라짐

부팅과 항구 장면을 함께 돌린 뒤 CDL 을 다시 받았더니 전원을 켤 때 지나는 `00:8068`(문맥 저장 `JSL $00D227`)이 여전히 0 이었습니다. MesenCE 는 실행이 끝날 때 디스크의 CDL 을 통째로 쓰므로, 함께 돈 실행 가운데 나중에 끝난 쪽이 앞 실행의 기록을 덮습니다. 그래서 실행마다 `lua/dq5cdldump.lua` 로 그 실행의 `getCdlData` 를 받고, `dq5cdlsweep.py` 가 바이트 OR 로 합치게 했습니다.

```
장면                                   코드 바이트   자료 바이트
처음(지금까지 쌓인 것)                    124,461      559,791
실내 맵 346곳·몬스터 236종·세계 셋         140,058      805,229
시퀀스 0x47개                             142,509      846,265
행동 00~AA 전투 171번                     150,075      887,937
슬롯 셋·슬라임 레이스·격투장               157,339      902,310
```

슬라임 레이스 하나로 뱅크 `11` 의 코드가 2,649 → 7,524 바이트(슬롯까지 돌린 뒤와 견줌)가 되었습니다. 레이스는 뱅크 `11` 뒤쪽(`11:DD4E`~ 등)에 모여 있었습니다.

## 3. 쓰이던 `7E:1BB1`

정렬로 다시 보자, 직접 피연산자 가운데 명령 시작으로 실행된 것이 둘 나왔습니다. 모두 `$1BB1` 입니다.

```
02:A2FF  STZ $1BB1     M 8비트
03:F472  AND $1BB1     LDA $7F 뒤, 0 이 아니면 03:F4B8 로
```

`02:A2FF` 는 `02:A2D5` 안입니다. 처음에는 롬에서 `D5 A2 02` 를 찾다 `12:8963` 에 걸려 맵 02/09 로 가 보았는데, 그곳은 인물 목록 표(6바이트, `10:A2D5`)였고 아무것도 잡히지 않았습니다. 맵별 루틴 표(`15:F907` 쪽)에서 `17 01 FF 00 | D5 A2 02 | 85 A3 02`, 곧 17/01 의 처음 루틴이 `02:A2D5` 였습니다. 쓰기 감시를 낮은 WRAM 거울(뱅크 `00`~`3F`·`80`~`BF`)까지 걸고 17/01 로 옮기자 이렇게 나왔습니다.

```
112 X 02A2D5
115 X 02A2FF
115 W 151BB1=00  db=15
```

`03:F472` 는 `03:F349` 의 고리 안입니다. `03:F349` 를 부르는 곳은 네이티브 `02:A35C` 하나이고, 그것을 `06:D39A` 가, 그것을 17/01 의 대체 목록 `10:B135`(`7E:2192` bit7)에 있는 (49,53) 인물이 `37 9A D3 06` 으로 부릅니다. 이 인물은 `21A1.7` 을 기다려 `21A1.6` 을 켜고, `21A4.7` 을 기다린 뒤 걸어가 이 네이티브를 부릅니다.

```sh
STATE=…/ship.mss TO=17/01,40,56 SET="2192|80" LATESET="21A1|80;21A4|80" SETTLE=60 TEST="wait:1500"
```

```
539 X 06D39A / 02A35C / 03F349
541 X 03F472   R 031BB1=00  db=03
543 X 03F472   …  (2프레임마다)
```

`1BB1` 은 17/01 에 들어설 때 0 으로 지워지고, 항구 장면이 입력 바이트와 AND 합니다. 0 이 아니면 고리를 빠져나가는 갈래로 갑니다. 옮긴 레코드를 `1BB1` 까지 쓰면 이 장면이 달라질 수 있으므로 자리를 `7E:1ABC`~`1BB0`(245바이트)으로 줄였습니다. 지금 시제품은 `7E:1AC0` 부터 레코드 길이만 복사해 닿지 않습니다.

## 4. 새로 실행된 `TCD`·`PLD`

정렬로 본 「명령 시작으로 실행된」 값 모름 후보 가운데 앞에서 재지 않은 것은 넷이었습니다. 실행 감시로 D 를 쟀습니다.

```
00:D282 TCD   00:D267(문맥 되살리기) 안. D = 7E:1A7B
              세이브스테이트 여섯의 7E:1A72~: 50 07 00 00 FB 02 27 00 00 00 00 00 00 6C 80 00 → D = 0000
00:88DA PLD   NMI 처리기 00:885D 의 PHD 를 되돌림
03:9F5A PLD   03:9F2C 끝. 01/0A 의 여행의 문(출구 속성 33)을 밟자 D = 0000 (5번)
11:FCD7 PLD   슬라임 레이스. D = 1200 (11번)
```

`03:9F5A` 는 필드·전투·마을 세 곳에서 걸리지 않았습니다. CDL 의 서브루틴 입구 표시를 거슬러 `03:9CDB` ← `03:9B19` ← `03:9B0F` ← `02:BB37` ← `00:C9EB` 를 찾았고, `00:C9EB` 는 맵을 옮긴 뒤 선 칸의 출구 속성이 `33` 일 때 부르는 곳이었습니다([dq5-field-format.md 「순간이동 칸」](../docs/dq5-field-format.md#순간이동-칸-00c99e-039b9c)). 01/0A (8,12) 에서 위로 걸어 (8,10) 의 문에 서자 불렸습니다. 문 칸에 바로 내려서는 불리지 않았습니다.

## 5. 표시 없는 바이트를 롬으로 나누기

CDL 이 닿지 않은 후보는 롬의 자료 구조로 나눴습니다. 디코더가 실제로 읽어 내는 범위(대화 스크립트 574개, 스프라이트 레코드·타일, 맵 OBJ 타일, 그룹 `50` 이상의 블록·CHR, 실내 맵 블록, 몬스터 그림, 연출 조각·색, 전투 배경, 연출 스크립트, 탈것, 보상 표, 이름 표 3)와 형식 문서가 「이어져 있다」 고 적은 덩어리(메시지, 인물 목록, 몬스터·구역·성장 표, 물건 표, 이름 표, 조우 격자, 창 레코드, 상점 목록, 맵 레코드 등)입니다.

몬스터·구역·성장 표는 크기를 더해 이어짐을 확인했습니다. 구역 `23:96F3` + 85 × 22 = `9E41`, 사람 성장 `9E41` + 11 × `50`(16진) = `A1B1`, 몬스터 성장 + 42 × `50` = `AED1` 이 바로 다음 표의 시작입니다.

범위마다 CDL 이 코드로 표시한 바이트와 겹치는지 셌습니다. 처음 만든 범위 셋은 겹쳤고, 고치거나 뺐습니다.

```
전투 배경 팔레트   841,595바이트 중 코드 1,149  → 시대 번호(+98·+B4)를 k < 1E 에만 → 6,115바이트, 코드 0
연출 조각 구간      29:8000~FACF 한 덩어리로 봄 → 코드 88 → 뺌(조각마다만 받음)
실내 맵 CHR         블록이 가리키는 가장 큰 번호까지 → 코드 800 → 뺌(블록 표 끝에 블록이 아닌 바이트가 섞임)
```

남은 범위는 모두 코드 0 이었습니다.

그 밖은 같은 뱅크의 바로 앞 실행 명령부터 틈을 이어 읽었습니다. 처음에는 무조건 분기에서 멈췄는데 거의 다 「끊김」 이었습니다. 이어서 `RTS`·`JMP` 뒤도 읽고 BRK 는 서비스마다의 인자 수(`dq5talk.brk_args`)로 건너뛰게 하자, `06:BBF2` 처럼 `BRK 0C 02 2D` 의 인자 `2D` 와 `STZ $0F1B` 가 만난 자리가 명령 중간으로 갈렸습니다. 다음 실행 명령까지 닿은 45곳은 모두 틈 끝이 그 명령 시작에 꼭 맞았습니다. 다만 맞는다고 코드라는 뜻은 아닙니다. `03:A4AC`(`04 05 06 07 08 09 10 …`)는 「명령 시작, 틈 끝 맞음」 이었지만 타이틀 바다 타일맵의 바이트 128개(`03:A478`~) 안이었습니다.

연출 스크립트는 형식 문서의 명령표대로 흐름을 따라갔습니다. `32 x t`(표 t 의 칸으로 부르기)의 표는 칸 수가 롬에 없어 처음에 「8000 이상인 동안」 으로 읽었더니 모르는 명령이 둘 나왔습니다. 칸이 가리키는 곳을 따로 따라가 모르는 명령 없이 끝나는 동안만 칸으로 받게 바꿨습니다. 목록에 없는 연출 조각은 아는 조각의 끝에서 이어 풀어 다음 아는 조각 시작에 꼭 맞게 닿는 것만 받았고, 뱅크 `29` 의 다섯 곳이 그렇게 갈렸습니다.

```
표시 없는 후보   자료 구조 안  명령 중간  모양으로 자료 보임  명령 시작  미정
직접 피연산자        563          46          9               1        15
값 모름            3,112         425         68              33       413
```

직접 피연산자의 「명령 시작」 1곳은 `03:F5C4 AND $1BB1`(3절과 같은 고리)입니다. 「미정」 15곳은 리스팅과 바이트를 눈으로 봤습니다.

```
03:CF90  … C9 7E D0 1A …   CMP #$7E / BNE 안            실행되지 않은 코드의 명령 중간
23:DE3F  20 F3 DE 20 1B DF  JSR $DEF3 의 끝 바이트       〃
23:DF8C  49 FF FF 1A 8D …   EOR #$FFFF 안                〃
13:9EC4  13:9EC0~9EDF 한 타일만 읽히지 않음 (블록 #189 만 가리킴, 어느 맵도 쓰지 않음)
14:886A  14:8860~889F 두 타일 (블록 #545)
04:FBDB  DD FB 33 FC AB FC 2D FD  상점 목록 포인터(04:FBD5~)
나머지 9곳  작은 수의 표, FF 로 나뉜 목록, 15비트 색
```

## 틀렸던 것들

- 롬에서 `D5 A2 02` 가 처음 걸린 `12:8963` 을 맵별 루틴 표로 읽었습니다. 6바이트 항목의 인물 목록 표였고, 맵별 루틴 표는 `15:F907` 쪽이었습니다.
- 쓰기 감시를 `7E:1ABC`~`1BB1` 에만 걸어 17/01 의 쓰기를 놓쳤습니다. 데이터 뱅크가 `15` 라 `15:1BB1`(낮은 WRAM 거울)로 썼습니다.
- CDL 은 쌓이기만 한다고 보았습니다. 함께 돈 실행은 서로 덮어써, 실행마다 받아 합쳐야 했습니다.
- 몬스터 그림·전투 배경 그림을 자료 구조로 더하면 많이 줄 것으로 보았지만 거의 이미 CDL 의 자료였습니다. 줄어든 것은 몇 개의 팔레트·목록이었습니다.
