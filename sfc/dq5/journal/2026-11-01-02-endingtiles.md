# 2026-11-01-02: 엔딩 비행에서 늘린 필드 타일 쓰지 않기

필드 타일을 512개 넘게 늘린 롬은 엔딩에서 天空城 을 타고 나는 장면의 땅이 검었습니다. 스태프 롤 글자가 늘린 타일과 같은 VRAM 자리(워드 `4000`~`5FFF`)를 쓰기 때문입니다([세계 실측 일지 6절](2026-10-31-03-worldmeasure.md#6-엔딩-비행과-늘린-타일)). 스태프 롤은 그대로 두고, 엔딩 동안은 필드가 타일 512 이상을 쓰지 않게 했습니다. 결과는 [필드 형식 「타일 512개 넘기기」](../docs/dq5-field-format.md#타일-512개-넘기기)와 [필드 그림 쓰기](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)에 넣었습니다.

## 1. 무엇을 바꿀지

VRAM 은 필드 타일 1,024개·OBJ·타일맵·BG3 창 글자로 다 차 있어, 스태프 롤 글자 16KB 를 옮길 자리가 없습니다. 옮긴다 해도 원래 장면이 바뀝니다. 그래서 바꿀 쪽은 필드입니다. 엔딩 비행에서만 늘린 타일을 보내지 않고, 타일맵에 타일 512 이상을 쓰지 않으면 됩니다.

엔딩인지는 `7E:21EA` bit7 로 가릅니다. 켜는 곳은 엔딩 준비 `02:F974`(`BRK 0C 80 5A`) 하나이고([그래픽 형식](../docs/dq5-graphics-format.md)), 게임도 이 비트로 매 걸음 스태프 롤을 부릅니다(`00:841D`·`00:8436`). 엔딩 장면은 앞 일지와 같이 02/06 인물 스크립트 첫머리(`10:9B89`)를 `37 74 F9 02` 로 덮어 들어갑니다. 원본 게임으로 3,100프레임을 돌리자 성은 화면 가운데 있고 땅이 아래로 흘렀습니다. 타일맵을 계속 새로 쓰는 것입니다.고치기 전 tiles 롬은 같은 프레임에 성만 보이고 땅이 검었습니다.

## 2. 블록마다가 아니라 타일마다 바꾼 까닭

처음에는 엔딩용 블록 표를 따로 두려 했습니다. 그런데 블록을 읽는 길이 셋입니다. 번호 511 미만은 `00:BC6D`(타일 늘리기가 제자리에서 바꾼 짧은 코드), 511 이상은 `dq5fieldtables.py` 의 `00:BC4E` 훅, 지도를 늘린 롬은 `dq5fieldwrite.py` 의 빠른 훅(`00:BBF8`)이 옮긴 표를 직접 읽습니다. 셋 모두 엔딩 갈래를 넣으면 도구 셋을 고쳐야 하고, 필드를 불러올 때 칸마다 1,090번 도는 코드가 길어집니다.

세 길은 모두 `$94`·`$96`(두 층 타일 번호, 10비트)을 채운 뒤 `00:BBAC` 로 팔레트 비트를 붙입니다. 그래서 `00:BBAC` 한 곳에서 타일 번호를 바꿨습니다. 블록 대신 타일마다 「엔딩에서는 이 타일 대신 저 타일」을 주는 `ending_tiles` 입니다.

## 3. 코드

`dq5fieldgfxwrite.py` 의 타일 늘리기 패치(`--worlds-at`)에 세 가지를 더했습니다.

```
00:BBAC  LDA $7E21E9 / BMI 엔딩     ; 16비트로 읽으면 21EA bit7 이 N
         (palette_fast 또는 palette_worlds, 원래와 같음) ... RTS
엔딩:    JML 엔딩 코드

엔딩 코드  LDA $96 / ASL / TAX / LDA 엔딩위층표,X / ORA $C6 / STA $96
           LDA $94 / ASL / TAX / LDA 엔딩아래층표,X / STA $94 / JML (00:BBAC 코드 끝 RTS)

DMA 문    LDA $7E21E9 / BMI +3 / JMP DMA / RTS   ; 불러오기·다시 그리기 훅이 DMA 대신 JSR
```

엔딩 워드 표는 타일 0~1,023 마다 타일맵 워드 하나(위층 니블 4비트·아래층 3비트)입니다. 타일 0~511 은 그 타일 그대로, 512 이상은 대체 타일의 워드입니다. 엔딩은 `02:B9D8` 이 `$1949` 를 0 으로 두므로 세계 0 니블로 셉니다. `ending_tiles` 가 없거나 짧으면 나머지 대체는 타일 − 512 입니다. `tile_attributes` 를 주지 않을 때 늘린 타일 속성이 타일 − 512 인 것과 같은 규칙입니다. 대체 타일이 512 이상이면 `ValueError` 로 거부합니다.

자리는 `--worlds-at` 의 팔레트 표 뒤, 세계 1·2 RLE 앞입니다(엔딩 코드 34바이트·표 4KB). 읽는 도구(`current`·`rom_layout`)는 고르기 표·니블 표 자리만 읽으므로, 엔딩 갈래 전에 만든 롬도 그대로 읽습니다. 디코더 `dq5field` 는 `00:BBAC` 가 `AF E9 21 7E 30` 으로 시작하면 팔레트 코드를 6바이트 뒤에서 읽고, `ending_word` 로 엔딩 워드를 냅니다. 타일을 늘리지 않은 롬에는 아무것도 쓰지 않습니다.

## 4. 엔딩 비행 실측

`dq5gfxlimitcheck.py` 의 시험 롬으로 쟀습니다. tiles 롬은 늘린 타일 512개가 원래 타일의 비트 반전이고, 블록 두 층의 칸 타일에 512 를 더했습니다(위층 0 은 그대로). 그래서 필드 칸이 모두 늘린 타일을 씁니다. endmap 롬은 tiles 와 같되 `ending_tiles` 로 512 + t 를 511 − t 로 바꿉니다.

1,000프레임에 세 롬 모두 BG3 글자 기준이 `4000`, VRAM 워드 `4000`~`5FFF` 는 비어 있었습니다(스태프 롤이 지운 자리). BG1·2 에서 채운 칸은 셋 다 2,176개였습니다.

```
롬             타일 512 이상 칸   타일맵 0000~0FFF
고치기 전 tiles     1,285            -
원본 게임              0            -
tiles                  0            원본 게임과 바이트마다 같음
endmap                 0            2,176칸 모두 ending_word 와 같음
```

tiles 롬은 600·700·800·1,000·1,300·1,600·2,000·2,500·3,000프레임 아홉 장면 모두 타일 512 이상 칸이 0개였습니다. 그 가운데 600~1,300·2,500·3,000프레임은 VRAM 64KB 전체가 원본 게임과 같았습니다. 1,600·2,000프레임은 BG 스크롤이 1점 달라 새로 쓴 타일맵 한 줄(64·30워드)이 달랐고, 화면 픽셀은 스크롤 1점과 CGRAM 14바이트 때문에 달랐습니다(아래 「틀렸던 것들」). 세계마다 니블이 다른 nibs 롬은 아홉 장면 모두 VRAM 이 tiles 롬과 같았습니다.

## 5. 엔딩이 아닐 때

`00:BBAC` 앞의 6바이트는 엔딩이 아니면 `LDA long`·`BMI`(건너뛰지 않음) 8사이클입니다. 칸마다 95마스터 클록을 더한 롬은 필드 불러오기가 한 프레임 늦은 적이 있어([블록 훅 일지](2026-10-30-25-mblock.md)), `dq5watercheck.py` 와 같은 방법(`lua/dq5framelog.lua`)으로 다시 쟀습니다. 마지막 멈춘 구간과 세계 2 첫걸음입니다.

```
롬                세계 0 (341,56)   세계 1 (50,28)   세계 2 (62,64)   세계 2 첫걸음
원본 게임            462~492           453~483          451~481           822
엔딩 갈래 전 tiles   462~492           453~483          451~481           822
tiles·nibs           462~492           453~483          451~481           822
```

900프레임 VRAM 은 세 세계 모두 엔딩 갈래 전 tiles 롬과 바이트마다 같았습니다. `dq5gfxlimitcheck.py` 의 나머지 시험(필드에 서기·걷기·이벤트 전투 뒤 `01:B4D5`·다시 그리기·キメラのつばさ·ルーラ·융단·세계를 오가는 열한 장면)도 그대로 통과해, 엔딩이 아닐 때는 늘린 타일을 여전히 보냅니다.

## 6. DQ4 쪽에서 쓰는 법

DQ4 필드 그림을 512개 넘게 쓰면 `fieldgfx.json` 에 `ending_tiles` 를 둡니다. 타일 512 부터 차례로, 엔딩 비행에서 대신 그릴 타일(0~511)입니다.

```json
{"format": "dq5fieldgfx/1", "tiles_file": "tiles.bin", "...": "...",
 "ending_tiles": [36, 36, 37, 120]}
```

이 예는 타일 512·513 을 36, 514 를 37, 515 를 120 으로 그리고, 516 부터는 타일 − 512 로 그립니다. 엔딩에서 날아가는 땅이 늘린 타일만 쓰는 지형(새 산·새 숲 등)이면 비슷한 원래 512개 안의 타일을 고릅니다. 팔레트는 대체 타일의 니블을 따릅니다. 엔딩 장면은 세계 0 만 보이므로 세계 0 타일을 고릅니다. 빌드는 그대로 `dq5fieldgfxwrite.py … patch --worlds-at … --extra-at …` 입니다.

## 틀렸던 것들

- 엔딩 동안은 늘린 타일 DMA 를 건너뛰어도 화면이 원본 게임과 같은 프레임에 흐를 줄 알았습니다. 두 갈래를 함께 넣은 롬은 엔딩의 BG 스크롤이 원본 게임과 1점(한 프레임) 어긋났습니다(800프레임 세로 83 대 82). DMA 건너뛰기만 끈 롬과 엔딩 워드 표 읽기만 끈 롬은 각각 원본과 같은 82 였습니다. 타일맵 내용은 같으므로 고치지 않았습니다.
- 처음 짠 endmap 검사는 위층 타일 0 칸까지 대체를 기대해 891칸이 틀렸다고 했습니다. 시험 롬의 블록은 위층 0(「위층 없음」)에 512 를 더하지 않으므로 대체되지 않는 것이 맞습니다.

## 남은 것

- 두 갈래를 함께 넣을 때만 엔딩 비행이 한 프레임 어긋나는 까닭.
- 블록마다 다른 엔딩 대체(같은 늘린 타일을 블록에 따라 다른 타일로). 지금은 타일마다 하나입니다.
