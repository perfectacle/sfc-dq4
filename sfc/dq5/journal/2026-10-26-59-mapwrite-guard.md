# 2026-10-26-59: 맵 번호와 지원하지 않는 입력 필드 검사

맵 쓰기 도구가 없는 맵 번호를 받아 이웃 그룹의 포인터를 덮거나, 지원하지 않는 입력 필드를 조용히 버리는 문제를 고쳤습니다. 입력 범위는 [쓰기 형식](../docs/dq5-build-format.md#실내-맵-레코드-dq5map1)에 적었습니다.

## 1. 없는 맵 번호가 이웃 그룹을 가리킴

원본 그룹 `17`에는 `00`~`04` 맵만 있습니다. `17/00`을 내보낸 JSON의 `map`을 `17/05`로 바꾸자 기존 도구는 쓰기 두 개를 정상 생성했습니다. 그룹 포인터 표에서 다섯 칸을 더한 주소 `0F:8CD3`가 다음 그룹 `18/00`의 포인터 자리였기 때문입니다.

실제로 빌더에 넣은 롬에서 그 세 바이트가 `F0 CF 1B`에서 `00 80 30`으로 바뀌었습니다. 새 맵을 추가한 것이 아니라 `18/00`이 `1B:CFF0` 대신 새 레코드 `30:8000`을 가리킨 것입니다. 이번 확인은 롬 바이트 비교이며 게임 실측은 아닙니다.

포인터 주소를 계산하기 전에 원본 맵 목록에 번호가 있는지 검사하도록 고쳤습니다. `patch`와 `dump` 모두 없는 번호를 거부합니다.

## 2. 출구 필드는 맵 그림에 포함되지 않음

맵 JSON에 `exits`를 넣어도 기존 도구는 오류 없이 같은 패치를 만들었습니다. 출구 목적지 표는 맵 레코드 바깥에 있고, 인코더는 그 필드를 읽지 않았습니다.

최상위 필드를 검사해 지원하지 않는 이름은 오류로 알립니다. JSON 객체가 아니거나 필수 필드가 빠진 입력도 거부합니다. 정상 `dump`가 내보내는 보존 비트와 배치 목록 컴파일러의 출력은 계속 받습니다.

## 3. 정상 입력과 거부 결과

- 원본 맵 364개를 풀고 다시 쌌습니다. 233,794바이트 모두 같았습니다.
- 합성 검사 네 개에서 원본 목록의 경계, 지원하지 않는 필드, 정상 레코드 왕복, 오류 때 기존 출력 파일 보존을 확인했습니다.
- 원본 `17/00`을 내보내 `17/05`나 `exits`를 넣은 CLI 입력은 종료값 1이며 패치 파일을 만들지 않았습니다. 그대로 둔 입력은 종료값 0이었습니다.
- `17/00`을 배치 목록으로 펼쳐 다시 컴파일한 뒤 패치를 만들었습니다. 명령 101개·레코드 560바이트를 정상 처리했습니다.

## 남은 것

새 맵 번호 증설, 출구 목적지·영역 이동 표 쓰기는 이번 수정에 포함되지 않습니다. 기존 맵 번호를 골라 레코드를 교체하는 기능의 입력 경계를 고친 것입니다.
