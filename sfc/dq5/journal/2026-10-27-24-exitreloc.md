# 2026-10-27-24: 실내 출구·영역 이동 표 늘리고 옮기기

DQ4 의 마을을 DQ5 맵에 올리면 계단과 가장자리 수가 원래 맵과 달라집니다. 기존 `dq5exitwrite.py` 는 원래 슬롯만 고치므로, 출구 목적지 표·영역 이동 레코드와 색인·고층 목록을 통째로 다시 쓰고 다른 자리로 옮기는 `dq5exitreloc.py` 를 만들었습니다. 표를 찾는 코드를 디스어셈블과 실행 기록으로 감사해서 표마다 둘 수 있는 뱅크를 정했습니다. 결과는 [쓰기 형식](../docs/dq5-build-format.md#실내-출구영역-이동-표-옮기기-dq5exittables1)에 있습니다.

## 1. 빈 곳이 없는 뱅크 2A

원래 표 넷은 빈틈없이 붙어 있습니다. 영역 이동 레코드 `2A:D812`~, 색인 `2A:EB0E`~, 출구 목적지 `2A:ED61`~`2A:F223`, 그 뒤는 코드입니다. 고층 목록 16개는 뱅크 `01` 의 `01:9635`~`9770` 에 따로 있습니다. 출구 하나만 늘어도 뒤의 코드를 덮으므로, 늘리려면 어느 표든 옮겨야 합니다.

표를 찾는 코드는 이렇습니다.

| 표 | 찾는 코드 | DB |
| --- | --- | --- |
| 출구 목적지 | `2A:F709` 에서 `$84`·`$85` 에 즉값 `61`·`ED`, 읽기는 `LDA ($84)`·`LDA ($84),Y` | `2A`(`2A:F701`) |
| 색인 | `01:9448` 등 `LDA $EB0E,Y` | `2A`(`01:943D`) |
| 레코드 | `01:94A1` `ADC #$D812`, `01:94AC` `ADC #$2A` → `$183A`·`$183C` | 실행기에서 `$183C` |
| 고층 목록 | `01:94B4` 이하 목록마다 `LDA $01xxxx`·`LDX #`·`LDA #$01` | 실행기에서 `$183C` |

출구 표의 포인터는 16비트이고 뱅크는 DB 입니다. 즉값 두 개를 바꾸면 뱅크 `2A` 안에서는 어디로든 옮길 수 있지만, 다른 뱅크로 가려면 DB 를 바꾸거나 읽는 방식을 바꿔야 합니다.

## 2. DB 를 쓰는 곳 감사

DB 를 표 뱅크로 바꾸면, 그동안 abs 로 읽고 쓰는 모든 것이 그 뱅크로 갑니다. 뱅크 `00`~`3F` 는 `0000`~`7FFF` 에 WRAM 과 MMIO 가 보이지만 `40` 이상은 보이지 않습니다. 그래서 표 뱅크를 DB 로 두는 동안 실행하는 명령을 모두 보아야 합니다.

정적 검색으로는 `$183C` 를 DB 로 쓰는 곳이 `00:CDEC` 하나뿐인 줄 알았습니다. 읽어 보니 `2A:F4B9` 도 `$183C` 를 DB 로 두고 레코드를 `($00),Y` 로 읽으면서 `LDA $1954`·`INC $1EAB` 를 합니다. `2A:F486` 은 `$183C` 를 `$1E82` 로 옮기고, `2A:FD11` 이 그것을 DB 로 두어 `STA $198E` 를 합니다.

빠뜨린 곳이 없는지 보려고 `dq5exitcheck.lua` 에 `AUDIT=1` 을 더했습니다. PLB 다음 명령 다섯 곳(`2A:F705`·`01:9441`·`00:CDF9`·`2A:F4C2`·`2A:FD1A`)에서 창을 열고, DB 가 그 값인 동안 실행한 명령과 그 뱅크 `8000`~ 의 자료 읽기를 모읍니다. 원본 롬의 8장면(출구 세 종류, 일반·고층·음수 가장자리 영역 이동, 효과음 갈래, 속성 `33` 계단)에서 돌렸습니다.

```
DB 창 명령 417개, DB 기준 접근 45곳 (abs 8000~ 4곳)
  01:9448 LDA $EB0E,Y   1086회 롬 읽기 199곳 2A:EB0E~2A:ED60
  2A:F4CA LDA $1954        2회 롬 읽기 0곳
  00:8F99 LDA ($0B,S),Y    2회 롬 읽기 1곳 2A:F4D2~2A:F4D2
  …
```

`8000` 이상 abs 는 색인 읽기 4곳뿐이고, 나머지 abs 는 WRAM 과 MMIO 였습니다. 마음에 걸린 것은 BRK 처리기 `00:8F99` 가 `LDA ($0B,S),Y` 로 효과음 인자를 DB 기준으로 읽는 것이었습니다. 레코드를 옮기면 인자를 엉뚱한 뱅크에서 읽을 것처럼 보였지만, 처리기는 그 전에 스택의 K 를 DB 로 둡니다(`00:8F92`~`8F95`). 호출한 코드의 뱅크에서 읽으므로 레코드 뱅크와 상관없습니다.

장면이 지나지 않은 필드행 갈래(`2A:F52A`·`F425`)는 코드로 읽었습니다. `STA $198E`·`INC $1EAB` 와 레코드 `($00)` 읽기뿐이었습니다.

결론은 이렇습니다.

- 색인은 DB 로 MMIO 곱셈을 쓰고, 레코드·고층 목록은 실행기가 DB 로 WRAM 을 씁니다. 셋 다 뱅크 `00`~`3F` 에만 둡니다.
- 출구 로더는 DB 를 `2A` 그대로 두고 표만 long 간접으로 읽게 하면 다른 접근은 바뀌지 않습니다. 출구만 뱅크 `40` 이상에 둘 수 있습니다.

## 3. 가장 작은 코드 고침

출구 표를 다른 뱅크로 옮길 때 `LDA ($84)`(`B2 84`)를 `LDA [$84]`(`A7 84`)로, `LDA ($84),Y`(`B1 84`)를 `LDA [$84],Y`(`B7 84`)로 바꾸면 길이가 같습니다. 11곳입니다. 셋째 바이트 `$86` 에 뱅크를 넣을 자리가 모자라서, `2A:F709` 의 8바이트(`LDA #/STA $84/LDA #/STA $85`)를 `JSL 스텁` 과 `NOP` 넷으로 바꾸고, 표 바로 앞에 13바이트 스텁(`$84`~`$86` 을 채우고 `RTL`)을 둡니다. 스텁은 직접 페이지만 쓰므로 어느 뱅크에 있어도 됩니다. 출구가 뱅크 `2A` 안에서만 움직이면 즉값 둘만 바꿉니다.

색인·레코드·고층 목록은 즉값만 바꿉니다. 색인은 뱅크 즉값 하나와 주소 넷, 레코드는 주소와 뱅크, 고층 목록은 목록마다 개수 주소(long)·레코드 주소·뱅크입니다. 표가 원래 자리에 들어가면 코드는 한 바이트도 쓰지 않습니다.

옮긴 표가 떠난 자리는 비므로 다른 표를 넣어도 됩니다. 레코드를 늘린 뱅크로 보내면 `2A:D812`~`2A:F223` 6,674바이트가 비어, 출구와 색인이 그 안에서 즉값만으로 늘어날 수 있습니다.

## 4. 직렬화와 왕복

`dump` 는 코드의 즉값이 가리키는 자리에서 네 표를 읽어 `dq5exittables/1` 문서로 냅니다. 출구는 맵 346개 모두, 영역 이동은 색인 순서, 고층은 목록 16개를 원래 순서로 담습니다. 원본을 다시 직렬화한 6,990바이트는 원래 바이트와 같았습니다(쓰기 0개).

`check` 는 빌드한 롬을 코드가 가리키는 자리에서 다시 읽고, 맵마다 엔진 순서로 레코드를 찾아 입력과 견줍니다. 세 가지 배치를 돌렸습니다.

```
표 자리 exits 2A:ED61, records 2A:D812, index 2A:EB0E, high 01:9635; 쓰기 0개, 롬 1.5MB 검사 통과
표 자리 exits 7C:800D, records 3E:8000, index 0B:FBB0, high 3E:A000; 쓰기 71개, 롬 4MB 검사 통과
표 자리 exits 2A:D812, records 3F:8000, index 2A:EB0E, high 01:9635; 쓰기 5개, 롬 2MB 검사 통과
```

합성 롬 단위 테스트 8개가 원래 자리 왕복, 줄여서 원래 자리에 쓰기, 늘려서 다른 뱅크로 옮기기, 뱅크 `2A` 안 옮기기, 자리 제약, 입력 검사, 음수 가장자리 왕복, 옮긴 롬에서 고정 슬롯 쓰기 거부를 봅니다.

## 5. 밟아서 확인

`dq5exitcheck.py` 에 롬 세 벌을 더했습니다. `r` 은 원본 그대로 네 표를 옮긴 롬(출구는 뱅크 `7C`), `g` 는 늘린 롬, `p` 는 줄여서 원래 자리에 쓴 롬입니다. 기존 24장면에 20장면을 더해 44장면이 모두 맞았습니다.

| 장면 | 바꾼 롬 | 원본 롬 |
| --- | --- | --- |
| `r` 같은 그룹·다른 그룹·좌표 출구 | 01/03 (19,5), 0E/03 (38,67), 01/00 (21,28) | 같음 |
| `r` 고층 공유 50/50·50/51, 음수 가장자리 | 05/01 (33,47), 01/04 (16,8) | 같음 |
| `g` 출구 종류 같은 그룹 → 좌표 | 01/04 (16,6) 층 1 | 01/03 (19,5) |
| `g` 01/03 에 출구 추가 | 01/09 (24,5) | 01/05 (4,7) |
| `g` 01/03 을 색인에 추가 | 01/04 (16,7) | 01/03 (14,14) 에 남음 |
| `g` 고층 공유 목록에 레코드 추가 | 두 맵 모두 01/04 (16,7) | 두 맵 모두 05/01 (33,47) |
| `p` 좌표 출구 → 같은 그룹 | 01/04 (13,47) | 01/00 (21,28) |

`r` 롬 9장면에서는 옛 표 자리 전체(뱅크 `80`~ 거울 포함)에 읽기 감시를 걸었고 읽기가 한 번도 없었습니다. 표를 찾는 곳이 위의 코드뿐이라는 뜻입니다.

스텁이 원래 쓰지 않던 직접 페이지 `$86` 을 쓰는 것도 걸렸습니다. 처음에는 `$86` 을 건드리는 PC 를 모두 모아 스텁 말고는 없기를 기대했지만, 뱅크 `00`·`01`·`0F`·`12` 의 32곳이 읽고 썼습니다. `$86` 은 흔한 임시 칸입니다. 물어야 할 것은 「로더가 덮은 값을 누가 읽는가」 이므로, `2A:F709` 에 닿은 뒤 다른 코드가 `$86` 을 다시 쓰기 전에 읽는 PC 만 모으게 바꿨습니다. 44장면 모두 그런 읽기가 없었습니다. 이 검사는 `dq5exitcheck.py` 가 장면마다 합니다.

고정 슬롯 쓰기와 함께 빌드하면, 옮긴 표가 떠난 자리에 고정 슬롯 편집이 떨어져 아무 효과 없이 빌드가 통과할 수 있었습니다. 그래서 `dq5exitreloc.py` 는 쓰기가 있으면 원래 표 자리 전체를 맡습니다(새 표가 들지 않은 곳은 같은 바이트로 씀). 01/00 출구 1 을 고친 고정 슬롯 패치와 레코드를 옮긴 패치를 함께 빌드하자 `겹침 2A:ED86~2A:ED87` 로 거부됐습니다.

장면 이동 도구 `dq5warp.lua` 는 배 사다리 항목 `2A:EFF5` 를 덮어 순간이동합니다. 출구 표를 옮기면 엔진이 그 자리를 읽지 않으므로 순간이동이 원래 사다리로 갑니다. `WARPEXIT` 로 덮을 자리를 받게 하고, `dq5exitcheck.py` 가 롬마다 옮긴 표의 17/00 첫 항목 자리를 계산해 넘깁니다.

## 틀렸던 것들

- 추가 출구를 01/03 의 (10,13) 에 만들었더니 주인공이 그 칸으로 내려가지 못했습니다. 셀 `+1` bit7(가구)이 켜진 탁자였습니다. 빈 바닥 (4,13) 으로 옮기자 걸어 들어갔지만, 이번에는 출구가 불리지 않았습니다. 계단 판정 `00:E2C5` 는 주인공이 선 두 칸을 다 봅니다. 오른쪽 칸만 `85` 로 두면 왼쪽 칸이 바닥이라 넘어가지 못합니다. 왼쪽 (3,13) 을 `05` 로 함께 바꾸자 발동했습니다. 출구 번호는 `+4` = `85` 인 오른쪽 칸만 셉니다.
- 처음에는 원본 롬에서 01/03 의 출구 1 이 01/04 로 갈 줄 알았습니다. 레코드가 하나뿐인 맵의 다음 출구는 다음 맵(01/04)의 첫 레코드인 「01/05 출구 0」 이고, 실제로 01/05 (4,7) 에 섰습니다.
- 재패치 검사에서 `0B:FBB0` 에 둔 색인이 「빈 자리 밖」 이라며 거부됐습니다. 빈 자리를 롬의 0 줄로 찾기 때문에, 이미 색인이 들어간 롬에서는 그 자리가 빈 자리로 보이지 않습니다. 지금 표가 놓인 자리를 허용 목록에 더했습니다.

## 남은 것

- 새 맵 번호 연결. 맵 목록을 늘리는 일(`dq5mapwrite.py`)과 함께 해야 하고, 출구 표는 그룹마다 맵 번호가 0부터 이어져야 합니다(`2A:F732`).
- 고층 맵이 목록을 나눠 쓰는 방식(50/* 한 목록, 52/* 한 목록 등)은 `01:94B4` 의 코드가 정하므로 바꾸지 못합니다.
- 실제 새 뱅크 자리. 「새 뱅크 나누기」 표에 출구·영역 이동 줄은 아직 없습니다. 통합 빌드에서 정합니다.
- 필드행 영역 이동 갈래(`2A:F52A`)의 DB 감사는 코드 읽기만 했습니다.
