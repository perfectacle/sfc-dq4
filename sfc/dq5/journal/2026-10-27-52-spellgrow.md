# 2026-10-27-52: 행동 번호 늘리기와 새 주문

DQ4 에는 DQ5 에 없는 주문이 있습니다. 기존 주문 칸을 덮어 쓰지 않고 새 주문을 더하려면, 전투 행동 번호(`00`~`AA`, 171개)를 늘려야 합니다. 행동 번호로 색인하는 표를 찾아 늘리는 `dq5spellgrow.py` 를 만들고, 새 번호 `AB` 를 배워서 필드와 전투에서 외우는 것을 확인했습니다. 결과는 [쓰기 형식](../docs/dq5-build-format.md#행동-번호-늘리기-dq5spellgrow1)에 있습니다.

## 1. 어떤 표가 행동 번호로 색인되나

문서에 적힌 표만으로는 빠진 것이 있을까 봐 실행으로 찾았습니다. 같은 전투에서 주인공이 ホイミ(`27`)를 외우는 실행과 ベホイミ(`28`)를 외우는 실행을 돌렸습니다. 프레임 90~320 사이 롬 바이트의 읽기 횟수를 MesenCE 접근 카운터로 남겨 견줬습니다.

```text
27 쪽만  20:B847-48  26:85B3-B4  26:878C  26:88B3-B4  21:9BDB  22:80DE~  27:8097-98 …
28 쪽만  20:B849-4A  26:85B5-B6  26:878D  26:88B5-B6  21:9BDC  22:80E1~  27:8099-9A …
```

두 번호 차이만큼(1 이나 2) 떨어진 짝이 행동 번호로 색인하는 표입니다. `20:B7F9`(처리 루틴)·`26:8765`(MP·범위)·`26:8865`(실행 루틴)는 알던 것이었습니다. `26:8565`(2바이트)와 `21:9BB4`(1바이트)가 새로 나왔습니다. `21:9BB4` 는 `21:9BAD` 가 읽어 `$47` 에 두는 값으로, 주문 목록 창의 「しょうひMP」 숫자입니다(メラ 2, メラミ 4 …). `22:80DE~` 는 이름 표 3 이고, `27:8097~` 은 처리 루틴이 고른 양 번호의 표라 행동 번호 색인이 아닙니다.

`26:8565` 는 `20:84A6` 이 `$1016` bit4 일 때 실행 루틴 대신 읽습니다. ホイミ 칸 값이 `0070` 이라 루틴 주소는 아닌 것으로 보이지만, 뜻은 보지 않고 다른 표처럼 베껴 늘렸습니다. 연출 표(`26:8BE0`·`26:8C75`)는 이 비교에 나오지 않았지만, 긴 주소로 읽으므로 함께 옮겼습니다.

## 2. 옮길 수 있는 표와 없는 표

표마다 롬 전체에서 그 주소를 피연산자로 쓰는 명령을 찾았습니다. 여섯은 `LDA long,X` 로만 읽혀 어디로든 옮길 수 있습니다. 처리 루틴 표는 `20:AA9D`·`20:AAD0` 의 `JSR ($B7F9,X)` 이고, 필드 처리기 표는 `11:801C` 의 `JSR ($8024,X)` 입니다. `JSR (abs,X)` 는 지금 뱅크에서 표를 읽으므로 이 둘은 뱅크 20·11 을 떠날 수 없습니다.

뱅크 20 끝에는 `20:FFD9` 부터 39바이트의 0 이 있습니다. 표를 옮기기엔 모자라서, 원래 표는 두고 `JSR` 을 스텁으로 돌렸습니다. 스텁은 X 가 원래 범위면 `JMP ($B7F9,X)`, 넘으면 스텁 뒤에 덧붙인 표로 갑니다. 필드도 같은 꼴로 `11:FFB0` 에 두었습니다.

## 3. 처음 돌린 필드에서 나온 것

처음 롬에서는 필드 じゅもん 창에 「ホイミミ」 가 나왔지만, 골라도 외워지지 않았습니다. 스텁에 들어온 X 가 `0108` 이 아니라 `0008` 이었습니다. `11:8014` 의 `SBC` 부터 A 를 8비트로 다뤄서 `(AB − 27) × 2 = 108` 의 bit8 이 `ASL` 에서 carry 로 빠진 것입니다. 원래 표는 18칸이라 이런 일이 없었습니다. 스텁 앞에 `BCC / XBA / LDA #1 / XBA / TAX` 를 두어 carry 를 B 로 되살리고(그 뒤 B 는 다시 0), 그러자 HP 5 → 35, MP 100 → 97 로 외워졌습니다.

## 4. 「とくぎ」 로 배운다

레벨업 메시지는 「ホイミミの とくぎを おぼえた！」(`19F`) 였습니다. 같은 자리의 원래 주문은 「じゅもんを おぼえた！」(`0C7`)입니다. 습득 루틴을 실행 기록으로 훑자 `25:8BF3` 의 `CMP #$66` 이 둘을 가르고 있었습니다. 롬에서 같은 비교를 찾으면 `20:8460`(`66` 밑에서만 `20:A7B4` 를 부름)과 AI 의 `21:F66C`·`21:F81B` 가 있습니다. `00`~`65` 는 주인공·몬스터 주문으로 다 차 있어, 새 번호는 `66` 이상인 특기 쪽에 들어갑니다. 주문으로 다루게 하려면 이 경계들을 바꿔야 하는데, 이번에는 하지 않았습니다.

## 5. 원래 롬과 견주기

`dq5spellgrowcheck.py` 로 롬 두 벌을 견줬습니다. 늘린 롬은 `AB` 를 ホイミ 로 베끼고 이름 「ホイミミ」 를 덧붙인 롬입니다. 대조 롬은 목록에만 `AB` 를 넣은 롬입니다. 둘 다 주인공 습득 레벨을 2 로, 필드·전투 목록 첫 칸을 `AB` 로 썼습니다.

```text
레벨 2            비트 01 01 00, 메시지 19F, 옮긴 목록 MP 표의 AB 칸을 읽음
필드 늘린 롬      창에 ホイミミ·しょうひMP 3, 스텁 11:FFB0, HP 5→35, MP 100→97
필드 대조 롬      이름 칸 빈칸·MP 0, 골라도 멈춤(HP 5, MP 100)
전투 늘린 롬      스텁 20:FFE0 X=0156, 070 → 094, HP 5→44, MP 100→97
전투 대조 롬      049·04B 뒤 주문 메시지 없음
```

```sh
MESENCE=… uv run --locked python sfc/dq5/tools/dq5spellgrowcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/spellgrowcheck
```

## 틀렸던 것들

필드 처리기 표의 색인이 16비트로 계산된다고 보았습니다. 실제로는 8비트 `ASL` 이라 `A7` 이상의 주문은 bit8 을 잃었습니다.

## 남은 것

- 새 번호를 주문으로 다루게 하기(`25:8BF3`·`20:8460`·`21:F66C`·`21:F81B` 의 `66` 경계). 지금은 특기로 배우고, `20:A7B4` 검사(マホトーン 으로 보임)를 거치지 않습니다.
- 행동 AI 레코드(`21:BC86`, 뱅크 21 의 `abs` 읽기 50곳) 늘리기. 작전으로 움직이는 동료는 새 번호를 쓰면 다른 자료를 레코드로 읽습니다.
- `dq5learnwrite.py` 가 습득 목록에 `AB` 이상을 받게 하기. 이번에는 목록 두 칸을 직접 썼습니다.
- 원래 행동을 베끼지 않고 처리 루틴·실행 루틴을 따로 고르기, `26:8565` 의 뜻.
- 옮긴 연출 표(`26:8BE0`·`26:8C75`)는 이번 비교와 실측에서 읽히지 않아 게임에서 보지 않았습니다. 원래 게임이 `$10F7` 에 `AB` 이상을 넣는 일이 없는지도 확인하지 않았습니다.
- 처리 루틴 스텁 자리가 10개분이라 새 번호는 `AB`~`B4` 까지입니다. 게임에서 확인한 것은 `AB` 하나입니다.
