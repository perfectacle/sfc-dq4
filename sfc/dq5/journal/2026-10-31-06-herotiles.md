# 2026-10-31-06: 주인공 그림 타일 48개와 맵마다 인물 OBJ VRAM

dq4 트랙이 DQ6 풍 주인공 그림(타일 48개)을 넣으면서 `dq5spritewrite.py` 의 타일 수 검사를 꺼야 했습니다. 이 검사는 「그림 번호마다 원래 세트의 타일 수를 넘지 않기」였습니다. 주인공 자리와 인물 자리가 VRAM 을 어떻게 잡는지 재고, 검사를 「인물 목록마다 OBJ VRAM 이 512타일을 넘지 않기」로 바꿨습니다. 결과는 [그래픽 형식의 「그림 번호와 세트」](../docs/dq5-graphics-format.md#그림-번호와-세트)와 「[인물 OBJ VRAM 셈](../docs/dq5-graphics-format.md#인물-obj-vram-셈)」에 있습니다.

## 1. 주인공 입구와 인물 입구

형식 문서에는 주인공은 `1F:CF14`, 인물은 `1F:CF1E` 로 들어간다고 적혀 있었습니다. 두 입구는 `$A0` 만 다르게(`80`·`00`) 두고 같은 몸통으로 갑니다. 몸통을 읽어 보면 다른 점은 세 곳입니다.

```
1F:CF4F  LDA $A0 / BNE      ; 주인공이면 칸 목록 캐시 7E:AC00+세트*2 를 보지 않음
1F:CF91  LDA $A0 / BNE      ; 주인공이면 캐시에 적지도 않음
1F:D23A  LDA $A0 / BNE D24E ; 인물: $1995 += 세트 타일 수,  주인공: $1995 += 30(48)
```

맵에 들어갈 때 `00:E977` 이 `$1995` 와 캐시를 0 으로 둡니다. 그 뒤 주인공(`00:E232`), 일행 슬롯 1·2(`00:E3D4`, 모자라면 `00:E45E` 가 그림 `00` 으로) 순서로 48타일씩 잡아서 인물은 늘 타일 `090` 부터 놓입니다. 롬에서 `JSL $1FCF14` 는 이 네 곳뿐이고, `JSL $1FCF1E` 는 인물(`1E:DC8C`)·일행 슬롯 3 이상(`00:E3DA`·`E43B`)·`01:87BA`·`2B:83F5`·`2B:8402` 여섯 곳입니다. `02:C784` 가 carry 를 돌려주는 갈래(`00:E3F8`)에서는 슬롯 3·4 가 `CF14`, 슬롯 1·2 가 `CF1E` 로 바뀝니다. 이 갈래는 코드로만 읽었습니다.

## 2. 타일 48개 세트를 주인공과 인물에 이어 보기

타일 48개가 모두 다른 시험 무늬를 만들었습니다. 타일마다 왼쪽 열을 채워 좌우 반전도 다른 타일과 겹치지 않게 했습니다. 이 무늬를 새 세트 `70` 에 넣고, 선실 세이브스테이트에서 02/06 에 들어가 덤프했습니다(`dq5spritevramcheck.py`).

```
original-0206: 7E:1995 0CF(셈 0CF), 세트 70 0/0, 타일이 다른 세트 없음, OAM 묶음 2/2
hero-0206: 7E:1995 0CF(셈 0CF), 세트 70 48/48, 타일이 다른 세트 없음, OAM 묶음 2/2
npc-0206: 7E:1995 0DB(셈 0DB), 세트 70 48/48, 타일이 다른 세트 없음, OAM 묶음 2/2
both-0206: 7E:1995 0DB(셈 0DB), 세트 70 96/96, 타일이 다른 세트 없음, OAM 묶음 2/2
```

- hero: 어린 주인공 그림 `2E`(원래 세트 `82`, 34타일)를 `70` 으로 이었습니다. `$1995` 가 원본과 같고 타일 48개가 모두 VRAM 에 있습니다. 주인공 자리는 48타일을 이미 잡아 두고 있습니다.
- npc: 02/06 인물의 그림 `2B`(세트 `00`, 36타일)를 이었습니다. `0CF` = `090` + 세트 `00` 36 + 세트 `84` 27 이고, 세트 `00` 을 이 맵에서는 `2B` 만 쓰므로 `0DB` = `090` + 48 + 27 입니다.
- both: 둘 다 이으면 세트 `70` 이 VRAM 에 두 벌 올라옵니다. 주인공이 캐시를 적지 않으니 같은 그림 번호를 인물이 쓰면 따로 48타일을 씁니다.

그래서 주인공 그림은 48 까지 늘려도 됩니다. 다만 DQ5 에서 주인공 그림 번호도 인물 목록에 나옵니다(`2E` 10목록, `2D` 25목록, `3A` 2목록). dq4 트랙이 주인공에 쓰는 `2B` 도 DQ5 의 02/06·02/07 인물이 씁니다. 「주인공 그림이면 통과」 같은 규칙은 쓸 수 없고, 그 그림을 쓰는 인물 목록에서 VRAM 이 넘치는지를 따져야 합니다.

## 3. 맵마다 `$1995` 를 롬에서 세기

1 의 셈대로라면 맵을 다 놓은 뒤 `$1995` 는 `090` + 맵 OBJ 타일(`1F:D59A`) + 놓인 인물 세트의 타일 수 합(같은 세트는 한 번)입니다. 실내 346곳 훑기(`dq5objsweep.py`)를 다시 돌려 맵마다 잰 `$1995` 최대와, 그때 플래그로 고른 목록(`12:8009`)의 셈을 견줬습니다.

```
objsweep 맵 346곳 중 셈과 같은 곳 325, 다른 곳 21: 03/07 잼 199 셈 15C, 03/0E 잼 0BE 셈 0A7, 07/04 잼 11A 셈 108, 0A/00 잼 105 셈 0BC, …
```

다른 21곳은 모두 잰 값이 큽니다. 12곳은 잰 최대가 똑같이 `105` 이고, 슬롯을 가장 많이 센 프레임의 슬롯이 선실 세이브스테이트의 인물(`2E 2C 2E 2E 2C A6`)이었습니다. 맵 번호가 바뀐 뒤에도 앞 맵의 값을 센 것으로 보입니다. 나머지 9곳(03/07·03/0E·07/04·0B/02·1D/06·1E/00·1F/0A·21/04·31/10)은 목록에 없는 그림이 슬롯에 나와 장면이 인물을 더한 것으로 보입니다.

그림 `9A`(아내)는 `7E:21B3` bit3 에 따라 `97`·`2F` 의 세트를 씁니다. 도구는 플래그를 모르므로 둘 가운데 큰 쪽을 셉니다. 원본 롬의 기본·대체 목록 818줄(낮·밤)을 세면 가장 큰 것이 2B/02 의 `1FF`(ビアンカ 쪽, 잰 값은 フローラ 쪽 `1F6`)이고 512 를 넘는 줄은 없습니다. 19/00 이 `1FE`, 19/02 가 `1F7` 로 2타일·9타일밖에 남지 않습니다.

## 4. 넘치면

19/00 인물 그림 `08`(세트 `03`, 38타일)을 세트 `70` 으로 이으면 셈은 `208` 이고, 게임에서도 `208` 이었습니다. 그림 `01`(세트 `8C`, 35타일)이면 셈·잼 모두 `20B` 입니다.

```
original-1900: 7E:1995 1FE(셈 1FE), 세트 70 0/0, 타일이 다른 세트 없음, OAM 묶음 1/1
over-1900: 7E:1995 208(셈 208), 세트 70 48/48, 타일이 다른 세트 없음, OAM 묶음 1/1
over-1900 에서 칸 목록·VRAM 이 맞지 않게 된 세트: 8B
```

마지막에 놓이는 세트 `8B`(그림 `0E`, 44타일)가 `1DC` 부터 놓여 앞 36개만 OBJ 영역에 들어가고, 뒤 8개는 VRAM 덤프 어디에도 없었습니다. 원본 덤프와 다른 곳은 세트들이 놓인 워드 `6900`~`7FFF` 뿐이었습니다. 칸 목록은 `세트 안 타일 + $1995 | 팔레트` 를 OR 로 씁니다. 그래서 9비트를 넘은 타일 번호의 윗비트가 팔레트 비트(이 세트는 팔레트 1)에 묻혀 `0201`~`0207` 이 되고, 그 칸들은 타일 `001`~`007`, 곧 주인공 타일을 가리킵니다. 400프레임 동안 멈추지는 않았습니다. 이 칸들은 그 인물의 왼쪽 몸(칸 40~47)과 아래 몸 프레임 1 의 칸 하나라, 인물을 주인공 옆으로 옮기고(`dq5npcrecord.py`) 엔트리의 방향을 왼쪽으로 바꿨지만 덤프에서는 아래를 보고 있어 화면에서는 보지 못했습니다.

## 5. 도구

`dq5spritewrite.py` 는 이제 그림 번호마다의 타일 수 한도를 보지 않습니다. 대신 문서대로 바꾼 뒤 인물 목록마다 3 의 셈을 하고, 512 를 넘으면서 원래보다 커진 줄이 있으면 거부합니다(`vram_check`). 원래부터 512 를 넘는 줄은 그 문서 탓이 아니므로 두지만, 원본 롬에는 그런 줄이 없습니다. 같은 셈을 `vram` 명령으로 찍습니다.

```
$ uv run --locked python sfc/dq5/tools/dq5spritewrite.py rom/dq5.sfc patch over08.json -o /dev/null --at 3A:8000
오류: 인물 OBJ VRAM 이 200타일을 넘는 목록 3개: 19/00 목록 05:AB26 낮 208(원래 1FE), 2B/02 목록 05:CD73 낮 209(원래 1FF), 19/00 목록 10:B394 낮 208(원래 1FE). 그 맵에서 그 그림을 빼거나 타일을 줄여야 함
$ uv run --locked python sfc/dq5/tools/dq5spritewrite.py rom/dq5.sfc vram npc2b.json --top 900 | grep →
02/07 목록 05:8D3C 낮: 10E → 11A, 남는 타일 230(맵 OBJ 42, 그림 04 2A 2B)
02/06 목록 05:8CD4 낮: 0CF → 0DB, 남는 타일 293(맵 OBJ 0, 그림 29 2B)
```

dq4 트랙의 DQ6 풍 주인공 시험 문서(그림 `2B` → 세트 `70`, 타일 48개)는 원본 롬에서 거부되지 않습니다. 그 문서로 만든 1장 롬에서 `vram` 을 돌리면 목록 909줄 가운데 512 를 넘는 줄은 없고, DQ4 맵(그룹 `36` 이상) 109줄 가운데 가장 큰 것이 3D/04 의 `1D1`(47타일 남음), 그다음이 3D/03 `1C5`·3C/00 `1B7`·36/01 `1B3` 입니다. DQ4 목록에는 그림 `2B` 를 쓰는 인물이 없습니다. 1장 롬은 게임에서 재지 않았습니다.

## 틀렸던 것들

- 원래 검사(「그림 번호마다 원래 세트의 타일 수까지」)는 너무 좁았습니다. 주인공 자리는 처음부터 48타일을 잡고, 인물 자리도 맵에 여유가 있으면 더 받습니다. 거꾸로 이 검사는 다른 그림 번호를 큰 세트로 옮길 때 맵마다 늘어나는 양을 보지 않았습니다.
- 처음 셈을 견줄 때 훑기의 `v1997`(훑기가 끝날 때 읽은 값)도 함께 맞추려다 147곳이 어긋났습니다. 이 값은 다음 맵으로 가는 중에 읽혀 그 맵의 값이 아닙니다. `$1995` 최대만 견주자 325곳이 맞았습니다.
- 그림 `9A` 의 두 세트를 함께 세자 2B/02 가 `219`, 02/06 이 `201` 로 원본에서도 512 를 넘었습니다. 게임은 둘 중 하나만 올리므로 큰 쪽 하나만 세도록 고쳤습니다.

## 남은 것
