# 2026-10-30-33: 세계마다 니블이 다른 타일 늘리기 롬의 필드 불러오기 4프레임 없애기

[타일 늘리기 일지](2026-10-30-28-tilefast.md)가 남긴 것 가운데 첫째를 했습니다. 타일을 512개 넘게 늘리고 `worlds` 로 세계 1·2 의 니블을 따로 준 롬은 니블 훅을 그대로 써서 필드를 원본보다 4프레임 늦게 불러왔습니다. 팔레트 비트를 붙이는 `00:BBAC` 를 `$1949` 로 세계를 고르는 짧은 코드로 제자리에서 바꿨습니다. 이제 이 롬도 세 세계에서 원본과 같은 프레임에 필드를 불러옵니다. 형식은 [쓰기 형식의 「필드 그림」](../docs/dq5-build-format.md#필드-그림-dq5fieldgfx1)과 [블록 훅 속도·빛 칸·세계 지도 실측](../docs/dq5-build-format.md#블록-훅-속도빛-칸세계-지도-실측)에 있습니다.

## 1. 얼마나 덜어야 하나

앞 일지에서 세 세계의 니블이 같은 롬은 `00:BBAC` 한 번이 원본 717 에서 500마스터 클록이 되어 프레임이 원본과 같아졌습니다. 같은 셈으로 `00:BBAC` 를 원래와 같은 사이클로만 맞춘 롬은 한 프레임 늦었습니다. 불러오기 안에서 `01:B4D5` 의 다시 그리기 훅이 늘린 타일 16KB 를 DMA 로 더 보내기 때문입니다. 그러니 세계를 고르는 판도 500 언저리여야 안전합니다.

같은 니블 판은 1바이트 표(`니블 × 4 + 8`)를 층마다 읽어 `$97`·`$95` 에 `ORA` 하고, 위층에는 `$C6` 을 더 `ORA` 합니다. 여기에 세계 색인을 그대로 더하면(층마다 `$1949` 를 읽거나, 위층 색인에서 세계 비트를 다시 꺼내거나) 손으로 센 사이클이 같은 니블 판보다 20 남짓 깁니다. 그래서 표를 타일맵 워드 그대로(`타일 | (니블 × 4 + 8) << 8`, 2바이트)로 바꿨습니다. 이러면 `SEP`·`REP` 와 `$97` 에 `ORA` 하는 걸음이 빠져, 세계 고르기를 넣고도 같은 니블 판과 사이클이 거의 같습니다.

```
00:BBAC  LDA $7E1949 / AND #$0003 / XBA / ASL / ASL / ORA $96 / ASL / TAX / LDA 위층표,X / ORA $C6 / STA $96
00:BBC2  TXA / AND #$F800 / LSR / ORA $94 / ASL / TAX / LDA 아래층표,X / STA $94 / RTS
```

- 색인은 `($1949 & 3) << 11 | 타일 << 1` 입니다. 타일 번호(`$96`·`$94`)는 칸 비트 표나 옮긴 블록 표에서 온 1,023 이하라(앞 일지 3절) 세계 비트와 겹치지 않습니다.
- 아래층은 위층 색인에서 `AND #$F800` 으로 세계 비트만 남기고 타일을 바꿔 끼웁니다. `$1949` 는 한 번만 읽습니다.
- `$1949` 는 DB 를 따지지 않게 긴 주소로 읽습니다. 16비트로 읽으므로 `AND #$0003` 이 윗바이트(`$194A`)를 지웁니다.
- 나갈 때 A 는 원래처럼 `$94`(고친 워드)입니다. `00:B769`·`B7B5` 가 돌아오자마자 A 를 타일맵에 씁니다. X 는 아래층 색인인데, 부른 곳은 모두 X 를 다시 둔 뒤 씁니다(같은 니블 판과 같은 코드 읽기).
- 38바이트라 원래 자리(75바이트)에 들어가고 `00:BBD1` 에서 `RTS` 합니다.

표는 위층·아래층마다 세계 넷 × 2KB 로 16KB 입니다(넷째는 세계 0 의 것, 다른 세계 고르기 훅들과 같음). `--worlds-at` 뱅크에는 세계 1·2 의 RLE 가 함께 있어 16KB 를 더 넣을 자리가 모자랄 수 있으므로, 늘린 타일과 같은 규칙으로 `--extra-at` 의 늘린 타일 뒤에 둡니다(한 뱅크 안, 넘으면 다음 뱅크 `8000`). `LDA long,X` 는 뱅크 경계를 넘지 않아야 하는데 이 규칙이 그것을 지킵니다. 니블 훅은 `--worlds-at` 자리 배치(`rom_layout`)가 바뀌지 않게 그대로 남지만 부르는 곳은 없습니다. 세 세계의 니블이 같으면 예전처럼 1바이트 표 판을 써서 롬이 한 바이트도 바뀌지 않습니다.

디코더(`dq5field.tile_word`)는 `00:BBAC` 가 `LDA long`(`AF`)이면 `00:BBBA`·`BBCB` 의 `LDA long,X` 가 가리키는 두 표에서 그 세계의 워드를 읽습니다.

## 2. 다시 재기

앞 일지와 같이 `dq5warp.lua` 로 배 선실 세이브스테이트에서 필드에 내리며 `lua/dq5framelog.lua` 로 프레임마다 `$7F`·`$BE` 를 적고, 둘 다 그대로인 프레임을 멈춘 구간으로 셌습니다. 세계 1·2 는 (50,28) 에 `$1949` 를 고정해 서고, 세계 2 첫걸음은 바다 (62,64) 에서 왼쪽으로 밉니다. 같은 실행에서 `00:BBF7`·`00:BBAC` 에 들어가 나올 때까지(`00:BC46`, 각 판의 `RTS`) 마스터 클록을 600프레임까지 더했습니다. 롬은 모두 `--worlds-at 34:8000 --extra-at 60:8000` 이고, 타일은 `dq5gfxlimitcheck.py` 의 tiles 롬처럼 늘린 타일 512개를 원래 타일 XOR FF·니블 bit0 반전으로 두었습니다. 블록 표는 그대로라 화면은 원본과 같아야 합니다.

- 타일: 세 세계 니블이 같음.
- 세계 1 니블: 세계 1 의 늘린 타일 니블만 bit1 을 더 뒤집음.
- 세계 1·2 니블: 거기에 세계 2 의 늘린 타일 니블만 bit2 를 더 뒤집음.

고치기 전 도구(`origin/main`)와 지금 도구로 같은 입력에서 만들었습니다.

```
                          00:BBF7   00:BBAC   세계 0     세계 1     세계 2     세계 2 첫걸음
원본                      1,901.0   717.1     462~492   453~483   451~481   822
타일(고치기 전·지금)       1,851.8   500.1     462~492   453~483   451~481   822
세계 1 니블(고치기 전)     1,853.1   1,788.8   462~496   453~487   451~485   826
세계 1 니블(지금)          1,851.8   500.1     462~492   453~483   451~481   822
세계 1·2 니블(고치기 전)   1,853.1   1,788.8   462~496   453~487   451~485   826
세계 1·2 니블(지금)        1,851.8   500.1     462~492   453~483   451~481   822
```

고치기 전 숫자는 앞 일지의 세계 1 니블 롬(462~496·453~487·451~485, 첫걸음 826)과 같습니다. 두 루틴은 세계 0 에서 1,090·1,088번 불립니다. `00:BBAC` 는 세 세계의 니블이 같은 판과 같은 500마스터 클록이었습니다. 세계 0 에서 `01:B4D5` 에 두 번 들어가 돌아오기까지 합은 원본 7,051,252, 고치기 전 8,301,872, 지금 6,898,168 로 같은 니블 판과 같습니다.

타일 롬은 고치기 전 도구와 지금 도구로 만든 것이 바이트마다 같았습니다. 세계 1 니블·세계 1·2 니블 롬은 둘 다 16,402바이트가 다릅니다. `00:BBAC`~`BBD1` 의 새 코드 38바이트(옛 `JSL` 둘이 있던 `00:BBB4`·`BBBE` 포함), 옛 `JSL` 이 원래 `LDA $2AD712,X` 로 되돌아간 `00:BBDA`·`BBE4` 8바이트, 체크섬 `00:FFDC`~`FFDF` 4바이트, `60:C000` 의 표 16,384바이트 가운데 그 자리 원래 바이트와 다른 16,352바이트입니다. `00:BBD2`~`BBF6` 은 원본 그대로입니다.

## 3. 화면

원본과 지금 도구로 만든 세 롬을 같은 장면에서 덤프해 VRAM `0000`~`7FFF`(타일맵과 원래 타일 512개)·CGRAM 을 바이트마다 견주었습니다. 세계 0 (341,56)·세계 1·2 (50,28) 에 서서 700·900프레임, 세계 0 에서 네 방향으로 32프레임씩 걸으며 700~960프레임 여섯 번, 세계 2 바다 (62,64) 에서 왼쪽으로 밀며 700·800·900프레임, 롬마다 30쌍이 모두 같았습니다. 마지막 덤프의 좌표 `$B6`·`$B8` 와 지형 `$1AA0`, `$1949` 도 같았습니다.

이 롬들은 늘린 타일을 블록이 쓰지 않아 세계를 고르는 것이 화면에 드러나지 않습니다. 그래서 `dq5gfxlimitcheck.py` 에 nibs 롬을 더했습니다. 세계 1·2 니블 롬에 tiles 롬과 같은 블록 패치(블록 511개 두 층의 칸 타일에 512 를 더함)를 넣은 롬입니다. 세계 0 (341,56)·세계 1·2 (50,28) 에 서서 900프레임에 타일맵을 보았습니다.

```
세계   늘린 타일로 그린 칸   디코더 워드와 같음   팔레트 비트가 그 세계 입력 니블과 같음
0      1,394                1,394               1,394
1      1,288                1,288               1,288
2      1,352                1,352               1,352
```

팔레트 비트는 디코더를 거치지 않고 입력 니블로 바로 셈했습니다(위층 4비트·아래층 3비트, `((니블 & 마스크) + 2) & 7` 이 워드 bit10~12). 대조로 세계 1·2 덤프를 세계 0 니블과 견주자 1,288·1,352칸 모두 달랐습니다. 세계마다 다른 표를 읽는다는 뜻입니다.

## 남은 것

- 세계마다 타일맵 워드 표가 `--extra-at` 에서 16KB 를 더 씁니다. 넷째 세계 표(`$1949 & 3` = 3)는 세계 0 의 사본이라 줄일 수 있지만, `$1949` 가 3 이 되는 장면이 없는지 확인하지 않아 두었습니다.
- 같은 니블 판과 마찬가지로, 세계를 오가는 이벤트·ルーラ 로 다른 세계에 내릴 때의 화면은 재지 않았습니다. `00:BBAC` 는 부를 때마다 `$1949` 를 읽으므로 코드 읽기로는 그 세계의 표를 씁니다.
