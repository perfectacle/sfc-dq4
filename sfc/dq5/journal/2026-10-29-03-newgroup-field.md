# 2026-10-29-03: 새 그룹을 필드와 잇기

[지난 일지](2026-10-27-55-newgroup.md)에서 새 그룹 번호 `36` 을 만들었지만, 그 그룹은 필드와 오갈 수 없었고 팔레트도 정해지지 않았습니다. 이번에는 새 그룹의 필드 출구·도착·팔레트 세트를 쓰는 길을 만들고, 인물 도구가 새 그룹을 읽게 했습니다. 결과는 [쓰기 형식의 「새 그룹을 필드와 잇기」](../docs/dq5-build-format.md#새-그룹을-필드와-잇기)와 [팔레트 세트 표](../docs/dq5-build-format.md#팔레트-세트-표-dq5palset1)에 있습니다.

## 1. 도구를 어디에 붙일지

필드 출구는 입구 표 둘(`04:FD97`·`04:FE83`)입니다. 실내에서 필드로 나가면 `2A:F425` 가 일반 표에서 `$BC` 를 찾고, 없으면 보조 표에서 찾습니다. 이 두 표는 이미 `dq5fieldtables.py --entrances-at` 이 옮기고 늘립니다. 막고 있던 것은 입구 그룹 번호 검사 하나였습니다. `36`~`4F` 를 늘 거부했습니다. 그래서 그룹 수를 롬의 맵 포인터 그룹 표에서 세게 바꿨습니다. 원본 롬에서 패치를 만들 때는 다른 도구처럼 `--new-map 36/00` 으로 새 그룹을 알립니다.

도착 표 `0F:EA97` 은 `dq5newmap.py` 가 「들어가는 곳 표」라고 부르며 이미 옮기고 늘리는 바로 그 표였습니다. 두 도구가 같은 자리를 쓰면 빌드에서 겹칩니다. [지난번](2026-10-27-55-newgroup.md#3-그룹-50-이상) 고층 속성 목록에서 겪은 일입니다. 그래서 도착은 `dq5newmap.py` 의 `groups[].entrance` 에 맡겼습니다. `dq5fieldtables.py` 는 옮긴 자리를 읽기만 하고, 값을 바꾸려 하면 거부합니다.

팔레트 세트 표(`10:DEBC`)는 맡은 도구가 없어 `dq5palsetwrite.py` 를 새로 만들었습니다. 표 바로 뒤가 목록 표(`10:DFE4`)이고 뱅크 10 의 빈 자리는 32바이트뿐입니다. 표를 읽는 코드는 `10:DE0B` 하나이고, 그 안의 `LDA $DEBC,X`·`$DEBD,X` 다섯 곳이 DB = 10 으로 읽습니다(`10:DDDD` 의 `PHK`·`PLB`). DB 를 바꾸면 이어지는 `$DFE4,X`·`$E5C8,Y` 읽기가 깨집니다. 그래서 찾기를 통째로 다른 뱅크의 루틴으로 보냈습니다. `10:DE0B` 를 `JSL 루틴 / BCS +1 / RTS / JMP $DE43` 10바이트로 바꾸고, 루틴은 원래와 같은 차례로 표를 긴 주소로 읽습니다.

```
3C:9007  bf 41 90 3c  LDA $3C9041,X
3C:900B  c9 ff        CMP #$FF
3C:900D  f0 30        BEQ $3C903F     ; 없음: CLC / RTL
3C:900F  c5 bc        CMP $BC
…
3C:9037  bf 42 90 3c  LDA $3C9042,X   ; 맞는 맵의 세트
3C:903B  85 00        STA $00
3C:903D  38           SEC
3C:903E  6b           RTL
```

원본 표에는 롬에 없는 맵을 가리키는 항목도 있었습니다(52/00, 00/00). 처음에는 롬에 없는 맵을 모두 거부해서, 원본을 내보낸 그대로 다시 넣는 것도 실패했습니다. 원래 표에 있던 맵 번호는 그대로 받게 했습니다.

## 2. 인물 도구의 그룹 수

`dq5npc.all_lists` 는 그룹 포인터 표 `05:D4B2` 에서 54그룹만 읽었습니다. `dq5npcrelocate.py` 가 옮긴 롬은 `12:8020`(`LDA #$05`)·`12:8050`(`LDA $D4B2,Y`) 두 피연산자가 새 자리를 가리키고, 표 바로 뒤에서 첫 목록이 시작합니다. 그래서 두 피연산자로 자리를 읽고, 가장 앞 목록 앞까지를 그룹 수로 셌습니다. 옮긴 표의 맨 뒤 그룹은 끝을 알 수 없어서, 맵 포인터 그룹의 맵 수만큼 셉니다. 원본 롬에서는 목록 639개(기본 346, 대체 293)가 전과 같았습니다.

## 3. 01/00 을 복사한 맵이 가장자리에서 멈춤

시험 롬은 처음에 36/00 을 01/00(아래 가장자리로 필드에 나감)의 복사로 만들었습니다. 필드에서 걸어 들어가기와 팔레트는 맞았는데, 36/00 (32,92) 에서 아래로 걸으면 한 칸도 움직이지 않았습니다. 01/00 은 같은 걸음으로 필드 (331,67) 에 나갔습니다.

먼저 `2A:F234`·`2A:F425` 를 지나는지 보았습니다. 01/00 은 555프레임에 셋 다 지났고, 36/00 은 하나도 지나지 않았습니다. 필드로 나가기 전에 맵 안에서 막힌 것입니다. 걸음 판정 코드를 프레임마다 추적해 두 롬을 견주자, `00:A97D` 의 맵 밖 칸 검사에서 갈렸습니다.

```
00:A9F7  LDA $96 / CMP $C0 / BCC …   ; 다음 칸이 맵 안이면 보통 판정
00:A9FD  LDA $C3 / CMP $182F         ; 맵 밖: 주인공 층과 $182F 를 견줌
00:AA02  BEQ $AA07                   ; 같으면 CLC(나갈 수 있음), 다르면 SEC(막힘)
```

두 롬에서 `$182F` 가 36/00 은 1, 01/00 은 2 였습니다. `$182F` 를 쓰는 곳은 셋입니다. `01:97D3` 은 맵을 불러올 때마다 1 로 둡니다. `02:B1E5`·`02:B1EB` 는 2 로 둡니다. 둘은 [맵별 루틴](../docs/dq5-map-format.md#맵별-루틴-15f907) 162개 가운데 01/00·07/00 의 루틴입니다. 맵별 루틴은 `[BC][BD]` 로 고르므로 36/00 에는 걸리지 않습니다. 01/00 은 층 2 에서 걷는 맵이라 이 루틴이 있어야 가장자리로 나갈 수 있었습니다.

추적 중에 그룹마다 걸음마다 부르는 루틴 표(`00:C689`, `[BC][루틴 16비트]`, 15그룹)도 보았습니다. 36 은 없어서 기본 `00:C687`(CLC)이 걸리고, 01 은 `00:C385` 가 걸립니다. 01/00 에서는 두 루틴 모두 CLC 로 돌아와 이번 차이와는 상관이 없었습니다.

그래서 시험 맵을 층 1 의 03/00(성 앞뜰)의 복사로 바꿨습니다. 03/00 은 맵별 루틴 없이 아래 가장자리로 나가는 맵입니다.

## 4. 밟아서 확인

`dq5newgroupcheck.py` 가 원본에서 도구 다섯의 패치를 만들어 롬 두 벌을 빌드합니다. `g` 는 다섯을 모두 넣고, `p` 는 팔레트 세트만 뺍니다.

| 도구 | 넣은 것 |
| --- | --- |
| `dq5newmap.py` | 36/00(03/00 복사), 그룹 36 도착 `20 26 44 01 00`(36/00 (38,68) 층 1). 들어가는 곳 표 `3E:C000`, 문 표 `--door-bank 3D` |
| `dq5npcrelocate.py --new-map 36/00` | 그룹 36 의 인물 그룹 포인터와 빈 목록 |
| `dq5exitreloc.py --new-map 36/00` | 36/00 의 출구(기본값) |
| `dq5fieldtables.py --entrances-at 3C:8000 --new-map 36/00` | 보조 입구 표 끝에 (345,56) → 그룹 36 |
| `dq5palsetwrite.py --table-at 3C:9000 --new-map 36/00` | 그룹 36 기본 세트 `06`, 36/00 은 세트 `13` |

```
exit: {'map': '36/00', 'BE': 0, 'field': [345, 57]}
exit-03: {'map': '03/00', 'BE': 0, 'field': [251, 216]}
enter: {'map': '36/00', 'BE': 128, 'cell': [38, 68]}
enter-original: {'BE': 0, 'field': [346, 56]}
palette: {'map': '36/00', 'BE': 128, '1983': 8, 'cell': [38, 60]}
palette-03: {'map': '03/00', 'BE': 128, '1983': 12, 'cell': [38, 60]}
nopal: {'map': '36/00', 'BE': 128, '1983': 8, 'cell': [38, 60]}
인물 36/00 목록 비었음=True, 1983=08; 도착 36 20 26 44 01 00; 팔레트 없는 36/00 = ['17/00']
7회 실행, 새 그룹 검사 7개 통과
```

- 36/00 (38,70) 에서 아래로 걸어 나가자 필드 (345,57) 에 섰습니다. 일반 표에 36 이 없어 보조 표 항목 (345,56) 의 Y+1 입니다. 같은 롬에서 03/00 은 원본과 같은 (251,216) 에 섰습니다.
- 필드 341,56 에서 오른쪽으로 걷자 (345,56) 에서 36/00 (38,68) 에 들어섰습니다. 옮긴 도착 표의 그룹 36 항목 그대로입니다. 원본 롬은 같은 걸음으로 필드에 남았습니다.
- 36/00 에 서 있을 때 CGRAM 1~7번 줄 224바이트가 만든 롬에서 `dq5map.map_cgram` 으로 계산한 세트 `13` 과 같았습니다. 세트 `13` 은 옮긴 표에만 있는 값이라, 게임이 옮긴 표를 읽은 것입니다. 대조로 원본 03/00 도 같은 비교가 맞았습니다(세트 `15`). 두 맵의 CGRAM 은 99바이트가 달랐습니다.
- 팔레트 세트 표에 36 이 없는 `p` 롬에서는 36/00 의 CGRAM 1~7번 줄이 출발한 배 선실 17/00 의 팔레트와 같았습니다. 표에 그룹이 없으면 `10:DE0B` 가 CLC 로 돌아와 앞 맵의 팔레트가 남는 것입니다. 지난 일지에서 확인하지 못한 부분입니다.
- 같은 롬에서 `dq5npc.all_lists` 는 36/00 의 목록을 옮긴 표 `32:CECF` 에서 찾았고 목록은 비어 있었습니다. 게임에서도 36/00 의 인물 뒤 슬롯 `7E:1983` 은 `08` 이었습니다.

장면 이동 도구(`dq5warp.lua`)와 표 검사 프로브(`dq5tablecheck.lua`)는 끝에 WRAM·CGRAM 을 `final.wram`·`final.cgram` 으로 남기게 했습니다. 두 프로브를 쓰는 `dq5entrancecheck.py`(4회)와 `dq5newmapcheck.py`(46장면)도 다시 돌려 모두 통과했습니다.

## 5. 블록 표의 번호 범위

블록 표 증설은 하지 않았습니다. 번호를 읽는 `00:BC4E` 앞의 `00:BBF7` 은 칸 하나의 번호를 `7F:0000` 의 바이트(하위 8비트)와 `7E:E000` 의 비트 하나(9번째 비트)로 모읍니다. 그래서 번호는 0~511 이 한도입니다(코드 읽기). `00:BC4E` 는 그 값×5 로 두 표를 긴 주소로 읽고, 표를 읽는 명령은 `00:BC72`·`BC78`·`BC80`·`BC8D` 넷뿐입니다(24비트 정적 검색). 두 표를 떼어 옮기면 지금 위층 표와 겹치는 번호 511 하나를 더 쓸 수 있을 뿐이고, 그 이상은 필드 지도 꼴을 바꿔야 합니다.

## 틀렸던 것들

- 01/00 을 복사하면 아래 가장자리로 필드에 나갈 것이라 여겼습니다. 가장자리 판정이 주인공 층과 `$182F` 를 견주고, 01/00 은 맵별 루틴이 `$182F` 를 2 로 둬서 나갈 수 있던 것이었습니다.
- `dq5palsetwrite.py` 는 처음에 롬에 없는 맵을 모두 거부해, 원본 표를 그대로 다시 넣는 것도 실패했습니다(52/00).

## 남은 것

- 층 2 맵을 복사한 새 그룹 맵의 가장자리 출구. `$182F` 를 2 로 두는 맵별 루틴 항목을 `dq5maphook.py` 로 더해 실측해야 합니다.
- 걸음마다 부르는 루틴 표 `00:C689`(15그룹) 늘리기. 뱅크 00 에 빈 자리가 없어 찾기를 옮겨야 합니다.
- 필드 블록 표 옮기기(번호 511 을 쓰려면).
- 맵 번호 조사를 상점·여관·교회·이벤트 장면으로 넓히기.
