# 2026-10-27-09: 마스터 클록 단위로 돌린 전투 연출과 DDDC 를 부르는 장면

전투 연출 `0C`·`6F` 는 롬 코드로 돌린 해석기(`dq5fxvm.py --clock`)에서 처리 도중 NMI 가 끼는 명령이 게임과 달라 갈렸습니다. 주기 모형을 MesenCE 와 같은 차례로 마스터 클록 단위로 세는 해석기(`sfc/dq5/tools/dq5clock.py`)로 바꿔, 두 연출을 포함한 139벌이 모두 게임과 같아졌습니다. 그리고 `3E` 루틴 `DDDC` 를 부르는 장면을 찾았습니다. 결과는 [dq5-graphics-format.md 「롬 코드로 돌리기」](../docs/dq5-graphics-format.md#롬-코드로-돌리기-dq5fxvmpy)와 그 앞 「불리지 않았던 21곳을 억지로 부르기」 에 있습니다.

## 1. 명령마다 주기를 견주는 추적

앞의 모형(`dq5titlevm.Cpu`)은 NMI 를 받을 때 셈을 0 으로 되돌리고, 리프레시를 한 프레임 길이에서 한꺼번에 빼고, HDMA 를 줄마다 어림했습니다. 어디가 틀렸는지 보려고 게임 쪽에서 명령마다 마스터 클록을 남겼습니다. 연출 입구 `22:D73C` 뒤로 모든 주소에 실행 콜백을 걸고 `emu.getMasterClock()` 을 적은 것입니다. 해석기도 명령마다 시각을 적고, 두 줄을 한 명령씩 견줬습니다.

```
seg 0: same 205 instr ... diverge g 0088BE m 0088C4
8D p20 {0: 89, 4352: 6, -40: 1}     ← 일반 DMA
60 p20 {0: 29, -4500: 3, -40: 1}    ← DMA 다음 명령
```

차이는 셋이었습니다. 줄마다 40 씩 멈추는 리프레시, DMA 앞뒤의 맞춤, 그리고 NMI 처리기가 갈리는 자리입니다. 처리기는 스택의 돌아갈 주소를 보고 「소리 대기열 고리(`2B:BECE`~`C422`) 안에서 NMI 를 받았는가」 로 갈립니다. 해석기는 프레임 기다림 `00:969A` 를 건너뛰고 거기서 NMI 를 넣었으므로 늘 다른 갈래로 갔습니다.

## 2. 절대 시각으로 다시 세기

MesenCE 의 SNES 코어 소스(`SnesCpu.Instructions.h`, `SnesMemoryManager.cpp`, `SnesDmaController.cpp`, `InternalRegisters.h`)를 읽고, 그 차례대로 세는 해석기를 새로 썼습니다.

- 명령마다 메모리 접근과 내부 주기의 차례(예: `STA abs,X` 는 코드 셋·내부 하나·쓰기). 받기로 정해진 NMI 가 있으면 내부 주기 하나짜리 명령이 그 주기를 코드 읽기로 하는 것까지.
- 주기 시작에 걸린 DMA·HDMA 를 먼저 하고 접근 시간을 민다. DMA 는 8 단위 맞춤 + 덧 8 + 채널 8 + 바이트 8 + 끝 맞춤.
- 입구의 MesenCE 상태(`masterClock`·`memoryManager.hClock`·`ppu.scanline`, DMA 채널 내부 상태)를 `dq5fx3e.lua` 가 `v<연출>.clock0` 으로 남기게 했습니다.

첫 실행에서 리프레시는 맞았지만 HDMA 가 한 명령 일찍 붙었습니다. HDMA 를 시작할 때도 일반 DMA 처럼 한 주기를 쉬는 것(`BeginHdmaTransfer` 가 `_dmaStartDelay` 를 켬)을 넣자 줄마다 HDMA 값이 40·42·48 로 게임과 같아졌습니다. 다음은 리프레시가 몇 줄에서만 한 명령 어긋났습니다. 줄 첫머리마다 리프레시 자리를 538 - (클록 & 7) 로 다시 정하는 것(줄 길이 1364 가 8 의 배수가 아니라 534·538 을 오감)을 넣자 첫 NMI 까지 명령 10,935개가 주기 0 차이였습니다.

## 3. 기다림 고리와 입력

NMI 를 받는 순간 CPU 는 소리 대기열 고리를 돌고 있습니다. 고리 한 바퀴는 402 마스터 주기이고, 어느 명령에서 받느냐에 따라 처리기 시작이 수십 주기 흔들립니다. 그래서 기다림을 건너뛰지 않고 롬 코드 그대로 돌게 했습니다. 처리기가 고리 안의 자리를 `08DE`~ 에 저장하고 다음 기다림의 `2B:C473` 이 그 자리에서 이어 도는데, 입구 WRAM 에 게임이 저장한 자리가 이미 있어 그대로 이어집니다.

그 뒤로 갈린 곳은 셋이었습니다.

- 짧은 줄: 겹쳐 보기 모드에서 홀수 프레임의 240줄은 1360 입니다. 프레임 수(`ppu.frameCount`)는 240줄에서 늘고 MesenCE 의 `_oddFrame` 은 0줄로 넘어갈 때 바뀌므로, 입구가 240줄 뒤면 하나 어긋나게 정했습니다. `6F`(입구 247줄)는 이것으로 맞았습니다.
- 조이패드: `6F` 실행은 A 를 3프레임씩 누르는데, 처리기가 `00:8BEB` 에서 읽은 값으로 갈래가 바뀝니다. NMI 마다 읽은 값을 `v<연출>.pad` 로 남겨 입력으로 넣었습니다.
- 소리 칩: 효과음을 보낼 때 `2B:C373` 등이 `$2140` bit7 이 바뀔 때까지 기다립니다. 소리 칩(SPC700)은 흉내 내지 않고, CPU 가 `$2140`~`$2143` 에서 읽은 값과 그 마스터 클록을 `v<연출>.apu` 로 남겨 같은 시각의 값을 돌려주게 했습니다. 해석기의 읽기 시각이 게임과 같으므로 시각이 어긋난 읽기는 0번이었습니다.

`$4212` 의 자동 읽기 비트는 처음에 접근 끝 시각으로 셌다가, 값이 접근 끝 4 주기 앞에서 정해지는 것(`SnesMemoryManager::Read`)으로 고치자 맞았습니다.

```
0C frames vm 114 game 114 same 114   same instr 2268227 of 2268227   nbad 0
6F frames vm 148 game 148 same 148   same instr 1768864 of 1768864   nbad 0
```

## 4. HDMA 를 실제로 쓰기

139벌을 다시 떠서 견주자 BG3 사본은 139벌, 연출 층 그림은 137벌이 같았습니다. `06`·`0F` 는 HDMA 가 줄마다 바꾸는 BG3 스크롤, `1F`·`20` 은 CGRAM `1E2`(OBJ 팔레트 7 색 1)가 달랐습니다. 둘 다 HDMA 가 PPU 레지스터에 쓰는 값이라, HDMA 를 시간만 세지 않고 실제로 PPU 에 쓰게 하자 139벌 모두 BG3 사본·연출 층 그림·프레임마다 VRAM·CGRAM·OAM 이 같아졌습니다(4,453프레임). 앞의 모형은 같은 139벌에서 BG3 사본 137벌, 그림 135벌이었습니다.

## 5. DDDC 를 부르는 장면

`3E DC DD` 는 롬에 `24:DC18` 한 곳뿐입니다. 연출 포인터 표(`00`~`A9`)의 스크립트를 갈래(`2B`·`2C`·`2D`·`2E`·`3D`)까지 따라가자 이곳에 닿는 연출은 `36`(トラマナ)·`9E`·`A4`·`A6` 넷이었습니다. 모두 `24:DBBF`~ 꼬리를 함께 쓰고, `3E D3 DD`(변수 1 = `$0DA8`) 뒤 `2D 01 00 18 DC`(변수 1 ≠ 0)를 지나야 닿습니다.

- トラマナ 는 그 앞 `DBBA` 의 `2C 05 00 E2 DB`(변수 5 = `$9E78` 이 0 이면 건너뜀)에서 늘 건너뜁니다. 입구에 `$9E78` = `08` 을 써 넣은 실행을 해석기로 돌리며 쓰기를 보자 연출 입구 `22:D774` 가 0 으로 지웠고, `DBBA` 에서 0 이었습니다.
- `9E`·`A4`·`A6` 은 몬스터 행동 ぶきみなひかり·まぶしいひかり·いてつくはどう 입니다. `26:8D3A` 가 `26:8DB3` 의 행동 목록에 있는 행동을 그 번호 그대로 연출 번호로 넘깁니다. 실행 루틴(`20:D226`·`D4CE`·`D5B7`)은 대상이 몬스터 쪽(`$10F6` bit7)일 때 `DEC $0DA8` 로 `FF` 를 만듭니다(코드 읽기).

슬라임에게 이 행동을 시키면(행동 여섯 칸, 대기 시간을 바꾼 실행 18번, 192번 사용) `$0DA8` 이 늘 0 이라 `DDDC` 가 한 번도 불리지 않았습니다. 주인공 주문 칸을 그 행동으로 바꾸자(`ROMPATCH="11BE31=9E"`·`A4`·`A6`, `FORCE` 없음) 세 번 모두 `DDD3` 이 변수 1 을 `00 → FF` 로 두고 `DDDC` 가 불렸습니다. `DDDC` 는 변수 0 을 지우고 연출이 `9E` 가 아니면 `FF` 로 줄입니다(`A4`·`A6` 은 `00 → FF`). 이 세 실행도 새 해석기로 21/21프레임씩 같았습니다.

## 틀렸던 것들

- 앞 일지들은 `6F` 의 차이를 HDMA 어림 탓으로 보고 줄마다 비용을 맞추려 했습니다. 실제로는 HDMA 시작의 한 주기 지연, 줄마다 바뀌는 리프레시 자리, 기다림 고리 안에서 NMI 를 받는 자리, 조이패드·소리 포트 입력이 함께 걸려 있었습니다. 줄 수나 반복 시간의 분포를 맞추는 것으로는 끼는 명령이 맞지 않았습니다.
- 입구 상태의 `memoryManager.dramRefreshPosition`(534)을 줄마다 그대로 썼습니다. 이 값은 줄 첫머리마다 다시 정해집니다.
- 짧은 줄을 프레임 수의 홀짝으로 정했다가 `6F` 에서 4 주기 어긋났습니다. 입구가 240줄 앞인지 뒤인지에 따라 하나 어긋납니다.
- `DDDC` 를 トラマナ(`36`)의 루틴으로 적었습니다. `24:DC18` 은 넷이 함께 쓰는 꼬리이고, トラマナ 로는 닿지 않습니다.

## 남은 것

- 전투 연출을 입구 상태 없이 롬만으로 그리기: 입구의 WRAM·VRAM·DMA 상태와 입구 뒤 조이패드·소리 포트 값이 입력입니다. 전투를 처음부터 세우는 일과 SPC700 을 흉내 내 포트 값을 롬만으로 내는 일은 하지 않았습니다.
