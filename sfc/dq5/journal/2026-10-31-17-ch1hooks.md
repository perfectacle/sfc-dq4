# 2026-10-31-17: 1장 빌드가 원래 롬 안에서 고친 곳과 `3E` 의 끝

[dq4 구간 다시 견주기](2026-10-31-09-dq4ranges2.md)가 남긴 둘을 풀었습니다. 하나는 dq4 1장 빌드가 원래 롬 자리(`00`~`2F`)에서 고친 곳을 dq4 문서와 하나씩 맞추는 일이고, 다른 하나는 `3E` 의 0 아닌 끝 `3E:D93E` 가 dq4 문서의 `3E:D934` 와 다른 까닭입니다. 결과는 [통합 포팅 빌드](../docs/dq5-build-format.md#1장-빌드가-원래-롬-안에서-고친-곳)에 있습니다.

## 1. 단계마다 나누기

`origin/main` `8c5b47b1` 에서 `dq4build.py --no-sound` 로 1장 롬(`8d0fe4c8…`)을 만들었습니다. 2장 맵이 더해져 앞 일지의 롬(`b8634d80…`)과 다릅니다.

메뉴 롬에서 1장 롬까지 원래 롬 자리의 차이를 어느 단계가 썼는지 나누려고, `dq4chapter1.build` 를 그대로 부르되 함수 셋을 감쌌습니다.

- `apply_writes`: 그룹 빌드 패치를 파일 하나씩 얹고, 앞뒤 차이를 그 파일의 쓰기 `note` 와 함께 적음
- `dq4chapterbox`·`dq4ch1event`·`dq4ch2event`·`dq4josa`·`dq4msgnames`·`dq4prologue` 의 `apply`: 앞뒤를 견줌
- `return_places`

```
same as dq4-ch1.sfc: True
uncovered ['00:A738', …, '25:8621', …, '25:8639', …]
129 rows
```

다시 합친 롬은 `dq4-ch1.sfc` 와 같았습니다. 기록에 없는 바이트는 셋으로 모였습니다. `build` 안에서 직접 쓰는 시간 멈춤(`00:A738`)과 새 게임 자리(`25:8621`), 그리고 `return_places` 의 다시 시작 자리(`25:8639`~`8684`)입니다. `return_places` 는 받은 롬을 제자리에서 고쳐 돌려주므로, 감싼 쪽에서는 앞뒤가 같은 객체라 차이가 보이지 않았습니다. 모두 132묶음입니다.

## 2. dq4 문서와 맞추기

묶음마다 시작 주소의 앞 세 바이트부터 끝 주소까지, 그리고 `note` 에 적힌 주소를 `sfc/dq4/docs` 에서 `BB:AAAA` 꼴로 찾았습니다. 훅은 첫 바이트(명령 코드)가 원래와 같아 한 바이트 뒤부터 바뀌는 일이 많아 앞 세 바이트까지 봤습니다.

찾지 못한 것의 대부분은 dq5 도구가 쓴 자리였습니다(`dq5newmap.py`·`dq5exitreloc.py`·`dq5fieldtables.py` 등). dq4 문서는 도구와 입력만 적습니다. 같은 방식으로 dq5 문서를 찾으니 거의 다 나왔습니다. 표 안의 항목은 표 시작 주소로만 적혀 있었습니다(구역 표 `23:96F3`, 이름 표 `23:C242`~`D6A0`, 몬스터 표 `23:8000`~`970B`, 이벤트 무리 표 `23:D757`). dq5 문서에 주소가 없는 것은 `12:8021`·`8051`(기본 인물 목록 뱅크·그룹 포인터) 하나뿐이고, `dq5npcrelocate.py` 의 상수에는 있습니다. `1F:FD39` 도 처음엔 못 찾았는데, 문서가 `1F:FD23`·`FD38` 처럼 뱅크를 앞에만 적어 `BB:AAAA` 꼴 찾기에 걸리지 않은 것이었습니다.

dq4 코드가 직접 쓰는 곳 가운데 dq4 문서에 주소가 없는 것은 둘입니다.

- `0F:8B53`~`8CB7` 의 묶음 일곱: `dq4environmentrom.py` 가 빌린 DQ5 맵 30곳의 맵 포인터(맵마다 3바이트)를 새 레코드로 바꾼 곳입니다. 환경 문서에는 빌린 레코드 자리 표만 있습니다.
- `06:FF40`~`FF56`: 합류 팡파르 `FANFARE_AT`. 1장 문서는 이름과 「뱅크 06」만 적습니다.

나머지(환경 훅, 여관·가게 키, 입구별 도착 훅, `ルーラ`, 우물 조우율, `dq4chapterbox`·`dq4ch1event`·`dq4ch2event`·`dq4josa`·`dq4msgnames`, 시간 멈춤·새 게임·다시 시작 자리)는 주소나 표 시작 주소로 dq4 문서에 있었습니다.

## 3. `3E` 의 끝

`dq4chapter1.py build --keep` 으로 그룹 빌드 패치를 남겨 `3E` 에 쓰는 것을 찾았습니다. 앞 일지의 롬(`6d7a49a8`)을 압축본(`git archive`)으로 꺼내 다시 빌드한 것입니다.

```
groups/env/dq4-environment.dq5patch.json 3E:D26D 3E:D93E 1746 dq4-environment writes[80] 3E:D26D 48-01 맵 레코드
```

`3E` 의 끝은 마지막 환경 맵 레코드 `48-01` 의 끝입니다. dq4 문서의 `3E:D934` 를 적은 커밋 `213164b0` 을 꺼내 빌드해도 끝은 같았습니다.

```
213164b0 → 1장 롬 55dde9c7…  3E last nz D93E  3F last nz E88A
```

그래서 문서 값이 처음부터 10바이트 틀린 것으로 봤습니다. 지금 `origin/main` 에서는 2장 맵으로 환경 맵이 줄어 끝이 또 다릅니다.

```
3D 15 3D:9000 3D:DB43 19268
3E 15 3E:8000 3E:D6F3 22260
30 41528
npc 3F:8000 3F:EABD
```

환경 맵 레코드는 30개 41,528바이트, `3E:D6F3` 에서 끝납니다. 1장 문서의 기본 인물 목록 끝(`3F:E88B`)도 지금은 `3F:EABD` 입니다. [환경 문서](../../dq4/docs/dq4-environment-format.md)의 「맵 레코드(빌린 자리) `3D:9000`~, `3E:8000`~, `3F:8000`~`3F:9B5A`, 43개 58,891바이트」도 지금 빌드와 맞지 않습니다. dq4 파일은 고치지 않고 [todo](../todo.md)의 「DQ4 트랙에 요청할 것」에 적었습니다.

## 틀렸던 것들

- 처음 단계별 기록에 `return_places` 가 하나도 없어, 이 단계가 원래 롬 자리를 쓰지 않는다고 봤습니다. 받은 `bytearray` 를 고쳐 그대로 돌려주는 함수라 앞뒤가 같은 객체였습니다. 기록 밖 바이트를 따로 모아 찾았습니다.
