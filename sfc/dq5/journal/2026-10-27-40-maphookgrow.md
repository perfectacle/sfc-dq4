# 2026-10-27-40: 맵별 루틴 표 늘리기와 셀 읽기 루틴 표

[맵별 루틴 표 쓰기](2026-10-27-18-maphook.md)에서 남긴 두 가지를 마저 했습니다. 하나는 표를 163개 넘게 늘려 뱅크 15 밖으로 옮기는 것이고, 다른 하나는 바로 뒤 `15:FF5C` 의 둘째 표를 쓰는 것입니다. 둘 다 `dq5maphook.py` 에 더했고 게임에서 원본과 견줬습니다. 결과는 [쓰기 형식](../docs/dq5-build-format.md#맵별-루틴-표-dq5maphook1)에 있습니다.

## 1. 로더가 DB 를 무엇에 쓰나

`15:F7D0` 은 `PHB / PHK / PLB` 로 DB 를 15 로 두고 `JSR $F7F4`(맵별 루틴 표)와 `JSR $F887`(둘째 표)을 차례로 부릅니다. 두 루틴을 디스어셈블해 `abs` 접근을 모두 적었습니다.

```text
15:F7F4~F886  LDA $F907,X 꼴 11곳(표)    LDA $1949        STA/STX $1AA6~$1AA8
15:F887~F905  LDA $FF5C,X 꼴 7곳(둘째 표)  LDA $1949·$1A35  STX $1AAA·STA $1AAB
```

표만 보면 어느 뱅크든 되지만, `$1949`·`$1AA6` 같은 WRAM 자리도 `abs` 로 씁니다. DB 가 `40`~`7D` 면 그 뱅크의 `0000`~`1FFF` 에 WRAM 거울이 없어 엉뚱한 곳을 읽고 씁니다. 그래서 표를 옮길 뱅크는 `00`~`3F`·`80`~`BF` 만 됩니다. 늘린 롬에서는 `30`~`3F`(2MB 안)이고, 텍스트·DQ4 타이틀이 쓰는 뱅크라 겹치지 않게 골라야 합니다.

## 2. 스텁

`PHK / PLB` 두 바이트 자리에는 다른 뱅크를 넣을 명령이 들어가지 않습니다. 대신 `15:F7E2` 의 `JSR $F7F4` 세 바이트를 뱅크 15 의 스텁로 돌렸습니다.

```text
15:FFF0  PHB / LDA #$3F / PHA / PLB / JSR $F7F4 / PLB / RTS
```

스텁는 첫 표를 읽는 동안만 DB 를 바꾸고 돌아오므로, 다음 `JSR $F887` 은 DB = 15 인 채 둘째 표를 읽습니다. 들어올 때 M 은 8비트, X 는 16비트(`15:F7D4`·`F7D6`)라 `LDA #imm` 은 두 바이트입니다. 스텁는 뱅크 15 의 빈 자리 지도 `15:FF80`~`FFFF` 안에 두고, 표와 스텁에는 `orig` 를 붙이지 않아 빌더가 빈 자리 밖이면 거부합니다.

## 3. 둘째 표

`15:F887` 은 맵별 루틴 표와 같은 꼴(그룹·맵·플래그·마스크)로 6바이트 항목을 훑고, 맞으면 뒤 16비트를 `$1AAA` 에 둡니다. 없으면 `$1A35` 에 따라 `00:B8CA` 나 `00:B869` 입니다. 롬에서 `AA 1A` 를 찾자 명령으로 읽히는 것은 `15:F8E1`·`F902`(쓰기)와 `00:B8C6` 의 `JMP ($1AAA)` 셋이었고, 나머지 11곳은 `$1AAA` 를 피연산자로 받는 명령이 아니었습니다(`21:A172` 의 `TAX / INC A`, `18:F89E` 의 자료 등, 바이트 검색과 디스어셈블). 그 앞 `00:B8B7` 은 셀 좌표(`$90`·`$92`)가 맵 크기(`$BF`·`$C0`) 안인지 보고 셀을 읽으러 갑니다. 그러니 둘째 표는 맵마다 셀 읽기 루틴을 고르는 표입니다. 원본 항목은 17/01(배 갑판) → `00:BCC3` 하나이고, `00:BCC3` 은 이야기 플래그와 좌표로 갑판의 특정 칸을 따로 다루는 것으로 보입니다(코드 읽기).

`JMP (abs)` 는 같은 뱅크로만 뛰므로 루틴은 뱅크 00 의 16비트 주소입니다. 도구는 세 루틴만 받고, 다른 주소는 `--raw-routines` 로 받습니다. `15:F887` 은 DB = 15 로 읽으므로 둘째 표는 뱅크 15 안에만 둡니다. 처음에는 이 검사가 빠져 `2F:FFC0` 같은 자리도 받았는데, 리뷰에서 게임이 엉뚱한 곳을 읽는다는 지적을 받고 막았습니다.

## 4. 게임에서 견주기

`dq5maphookcheck.py` 에 롬 세 벌을 더했습니다. `lua/dq5maphookcheck.lua` 가 맵을 푼 직후의 `$1AAA` 와 `JMP ($1AAA)` 가 간 곳별 횟수도 적게 했습니다.

```text
163개로 3F:8000 (스텁 15:FFF0)
  01/04 (32,5)  원본: 매 프레임 15:F906, 01/04 에 남음 → 고친 롬: 02:A7BD, 04/0A (8,17)
  04/00 (32,12) 고친 롬: 02:A7BD, 04/0A (8,17)
  01/05 계단    고친 롬: 02:94E0, (51,20) = 85, 01/04 (13,47)
둘째 표를 15:FF80 으로, 01/04 → 00:BCC3 더함
  원본          $1AAA = B869, 실행 전체에서 B869 로 714번(선실의 B8CA 1,088번 따로)
  조건 없음     $1AAA = BCC3, BCC3 으로 714번
  bit6 켜졌을 때 B869(어린 시절) / SET 2190|40 이면 BCC3
```

01/04 항목은 옮긴 163개 표에만 있으므로, 맵별 루틴이 바뀐 것은 로더가 뱅크 3F 를 읽었다는 뜻입니다. 원래 항목 04/00·01/05 도 그대로 불렸습니다. 22장면 모두 통과했습니다.

## 남은 것

스텁를 쓴 롬에서 표를 원래 롬의 빈 자리 뱅크(`00`~`2F`)에 둔 경우는 돌려 보지 않았습니다. `00:BCC3` 을 01/04 에서 불렀을 때 걷기가 어떻게 바뀌는지, `00:BCC3` 이 갑판에서 무엇을 막는지도 보지 않았습니다. 맵 고르기를 바꾼 롬과 `--raw-routines` 롬의 실측도 남아 있습니다.
