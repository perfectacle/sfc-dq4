# 2026-10-26-05: ミルドラース 가 쓰러질 때의 색 셈

[2026-10-25-192](2026-10-25-192-monmotion4.md) 에서 `22:CC16` 의 단계 목록(처리 번호 차례)까지는 읽었지만, 처리 번호마다 무슨 색이 되는지와 섞는 셈은 코드 읽기로만 적어 두었습니다. 처리 루틴 표 `22:A7E2` 를 모두 풀고, 롬만으로 프레임마다의 색을 내는 [sfc/dq5/tools/dq5bossfade.py](../tools/dq5bossfade.py) 를 써서 두 보스의 270프레임과 견줬습니다. 결과는 [dq5-graphics-format.md](../docs/dq5-graphics-format.md) 의 「`22:CC16` 의 처리 번호」 에 있습니다.

## 1. 섞는 셈

`22:A668` 을 끝까지 읽었습니다. 색마다 회색 g = (3R + 6G + B) / 10 을 하드웨어 나눗셈(`$4204`/`$4206` = 10)으로 내고, R·G·B 를 모두 g 로 둔 뒤 처리 번호로 `22:A7E2` 표의 루틴을 `JSR ($A7E2,X)` 로 부릅니다. 끝 처리(`$8585`)는 `$60`·`$64`·`$68`, 처음 처리(`$8587`)는 `$62`·`$66`·`$6A` 에 결과를 두고, `22:AA39` 가 각각 `$8589` 와 `$858A` − `$8589` 를 곱하고 `22:AA84` 가 더해 `$858A` 로 나눕니다.
처리 번호 `00` 은 `LDX $8585,Y / BEQ` 로 루틴을 건너뛰어 원래 색이 남습니다. `0A` 의 루틴 `22:A8E8` 은 `RTS` 하나라 회색 그대로입니다.

## 2. 처리 루틴 열여덟

`22:A7E2` 의 16비트 표에서 `02`~`24` 의 루틴을 하나씩 풀었습니다. 대부분 g 를 두 배·여덟 배 하거나 반으로 줄여 성분마다 다르게 두는 꼴이고, `0C`(흰색)·`18`(31,28,19)·`24`(검정)는 고정 색, `1A` 는 원래 색을 다시 읽어 반으로 줄입니다. `16` 은 A 에 남은 g 를 그대로 써서 B = g/2, G = g/4 로 둡니다.
`2B` 의 단계 `00 → 20 → 1E → 02 → 24` 는 원래 색 → 푸르스름한 흰색 → 주황 → 붉은색 → 검정이 되어, 앞서 덤프에서 본 차례와 같았습니다.

## 3. 덤프와 견주기

`dq5warp.lua` 의 `GROUP=2B`·`GROUP=2F` 로 전투 세이브스테이트를 만들고, `dq5battle.lua` 를 드라이버로 둔 `lua/dq5monlog.lua` 로 보스 HP(`7E:07C2`)를 1, 주인공 HP(`7E:2042`)를 999 로 고정해 쓰러뜨리며 프레임마다 CGRAM 을 남겼습니다.

```sh
STATE=$PWD/work/state/ship.mss FIELD=341,56 GROUP=2F SETTLE=300 SAVE=battle-2F.mss SHOT_DIR=$PWD/work/w2F \
  "$MESENCE" --testrunner "$PWD/rom/dq5.sfc" "$PWD/sfc/dq5/tools/lua/dq5warp.lua"
LIBDIR=<lib.lua·probe 와 boot.lua = dq5battle.lua 를 둔 폴더> STATE=$PWD/work/w2F/battle-2F.mss \
  POKE="7E07C2=01,7E07C3=00,7E2042=E7,7E2043=03" FROM=1 TO=1400 MAXF=1450 EXEC=22CC16,22A650 SHOT_DIR=$PWD/work/m2F \
  "$MESENCE" --testrunner "$PWD/rom/dq5.sfc" "$PWD/sfc/dq5/tools/lua/dq5monlog.lua"
uv run --locked python sfc/dq5/tools/dq5bossfade.py rom/dq5.sfc --check work/m2B work/m2F
```

처음에는 CC16 직전 CGRAM 줄 8 의 16색을 모두 바꾸게 했더니 `2B` 에서 색 14·15 가 늘 어긋났습니다. 그 둘은 끝까지 바뀌지 않았습니다. `22:A68E` 가 버퍼 색 0 자리를 색 수로 읽는다는 것을 보고 몬스터 레코드의 색 수(`E7` 13색 → 14)를 쓰자 120/120 이 맞았습니다.

```
work/m2B 첫 몬스터 E7, 단계 4개 00 → 20 → 1E → 02 → 24
  단계 시작 프레임 [277, 308, 341, 372], 덤프는 2 프레임 뒤
  레코드 색 13개, 줄 8 의 색 1~15 가 같은 프레임 120/120
work/m2F 첫 몬스터 EA, 단계 9개 00 → 20 → 0A → 10 → 04 → 06 → 08 → 1E → 02 → 24
  단계 시작 프레임 [616, 647, 678, 711, 743, 774, 807, 841, 875], 덤프는 2 프레임 뒤
  레코드 색 15개, 줄 8 의 색 1~15 가 같은 프레임 265/270
  다른 프레임: 646(색 4) 647(색 4) 727(색 1) 728(색 1) 729(색 1)
```

## 4. `2F` 의 다섯 프레임

같은 장면을 다시 돌려 버퍼 `7E:2E00` 을 프레임마다 읽었습니다. 270가지 (단계, k) 색이 모두 나왔고 디코더와 다른 버퍼는 없었습니다. 셈은 맞고, 차이는 버퍼에서 CGRAM 으로 가는 쪽입니다.
그 프레임의 `$2121`·`$2122` 쓰기를 감시하니 화면 56줄째에 `$2121` = `84`(646 언저리)·`81`(727 언저리)과 `$2122` 두 바이트가 쓰였습니다. 그때 PC 는 소리 대기열 루프(`2B:BEDx`)나 `22:A6xx` 처럼 그 순간 돌던 코드였습니다. 줄 위치가 정해져 있고 PC 가 아무 데나라 HDMA 를 의심했습니다. 646 프레임의 DMA 레지스터를 읽으니 `$420C` = `3E`(채널 1~5)이고, 채널 4 가 `$4340` = `43`(간접, 쓰기 꼴 3 = `$2121`·`$2121`·`$2122`·`$2122`), `$4341` = `21`(CGRAM 주소), 표 `00:0DB9`, 간접 뱅크 `27` 이었습니다. 이 채널이 CGRAM 에 쓴 것입니다.

```
ch4 43 21 B9 0D 00 00 00 27 CA 0D 00
```

## 틀렸던 것들

- 색 1~15 를 모두 바꾸는 줄 알았습니다. 바꾸는 색 수는 버퍼 색 0 자리에 적힌 「레코드 색 수 + 1」 입니다.
- CGRAM 색 0 자리에서 색 수를 읽으려 했습니다. `2B` 덤프에서는 `000E` 로 맞았지만 `2F` 덤프에서는 `0000` 이라, 레코드에서 읽게 바꿨습니다.

## 남은 것

- HDMA 채널 4(표 `00:0DB9`, 간접 뱅크 `27`)가 `2F` 장면의 몇 프레임에만 OBJ 팔레트 0 의 색 하나를 가리키는 까닭.
