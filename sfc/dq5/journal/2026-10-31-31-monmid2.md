# 2026-10-31-31: 물건 k4 하위 06, 첫째 바다 직사각형의 X1, 무리 값과 부르기, モシャス 의 그림 풀기

[일반 입구·바다 구역·물건 k2 bit4·k4 하위](2026-10-31-23-writerest.md)와 싸우는 도중의 그림 풀기에서 남긴 것 넷을 쟀습니다. 결과는 데이터 형식의 [물건 표](../docs/dq5-data-format.md#물건-표-23b081)·[전투 조우](../docs/dq5-data-format.md#전투-조우-23e7c2), 쓰기 형식의 [게임 데이터 표](../docs/dq5-build-format.md#게임-데이터-표-dq5tables1), 그래픽 형식의 몬스터 표 바꾸기 표(`22:D3B9` 줄)에 있습니다.

## 1. k4 하위 06 은 「장비해 본다」

`20:BA0F` 의 `BRK #94 0F` 뒤는 값이 `06` 이면 따로 갑니다. 바이트를 하나씩 풀었습니다. 디스어셈블러가 `BRK` 의 피연산자 길이를 몰라 뒤가 어긋나 보였기 때문입니다.

```text
20:BA12  LDA $46 / CMP #$06 / BNE $BA2D
20:BA18  LDA $F5 / BRK #8B …
20:BA1E  LDA $46 / XBA / LDA $10F7 / BRK #94 01 / LDA #$06 / BCS $BA2D / LDA #$23
20:BA2D  ASL / TAX / LDA $2781D0,X …
```

`BRK #94 01` 은 장비 검사입니다. 장비할 수 있으면 표 칸 `06`(`0D1`「…を みにつけた！」), 아니면 `23`(`0D2`「…を そうびできない！」)을 띄웁니다. 값이 `06` 인 물건은 ほしふるうでわ(`9A`)·エルフのおまもり(`9B`)·ビアンカのリボン(`9C`)·メガンテのうでわ(`9D`)·いのちのリング(`A0`)로, 장신구입니다. `dq5grouptargetcheck.py` 에 셋을 더했습니다.

```text
やくそう k4하위 06:      전투 메시지 0D2 094 05E 06A
ほしふるうでわ(06):      전투 메시지 0D1 05E 06A 05E 06A
ビアンカのリボン(06):    전투 메시지 0D2 05E 06A 05E
```

주인공은 ほしふるうでわ 를 「みにつけた」, ビアンカのリボン 은 「そうびできない」 였습니다. `06` 으로 바꾼 やくそう 도 「そうびできない」 뒤 회복(`094`)으로 이어졌습니다. 실제로 장비가 바뀌는지는 보지 않았습니다.

## 2. 첫째 바다 직사각형의 X1

첫째 직사각형의 X1(33) 양쪽이 모두 바다인 칸은 세계 0 지도에 없습니다. 그래서 X1 을 `06` 으로 덮은 롬(`01:85DA`)에서, X0 을 잴 때와 같은 줄((2,140) 에서 오른쪽)을 저었습니다(`dq5searectcheck.py` 의 `x1p`).

```text
x1p: B6/2 경계 06 — 01:52 02:52 03:52 04:51 05:51 06:52 07:52
```

X1 도 끝 값은 밖이었습니다. 표 값만 바꾼 것이고, 견주는 명령은 원래 롬의 `01:85B2` 그대로입니다.

## 3. 무리 값과 부르기

`dq5warp.lua` 의 `BATTLE` 에 셋째 값을 더했습니다. `"00:2:02"` 처럼 주면 그 무리 값(이벤트 무리 `+9`~`+C` → `$1009`~)이 됩니다. スライム 2 무리의 값을 `00`·`01`·`02`·`80` 으로 두고, 행동을 모두 같은 몬스터 부르기 `AB` 로 바꿨습니다. 슬라임 HP 는 붙잡아 두었습니다(`dq5groupvaluecheck.py`).

```text
무리 값 00: 부르기 04B ×8, 마릿수 2~10
무리 값 01: 부르기 04A ×6, 마릿수 2
무리 값 02: 부르기 04A ×6, 마릿수 2
무리 값 80: 부르기 04B ×8, 마릿수 2~10
```

`04A` 는 「しかし たすけは こなかった！」입니다. 값 `02` 는 앞줄에 서지만, 부르기(`22:D1C0`)에서는 뒷줄인 `01` 과 같이 막혔습니다. 효과 기준 칸(`22:EB60`)은 연출 `73`(무기 번호 `21`)에서만 불려 재지 못했습니다.

## 4. モシャス 의 그림 풀기

`dq5scenes.py` 의 `mosyas-58` 장면에서 그림 풀기가 없었던 까닭을 찾았습니다. `22:D3B9`·`D3EF`·`9088` 에 실행 감시를 걸었습니다.

```text
f567 22F285 DA7=00 D0E=02 19=02 / 22D3B9 / 22D3EF / 229088
```

モシャス 는 세 번 모두 `22:9088` 까지 갔습니다. 하지만 고른 몬스터 `$0DA7` 이 `00`(スライム 자신)이라, 이미 풀린 그림을 다시 풀지 않았습니다. 이때 `$19` 는 `02`, 곧 연출 중이었습니다(덮은 뒤 그림을 푸는 프레임은 `03`, 그래픽 형식 문서의 값). 그래서 `22:D3DD` 에서 `$0DA7` 을 동료 종류 09 의 몬스터 `2A`(그림 `03`)로 덮어 보았습니다. 게임이 고른 값이 아니라 실험으로 바꾼 값입니다.

```text
568 nmi 240 92 0 19=03 oam 240 1010
568 entry 244 1080 … 6080   entry 246 926 … 6180   end 248 454
```

그림 `03` 이 OAM DMA 뒤에 풀렸습니다. 첫 DMA 는 244줄 1,080~1,100 으로, 연출의 OBJ 그림을 보낼 때와 같은 지연이었습니다. 그림 `03` 을 늘려 닿은 수를 셌습니다.

```text
타일 84:  항목 [8,8] [24,74] [112,2],  닿음 84 (지연으로 셈 84)
타일 90:  항목 [8,8] [24,78] [112,4],  닿음 86 (셈 86)
타일 100: 항목 [8,8] [24,82] [112,10], 닿음 86 (셈 87)
```

잰 첫 DMA 지연을 `margin` 으로 준 `dq5mongfx.nmi_tiles` 는 둘을 맞혔고 하나는 1개 많게 셌습니다. `dq5monwrite.py` 가 モシャス 그림에 남기는 몫(4,850 + 타일 하나 몫 264)으로 세면 85개라, 셋 모두 실제로 닿는 수를 넘지 않습니다. 이 몫은 `dq5monmidcheck.py` 쪽에서 정한 것입니다. 이 실험은 그 도구와 같은 그림 늘리기에 `$0DA7` 덮기를 더한 것이라, 그 도구가 들어온 뒤에 장면으로 옮깁니다.

## 틀렸던 것들

- `mosyas-58` 에서 그림 풀기가 없던 것을 「그림 표가 바뀌지 않았다」로만 보았습니다. 실제로는 モシャス 가 スライム 자신을 골라 풀 그림이 없었던 것입니다.

## 남은 것

- 게임이 동료의 몬스터를 고르는 モシャス 장면(`$0DA7` 이 동료 쪽이 되는 조건), 그리고 그때의 그림 풀기 실측.
- 효과 기준 칸(`22:EB60`·`EBB2`)이 무리 값 `02`~`7F` 를 뒷줄로 세는지(연출 `73`).
- `22:ADE7` 로 자리 사슬이 끊겨 이어질 때의 목록 항목 수.
- k4 하위 06 으로 장신구를 실제로 장비하는지.
