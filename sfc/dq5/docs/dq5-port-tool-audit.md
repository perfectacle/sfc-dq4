# DQ4 포팅용 쓰기 도구 점검

**현재 도구만으로 DQ4 전체를 포팅할 수 있는 상태는 아닙니다.** 기존 DQ5 자료를 교체하는 경로는 늘었지만, 출구·인물 배치·대화 분기·주문 습득·새 그림·게임 전체 한글 표시에 필요한 쓰기 경로가 남아 있습니다. DQ4 타이틀·메뉴와 DQ5 쓰기 도구의 기본 배치도 충돌합니다.

이 문서는 `b38afd1`의 추적 소스를 기준으로 `sfc/dq5/tools/`, `sfc/dq4/tools/`, FC DQ4의 형식 문서와 각 트랙의 남은 일을 대조한 결과입니다. CLI뿐 아니라 인코더·패치 함수·입력 스키마까지 확인했습니다. 실제 롬·IPS 생성, 거절해야 할 입력, MesenCE 실행을 구분해 기록합니다. 이후 해결한 항목은 해당 구현 일지로 연결합니다.

`dq5build.py`로 주소와 바이트를 직접 쓰는 것은 가능합니다. 아래의 ‘작성기 없음’은 원시 패치로 구현 불가능하다는 뜻이 아니라, 해당 형식의 입력·포인터·개수·연결을 검증하는 작성 경로가 없다는 뜻입니다. 원본 읽기 도구나 소수 자료를 고정해서 넣는 실험도 범용 작성기와 구분합니다.

## 2. 포팅 통합에서 발견한 문제

### 기본 배치 다섯 조합이 충돌합니다

앞서 확인한 필드·인물·대사·성장 패치의 통합은 DQ5 원본 위의 통합이었습니다. DQ4 타이틀·메뉴를 포함하지 않았으므로 최종 포팅 롬의 통합 검사로 볼 수 없습니다.

현재 코드로 DQ4 타이틀·메뉴를 만들고 `dq5build.py fromrom`으로 변환한 뒤 다음 조합을 `check --size 4`로 검사했습니다. 모두 종료값 1로 겹침을 거부했습니다.

| 기존 포팅 자료 | 함께 넣은 기본 쓰기 | 첫 충돌 주소 |
| --- | --- | --- |
| DQ4 타이틀 | `dq5mapwrite.py`의 맵 `01/05` | `30:8000` |
| DQ4 타이틀 | `dq5npcrelocate.py` | `32:8000` |
| DQ4 타이틀 | `dq5fieldwrite.py` 세 세계 | `34:8000` |
| DQ4 타이틀 | `dq5textwrite.py` | `38:8000` |
| DQ4 한글 메뉴 | `dq5eventwrite.py` 이벤트 8 | `60:8000` |

이는 빈 영역의 미러 바이트만 겹치는 경우가 아닙니다. 타이틀은 `30` 뱅크의 코드, `32`의 전경 CHR, `34`의 OBJ 그림을 사용합니다. 실제 생성한 `layer-payload.bin` 98,848바이트는 `36:8000`~`39:821F`를 차지하므로 대사 기본 뱅크 `38`도 사용 중입니다. 메뉴 창 처리 훅은 `60:8000`입니다. 배치는 [DQ4 타이틀](../../dq4/docs/dq4-title-animation.md), [메뉴](../../dq4/docs/dq4-menu-format.md)에 있습니다.

필요한 것은 모든 작성기가 공유하는 영역 예약·배치 정보와 최종 포팅 빌드입니다. `--at`을 수동으로 바꾸는 기능은 일부 있으나, 필드·인물·보행 대사는 `30`~`3F` 제약이 있어 다른 뱅크로 임의 이동하면 안 됩니다. 빌더는 충돌을 발견하지만 재배치를 대신 결정하지 않습니다.

재현 형태:

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc fromrom work/title.sfc --name title -o work/title.patch.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc dump 01 05 -o work/map.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc patch work/map.json -o work/map.patch.json
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc check work/title.patch.json work/map.patch.json --size 4
```

`work/title.sfc`는 [타이틀 재현 절차](../../dq4/docs/dq4-title-animation.md#재현-빌드와-자동-검사)로 먼저 만듭니다.

### 영역 할당만으로 저뱅크 공간이 늘지는 않습니다

다음 수치는 위 기준 커밋에서 실제 자료 길이를 합산한 것입니다. 원본 DQ5 전체를 다시 넣는 경우이며, 필요한 맵 일부만 교체하거나 새 DQ4 자료를 만드는 경우의 크기는 따로 계산해야 합니다.

| 자료 | 확장 영역의 자료 크기 |
| --- | ---: |
| 기본·대체 인물 목록 | 44,159바이트 |
| 세 세계 필드 압축 | 39,260바이트 |
| 보행 대사 디코더·트리·스트림 | 145,288바이트 |
| 실내 맵 364개 원본 레코드 | 233,794바이트 |
| 같은 맵의 배치 목록 재컴파일 | 249,471바이트 |
| 타이틀 실제 그래픽 자료 | 203,456바이트(코드 별도) |

저뱅크 `30`~`3F`는 524,288바이트입니다. 재컴파일 맵을 포함한 인물·필드·대사는 478,178바이트지만, 타이틀까지 합치면 681,634바이트로 **코드를 제외해도 157,346바이트가 넘습니다.** `fromrom`에 잡힌 타이틀 변경량에는 원본 미러 복제도 있으므로, 그 전체를 타이틀 자료량으로 세지 않았습니다.

타이틀을 제외하면 뱅크 끝의 공간을 공유하는 배치 후보는 계산할 수 있습니다. 인물 `30`·`31`, 필드 `32:8000`, 대사 `33:9C00`, 맵 `37:D388`부터 놓으면 재컴파일 맵 끝은 `3F:A207`(미포함)입니다. 이는 주소 계산이며 이 새 배치의 전체 롬·게임 검증은 아직 하지 않았습니다. 새 자료의 크기·디코더 머리·압축 덩어리 경계도 다시 검사해야 합니다.

타이틀은 DB를 `00`으로 두고 롱 주소와 DMA의 원본 뱅크를 쓰므로, 상위 뱅크로 옮길 후보입니다. 하지만 내부 포인터·전송표·ASM 상수·메뉴 진입 훅까지 다시 만들어야 하며 **상위 배치의 게임 실행은 미확인**입니다. 타이틀을 통째로 복사하거나 `--at`만 바꾸는 것으로 검증을 대신할 수 없습니다.

### 없는 맵 번호가 다음 그룹의 맵을 바꿉니다

아래는 감사 기준 커밋에서 재현한 결함이며, 이후 [입력 보호 수정](../journal/2026-10-26-59-mapwrite-guard.md)으로 없는 맵 번호와 미지원 필드를 거부하도록 고쳤습니다. 새 맵 증설 기능을 추가한 것은 아닙니다.

정상 `17/00` 입력의 `map`만 원본에 없는 `17/05`로 바꾸자 당시 `dq5mapwrite.py`는 종료값 0으로 패치를 냈습니다. 실제 빌드 후 **`18/00`의 포인터 `0F:8CD3`가 `1B:CFF0`에서 `30:8000`으로 바뀌었습니다.** IPS 재적용도 같은 롬을 만들었습니다. 게임은 실행하지 않았으며, 생성 롬 바이트를 확인한 결함입니다. 새 맵 번호 증설로 사용할 수 없습니다.

또 정상 맵 JSON에 `exits` 필드를 추가해도 성공으로 끝나고 원래 입력과 동일한 패치를 냈습니다. 출구 필드가 지원되는 것이 아니라 무시된 것입니다. 없는 맵 번호와 미지원 필드를 명시적으로 거부해야 합니다.

| 음악·효과음 | 공용 시퀀스 인코더·재배치, WAV/파형→BRR, 샘플·묶음 교체, DQ4 서곡 | 맵 음악·장면별 효과음 연결표, 악기 묶음의 의미 기반 편집·메모리 사용 검사. 곡 편곡은 별도 콘텐츠 작업 |
| 타이틀·엔딩 | 채택 타이틀의 레이어·애니메이션·엔진 연결 | 엔딩/스태프롤 문구·레이아웃·그림 작성. 초상·일러스트는 사용 여부와 표시 엔진부터 결정 |
| 통합·검증 | 원시 패치 빌더·겹침/orig/IPS 검사, 개별 장면 재현 | DQ4 포팅 전체 영역 예약, 모든 자료 연결과 새 게임→장 진행→저장·재개를 검증하는 빌드 |

근거: [맵 형식](dq5-map-format.md), [텍스트 형식](dq5-text-format.md), [데이터 형식](dq5-data-format.md), [그래픽 형식](dq5-graphics-format.md), [DQ4 도구](../../dq4/tools/README.md), [FC DQ4 장·저장 형식](../../../fc/dq4/docs/dq4-save-format.md).

표의 항목마다 별도 실행 파일을 만들 필요는 없습니다. 기존 인코더를 확장하거나 여러 표를 한 입력으로 묶는 편이 연결 오류를 줄일 수 있습니다. 항목 증설은 원본 슬롯을 재사용해도 부족한지 먼저 계산한 뒤 결정합니다.

## 4. 입력 경계를 실제로 확인한 사례

| 입력 | 실제 결과 |
| --- | --- |
| 인물 `entries`·등장 조건 또는 스크립트 항목의 `talk` | `dq5npcrelocate.py`가 미지원 필드로 거부 |
| 원본 슬롯이 아닌 인물 스크립트 `32:8000` | 원본 슬롯이 아니라는 오류 |
| 이벤트 `binding.kind=talk` | `event`·`number`만 허용 |
| 메시지의 `if_flag` 또는 유니코드 `text` | `id`·`codes`만 허용 |
| 보행 글자 코드 `3DB` | 기존 글꼴 범위 밖으로 거부 |
| `dq5tables.py`에서 `_이름`만 수정 | 쓰기 0개. 표시용 필드를 무시하는 기존 명세이며 명칭 편집 기능이 아님 |
| 필드 일반 입구 47·블록 511 추가 | 각각 0~46·0~510 범위 오류 |
| 기존 6품목 상점에 1품목 추가·키 변경 | 길이/키 오류 |
| 이벤트 번호 표 뒤에 항목 추가 | 이벤트 0~9·번호 표 0~82 한도 오류 |

반대로 원시 패치로 `17/00` 출구 목적지를 `17/02`→`17/03`으로 고치면 빌더·IPS·읽기 검사는 통과했습니다. 이 실험은 게임 보행 검사는 아니며, 원시 쓰기 통로가 존재함을 확인한 대조군입니다.

## 5. 제작 순서와 엔진 작업의 구분

1. **입력 안전성과 통합 배치**: 없는 맵 번호·미지원 필드를 거부하고, DQ4 타이틀/메뉴/음악을 포함한 영역 사용표와 배치 규칙을 정합니다.
2. **한 마을의 연결을 완성**: 실내 출구·영역 이동, 인물 레코드·조건 목록, 대화 VM·메시지 연결, 상자·조사 보상을 작성합니다. 왕좌에서 대화하고 마을·필드를 왕복하는 작은 DQ4 장면으로 검증합니다.
3. **인물·전투 데이터를 맞춤**: 주문 습득·목록·효과·필드/전투/AI 비용과 초기 파티 데이터를 함께 편집합니다. 맵 조우와 보스 무리 연결도 필요합니다.
4. **게임 전체 글자·그림**: 보행/전투/명칭/창의 한글 출력 경로와 코드북을 정하고, 기존 RLE·글리프 생성기를 재사용해 범용 그림·텍스트 작성기로 확장합니다.
5. **장별 진행과 저장 재개**: 장 시작/끝, 주인공 교체, 재산·소지품 승계, 임시 동료·탈것·패배 후 진행·엔딩을 구현하고 저장 후 다시 이어 봅니다.

마지막 항목은 단순 표 인코더가 아닙니다. FC DQ4의 장 시작 표에는 다섯 장의 선두·골드·초기화 인물·출발 장소가 따로 있습니다. 3장의 상점 경영과 납품, 4장의 패배 후 진행, 5장의 동료 합류·열기구·장벽 보스도 기존 DQ5 사건을 그대로 바꾸는 것만으로 완성되지 않습니다. 필요한 네이티브 처리와 이벤트 설계를 분리해야 합니다.

4인 전투·메뉴 전체 지원, DQ4 고유 효과·AI, 저장 영역 확장도 엔진 작업입니다. 기존 저장 영역 안에서 플래그를 배정할 수 있다면 별도 저장 인코더가 반드시 필요한 것은 아닙니다. 새 저장 형식을 쓰면 로드·체크섬·초기화·버전 구분까지 검증해야 합니다.

이 점검으로 ‘이밖에 누락은 없다’고 보증하지 않습니다. 추적 도구와 분석된 데이터 형식의 공백을 확인했으며, 실제 DQ4 장을 처음부터 끝까지 만든 검사는 아직 아닙니다. 이후 완성할 장면별로 입력→롬→게임→저장 재개 경로를 검증해야 합니다.
