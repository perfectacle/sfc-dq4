## 흐름

```
쓰기 도구 A ─┐
쓰기 도구 B ─┼─ *.dq5patch.json ─ dq5build.py build ─ work/build/dq5kr.sfc ─ dq5boottest.py
롬 전체를 내는 도구 ─ dq5build.py fromrom ─┘                      └ work/build/dq5kr.ips
```

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc build work/build/*.dq5patch.json --size 4 \
    -o work/build/dq5kr.sfc --ips work/build/dq5kr.ips
MESENCE=… uv run --locked python sfc/dq5/tools/dq5boottest.py rom/dq5.sfc work/build/dq5kr.sfc
```

## 입력 형식 `dq5patch/1`

쓰기 도구 하나가 파일 하나(`<이름>.dq5patch.json`)를 냅니다.

```json
{
  "format": "dq5patch/1",
  "name": "hangul-font",
  "rom_size": 4,
  "writes": [
    {"at": "24:9E02", "hex": "22 00 80 30 60", "orig": "08 8B 4B AB E2", "note": "디코더를 뱅크 30 으로"},
    {"at": "30:8000", "file": "hangul-font.000.bin", "note": "새 글꼴"},
    {"at": "0x180000", "hex": "00 01"}
  ]
}
```

| 키 | 뜻 |
| --- | --- |
| `format` | 늘 `dq5patch/1`. 형식을 바꾸면 숫자를 올립니다 |
| `name` | 오류·보고에 쓰는 이름. 세션·도구 이름 |
| `rom_size` | 이 목록이 바라는 롬 크기(MB, `2`·`3`·`4`). 빼면 늘리지 않음. 빌더는 목록들과 `--size` 가운데 가장 큰 값으로 늘림 |
| `writes[].at` | 쓰는 자리. `BB:AAAA`(LoROM CPU 주소, 뱅크 `00`~`7D`·`80`~`FF`, `AAAA` 는 `8000`~`FFFF`, 뱅크 `80` 부터는 거울) 또는 `0x` 로 시작하는 파일 위치 |
| `writes[].hex` | 쓸 바이트(16진, 띄어 써도 됨) |
| `writes[].file` | 쓸 바이트가 든 파일. JSON 파일과 같은 폴더 기준 상대 경로. `hex` 와 둘 중 하나만 |
| `writes[].orig` | 원래 롬의 그 자리 바이트(16진, 쓰는 길이와 같게). 빌더가 원래 롬과 대조함 |
| `writes[].note` | 설명. 겹침 오류에 함께 나옴 |

빌더가 거부하는 것:

- **겹침**: 두 쓰기(같은 목록이든 다른 목록이든)가 한 바이트라도 겹치면 거부합니다. 두 쓰기의 이름·주소·`note` 를 보입니다. 같은 값을 쓰더라도 겹치면 거부합니다. 한 자리는 한 도구만 맡습니다.
- **원래 롬을 쓰는데 `orig` 가 없음**: 원래 롬(파일 `0`~`17FFFF`)을 쓰는 쓰기에는 `orig` 가 있어야 합니다. 다른 세션이 이미 고친 자리나 주소를 잘못 짚은 경우를 잡기 위해서입니다. 아래 「빈 자리 지도」 안을 쓸 때만 `orig` 를 빼도 됩니다.
- **`orig` 가 원래 롬과 다름**
- **CPU 주소 쓰기가 뱅크를 넘음**: `BB:AAAA` 로 준 쓰기는 한 뱅크(`8000`~`FFFF`) 안이어야 합니다. 뱅크를 넘는 큰 자료는 `0x` 파일 위치로 줍니다.
- **롬 크기 밖**: 늘린 크기에서 CPU 로 보이지 않는 자리, 그리고 원래 롬과 늘린 자리에 걸친 쓰기.
- **머리**: `00:FFB0`~`FFFF`(파일 `7FB0`~`7FFF`)는 빌더가 씁니다(롬 크기 `7FD7`, 체크섬 `7FDC`~`7FDF`).

빌더가 하는 일은 이렇습니다. 먼저 롬을 늘립니다(`dq5hangul.py expand` 와 같은 방식이라 늘린 뱅크마다 첫 8바이트에 표지 `DQ5X`+뱅크가 들어감). 다음으로 모든 쓰기를 넣고 체크섬을 고칩니다. 마지막으로 원래 롬(1.5MB) 기준 IPS 를 만들고(`kr_patch.ips.make` 의 레코드에서 같은 바이트가 16개 넘게 이어지는 곳을 RLE 레코드로 바꿈), 그 IPS 를 원래 롬에 다시 붙여 같은 롬이 되는지 확인합니다. 새 뱅크 첫 8바이트의 표지 위에는 써도 됩니다.

### 롬 전체를 내는 도구

`dq5hangul.py retree` 처럼 롬 전체를 내는 도구는 `fromrom` 으로 패치 목록을 만듭니다. 원래 롬을 같은 크기로 늘린 것과 견주어 다른 곳을 쓰기로 바꾸고 원래 롬 자리에는 `orig` 를 채웁니다. 4바이트 안쪽으로 떨어진 다른 곳은 한 쓰기로 묶고, 뱅크 경계에서 자릅니다. 1KB 가 넘는 쓰기는 옆에 `.bin` 파일로 둡니다. 머리는 견주지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc fromrom work/hangul/retree.sfc --name retree \
    -o work/build/retree.dq5patch.json
```

`retree` 롬(2MB)을 이렇게 바꾸면 쓰기 13개, 146,209바이트가 나왔습니다. 그것만 넣어 `build` 한 롬은 `retree` 롬과 바이트까지 같았습니다.

### 게임 데이터 표 `dq5tables/1`

`sfc/dq5/tools/dq5tables.py` 는 [dq5-data-format.md](dq5-data-format.md) 의 고정 크기 표를 필드 이름이 붙은 JSON 으로 내보내고, 고친 JSON 을 패치 목록으로 바꿉니다. 표의 항목 수는 늘리지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc export -o work/tables/dq5.json
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc patch work/tables/edit.json -o work/build/tables.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc check work/tables/edit.json
```

```json
{"format": "dq5tables/1",
 "monsters": [{"id": "00", "HP": 300, "경험치": 777, "내성": "000000000103300000"}],
 "items": [{"id": "06", "가격": 30, "장비사람": "10100110"}]}
```

| 표 | 자리 | 항목 | 필드 |
| --- | --- | --- | --- |
| `monsters` | `23:8000` + n×25 | 236 | `HP` `MP` `민첩` `공격` `수비` `경험치` `금화` `행동수` `재생` `첫상태확률` `첫상태종류` `드롭률` `드롭` `f68` `f69` `대상고정` `피하기` `동료확률` `동료종류` `행동1`~`행동6` `내성`(내성 종류 `50`~`61` 의 단계 0~3 을 18자리로) |
| `items` | `23:B081` + k×D8 + n, `23:B669` + n×2 | 216 | `가격` `가격배수` `k1b2` `팔수없음` `가득창` `쓰면없어짐` `필드대상창` `사용메시지없음` `칸` `저주` `그룹무작위` `적쪽` `전투대상창` `상점전투설명` `인파스설명` `인파스가격줄` `인파스횟수줄` `k4하위` `인파스장비줄` `인파스종류` `힘` `장비사람` `장비몬스터` |
| `spells` | `26:8765` + n, `26:8865` + n×2 | 171 | `MP`(원값: `1F` 없음, `1E` = 36, `1D` = 남은 MP 전부) `범위` `적쪽` `대상루틴` |
| `amounts` | `27:8071` + n×2 | 64 | `바탕`(`FE` = 300) `폭`. 게임은 주문 처리 루틴의 `LDA #` 번호 & 3F 로 읽으므로 64칸을 모두 내보내지만, 처리 루틴이 쓰지 않는 번호는 뜻이 없습니다(`dq5spell.py` 의 `양` 이 쓰는 번호) |
| `companions` | `23:AED1` + n×9 | 42 | `레벨` `최대레벨` `HP` `MP` `장비갈래` |

- 값은 정수이고, `드롭`·`동료종류`·`행동n`·`대상루틴` 은 16진 문자열, `장비사람`·`장비몬스터` 는 2진 문자열(왼쪽이 높은 비트)입니다. 필드의 뜻과 근거는 [dq5-data-format.md](dq5-data-format.md) 의 같은 이름 절을 봅니다.
- 입력에는 고칠 항목·필드만 적어도 됩니다. 적지 않은 필드와 어느 필드도 차지하지 않는 비트(몬스터 바이트11 bit0-5 등)는 롬 값 그대로 남습니다. `_이름` 처럼 `_` 로 시작하는 키와 모르는 키는 읽지 않습니다.
- 값이 필드 비트 수를 넘으면 거부합니다(HP 는 11비트라 2,047 까지). 두 입력이 같은 바이트를 다른 값으로 고쳐도 거부합니다.
- 패치 목록에는 롬과 다른 바이트만 들어가고, 이어진 바이트는 쓰기 하나로 묶으며 모두 `orig` 를 채웁니다. `check` 는 패치를 붙인 롬을 다시 읽어 적은 값이 그대로 나오는지 봅니다.

확인한 것:

- 내보낸 JSON 을 그대로 다시 넣으면 바뀐 바이트가 0개였습니다. 내보낸 값은 읽기 도구 `dq5monster.py`(236종의 필드·내성·행동)·`dq5item.py`(216개)·`dq5spell.py`(171개)와 하나도 다르지 않았습니다.
- 다섯 표의 첫·둘째·마지막 항목에서 필드마다 0 과 최댓값을 넣고 다시 읽자 354번 모두 그 필드만 바뀌었습니다.
- スライム(`00`)을 고친 롬을 빌더로 만들어 슬라임 셋 이벤트 전투(handoff 의 전투 재현)를 했습니다. `HP` 300 이면 전투 슬롯 `7E:07C0 + 슬롯*16 + 2` 가 셋 모두 `2C 01` 이었습니다(바이트10 의 위 비트까지 들어감). `HP` 1·`경험치` 777 이면 「それぞれ 2331ポイントの けいけんちを かくとく！」, `경험치` 0·`금화` 600 이면 소지금(`7E:2019`)이 20 → 1,820 이었습니다(바이트8 bit2-3 의 위 비트까지).

### 성장·조우·상점 `dq5progress/1`

`sfc/dq5/tools/dq5progresswrite.py`는 성장 53개, 조우 구역 85개, 상점 48목록, 메달·코인 교환 값 6개씩을 편집합니다. 목록·필드를 생략하면 원래 값을 유지합니다. 바뀐 레코드만 `orig`를 포함한 패치 목록으로 냅니다. 일반 물건 가격은 기존 `dq5tables.py`의 `items`로 고칩니다.

```sh
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc dump -o work/progress.json
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc patch work/progress.json -o work/progress.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc check
```

```json
{"format":"dq5progress/1",
 "growth":[{"kind":"person","index":0,"exp2":8}],
 "encounters":[{"index":1,"slots":[{"index":5,"monster":3,"weight":7,"count_code":0}]}]}
```

`growth`의 `kind`는 `person`(11종)·`monster`(42종), `index`는 종류 안 번호입니다. 레코드는 16진 `50`, 즉 80바이트입니다. `breaks`는 꺾이는 레벨 최대 7개, `exp2`는 레벨 2의 누적 경험치, `multipliers`는 구간별 배수 바이트(`breaks` 수+1개)입니다. `stats`의 키는 `hp`·`mp`·`strength`·`agility`·`wisdom`·`luck`·`resilience`이며, 각 배열에 레벨 1·꺾이는 레벨들·레벨 99의 저장값을 적습니다. HP·MP는 레벨 1을 제외한 저장값의 두 배가 실제 값입니다.

꺾임 수를 바꾸면 배수와 능력치 일곱 배열을 모두 지정해야 합니다. 새로 바꾼 꺾임은 2~99에서 엄격한 오름차순, 새 능력치 곡선은 실제 값 기준 비감소여야 합니다. 원본의 중복 꺾임이나 감소 곡선을 수정하지 않는 경우는 그대로 보존합니다. 활성 값 밖의 빈 칸도 원본에서 유지합니다.

`encounters`는 `index` 0~84로 고릅니다. `slots`는 일반 몬스터 칸 0~9 중 고칠 칸만 적으며 `weight`·`count_code`는 각각 0~7, `monster`는 0~235입니다. 마지막 칸 10은 `fixed`의 `weight`(0~7)·`group`(0~8)으로 따로 고칩니다. `species_weights`는 여러 종 무리의 종 수 무게 셋(각 0~3), `rate_index`는 조우 확률 계수 색인(0~7), `flag_1000`은 2비트, `flag_1010`·`fixed_night_only`는 bool입니다. 모든 칸의 무게가 0이거나 여러 종을 뽑는데 종 수 무게가 모두 0이면 거부합니다. 원시 비트가 겹치는 칸도 다른 필드의 비트는 보존합니다.

`shops`는 `kind`(0 도구·1 방어구·2 무기·3 잡화)와 종류 안의 `index`로 고릅니다. 종류별 목록 수는 11·15·17·5개입니다. `items`는 원래와 같은 수의 물건 번호(0~215)여야 합니다. `key`를 적었다면 원래 값과 같은지 확인하며 키·순서·품목 수·종료 `FF`는 바꾸지 않습니다. 같은 키라도 이야기 플래그나 주인공 자리로 다른 목록을 고르기 때문입니다. `medal_prices`와 `coin_prices`는 각각 여섯 값이고 범위는 0~255·0~16,777,215입니다.

숫자는 JSON 정수이며 모르는 필드·잘못된 타입·중복 식별자는 오류입니다. 원본 전체를 내보내 다시 인코딩한 6,510바이트가 모두 같았고, 그대로 패치하면 쓰기는 0개였습니다. 게임에서는 수정한 성장 표로 레벨업한 능력치·다음 경험치, 던전 보행 조우의 몬스터·마릿수, 상점 품목 여섯 개와 가격을 확인했습니다. 일반 가격 둘은 `dq5tables.py`로 바꾸어 상점 계산 결과까지 대조했습니다([일지](../journal/2026-10-26-55-progresswrite.md)).

`MESENCE`를 설정한 뒤 다음 명령으로 레벨업·조우·상점 검사를 다시 돌립니다. 결과와 실행별 로그는 출력 폴더 아래 새 하위 폴더에 남습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5progresscheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/progresscheck
```


### 실내 맵 레코드 `dq5map/1`

`sfc/dq5/tools/dq5mapwrite.py` 는 [dq5-map-format.md 「맵 레코드」](dq5-map-format.md#맵-레코드) 를 명령 단위 JSON 으로 풀고 다시 쌉니다. 실내 맵 346개와 그룹 `50` 이상 맵 18개를 모두 다룹니다.

```sh
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc check
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc dump 01 05 -o work/map/0105.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc patch work/map/0105.json -o work/build/map.dq5patch.json
```

```json
{
 "format": "dq5map/1",
 "map": "01/05",
 "kind": 1, "width": 68, "height": 60, "outside": 0, "zone": 0, "attr": 8, "bits": 12,
 "background_hi": 130, "background_lo": 206,
 "commands": [
  ["block", 904],
  ["fill", 50, 56, 66, 58],
  ["put", 42, 50],
  ["end"]
 ],
 "stream_tail": 0,
 "passes": [
  {"vertical": false, "flag_low": 0, "end_low": 8, "entries": [
    [1, 4, 66, 1, "long"]
  ]},
  …
 ],
 "junk": "800"
}
```

| 키 | 뜻 |
| --- | --- |
| `kind`~`background_lo` | 머리 9바이트(`+0`~`+8`) 그대로. `bits` 는 위치 비트 수 |
| `commands` | `["block", 블록 번호]`·`["put", x, y]`·`["fill", x0, y0, x1, y1]`·`["end"]`. 위치 `y*폭+x` 가 `bits` 비트에 들어가야 함. 마지막은 `end` |
| `passes` | 속성 패스 1·2·3. `vertical` 은 반복 방향, `entries` 는 `[x, y, 칸 수, 값 니블, 꼴]`. 꼴 `one` 은 1칸, `short` 는 2~17칸, `long` 은 2~257칸 |
| `stream_tail`·`flag_low`·`end_low`·`junk` | 게임이 읽지 않는 비트(비트스트림 끝의 남은 비트, 패스 머리 바이트 아래 7비트, 끝 바이트 아래 6비트, 아무도 읽지 않는 니블). 원래 레코드와 바이트까지 같게 싸려고 담음. 빼면 0 |

- `patch` 는 새 레코드를 늘린 롬의 `--at`(기본 `30:8000`)부터 차례로 놓고 맵 포인터(그룹 목록 `0F:8ED7`, 그룹 `50` 이상은 `1F:CEB6`)의 24비트를 바꿉니다. 레코드는 파일 위치(`0x…`)로 써서 뱅크를 넘어도 됩니다(게임 리더 `01:AC66` 이 `FFFF` 에서 다음 뱅크로 넘어감). `rom_size` 는 놓은 끝에 맞춰 2·3·4 를 적습니다.
- `--in-place` 는 원래 자리에 덮습니다. 원래 레코드보다 길면 거부합니다.
- `map`은 `GG/MM` 형태의 두 자리 16진 번호이며 원본 목록에 있는 맵만 받습니다. 새 맵 번호를 추가하지는 않습니다. `dump`도 목록 밖 번호를 거부합니다.
- 최상위 필드는 `format`, `map`, 머리 9개, `commands`, `passes`, `stream_tail`, `junk`만 받습니다. `exits` 같은 다른 필드는 무시하지 않고 오류로 끝냅니다. 출구 목적지·인물 목록은 이 맵 레코드에 포함되지 않습니다.
- 속성 패스의 니블 위치는 게임 리더를 그대로 따릅니다. 게임 리더의 상태(주소, 반 바이트)를 니블 위치 q 로 보면 패스 머리는 `N[q]` 의 bit3 이고, 이어 읽는 바이트·니블은 `N[q+1]` 부터입니다. 그래서 패스 2·3 의 머리 니블은 앞 패스의 끝 바이트 아래 니블과 겹칠 수 있고(그때는 `flag_low` 가 없음), 머리 다음 니블은 아무도 읽지 않습니다.
- 레코드는 마지막으로 읽힌 니블이 든 바이트까지입니다. 20/03·31/04·31/05 세 맵은 패스 3 끝 바이트의 아래 니블이 다음 맵 머리 첫 바이트와 같은 바이트라 레코드가 1바이트 겹칩니다(게임은 그 니블을 보지 않음).

확인한 것:

- `check`: 364개 맵을 풀고 다시 싸자 233,794바이트 모두 원래 롬과 같았습니다. 레코드 끝은 다음 맵 시작과 맞닿았고(겹치는 세 곳 빼고), `dq5map.py` 디코더가 속성 패스를 끝낸 자리와도 같았습니다.
- 01/05 를 고치지 않고 `30:8000` 으로 옮긴 2MB 롬과, 끝에 `["block", 774], ["put", 4, 2], ["block", 356], ["fill", 8, 2, 13, 5]` 를 더해 옮긴 롬을 만들었습니다. 배 사다리 순간이동으로 들어가 `01:BA4C`(속성 패스 끝)에서 WRAM 을 덤프하자, 옮기기만 한 롬은 셀 버퍼가 원래 롬과 같았고, 고친 롬은 셀 28칸이 달라졌으며 `dq5map.py --compare` 가 두 롬 모두 0바이트 차이였습니다. 화면에도 더한 붉은 바닥과 벽 조각이 보였습니다.

### 블록 배치 목록 `dq5mapsrc/1`

배치 명령을 손으로 적는 대신, 블록을 놓을 자리를 칠하는 순서대로 적으면 `sfc/dq5/tools/dq5mapcompile.py` 가 put·block·fill 명령으로 바꿉니다. 새 맵을 그릴 때는 이 목록을 씁니다.

```sh
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc extract 01 05 -o work/map/0105.src.json
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc compile work/map/0105.src.json -o work/map/0105.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc patch work/map/0105.json -o work/build/map.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc check
```

```json
{
 "format": "dq5mapsrc/1",
 "map": "01/05",
 "kind": 1, "width": 68, "height": 60, …, "background_hi": 130, "background_lo": 206,
 "placements": [
  [50, 56, 904],
  [52, 56, 904],
  [4, 2, 774]
 ],
 "passes": [ … dq5map/1 과 같음 … ]
}
```

- `placements` 는 `[x, y, 블록]` 을 칠하는 순서대로 적습니다. 블록은 원점(왼쪽 위)부터 블록 폭×높이 셀을 덮고, 뒤 배치가 앞 배치를 덮습니다. 머리의 배경 블록(`background_hi` bit7)은 모든 배치보다 먼저 맵 전체를 칠합니다.
- `extract` 는 기존 맵의 명령을 펼쳐(fill 은 게임처럼 원점마다) 이 목록으로 만듭니다. 머리와 속성 패스는 그대로 옮깁니다.
- `compile` 이 순서를 고르는 법: 셀마다 배치가 쓰는 단위(`+1` 플래그, 아래층 `+2`~`+4`, 위층 `+5`~`+7`)를 보고 끝까지 남는 단위가 하나도 없는 배치는 버립니다. 남은 배치끼리는 같은 단위를 쓰는 앞뒤만 지키고, 지금 칠할 수 있는 배치가 가장 많은 블록을 골라 한 묶음으로 냅니다. 묶음은 블록 크기 간격의 직사각형(원점 3개 이상)을 fill, 나머지를 put 으로 냅니다. 버린 배치 자리는 그것을 덮을 배치가 아직 나오지 않았고 같은 묶음에도 없을 때만 직사각형을 메우는 데 씁니다.
- CHR 의 VRAM 슬롯은 블록을 처음 쓰는 순서대로 받으므로(`01:8C15`), 명령 순서가 바뀌면 셀 버퍼의 타일 워드 값(슬롯 번호)은 원래와 달라도 그림은 같습니다. `check` 는 슬롯을 CHR 번호로 되돌려 견줍니다.

확인한 것:

- `check`: 364개 맵을 `extract` → `compile` 해 새 레코드로 풀자 셀 버퍼(슬롯을 CHR 로 되돌린 것)가 모두 원래와 같았고, 쓰는 슬롯이 늘어난 맵도 없었습니다. 레코드는 233,794바이트에서 249,471바이트로 6.7% 컸습니다(사람이 겹쳐 놓은 큰 fill 을 다 되살리지 못함).
- 01/05 를 `extract` 한 목록 그대로, 그리고 블록 7개(`[4, 2, 774]` 와 블록 356 의 2×3 격자)와 속성 패스 엔트리 셋을 더한 목록을 각각 컴파일해 `30:8000` 에 놓았습니다. 두 롬 모두 `01:BA4C` 의 게임 셀 버퍼가 `dq5map.py --compare` 와 0바이트 차이였습니다. 더한 엔트리는 게임에서도 패스 1 `(10,6)` 의 `+1` 아래 니블 1 → 5, 패스 2 세로 3칸 `(20,6)`~`(20,8)` 의 `+1` 에 `40`, 패스 3 세로 4칸 `(30,10)`~`(30,13)` 의 `+0` 위 니블 3 으로 들어갔습니다.

### 필드 세계 지도

`sfc/dq5/tools/dq5fieldwrite.py` 는 세계(`$1949` = 0·1·2)마다 256×256 칸의 블록 번호(0~510)를 [dq5-field-format.md 「불러오기」](dq5-field-format.md#불러오기-01a5c2) 의 RLE 두 덩어리(지도 하위 8비트 64KB, 9번째 비트 8KB)로 싸서 늘린 롬에 놓습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc dump 0 -o work/field/w0.bin
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc patch --world 0 work/field/w0.bin -o work/build/field.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc check
```

- 지도 파일은 칸 `y*256+x` 순서로 16비트 리틀 엔디언 블록 번호를 둔 131,072바이트입니다. 세계 1·2 도 256×256 이고 게임은 왼쪽 위 128×128 만 씁니다.
- 불러오기 루틴(`01:A5C2`·`A5F1`·`A620`)은 덩어리마다 `LDA #뱅크 / STA $4374 / PHA / PLB / LDX #주소 / JSR $A64F` 입니다. `patch` 는 덩어리를 `--at`(기본 `34:8000`)부터 놓고 이 두 즉값(`orig` 포함)을 바꿉니다. `01:A64F` 는 덩어리를 DMA 원본(16비트 주소 + 뱅크)으로 읽으므로 덩어리 하나가 뱅크를 넘으면 다음 뱅크 `8000` 으로 옮겨 놓습니다.
- 배치 영역은 `30:8000`~`3F:FFFF` 안이어야 합니다. 실행 커버리지에서 `01:A5D1`의 `PLB` 뒤 `01:A668`·`A673`이 `$00A5`, `01:A656`·`A660`·`A66C`이 `$4371`·`4375`·`4372`, `01:A67D`가 `$420B`를 접근하는 것을 확인했습니다. 자료 뱅크를 DB에 넣은 채 이 주소들을 쓰므로 WRAM·I/O 미러가 없는 `40`~`7D` 뱅크로 옮기면 정상 실행되지 않습니다. 도구는 시작 주소와 모든 덩어리의 끝을 검사합니다.
- RLE 는 같은 값 3개 이상을 반복(최대 128), 나머지를 글자 그대로(최대 128) 냅니다. 원래 덩어리와 크기가 조금 다릅니다(세계 0 지도 25,868 → 25,958바이트, 9번째 비트는 같음).

확인한 것:

- `check`: 세 세계 여섯 덩어리를 다시 싸서 풀면 모두 원래와 같았습니다.
- 세계 0 을 고치지 않고 옮긴 2MB 롬과, 블록 (172~176, 25~28) 을 블록 307(9번째 비트가 켜진 언덕)으로 칠한 롬을 만들었습니다. `dq5warp.lua` `FIELD=341,56` 으로 필드에 서서 `00:8090` 에서 WRAM 을 덤프하자 두 롬 모두 `7F:0000`·`7E:E000` 이 입력 지도와 바이트까지 같았고, 고친 롬은 주인공 오른쪽의 산이 언덕으로 바뀌어 보였습니다.

세 세계를 함께 `34:8000`부터 다시 배치한 롬에서는 세계마다 지도 65,536바이트·상위 비트 8,192바이트, 합계 73,728바이트가 게임 WRAM과 같았습니다. `60:8000`에 배치한 대조 롬은 세 세계 모두 화면이 꺼진 채 멈췄고 WRAM도 달랐습니다.

### 필드 블록·입구 표 `dq5fieldtables/1`

`sfc/dq5/tools/dq5fieldtables.py` 는 고정 크기 표를 내보내고 고친 필드만 원래 자리에 씁니다. 항목 수·순서·종료 표지를 유지합니다. 패치 목록에는 바뀐 5바이트 항목만 넣고 `orig`로 원래 값을 확인합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc dump -o work/fieldtables.json
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc patch work/fieldtables.json -o work/fieldtables.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc check
```

```json
{"format":"dq5fieldtables/1",
 "blocks":[{"index":307,"lower":[1,2,257,258]}],
 "entrances":[{"table":"main","index":0,"group":2}],
 "arrivals":[{"group":2,"x":10,"y":20,"layer":1}]}
```

목록이나 필드를 생략하면 원본 값을 보존합니다. 숫자는 모두 JSON 정수입니다. 위 예는 블록 307의 아래층 네 타일, 일반 입구 첫 항목의 그룹, 그룹 2의 도착 자리·층을 바꿉니다. 실제 목적지의 바닥과 도착 층이 맞는지는 게임에서 확인해야 합니다.

| 목록 | 식별자·범위 | 편집 필드 |
| --- | --- | --- |
| `blocks` | `index` 0~510 | `lower`·`upper`: 왼위·오위·왼아래·오아래 타일 번호 4개, 각 0~511 |
| `entrances` | `table`은 `main` 또는 `aux`, `index`는 각각 0~46·0~13 | `group`: `00`~`35` 또는 `50`~`54`(16진 범위), `x`·`y`: 0~511 |
| `arrivals` | `group` 0~53(`00`~`35`) | `map`: 0~31, `x`·`y`·`layer`: 바이트, `world_code`: 0~3, `wagon`: bool, `direction`: 0~3, `party_overlap`: bool, `map_flags`: 0~31 |

- 블록의 다섯째 바이트 하위 니블은 뜻을 확인하지 못했으므로 원본 그대로 보존합니다. 블록 번호 511은 다음 표 또는 압축 지도와 겹쳐 거부합니다.
- 같은 그룹의 입구가 여럿이므로 그룹 번호가 아닌 목록 안의 `index`로 고칩니다. 두 입구 표의 끝 `FF`를 바꾸거나 항목을 늘리지 않습니다.
- 도착 `world_code`는 롬의 원시 2비트 값입니다. 1·2·3은 세계 0·1·2이며 원본의 0도 보존합니다. `wagon`은 첫 바이트 bit7, `party_overlap`은 마지막 바이트 bit7, `map_flags`는 마지막 바이트 bit2~6입니다.
- 특수 그룹 `50`~`54`와 좌표별 예외는 게임의 별도 코드가 처리합니다. 입구 그룹을 바꾸어도 이 코드를 다시 쓰지는 않습니다.
- 알 수 없는 필드·잘못된 타입·중복 식별자·범위 초과는 오류입니다. 원본 전체를 내보냈다가 패치하면 쓰기가 0개입니다.

블록 1,022항목·입구 61항목·도착 54항목, 합계 5,685바이트를 다시 인코딩해 원본과 같았습니다. 블록 양층·일반/보조 입구·도착 표를 고쳐 빌더에 넣은 뒤 기존 읽기 도구로 다시 확인했습니다.

게임에서는 블록 양층의 BG 타일맵 8,192바이트가 예측과 같았고, 일반·보조 입구를 실제 걸어 바꾼 도착 맵·좌표·층·방향에 섰습니다. 마을에서 나오는 필드 좌표도 맞았습니다. `dq5fieldtablecheck.py`가 이 보행과 세계 지도 검사를 재현합니다([일지](../journal/2026-10-26-54-fieldtables.md)).

### 보행 대사 일괄 쓰기 `dq5text/1`

`sfc/dq5/tools/dq5textwrite.py`는 보행 메시지 3,200개를 코드 목록으로 내보내고, 고친 항목을 반영해 허프만 트리·메시지 전체를 다시 만듭니다. 원래 글꼴과 메시지 번호를 유지하며 새 글꼴·전투 메시지·창·이름 표는 편집하지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc export -o work/messages.json
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc patch work/messages.json -o work/text.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc check work/messages.json
```

```json
{"format":"dq5text/1", "messages":[{"id":297,"codes":[4102,0,4097]}]}
```

`id`는 0~3199의 정수입니다. `codes`에는 글자·제어 코드 정수를 순서대로 적습니다. 예제는 메시지 `129`를 `{1006}`·글자 `000`·끝 `{1001}`로 바꿉니다. 글자는 기존 코드 `000`~`3DA`, 제어는 `1000`~`101D`·`1100`~`1118` 범위입니다(범위 설명은 16진수, JSON 예는 10진수). 끝 코드 `1001`·`1010`·`1018` 중 하나가 마지막에 한 번만 있어야 합니다. 이름·숫자 변수에 필요한 인자는 원래처럼 부르는 코드가 대기열에 넣어야 합니다.

- 적지 않은 메시지는 원본 그대로 유지합니다. 빈 `messages` 배열이면 원본 전체를 다시 부호화합니다. `check`에 입력 파일을 빼도 같은 원본 재압축 검사를 합니다.
- 문자열을 글자 코드로 바꾸는 번역 편집기 기능은 없습니다. 원본 `export`의 코드 목록을 편집하는 단계입니다. 새 한글 글꼴 추가와 함께 쓰려면 글꼴·코드 배분을 별도로 설계해야 합니다.
- `patch --at BB:AAAA`의 기본 위치는 `38:8000`입니다. 보행 디코더 사본·마스크·트리는 한 뱅크에, 메시지는 그 뒤에 이어 놓습니다. 허용 뱅크는 `30`~`3F`이고 모든 자료가 `3F:FFFF` 안에 들어가야 합니다. 다른 도구와 같은 자리를 쓰면 빌더가 거부합니다.
- 원본 쪽에서는 색인, 보행 디코더 호출, 보행 색인 호출과 훅만 바꾸고 `orig`를 기록합니다. 전투 호출은 바꾸지 않습니다. 패치의 최소 롬 크기는 2MB이며 다른 패치와 합쳐 3·4MB로 빌드할 수도 있습니다.
- 중복 번호, 잘못된 타입·코드·끝 코드, 디코더·트리의 뱅크 초과, 전체 배치 초과는 거부합니다. 입력은 원본 롬이어야 합니다.

원본 3,200개·163,649코드를 재압축해 빌더에 넣은 뒤 새 디코더의 트리·색인을 따라 풀자 모두 같았습니다. 메시지 두 개를 바꾼 검사에서는 두 개만 입력대로 바뀌고 나머지 3,198개가 그대로였습니다. 기존 한글 실험용 `retree`도 같은 결과를 유지했습니다.

게임에서도 원본·원문 재배치·수정·뒤쪽 뱅크 메시지의 디코더 반환 64코드를 각각 비교해 일치했습니다. 뒤쪽 메시지는 `3C:B1BE`에서 읽혔습니다([일지](../journal/2026-10-26-56-textwrite.md)).

`MESENCE`를 설정한 뒤 다음 명령으로 게임 검사 4건을 재현합니다. 실행마다 새 출력 폴더에 `results.json`과 디코더 기록·화면을 남깁니다.

```sh
uv run --locked python sfc/dq5/tools/dq5textcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/textcheck
```


### 이벤트 스크립트 `dq5event/1`

`sfc/dq5/tools/dq5eventwrite.py` 는 [이벤트 명령](dq5-event-format.md)을 JSON으로 내보내고, 편집한 명령을 확장 뱅크에 놓습니다. `patch` 는 `binding` 으로 지정한 표 항목만 바꿉니다.

```sh
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc dump --number 41 -o work/event.json
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc patch work/event.json -o work/event.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc check
```

명령의 `op` 는 두 자리 16진 문자열이고 `args` 는 바이트 정수 목록입니다. 메시지 번호와 네이티브 주소도 롬에 쓰는 순서인 하위 바이트부터 적습니다. `C3` 점프만 `args` 대신 `target` 에 24비트 CPU 주소 정수 또는 명령의 `label` 을 적습니다.

```json
{"format":"dq5event/1", "binding":{"kind":"number","index":65},
 "commands":[{"op":"10","args":[37,16]}, {"op":"FF"}]}
```

이 예는 번호 `41` 의 스크립트를 플래그 `7E:21B5` 에 `10` 을 OR하고 끝내는 명령으로 바꿉니다. `binding.index` 는 정수이므로 65가 번호 `41` 입니다. CLI의 `--number` 는 16진수, `--event` 는 0~9의 이벤트 번호입니다. `binding.kind` 를 `event` 로 쓰면 이벤트 표 `23:E2C2` 의 `index` 항목을 바꾸고, `x`·`y` 로 목표 좌표도 지정할 수 있습니다. 좌표를 빼면 원래 값을 보존합니다.

- `dump 주소` 는 임의 시작점을 읽지만 표 연결을 고르지 않습니다. `patch` 하려면 `binding` 을 넣어야 합니다.
- `encode 입력 -o 출력.bin --at 60:8000` 은 패치 목록 없이 명령 바이트만 만듭니다. 내부 라벨을 쓰면 배치 주소가 필요합니다.
- `patch` 의 기본 위치는 `60:8000` 이며 4MB 롬을 만듭니다. `--at` 으로 바꿀 수 있고, 스크립트 하나가 뱅크 끝을 넘으면 다음 뱅크 첫머리에 놓습니다.
- 같은 주소를 가리키는 다른 표 항목이나 스크립트 중간을 가리키는 항목은 그대로 둡니다. 코드 안에 직접 적힌 주소, 계산해서 만든 주소, 외부 주소로 적은 `C3` 대상도 자동으로 고치지 않습니다.
- 마지막 명령은 `FF` 또는 `C3` 여야 합니다. 모르는 명령, 인자 수·값 범위 오류, 정의하지 않은 라벨, 한 뱅크보다 긴 코드는 거부합니다.
- 번호 `1A`·`1B`·`1C`·`3C` 는 원본에서 코드를 가리키므로 `dump` 는 거부합니다. 새 명령을 작성해 그 표 항목을 지정하는 것은 별개입니다.

### 인물 스크립트 `dq5npcscript/1`

`sfc/dq5/tools/dq5npcwrite.py` 는 [인물 인라인 명령](dq5-map-format.md#인라인-스크립트-01c800)을 편집합니다. 인물 목록의 뱅크와 레코드 경계를 유지하기 위해 기존 슬롯 안에서만 패치합니다. 더 긴 스크립트는 `encode` 로 바이트를 만들 수 있지만 목록에 넣거나 재배치하는 기능은 아직 없습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc dump 05:A84F -o work/npc.json
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc patch work/npc.json -o work/npc.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc encode work/npc.json -o work/npc.bin
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc check
```

`address` 는 첫 명령 주소가 아니라 **길이 바이트 주소**입니다. 선실 파파스는 `05:A84F` 에 길이 23이 있고 첫 명령이 `05:A850` 에 있습니다. `dump` 의 `references` 는 그 슬롯을 사용하는 인물 엔트리와 낮·밤을 보여 줍니다. 공유 슬롯을 바꾸면 참조하는 시간대 모두 바뀝니다.

```json
{"format":"dq5npcscript/1", "address":"05:A84F", "length":23,
 "commands":[
   {"op":"06","args":[15,1],"target":"on"},
   {"op":"2B","args":[5,13]}, {"op":"16"},
   {"op":"2B","args":[8,13],"label":"on"}, {"op":"16"}
 ]}
```

이 예는 플래그 `7E:219F` 의 bit0에 따라 인물을 (5,13) 또는 (8,13)으로 옮기고 멈춥니다. 명령의 `op` 는 두 자리 16진 문자열, `args` 는 바이트 정수 목록입니다. `03`·`06`·`07` 의 마지막 변위 바이트를 `target` 라벨로 바꿔 적을 수 있습니다. `03` 은 명령 주소+1, `06`·`07` 은 명령 주소에서 변위를 계산합니다. 변위는 −128~127이고 도착점은 스크립트 안의 명령 첫 바이트여야 합니다. `04` 절대 점프와 `05`·`37` 네이티브 주소는 원시 바이트 인자를 그대로 씁니다.

- `patch` 는 `address` 가 원본 인물 슬롯이고 `length` 가 원본 길이와 같은지 확인합니다. 길이 바이트를 유지하고 남는 부분은 `00`(그 자리)으로 채웁니다. 원본보다 길면 거부합니다.
- 바뀐 슬롯은 도달 가능한 명령 흐름이 슬롯 끝이나 명령 중간으로 넘어가는지 검사합니다. 외부 절대 점프·네이티브 호출의 동작까지 해석하지는 않습니다. 원본과 같은 패치는 원본의 끝 명령을 보존합니다.
- 모르는 명령, 인자 수·범위 오류, 중복·미정의 라벨, 잘못된 상대 분기를 거부합니다. 길이 바이트 한계가 있어 새 명령 본문도 1~255바이트여야 합니다.
- `encode` 는 길이 바이트를 뺀 명령 본문만 내보냅니다. 롬에 쓸 때는 `patch` 와 빌더의 슬롯·원본 대조를 거칩니다.

### 스크립트 쓰기 검증

이벤트 시작점 106개(2,420바이트)와 연속 영역 86개(1,664바이트), 인물 고유 스크립트 1,034개(21,559바이트)를 JSON으로 내보내고 다시 인코딩해 원본과 모두 같았습니다. 이벤트 두 집합은 일부가 겹칩니다. 인물의 낮·밤 참조는 1,274개입니다.

MesenCE에서는 번호 표와 이벤트 표를 거쳐 `60:8000`의 플래그 변경·보행·종료 명령을 실행했습니다. 두 경우 모두 주인공이 (9,11)에서 (11,11)로 갔고 `7E:220F`에 `40`이 들어갔습니다. 인물은 `03`의 무조건 분기, `06`의 플래그 꺼짐·켜짐, `07`의 사각형 안·밖을 시험해 다섯 경우 모두 예상 좌표에 멈췄습니다. 이 확인은 시험용 명령의 실행 결과이며 모든 이야기 장면을 다시 돌린 것은 아닙니다.

재현은 [스크립트 쓰기 일지](../journal/2026-10-26-53-scriptwrite.md)에 있습니다.

### 인물 목록 재배치 `dq5npcrelocate/1`

`sfc/dq5/tools/dq5npcrelocate.py`는 스크립트 길이를 바꾸고 인물 목록을 확장 뱅크로 옮깁니다. 인물 수·순서·등장 조건과 낮밤 스크립트 공유 관계를 유지합니다. 기존 슬롯 안에서만 바꾸는 `dq5npcwrite.py`와 달리, 뒤따르는 레코드의 주소도 다시 계산합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc dump -o work/npc-lists.json
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc patch work/npc-lists.json \
  -o work/npc-lists.dq5patch.json --report work/npc-layout.json
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc check
```

입력의 `format`은 `dq5npcrelocate/1`, `scripts`는 `{address, commands}` 배열입니다. `address`는 **원본 길이 바이트**의 CPU 주소 문자열(`05:A84F` 등)이고, `commands`는 `dq5npcscript/1`과 같은 명령 목록입니다. 입력에서 빠진 스크립트는 원본을 유지합니다. 빈 배열이면 내용을 바꾸지 않고 목록만 옮깁니다.

- 새 스크립트는 1~255바이트이며, 바뀐 명령의 상대 분기를 새 주소에서 검사합니다. 명령 `04`의 절대 점프는 지원하지 않습니다.
- 기본 `--base 32:8000`에는 그룹 포인터 54개와 기본 목록을, `--alt 33:8000`에는 대체 목록을 놓습니다. 두 목적지는 서로 다른 `30`~`3F` 뱅크여야 하고 각 덩어리는 한 뱅크 안에 들어가야 합니다. 최소 롬 크기는 2MB입니다.
- 원본 639목록·2,483인물 레코드·1,034스크립트를 유지하면 기본 20,173바이트·대체 23,986바이트입니다. 기본 로더의 뱅크·그룹 포인터 주소, 대체 로더의 뱅크와 선택 표 296항목의 목록 주소를 고칩니다. 원본 영역을 고칠 때는 `orig`를 확인합니다.

정한 규칙은 이렇습니다. 뱅크 끝에서 거슬러 0 이 이어지는 곳을 찾고, 그 시작에서 16바이트를 띄운 뒤 16바이트 경계로 올립니다. 그렇게 남은 길이가 32바이트 이상이면 빈 자리로 봅니다. 뱅크 `00` 은 끝에 머리·벡터가 있어 없습니다.

어떻게 확인했나:

- **0 줄 전부에 읽기·실행 감시**: 뱅크 안의 0 이나 FF 가 64바이트 넘게 이어지는 곳 32곳(뱅크 가운데 포함)에 읽기·실행 감시를 걸었습니다. 돌린 장면은 전원부터 8,000프레임(A 연타, 오프닝·이름 입력·배 선실), 그리고 선실 세이브스테이트에서 다섯 장면입니다(첫 필드 이벤트와 전투, 청년기 グランバニア 성, 필드 걷기와 명령 창, 탑 안). 뱅크 가운데 0 줄은 모두 읽혔습니다(`04:9750`, `2A:ADC4`·`B06F`·`B4B3`·`D712`, 필드 맵 자료). 그래서 빼고 뱅크 끝만 남겼습니다.
- **뱅크 끝의 첫 바이트**: 뱅크 끝 줄에서 읽힌 것은 `2F:FF86` 한 바이트뿐입니다(136프레임, `2B:C2C7` 이 소리 자료를 `$2143` 으로 보낼 때). 소리 자료를 두 바이트씩 보내다 끝을 한 바이트 넘겨 읽는 것으로 보입니다. 16바이트를 띄우는 까닭입니다.
- **위 22곳에 다시 감시**: 같은 여섯 장면에서 한 번도 읽히거나 실행되지 않았습니다.
- **채워서 켜기**: `build --fill-free 55` 로 22곳을 모두 `55` 로 채운 4MB 롬을 부팅 시험에 넣었습니다. 11개 프레임의 VRAM·CGRAM·OAM·WRAM 해시가 원래 롬과 모두 같았고, 6,500프레임에 17/00 에 닿았습니다.
- **곡·효과음을 모두 틀며 감시**: 곡 자료(샘플 `2B:EB00`~, 시퀀스 `2E:E2E4`~`2F:FF85`)는 곡을 틀 때 CPU 가 롬에서 읽어 SPC 로 보냅니다. 곡 49개, 곡 갈래 6개, 효과음 갈래 137개를 `dq5spcfile.py --free-watch` 로 틀었습니다(곡 묶음의 샘플을 곡 전에 모두 보내게 함). 22곳의 읽기·실행은 192번 모두 0번이었습니다.
  감시가 걸리는지는 곡 `02` 의 시퀀스 첫 11바이트(`2E:E7A6`~)로 따로 보았습니다(`2B:C266` 이 11번 읽음). 늘 올려 두는 곡·샘플(`2B:C422`·`C429` 목록)은 전원을 켤 때 한 번 보내므로 위 8,000프레임 감시에 들어 있습니다. 그때 읽힌 것은 `2F:FF86`(시퀀스 `46` 의 끝 다음 바이트) 하나뿐입니다.
- **맵·전투·필드를 넓게 감시**: `dq5freesweep.py` 로 실내 맵 346곳(들어갈 칸은 `dq5mapmusic.entry_cells`, 들어가 상하좌우로 걷기)을 돌았습니다. 몬스터 236종마다 첫 필드 이벤트 전투(`BATTLE=XX:1`, A 12번), 필드 세계 0·1·2(`POKE 7E1949`, 세계 1·2 는 그 칸에서 걷지 못하고 지도만 그림)도 돌렸습니다. 22곳의 읽기·실행은 585번 모두 0번이었습니다.

### 늘린 롬

`dq5hangul.py expand` 의 실측(「[롬 확장](dq5-hangul-format.md#롬-확장)」)에 4MB 의 뱅크 `C0`~`FF` 를 더 재었습니다. 표지를 쓴 4MB 롬을 켜고 5프레임째에 CPU 주소를 읽었습니다.

| 크기 | 새로 생기는 자리(각 뱅크 `8000`~`FFFF`) | 파일 위치 | 크기 |
| --- | --- | --- | --- |
| 2MB | `30`~`3F` | `180000`~`1FFFFF` | 512KB |
| 3MB | `30`~`5F`(`60`~ 은 `40`~ 을 되풀이) | `180000`~`2FFFFF` | 1.5MB |
| 4MB | `30`~`7D`, `FE`·`FF` | `180000`~`3FFFFF` | 2.5MB |

- 4MB 롬에서 `C0:8000` 은 표지 `40`, `FD:8000` 은 `7D` 로 `40`~`7D` 의 거울입니다. `FE:8000`·`FF:8000` 은 표지 `7E`·`7F`(파일 `3F0000`·`3F8000`)입니다. `7E`·`7F` 는 WRAM 이라 이 두 뱅크는 `FE`·`FF` 로만 닿습니다.
- `40:0000` 은 0 이었습니다(파일 `200000` 의 표지가 보이지 않음). 뱅크 `40`~ 의 `0000`~`7FFF` 는 롬으로 쓰지 않습니다.

두 도구가 같은 새 뱅크를 잡으면 빌더가 겹침으로 거부합니다. 필드 지도 기본 `34:8000`은 `dq5hangul.py retree`의 메시지 영역과 겹칠 수 있으므로 함께 빌드할 때 `--at`으로 겹치지 않게 나눕니다. 그 전에 맡을 뱅크를 이 표에서 나눕니다. 처음 쓰는 세션이 자기 줄을 고쳐 PR 로 잡습니다.

| 뱅크 | 맡은 쪽 | 쓰임 |
| --- | --- | --- |
| `30`~`3F` | 텍스트(`dq5hangul.py retree` 가 `30`~ 을 씀) | 다시 부호화한 메시지·트리·디코더, 한글 글꼴 |
| `40`~`4F` | 그래픽 | 포팅한 인물·몬스터·타일 그림 |

| `78`~`7D`, `FE`·`FF` | 비움 | 위가 모자랄 때 |

## 부팅 시험

`dq5boottest.py 원래롬 만든롬` 은 두 롬을 `work/boot/` 에 시험 전용 이름(`dq5boot-orig.sfc`·`dq5boot-build.sfc`)으로 복사해 MesenCE testrunner 로 함께 돌립니다. Lua 는 `sfc/dq5/tools/lua/dq5boot.lua` 입니다. 전원을 켜 A 를 40프레임마다 4프레임씩 누릅니다. 600프레임마다(그리고 6,500) VRAM·CGRAM·OAM·WRAM 의 Adler 해시와 화면 PNG 를 남기고, 6,500프레임에 맵 번호를 읽습니다. 통과 조건은 둘입니다.

- 6,500프레임에 맵이 17/00(배 선실, 새 게임 첫 장면)
- 11개 프레임의 해시가 원래 롬과 같음. 글자·그림을 바꾼 롬이면 `--allow-diff` 로 첫 장면만 봄

같은 롬이 같은 결과를 내도록 두 가지를 맞춥니다.

- **RAM 을 0 으로 켜기**: 이 PC 의 MesenCE 설정은 `Snes.RamPowerOnState` = `Random` 입니다. 인자 없이 켜면 첫 프레임 WRAM 뒤쪽 64KB 가운데 65,274바이트가 0 이 아니었습니다. 시험은 MesenCE 인자 `--Snes.RamPowerOnState=AllZeros` 를 주어 그 실행만 0 으로 켭니다(첫 프레임 WRAM 합 0 확인).
- **새 SRAM**: MesenCE 는 롬 파일 이름마다 SRAM 파일(`<이름>.srm`)을 둡니다. 시험 전용 이름의 SRAM 파일을 돌리기 전에 지웁니다. 폴더는 환경 변수 `MESENCE_SAVES` 로 바꿀 수 있고, 기본은 macOS 의 MesenCE 설정 폴더 아래 `Saves` 입니다.

**화면 PNG 해시는 견주지 않습니다.** 같은 세이브스테이트에서 같은 롬을 네 번 함께 돌렸을 때 600프레임마다 찍은 VRAM·CGRAM·OAM·WRAM 해시는 네 번 모두 같았습니다. 그런데 같은 프레임의 PNG 는 여섯 장 가운데 네 장이 실행마다 달랐습니다(커서 깜빡임, 그리다 만 글자처럼 한 프레임 앞뒤 화면). 에뮬레이션은 같고 `emu.takeScreenshot` 이 찍는 프레임이 흔들리는 것이라, 화면 대신 화면을 만드는 메모리의 해시를 견줍니다.

| 시험한 롬 | 결과 |
| --- | --- |
| 아무것도 넣지 않은 4MB 롬 | 통과. 해시 11개 같음, 17/00 |
| 빈 자리 22곳을 `55` 로 채운 4MB 롬 | 통과. 해시 11개 같음, 17/00 |
| `retree` 롬을 `fromrom` → `build` 로 다시 만든 2MB 롬 | `--allow-diff` 로 통과. 17/00 에 닿고, 원래 롬과 다른 프레임 9개(메시지 디코더를 바꾼 롬이라 다를 수 있음, 까닭은 보지 않음) |

### 첫 장면 뒤(`--scenes`)

`--scenes 세이브스테이트` 를 주면 배 선실 세이브스테이트(`work/state/ship.mss`)에서 두 롬 모두 `dq5warp.lua` 로 세 장면을 더 돌립니다. Lua 는 `lua/dq5scenehash.lua` 입니다. 정한 프레임의 VRAM·CGRAM·OAM·WRAM 해시와 끝 상태(`warp.txt` 의 `end` 줄)를 견줍니다. 세이브스테이트에서 시작하므로 RAM 무작위 켜기와는 상관이 없습니다.

| 장면 | dq5warp 변수 | 해시 프레임 | 화면 |
| --- | --- | --- | --- |
| 필드 걷기 | `FIELD=174,110`, 왼·위·오른·아래 60프레임씩 | 600·660·720·780 | (174,110) → (167,103) |
| 전투 | `FIELD=341,56 BATTLE=00:1`, A 15번 | 600~1200 7개 | スライム 하나와 전투, 명령 창·공격 메시지 |
| 메뉴 | `FIELD=341,56`, A·아래·A·B·B | 580·620·660·700 | 명령 창 → つよさ 창 → 닫기 |
| 대화 | `TO=01/00,12,80,2`, 위·A 4번·B 2번 | 660·720·780·840 | 도구 가게 「はい いらっしゃいませ！…」·「お買い上げですね」·물건 창(보행 모드 메시지) |

빈 4MB 롬과 빈 자리를 채운 4MB 롬은 네 장면 모두 해시와 끝 상태가 원래 롬과 같았습니다. retree 4MB 롬은 걷기·전투·메뉴가 같았고, 대화는 네 프레임 모두 해시가 달랐습니다(메시지 디코더를 바꾼 롬). 끝 상태는 같아 `--allow-diff` 로 통과합니다. 글자를 바꾼 롬은 대화 장면에서 해시가 달라지는 것을 보고, 끝 상태로 흐름이 같은지만 봅니다.
음성 대조로 몬스터 레코드 `23:8002`(スライム) 한 바이트만 바꾼 롬을 넣었습니다. 전투 장면만 7개 프레임 가운데 6개가 달라 실패했고, 걷기·메뉴는 같았습니다.

### IPS 크기

늘린 자리는 거의 0 과 표지라, 같은 바이트가 16개 넘게 이어지는 곳을 RLE 레코드(크기 0, [횟수 2][값 1])로 씁니다. 빈 4MB 롬의 IPS 가 2,621,670바이트에서 1,785바이트로 줄었습니다. retree 를 넣은 4MB 롬은 147,158바이트입니다. 둘 다 `kr_patch.ips.apply` 로 원래 롬에 다시 붙여 같은 롬이 되었습니다.

## 남은 것

포팅 전체의 지원 범위와 통합 배치 문제는 [도구 점검](dq5-port-tool-audit.md)을 봅니다. 아래 목록만으로 전체 도구가 갖춰졌다고 판단하지 않습니다.

- 필드 표 항목 증설·재배치, 인물 수·순서·등장 조건 편집과 새 목록 추가.
- 문자열 번역 편집·새 한글 글꼴 대량 삽입, 전투 메시지·창·이름 표 쓰기.
- 성장·조우 레코드 수와 상점 품목 수 증설, 필드 조우 격자·실내 구역 연결·고정 무리·전투 이벤트 무리 쓰기.
- `dq5tables.py`의 물건 가격 쓰기는 상점에서 확인했습니다. 물건 힘과 전투 주문 MP도 추가 실측했습니다. 그 밖의 물건 플래그·주문 필드·피해량·동료 표 쓰기는 수정 롬의 게임 실측이 남아 있습니다.
