## 흐름

```
쓰기 도구 A ─┐
쓰기 도구 B ─┼─ *.dq5patch.json ─ dq5build.py build ─ work/build/dq5kr.sfc ─ dq5boottest.py
롬 전체를 내는 도구 ─ dq5build.py fromrom ─┘                      └ work/build/dq5kr.ips
```

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc build work/build/*.dq5patch.json --size 4 \
    -o work/build/dq5kr.sfc --ips work/build/dq5kr.ips
MESENCE=… uv run --locked python sfc/dq5/tools/dq5boottest.py rom/dq5.sfc work/build/dq5kr.sfc
```

## 입력 형식 `dq5patch/1`

쓰기 도구 하나가 파일 하나(`<이름>.dq5patch.json`)를 냅니다.

```json
{
  "format": "dq5patch/1",
  "name": "hangul-font",
  "rom_size": 4,
  "writes": [
    {"at": "24:9E02", "hex": "22 00 80 30 60", "orig": "08 8B 4B AB E2", "note": "디코더를 뱅크 30 으로"},
    {"at": "30:8000", "file": "hangul-font.000.bin", "note": "새 글꼴"},
    {"at": "0x180000", "hex": "00 01"}
  ]
}
```

| 키 | 뜻 |
| --- | --- |
| `format` | 늘 `dq5patch/1`. 형식을 바꾸면 숫자를 올립니다 |
| `name` | 오류·보고에 쓰는 이름. 세션·도구 이름 |
| `rom_size` | 이 목록이 바라는 롬 크기(MB, `2`·`3`·`4`). 빼면 늘리지 않음. 빌더는 목록들과 `--size` 가운데 가장 큰 값으로 늘림 |
| `writes[].at` | 쓰는 자리. `BB:AAAA`(LoROM CPU 주소, 뱅크 `00`~`7D`·`80`~`FF`, `AAAA` 는 `8000`~`FFFF`, 뱅크 `80` 부터는 거울) 또는 `0x` 로 시작하는 파일 위치 |
| `writes[].hex` | 쓸 바이트(16진, 띄어 써도 됨) |
| `writes[].file` | 쓸 바이트가 든 파일. JSON 파일과 같은 폴더 기준 상대 경로. `hex` 와 둘 중 하나만 |
| `writes[].orig` | 원래 롬의 그 자리 바이트(16진, 쓰는 길이와 같게). 빌더가 원래 롬과 대조함 |
| `writes[].note` | 설명. 겹침 오류에 함께 나옴 |

빌더가 거부하는 것:

- **겹침**: 두 쓰기(같은 목록이든 다른 목록이든)가 한 바이트라도 겹치면 거부합니다. 두 쓰기의 이름·주소·`note` 를 보입니다. 같은 값을 쓰더라도 겹치면 거부합니다. 한 자리는 한 도구만 맡습니다.
- **원래 롬을 쓰는데 `orig` 가 없음**: 원래 롬(파일 `0`~`17FFFF`)을 쓰는 쓰기에는 `orig` 가 있어야 합니다. 다른 세션이 이미 고친 자리나 주소를 잘못 짚은 경우를 잡기 위해서입니다. 아래 「빈 자리 지도」 안을 쓸 때만 `orig` 를 빼도 됩니다.
- **`orig` 가 원래 롬과 다름**
- **CPU 주소 쓰기가 뱅크를 넘음**: `BB:AAAA` 로 준 쓰기는 한 뱅크(`8000`~`FFFF`) 안이어야 합니다. 뱅크를 넘는 큰 자료는 `0x` 파일 위치로 줍니다.
- **롬 크기 밖**: 늘린 크기에서 CPU 로 보이지 않는 자리, 그리고 원래 롬과 늘린 자리에 걸친 쓰기.
- **머리**: `00:FFB0`~`FFFF`(파일 `7FB0`~`7FFF`)는 빌더가 씁니다(롬 크기 `7FD7`, 체크섬 `7FDC`~`7FDF`).

빌더가 하는 일은 이렇습니다. 먼저 롬을 늘립니다(`dq5hangul.py expand` 와 같은 방식이라 늘린 뱅크마다 첫 8바이트에 표지 `DQ5X`+뱅크가 들어감). 다음으로 모든 쓰기를 넣고 체크섬을 고칩니다. 마지막으로 원래 롬(1.5MB) 기준 IPS 를 만들고(`kr_patch.ips.make` 의 레코드에서 같은 바이트가 16개 넘게 이어지는 곳을 RLE 레코드로 바꿈), 그 IPS 를 원래 롬에 다시 붙여 같은 롬이 되는지 확인합니다. 새 뱅크 첫 8바이트의 표지 위에는 써도 됩니다.

### 롬 전체를 내는 도구

`dq5hangul.py retree` 처럼 롬 전체를 내는 도구는 `fromrom` 으로 패치 목록을 만듭니다. 원래 롬을 같은 크기로 늘린 것과 견주어 다른 곳을 쓰기로 바꾸고 원래 롬 자리에는 `orig` 를 채웁니다. 4바이트 안쪽으로 떨어진 다른 곳은 한 쓰기로 묶고, 뱅크 경계에서 자릅니다. 1KB 가 넘는 쓰기는 옆에 `.bin` 파일로 둡니다. 머리는 견주지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc fromrom work/hangul/retree.sfc --name retree \
    -o work/build/retree.dq5patch.json
```

`retree` 롬(2MB)을 이렇게 바꾸면 쓰기 13개, 146,209바이트가 나왔습니다. 그것만 넣어 `build` 한 롬은 `retree` 롬과 바이트까지 같았습니다.

### 게임 데이터 표 `dq5tables/1`

`sfc/dq5/tools/dq5tables.py` 는 [dq5-data-format.md](dq5-data-format.md) 의 고정 크기 표를 필드 이름이 붙은 JSON 으로 내보내고, 고친 JSON 을 패치 목록으로 바꿉니다. 표의 항목 수는 늘리지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc export -o work/tables/dq5.json
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc patch work/tables/edit.json -o work/build/tables.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5tables.py rom/dq5.sfc check work/tables/edit.json
```

```json
{"format": "dq5tables/1",
 "monsters": [{"id": "00", "HP": 300, "경험치": 777, "내성": "000000000103300000"}],
 "items": [{"id": "06", "가격": 30, "장비사람": "10100110"}]}
```

| 표 | 자리 | 항목 | 필드 |
| --- | --- | --- | --- |
| `monsters` | `23:8000` + n×25 | 236 | `HP` `MP` `민첩` `공격` `수비` `경험치` `금화` `행동수` `재생` `첫상태확률` `첫상태종류` `드롭률` `드롭` `f68` `f69` `대상고정` `피하기` `동료확률` `동료종류` `행동1`~`행동6` `내성`(내성 종류 `50`~`61` 의 단계 0~3 을 18자리로) |
| `items` | `23:B081` + k×D8 + n, `23:B669` + n×2 | 216 | `가격` `가격배수` `k1b2` `팔수없음` `가득창` `쓰면없어짐` `필드대상창` `사용메시지없음` `칸` `저주` `그룹무작위` `적쪽` `전투대상창` `상점전투설명` `인파스설명` `인파스가격줄` `인파스횟수줄` `k4하위` `인파스장비줄` `인파스종류` `힘` `장비사람` `장비몬스터` |
| `spells` | `26:8765` + n, `26:8865` + n×2 | 171 | `MP`(원값: `1F` 없음, `1E` = 36, `1D` = 남은 MP 전부) `범위` `적쪽` `대상루틴` |
| `amounts` | `27:8071` + n×2 | 64 | `바탕`(`FE` = 300) `폭`. 게임은 주문 처리 루틴의 `LDA #` 번호 & 3F 로 읽으므로 64칸을 모두 내보내지만, 처리 루틴이 쓰지 않는 번호는 뜻이 없습니다(`dq5spell.py` 의 `양` 이 쓰는 번호) |
| `companions` | `23:AED1` + n×9 | 42 | `레벨` `최대레벨` `HP` `MP` `장비갈래` |

- 값은 정수이고, `드롭`·`동료종류`·`행동n`·`대상루틴` 은 16진 문자열, `장비사람`·`장비몬스터` 는 2진 문자열(왼쪽이 높은 비트)입니다. 필드의 뜻과 근거는 [dq5-data-format.md](dq5-data-format.md) 의 같은 이름 절을 봅니다.
- 입력에는 고칠 항목·필드만 적어도 됩니다. 적지 않은 필드와 어느 필드도 차지하지 않는 비트(몬스터 바이트11 bit0-5 등)는 롬 값 그대로 남습니다. `_이름` 처럼 `_` 로 시작하는 키와 모르는 키는 읽지 않습니다.
- 값이 필드 비트 수를 넘으면 거부합니다(HP 는 11비트라 2,047 까지). 두 입력이 같은 바이트를 다른 값으로 고쳐도 거부합니다.
- 패치 목록에는 롬과 다른 바이트만 들어가고, 이어진 바이트는 쓰기 하나로 묶으며 모두 `orig` 를 채웁니다. `check` 는 패치를 붙인 롬을 다시 읽어 적은 값이 그대로 나오는지 봅니다.

확인한 것:

- 내보낸 JSON 을 그대로 다시 넣으면 바뀐 바이트가 0개였습니다. 내보낸 값은 읽기 도구 `dq5monster.py`(236종의 필드·내성·행동)·`dq5item.py`(216개)·`dq5spell.py`(171개)와 하나도 다르지 않았습니다.
- 다섯 표의 첫·둘째·마지막 항목에서 필드마다 0 과 최댓값을 넣고 다시 읽자 354번 모두 그 필드만 바뀌었습니다.
- スライム(`00`)을 고친 롬을 빌더로 만들어 슬라임 셋 이벤트 전투(handoff 의 전투 재현)를 했습니다. `HP` 300 이면 전투 슬롯 `7E:07C0 + 슬롯*16 + 2` 가 셋 모두 `2C 01` 이었습니다(바이트10 의 위 비트까지 들어감). `HP` 1·`경험치` 777 이면 「それぞれ 2331ポイントの けいけんちを かくとく！」, `경험치` 0·`금화` 600 이면 소지금(`7E:2019`)이 20 → 1,820 이었습니다(바이트8 bit2-3 의 위 비트까지).
- 물건 `가격`은 [성장·조우·상점](#성장조우상점-dq5progress1)의 상점 검사에서, 물건 `00` 의 `힘`과 주문 `01` 의 전투 `MP` 는 [포팅 도구 점검](dq5-port-tool-audit.md)에서 게임이 고친 값을 쓰는 것을 봤습니다.
- 물건 플래그·주문 필드·피해량·동료 표는 `sfc/dq5/tools/dq5tablecheck.py` 가 고친 롬과 원래 롬으로 같은 장면을 돌려 견줍니다(장면 준비 1회와 견주기 38회). 장면 준비용 롬 덮기와 WRAM 쓰기(상점 장면, 전투로 순간이동, 슬라임 HP 200, 파파스 행동을 모두 メラ, 동료 조건 `7E:21B1`·`$1010`, 슬라임 동료 확률 1/1, 일행에 슬라임 레코드, 가진 물건·HP·MP·주문 칸, 주인공 전투 주문 칸 8 을 メラ 로, 떨어뜨리기 확률을 건너뛰는 `20:8000` bit5)는 확인하는 표를 건드리지 않습니다. 아래 읽기 PC 는 MesenCE 읽기 콜백이 주는 값이라 읽은 명령의 다음 명령 주소입니다(`21:A55B` 는 `21:A557` 의 `LDA 23:B591,X` 다음, `21:A561` 은 `21:A55D` 의 `AND 21:A632,X` 다음).

  | 고친 것 | 장면 | 원래 롬 | 고친 롬 |
  | --- | --- | --- | --- |

  피해는 메시지 `070`(주문)에 이어지는 `069`(피해)마다 전투 슬롯 HP(`7E:07C0 + 슬롯*16 + 2`)가 줄어든 양입니다. 실행 끝에서 잘린 주문은 세지 않습니다. 폭 1 이면 난수 폭이 0~0 이라 피해가 바탕 그대로입니다. 창 번호는 창을 여는 `04:9C52` 의 A(창 레코드 `04:EB48[창]`: `38` = `F197`, `4A` = `F2F6`, `4C` = `F314`, `4F` = `F337`, `6F` = `F99D`)로 셉니다. 메시지는 보행 모드 `24:8BAF`, 전투 모드 `24:8C39` 의 A 입니다. 화면 문구는 두 롬의 화면을 눈으로 견줬고, 도구는 읽기 값·AND 값·HP·레코드·창·메시지 번호를 단언합니다.
- 물건·주문·피해량·동료 표에서 고친 롬으로 게임에서 보지 않은 필드는 물건 셋입니다.
  - `k1b2`(k1 bit2): 읽는 루틴 `21:A4DD` 로 가는 길이 `BRK #94 07` 하나인데, 롬에 그 바이트가 있는 `11:D137` 은 코드가 아닌 자리입니다([dq5-data-format.md](dq5-data-format.md#물건-표-23b081), 정적 검색). 읽는 길을 찾지 못해 무엇을 볼지 없습니다.
  - `k4하위`(k4 bit0-5): `BRK #94 15` 로 읽지만 부르는 곳의 뜻을 아직 모릅니다. 무엇을 볼지 정하지 못했습니다.
  - `그룹무작위`(k2 bit4): 적 그룹을 고른 뒤 살아 있는 한 마리를 난수로 고르는 갈래(`20:A917`)입니다. 한 마리 무리에서는 차이가 없고, 여러 마리 무리에서는 원래 롬도 난수로 대상이 갈려 한 번씩 돌려서는 견줄 수 없습니다. 슬라임 셋 무리에 기다리는 프레임을 바꿔 여러 번 쓰거나 난수를 고정하면 견줄 수 있으나 아직 하지 않았습니다. 그룹 전체를 치는 いかずちのつえ 에서는 꺼도 맞는 수가 같았습니다([dq5-data-format.md](dq5-data-format.md#물건-표-23b081)).

### 성장·조우·상점 `dq5progress/1`

`sfc/dq5/tools/dq5progresswrite.py`는 성장 53개, 조우 구역 85개, 상점 48목록, 메달·코인 교환 값 6개씩을 편집합니다. 목록·필드를 생략하면 원래 값을 유지합니다. 바뀐 레코드만 `orig`를 포함한 패치 목록으로 냅니다. 일반 물건 가격은 기존 `dq5tables.py`의 `items`로 고칩니다.

```sh
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc dump -o work/progress.json
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc patch work/progress.json -o work/progress.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5progresswrite.py rom/dq5.sfc check
```

```json
{"format":"dq5progress/1",
 "growth":[{"kind":"person","index":0,"exp2":8}],
 "encounters":[{"index":1,"slots":[{"index":5,"monster":3,"weight":7,"count_code":0}]}]}
```

`growth`의 `kind`는 `person`(11종)·`monster`(42종), `index`는 종류 안 번호입니다. 레코드는 16진 `50`, 즉 80바이트입니다. `breaks`는 꺾이는 레벨 최대 7개, `exp2`는 레벨 2의 누적 경험치, `multipliers`는 구간별 배수 바이트(`breaks` 수+1개)입니다. `stats`의 키는 `hp`·`mp`·`strength`·`agility`·`wisdom`·`luck`·`resilience`이며, 각 배열에 레벨 1·꺾이는 레벨들·레벨 99의 저장값을 적습니다. HP·MP는 레벨 1을 제외한 저장값의 두 배가 실제 값입니다.

꺾임 수를 바꾸면 배수와 능력치 일곱 배열을 모두 지정해야 합니다. 새로 바꾼 꺾임은 2~99에서 엄격한 오름차순, 새 능력치 곡선은 실제 값 기준 비감소여야 합니다. 원본의 중복 꺾임이나 감소 곡선을 수정하지 않는 경우는 그대로 보존합니다. 활성 값 밖의 빈 칸도 원본에서 유지합니다.

`encounters`는 `index` 0~84로 고릅니다. `slots`는 일반 몬스터 칸 0~9 중 고칠 칸만 적으며 `weight`·`count_code`는 각각 0~7, `monster`는 0~235입니다. 마지막 칸 10은 `fixed`의 `weight`(0~7)·`group`(0~8)으로 따로 고칩니다. `species_weights`는 여러 종 무리의 종 수 무게 셋(각 0~3), `rate_index`는 조우 확률 계수 색인(0~7), `flag_1000`은 2비트, `flag_1010`·`fixed_night_only`는 bool입니다. 모든 칸의 무게가 0이거나 여러 종을 뽑는데 종 수 무게가 모두 0이면 거부합니다. 원시 비트가 겹치는 칸도 다른 필드의 비트는 보존합니다.

`shops`는 `kind`(0 도구·1 방어구·2 무기·3 잡화)와 종류 안의 `index`로 고릅니다. 원본의 종류별 목록 수는 11·15·17·5개입니다. `items`는 물건 번호(0~215) 1~6개입니다. 7번째부터는 커서로 고를 수는 있지만 목록 창 밖, 비교 창 아래라 보이지 않아 받지 않습니다. 있는 목록의 `key`를 적었다면 원래 값과 같은지 확인하며, 키와 목록 순서는 바꾸지 않습니다. 같은 키라도 이야기 플래그나 주인공 자리로 다른 목록을 고르기 때문입니다. `index`를 그 종류의 목록 수와 같게 두고 `key`(0~254)와 `items`를 적으면 종류 끝에 새 목록을 더합니다.

상점 목록은 `04:FBD5` 의 종류별 포인터 4개 뒤에 `[키][품목…][FF]` 가 이어지며 `04:FD55` 까지 빈틈이 없습니다(384바이트). 쓰기 도구는 네 종류를 다시 늘어놓아 포인터를 고치고, 줄어든 자리는 `FF` 로 채웁니다. 마지막 종류는 키 자리의 `FF` 나 원래 끝에서 끝납니다. 늘어나 원래 자리를 넘으면 `--shop-at` 으로 옮겨야 합니다. 키 찾기 `06:F49C` 와 품목 읽기 `06:F545` 는 `LDA #$04 / PLB` 로 DB 를 `04` 로 두고 `$0F20`·`$0F25`·`$0F26` 을 abs 로 읽습니다. 그래서 옮길 자리는 WRAM 낮은 거울이 보이는 뱅크(`00`~`3F`·`80`~`BF`)여야 합니다. 원래 롬의 빈 자리 `0B:FBB0`(1,104바이트)이 맞습니다. 옮기면 두 루틴의 뱅크 즉값(`06:F4AE`·`06:F54E`)과 포인터 표 주소(`06:F4BA`·`06:F50D`)를 고치고, 목록 뒤에 끝 표시 `FF` 를 둡니다. 목록 본문을 읽는 `LDA ($00),Y` 도 DB 를 따르므로, 포인터 표와 목록은 같은 뱅크에 있어야 합니다. 원래 자리에 쓸 때도 384바이트를 한 덩어리로 쓰므로, 같은 구간을 쓰는 다른 패치와는 빌더가 겹침으로 거부합니다. `dq5shop.py` 는 원래 자리만 읽습니다. `medal_prices`와 `coin_prices`는 각각 여섯 값이고 범위는 0~255·0~16,777,215입니다.

숫자는 JSON 정수이며 모르는 필드·잘못된 타입·중복 식별자는 오류입니다. 원본 전체를 내보내 다시 인코딩한 6,518바이트(상점 포인터 8바이트 포함)가 모두 같았고, 그대로 패치하면 쓰기는 0개였습니다. 게임에서는 수정한 성장 표로 레벨업한 능력치·다음 경험치, 던전 보행 조우의 몬스터·마릿수, 상점 품목 여섯 개와 가격을 확인했습니다. 일반 가격 둘은 `dq5tables.py`로 바꾸어 상점 계산 결과까지 대조했습니다([일지](../journal/2026-10-26-55-progresswrite.md)). 목록 길이 변경은 무기점 키 1 을 6→4품목으로 줄인 롬(제자리)과, 무기점에 새 키 `40` 목록 6품목을 더해 `0B:FBB0` 으로 옮긴 롬에서 확인했습니다. 옮긴 롬의 키 1·`1A` 목록은 원본과 같았습니다([일지](../journal/2026-10-27-15-shopgrow.md)).

`MESENCE`를 설정한 뒤 다음 명령으로 레벨업·조우·상점 검사를 다시 돌립니다. 결과와 실행별 로그는 출력 폴더 아래 새 하위 폴더에 남습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5progresscheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/progresscheck
```


### 조우 표 `dq5encounter/1`

`sfc/dq5/tools/dq5encounterwrite.py` 는 조우 구역을 고르는 표와 구역 밖의 무리 표를 고칩니다. 구역 레코드(`23:96F3`)는 위 `dq5progresswrite.py` 가 씁니다. 표의 크기와 자리는 그대로이고 적은 값만 바꿉니다. 뜻과 근거는 [dq5-data-format.md](dq5-data-format.md#전투-조우-23e7c2) 를 봅니다.

```sh
uv run --locked python sfc/dq5/tools/dq5encounterwrite.py rom/dq5.sfc dump -o work/encounter.json
uv run --locked python sfc/dq5/tools/dq5encounterwrite.py rom/dq5.sfc patch work/encounter.json -o work/build/encounter.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5encounterwrite.py rom/dq5.sfc check
```

```json
{"format": "dq5encounter/1",
 "maps": [{"map": "21/02", "areas": [13, 1, 13]}],
 "fixed_groups": [{"index": 5, "members": [{"monster": 0, "count_code": 2}, {"monster": 3, "count_code": 0}]}],
 "event_groups": [{"index": 1, "members": [{"monster": 3, "count": 2}]}]}
```

| 키 | 자리 | 항목 | 쓰는 값 |
| --- | --- | --- | --- |
| `field_grids` | `23:F1FC`~`23:F54D` | 격자 5개(`index` 0~4, `$1949`·`$1948` 로 고름) | `rows`: 17칸 줄의 배열. 줄 수(7·17·17·5·4)는 원래대로. 값은 구역 0~84 |
| `maps` | `23:FD6A` 포인터가 가리키는 6바이트 항목 | 그룹 `00`~`35` 의 맵 346개(`"BC/BD"`) | `areas`: `$1948` = 0·1·2 일 때 구역 셋(0~84, 255 = 조우 없음). `+3`~`+5`(전투 배경·주문 막기·소리)는 원래대로 |
| `fixed_groups` | `23:B04B` + n×6 | 9개(`index` 0~8) | `members`: 1~3개의 `monster`(0~235)·`count_code`(마릿수 부호 0~14). 줄 번호(하위 4비트)는 원래대로 |
| `event_groups` | `23:D757` + n×13 | 64개(`index` 0~63) | `flags`: 첫 바이트. bit0-1(곡 0~2)·bit4~7 만 받고, 곡 번호 3 과 뜻을 보지 못한 bit2·3 은 거부. `members`: 1~4개의 `monster`(0~235)·`count`(1~9). `+9`~`+C` 는 원래대로 |

- JSON 의 수는 10진입니다(구역 `0D` 는 13). 무리의 빈 자리는 몬스터 `FF` 로 채웁니다. 이벤트 무리의 빈 자리 마릿수는 원래 표처럼 0 입니다. 고정 무리 빈 자리의 하위 4비트는 그대로 둡니다.
- 맵은 구역 연결 표에 있는 그룹 `00`~`35` 만 받습니다. 그룹 `50` 이상의 맵(`23:FDD6`, 코드 읽기만 함)은 받지 않습니다.
- 이벤트 무리의 마릿수 상한 9 는 실측한 가장 큰 값입니다. 한 줄에 들어가는 수는 게임이 몬스터 너비로 다시 줄입니다(「줄과 마릿수」).
- 내보낸 JSON 을 그대로 넣으면 쓰기가 0개입니다(`check`, 3,812바이트).

확인한 것(`sfc/dq5/tools/dq5encountercheck.py`, 12회 실행). 장면 준비로 조우 계수 표 `23:EA44` 를 모두 `FF` 로 덮어 조우를 잦게 했고, 이 표는 확인하는 표가 아닙니다. 걸음마다 `23:E7C2` 의 A(구역)와 무리를 정하고 나가는 세 곳의 `$1001`~`$1008` 을 기록했습니다.

| 고친 것 | 장면 | 대조 롬 | 고친 롬 |
| --- | --- | --- | --- |
| 격자 0 의 (9~11, 0~2) 를 구역 `01` 로 | 필드 341,56 에서 좌우로 걸음 | 12걸음 모두 구역 `0D`, 무리 몬스터 `20` 2·`22` 2 | 12걸음 모두 구역 `01`, 몬스터 `01` 2·`00` 2 |
| 21/02 의 `areas` 를 `01`·`14`·`14` → `0D`·`01`·`0D` | 21/02 (50,43) 에서 좌우로 걸음, `$1948` = 0 | 26걸음 모두 구역 `01`, 몬스터 `01` 2 | 26걸음 모두 구역 `0D`, 몬스터 `22` 1·`26` 1 |
| 같은 롬 | 같은 장면, 시작할 때 `$1948` = 1 | 구역 `14`, 몬스터 `28` 3·`00` 3 | 구역 `01`, 몬스터 `01` 2 |
| 같은 롬 | 같은 장면, `$1948` = 2 | 구역 `14`, 몬스터 `28` 3·`00` 3 | 구역 `0D`, 몬스터 `22` 1·`26` 1 |

### 실내 맵 레코드 `dq5map/1`

`sfc/dq5/tools/dq5mapwrite.py` 는 [dq5-map-format.md 「맵 레코드」](dq5-map-format.md#맵-레코드) 를 명령 단위 JSON 으로 풀고 다시 쌉니다. 실내 맵 346개와 그룹 `50` 이상 맵 18개를 모두 다룹니다.

```sh
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc check
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc dump 01 05 -o work/map/0105.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc patch work/map/0105.json -o work/build/map.dq5patch.json
```

```json
{
 "format": "dq5map/1",
 "map": "01/05",
 "kind": 1, "width": 68, "height": 60, "outside": 0, "zone": 0, "attr": 8, "bits": 12,
 "background_hi": 130, "background_lo": 206,
 "commands": [
  ["block", 904],
  ["fill", 50, 56, 66, 58],
  ["put", 42, 50],
  ["end"]
 ],
 "stream_tail": 0,
 "passes": [
  {"vertical": false, "flag_low": 0, "end_low": 8, "entries": [
    [1, 4, 66, 1, "long"]
  ]},
  …
 ],
 "junk": "800"
}
```

| 키 | 뜻 |
| --- | --- |
| `kind`~`background_lo` | 머리 9바이트(`+0`~`+8`) 그대로. `bits` 는 위치 비트 수 |
| `commands` | `["block", 블록 번호]`·`["put", x, y]`·`["fill", x0, y0, x1, y1]`·`["end"]`. 위치 `y*폭+x` 가 `bits` 비트에 들어가야 함. 마지막은 `end` |
| `passes` | 속성 패스 1·2·3. `vertical` 은 반복 방향, `entries` 는 `[x, y, 칸 수, 값 니블, 꼴]`. 꼴 `one` 은 1칸, `short` 는 2~17칸, `long` 은 2~257칸 |
| `stream_tail`·`flag_low`·`end_low`·`junk` | 게임이 읽지 않는 비트(비트스트림 끝의 남은 비트, 패스 머리 바이트 아래 7비트, 끝 바이트 아래 6비트, 아무도 읽지 않는 니블). 원래 레코드와 바이트까지 같게 싸려고 담음. 빼면 0 |

- `patch` 는 새 레코드를 늘린 롬의 `--at`(기본 `30:8000`)부터 차례로 놓고 맵 포인터(그룹 목록 `0F:8ED7`, 그룹 `50` 이상은 `1F:CEB6`)의 24비트를 바꿉니다. 레코드는 파일 위치(`0x…`)로 써서 뱅크를 넘어도 됩니다(게임 리더 `01:AC66` 이 `FFFF` 에서 다음 뱅크로 넘어감). `rom_size` 는 놓은 끝에 맞춰 2·3·4 를 적습니다.
- `--in-place` 는 원래 자리에 덮습니다. 원래 레코드보다 길면 거부합니다.
- `map`은 `GG/MM` 형태의 두 자리 16진 번호이며 원본 목록에 있는 맵만 받습니다. 새 맵 번호를 추가하지는 않습니다. `dump`도 목록 밖 번호를 거부합니다.
- 최상위 필드는 `format`, `map`, 머리 9개, `commands`, `passes`, `stream_tail`, `junk`만 받습니다. `exits` 같은 다른 필드는 무시하지 않고 오류로 끝냅니다. 출구 목적지·인물 목록은 이 맵 레코드에 포함되지 않습니다.
- 속성 패스의 니블 위치는 게임 리더를 그대로 따릅니다. 게임 리더의 상태(주소, 반 바이트)를 니블 위치 q 로 보면 패스 머리는 `N[q]` 의 bit3 이고, 이어 읽는 바이트·니블은 `N[q+1]` 부터입니다. 그래서 패스 2·3 의 머리 니블은 앞 패스의 끝 바이트 아래 니블과 겹칠 수 있고(그때는 `flag_low` 가 없음), 머리 다음 니블은 아무도 읽지 않습니다.
- 레코드는 마지막으로 읽힌 니블이 든 바이트까지입니다. 20/03·31/04·31/05 세 맵은 패스 3 끝 바이트의 아래 니블이 다음 맵 머리 첫 바이트와 같은 바이트라 레코드가 1바이트 겹칩니다(게임은 그 니블을 보지 않음).

확인한 것:

- `check`: 364개 맵을 풀고 다시 싸자 233,794바이트 모두 원래 롬과 같았습니다. 레코드 끝은 다음 맵 시작과 맞닿았고(겹치는 세 곳 빼고), `dq5map.py` 디코더가 속성 패스를 끝낸 자리와도 같았습니다.
- 01/05 를 고치지 않고 `30:8000` 으로 옮긴 2MB 롬과, 끝에 `["block", 774], ["put", 4, 2], ["block", 356], ["fill", 8, 2, 13, 5]` 를 더해 옮긴 롬을 만들었습니다. 배 사다리 순간이동으로 들어가 `01:BA4C`(속성 패스 끝)에서 WRAM 을 덤프하자, 옮기기만 한 롬은 셀 버퍼가 원래 롬과 같았고, 고친 롬은 셀 28칸이 달라졌으며 `dq5map.py --compare` 가 두 롬 모두 0바이트 차이였습니다. 화면에도 더한 붉은 바닥과 벽 조각이 보였습니다.

### 블록 배치 목록 `dq5mapsrc/1`

배치 명령을 손으로 적는 대신, 블록을 놓을 자리를 칠하는 순서대로 적으면 `sfc/dq5/tools/dq5mapcompile.py` 가 put·block·fill 명령으로 바꿉니다. 새 맵을 그릴 때는 이 목록을 씁니다.

```sh
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc extract 01 05 -o work/map/0105.src.json
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc compile work/map/0105.src.json -o work/map/0105.json
uv run --locked python sfc/dq5/tools/dq5mapwrite.py rom/dq5.sfc patch work/map/0105.json -o work/build/map.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5mapcompile.py rom/dq5.sfc check
```

```json
{
 "format": "dq5mapsrc/1",
 "map": "01/05",
 "kind": 1, "width": 68, "height": 60, …, "background_hi": 130, "background_lo": 206,
 "placements": [
  [50, 56, 904],
  [52, 56, 904],
  [4, 2, 774]
 ],
 "passes": [ … dq5map/1 과 같음 … ]
}
```

- `placements` 는 `[x, y, 블록]` 을 칠하는 순서대로 적습니다. 블록은 원점(왼쪽 위)부터 블록 폭×높이 셀을 덮고, 뒤 배치가 앞 배치를 덮습니다. 머리의 배경 블록(`background_hi` bit7)은 모든 배치보다 먼저 맵 전체를 칠합니다.
- `extract` 는 기존 맵의 명령을 펼쳐(fill 은 게임처럼 원점마다) 이 목록으로 만듭니다. 머리와 속성 패스는 그대로 옮깁니다.
- `compile` 이 순서를 고르는 법: 셀마다 배치가 쓰는 단위(`+1` 플래그, 아래층 `+2`~`+4`, 위층 `+5`~`+7`)를 보고 끝까지 남는 단위가 하나도 없는 배치는 버립니다. 남은 배치끼리는 같은 단위를 쓰는 앞뒤만 지키고, 지금 칠할 수 있는 배치가 가장 많은 블록을 골라 한 묶음으로 냅니다. 묶음은 블록 크기 간격의 직사각형(원점 3개 이상)을 fill, 나머지를 put 으로 냅니다. 버린 배치 자리는 그것을 덮을 배치가 아직 나오지 않았고 같은 묶음에도 없을 때만 직사각형을 메우는 데 씁니다.
- CHR 의 VRAM 슬롯은 블록을 처음 쓰는 순서대로 받으므로(`01:8C15`), 명령 순서가 바뀌면 셀 버퍼의 타일 워드 값(슬롯 번호)은 원래와 달라도 그림은 같습니다. `check` 는 슬롯을 CHR 번호로 되돌려 견줍니다.

확인한 것:

- `check`: 364개 맵을 `extract` → `compile` 해 새 레코드로 풀자 셀 버퍼(슬롯을 CHR 로 되돌린 것)가 모두 원래와 같았고, 쓰는 슬롯이 늘어난 맵도 없었습니다. 레코드는 233,794바이트에서 249,471바이트로 6.7% 컸습니다(사람이 겹쳐 놓은 큰 fill 을 다 되살리지 못함).
- 01/05 를 `extract` 한 목록 그대로, 그리고 블록 7개(`[4, 2, 774]` 와 블록 356 의 2×3 격자)와 속성 패스 엔트리 셋을 더한 목록을 각각 컴파일해 `30:8000` 에 놓았습니다. 두 롬 모두 `01:BA4C` 의 게임 셀 버퍼가 `dq5map.py --compare` 와 0바이트 차이였습니다. 더한 엔트리는 게임에서도 패스 1 `(10,6)` 의 `+1` 아래 니블 1 → 5, 패스 2 세로 3칸 `(20,6)`~`(20,8)` 의 `+1` 에 `40`, 패스 3 세로 4칸 `(30,10)`~`(30,13)` 의 `+0` 위 니블 3 으로 들어갔습니다.

### 필드 세계 지도

`sfc/dq5/tools/dq5fieldwrite.py` 는 세계(`$1949` = 0·1·2)마다 256×256 칸의 블록 번호(0~510)를 [dq5-field-format.md 「불러오기」](dq5-field-format.md#불러오기-01a5c2) 의 RLE 두 덩어리(지도 하위 8비트 64KB, 9번째 비트 8KB)로 싸서 늘린 롬에 놓습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc dump 0 -o work/field/w0.bin
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc patch --world 0 work/field/w0.bin -o work/build/field.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5fieldwrite.py rom/dq5.sfc check
```

- 지도 파일은 칸 `y*256+x` 순서로 16비트 리틀 엔디언 블록 번호를 둔 131,072바이트입니다. 세계 1·2 도 256×256 이고 게임은 왼쪽 위 128×128 만 씁니다.
- 불러오기 루틴(`01:A5C2`·`A5F1`·`A620`)은 덩어리마다 `LDA #뱅크 / STA $4374 / PHA / PLB / LDX #주소 / JSR $A64F` 입니다. `patch` 는 덩어리를 `--at`(기본 `34:8000`)부터 놓고 이 두 즉값(`orig` 포함)을 바꿉니다. `01:A64F` 는 덩어리를 DMA 원본(16비트 주소 + 뱅크)으로 읽으므로 덩어리 하나가 뱅크를 넘으면 다음 뱅크 `8000` 으로 옮겨 놓습니다.
- 배치 영역은 `30:8000`~`3F:FFFF` 안이어야 합니다. 실행 커버리지에서 `01:A5D1`의 `PLB` 뒤 `01:A668`·`A673`이 `$00A5`, `01:A656`·`A660`·`A66C`이 `$4371`·`4375`·`4372`, `01:A67D`가 `$420B`를 접근하는 것을 확인했습니다. 자료 뱅크를 DB에 넣은 채 이 주소들을 쓰므로 WRAM·I/O 미러가 없는 `40`~`7D` 뱅크로 옮기면 정상 실행되지 않습니다. 도구는 시작 주소와 모든 덩어리의 끝을 검사합니다.
- RLE 는 같은 값 3개 이상을 반복(최대 128), 나머지를 글자 그대로(최대 128) 냅니다. 원래 덩어리와 크기가 조금 다릅니다(세계 0 지도 25,868 → 25,958바이트, 9번째 비트는 같음).

확인한 것:

- `check`: 세 세계 여섯 덩어리를 다시 싸서 풀면 모두 원래와 같았습니다.
- 세계 0 을 고치지 않고 옮긴 2MB 롬과, 블록 (172~176, 25~28) 을 블록 307(9번째 비트가 켜진 언덕)으로 칠한 롬을 만들었습니다. `dq5warp.lua` `FIELD=341,56` 으로 필드에 서서 `00:8090` 에서 WRAM 을 덤프하자 두 롬 모두 `7F:0000`·`7E:E000` 이 입력 지도와 바이트까지 같았고, 고친 롬은 주인공 오른쪽의 산이 언덕으로 바뀌어 보였습니다.

세 세계를 함께 `34:8000`부터 다시 배치한 롬에서는 세계마다 지도 65,536바이트·상위 비트 8,192바이트, 합계 73,728바이트가 게임 WRAM과 같았습니다. `60:8000`에 배치한 대조 롬은 세 세계 모두 화면이 꺼진 채 멈췄고 WRAM도 달랐습니다.

### 필드 블록·입구 표 `dq5fieldtables/1`

`sfc/dq5/tools/dq5fieldtables.py` 는 고정 크기 표를 내보내고 고친 필드만 원래 자리에 씁니다. 항목 수·순서·종료 표지를 유지합니다. 패치 목록에는 바뀐 5바이트 항목만 넣고 `orig`로 원래 값을 확인합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc dump -o work/fieldtables.json
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc patch work/fieldtables.json -o work/fieldtables.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5fieldtables.py rom/dq5.sfc check
```

```json
{"format":"dq5fieldtables/1",
 "blocks":[{"index":307,"lower":[1,2,257,258]}],
 "entrances":[{"table":"main","index":0,"group":2}],
 "arrivals":[{"group":2,"x":10,"y":20,"layer":1}]}
```

목록이나 필드를 생략하면 원본 값을 보존합니다. 숫자는 모두 JSON 정수입니다. 위 예는 블록 307의 아래층 네 타일, 일반 입구 첫 항목의 그룹, 그룹 2의 도착 자리·층을 바꿉니다. 실제 목적지의 바닥과 도착 층이 맞는지는 게임에서 확인해야 합니다.

| 목록 | 식별자·범위 | 편집 필드 |
| --- | --- | --- |
| `blocks` | `index` 0~510 | `lower`·`upper`: 왼위·오위·왼아래·오아래 타일 번호 4개, 각 0~511 |
| `entrances` | `table`은 `main` 또는 `aux`, `index`는 각각 0~46·0~13 | `group`: `00`~`35` 또는 `50`~`54`(16진 범위), `x`·`y`: 0~511 |
| `arrivals` | `group` 0~53(`00`~`35`) | `map`: 0~31, `x`·`y`·`layer`: 바이트, `world_code`: 0~3, `wagon`: bool, `direction`: 0~3, `party_overlap`: bool, `map_flags`: 0~31 |

- 블록의 다섯째 바이트 하위 니블은 뜻을 확인하지 못했으므로 원본 그대로 보존합니다. 블록 번호 511은 다음 표 또는 압축 지도와 겹쳐 거부합니다.
- 같은 그룹의 입구가 여럿이므로 그룹 번호가 아닌 목록 안의 `index`로 고칩니다. 두 입구 표의 끝 `FF`를 바꾸거나 항목을 늘리지 않습니다.
- 도착 `world_code`는 롬의 원시 2비트 값입니다. 1·2·3은 세계 0·1·2이며 원본의 0도 보존합니다. `wagon`은 첫 바이트 bit7, `party_overlap`은 마지막 바이트 bit7, `map_flags`는 마지막 바이트 bit2~6입니다.
- 특수 그룹 `50`~`54`와 좌표별 예외는 게임의 별도 코드가 처리합니다. 입구 그룹을 바꾸어도 이 코드를 다시 쓰지는 않습니다.
- 알 수 없는 필드·잘못된 타입·중복 식별자·범위 초과는 오류입니다. 원본 전체를 내보냈다가 패치하면 쓰기가 0개입니다.

블록 1,022항목·입구 61항목·도착 54항목, 합계 5,685바이트를 다시 인코딩해 원본과 같았습니다. 블록 양층·일반/보조 입구·도착 표를 고쳐 빌더에 넣은 뒤 기존 읽기 도구로 다시 확인했습니다.

게임에서는 블록 양층의 BG 타일맵 8,192바이트가 예측과 같았고, 일반·보조 입구를 실제 걸어 바꾼 도착 맵·좌표·층·방향에 섰습니다. 마을에서 나오는 필드 좌표도 맞았습니다. `dq5fieldtablecheck.py`가 이 보행과 세계 지도 검사를 재현합니다([일지](../journal/2026-10-26-54-fieldtables.md)).

### 보행 대사 일괄 쓰기 `dq5text/1`

`sfc/dq5/tools/dq5textwrite.py`는 보행 메시지 3,200개를 코드 목록으로 내보내고, 고친 항목을 반영해 허프만 트리·메시지 전체를 다시 만듭니다. 원래 글꼴과 메시지 번호를 유지하며 새 글꼴·전투 메시지·창·이름 표는 편집하지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc export -o work/messages.json
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc patch work/messages.json -o work/text.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5textwrite.py rom/dq5.sfc check work/messages.json
```

```json
{"format":"dq5text/1", "messages":[{"id":297,"codes":[4102,0,4097]}]}
```

`id`는 0~3199의 정수입니다. `codes`에는 글자·제어 코드 정수를 순서대로 적습니다. 예제는 메시지 `129`를 `{1006}`·글자 `000`·끝 `{1001}`로 바꿉니다. 글자는 기존 코드 `000`~`3DA`, 제어는 `1000`~`101D`·`1100`~`1118` 범위입니다(범위 설명은 16진수, JSON 예는 10진수). 끝 코드 `1001`·`1010`·`1018` 중 하나가 마지막에 한 번만 있어야 합니다. 이름·숫자 변수에 필요한 인자는 원래처럼 부르는 코드가 대기열에 넣어야 합니다.

- 적지 않은 메시지는 원본 그대로 유지합니다. 빈 `messages` 배열이면 원본 전체를 다시 부호화합니다. `check`에 입력 파일을 빼도 같은 원본 재압축 검사를 합니다.
- 문자열을 글자 코드로 바꾸는 번역 편집기 기능은 없습니다. 원본 `export`의 코드 목록을 편집하는 단계입니다. 새 한글 글꼴 추가와 함께 쓰려면 글꼴·코드 배분을 별도로 설계해야 합니다.
- `patch --at BB:AAAA`의 기본 위치는 `38:8000`입니다. 보행 디코더 사본·마스크·트리는 한 뱅크에, 메시지는 그 뒤에 이어 놓습니다. 색인은 21비트라 보행 색인 훅이 뱅크 바이트에 창의 첫 뱅크를 OR 합니다. 창은 `30`~`3F`(OR `20`)와 `60`~`7D`(OR `60`, 4MB 패치) 둘이고, 모든 자료가 같은 창의 끝(`3F:FFFF`·`7D:FFFF`) 안에 들어가야 합니다. 디코더 사본은 `PHK`·`PLB` 로 자기 뱅크의 표만 읽어 낮은 WRAM 거울이 없는 `60`~ 에서도 돕니다(DQ4 메뉴가 `65:8000` 에서, [통합 포팅 빌드](#통합-포팅-빌드-dq5portbuild1)가 `65`~`69` 에서 게임으로 확인). `40`~`5F` 는 실측하지 않아 받지 않습니다. 다른 도구와 같은 자리를 쓰면 빌더가 거부합니다.
- `--base 롬`은 보행 메시지를 이미 옮긴 롬(DQ4 메뉴 빌드 등)을 기준으로 삼습니다. 그 롬의 디코더 호출(`24:9E02`)·색인 창(`24:9E07` 훅의 OR 값)으로 3,200개를 읽고, 입력에 적은 메시지만 바꿉니다. 글자 묶음 표 피연산자(`24:A63C` 등 넷)가 머리 끝의 늘린 표를 가리키면 그 표(DQ4 메뉴는 270바이트, 글자 `000`~`D3F`)를 새 머리 끝에 옮기고 피연산자도 새 자리로 씁니다. 그래서 `codes` 에 한글 글자 코드 `3DB`~ 를 쓸 수 있습니다. 패치는 여전히 원래 롬 기준(`orig`)이라, 기준 롬이 쓴 색인·훅·피연산자와 옛 묶음 자리를 대신합니다. 함께 빌드할 때는 통합 포팅 빌드가 그 자리를 고정 패치에서 뺍니다. `export --base` 는 기준 롬의 메시지를 내보냅니다.
- 원본 쪽에서는 색인, 보행 디코더 호출, 보행 색인 호출과 훅만 바꾸고 `orig`를 기록합니다. 전투 호출은 바꾸지 않습니다. 패치의 최소 롬 크기는 2MB이며 다른 패치와 합쳐 3·4MB로 빌드할 수도 있습니다.
- 중복 번호, 잘못된 타입·코드·끝 코드, 디코더·트리의 뱅크 초과, 전체 배치 초과는 거부합니다. 입력은 원본 롬이어야 합니다.

원본 3,200개·163,649코드를 재압축해 빌더에 넣은 뒤 새 디코더의 트리·색인을 따라 풀자 모두 같았습니다. 메시지 두 개를 바꾼 검사에서는 두 개만 입력대로 바뀌고 나머지 3,198개가 그대로였습니다. 기존 한글 실험용 `retree`도 같은 결과를 유지했습니다.

게임에서도 원본·원문 재배치·수정·뒤쪽 뱅크 메시지의 디코더 반환 64코드를 각각 비교해 일치했습니다. 뒤쪽 메시지는 `3C:B1BE`에서 읽혔습니다([일지](../journal/2026-10-26-56-textwrite.md)).

`MESENCE`를 설정한 뒤 다음 명령으로 게임 검사 4건을 재현합니다. 실행마다 새 출력 폴더에 `results.json`과 디코더 기록·화면을 남깁니다.

```sh
uv run --locked python sfc/dq5/tools/dq5textcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/textcheck
```


### 전투 메시지 일괄 쓰기 `dq5battletext/1`

`sfc/dq5/tools/dq5battletextwrite.py`는 전투 모드 메시지 432개(`24:8C39`, [형식](dq5-data-format.md#전투-모드-메시지))를 1바이트 부호 목록으로 내보냅니다. 고친 항목을 반영해 허프만 트리와 메시지 전체를 다시 만듭니다. 원래 글꼴과 메시지 번호를 유지하며, 보행 메시지·창·글꼴은 바꾸지 않습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5battletextwrite.py rom/dq5.sfc export -o work/battle.json
uv run --locked python sfc/dq5/tools/dq5battletextwrite.py rom/dq5.sfc patch work/battle.json --at 3B:8000 \
    -o work/battle.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5battletextwrite.py rom/dq5.sfc check work/battle.json --at 3B:8000
```

```json
{"format":"dq5battletext/1", "messages":[{"id":94,"codes":[247,40,1,84,78,85,25,18,132,24,22,122,254]}]}
```

예제는 메시지 `05E` 「{F7}の　こうげき！」 를 「{F7}の　テストこうげき！」 로 바꿉니다. `codes` 는 0~255 정수이고, 글자는 [이름 문자열](dq5-text-format.md#이름-문자열-21955d)과 같은 1바이트 부호(전투 창에서는 BG3 타일 번호), `E2` 이상은 `24:86F2` 처리기입니다. 끝 부호 `E7`·`EF`·`FE` 가운데 하나가 마지막에 한 번만 있어야 합니다. 이름·숫자 부호(`F7`·`FB` 등)의 인자는 원래처럼 부르는 코드가 대기열에 넣어야 합니다.

- 적지 않은 메시지는 원본 그대로입니다. 빈 `messages` 면 원본 전체를 다시 부호화합니다.
- 메시지 하나는 끝 부호까지 128바이트 이하입니다. `24:8C21` 이 메시지마다 `7E:0E4B` 에 128바이트를 한 번에 풀고 `24:86A5` 가 그 버퍼에서만 꺼내기 때문입니다(코드 읽기). 원본에서 가장 긴 메시지는 99바이트입니다.
- `--at` 은 꼭 줍니다. 기본값을 두지 않은 것은 `30`·`32`·`34`·`38`·`60:8000` 을 DQ4 타이틀·메뉴와 다른 쓰기 도구가 이미 쓰기 때문입니다([인계](../handoff.md)). 뱅크 `30`~`7D` 만 받고, 패치의 롬 크기(2·3·4MB)는 메시지가 끝나는 자리로 정합니다.

배치와 고치는 곳은 아래와 같습니다. 원래 자리에는 모두 `orig` 를 적습니다.

| 자리 | 내용 |
| --- | --- |
| `--at` | `24:9E47`~`9E8B` 디코더 사본(마스크·트리 1·0·뿌리 피연산자와 끝 `RTL` 만 바꿈), 마스크 8바이트, 트리 1·0, 그 뒤 메시지 비트열 |
| `24:9E47` | `JSL` 사본 / `RTS` |
| `24:9E4C` | `JSR 8C8D` / `LDA $F2` / `ORA #(뱅크 & E0)` / `STA $F2` / `RTS` |
| `24:8C61` | `JSR 8C8D` → `JSR 9E4C`(전투 쪽 호출만) |
| `24:AECD` | 새 색인(16개마다 3바이트, 값 = (주소 − (뱅크 & E0) × 10000) × 8 + 비트) |

제약은 코드를 읽어 정했습니다.

- **디코더·트리는 한 뱅크**: 디코더는 `PHK`·`PLB` 로 데이터 뱅크를 자기 뱅크로 두고 `LDA $9C2E,X`·`AND $9E8C,Y` 처럼 16비트 주소로 트리와 마스크를 읽습니다. 그래서 사본·마스크·트리를 한 뱅크에 둡니다. 낮은 WRAM 절대 주소는 읽지 않으므로 뱅크 `40` 이상에도 둘 수 있습니다.
- **노드는 256개까지**: 가지 노드 값은 `AND #$00FF` 뒤 두 배가 다음 X 이고, 잎은 bit15 와 값 & FF 입니다. 1바이트 부호는 256종이 넘지 않아 노드도 255개를 넘지 않습니다.
- **색인은 21비트**: `24:8C8D` 가 3바이트 색인을 3비트 밀어 뱅크 `1F` 까지만 가리킵니다. 보행 쪽(`24:8BD6`)도 같은 루틴을 부르므로 그 안은 고치지 않고, 전투 호출 `24:8C60` 만 훅으로 돌려 뱅크에 `--at 뱅크 & E0` 을 OR 합니다. 메시지는 그 값 + `1F` 뱅크와 `7D` 안에서 끝나야 합니다(`--at 3B:8000` 이면 `20`~`3F`, `4F:FD00` 이면 `40`~`5F`).
- **메시지는 뱅크를 넘어 이어짐**: 비트 위치가 `FFFF` 를 넘으면 디코더가 뱅크를 올리고 `8000` 으로 갑니다(`24:9E74`~`9E7A`).
- **보행 마스크는 그대로**: `24:9E8C` 마스크는 보행 디코더(`24:9E16`)도 읽으므로 덮지 않고 사본 쪽에 따로 둡니다. 훅 자리 `24:9E4C`~`9E55` 는 보행 쓰기(`24:9E02`~`9E10`)와 겹치지 않습니다.

원본 432개·8,910바이트를 다시 부호화해 빌더에 넣은 뒤 새 디코더의 트리·색인을 따라 풀자 모두 같았습니다(`--at` `3B:8000`·`60:8000` 둘 다). 보행 쓰기(`38:8000`)·전투 쓰기(`4F:FD00`)·이름 표 옮기기(`4E:8000`)를 한 롬으로 빌드해도 겹치지 않고 셋 다 원본과 같게 풀렸습니다. 보행 쓰기가 `38`~`3C` 를 쓰므로 함께 빌드할 때는 전투를 그 밖에 둡니다. `3D` 와 `40`·`41` 은 DQ4 환경 그림이 씁니다.

마지막 메시지 `1AF` 를 불러도 `24:8C21` 은 128바이트를 풀므로 스트림 끝 뒤를 읽습니다. 원본도 같고 읽기만 하므로 해가 없지만, 스트림이 `7D:FFFF` 에서 끝나면 그 뒤 `7E:8000`(WRAM)을 읽습니다(코드 읽기). 게임 실측은 아래 「[전투 메시지·이름 게임 실측](#전투-메시지이름-게임-실측)」에 있습니다.

### 이름 문자열 표 쓰기 `dq5names/1`

`sfc/dq5/tools/dq5namewrite.py`는 [이름 문자열](dq5-text-format.md#이름-문자열-21955d) 표 아홉 개를 1바이트 부호 목록으로 내보내고, 이름 길이를 바꿔 다시 넣습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5namewrite.py rom/dq5.sfc export -o work/names.json
uv run --locked python sfc/dq5/tools/dq5namewrite.py rom/dq5.sfc patch work/names.json -o work/names.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5namewrite.py rom/dq5.sfc patch work/names.json --at 4E:8000 \
    -o work/names.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5namewrite.py rom/dq5.sfc check work/names.json [--at 4E:8000]
```

```json
{"format":"dq5names/1", "tables":[{"table":4, "names":[{"id":0, "bytes":[84,78,85,78,104,67,98]}]}]}
```

예제는 몬스터 0 スライム(`4E 68 43 62`)을 テストスライム 으로 바꿉니다. `table` 은 `0`·`1`·`2`·`3`·`4`·`5`·`6`·`10`(`0A`)·`11`(`0B`)이고, `id` 는 그 표의 순번, `bytes` 는 0~255 정수 0~12개입니다. 항목 수는 바꾸지 않습니다. 몬스터·물건·주문 번호가 곧 순번이기 때문입니다.

| 표 | 원래 자리 | 항목 |
| --- | --- | --- |
| `0A`·`0`·`1`·`2`·`4`·`5`·`6`·`0B` | `23:C242`~`D6A0` 에 빈틈 없이 이어짐(5,215바이트) | 168·8·17·3·236·222·6·23 |
| `3` | `22:8000`~`841E`(1,055바이트) | 171 |

- `--at` 을 빼면 두 자리 안에 표를 원래 순서로 다시 채우고, 바뀐 바이트 범위와 시작이 달라진 표의 포인터(`21:959B` + 표 × 3)만 씁니다. 원래 자리에는 남는 바이트가 없으므로 한 이름을 늘리면 같은 자리의 다른 이름을 그만큼 줄여야 합니다. 모자라면 거부합니다.
- `--at` 을 주면 표 아홉 개를 그 자리부터 차례로 옮기고 포인터 아홉 개를 고칩니다. 원래 자리는 그대로 둡니다. 뱅크 `30`~`7D` 만 받습니다.
- 표 `7`(`30:8000`, 원래 롬 밖)과 `8`·`9`(`23:D6A1`, 표가 아니라 `21:A1D7` 이 `JSL` 하는 코드)는 다루지 않습니다. 롬을 늘리면 표 7 이 늘린 뱅크 `30:8000` 을 읽게 되는 것은 그대로입니다.

제약은 코드를 읽어 정했습니다.

- **한 표는 한 뱅크 안**: `21:957B` 는 길이 + 1 을 `$3A` 에 더하고 올림이 나면 `$3B` 만 올립니다. 뱅크 바이트 `$3C` 는 그대로라, 표가 `FFFF` 를 넘으면 같은 뱅크의 `0000` 을 읽습니다. 그래서 `--at` 배치에서 뱅크 끝에 들어가지 않는 표는 다음 뱅크 `8000` 에서 시작합니다.
- **표 주소는 `21:959B` 포인터만**: 표 시작 주소 열 개(24비트)를 롬 전체에서 찾았을 때 나온 곳은 `21:959B` 포인터 표뿐이었습니다(표 3 의 `22:8000` 은 다섯 곳 더 나오나 앞 바이트가 그 주소를 읽는 명령 꼴이 아님). 16비트 주소는 앞 바이트가 `LDA`·`LDX`·`LDY` 즉값·절대·롱 주소 명령인 곳만 골라(7곳) 디스어셈블했으나 표를 읽는 코드가 아니었습니다. 그 밖의 16비트 일치(표마다 6~47곳)는 보지 않았습니다.
- **이름은 12바이트까지**: `21:9589` 는 [길이][바이트…] 를 직접 페이지 `$00` 부터 복사합니다. 길이가 `39` 를 넘으면 복사하는 도중 표 포인터 `$3A` 를 덮습니다. 그보다 짧아도 `$0D` 뒤 직접 페이지를 부른 쪽이 쓰는지는 확인하지 않았으므로, 원본에서 가장 긴 이름(12바이트)까지만 받습니다. 첫 바이트가 `7A` 인 이름은 `21:95BF` 가 주인공 이름 뒤에 `$02`~`$0D` 12바이트를 붙입니다.

원본 854개 이름을 그대로 넣으면 쓰기가 0개이고, `--at 3C:8000`·`3C:F000`·`4E:8000` 으로 옮긴 롬에서 포인터를 따라 읽은 이름이 원본과 모두 같았습니다.

### 이벤트 스크립트 `dq5event/1`

`sfc/dq5/tools/dq5eventwrite.py` 는 [이벤트 명령](dq5-event-format.md)을 JSON으로 내보내고, 편집한 명령을 확장 뱅크에 놓습니다. `patch` 는 `binding` 으로 지정한 표 항목만 바꿉니다.

```sh
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc dump --number 41 -o work/event.json
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc patch work/event.json -o work/event.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5eventwrite.py rom/dq5.sfc check
```

명령의 `op` 는 두 자리 16진 문자열이고 `args` 는 바이트 정수 목록입니다. 메시지 번호와 네이티브 주소도 롬에 쓰는 순서인 하위 바이트부터 적습니다. `C3` 점프만 `args` 대신 `target` 에 24비트 CPU 주소 정수 또는 명령의 `label` 을 적습니다.

```json
{"format":"dq5event/1", "binding":{"kind":"number","index":65},
 "commands":[{"op":"10","args":[37,16]}, {"op":"FF"}]}
```

이 예는 번호 `41` 의 스크립트를 플래그 `7E:21B5` 에 `10` 을 OR하고 끝내는 명령으로 바꿉니다. `binding.index` 는 정수이므로 65가 번호 `41` 입니다. CLI의 `--number` 는 16진수, `--event` 는 0~9의 이벤트 번호입니다. `binding.kind` 를 `event` 로 쓰면 이벤트 표 `23:E2C2` 의 `index` 항목을 바꾸고, `x`·`y` 로 목표 좌표도 지정할 수 있습니다. 좌표를 빼면 원래 값을 보존합니다.

- `dump 주소` 는 임의 시작점을 읽지만 표 연결을 고르지 않습니다. `patch` 하려면 `binding` 을 넣어야 합니다.
- `encode 입력 -o 출력.bin --at 60:8000` 은 패치 목록 없이 명령 바이트만 만듭니다. 내부 라벨을 쓰면 배치 주소가 필요합니다.
- `patch` 의 기본 위치는 `60:8000` 이며 4MB 롬을 만듭니다. `--at` 으로 바꿀 수 있고, 스크립트 하나가 뱅크 끝을 넘으면 다음 뱅크 첫머리에 놓습니다.
- 같은 주소를 가리키는 다른 표 항목이나 스크립트 중간을 가리키는 항목은 그대로 둡니다. 코드 안에 직접 적힌 주소, 계산해서 만든 주소, 외부 주소로 적은 `C3` 대상도 자동으로 고치지 않습니다.
- 마지막 명령은 `FF` 또는 `C3` 여야 합니다. 모르는 명령, 인자 수·값 범위 오류, 정의하지 않은 라벨, 한 뱅크보다 긴 코드는 거부합니다.
- 번호 `1A`·`1B`·`1C`·`3C` 는 원본에서 코드를 가리키므로 `dump` 는 거부합니다. 새 명령을 작성해 그 표 항목을 지정하는 것은 별개입니다.

### 인물 스크립트 `dq5npcscript/1`

`sfc/dq5/tools/dq5npcwrite.py` 는 [인물 인라인 명령](dq5-map-format.md#인라인-스크립트-01c800)을 편집합니다. 인물 목록의 뱅크와 레코드 경계를 유지하기 위해 기존 슬롯 안에서만 패치합니다. 더 긴 스크립트는 `encode` 로 바이트를 만들 수 있지만 목록에 넣거나 재배치하는 기능은 아직 없습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc dump 05:A84F -o work/npc.json
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc patch work/npc.json -o work/npc.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc encode work/npc.json -o work/npc.bin
uv run --locked python sfc/dq5/tools/dq5npcwrite.py rom/dq5.sfc check
```

`address` 는 첫 명령 주소가 아니라 **길이 바이트 주소**입니다. 선실 파파스는 `05:A84F` 에 길이 23이 있고 첫 명령이 `05:A850` 에 있습니다. `dump` 의 `references` 는 그 슬롯을 사용하는 인물 엔트리와 낮·밤을 보여 줍니다. 공유 슬롯을 바꾸면 참조하는 시간대 모두 바뀝니다.

```json
{"format":"dq5npcscript/1", "address":"05:A84F", "length":23,
 "commands":[
   {"op":"06","args":[15,1],"target":"on"},
   {"op":"2B","args":[5,13]}, {"op":"16"},
   {"op":"2B","args":[8,13],"label":"on"}, {"op":"16"}
 ]}
```

이 예는 플래그 `7E:219F` 의 bit0에 따라 인물을 (5,13) 또는 (8,13)으로 옮기고 멈춥니다. 명령의 `op` 는 두 자리 16진 문자열, `args` 는 바이트 정수 목록입니다. `03`·`06`·`07` 의 마지막 변위 바이트를 `target` 라벨로 바꿔 적을 수 있습니다. `03` 은 명령 주소+1, `06`·`07` 은 명령 주소에서 변위를 계산합니다. 변위는 −128~127이고 도착점은 스크립트 안의 명령 첫 바이트여야 합니다. `04` 절대 점프와 `05`·`37` 네이티브 주소는 원시 바이트 인자를 그대로 씁니다.

- `patch` 는 `address` 가 원본 인물 슬롯이고 `length` 가 원본 길이와 같은지 확인합니다. 길이 바이트를 유지하고 남는 부분은 `00`(그 자리)으로 채웁니다. 원본보다 길면 거부합니다.
- 바뀐 슬롯은 도달 가능한 명령 흐름이 슬롯 끝이나 명령 중간으로 넘어가는지 검사합니다. 외부 절대 점프·네이티브 호출의 동작까지 해석하지는 않습니다. 원본과 같은 패치는 원본의 끝 명령을 보존합니다.
- 모르는 명령, 인자 수·범위 오류, 중복·미정의 라벨, 잘못된 상대 분기를 거부합니다. 길이 바이트 한계가 있어 새 명령 본문도 1~255바이트여야 합니다.
- `encode` 는 길이 바이트를 뺀 명령 본문만 내보냅니다. 롬에 쓸 때는 `patch` 와 빌더의 슬롯·원본 대조를 거칩니다.

### 스크립트 쓰기 검증

이벤트 시작점 106개(2,420바이트)와 연속 영역 86개(1,664바이트), 인물 고유 스크립트 1,034개(21,559바이트)를 JSON으로 내보내고 다시 인코딩해 원본과 모두 같았습니다. 이벤트 두 집합은 일부가 겹칩니다. 인물의 낮·밤 참조는 1,274개입니다.

MesenCE에서는 번호 표와 이벤트 표를 거쳐 `60:8000`의 플래그 변경·보행·종료 명령을 실행했습니다. 두 경우 모두 주인공이 (9,11)에서 (11,11)로 갔고 `7E:220F`에 `40`이 들어갔습니다. 인물은 `03`의 무조건 분기, `06`의 플래그 꺼짐·켜짐, `07`의 사각형 안·밖을 시험해 다섯 경우 모두 예상 좌표에 멈췄습니다. 이 확인은 시험용 명령의 실행 결과이며 모든 이야기 장면을 다시 돌린 것은 아닙니다.

재현은 [스크립트 쓰기 일지](../journal/2026-10-26-53-scriptwrite.md)에 있습니다.

### 인물 목록 재배치 `dq5npcrelocate/1`

`sfc/dq5/tools/dq5npcrelocate.py`는 스크립트 길이를 바꾸고 인물 목록을 확장 뱅크로 옮깁니다. 따로 적지 않으면 인물 수·순서·등장 조건과 낮밤 스크립트 공유 관계를 유지하고, 아래 「인물 수·순서와 조건 표」의 키로 바꿀 수 있습니다. 기존 슬롯 안에서만 바꾸는 `dq5npcwrite.py`와 달리, 뒤따르는 레코드의 주소도 다시 계산합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc dump -o work/npc-lists.json
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc patch work/npc-lists.json \
  -o work/npc-lists.dq5patch.json --report work/npc-layout.json
uv run --locked python sfc/dq5/tools/dq5npcrelocate.py rom/dq5.sfc check
```

입력의 `format`은 `dq5npcrelocate/1`, `scripts`는 `{address, commands}` 배열입니다. `address`는 **원본 길이 바이트**의 CPU 주소 문자열(`05:A84F` 등)이고, `commands`는 `dq5npcscript/1`과 같은 명령 목록입니다. 입력에서 빠진 스크립트는 원본을 유지합니다. 빈 배열이면 내용을 바꾸지 않고 목록만 옮깁니다.

- 새 스크립트는 1~255바이트이며, 바뀐 명령의 상대 분기를 새 주소에서 검사합니다. 명령 `04`의 절대 점프는 지원하지 않습니다.
- 기본 `--base 32:8000`에는 그룹 포인터 54개와 기본 목록을, `--alt 33:8000`에는 대체 목록을 놓습니다. 두 목적지는 서로 다른 `30`~`3F` 뱅크여야 하고 각 덩어리는 한 뱅크 안에 들어가야 합니다. 최소 롬 크기는 2MB입니다.
- 원본 639목록·2,483인물 레코드·1,034스크립트를 유지하면 기본 20,173바이트·대체 23,986바이트입니다. 기본 로더의 뱅크·그룹 포인터 주소, 대체 로더의 뱅크와 선택 표 296항목의 목록 주소를 고칩니다. 원본 영역을 고칠 때는 `orig`를 확인합니다.
- `--report`에는 목록·인물·스크립트의 옛 주소→새 주소와 영역별 크기를 저장합니다. 코드 안의 임의 직접 참조는 자동으로 바꾸지 않습니다.
- 패치는 원본 롬에서 만듭니다. 기존 슬롯을 고치는 패치와 합쳐도 옛 슬롯의 변경이 새 목록에 전파되지는 않으므로, 옮길 명령은 이 입력의 `commands`에 적습니다. 인물 필드·등장 조건은 `--records`로 `dq5npcrecord/1` 문서를 넘깁니다([아래](#인물-레코드등장-조건-dq5npcrecord1)). 다른 도구와의 확장 영역 겹침은 빌더가 검사합니다.

원본 왕복에서는 낮·밤 인물 3,474개와 스크립트를 비교했습니다. 게임에서 기본 맵 낮밤 692쌍과 대체 목록 2쌍, 합계 694쌍의 인물 표와 새 포인터가 일치했습니다(1,581슬롯·활성 포인터 649개). 실제 게임에서는 길이를 39바이트로 늘린 선실·기본 공유·대체 공유 스크립트 5건의 좌표·이동 상태·포인터를 확인했습니다([일지](../journal/2026-10-26-57-npc-relocate.md)).

`MESENCE`를 설정하고 다음 명령으로 기본 맵의 낮밤 전수 비교와 긴 스크립트 실행을 재현합니다. `--all`을 빼면 대표 장면 8쌍만 비교합니다. 결과·덤프·시험 롬은 출력 폴더의 새 하위 폴더에 남습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcrelocatecheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/npc-relocate-check --all --mutations --jobs 6
```

#### 인물 수·순서와 조건 표 (`lists`·`new_lists`·`overrides`·`no_npc`)

같은 문서에 아래 키를 더하면 목록 구조와 등장 조건 표를 다시 씁니다. 빠진 키는 원본 그대로입니다.

```json
{
  "format": "dq5npcrelocate/1",
  "lists": [{"list": "05:8CD4", "entries": [
    {"from": 1}, {"from": 0},
    {"from": 3, "time": "day", "fields": {"x": 24, "y": 12, "talk": 768}}]}],
  "new_lists": [{"name": "extra", "entries": [{"from": {"list": "05:8CD4", "index": 1}}]}],
  "overrides": [{"map": "02/06", "flag": 29, "when": "off", "mask": 16, "list": "new:extra"}],
  "no_npc": [{"map": "17/00", "flag": 2, "when": "on", "mask": 128}]
}
```

- **`lists`**: 원본 목록 하나(`list` 는 그 시작 주소)의 새 엔트리 차례입니다. 항목마다 `from` 으로 원본 엔트리를 고릅니다. 같은 목록이면 번호, 다른 목록이면 `{"list", "index"}` 입니다. 빠진 엔트리는 지워지고, 같은 엔트리를 여러 번 쓰면 복사됩니다. 항목에 `time`·`fields`·`day`·`night` 를 더하면 그 사본을 [`dq5npcrecord/1`](#인물-레코드등장-조건-dq5npcrecord1) 과 같은 규칙으로 고칩니다. 스크립트는 원본 엔트리의 것을 따라가고, `scripts` 로 바꾼 스크립트도 사본마다 들어갑니다.
- **`new_lists`**: 새 대체 목록입니다. 대체 목록 뒤에 놓이며 `overrides` 에서 `new:이름` 으로 가리킵니다. 엔트리의 `from` 은 `{"list", "index"}` 만 받습니다.
- **`overrides`**: 대체 표 전체입니다. 표 순서대로 처음 참인 항목을 쓰므로 원본 항목을 남기려면 함께 적습니다. `list` 는 원본 대체 목록 시작(`10:xxxx`) 또는 `new:이름` 입니다. 이 키가 있으면 표를 대체 목록 뒤로 옮기고 `12:82FB` 다섯 바이트를 `JSL 새 루틴; RTS` 로 덮습니다. 새 루틴은 데이터 뱅크를 `7E` 로 두어 플래그를 `$2190,Y` 로 읽고, 표는 긴 주소 `,X` 로 읽고, `$A7` 에 대체 목록 뱅크를 넣습니다. 이때 `12:833C` 와 옛 표는 쓰지 않습니다.
- **`no_npc`**: 빈 맵 표 전체(63항목까지)를 `12:839C` 에 다시 씁니다. 43항목을 넘으면 옛 대체 표 자리를 덮으므로 대체 표도 함께 옮깁니다.
- 조건 행의 `map`·`flag`·`when`·`mask` 규칙은 `dq5npcrecord/1` 과 같습니다. `--records` 의 조건 표 수정과 이 키들은 함께 쓸 수 없고, `--records` 로 고친 엔트리를 `lists` 에서 다시 고칠 수도 없습니다.
- **슬롯 한도**: 맵·낮밤마다 「8 + 놓이는 인물 수 + 맵 OBJ 물체 수」(물체까지 놓은 뒤의 `$81`, [맵 형식의 인물 슬롯](dq5-map-format.md#인물-슬롯-81))를 셉니다. 기본은 그 맵의 원본 목록들이 같은 시간대에 쓰던 최댓값까지입니다. `--allow-growth` 를 주면 원본 전체 최댓값 `1F` 까지 늘리고, 원본보다 늘어난 맵을 출력합니다. 이 한도는 `--records` 만 줄 때도 봅니다. 낮밤 전환이나 대체 항목의 목록 바꾸기로 인물이 늘면 같은 기준을 넘을 수 없습니다. 맵을 놓은 뒤 `7E:1983` 부터 슬롯을 더 쓰는 장면 코드(`04:FB1C` 등)는 따지지 않으므로, 그런 장면이 있는 맵에서는 늘리지 않습니다.
- 인물을 지우거나 순서를 바꾸면 그 뒤 인물의 슬롯 번호가 달라집니다. 이벤트 코드가 슬롯 번호를 직접 쓰는 맵에서는 장면이 다른 인물을 움직입니다.
- 대체 표를 옮기면 표(항목 × 6 + 1바이트)와 루틴 102바이트가 `--alt` 뱅크의 대체 목록 뒤에 붙고, 그 덩어리가 한 뱅크에 들어가야 합니다. `--report` 에는 `override_table`·`override_find` 주소와 늘어난 슬롯(`slot_growth`)이 더해집니다. 같은 엔트리를 여러 번 쓰면 `entries`·`scripts` 대응표에는 첫 사본만 남습니다. 대체 표가 가리키지 않는 새 목록과, `12:82FB` 가 원본 루틴이 아닌 롬은 받지 않습니다.

`dq5npclistcheck.py` 가 롬 세 벌(목록 구조, 옮긴 조건 표, 슬롯 1F 까지 늘림)을 원본과 함께 02/06·01/01·21/00 에서 10장면 돌립니다. 장면마다 로더 직후 인물 표 23칸·목록 끝 주소(`$A5`~`$A7`)와 맵을 다 놓은 직후 `7E:1983` 을 롬에서 예측한 값과 견주고, 더한 인물에게 말을 겁니다. `--objects` 를 주면 맵 OBJ 물체가 있는 33개 맵의 낮·밤 물체 슬롯 수(66장면)도 잽니다.

```sh
MESENCE="$MESENCE" uv run --locked python sfc/dq5/tools/dq5npclistcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/npclistcheck --objects
```

| 장면 | 변경 롬 | 원본 롬 |
| --- | --- | --- |
| 02/06 낮, 목록 [둘째, 첫째, 넷째를 낮·(24,12)·대화 `300` 으로] | 3명이 그 순서로, `$1983` = `0B`, 말을 걸자 메시지 `6C6` | 2명, `0A`, 메시지 `129` |
| 02/06 밤, 같은 롬 | 0명(밤 인물을 지움) | 2명 |
| 02/06 낮, 맨 앞에 더한 대체 항목 → 새 목록 | 새 목록 2명, 메시지 `6C6` | 기본 목록 |
| 01/01, 빈 맵 표 44번째 항목 | 인물 없음, `$81` = `08` | 5명 |
| 21/00, 옮긴 표의 원래 항목 | 옮긴 `10:CB92` 사본 10명 | `10:CB92` 10명 |
| 02/06 낮, `--allow-growth` 로 23명 | 23명, `$1983` = `1F`, 메시지 `6C6` | |

10장면 모두 인물 표와 목록 끝 주소가 예측과 같았고, 33개 맵 낮·밤 66장면의 물체 수도 모두 같았습니다.

### 보물상자·조사 보상 (`dq5chest/1`)

`dq5chestwrite.py`는 보물상자와 서랍·항아리·통, 발밑, 두 칸 앞, 아래층 상자의 기존 표와 필드 조사 코드의 보상 하나를 편집합니다. 원본 슬롯 수와 순서를 유지하고, 지정하지 않은 필드·미사용 바이트·종료자는 보존합니다. 결과는 바뀐 항목의 원본 바이트를 `orig`에 담은 `dq5patch/1` 목록입니다. 읽기 형식과 처리 루틴은 [맵 형식의 보물상자 절](dq5-map-format.md#보물상자와-タンスツボタル-12e4c9)에 있습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5chestwrite.py rom/dq5.sfc dump -o work/chests.json
uv run --locked python sfc/dq5/tools/dq5chestwrite.py rom/dq5.sfc patch work/chests.json -o work/chests.patch.json
uv run --locked python sfc/dq5/tools/dq5chestwrite.py rom/dq5.sfc check work/chests.json
uv run --locked python sfc/dq5/tools/dq5build.py rom/dq5.sfc build work/chests.patch.json \
  -o work/chests.sfc --ips work/chests.ips
```

`check`의 입력을 생략하면 필드 조사 코드까지 원본 전체를 다시 쓰고 읽어 비교합니다. `field`가 없는 입력은 그 코드를 읽지 않으므로, 다른 패치가 그 코드를 바꾼 롬에서도 표만 고칠 수 있습니다. 입력이 있으면 편집 결과를 메모리에 적용한 뒤 다시 읽습니다. 두 경우 모두 일반 상자 맵 83개의 셀 수와 등록 개수를 대조합니다.

#### 입력과 고정 한도

형식 표시는 `"format": "dq5chest/1"`입니다. 아래 목록 중 필요한 것만 넣을 수 있고, 각 항목은 `index`와 바꿀 필드만 적어도 됩니다. 숫자는 모두 JSON 정수이며 `true`·문자열은 받지 않습니다. 모르는 필드·중복 번호·같은 표에서 먼저 나오는 항목에 가려지는 중복 위치는 거부합니다.

| 목록 | 항목 수 | 필드 (`index` 외) | 롬 위치 |
| --- | ---: | --- | --- |
| `chests` | 161 | `reward` | `1E:EE4E` |
| `chest_maps` | 83 | `group`, `map`, `count` | `1E:EF90` |
| `search` | 86 | `group`, `map`, `x`, `y`, `reward`, `flag_index`, `mask` | `1F:F5CB` |
| `foot` | 18 | 위 필드와 `layer` | `1E:F08B` |
| `ahead` | 17 | `group`, `map`, `x`, `y`, `reward`, `flag_index`, `mask` | `1E:F435` |
| `lower` | 11 | 위 필드 | `1E:F4DF` |
| `field` | 1 | `reward` | `12:E61F`(`12:E5F2` 의 즉시값) |

`index`는 해당 표의 0부터 시작하는 슬롯 번호입니다. `group`·`map`은 디코더가 아는 364개 맵 중 한 곳이어야 합니다. 새로 지정한 좌표는 그 맵의 크기 안이어야 합니다. 서랍·항아리·통의 `+4`는 엔진이 읽지 않는 바이트이므로 입력으로 받지 않고 원본을 보존합니다. `foot.layer`는 방향이 아니라 주인공 층(`$C3`)입니다.

`field`는 표가 아니라 [필드 조사 코드](dq5-map-format.md#필드-12e5a2)의 `LDA #` 즉시값입니다. `dump`는 그 코드에서 읽은 `x`·`y`·`width`·`height`(필드 8픽셀 칸)와 `flag_index`·`mask`(`7E:2190 + flag_index`)도 내지만, 입력에서는 `reward`만 바꿀 수 있습니다. 다른 값을 바꾸면 거부합니다. 같은 칸과 열림 플래그를 뱅크 `01`의 빛나는 풀 블록 코드가 따로 갖고 있어서, `12:E5F2`만 고치면 빛과 보상 자리가 어긋나기 때문입니다. `field`의 `reward`는 물건(`0000`~`00FF`)과 금화(`0100`~`CFFF`)만 받습니다. 쓰기 전에 `12:E5A7`의 호출과 `12:E5F2`~`E62F`의 명령 바이트를 확인하고, 열림 시험(`BRK 0B`)과 기록(`$1E80`·`$1E81`)의 번호·마스크가 같아야 읽습니다.

`reward`는 엔진의 16비트 보상 값입니다. `0000`~`00FF`는 물건 번호, `0100`~`CFFF`는 값에서 `0100`을 뺀 금화, `D000`~`D009`는 기존 특수 처리, `FFFC`~`FFFF`는 잠김·몬스터·빈 상자입니다. 이 사이의 지원하지 않는 값은 거부합니다. 특수 처리의 내용과 맵·시대·플래그에 따른 예외 코드는 바꾸지 않습니다. 예를 들어 일반 상자 2를 321G로, 선실 서랍 31을 432G와 다른 열림 비트로 바꾸려면 다음처럼 씁니다.

```json
{
  "format": "dq5chest/1",
  "chests": [{"index": 2, "reward": 577}],
  "search": [{"index": 31, "reward": 688, "flag_index": 4, "mask": 128}]
}
```

#### 상자 위치와 열림 플래그

일반 상자는 좌표와 열림 비트를 표에 직접 저장하지 않습니다. `chest_maps` 앞 항목의 `count` 합계에, 맵 셀 버퍼에서 상자를 센 순서를 더해 `chests.index`를 얻습니다. 위치를 옮기려면 맵 쓰기 도구로 상자 셀 배치를 바꿉니다. 맵 쓰기를 먼저 적용한 롬에서 보상 목록을 만들면 변경된 셀 배치를 기준으로 검사할 수 있습니다.

`chest_maps`는 일반 실내 그룹 `00`~`35`만 받으며, 총 `count` 161을 유지해야 하며, 연결이나 개수가 바뀌면 실제 맵 상자 셀 수와 일치해야 합니다. 맵 표의 항목 순서를 바꾸거나 앞쪽 개수를 바꾸면 뒤 상자의 번호·보상·열림 비트 연결도 달라집니다. 기존 세이브의 비트를 자동으로 옮기지는 않습니다.

| 목록 | 열림 비트 |
| --- | --- |
| 일반 상자 번호 `n` | `7E:2210 + (n >> 3)`, 마스크 `80 >> (n & 7)` |
| `search` | `7E:222C + flag_index`, `mask` |
| `foot` | `7E:2240 + flag_index`, `mask` |
| `ahead`·`lower` | `7E:2190 + (flag_index \| 80)`, `mask` |
| `field` | `7E:2190 + flag_index`, `mask`(원본 `21B3 & 10`, 바꿀 수 없음) |

`flag_index`는 원본 한 바이트(0~255), `mask`는 1~255입니다. 두 칸 앞·아래층 상자의 `flag_index` 상위 비트도 원본대로 보존합니다. 여러 비트를 묶는 마스크와 다른 항목의 비트 공유는 허용합니다. 새 비트가 이야기 진행이나 다른 보상에 쓰이는지는 편집자가 확인해야 합니다.

#### 확인한 범위와 남은 것

원본 376항목 1,731바이트를 다시 써도 바이트가 같고, 일반 상자 맵 83개의 개수가 셀 버퍼와 일치했습니다. 다음 명령은 입력 JSON부터 롬·IPS·장면 준비·실제 컨트롤러 조사까지 재현하며, 결과를 새 출력 하위 폴더에 남깁니다.

```sh
MESENCE="$MESENCE" uv run --locked python sfc/dq5/tools/dq5chestcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/chest-check
```

원본·패치 롬 6쌍, 12회 실행을 비교했습니다. `--case 이름`을 여러 번 주면 그 사례만 돌립니다.

| 사례 | 장면 | 원본 | 패치 |
| --- | --- | --- | --- |
| `chest` 상자 2 | 01/02 (34,31) | 물건 `33`, `2210 & 20` | 321G, 같은 비트 |
| `search` 서랍 31 | 선실 (3,5) | 물건 `A1`, `222F & 01` | 432G, `2230 & 80`, `222F` 는 0 |
| `foot` 항목 0 을 선실 (3,5)·층 1로 | 선실 (3,5) | 서랍을 엶 | 543G, `2243 & 40`, `222F` 는 0 |
| `ahead` 항목 11 | 03/04 (10,10) 에서 위로 한 칸 | 물건 `5F`, `223D & 08` | 654G, `223E & 02`, `223D` 는 0 |
| `lower` 항목 3 | 51/51 (18,37)·층 2 에서 위로 한 칸 | 물건 `B1`, `2228 & 08` | 765G, `2229 & 08`, `2228` 은 0 |
| `field` | 필드 (22,166), 밤·`21AA.0` | 물건 `CA`, `21B3 & 10` | 876G, 같은 비트 |

조사 종류 메시지(상자·아래층 `131`, 서랍 `12F`, 발밑·두 칸 앞·필드 `12B`)·`12:F43B`에서 실제 조회한 보상·금화 증가·열림 비트를 확인했습니다. 두 칸 앞 상자는 마지막 메시지 132 가 나오고 40프레임 뒤에 `12:F847` 이 비트를 쓰므로(쓰기 감시), 조사 입력의 마지막 대기는 그보다 길어야 합니다(220프레임).

목록 증설·재배치, 일반 상자 수 161의 증설, 상자 그림 배치 자동 편집, 필드 조사의 칸·열림 플래그 변경은 이번 범위 밖입니다. 좌표가 맵 안이라는 검사만으로 알맞은 가구·상자 속성이 그 자리에 생기거나 걸어갈 수 있게 되지는 않습니다.

표를 늘리거나 옮기는 데 필요한 것이 아직 정리되지 않았습니다. 표마다 시작 주소를 쓰는 명령이 몇 개이고 어느 뱅크 기준인지는 `タンス` 표(`1F:F5CB`, `12:FB9D` 안 4개)만 적혀 있습니다. 일반 상자 열림 비트는 161개가 `7E:2210`~`2224` 를 쓰고 `2228` 부터는 아래층 상자·서랍 비트라, 상자 수를 늘리면 새 비트 자리부터 정해야 합니다.


### 실내 출구·영역 이동 (`dq5connections/1`)

`dq5exitwrite.py`는 실내 맵의 기존 출구 목적지와 영역 이동 레코드를 고칩니다. 출구 수·종류·길이, 맵마다의 끝 표시, 영역 이동 레코드 수와 색인은 원본 그대로 둡니다. 결과는 바뀐 레코드의 원본 바이트를 `orig`에 담은 `dq5patch/1` 목록입니다. 읽기 형식은 [맵 형식의 출구 절](dq5-map-format.md#출구-2af6b8)과 [영역 이동 절](dq5-map-format.md#영역-이동-00cdec)에 있습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5exitwrite.py rom/dq5.sfc dump -o work/connections.json
uv run --locked python sfc/dq5/tools/dq5exitwrite.py rom/dq5.sfc patch work/connections.json -o work/connections.patch.json
uv run --locked python sfc/dq5/tools/dq5exitwrite.py rom/dq5.sfc check work/connections.json
```

`check`의 입력을 생략하면 원본 전체를 내보내고 다시 패치해 쓰기가 0개인지 봅니다. 입력이 있으면 빌더로 롬을 만든 뒤 같은 입력을 다시 패치해 쓰기가 남지 않는지, 만든 롬을 다시 읽고 인코딩해도 같은지 확인합니다. 원본 고정 표는 출구 569개 1,219바이트(`2A:ED61` 이상 `2A:F224` 미만), 일반 영역 이동 405개 4,860바이트와 색인 595바이트, 고층 목록 16개 316바이트입니다.

#### 입력

형식 표시는 `"format": "dq5connections/1"`이고 `exits`·`triggers` 배열에 고칠 레코드만 넣습니다. 각 항목은 `map`(`"01/00"`처럼 16진 그룹/맵)과 그 맵의 0부터 센 `index`, 바꿀 필드만 적습니다. 숫자는 JSON 정수만 받고, 모르는 필드·같은 레코드 두 번 지정·원본 목록에 없는 맵은 거부합니다.

| 출구 `kind` | 길이 | 필드 |
| --- | ---: | --- |
| `same-group` | 2 | `destination_map`(0~31), `exit`(도착 맵의 출구 번호) |
| `other-group` | 3 | 위 필드와 `group` |
| `position` | 5 | `destination_map`, `x`, `y`, `layer`(도착 층 `$C3`), `group` |
| `special` | 1 | `special`(아래 5비트, `2A:F7B2` 특수 처리) |

`kind`는 바꿀 수 없습니다. 같은 그룹 출구를 좌표 출구로 바꾸는 것처럼 길이가 달라지는 편집은 표를 다시 배치해야 하므로 이 도구의 범위 밖입니다. 목적지 맵은 원본 목록에 있어야 하고, `exit`는 목적지 맵의 출구 수보다 작아야 합니다. 도착 칸은 목적지 맵의 그 번호 출구 셀 한 칸 왼쪽입니다.

영역 이동은 `rect`(x0, y0, x1, y1), `source_layer`, `flags`, `destination_group`, `destination_map`, `x`, `y`, `span_raw`, `destination_layer`를 받습니다. `source_layer`는 들어서는 주인공의 층과 같아야 발동하는 값이고, `destination_layer`는 도착한 뒤의 층입니다. 둘 다 방향이 아닙니다. `destination_group` bit7은 필드로 나가는 레코드이며 목적지 맵을 검사하지 않습니다.

- **음수 가장자리**: 원본 사각형 8개는 x0 = `FF`, x1 = `00`처럼 맵 왼쪽 밖을 가리킵니다. 주인공 X·Y(`$C1`·`$C2`)가 음수(bit7)이면 엔진은 상한 대신 시작 좌표와 같은지만 봅니다(`00:CDFE`→`CE0C`, `00:CE13`→`CE21`). 그래서 시작 좌표 bit7 이 켜진 쪽은 시작<끝 검사를 하지 않고, 양수 쪽만 끝이 시작보다 커야 합니다.
- **`span_raw`**: `FA`~`FE` 같은 원본 값을 그대로 둡니다. 사각형이 넓으면 도착 칸은 들어선 자리에 비례해 정해지므로(`2A:F650`), 사각형 크기를 바꾸면 같은 자리에서 들어서도 도착 칸이 달라집니다.
- **고층 공유 목록**: 그룹 `$50` 이상은 여러 맵이 같은 목록을 씁니다. `dump`는 공유 레코드에 `shared_maps`를 붙이며, 그 레코드를 바꾸려면 같은 `shared_maps`를 모두 적어야 합니다. 공유하지 않는 레코드에 `shared_maps`를 적어도 거부합니다.

#### 게임 실측

`dq5exitcheck.py`가 변경 롬 세 벌과 원본 롬에서 같은 자리를 밟는 24장면을 재현합니다(표를 옮긴 롬의 장면은 [아래](#게임-실측-1)). 입력·패치·롬·IPS·장면 기록은 실행마다 새 하위 폴더에 남습니다.

```sh
MESENCE="$MESENCE" uv run --locked python sfc/dq5/tools/dq5exitcheck.py rom/dq5.sfc \
  --state work/state/ship.mss --out work/exitcheck
```

| 장면 | 변경 | 변경 롬 | 원본 롬 |
| --- | --- | --- | --- |
| 같은 그룹 출구 | 01/00 출구 1 → 01/09 출구 1 | 01/09 (24,5) | 01/03 (19,5) |
| 다른 그룹 출구 | 21/02 출구 0 → 01/03 출구 0 | 01/03 (19,5) | 0E/03 (38,67) |
| 좌표 출구 | 01/01 출구 0 → 01/04 (16,6) 층 1 | 01/04 (16,6) 층 1 | 01/00 (21,28) 층 2 |
| 출발층 | 01/00 영역 6 `source_layer` 1 → 2, 목적지 01/04 | 층 2로 들어서 01/04 (16,7) | 그대로 01/00 (32,60) |
| 고층 공유 목록 | 50/50·50/51 공유 레코드 → 01/04 | 두 맵 모두 01/04 (17,7) | 두 맵 모두 05/01 (33,47) |
| 음수 가장자리 | 01/06 영역 0 의 y 범위 6~11 → 6~8 | y=8 은 01/04 (16,9), y=10 은 필드로 나감 | y=8 은 01/04 (16,6), y=10 도 01/04 (16,8) |
| 사각형 이동 | 01/00 영역 6 을 (32,58) 한 칸으로 | (32,58) 에서 01/04 (16,7), 옛 자리 (32,60) 은 그대로 | (32,58) 은 그대로, (32,60) 에서 01/01 |
| 이동 효과음 | 01/06 영역 0 `flags` `80` → `C0` | 01/04 (16,6), `2A:F4D1` 효과음 없음 | 01/04 (16,6), 효과음 `34 02` 한 번 |
| 속성 33 계단 | (변경 없음) 01/0A (9,10) `+4` 를 실행 중 `85` 로 | 2A/00 (18,11) | 그대로 01/0A (8,10) |

출구는 reader 의 도착 칸 계산과 같은 칸에 섰고, 영역 이동은 걸어 들어온 방향으로 한 칸 더 간 자리에 섰습니다. 밟는 자리는 출구마다 달랐습니다. 01/00 출구 셀 (60,80) 은 주인공 x 60 으로 내려가 발동했고, 21/02 의 (112,7) 은 x 112 로는 지나가기만 하고 x 111 에서 발동했습니다. 01/0A (9,10)·2A/00 (19,11) 의 다른 그룹 출구는 원본 롬에서 어떻게 밟아도 출구 처리(`2A:F6FD`)가 불리지 않았습니다. 두 블록은 위아래 네 칸의 `+4` 가 모두 속성 `33`(출구 셀은 `B3`)입니다. 01/0A 에서 오른쪽 칸 (9,10) `+4` 만 실행 중에 `85` 로 바꾸자 같은 걸음으로 2A/00 (18,11) 에 섰습니다. 출구 표는 맞고, 셀 속성이 출구 처리를 막습니다. 계단 판정 `00:E2C5` 는 속성 `33` 도 받으므로 막는 곳은 그 뒤입니다. `00:C9E5` 가 속성 `33` 이면 `02:BB37` 을 부르는 갈래가 후보이지만 확인하지 않았습니다. 배 맵(17/xx)은 `dq5warp.lua`가 `2A:EFF5`부터 5바이트를 덮어 17/01 의 항목까지 바뀌므로 이 실측에 쓰지 않습니다.

출구 레코드 안의 `FF` 는 받지 않습니다. 엔진(`2A:F711`)은 다른 그룹을 `FF` 가 나올 때까지 한 바이트씩 건너뛰므로 레코드 안의 `FF` 가 그룹을 끊기 때문입니다. 원본 569개에는 `FF` 바이트가 없고, `check` 는 빌드한 롬에서 같은 방식으로 54개 그룹 머리를 찾아 표 구조와 같은 곳에 닿는지 확인합니다.

`flags` bit6 은 발동 조건이 아닙니다. 꺼진 레코드는 `2A:F4C6` 에서 `2A:F4CA` 로 가서, 탈것 상태 `$1954` 가 4 가 아니면 효과음 `BRK 19 34 02` 를 한 번 더 내고 켜진 레코드와 같은 길(`2A:F4D5`)로 이어집니다. 01/06 영역 0 을 `80` → `C0` 으로 바꾸자 같은 자리에서 같은 01/04 (16,6) 에 섰고 `2A:F4D1` 만 지나가지 않았습니다.

출구·레코드 증설과 재배치, 출구 종류 변경은 아래 [표 옮기기](#실내-출구영역-이동-표-옮기기-dq5exittables1)가 맡습니다. 새 맵 번호 연결은 남았습니다.

### 실내 출구·영역 이동 표 옮기기 (`dq5exittables/1`)

`dq5exitreloc.py`는 출구 목적지 표, 일반 영역 이동 레코드와 색인, 고층 목록 16개를 통째로 다시 씁니다. 맵마다 출구·영역 이동 수를 바꾸고, 출구 종류(길이)를 바꾸고, 영역 이동이 없던 맵을 색인에 넣을 수 있습니다. 표가 원래 자리에 들어가면 원래 자리에 쓰고 코드는 고치지 않습니다. 넘치면 `--exits-at`·`--records-at`·`--index-at`·`--high-at` 으로 준 자리로 옮기고, 표를 찾는 코드의 즉값만 고칩니다.

```sh
uv run --locked python sfc/dq5/tools/dq5exitreloc.py rom/dq5.sfc dump -o work/exit-tables.json
uv run --locked python sfc/dq5/tools/dq5exitreloc.py rom/dq5.sfc patch work/exit-tables.json \
  -o work/exit-tables.dq5patch.json --exits-at 2A:D812 --records-at 3F:8000
uv run --locked python sfc/dq5/tools/dq5exitreloc.py rom/dq5.sfc check work/exit-tables.json \
  --exits-at 2A:D812 --records-at 3F:8000
```

`check` 의 입력을 생략하면 원본을 읽어 다시 직렬화한 6,990바이트가 원래 바이트와 같은지(쓰기 0개) 봅니다. 입력이 있으면 빌더로 롬을 만들고, 코드의 즉값이 가리키는 자리에서 표를 다시 읽어 입력과 같은지, 맵마다 엔진 순서(출구는 `2A:F711` 의 그룹 건너뛰기, 영역 이동은 `01:9430` 의 개수 더하기)로 찾은 레코드가 입력과 같은지, 만든 롬에 같은 입력을 다시 패치하면 쓰기가 0개인지 확인합니다. 고정 슬롯만 고치는 `dq5exitwrite.py` 와는 한 빌드에 함께 넣을 수 없습니다. `dq5exitreloc.py` 는 쓰기가 하나라도 있으면 원래 표 자리(`2A:D812`~`2A:F223`, `01:9635`~`01:9770`) 가운데 새 표가 들지 않은 곳도 같은 바이트로 써서 맡으므로, 둘을 함께 넣으면 빌더가 겹침으로 거부합니다. 표를 옮긴 롬을 주면 `dq5exitwrite.py` 는 옛 자리를 읽지 않고 오류를 냅니다. `--…-at` 을 빼면 그 표는 지금 자리(원래 롬이면 원래 자리, 옮긴 롬이면 옮긴 자리)에 둡니다.

#### 입력

```json
{"format": "dq5exittables/1",
 "exits": [{"map": "00/00", "records": [{"kind": "special", "special": 0}]}, "…"],
 "triggers": [{"map": "01/00", "records": [{"rect": [32, 58, 33, 59], "source_layer": 2, "flags": 192,
   "destination_group": 1, "destination_map": 4, "x": 16, "y": 6, "span_raw": 1, "destination_layer": 1}]}, "…"],
 "high_triggers": [{"maps": ["50/50", "50/51"], "records": ["…"]}, "…"]}
```

- **`exits`**: 그룹 `00`~`35` 의 맵 346개를 맵 번호 순서로 모두 담습니다. 레코드 필드는 [위 표](#입력-1)와 같고 `kind` 를 바꿀 수 있습니다. 맵의 끝 표시(bit7)는 도구가 마지막 레코드에 붙입니다. 맵마다 레코드가 하나 이상이어야 하고(출구가 없는 맵은 `special` 0 하나), 레코드 안의 `FF` 는 받지 않습니다. 목적지 맵은 원본 목록에 있어야 하고, `exit` 는 입력에 적은 목적지 맵의 출구 수보다 작아야 합니다.
- **`triggers`**: 색인 순서입니다. 그룹 `00`~`35` 맵만, 맵마다 한 번, 레코드 1~255개입니다. 없던 맵을 넣으면 색인 항목(3바이트)이 하나 늘어납니다. 레코드 검사는 `dq5connections/1` 과 같습니다.
- **`high_triggers`**: `01:94B4` 가 고르는 목록 16개를 원래 순서로 담습니다. `maps` 는 그 목록을 쓰는 맵이고 바꿀 수 없습니다. 어느 맵이 어느 목록을 쓰는지는 코드가 정하므로, 공유 목록을 바꾸면 그 맵들이 함께 바뀝니다. 레코드는 0~255개입니다.
- 출구 레코드를 더해도 맵의 출구 셀이 늘지 않으면 밟을 수 없습니다. 출구 번호는 셀 버퍼에서 출구 셀을 센 순서이므로, 새 출구 셀은 맵 자료(`dq5mapwrite.py`)에서 만듭니다.

#### 자리와 고치는 코드

| 표 | 원래 자리(바이트) | 옮길 때 고치는 코드 | 둘 수 있는 뱅크 |
| --- | --- | --- | --- |
| 출구 목적지 | `2A:ED61` (1,219) | 뱅크 `2A` 안이면 `2A:F70A`·`F70E` 즉값 둘. 다른 뱅크면 `2A:F709` 8바이트를 `JSL 스텁` + `NOP` 넷으로, `LDA ($84)` 5곳(`F711`·`F71B`·`F738`·`F74B`·`F755`)과 `LDA ($84),Y` 6곳(`F76E`·`F773`·`F778`·`F77D`·`F7C9`·`F7D6`)을 `[$84]`·`[$84],Y` 로. 스텁 13바이트(`$84`~`$86` 을 채우고 `RTL`)는 표 바로 앞 | `00`~`7D` |
| 영역 이동 색인 | `2A:EB0E` (595) | `01:943E`(DB), `01:9449`·`9454`·`9459`·`9470`(주소) | `00`~`3F` |
| 영역 이동 레코드 | `2A:D812` (4,860) | `01:94A2`(주소), `01:94AD`(뱅크) | `00`~`3F` |
| 고층 목록 16개 | `01:9635` (316) | 목록마다 `01:94B4` 이하의 `LDA long`(개수 주소), `LDX #`(레코드 주소), `LDA #`(뱅크) | `00`~`3F` |

표마다 한 뱅크의 `8000`~`FFFF` 안에 들어가야 하고, 네 표끼리 겹치면 거부합니다. 둘 수 있는 곳은 원래 네 표 자리(`2A:D812`~`2A:F223`, `01:9635`~`01:9770`. 표를 옮기면 비므로 다른 표를 넣어도 됩니다), 위 [빈 자리 지도](#원래-롬)의 원래 롬 빈 자리, 늘린 뱅크 `30`~`7D` 입니다. 기본 새 자리는 없습니다. `30`~`3F` 는 텍스트·DQ4 타이틀, `60`~ 은 스크립트·자료 표가 쓰므로 [새 뱅크 나누기](#새-뱅크-나누기제안)에서 맡은 곳과 겹치지 않게 고릅니다. 다른 도구와 겹치면 빌더가 거부합니다. 늘린 뱅크를 쓰면 패치 목록에 `rom_size` 가 붙습니다.

출구를 다른 뱅크로 옮겨도 DB 는 그대로 `2A` 입니다. 표만 long 간접(`[$84]`)으로 읽으므로 같은 루틴의 `INC $1EAB`, 그룹 머리를 찾기 전 출구 번호 루틴(`2A:FC16`, 스스로 DB = `2A`), 특수 출구 갈래(`2A:F7B2` 이하)는 원래대로 돕니다. 그래서 출구만 뱅크 `40` 이상에 둘 수 있습니다. 나머지 셋은 표 뱅크를 DB 로 두고 낮은 주소를 abs 로 씁니다. 뱅크 `40` 이상은 `0000`~`7FFF` 에 WRAM·MMIO 거울이 없습니다.

- 색인(`01:9430`): DB = 색인 뱅크에서 색인을 `LDA $EB0E,Y` 로 읽고, 같은 DB 로 곱셈 `$4202`·`$4203`·`$4216`·`$4217` 과 `$183A`~`$183D` 를 씁니다.
- 레코드·고층 목록: `00:CDEC`(DB = `$183C`, `CMP $0000,Y`~`$0004,Y`), `2A:F4B9`(DB = `$183C`, `LDA ($00),Y` 와 `LDA $1954`·`INC $1EAB`·`DEC $1EAB`), `2A:FD11`(`$1E82` 에 옮긴 `$183C` 를 DB 로, `STA $198E` 등)이 레코드 뱅크를 DB 로 둡니다.

`dq5exitcheck.py --audit` 가 이 다섯 창(PLB 다음 명령 `2A:F705`·`01:9441`·`00:CDF9`·`2A:F4C2`·`2A:FD1A`)에서 DB 가 그 값인 동안 실행한 명령과 그 뱅크 롬 읽기를 모읍니다. 원본 롬 8장면(출구 세 종류, 일반·고층·음수 가장자리 영역 이동, 효과음 갈래, 속성 `33` 계단)에서 명령 417개를 실행했고, DB 를 기준으로 주소를 내는 명령은 45곳이었습니다.

- `8000` 이상 abs 는 색인 읽기 4곳(`01:9448`·`9453`·`9458`·`946F`)뿐입니다. 나머지 abs 는 WRAM(`$183A`~`$183D`, `$1954`, `$1EAB`, `$198E`)과 MMIO(`$4202`~`$4217`, `2A:F40D`~`F41E` 포함)입니다.
- 롬을 읽은 간접 명령은 표 읽기(`2A:F711`~`F7D6`, `00:CE00`~`CE28`, `2A:F4C4`·`FD1E`), `2A:FC5D` 의 출구 속성 목록(`2A:FF37`), BRK 처리기의 인자 읽기(`00:8F99`·`8FB2`)입니다. BRK 처리기는 스택에 쌓인 K 를 DB 로 둔 뒤 읽으므로(`00:8F92`~`8F95`) 레코드 뱅크와 상관없습니다.
- 장면이 지나지 않은 필드행 갈래(`2A:F52A`, `2A:F425`)는 코드 읽기로 보았습니다. DB 기준 접근은 `STA $198E`·`INC $1EAB` 와 레코드 `($00)` 읽기뿐이고, 그룹 `11` 갈래의 `JSL 05:E87C` 는 BRK 명령으로 이루어져 처리기가 DB 를 정합니다.

### 인물 레코드·등장 조건 (`dq5npcrecord/1`)

`dq5npcrecord.py`는 기존 인물 엔트리의 필드와 등장 조건 표 두 개(`12:8449` 대체 목록, `12:839C` 인물을 놓지 않음)의 기존 항목을 제자리에서 고칩니다. 엔트리 길이·인물 수·목록 순서·스크립트는 그대로 둡니다. 결과는 바뀐 레코드의 원본 바이트를 `orig`에 담은 `dq5patch/1` 목록입니다. 읽기 형식은 [맵 형식의 인물 절](dq5-map-format.md#인물-128000)에 있습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5npcrecord.py rom/dq5.sfc dump -o work/npc-records.json
uv run --locked python sfc/dq5/tools/dq5npcrecord.py rom/dq5.sfc patch work/npc-records.json -o work/npc-records.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5npcrecord.py rom/dq5.sfc check work/npc-records.json
```

`check`는 먼저 모든 엔트리 2,483개에서 이 도구의 필드 위치가 로더(`12:8161`·`12:8227`)를 옮긴 `dq5npc.py`의 값과 같은지 봅니다. 입력을 생략하면 원본 전체를 내보내고 다시 패치해 쓰기가 0개인지, 입력이 있으면 빌더로 롬을 만든 뒤 엔트리 크기·두 벌 여부가 원본과 같은지, 같은 입력을 다시 패치하면 쓰기가 남지 않는지, 만든 롬을 다시 읽고 인코딩해도 같은지 확인합니다.

#### 입력

형식 표시는 `"format": "dq5npcrecord/1"`이고 `entries`·`overrides`·`no_npc` 배열에 고칠 항목만 넣습니다. 숫자는 JSON 정수만 받고 `true`·문자열은 받지 않습니다. 모르는 키, 같은 항목 두 번 지정, 범위 밖 값은 거부합니다.

인물 엔트리는 `list`(목록 시작의 CPU 주소, 기본 목록 `05:xxxx`·대체 목록 `10:xxxx`)와 그 목록의 0부터 센 `index`로 고릅니다. `dump`가 붙이는 `name`(맵 또는 「대체」·「숨은 목록」)과 `address`(엔트리 주소)는 적으면 원본과 같아야 합니다. 시간대(`time`)가 `day`·`night`인 한 벌 엔트리는 `fields`, `both`인 두 벌 엔트리는 `day`·`night`에 필드를 적습니다.

| 필드 | 범위 | 엔트리 바이트 | 인물 표 |
| --- | --- | --- | --- |
| `x` | 0~127 | `X` 아래 7비트 | `3020`·`30E0` |
| `y` | 0~127 | `Y` 아래 7비트 − 기타 bit7 | `3080`·`3140` |
| `facing` | `up`·`right`·`down`·`left` | `X` bit7·`Y` bit7 | `31E0` |
| `talk` | 0~`FFF` | `b0`(밤은 `b3`) 아래 니블·대화 하위 | `36E0`·`3700` |
| `gfx` | 0~255 | 그림 번호 | `3220`, 그림에 따라 `32A0`·`33A0`·`3380` |
| `layer` | 0~3 | 이동 bit0-1 | `31A0`(3 이면 `33A0` bit7) |
| `interval` | 0~15 | 이동 bit2-5 | `3300` |
| `speed` | 0~3 | 이동 bit6-7 | `3360` |
| `step` | 0~7 | 기타 bit0-2 | `3320`·`3340` |
| `walk_anim`·`stand_anim` | 0~15 | 추가 값 위·아래 니블(추가 값이 있는 엔트리만) | `32C0`·`32E0` |

- **그대로 두는 비트**: `b0`·`b3` bit4-5(추가 값 없음·스크립트 있음), 기타 bit3-7, 두 벌 엔트리의 마스크입니다. 바꾸면 엔트리 길이가 달라지거나(`b0` bit4-5, 마스크) 뜻을 다 모르는 비트(기타 bit3 은 읽는 곳이 없고, bit4-6 은 `32A0`·`33A0` 으로 가며, bit7 은 `31C0` 을 켬)입니다. 그래서 추가 값이 없는 엔트리에는 `walk_anim`·`stand_anim`을 줄 수 없습니다.
- **`y`**: 인물 표에 들어가는 칸입니다. 기타 bit7 이 켜진 엔트리(낮 75·밤 107, 합계 182)는 저장값이 `y + 1` 이므로 `y`는 126 까지입니다.
- **낮·밤 전환**: 한 벌 엔트리는 `time`을 `day`↔`night`로 바꿀 수 있습니다(`b0` bit7-6). 두 벌 엔트리를 한 벌로, 또는 그 반대로 바꾸면 길이가 달라지므로 받지 않습니다. 전환으로 한 시간대 인물 수가 늘면, 그 목록을 쓰는 맵(기본 목록의 맵과 대체 표가 가리키는 맵)이 원본의 같은 시간대에 놓던 최대 수를 넘을 수 없습니다. 인물 표 슬롯 번호(`$81`)에는 상한 검사가 없고, 인물 뒤에 다른 물체가 같은 번호로 이어 놓이는지 확인하지 않았기 때문입니다. 대체 표 항목의 맵·목록을 바꿀 때도 같은 한도를 봅니다.
- **낮·밤 공유 바이트**: 두 벌 엔트리에서 마스크가 공유로 둔 필드는 바이트 하나를 낮·밤이 함께 씁니다. 한쪽만 다른 값을 주면 거부하므로, 공유 필드는 `day`·`night`에 같은 값을 적습니다. 마스크 bit7 이 켜진 엔트리는 `b0`를 낮·밤이 함께 써서 `talk`의 위 니블도 같아야 합니다. 예외로 Y 를 공유하면서 기타 bit7 만 낮·밤이 다른 엔트리 4개(`05:C3EF`·`05:CF8E`·`10:BBCC`·`10:CE00`)는 같은 바이트가 한 칸 다른 `y`로 풀리므로, bit7 이 켜진 쪽의 `y`를 하나 작게 적어야 합니다. 오류에는 충돌한 두 바이트 값이 나옵니다.

조건 표 항목은 `index`(0부터, `overrides` 296개·`no_npc` 43개)와 바꿀 필드만 적습니다. `map`은 원본 맵 목록에 있는 `GG/MM`, `flag`는 `7E:2190 + flag`의 0~127, `when`은 `on`(그 비트가 켜졌을 때)·`off`(꺼졌을 때, 플래그 바이트 bit7), `mask`는 한 비트(1·2·4·…·128)입니다. `overrides`의 `list`는 `10:8000`~`10:DDB1`의 대체 목록 시작점이어야 합니다(로더에 닿지 않던 숨은 목록 9개도 가리킬 수 있음). 대체 표는 순서대로 처음 참인 항목을 쓰므로 항목 순서도 뜻이 있습니다.

```json
{
  "format": "dq5npcrecord/1",
  "entries": [{"list": "05:8CD4", "index": 3, "time": "day",
               "fields": {"x": 24, "y": 12, "facing": "down", "gfx": 24, "talk": 768}}],
  "overrides": [{"index": 80, "when": "off"}]
}
```

#### 목록 재배치와 함께 쓰기

`dq5npcrelocate.py`로 목록을 옮기면 게임은 옮긴 사본을 읽습니다. 이때는 이 도구의 패치 목록을 따로 빌드에 넣지 않고, 같은 문서를 `dq5npcrelocate.py patch … --records work/npc-records.json`으로 넘깁니다. 재배치 도구가 고친 엔트리 바이트를 사본에 넣고, 고친 대체 표 항목은 조건 4바이트와 옮긴 목록 주소를 함께 씁니다. 빈 맵 표는 제자리에 씁니다. 원본 자리를 고치는 패치와 재배치를 함께 빌드하면 겹치지 않아 빌더가 막지 못하지만 게임에는 반영되지 않습니다.

#### 게임 실측

### 맵별 루틴 표 (`dq5maphook/1`)

`dq5maphook.py` 는 맵을 푼 뒤 도는 맵별 루틴 표([맵 형식의 「맵별 루틴」](dq5-map-format.md#맵별-루틴-15f907))를 고칩니다. 맵 그림을 바꿔도 DQ5 의 그 맵 항목은 남아서, 루틴이 셀 버퍼에 출구 셀을 만들거나 매 프레임 주인공을 옮깁니다. 포팅한 맵에서는 이 항목을 막거나 다른 맵으로 옮겨야 합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5maphook.py rom/dq5.sfc dump -o work/maphook/dump.json
uv run --locked python sfc/dq5/tools/dq5maphook.py rom/dq5.sfc patch work/maphook/edit.json -o work/build/maphook.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5maphook.py rom/dq5.sfc rewrite work/maphook/table.json --at 15:FF80 -o work/build/maphook.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5maphook.py rom/dq5.sfc check [work/maphook/edit.json] [--at 15:FF80]
```

#### 입력

```json
{"format": "dq5maphook/1",
 "entries": [{"index": 22, "post_load": "15:F906"},
             {"index": 15, "flag": {"index": "00", "mask": "40", "when": "clear"}}]}
```

| 필드 | 바이트 | 뜻 |
| --- | --- | --- |
| `group` | `+0` | `$BC` 16진 두 자리. `FE` 는 필드 항목 |
| `map` | `+1` | 실내는 `$BD` 16진 두 자리, `null` 이면 그룹 전체(`FF`). 필드는 세계 번호 `00`~`02`(`$1949`). `15:F85D` 는 `FF` 를 「모두」로 보지 않으므로 필드 항목에 `null` 은 받지 않음 |
| `flag` | `+2`·`+3` | `null` 이면 조건 없음(`FF 00`). `{"index", "mask", "when"}` 은 `7E:2190+index & mask` 가 켜졌을 때(`set`) 또는 꺼졌을 때(`clear`, `+2` bit7) 맞음. `index` `00`~`7F`, `mask` `01`~`FF`. `7F` 의 `clear` 는 바이트가 `FF` 라 쓸 수 없음 |
| `post_load` | `+4`~`+6` | 맵을 푼 뒤 부를 루틴 `BB:AAAA`. `15:F906` 이면 없음 |
| `per_frame` | `+7`~`+9` | 매 프레임 루틴 `BB:AAAA`. `15:F906` 이면 없음 |

- `dump` 는 162개 항목 모두에 `index` 와 위 필드를 붙이고 `table` 에 표 자리(로더가 가리키는 곳)를 적습니다. 원본을 그대로 `patch` 하면 쓰기가 0개입니다.
- `patch` 는 항목 수와 표 자리를 그대로 두고 `index` 로 고를 항목의 적은 필드만 바꿉니다. 모르는 필드, 같은 항목 두 번, 맵 목록(`dq5mapwrite.all_maps`)에 없는 그룹·맵은 거부합니다. `table` 을 적으면 롬의 표 자리와 같아야 합니다.
- 루틴 주소는 원래 표의 같은 칸에 있던 것만 받습니다. 맵을 푼 뒤 루틴 63가지와 매 프레임 루틴 42가지이고, 둘 다 `15:F906` 을 포함합니다. 두 칸에 함께 나오는 루틴은 `15:F906` 하나뿐이라, 맵을 푼 뒤 루틴을 매 프레임 칸에 두는 것도 거부합니다. 루틴 집합은 입력 롬의 표(표를 옮긴 롬이면 옛 자리 `15:F907` 에 남은 표도)에서 모으므로, 입력에는 원래 롬을 줍니다. 새 루틴을 넣을 때는 `--raw-routines` 를 줍니다. 그때도 `dq5build.py` 가 받는 주소(뱅크 `00`~`7D` 의 `8000`~`FFFF`)만 받고, 롬 크기는 보지 않으므로 늘린 뱅크(`30`~)의 루틴은 그 자리를 채우는 목록과 함께 빌드합니다. 두 루틴 모두 `JSL` 로 불리고(`15:F7EA` → `JML [$A5]`, `7E:1AA5` 의 `22 … 60`) `RTL` 로 돌아와야 합니다. 맵을 푼 뒤 루틴은 DB = 15, M·X 8비트(`15:F7E8` 의 `SEP #$30`)로 들어옵니다.
- 앞의 조건 없는 항목이 같은 맵을 먼저 잡아 불리지 않는 항목은 경고만 냅니다. 원본에도 넷 있습니다(10/00·03/05·12/09·1B/07 의 둘째 항목, 표 순서 65·80·100·148). `patch` 는 원본에 이미 있는 것은 다시 알리지 않습니다.
- 바뀐 바이트만 쓰기로 내고 4바이트 이하로 떨어진 것은 한 쓰기로 묶습니다. 모든 쓰기에 `orig` 를 채웁니다.

#### 표 다시 쓰기

`rewrite` 는 `entries` 전체(`index` 는 빼거나 순서와 같게)를 새 표로 보고, `--at` 자리에 항목과 끝 `FF` 를 씁니다. 표 자리가 바뀌면 로더의 피연산자 11곳도 고칩니다. `--at` 을 빼면 지금 자리에 다시 씁니다. 표를 둘 수 있는 자리는 코드 읽기로 이렇게 정했습니다.

- `15:F7D0` 은 `PHK`·`PLB`(`15:F7D2`)로 DB 를 15 로 두고, `15:F7F4` 가 `REP #$10` 인 채 `LDA $F907,X` 꼴의 `abs,X` 로 읽습니다. 그래서 표는 뱅크 15 안에 있어야 합니다. 이 함수를 부르는 곳은 `01:8F84`·`01:98FC`·`01:9FD6` 셋입니다.
- 표 주소는 `15:F7F7`(`+0`), `15:F80A`·`15:F85D`(`+1`), `15:F815`(`+2`), `15:F82B`(`+3`), `15:F865`·`F86A`·`F86F`(`+4`~`+6`), `15:F880`·`F87A`·`F874`(`+7`~`+9`) 의 피연산자에만 있습니다. 명령마다 표 시작에 항목 안 위치를 더한 값입니다. 뱅크 15 에서 `F907`~`F910` 을 `abs`·`abs,X` 피연산자로 쓰는 읽기·비교·AND·쓰기 명령을 바이트열로 찾으면 이 11개뿐이고, `15:F7F4` 를 부르는 곳도 `15:F7E2` 하나입니다. 도구는 11곳이 모두 같은 표 시작을 가리키지 않으면 거부합니다.
- 다시 쓸 수 있는 곳은 원래 표 자리 `15:F907`~`15:FF5B`(항목 162개와 끝 `FF`, 1,621바이트)와 [빈 자리 지도](#원래-롬)의 `15:FF80`~`15:FFFF`(128바이트, 항목 12개) 둘입니다. 바로 뒤 `15:FF5C`~`FF62` 는 `15:F887` 이 같은 DB 로 읽는 다른 표(6바이트 항목, `$1AAA` 에 둘 16비트 주소. 원본은 17/01 항목 하나)이므로 덮지 않습니다.
- 그래서 항목 수는 원래 자리에서 162개, `15:FF80` 에서 12개까지입니다. 163개 이상은 로더가 다른 뱅크를 읽도록 코드를 바꾸어야 해서(`15:F7D2` 의 DB, `15:F887` 이 같은 DB 를 씀) 이 도구가 하지 않습니다.
- 표를 옮겨도 옛 자리는 지우지 않습니다. 원래 자리를 다른 용도로 쓰려면 이 도구 밖에서 정합니다.
- 새 자리가 원래 표 자리도 지금 표도 아닌데 0 이 아닌 바이트가 있으면 거부합니다. 문서의 `table` 은 `--at`(빼면 지금 자리)과 같아야 합니다.
- 한 빌드에는 `patch` 목록과 `rewrite` 목록 가운데 하나만 넣습니다. 둘은 겹치지 않을 수 있지만, 표를 옮기면 `patch` 가 고친 옛 표는 더 읽히지 않습니다.

`check` 는 입력을 패치해 `dq5build.py` 로 롬을 만들고, 같은 입력을 다시 패치해 쓰기가 0개인지, 만든 롬을 다시 읽어 인코딩해도 같은지 봅니다. `--at` 을 주면 `rewrite` 로 보고, 만든 롬의 로더가 새 자리를 가리키고 항목 수가 입력과 같은지도 봅니다. 루틴 검사는 입력 롬의 표로 합니다. 입력을 빼면 원본 162개를 왕복해 쓰기 0개인지 봅니다.

#### 게임 실측

`dq5maphookcheck.py` 가 변경 롬 다섯 벌과 원본 롬에서 15장면을 돌립니다. 맵을 풀 때마다 `15:F7EA` 에서 고른 루틴(`$A5`~`$A7`, `7E:1AA6`~`1AA8`)을, `15:F7EE` 에서 01/05 셀 (51,20) `+4` 를 적고, 걸은 뒤의 맵과 칸을 견줍니다(`lua/dq5maphookcheck.lua`). 입력·패치·롬·IPS·기록은 실행마다 새 하위 폴더에 남습니다.

```sh
MESENCE="$MESENCE" uv run --locked python sfc/dq5/tools/dq5maphookcheck.py rom/dq5.sfc \
```

### 대화 스크립트 `dq5talk/1`

`dq5talkwrite.py`는 대화 번호 `011`~`24E` 가 실행하는 스크립트 574개를 JSON 으로 내보내고, 고친 스크립트를 다시 부호화해 `dq5patch/1` 목록을 냅니다. 읽기 형식과 조건 코드의 뜻은 [텍스트 형식의 대화 스크립트 절](dq5-text-format.md#대화-스크립트-06aef8)에 있습니다.

```sh
uv run --locked python sfc/dq5/tools/dq5talkwrite.py rom/dq5.sfc dump -o work/talk.json
uv run --locked python sfc/dq5/tools/dq5talkwrite.py rom/dq5.sfc dump --talk 012 -o work/papas.json
uv run --locked python sfc/dq5/tools/dq5talkwrite.py rom/dq5.sfc patch work/papas.json -o work/talk.dq5patch.json
uv run --locked python sfc/dq5/tools/dq5talkwrite.py rom/dq5.sfc check work/papas.json
```

`check` 의 입력을 빼면 원본 574개(11,727바이트)를 내보냈다 다시 패치해 쓰기가 0개인지, `dq5talk.py --check` 의 경계 검사도 통과하는지 봅니다. 입력이 있으면 빌더로 롬을 만들어 다시 읽은 스크립트가 입력과 같은지, 게임의 찾기(`06:AF85`)와 같은 주소에 닿는지, 같은 입력을 다시 패치하면 쓰기가 0개인지 봅니다. `patch` 에 준 `--at`·`--repack` 을 `check` 에도 같이 줍니다.

#### 입력

```json
{"format": "dq5talk/1", "scripts": [{"talk": "012", "body": [
  {"op": "if", "cond": {"code": "1B", "index": 1, "mask": 1, "not": true},
   "then": [{"op": "msg", "id": "74F"}, {"op": "flag-on", "index": 2, "mask": 128}],
   "else": {"op": "msg", "id": "742"}}]}]}
```

이 예는 선실 파파스(대화 번호 `012`)의 조건을 뒤집어, `7E:2191 & 01` 이 꺼져 있을 때 메시지 `74F` 를 띄우고 `7E:2192` 에 `80` 을 OR 합니다. `scripts` 에는 고칠 스크립트만 적고, 적지 않은 것은 원본을 그대로 둡니다. `talk` 와 메시지 `id`, 호출 `target` 은 16진 문자열, 플래그와 조건 인자는 0~255 정수입니다. 모르는 필드, 같은 대화 번호 두 번, 범위 밖 값은 거부합니다.

| `op` | 바이트 | 필드 |
| --- | --- | --- |
| `msg` | `40`~`7F` 2바이트 | `id`(메시지 `000`~`C7F`). `615` 이상은 `id - 615`, 미만은 bit5 를 켠 꼴로 씀(원본 1,930개가 모두 이 규칙) |
| `if` | `07 <조건> <then> [0B <else>]` | `cond`, `then`, `else`(없어도 됨). 분기가 목록이면 블록 `06 … 3E`, 객체 하나면 블록 없는 명령 하나 |
| `flag-off` | `17 i m` | `index`, `mask`: `7E:2190 + i &= m` |
| `flag-on` | `18 i m` | `index`, `mask`: `7E:2190 + i \|= m` |
| `flag-set` | `19 i v` | `index`, `value`: `7E:2190 + i = v` |
| `call` | `00 lo hi` | `target`: 뱅크 06 네이티브 루틴 주소(`B3A0` 꼴) |

`cond` 는 `code` 와 그 조건의 인자, 결과를 뒤집는 `not`(조건 바이트 bit7)입니다. 받는 조건은 형식 문서에서 실측한 것만입니다.

| `code` | 인자 | 참일 때 |
| --- | --- | --- |
| `1B` | `index`, `mask` | `7E:2190 + index & mask` 가 켜짐 |
| `1A` | `index`, `value` | `7E:2190 + index` 가 `value` 와 다름 |
| `05` | | はい/いいえ 창에서 はい |
| `03` | `member` | 그 인물 번호가 마차 밖 일행에 살아 있음 |
| `13` | `record` | 일행 레코드 `record` 번째가 살아 있음 |
| `11` | `item` | 일행 누군가가 그 물건을 가짐 |
| `02` | | `7E:0F1D` 가 0 이 아님 |
| `14` | | 낮 |
| `1E`·`1F` | | 신부가 ビアンカ |
| `20` | | 마차 밖에 살아 있는 딸이 없음 |

원본 574개는 모두 이 명령과 조건으로 풀려서, 날바이트로 남겨 두는 명령은 없습니다. 원본에 없는 명령 `01`·`12` 와 조건 `16`·`1C` 는 받지 않습니다(아래).

#### 배치 제약

아래는 코드 읽기로 정했고, 지킨 결과를 게임에서 확인했습니다(아래 「게임 실측」).

- **뱅크 06 고정**: `06:AF93` 과 `06:B05D` 가 데이터 뱅크를 `06` 으로 두고, `06:B065` 는 `LDA ($F9),Y` 로 읽습니다. `$F9` 는 16비트이고 묶음 포인터 표 `06:AEF8` 도 16비트입니다. 네이티브 루틴도 데이터 뱅크 `06` 에서 불립니다. 그래서 스크립트는 뱅크 06 안에만 둘 수 있고, `--at` 도 `06:XXXX` 만 받습니다. `30:8000`·`32`·`34`·`38`·`60:8000` 같은 늘린 뱅크는 쓰지 않습니다.
- **옮기는 단위는 묶음**: 묶음 g(스크립트 `32g`~`32g+31`)의 시작만 표에 있고, 묶음 안 스크립트는 `06:AFA9` 가 앞 스크립트를 건너뛰어 찾습니다. 한 스크립트가 길어지면 그 묶음 전체를 옮깁니다. 원래 묶음 18개의 크기는 316~1,069바이트입니다.
- **스크립트 하나는 256바이트까지**: `06:B061` 이 Y 를 8비트로 두고 `($F9),Y` 의 Y 만 늘립니다. 원본에서 가장 긴 것은 169바이트입니다.
- **건너뛰기 규칙과 맞을 것**: `06:AFA9` 는 명령을 해석하지 않고 `00`·`17`~`1C` 를 3바이트, bit6 이 켜진 바이트를 2바이트, 나머지를 1바이트로 세다 `3F` 에서 멈춥니다. 조건 `03` 의 인자 `3F` 처럼 이 규칙으로 읽으면 끝이 어긋나는 스크립트는 거부합니다. 원본 574개는 모두 맞습니다.
- **조건문 분기는 블록에**: 갈리지 않은 분기를 건너뛰는 `06:B23F` 는 블록 없는 분기의 `07` 을 1바이트로 건너뛰고 조건 바이트를 남깁니다. 그래서 `then`·`else` 에 조건문을 두려면 목록(블록)으로 씁니다.
- **빈 블록·빈 스크립트 금지**: `06:B065` 는 블록 첫 바이트를 끝 표시인지 보기 전에 명령으로 실행합니다.
- **받지 않는 조건**: `16` 은 실행(`06:B31F`)이 3바이트를 읽는데 건너뛰기 길이 표(`06:B27E`)는 2바이트라 갈리지 않을 때 어긋납니다. `1C` 는 코드 읽기뿐입니다.

배치는 세 가지입니다.

| 경우 | 하는 일 |
| --- | --- |
| 묶음이 원래 자리보다 짧거나 같음 | 원래 시작에 씀. 남는 뒤쪽 바이트는 그대로 둠(가리키는 곳이 없음) |
| 원래 자리보다 김, `--at 06:XXXX` | 그 묶음만 `--at` 부터 차례로 두고 `06:AEF8` 표를 고침. 옛 자리는 비게 됨 |
| `--repack --at 06:XXXX` | 묶음 전부를 `06:8129`~`06:AEF7` 에 차례로 다시 채우고, 들어가지 않는 묶음만 `--at` 에 둠 |

`--at` 자리는 [빈 자리 지도](#원래-롬) 안이거나, 이번에 다시 옮기는 묶음이 원래 자리 밖에서 쓰던 곳이어야 합니다. 새 자리끼리 겹치면 거부하고, 옮긴 묶음은 통째로 씁니다. 뱅크 06 의 빈 자리는 `06:FE10`~`06:FFFF` 496바이트뿐이라, 묶음 하나를 통째로 옮길 수 있는 것은 316·370·385바이트인 묶음 3·0·17 정도입니다. 그보다 큰 묶음이 길어지면 `--repack` 으로 마지막 묶음 17(385바이트)을 `06:FE10` 으로 내보내고 그만큼을 앞에서 씁니다. 이렇게 하면 원래 자리 11,727바이트와 빈 자리 496바이트에서 묶음 단위로 남는 만큼까지 늘릴 수 있습니다.

대화 번호 → 스크립트 대응은 표가 아니라 `T - 011` 계산이라 바꿀 표가 없습니다. 스크립트 수 574 도 `06:AF7B` 등의 `CMP #$024F` 로 정해져 늘리지 않습니다. 인물이 다른 스크립트를 쓰게 하려면 [인물 레코드](#인물-레코드등장-조건-dq5npcrecord1)의 `talk` 필드(`dq5npcrecord.py`)로 대화 번호를 바꾸거나, 그 스크립트의 내용을 옮겨 적습니다.

#### 게임 실측

`dq5talkcheck.py` 가 변경 롬 네 벌을 만들고 원본 롬과 함께 선실 세이브스테이트에서 파파스에게 말을 겁니다. 대화 번호는 파파스 인물 표(`7E:36EB`·`7E:370B`)를 `POKE` 로 바꿉니다. 대화 시작 `06:AF62`, 묶음 포인터를 읽은 `06:AF9C`(A = 묶음 시작), 메시지 `24:8BAF`(A = 번호)와 대화 뒤 `7E:2190`~ 을 적어 첫 대화를 기대값과 견줍니다. 입력·패치·롬·기록은 실행마다 새 하위 폴더에 남습니다.

```sh
MESENCE="$MESENCE" uv run --locked python sfc/dq5/tools/dq5talkcheck.py rom/dq5.sfc \
    --state work/state/ship.mss --out work/talkcheck
```

| 장면 | 롬 | 메시지 | 묶음 시작 | 플래그 |
| --- | --- | --- | --- | --- |
| 파파스 `012` | 원본 | `742` | `8129` | `7E:2192` = `00` |
| 조건 `1B` 에 `not` | 조건 뒤집기 | `74F` | `8129` | `7E:2192` = `80` |
| else 메시지 `742` → `129` | 메시지 바꾸기 | `129` | `8129` | `7E:2192` = `00` |
| 긴 스크립트(`--at 06:FE10`), はい | 묶음 0 을 옮김 | `742` `616` `1CC` `74F` | `FE10` | `21F0`~`21F3` = `5A 81 0F 01` |
| 같은 스크립트, いいえ | 묶음 0 을 옮김 | `742` `617` `1CC` `74F` | `FE10` | `21F0`~`21F3` = `5A 81 0F 00` |
| 같은 스크립트, はい | `--repack` | `742` `616` `1CC` `74F` | `8129` | `21F0`~`21F3` = `5A 81 0F 01` |
| 같은 묶음의 `015` | 원본 / 묶음 0 을 옮김 | `747` / `747` | `8129` / `FE10` | |
| 뒤로 밀린 `120` | 원본 / `--repack` | `A23` / `A23` | `9350` / `936A` | |
| 넘친 묶음 17 의 `24E` | 원본 / `--repack` | `C6E C7D` / `C6E C7D` | `AD77` / `FE10` | |

긴 스크립트는 원래 15바이트를 41바이트로 늘린 것으로, `flag-set 60 5A`·`flag-on 61 81`·`flag-off 62 0F`(`7E:21F2` 를 미리 `FF` 로 둠), 메시지 `742`, はい/いいえ 조건문(はい 면 블록 `616` + `flag-on 63 01`, いいえ 면 `617`), else 없는 조건문 둘(참: `7E:21F1 & 80` → `call B3A0`, 메시지 `1CC` 를 띄우는 루틴. 거짓: `7E:21F2 & F0` → 블록 `129` 를 건너뜀), 메시지 `74F` 입니다. 메시지 순서와 플래그가 모두 기대대로였고, いいえ 에서는 건너뛴 블록의 `flag-on 63 01` 이 실행되지 않았습니다. 바꾸지 않은 대화 셋은 옮긴 롬에서도 원본과 같은 메시지였고, 게임이 읽은 묶음 시작은 그 롬의 `06:AEF8` 표 값과 같았습니다. 확인한 것은 이 장면들이며, 모든 스크립트를 게임에서 다시 돌린 것은 아닙니다.

## 통합 포팅 빌드 `dq5portbuild/1`

DQ4 타이틀·서곡·메뉴(이름 입력 포함) 롬과 DQ5 쓰기 도구 작업을 한 롬으로 만듭니다. 고정 롬은 예약 영역이 되고, 작업마다 정한 뱅크 창 안의 남은 빈 자리에서 `--at` 을 골라 쓰기 도구를 돌린 뒤 `dq5build.py check`·`build` 로 합칩니다. 결과 IPS 는 원래 롬에 다시 붙여 같은 롬이 되는지 확인합니다.

```sh
uv run --locked python sfc/dq5/tools/dq5portbuild.py rom/dq5.sfc plan  work/port/port.json --out work/port/plan
uv run --locked python sfc/dq5/tools/dq5portbuild.py rom/dq5.sfc build work/port/port.json --out work/port/build
MESENCE=… uv run --locked python sfc/dq5/tools/dq5portcheck.py rom/dq5.sfc work/port/build/report.json \
  --state work/state/ship.mss --symbols work/menu/name-entry.sym --out work/port/check
```

`plan` 은 배치만 정해 보고하고, `build` 는 `--out` 에 작업별 패치 목록·`port.sfc`·`port.ips`·`report.json` 을 씁니다. 고정 롬은 DQ4 트랙의 재현 절차([타이틀](../../dq4/docs/dq4-title-animation.md#재현-빌드와-자동-검사)·[서곡](../../dq4/docs/dq4-overture-format.md#재현)·[메뉴](../../dq4/docs/dq4-menu-format.md#재현))로 먼저 만듭니다.

```json
{"format": "dq5portbuild/1", "size": 4,
 "fixed": [{"name": "dq4-menu", "rom": "../menu/dq4-menu.sfc", "title_layout": "../dq4-title-baseline"}],
 "reserve": [{"name": "dq4-sound-port", "from": "72:8000", "to": "7D:FFFF"}],
 "jobs": [
  {"name": "maps", "kind": "map", "inputs": ["src/map-0100.json", "src/map-0105.json"]},
  {"name": "npc", "kind": "npc", "input": "src/npc.json"},
  {"name": "field0", "kind": "field", "world": 0, "input": "src/w0.bin"},
  {"name": "text", "kind": "text", "input": "src/text.json", "over": "dq4-menu"},
  {"name": "events", "kind": "event", "inputs": ["src/event-number.json"]}]}
```

| 키 | 뜻 |
| --- | --- |
| `size` | 결과 롬 크기(MB, 2·3·4). 고정 롬은 이보다 크면 안 됨 |
| `fixed[]` | 다른 도구가 만든 롬 전체. `rom` 은 설정 파일 기준 상대 경로. `title_layout` 은 DQ4 타이틀 에셋 폴더(`dq4titlelayers.py --out`)이며 아래 「타이틀 거울」 규칙을 켬. `keep` 은 거울 안에서 더 예약할 CPU 범위 쌍 목록(`[["30:A000", "30:A8FF"]]`) |
| `reserve[]` | 아직 패치가 없지만 다른 작업이 잡아 둔 CPU 범위(`from`~`to`, 끝 포함). 예는 DQ4 메뉴 문서가 적은 소리 이식 몫 |
| `jobs[].kind` | `map`·`field`·`npc`·`text`·`event`·`patch` |
| `jobs[].input`·`inputs` | 쓰기 도구의 입력 파일(설정 파일 기준). `map` 은 `dq5map/1`·`dq5mapsrc/1`(먼저 컴파일) 여럿, `event` 는 `dq5event/1` 여럿, `field` 는 지도 `.bin` 과 `world`, `patch` 는 이미 만든 `dq5patch/1` |
| `jobs[].over` | `text` 에서 보행 메시지를 이미 옮긴 고정 롬 이름. 그 묶음을 기준으로 고친 메시지만 바꿈(`dq5textwrite.py --base`) |
| `jobs[].records`·`allow_growth` | `npc` 에서 `dq5npcrecord/1` 문서와 인물 수 늘리기 허용. `dq5npcrelocate.py --records`·`--allow-growth` 로 넘김 |
| `jobs[].at`·`alt_at` | 자리를 손으로 정할 때(인물은 기본·대체 목록 각각). 빼면 배치기가 고름 |

### 작업과 뱅크 창

배치기는 작업을 한 번 시험 자리에 써서 크기를 잰 뒤, 쓰기 도구의 배치 규칙대로 놓일 구간을 계산해 빈 자리에 맞춥니다. 실제로 돌린 쓰기 도구가 늘린 자리에 쓴 구간이 계산과 다르면 멈춥니다.

| 종류 | 쓰기 도구 | 조각 | 창 | 창을 그렇게 둔 근거 |
| --- | --- | --- | --- | --- |
| `map` | `dq5mapwrite.py patch --at` | 레코드를 잇달아(뱅크를 넘어도 됨) | `30`~`3F` | 비트 리더 `01:AC66` 이 `AND ($A5)` 로 DB 뱅크를 읽고, 같은 DB 로 낮은 WRAM 을 절대 주소로 씀 |
| `field` | `dq5fieldwrite.py patch --world N --at` | 9번째 비트·지도 두 덩어리, 덩어리마다 한 뱅크 | `30`~`3F` | [필드 세계 지도](#필드-세계-지도)의 DB 제약 |
| `npc` | `dq5npcrelocate.py patch --base --alt` | 기본·대체 목록 각각 한 뱅크, 서로 다른 뱅크 | `30`~`3F` | 인물 목록 로더의 DB 제약(도구가 거부) |
| `text` | `dq5textwrite.py patch --at` | 머리(디코더·마스크·트리·글자 묶음 표)는 시작 뱅크 안, 메시지는 이어서 | `over` 가 있으면 `60`~`7D` 를 먼저, 없으면 `30`~`3F` | 색인 창 OR `60`·`20`([보행 대사](#보행-대사-일괄-쓰기-dq5text1)) |
| `event` | `dq5eventwrite.py patch --at` | 스크립트마다 한 뱅크 | `60`~`7D` | `60:8000` 실측과 통합 롬 `65:8000` 실측 |
| `patch` | 없음 | 배치하지 않음. 늘린 자리를 쓰면 빈 자리여야 하고, 다른 조각보다 먼저 빼 둠 | — | 제자리 쓰기 도구의 결과(`dq5tables.py`·`dq5chestwrite.py` 등) |

`40`~`5F` 와 `FE`·`FF` 는 어느 창에도 없습니다. 배치 순서는 주소를 정한 조각, 창이 하나뿐인 조각, 큰 조각 순서이고, 창 안에서는 빈 구간의 시작과 그 안의 뱅크 첫머리를 앞에서부터 시도합니다. 덩어리가 뱅크를 넘으면 다음 뱅크로 미는 규칙은 쓰기 도구와 같고, 배치기가 고른 `--at` 은 민 뒤의 첫 덩어리 자리입니다.

### 고정 롬이 차지하는 자리

고정 롬을 같은 크기로 늘린 원래 롬(`dq5build` 의 늘리기, 뱅크 첫 8바이트 표지 포함)과 견주어 다른 바이트를 씁니다. 차지하는 자리는 따로 정합니다. 자료 안의 0 은 늘린 자리의 0 과 구별되지 않으므로, 다른 바이트가 하나라도 있는 늘린 뱅크는 **뱅크 전체**를 차지한 것으로 봅니다. 모두 0 인 뱅크(표지만 다름)는 비어 있습니다.

타이틀 빌드는 2MB 로 늘릴 때 `30`~`3F` 를 원래 롬 `20`~`2F` 의 복사본(거울)으로 채웁니다. `title_layout` 을 주면 이 구간만 뱅크 단위 대신 다음처럼 잡습니다.

- 타이틀이 선언한 자리: 코드 `30:8000`~`8FFF` 와 `dq4titlelayerpatch.PLACEMENTS` 의 에셋(파일 크기만큼).
- 선언 밖에서 거울과 다른 바이트 묶음(64바이트 안쪽 틈은 이음)을 앞뒤 64바이트 넓힌 자리. 서곡의 `30:FF00` 과 이름 입력 코드 `30:A000`~ 이 여기에 듭니다. 끝 바이트가 우연히 거울과 같아도 놓치지 않게 넓힙니다.
- 나머지 거울 바이트는 쓰지 않고 빈 자리로 돌립니다. 이번 고정 롬에서 272,252바이트였습니다.
- 다른 단계의 자료가 거울과 같은 바이트로 128바이트 넘게 이어지면 이 규칙으로는 찾지 못합니다. 그런 자리를 알면 `keep` 에 적습니다. `report.json` 의 `mirror_freed_overwritten` 은 작업이 덮은 비운 거울 바이트 수이고, 그 자리를 고정 롬이 읽지 않는지는 `dq5portcheck.py` 의 타이틀·DQ4 검사로 확인합니다.

`text` 작업에 `over` 를 주면 기준 롬의 옛 메시지 묶음(디코더 호출 대상부터 마지막 메시지 끝까지, DQ4 메뉴는 `65:8000`~`69:B941`, 차지한 자리에서도 뺌)과 새 패치가 쓰는 원본 자리(색인 `24:AF1E`, `24:9E02`·`24:9E07`·`24:8BD7`, 표 피연산자 넷)를 고정 패치에서 뺍니다. `over` 없이 보행 메시지를 옮긴 고정 롬과 함께 쓰면 같은 색인·훅을 둘이 쓰게 되므로 거부합니다.

### 실패 보고

들어갈 자리가 없으면 종료값 1 로, 못 놓은 조각과 창마다 「아직 못 놓은 작업 가운데 이 창만 쓰는 바이트 + 다른 창도 쓰는 바이트, 빈 바이트, 가장 긴 연속」을 보입니다. 맵 364개 전체를 넣은 실제 출력입니다.

정한 규칙은 이렇습니다. 뱅크 끝에서 거슬러 0 이 이어지는 곳을 찾고, 그 시작에서 16바이트를 띄운 뒤 16바이트 경계로 올립니다. 그렇게 남은 길이가 32바이트 이상이면 빈 자리로 봅니다. 뱅크 `00` 은 끝에 머리·벡터가 있어 없습니다.

어떻게 확인했나:

- **0 줄 전부에 읽기·실행 감시**: 뱅크 안의 0 이나 FF 가 64바이트 넘게 이어지는 곳 32곳(뱅크 가운데 포함)에 읽기·실행 감시를 걸었습니다. 돌린 장면은 전원부터 8,000프레임(A 연타, 오프닝·이름 입력·배 선실), 그리고 선실 세이브스테이트에서 다섯 장면입니다(첫 필드 이벤트와 전투, 청년기 グランバニア 성, 필드 걷기와 명령 창, 탑 안). 뱅크 가운데 0 줄은 모두 읽혔습니다(`04:9750`, `2A:ADC4`·`B06F`·`B4B3`·`D712`, 필드 맵 자료). 그래서 빼고 뱅크 끝만 남겼습니다.
- **뱅크 끝의 첫 바이트**: 뱅크 끝 줄에서 읽힌 것은 `2F:FF86` 한 바이트뿐입니다(136프레임, `2B:C2C7` 이 소리 자료를 `$2143` 으로 보낼 때). 소리 자료를 두 바이트씩 보내다 끝을 한 바이트 넘겨 읽는 것으로 보입니다. 16바이트를 띄우는 까닭입니다.
- **위 22곳에 다시 감시**: 같은 여섯 장면에서 한 번도 읽히거나 실행되지 않았습니다.
- **채워서 켜기**: `build --fill-free 55` 로 22곳을 모두 `55` 로 채운 4MB 롬을 부팅 시험에 넣었습니다. 11개 프레임의 VRAM·CGRAM·OAM·WRAM 해시가 원래 롬과 모두 같았고, 6,500프레임에 17/00 에 닿았습니다.
- **곡·효과음을 모두 틀며 감시**: 곡 자료(샘플 `2B:EB00`~, 시퀀스 `2E:E2E4`~`2F:FF85`)는 곡을 틀 때 CPU 가 롬에서 읽어 SPC 로 보냅니다. 곡 49개, 곡 갈래 6개, 효과음 갈래 137개를 `dq5spcfile.py --free-watch` 로 틀었습니다(곡 묶음의 샘플을 곡 전에 모두 보내게 함). 22곳의 읽기·실행은 192번 모두 0번이었습니다.
  감시가 걸리는지는 곡 `02` 의 시퀀스 첫 11바이트(`2E:E7A6`~)로 따로 보았습니다(`2B:C266` 이 11번 읽음). 늘 올려 두는 곡·샘플(`2B:C422`·`C429` 목록)은 전원을 켤 때 한 번 보내므로 위 8,000프레임 감시에 들어 있습니다. 그때 읽힌 것은 `2F:FF86`(시퀀스 `46` 의 끝 다음 바이트) 하나뿐입니다.
- **맵·전투·필드를 넓게 감시**: `dq5freesweep.py` 로 실내 맵 346곳(들어갈 칸은 `dq5mapmusic.entry_cells`, 들어가 상하좌우로 걷기)을 돌았습니다. 몬스터 236종마다 첫 필드 이벤트 전투(`BATTLE=XX:1`, A 12번), 필드 세계 0·1·2(`POKE 7E1949`, 세계 1·2 는 그 칸에서 걷지 못하고 지도만 그림)도 돌렸습니다. 22곳의 읽기·실행은 585번 모두 0번이었습니다.

### 늘린 롬

`dq5hangul.py expand` 의 실측(「[롬 확장](dq5-hangul-format.md#롬-확장)」)에 4MB 의 뱅크 `C0`~`FF` 를 더 재었습니다. 표지를 쓴 4MB 롬을 켜고 5프레임째에 CPU 주소를 읽었습니다.

| 크기 | 새로 생기는 자리(각 뱅크 `8000`~`FFFF`) | 파일 위치 | 크기 |
| --- | --- | --- | --- |
| 2MB | `30`~`3F` | `180000`~`1FFFFF` | 512KB |
| 3MB | `30`~`5F`(`60`~ 은 `40`~ 을 되풀이) | `180000`~`2FFFFF` | 1.5MB |
| 4MB | `30`~`7D`, `FE`·`FF` | `180000`~`3FFFFF` | 2.5MB |

- 4MB 롬에서 `C0:8000` 은 표지 `40`, `FD:8000` 은 `7D` 로 `40`~`7D` 의 거울입니다. `FE:8000`·`FF:8000` 은 표지 `7E`·`7F`(파일 `3F0000`·`3F8000`)입니다. `7E`·`7F` 는 WRAM 이라 이 두 뱅크는 `FE`·`FF` 로만 닿습니다.
- `40:0000` 은 0 이었습니다(파일 `200000` 의 표지가 보이지 않음). 뱅크 `40`~ 의 `0000`~`7FFF` 는 롬으로 쓰지 않습니다.

## 부팅 시험

`dq5boottest.py 원래롬 만든롬` 은 두 롬을 `work/boot/` 에 시험 전용 이름(`dq5boot-orig.sfc`·`dq5boot-build.sfc`)으로 복사해 MesenCE testrunner 로 함께 돌립니다. Lua 는 `sfc/dq5/tools/lua/dq5boot.lua` 입니다. 전원을 켜 A 를 40프레임마다 4프레임씩 누릅니다. 600프레임마다(그리고 6,500) VRAM·CGRAM·OAM·WRAM 의 Adler 해시와 화면 PNG 를 남기고, 6,500프레임에 맵 번호를 읽습니다. 통과 조건은 둘입니다.

- 6,500프레임에 맵이 17/00(배 선실, 새 게임 첫 장면)
- 11개 프레임의 해시가 원래 롬과 같음. 글자·그림을 바꾼 롬이면 `--allow-diff` 로 첫 장면만 봄

같은 롬이 같은 결과를 내도록 두 가지를 맞춥니다.

- **RAM 을 0 으로 켜기**: 이 PC 의 MesenCE 설정은 `Snes.RamPowerOnState` = `Random` 입니다. 인자 없이 켜면 첫 프레임 WRAM 뒤쪽 64KB 가운데 65,274바이트가 0 이 아니었습니다. 시험은 MesenCE 인자 `--Snes.RamPowerOnState=AllZeros` 를 주어 그 실행만 0 으로 켭니다(첫 프레임 WRAM 합 0 확인).
- **새 SRAM**: MesenCE 는 롬 파일 이름마다 SRAM 파일(`<이름>.srm`)을 둡니다. 시험 전용 이름의 SRAM 파일을 돌리기 전에 지웁니다. 폴더는 환경 변수 `MESENCE_SAVES` 로 바꿀 수 있고, 기본은 macOS 의 MesenCE 설정 폴더 아래 `Saves` 입니다.

**화면 PNG 해시는 견주지 않습니다.** 같은 세이브스테이트에서 같은 롬을 네 번 함께 돌렸을 때 600프레임마다 찍은 VRAM·CGRAM·OAM·WRAM 해시는 네 번 모두 같았습니다. 그런데 같은 프레임의 PNG 는 여섯 장 가운데 네 장이 실행마다 달랐습니다(커서 깜빡임, 그리다 만 글자처럼 한 프레임 앞뒤 화면). 에뮬레이션은 같고 `emu.takeScreenshot` 이 찍는 프레임이 흔들리는 것이라, 화면 대신 화면을 만드는 메모리의 해시를 견줍니다.

| 시험한 롬 | 결과 |
| --- | --- |
| 아무것도 넣지 않은 4MB 롬 | 통과. 해시 11개 같음, 17/00 |
| 빈 자리 22곳을 `55` 로 채운 4MB 롬 | 통과. 해시 11개 같음, 17/00 |
| `retree` 롬을 `fromrom` → `build` 로 다시 만든 2MB 롬 | `--allow-diff` 로 통과. 17/00 에 닿고, 원래 롬과 다른 프레임 9개(메시지 디코더를 바꾼 롬이라 다를 수 있음, 까닭은 보지 않음) |

### 첫 장면 뒤(`--scenes`)

`--scenes 세이브스테이트` 를 주면 배 선실 세이브스테이트(`work/state/ship.mss`)에서 두 롬 모두 `dq5warp.lua` 로 세 장면을 더 돌립니다. Lua 는 `lua/dq5scenehash.lua` 입니다. 정한 프레임의 VRAM·CGRAM·OAM·WRAM 해시와 끝 상태(`warp.txt` 의 `end` 줄)를 견줍니다. 세이브스테이트에서 시작하므로 RAM 무작위 켜기와는 상관이 없습니다.

| 장면 | dq5warp 변수 | 해시 프레임 | 화면 |
| --- | --- | --- | --- |
| 필드 걷기 | `FIELD=174,110`, 왼·위·오른·아래 60프레임씩 | 600·660·720·780 | (174,110) → (167,103) |
| 전투 | `FIELD=341,56 BATTLE=00:1`, A 15번 | 600~1200 7개 | スライム 하나와 전투, 명령 창·공격 메시지 |
| 메뉴 | `FIELD=341,56`, A·아래·A·B·B | 580·620·660·700 | 명령 창 → つよさ 창 → 닫기 |
| 대화 | `TO=01/00,12,80,2`, 위·A 4번·B 2번 | 660·720·780·840 | 도구 가게 「はい いらっしゃいませ！…」·「お買い上げですね」·물건 창(보행 모드 메시지) |

빈 4MB 롬과 빈 자리를 채운 4MB 롬은 네 장면 모두 해시와 끝 상태가 원래 롬과 같았습니다. retree 4MB 롬은 걷기·전투·메뉴가 같았고, 대화는 네 프레임 모두 해시가 달랐습니다(메시지 디코더를 바꾼 롬). 끝 상태는 같아 `--allow-diff` 로 통과합니다. 글자를 바꾼 롬은 대화 장면에서 해시가 달라지는 것을 보고, 끝 상태로 흐름이 같은지만 봅니다.
음성 대조로 몬스터 레코드 `23:8002`(スライム) 한 바이트만 바꾼 롬을 넣었습니다. 전투 장면만 7개 프레임 가운데 6개가 달라 실패했고, 걷기·메뉴는 같았습니다.

### IPS 크기

늘린 자리는 거의 0 과 표지라, 같은 바이트가 16개 넘게 이어지는 곳을 RLE 레코드(크기 0, [횟수 2][값 1])로 씁니다. 빈 4MB 롬의 IPS 가 2,621,670바이트에서 1,785바이트로 줄었습니다. retree 를 넣은 4MB 롬은 147,158바이트입니다. 둘 다 `kr_patch.ips.apply` 로 원래 롬에 다시 붙여 같은 롬이 되었습니다.

## 남은 것

포팅 전체의 지원 범위와 통합 배치 문제는 [도구 점검](dq5-port-tool-audit.md)을 봅니다. 아래 목록만으로 전체 도구가 갖춰졌다고 판단하지 않습니다.

- 필드 표 항목 증설·재배치. 인물 슬롯을 맵을 놓은 뒤 더 쓰는 장면 코드의 맵별 정리.
- 문자열 번역 편집·새 한글 글꼴 대량 삽입, 전투 창 쓰기. 이름 표는 항목 수 증설과 12바이트보다 긴 이름(부른 쪽 직접 페이지 확인)이 남았습니다.
- 성장·조우 레코드 수와 상점 품목 수 증설. 배의 바다 구역 직사각형(`01:85D8`)과 그룹 `50` 이상 맵의 구역 연결(`23:FDD6`) 쓰기, 고정 무리 줄 번호와 이벤트 무리 `+9`~`+C` 의 값 편집.
- `dq5tables.py` 의 물건 `k4하위`(뜻 모름)·`그룹무작위`(여러 번 돌리거나 난수를 고정해야 견줄 수 있음)는 고친 롬의 게임 실측이 남아 있습니다. `k1b2` 는 읽는 길을 찾지 못했습니다(정적 검색).
