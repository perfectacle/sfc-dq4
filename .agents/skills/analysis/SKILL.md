# 롬 분석

이 스킬이 ROM-01, ORIG-01, VERIFY-01, EMU-01 의 정본이다. 도구 하나하나의 사용법은 [tools/README.md](../../../tools/README.md) 가 정본이고, 여기에는 절차와 판단 기준만 둔다.

## 준비

워크트리마다 아래가 있어야 한다. `$MAIN` 은 저장소 원래 체크아웃이다([git-workflow 절차 1](../git-workflow/SKILL.md#절차) 이 링크를 만든다).

| 무엇                | 어디                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------- |
| 롬                  | `rom/dq5.sfc`, `rom/dq4.nes` — `$MAIN/rom` 심볼릭 링크. SHA-1 은 [README](../../../README.md#원본-롬) |
| 세이브스테이트      | `work/state/` — `$MAIN/work/state` 심볼릭 링크. 실험 출발점(예: `ship.mss` 배 선실)    |
| 실험 출력           | 워크트리의 `work/<실험 이름>/`. 다른 워크트리의 `work/` 에 쓰지 않는다                 |
| 에뮬레이터          | `$MESENCE` — MesenCE 실행 파일 경로(사람마다 다르다)                                   |
| 툴킷 Lua 라이브러리 | `LIBDIR=$(uv run --locked krpatch sfc lua)`                                            |

## 절차 — 한 항목 풀기

1. **기존 결과를 읽는다** — 그 트랙의 형식 문서(`sfc/dq5/docs/` 등)와 최근 일지를 읽어 이미 아는 주소·구조를 확인한다. 같은 것을 다시 찾지 않는다.
   완료: 이번 항목과 맞닿은 기존 주소를 목록으로 말할 수 있다.
2. **코드를 찾는다** — 값이 들어가는 RAM 을 읽기·쓰기 감시(`rwatch`·`wwatch`·`rprof`)로 잡거나, 실행 커버리지(`cover.lua`)를 모아 `tools/listing.py` 로 정확한 리스팅을 만든다. 정적 검색(`LDA $xxxx` 꼴)은 후보를 줄일 때만 쓴다.
   완료: 그 데이터를 읽는 루틴의 주소와 읽는 표의 주소.
3. **디코더를 쓴다** — 트랙의 `tools/<트랙><주제>.py`(예: `sfc/dq5/tools/dq5map.py`)에 ROM 만으로 같은 결과를 내는 코드를 쓴다. 모듈 docstring 에 형식 문서 링크와 근거 루틴 주소를 적는다.
4. **실측으로 확인한다**(VERIFY-01) — 디코더 출력을 게임의 RAM·VRAM 덤프(`atpc.lua`)와 바이트 단위로 비교하거나, `walk.lua` 로 실제로 걸어 화면·맵 번호가 예측과 같은지 본다. 전수 검사가 가능하면 전부 돌린다(예: 맵 346개).
   완료: 비교 결과(「N 바이트 중 0 차이」, 「예측 도착 좌표와 같음」)를 숫자로 말할 수 있다.
5. **문서로 남긴다** — [journal](../journal/SKILL.md).

## 규칙

### ROM-01 — 롬 데이터 금지

롬, 롬에서 잘라 낸 바이너리, RAM·VRAM 덤프, 세이브스테이트, 게임 화면을 그대로 담은 큰 이미지를 커밋하지 않는다. `.gitignore` 가 `rom/`, `work/`, `*.sfc`, `*.nes`, `*.mss` 등을 막는다.

- 이유: 저작권 데이터다. 공개 저장소에는 사용자가 자기 롬으로 결과를 다시 만들 수 있는 코드만 둔다.
- 롬을 다운로드 사이트에서 받지 않는다. 롬이 없으면 사용자에게 `rom/` 에 넣어 달라고 한다.
- 일지 그림(트랙의 `images/*.webp`)은 분석 결과를 설명하는 데 필요한 만큼의 화면·렌더링만 둔다. 트랙의 `<트랙>figures.py` 로 롬에서 다시 만들 수 있어야 한다.

### ORIG-01 — 남의 데이터 금지

다른 팬 해킹(DQ4 이식 시도 등)의 패치·그래픽·데이터를 받아 쓰지 않는다. 그들의 글·문서에서 아이디어와 주소 힌트만 참고하고 [docs/references.md](../../../docs/references.md) 에 링크한다. 그래픽은 직접 그린다.

- 이유: 원저작자의 허락이 없다.
- 예외: NDS DQ4 한글 팬패치(v1.1, [nds/dq4/references.md](../../../nds/dq4/references.md))는 사용자가 참고 자료로 허락했다. 명칭·번역 대조와 늘어난 내용 확인에 쓰고, 출처를 문서에 밝힌다. 롬에서 뽑은 대사 본문·그래픽은 ROM-01 에 따라 커밋하지 않는다.

### VERIFY-01 — 실측으로 확인

형식 문서와 일지에 사실로 적는 것은 실측(바이트 비교, 실제 보행, 값 고정 실험)으로 확인한 것뿐이다. 코드만 읽고 낸 결론은 「코드 읽기」라고 근거를 밝히고, 확인 못 한 것은 그 문서의 「남은 것」과 [docs/todo.md](../../../docs/todo.md) 에 둔다.

- 이유: 이 저장소의 결과를 바탕으로 패치를 만든다. 틀린 가설이 사실처럼 적히면 나중에 빌드가 엉뚱하게 깨지고 원인을 찾기 어렵다.
- 가설이 틀렸으면 지우지 말고 일지의 「틀렸던 것들」에 남긴다. 같은 실수를 다른 세션이 반복하지 않게 하려는 것이다.

### EMU-01 — 에뮬레이터는 MesenCE

분석·실험은 [MesenCE](https://github.com/nesdev-org/MesenCE) 로 한다(`--testrunner` + Lua). 문서에도 MesenCE 로 적는다. Mesen 2 는 호환 비교가 필요할 때만 쓴다.

- 이유: 툴킷의 Lua 라이브러리와 기존 프로브가 MesenCE 기준이다. 에뮬레이터가 다르면 같은 세이브스테이트가 다른 결과를 낸다.
- NDS(`nds` 트랙)는 MesenCE 가 돌리지 못한다. kr-patches 의 고스트 트릭 패치와 같이 desmume libretro 코어로 실측하고, 문서에 코어 커밋을 적는다.

## 참고 — 자주 밟는 함정

- **zsh 는 변수를 단어로 나누지 않는다**: `for m in "01 05"` 처럼 넘기면 한 인자가 된다. 함수나 `${m:0:2}` 로 나눈다.
- **macOS 에는 `timeout` 이 없다**: 붙이면 명령이 아예 실행되지 않고 결과 파일만 없다. 길이 제한은 프로브의 `MAXF` 로 건다.
- **`SHOT_DIR` 는 절대 경로**여야 한다. 프로브 결과 파일은 드라이버가 멈추기 전(`MAXF`·`TO` 직전)에 쓰이므로 드라이버의 `MAXF` 를 넉넉히 둔다.
- **`ROMPATCH` 문자열에 공백을 넣지 않는다**: 공백 뒤 바이트가 빠진다.
- **CPU 주소(`7E:xxxx`)에 건 쓰기 감시는 WRAM 포트(`$2180`) 쓰기를 못 잡는다**: 감시를 WRAM 오프셋(`emu.memType.snesWorkRam`)에 걸면 `$2180` 포트 DMA·MVN·`00:xxxx` 거울 쓰기도 잡힌다. 아니면 읽는 쪽을 감시한다. 예: `sfc/dq5/tools/lua/dq5worldlog.lua`.
- **덤프 시점을 화면과 함께 남긴다**: 장면 전환 전이나 전투 중에 덤프하면 엉뚱한 결과가 나온다. `atpc.lua` 는 스크린샷을 같이 저장한다.
- **`walk.lua` 를 고쳤으면** `seqlib.sh` 로 만든 드라이버 폴더의 `boot.lua` 도 다시 만든다.
- **색 변환**은 MesenCE 와 같게 `v << 3 | v >> 2` 로 한다. 그래야 덤프 화면과 픽셀이 같다.
