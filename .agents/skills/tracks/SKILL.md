# 트랙

이 스킬이 TRACK-01, TRACK-02, TRACK-03 의 정본이다.

## 절차 — 세션 시작

1. **트랙을 정한다** — 사용자가 말한 일이 어느 트랙인지 [TRACK-01](#track-01--트랙과-소유-파일) 표로 정한다. 두 트랙에 걸치면 사용자에게 묻는다.
   완료: 트랙 이름(`dq5`·`dq4`·`nds`)을 한 단어로 말할 수 있다.
2. **남은 항목을 고른다** — 자기 트랙 폴더의 `handoff.md` 와 `todo.md`(아직 옮기지 않은 트랙은 `docs/<트랙>-handoff.md` 와 [docs/todo.md](../../../docs/todo.md) 의 자기 트랙 절)를 읽고, 사용자가 따로 정하지 않았으면 위에서부터 고른다. 사용자가 "묻지 말고 쭉 진행" 하라고 했으면 항목마다 묻지 않고 이어서 한다.
   완료: 이번 작업의 항목 하나와, 그 항목을 「끝났다」고 할 조건(무엇을 실측으로 확인하면 되는지)을 말할 수 있다.
3. **워크트리를 판다** — [git-workflow 절차 1](../git-workflow/SKILL.md#절차).
   완료: 새 워크트리 안에서 `rom/` 이 보인다.
4. **분석하고 문서를 쓴다** — [analysis](../analysis/SKILL.md), [journal](../journal/SKILL.md). PR 하나에서는 일지를 쓰지 않고 형식 문서에 인터페이스만 넣는다.
5. **todo 를 고친다** — 끝낸 항목은 지우고, 새로 생긴 의문은 자기 트랙 절에 더한다. 같은 PR 에 넣는다.
   완료: todo 변경이 자기 트랙 폴더의 `todo.md`(옮기지 않은 트랙은 `docs/todo.md` 의 자기 트랙 절) 안에만 있다.
6. **핸드오프를 고친다** — 세션을 마칠 때(또는 큰 항목을 끝낼 때) 자기 트랙의 핸드오프 문서(`<플랫폼>/<게임>/handoff.md`, 옮기지 않은 트랙은 `docs/<트랙>-handoff.md`)의 「지금 상태」와 「다음에 할 일」을 고쳐, 다음 세션이 대화 기록 없이 이어 갈 수 있게 한다. 진행 중인 실험의 명령·관찰·다음 단계를 적는다. 같은 PR 에 넣는다.
   완료: 다음 세션이 핸드오프와 todo 만 읽고 첫 실험을 시작할 수 있다.

## 규칙

### TRACK-01 — 트랙과 소유 파일

| 트랙  | 하는 일                                                 | 소유 파일                                                                                     |
| ----- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `dq5` | SFC DQ5 엔진 분석: 실내 맵, 필드, 인물, 출구, 스크립트 | `sfc/dq5/`                                                                                    |
| `dq4` | FC DQ4 원작 데이터 분석: 맵, 대사, 몬스터, 이벤트. SFC 포팅용 그래픽 | `fc/dq4/`(원작 분석), `sfc/dq4/`(SFC 로 만드는 포팅 결과물). 일지 순번은 두 폴더가 함께 씀 |
| `nds` | NDS DQ4 리메이크·한글 팬패치 참고 분석: 명칭 대조, 늘어난 내용, 맵·스프라이트 참고 | `nds/dq4/`                                                                                    |

트랙마다 자기 폴더 `<플랫폼>/<게임>/`(예: `sfc/dq5/`) 하나에 모든 파일을 둔다. 공유 파일에는 트랙마다 그 폴더를 가리키는 한 줄만 둔다. 표에서 폴더 대신 접두어가 적힌 트랙은 아직 옮기지 않은 것이고, 옮길 때까지 옛 경로를 쓴다.

```
<플랫폼>/<게임>/
  README.md        문서 목록, 해킹 일지 목록
  handoff.md       트랙 시작점
  todo.md          남은 일
  references.md    트랙 전용 참고 자료
  docs/            형식 문서 <트랙>-<주제>-format.md
  journal/         해킹 일지 YYYY-MM-DD-NN-<주제>.md
  images/          그림 <트랙>-<주제>.webp
  tools/           도구 <트랙>*.py, tools/lua/ 프로브, tools/README.md
```

세션은 자기 트랙의 소유 파일만 만들고 고친다. 다른 트랙의 파일을 바꿔야 하면 고치지 않고 [docs/todo.md](../../../docs/todo.md) 의 그 트랙 절에 항목으로 남기거나 사용자에게 알린다.

- 이유: 두 세션이 동시에 PR 을 올린다. 같은 파일을 고치면 나중에 머지되는 쪽이 충돌을 풀어야 하고, 그 과정에서 상대 세션의 분석 결과가 지워질 수 있다.
- 새 트랙(예: 빌드·패치 단계의 `build`)이 필요하면 이 표와 [AGENTS.md](../../../AGENTS.md) 의 트랙 표에 한 줄을 더하는 PR 을 먼저 머지한다.

### TRACK-02 — 공유 파일

아래 파일은 여러 트랙이 함께 쓴다. 자기 트랙 몫의 줄·절만 더하거나 고치고, 다른 트랙의 줄은 손대지 않는다.

| 파일                  | 트랙 몫                                                                    |
| --------------------- | -------------------------------------------------------------------------- |
| `README.md`           | 「문서」 의 자기 트랙 목록, 「해킹 일지」 의 자기 트랙 소목록(`#### <트랙>`) |
| `docs/todo.md`        | `## dq5`·`## dq4`·`## nds` 절                                              |
| `docs/references.md`  | 표의 자기 트랙 줄. 두 트랙이 함께 쓰는 자료는 「공통」 절                  |
| `tools/README.md`     | Python 표의 자기 트랙 절(`### <트랙>`), 자기 트랙 도구 절                 |
| `tools/lua/*.lua`     | 기존 프로브는 출력·환경 변수를 바꾸지 않는다. 바꿔야 하면 새 파일로        |
| `tools/listing.py`    | 기존 옵션의 출력을 바꾸지 않는다                                           |
| `pyproject.toml`·`uv.lock` | [dependencies](../dependencies/SKILL.md) 절차로만                    |

- 폴더로 옮긴 트랙은 위 표의 공유 파일에 자기 폴더를 가리키는 한 줄만 두고, 목록·표·절은 자기 폴더의 같은 이름 파일에 쓴다.
- 이유: 공유 파일도 줄 단위로 나뉘어 있으면 git 이 자동으로 합친다. 같은 줄을 둘이 고칠 때만 충돌한다.
- 다른 트랙이 쓰는 프로브의 동작을 바꾸면 그 트랙의 실험이 조용히 다른 결과를 낸다. 그래서 공유 도구는 새 파일이나 새 옵션으로 넓힌다.

### TRACK-03 — 작업 방식

- **PR 은 기능 단위로 묶는다.** 같은 사건·같은 기능의 도구·데이터·검사·문서는 PR 하나에 넣고, 작은 고침도 같은 기능이면 그 PR 에 넣는다. 세션에 맡기는 지시에 「PR 둘로 나눠도 된다」 는 꼴을 쓰지 않는다. 다만 다른 세션이 기다리는 인터페이스(공용 장치)는 먼저 따로 올려도 된다.
- **하위 에이전트 모델을 나눈다(리드용).** 탐색·리스팅·충돌 처리·가드 돌리기·PR 마무리 같은 기계적인 일은 sonnet 이나 haiku, 설계·디버깅·새 사건 구현은 opus 에 맡긴다.
- **동시 세션은 한 트랙에 2개 정도.** 머신 load(`uptime`)가 코어 수(`sysctl -n hw.ncpu`)를 넘으면 새 세션과 무거운 실행(롬 빌드·가드 전체)을 띄우지 않고, 내려갈 때까지 기다린다.
- 이유: 일지·문서·PR 쪼개기에 드는 시간이 작업보다 커지면 속도가 죽는다. 근거는 커밋 메시지·PR 본문에 남아 있어 나중에 `git log` 로 요약할 수 있다. 동시 세션이 코어 수를 넘으면 모든 세션의 실행 검사가 함께 느려진다.
