# 2026-10-25-29: 원작 맵·필드·타일 그림 뽑기

SFC 로 다시 그릴 때 옆에 펴 놓을 참고 그림으로, FC 원작의 마을·던전 맵 279개와 필드 4개, 맵 종류별 블록 시트, CHR 뱅크·폰트 시트, 타이틀·창·전투 장면을 PNG 로 뽑았습니다. 롬만으로 그린 화면이 MesenCE 화면과 픽셀까지 같은지 맵 종류 50가지 중 48가지에서 확인했고, 그러다 필드의 물가가 이웃 칸으로 정해지는 블록이라는 것을 찾았습니다. 쓰는 법과 결과는 [dq4-fcgfx.md](../../dq4-fcgfx.md), 도구는 [tools/dq4fcgfx.py](../../../tools/dq4fcgfx.py) 입니다. 그림 자체는 비공개 에셋 저장소에만 둡니다.

## 1. 색부터 재기

블록 해석([dq4-block-format.md](../../dq4-block-format.md))은 이미 덤프와 0 바이트 차이였지만, 그 도구의 PNG 는 NES 색을 YIQ 로 근사한 확인용이라 화면과 색이 조금씩 달랐습니다. 화면과 픽셀로 견주려면 MesenCE 가 쓰는 RGB 가 필요해서, 색 번호마다 화면 전체를 그 색으로 칠해 찍는 [tools/lua/fc/fcgfxpal.lua](../../../tools/lua/fc/fcgfxpal.lua) 를 만들었습니다.

처음에는 프레임마다 색을 하나씩 바꿔 찍었더니 `pal-01.png` 가 `00` 의 회색이고, `1A`·`1B` 두 장이 같은 초록이었습니다. 화면 덤프가 메모리보다 한 프레임 늦고, 어떤 프레임은 두 번 겹쳐 찍힌 것이었습니다. 색마다 4프레임을 두고 마지막 프레임에 찍자 64장이 모두 한 색이 됐습니다.

```
00 (102, 102, 102)  01 (0, 42, 136)  … 30 (255, 254, 255)  3D (184, 184, 184)
```

## 2. 맵 렌더러와 첫 비교

[dq4block.py](../../../tools/dq4block.py) 의 `Map`(블록 표·그늘 바꾸기·구역)을 그대로 쓰고 블록마다 16×16 그림을 한 번만 만들어 붙이는 렌더러를 짰습니다. 참고용이라 구역 가리기(블록 20·21)는 빼고 칸마다 제 블록을 그립니다.

화면 비교는 RAM 의 장소·왼쪽 위 칸·스크롤·구역·시각만 읽고 나머지를 롬에서 그린 256×240 과 `end.png` 를 견줬습니다. 처음 돌린 결과는 엉망이었습니다.

```
work/v/02-01/: 02/01 맵 종류 0D  비교 61440 픽셀 중 47084 다름
```

`end.png` 가 258바이트, 새까만 화면이었습니다. 워프 뒤 40프레임은 아직 화면이 밝아지기 전이라 100프레임으로 늘렸습니다. 그다음에는 인물 스프라이트와 왼쪽 8픽셀(게임이 BG 를 가림)만 남았는데, OAM 으로 가린 자리가 실제 그림과 프레임이 어긋나 다 가려지지 않았습니다. MesenCE 설정 `--nes.disableSprites=true --nes.forceBackgroundFirstColumn=true` 로 스프라이트를 끄고 왼쪽 열을 보이게 한 화면을 따로 뜨자 `02/01` 이 61440 픽셀 모두 같았습니다.

## 3. 맵 종류마다 하나씩

맵 종류 50가지마다 맵 하나를 골라 워프했습니다. 들어오는 출구가 없어 워프가 좌표를 못 정한 곳은 맵 가운데서 가장 가까운, 위아래로 막히지 않은 바닥 칸을 골라 줬습니다.

```
work/v4/0E-00/: 0E/00 맵 종류 02  비교 61440 픽셀 중 0 다름(뺀 것 0)
…
59개 중 54개 같음
```

48가지가 0 다름입니다(처음 목록에 빠졌던 마지막 그룹 `48` 의 종류 `1B`·`1C` 포함). `02/00` 은 워프로 들어가면 성문 연출이 화면을 성문 쪽으로 옮겨서 RAM 의 화면 자리와 그림이 전혀 달랐고, 연출이 돌지 않는 (0F,20) 에 바로 내리니 0 다름이었습니다. `$62ED` 를 `90` 으로 써서 밤으로 들어간 `02/00`·`0E/00`·`12/00`·필드 0 도 모두 같았습니다.

## 4. 필드의 물가

필드 0 은 성 앞이라 바로 맞았지만 필드 1·3 은 물가에서 어긋났습니다. 화면 칸을 nametable 타일 넷으로 되돌려 블록을 찾으니, 롬 격자로는 블록 `00`(물)인 칸들이 블록 표에 없는 조합이었습니다.

```
00:FC8EFFFA 00:8DF68FF7 06:9FA0A1A2 … 00:FEF5FD90 00:8DF6F9FB
```

물 블록의 타일(`8D 8E 8F 90`) 가운데 몇 개가 `F4`~`FF` 로 바뀌어 있었습니다. 블록 번호를 받아 `$76C0` 을 읽는 `0F:$D49E` 바로 앞을 보니 `0F:$D478` 이 블록 `00` 이면 `$D4A8` 로 가서, 왼쪽·아래·오른쪽·위 칸을 `0F:$D244` 로 찾아 물(`00`·`16`·`0A`)이 아니면 1 을 밀어 넣고 `20` 을 더했습니다. 블록 `20`~`2F` 의 타일은 덤프의 `$7600`+4×블록에 있었고, 그 정의는 `08:$851E` 가 필드일 때만 `$80B7` 의 포인터(`08:$8ABB`)부터 올리는 2바이트 정의 16개였습니다. 이 정의로 만든 타일 그림이 필드 덤프 네 개의 CHR 과 모두 같았고, 렌더러에 넣자 필드 1 도 0 다름이 됐습니다.

같은 자리에 필드 3 의 블록 `01` 을 난수로 `18`·`19` 중에서 고르는 분기도 있었습니다(`0F:$D483`).

렌더러에서 필드 전체를 그리자 마지막 줄에서 `IndexError` 가 났습니다. `0F:$D2AA` 는 좌표에서 3 을 뺀 값이 폭·높이를 넘을 때만 0 이라 가장자리 칸의 이웃은 맵 밖 두 칸까지 원래 줄 데이터를 읽는데, `dq4field.decode` 는 줄을 폭에서 잘라 둡니다. 렌더러는 줄마다 256칸과 아래 세 줄을 따로 풀어 씁니다.

## 5. 장면 화면

타이틀·창·전투는 롬에서 바로 풀지 않고 MesenCE 덤프를 그렸습니다. 정한 프레임마다 nametable·CHR·팔레트·OAM·`$2000` 값을 덤프하는 [tools/lua/fc/fcgfxscene.lua](../../../tools/lua/fc/fcgfxscene.lua) 를 만들어, 전원을 켜 둔 채 기다린 제작진 화면(760프레임)·IV 로고(1040)·타이틀(2440), 이름 입력, 1장·5장 시작, 첫 전투를 떴습니다. `$2000` 은 모두 bit4 가 켜져 BG 패턴 표가 `$1000` 이고 bit5 가 꺼져 스프라이트는 8×8 이었습니다.

```
credits: 화면 61440 픽셀(스프라이트 자리 0 뺌) 중 0 다름, 스크롤 (0,0)
title: 화면 57856 픽셀(스프라이트 자리 3584 뺌) 중 5125 다름, 스크롤 (0,0)
battle: 화면 61376 픽셀(스프라이트 자리 64 뺌) 중 0 다름, 스크롤 (0,0)
```

타이틀에서 다른 곳은 IV 글자(스프라이트)와 아래 물결입니다. 창 테두리와 커서 ▶ 는 폰트 141자 안에 있었고, 이 141자(`18:$B840`)가 네 장면의 CHR 덤프와 모두 같았습니다. 전투 BG 는 검은 바탕과 창뿐이었습니다.

## 6. 장소 이름

파일 이름에 장소 이름을 붙이려 했는데 롬의 장소 이름표는 28개(ルーラ 목적지로 보임)이고 그룹은 73개라 바로 잇는 표가 없습니다. 그룹마다 인물 대사를 모아 「ここは」「ようこそ」 뒤에 나오는 이름을 고르니 24개 그룹에 이름이 붙었습니다(`02` バトランド, `0B` りバーサイド, `42` エンドールのどうくつ 등).

## 7. 맵 수와 주석판

처음에는 `dq4map.maps` 의 269개를 그렸는데, 이 목록은 다음 그룹 포인터로 맵 수를 세어 마지막 그룹 `48`(맵 10개)이 빠집니다. `dq4chest.all_maps` 의 279개로 바꾸자 맵 종류가 둘(`1B`·`1C`) 늘었고, `48/00`·`48/01` 도 워프 화면과 0 다름이었습니다.

주석판에는 블록 속성의 뜻(`dq4block.terrain`)으로 문과 잠금 단계, 계단, 떨어지는 칸, 리프트, 旅の扉, タンス·つぼ, 팻말을 더했습니다. 떨어지는 칸(`05`·`0B`)은 279개 맵에 19751칸이나 돼서(탑 바깥 하늘 등) 글자 없이 테두리만 그리고, JSON 에는 목적지마다 칸을 묶었습니다.

```
fall 19751, damage 1275, conveyor 652, exit 533, door 284, dresser 129, pot 97, lift 14, sign 9, travel_door 9
```

## 틀렸던 것들

- 장소 이름을 대사 전체에서 많이 나온 이름으로 고르면 `11`(ハバりア)이 キングレオ·エンドール 로, `05` 가 エンドール 로 나왔습니다. 인물이 다른 마을 이야기를 많이 해서입니다. 「ここは」「ようこそ」 바로 뒤로 좁혔습니다.
- 장소 이름표 순번 → 그룹 표가 롬 어딘가 있으리라 보고 알려진 몇 쌍(サントハイム→01, バトランド→02 …)으로 표를 찾았지만, 걸린 것은 팔레트 세트 표(`0E:$BC02`)나 도착 표처럼 그룹 순서로 늘어선 다른 표뿐이었습니다.
- 화면이 어긋난 `3B/00` 을 처음에는 팔레트 순환으로 봤는데, 덤프의 팔레트는 롬과 같았고 덤프로 그린 nametable 도 화면과 달랐습니다. 덤프의 CHR 이 롬 그림과 같으니, 화면이 한 프레임 늦은 사이에 폭포 타일 그림이 바뀐 것으로 보입니다.
