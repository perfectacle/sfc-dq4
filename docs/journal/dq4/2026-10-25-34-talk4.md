# 2026-10-25-34: 장 시작 상태의 일행 조건, 맵 목록의 마지막 그룹, 자동 입력

[앞 일지](2026-10-25-28-talk3.md)까지는 일행 조건을 왕좌의 방 한 곳에서 장·일행을 RAM 에 써서 확인했습니다. 이번에는 실제 장 시작 상태 여섯 곳에서 같은 스크립트 37개를 돌렸고, 다름은 0이었습니다. 그 과정에서 맵 목록이 마지막 그룹 `48` 의 10개를 빠뜨리던 버그를 고쳤습니다(맵 279개). `1C:$96CE` 가 3A/04 에서 `$64` 를 바꿔도 대화 번호에 영향이 없음을 실측했고, 이벤트가 쓰는 `$0530` 이 주인공 자동 입력이라는 것도 확인했습니다. 결과는 [dq4-script-format.md](../../dq4-script-format.md) 와 [dq4-map-format.md](../../dq4-map-format.md) 에 있습니다.

## 1. 맵 목록에 그룹 48 이 없었다

`tools/dq4map.py` 의 `maps()` 는 그룹 표 `17:$B181` 에서 **다음** 그룹 포인터까지의 레코드 수로 그룹의 맵 수를 셌습니다. 마지막 그룹은 다음 자리가 `FFFF` 라서 셀 수가 없고, 코드는 그 그룹을 통째로 건너뛰었습니다. 상자 분석(`dq4chest.all_maps`)은 이미 이 구멍을 알고 맵 번호 `FF` 앞까지 읽어 덧붙이고 있었습니다.

`maps()` 가 마지막 그룹을 맵 번호 `FF` 앞까지 읽게 고쳤습니다. `all_maps` 는 고친 `maps()` 를 그대로 쓰게 줄였습니다. 그대로 두면 그룹 48 이 두 번 들어갑니다.

```
$ uv run python tools/dq4map.py rom/dq4.nes check
맵 279개, 경계 278곳 중 0곳 다름
```

그룹 48 의 10개도 앞 맵 `47/01` 의 해제가 끝난 자리에서 바로 이어 시작했습니다. 실제로 들어가서도 확인했습니다. `warp.lua` 로 `48/00`·`01`·`04`·`05`·`07` 에 들어가 `tools/dq4block.py compare` 로 비교하니 그늘 바꾸기 뒤 `$7800` 이 모두 0 차이였습니다.

```
$ uv run python tools/dq4block.py rom/dq4.nes compare work/w4804
맵 종류 1C: 블록 표 0 다름, CHR 타일 63개 중 0 다름(애니메이션 0개 뺌)
BG 팔레트 같음
$7800(그늘 바꾸기 뒤) 225 바이트 중 0 다름, 바뀐 칸 22
```

`48/09` 는 (0C,0C)로 들어가면 해제하자마자 바트랜드 성 옆 필드로 나갔습니다. 그래서 해제 직후(`0F:$E560`)를 `atpc.lua` 로 덤프해 비교했고, 432바이트 0 차이였습니다.

## 2. 장 시작 상태 여섯 곳에서 조건 37개

조건 `03`(살아 있는 일행)·`11`(아이템)·`13`(죽은 일행)·`1E`(선두가 남자)가 들고 호출·서비스 문장이 없는 스크립트는 37개입니다. 이것을 `dq4-ch1`~`ch5-start.mss` 와 디버그 장 고르기 B 상태 `dq4-debugB-start.mss` 에서 돌렸습니다.

말 걸 인물이 있어야 `talk.lua` 의 `TID` 가 듭니다. 그래서 seq.lua 의 `POKE` 로 슬롯 6~9 의 X·Y(`$6F66`~·`$6F86`~)를 주인공 사방 한 칸에 매 프레임 고정하고, `SLOT=06` 으로 진입 슬롯을 정했습니다. 그다음 A 를 330번 눌렀습니다. 3장·4장은 머리 장면이 있어 먼저 넘겼습니다. 3장은 2000프레임쯤 기다린 뒤, 4장은 A 로 대사를 넘겨 15/00 (1A,02)에서 조작할 수 있게 된 뒤의 상태를 썼습니다.

| 상태 | 장소 | 일행 | 말 걸기(바꾼 것) | 참이 나온 조건 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 1장 시작 | 02/01 | ライアン | 56 (37) | `1E` | 다름 0 |
| 2장 시작 | 01/01 | アりーナ | 50 (37) | 없음 | 다름 0 |
| 3장 머리 장면 뒤 | 16/01 | トルネコ | 64 (37) | `03 05`, `1E` | 다름 0 |
| 4장 머리 장면 뒤 | 15/00 | ミネア·マーニャ | 62 (37) | `03 02`, `03 03` | 다름 0 |
| 5장 시작 | 14/00 | 주인공 | 54 (37) | `03 00`, `1E` | 다름 0 |
| 디버그 B | 14/00 | 8명·마차(`$618E` = `20`) | 51 (37) | `03 00`·`02`·`03`, `1E` | 다름 0 |

합쳐서 말 걸기 337번(대화 번호를 바꾼 것 222번)이 디코더 예측과 같았습니다. 기록을 빌린 조건은 0번이었습니다. 장 시작에는 죽은 동료나 조건에 걸린 아이템이 없어 `11`·`13` 은 거짓만 나왔습니다. 그 참 갈래는 앞 일지의 RAM 쓰기 실험으로만 확인한 것입니다. 2장은 アりーナ 혼자라 `1E` 도 거짓이었습니다.

## 3. 3A/04 의 `$64` 바꾸기

대화 번호를 꺼내는 `1C:$96C7` 은 장소가 3A/04 일 때만 `$64` 를 03 으로 바꾸고, `$96FC` 를 부른 뒤 되돌립니다.

```
1C:96CE  c9 3a    CMP #$3A
1C:96D4  c9 04    CMP #$04
1C:96D8  a9 03    LDA #$03
1C:96DA  85 64    STA $64
1C:96DE  20 fc 96 JSR $96FC
1C:96E2  85 64    STA $64
```

`$96FC` 와 거기서 부르는 `$994E`·`$9B71`·`$9798`·`$9BD9` 에는 `$64` 를 읽는 명령이 없습니다. 실측으로도 확인하려고 `tools/lua/fc/talkreads.lua` 를 만들었습니다. 바꿔 둔 동안(`$96DE` ~ `$96E1`) 정해 둔 주소의 읽기를 PC 와 함께 남기는 프로브입니다. 3A/04 (19,01)에서 위의 인물에게 말을 걸었습니다.

```
call 1 63=3A 64=03
read 003A B4 pc=96E7
read 003B B9 pc=96EB
```

`$64` 는 한 번도 읽히지 않았습니다. 목록은 맵에 들어갈 때 정한 `$3A`/`$3B` 만 쓰니, 이 바꾸기는 대화 번호에 영향이 없습니다. 다른 장소의 말 걸기에도 `talk.lua` 의 `w 0064 … 96E4` 줄이 찍히는데, 이것은 되돌리는 `STA $64` 가 같은 값을 다시 쓴 것입니다.

## 4. `$0530` 은 자동 입력

이벤트 `2E` 가 `$0530` = `83` 을, `1C:$BF3B` 가 `8F` 를 씁니다. `$0530` 을 읽는 곳은 고정 뱅크의 주인공 걷기였습니다. `0F:$CA41` 은 bit7 이 켜져 있으면 패드 `$14` 를 `0F:$DB0B` 의 값으로 바꿉니다. `$DB0B` 는 아래 4비트를 1씩 줄이고, 0 이 되면 `$0531` 을 줄여 `$0532`/`$0533` 이 가리키는 뱅크 1C 의 다음 바이트(위 니블 방향, 아래 니블 걸음 수)를 읽습니다(코드 읽기).

`$BF3B` 를 부르는 이벤트 `08`·`0B`·`2C` 를 `EV` 로 돌리며 `$0530` 을 프레임마다 보았습니다.

```
f00142 m=8F n=01 pad=01
f00170 m=8E n=01
f00186 m=8D n=01
f00202 m=8C n=01
...
```

16프레임, 곧 한 걸음마다 1씩 줄었습니다. `80` 다음 `00` 이 될 때까지 누른 A 는 무시됐고, 그 뒤에야 아래로 걸었습니다. `8F` 는 「15걸음 동안 입력 없음」 입니다.

## 틀렸던 것들

- 첫 맵 일지에서는 그룹 표가 그룹 74개(`00`~`49`), 맵 269개, 맵 번호 70가지라고 적었습니다. 실제로는 `17:$B181 + 2×49` 가 끝 표시 `FFFF` 이고, 그룹은 `00`~`48` 의 73개입니다. 마지막 그룹을 세지 못해 맵 10개가 빠졌고, 넣으면 맵이 279개, 맵 번호가 74가지입니다.
- 3장 시작 상태에서 처음부터 `POKE` 로 인물을 붙잡았더니 말 걸기가 한 번도 일어나지 않았습니다. 머리 장면은 인물이 걸어와 끝나는데, 인물 자리를 매 프레임 덮어써서 장면이 끝나지 않은 것으로 보입니다. 장면을 먼저 넘긴 상태에서 다시 돌렸습니다.
- `$0530` 을 시험하려고 처음 고른 이벤트 `04` 는 전투였습니다. 전투에 져 부활 장면으로 가는 바람에 `$0530` 이 `8F` 로 계속 남아, 풀리는 모습을 보지 못했습니다. 전투가 없는 `08`·`0B`·`2C` 로 바꿨습니다.

## 남은 것

- `48/09` 에 들어가면 곧바로 필드로 나가는 까닭. 맵 레코드 첫 바이트 bit7-6(`5B`·`5C` 등)의 뜻.
- 자동 입력 항목 바이트열(`$0532`/`$0533` 이 0 이 아닌 경우)의 실측과, 이를 쓰는 이벤트.
- `1C:$96CE` 가 `$64` 를 바꿔 둘 필요가 있던 곳(대화 번호에는 영향이 없음).
- 앞 일지에서 넘어온 것: 전투를 이긴 뒤의 갈래, 인물·OAM 만 움직이는 이벤트의 장면, 부르는 곳을 못 찾은 이벤트 `0A`·`10`·`20`·`2D`, `1D:$B8CA` 의 나머지 줄, `$618E` 아래 3비트를 바꾸는 때(`10:$91C6`~), `08:$979B` 의 형식, 걸음 간격·방향(`0F:$D884`), 02/01 에서 9명을 숨기는 곳, `$62A5` 갈래.
