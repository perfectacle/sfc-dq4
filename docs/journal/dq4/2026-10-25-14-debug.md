# 2026-10-25-14: 디버그 스위치와 숨은 개발 기능

FC DQ4 에 남은 개발용 기능을 찾았습니다. 고정 영역 첫 바이트 `$C000`(제품판 `FF`)이 비트마다 기능을 끄는 디버그 스위치였고, 테스트러너에서 이 바이트를 바꿔 벽 통과(bit7 + B)·인카운트 끄기(bit6, Start 를 누를 때만 조우)·전투 테스트 창을 실제로 띄웠습니다. 패드 2 를 읽는 유일한 코드는 값을 버리는데, 막힌 분기를 되살리면 패드 2 B 로 두 배 빨리 걷습니다. 결과는 [dq4-debug.md](../../dq4-debug.md) 에 있습니다.

## 1. 커버리지 모으기

먼저 어떤 코드가 한 번도 실행되지 않는지 알아야 했습니다. `probe/cover.lua` 를 18장면에서 돌렸습니다. 타이틀(전원 켜기 3000프레임), 이름 입력, 오프닝, 왕좌의 방 명령 창 8칸을 하나씩 들어갔다 나오기, 필드 걷기, 전투, 그리고 `warp.lua` 로 맵 6곳·필드 2곳에서 무작위로 걷고 말 걸기입니다.

명령 창 8칸을 도는 입력은 칸마다 `a`, 커서 이동, `a`·`a`·`down`·`a`·`a`, `b` 네 번입니다. 화면 몽타주로 はなす·じゅもん·つよさ·どうぐ·そうび·さくせん·とびら·しらべる 가 모두 열린 것을 확인했습니다.

합치면 실행된 명령 28579개였습니다. 이것만으로는 「실행 안 된 바이트」가 대부분 데이터라 쓸모가 없어서, 실행된 명령에서 갈 수 있는 곳만 따라가는 `tools/dq4debug.py unrun` 을 썼습니다. 조건 분기의 다른 쪽, `JMP`·`JSR` 대상, `BRK` 뱅크 호출 대상을 따라가면 「닿는데 안 돈 코드」가 18068명령, 35847바이트, 덩어리 1065개 나옵니다.

## 2. 패드 2

디버그 기능의 가장 흔한 흔적은 컨트롤러 2 입니다. `$4016`/`$4017` 을 쓰는 곳을 롬에서 찾으니, 패드 읽기는 `0F/1F:$C8EC` 하나이고 패드 1 을 `$14`, 패드 2 를 `$15` 에 둡니다. `$4017` 은 `1F:$F090` 이 APU 프레임 카운터로 쓸 뿐 읽는 곳이 없습니다.

영 페이지 `$15` 를 읽는 명령 꼴(`A5 15` 등)은 롬에 100곳 넘게 있지만, 닿는 코드 안에 있는 것은 `$CAD8` 하나뿐이었습니다.

```text
0F:CAD8  a5 15    LDA $15
0F:CADA  29 03    AND #$03
0F:CADC  4c ea ca JMP $CAEA      ; $CAEA 는 곧바로 LDA $0584
0F:CADF  8d 84 05 STA $0584      ; 아무 데서도 오지 않음
```

`$CAD8` 은 걸음마다 실행되는데 값을 버립니다. 바로 뒤 `$CADF` 는 그 값을 걷기 상태 `$0584` 에 쓰는 자리입니다. 이 RAM 은 미끄러지는 바닥에서 `02`, 보통 `01` 이고, `$CA21` 이 `$CA3C+$0584` 의 가면으로 걸음 간격을 정합니다.

실측하려고 `tools/lua/fc/debugpad.lua` 를 만들었습니다. 처음에는 `emu.setInput(버튼, 1)` 로 패드 2 를 눌렀는데 `$15` 는 그대로 `00` 이고 `$14` 가 바뀌었습니다. 포트 번호를 1·2·3 으로 바꿔도, `--nes.port2.type=NesController` 를 줘도, 전원 켜기부터 돌려도 같았습니다. 설정을 보니 MesenCE 의 포트 2 가 `None` 이었습니다. 그래서 패드 읽기가 패드 2 를 다 읽은 `$C90B`(X=1)에서 `$15` 를 덮도록 바꿨습니다. `$15` 를 읽는 곳이 하나뿐이라 결과는 같습니다.

`$CADC` 를 `F0 0C EA`(`BEQ $CAEA; NOP`)로 바꾸고 성 앞에서 아래로 걸었습니다.

```text
패드2 없음: 21 0045=0B, 37 0045=0C, 53 0045=0D   (16프레임에 한 칸)
패드2 B   : 21 0045=0B, 29 0045=0C, 37 0045=0D   (8프레임, $0584=02)
```

필드에서도 B 는 8프레임이었고, 덮어쓰지 않은 롬에서 B 를 누르면 16프레임 그대로였습니다.

## 3. 버려진 함수와 문자열

BRK 함수 표에서 아무도 부르지 않는 항목도 찾아봤습니다. 롬 전체에서 `00 f b2` 꼴 바이트도 없고 같은 뱅크에 주소 참조도 없는 항목은 `08[0E]`·`08[15]`·`14[04]`·`16[02]`·`1D[14]` 다섯 개였습니다. `16[02]` 는 `RTS` 한 바이트입니다. 나머지 넷은 쓰이는 진입점 바로 옆의 형제 진입점이라 디버그 기능은 아닙니다.

대사 2633개에서 「テスト」·「マップ」 같은 말을 찾았지만 없었습니다. 롬의 ASCII 문자열을 훑다가 `12:$AD78` 에서 「`MANABU YAMANA`」를 봤습니다. `12:$AC7A` 가 이 13바이트를 `$6BBF`·`$6BCC` 두 곳과 비교하는 배터리 RAM 유효 표시였고, 세이브스테이트의 SRAM 에 실제로 두 번 들어 있었습니다.

## 4. `$C000`

`find` 로 패드 1 `$14` 를 읽은 뒤 비교하는 곳을 늘어놓자, 미실행인 `1F:$F156` 이 눈에 띄었습니다. 오른쪽이면 장 번호 `$615A` 를 올리고 왼쪽이면 내리는 장 고르기 루틴입니다. 부르는 쪽 `1E:$A35B` 는 이렇습니다.

```text
1E:A35B  ad 00 c0 LDA $C000
1E:A35E  29 08    AND #$08
1E:A360  d0 10    BNE $A372
```

`$C000` 은 `FF` 이고 바로 뒤가 `JMP` 표라 코드가 아닌 스위치 바이트입니다. 테스트러너에서 PRG 메모리 `3C000`·`7C000` 을 `F7` 로 바꾸자 「シナリオ 1 2 3 4 5」 창이 떴고, 오른쪽 두 번에 `$615A` 가 0→1→2 가 됐습니다. 같은 때 다른 세션이 이 창을 찾아 [dq4-save-format.md](../../dq4-save-format.md#디버그-장-고르기) 에 장 시작 표와 함께 정리해 둬서, 장 고르기는 그쪽을 정본으로 둡니다.

롬에서 `AD 00 C0` 꼴을 모두 찾으니 다른 비트를 보는 곳이 더 있었습니다. 앞에서 「미실행」으로 나온 `CEA3`(Start)·`CFB6`·`D093`(B) 패드 검사가 모두 이 검사 바로 뒤였습니다.

- bit7: `$CFB1`·`$D08E` — 맵 걸음에서 B 를 누르면 바닥 검사를 건너뜀.
- bit6: `$CE9C` — Start 를 누를 때만 조우 판정(`18:$9BE6`)을 부름. `11:$BF02` — 몬스터 고르기 창들.
- bit5: `18:$A1F8` 특수 전투. bit4: `10:$9513`.
- 바이트 전체 0: `10:$81B9`, `18:$ABA9`.

## 5. 켜 보기

bit7 은 성 앞마당 (12,0A) 에서 왼쪽으로 걸었습니다. 원래는 벽에 막혀 움직이지 않습니다. `7F` 만 주거나 B 만 눌러도 그대로였고, 둘을 같이 하면 x=`00` 까지 18칸을 지나갔습니다.

bit6 은 필드에서 `dq4state.sh` 의 전투 입력(위아래 왕복)을 1600프레임 줬습니다. 제품판은 374프레임에 전투가 났고(`$6E49`=`01`), `BF` 는 약 93걸음 동안 전투가 없었습니다. `BF` 에 Start 를 같이 누르며 걸으면 230프레임에 전투가 났습니다.

`11:$BF02` 가 들어 있는 함수 `11[14]` 는 투기장으로 보이는 고리(`18:$ABA9`, `$C000`=`00` 일 때)에서만 불려서 정상 경로로는 못 갔습니다. 대신 걸음마다 부르는 `$CEAD` 의 `BRK 00 8F` 를 `BRK 14 1F` 로 바꿔 억지로 불렀습니다. 「― ひき」 네 줄과 「おわり」 창, 몬스터 이름 목록, 마릿수 창이 차례로 떴습니다. スライム 을 고르니 `$6E45`=`00`, 마릿수를 올리니 `$6E49`=`02` 로, 조우 무리 칸에 그대로 들어갔습니다.

bit5 는 읽어 보니 바로 앞 `ORA #$C0` 이 이미 같은 비트를 켜서 차이가 없습니다. bit4 는 장소 비트 `$6165`~ 로 목적지를 세는 처리기를 건너뛰는데, 이 장면들에서는 그 처리기가 돌지 않아 확인하지 못했습니다.

## 틀렸던 것들

- `emu.setInput` 의 두 번째 인자로 패드 2 를 누를 수 있다고 봤습니다. MesenCE 설정의 포트 2 가 `None` 이라 입력이 패드 1 로 들어갔습니다. 명령줄 `--nes.port2.type` 으로도 바뀌지 않았습니다.
- `tools/dq4debug.py brk` 의 첫 결과(111항목)는 「닿는 코드의 BRK 가 부르지 않음」이라 너무 많았습니다. 닿지 않은 코드에도 BRK 가 많기 때문입니다. 롬 전체 바이트에서 찾도록 좁히니 29개, 같은 뱅크 참조까지 빼니 함수 모양인 것은 다섯 개였습니다. 뱅크 `0B` 의 `$8000` 은 함수 표가 아니라 필드 줄 레코드입니다.
- `find` 를 처음엔 미실행 코드에만 돌려 후보가 0개였습니다. 디버그 검사는 매 걸음 실행되면서 분기만 안 타므로, 실행된 코드도 같이 훑어야 했습니다.

## 남은 것

- 전투 테스트 창의 정상 진입(투기장, `$C000`=`00`)과 「おわり」 뒤 그 무리로 전투가 시작되는지.
- bit4(`10:$9513`)를 ルーラ·キメラのつばさ 목적지 고르기에서 실측.
- `10:$81B9` 의 정체.
- 패드 2 흔적의 원래 분기 꼴, A(`01`)·A+B(`03`)의 뜻.
