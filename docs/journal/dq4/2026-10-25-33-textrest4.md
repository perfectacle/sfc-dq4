# 2026-10-25-33: 창 레코드(자리·크기·항목)와 자동 ＊「 의 규칙

대사 앞에 저절로 붙는 `＊「` 가 부르는 쪽과 상관없이 메시지 번호만으로 정해진다는 것을 찾았고, 창 115개의 자리·폭·열 수·항목 목록을 정하는 창 레코드를 풀었습니다. 레코드에서 읽은 자리를 nametable 의 틀과 견주는 도구도 만들었습니다. 결과는 [dq4-text-format.md](../../dq4-text-format.md#창-레코드) 와 [dq4-bank-format.md](../../dq4-bank-format.md) 에 있습니다.

## 1. `$058B` 를 쓰는 곳은 하나

앞 일지까지는 `16:$85C5` 가 `$058B ≥ 5` 일 때 `＊「` 를 붙이므로, `$058B` 를 「대화 종류」 로 보고 부르는 쪽마다 값을 찾으려 했습니다. 먼저 롬 전체에서 `$058B` 를 쓰는 명령을 찾았습니다(`STA`·`STX`·`STY`·`INC`·`DEC` 절대 주소와, 색인 쓰기 가운데 `$0500`~`$058B` 를 덮을 수 있는 것).

```text
STX 16:$8672 …8e8b05
LDA 16:$85C9 …ad8b05
```

쓰는 곳은 `16:$8672` 하나이고, 이 자리는 메시지 번호(X:A)로 시작 위치를 찾는 `16:$8656` 의 첫 단계입니다. X 는 번호의 위 바이트이니 `≥ 5` 는 「메시지 `0500` 이상」 입니다. 실행 중에도 봤습니다(`probe/writes.lua`, `WATCH=058B-058B`).

```text
throne  058B-058B pc=8672 val=06    ; 왕의 060A
court   058B-058B pc=8672 val=02
battle  058B-058B pc=8672 val=01 n=9
```

메시지를 바꿔 띄우면 확실해집니다. 왕에게 말을 건 순간 `textforce.lua` 로 `0002` 를 띄우면 `＊「` 가 없고, `0501` 이면 붙습니다. 전투 첫 메시지를 `0501` 로 바꿔도 nametable 에 `70 6F 1F 31`(`＊「なら`)이 찍혔습니다. 롬의 메시지도 이 규칙에 맞게 쓰여 있습니다. `0500` 미만 1126개 중 380개는 본문이 직접 `＊「` 로 시작하고, `0500` 이상은 하나도 그렇지 않습니다. 그래서 `export` 의 `auto_quote` 를 「번호 `0500` 이상이고 첫 바이트가 `F1` 이 아님」(1361개)으로 바꿨습니다. 경로를 따질 필요가 없어 unknown 은 없습니다.

## 2. 창 번호와 레코드

명령 창을 여는 순간의 스택을 보니 `16:$89C9` 로 돌아가고, 그 위에는 `1E:$8096` 의 BRK 에서 온 복귀 주소가 있었습니다. `16:$89A3`(뱅크 `16` 함수 `07`)이 BRK 뒤 한 바이트를 `$C3EA` 로 읽어 `$F6` 에 두고 `16:$8A03` 을 부릅니다. 곧 창은 `BRK 07 6F nn` 으로 엽니다. 롬에서 이 꼴을 찾으니 71가지 번호가 나왔고, 필드 명령 처리 `1E:$81D7`~`$84B2` 에 몰려 있습니다.

`16:$94B5` 가 `16:$A48A` 의 포인터 표에서 레코드 주소를 `$EE/$EF` 에 둡니다. 레코드를 늘어놓아 보니 명령 창 `03` 은 이랬습니다.

```text
03 $A759 62 12 AA 38 D3 39 3A 3B 3C 3D 40 3F 3E
```

`38`~`40` 은 창 문자열 표의 `コマンド`, `はなす` … `しらべる` 입니다. 머리 두 바이트를 풀려고, 왕좌의 방에서 명령 창을 여는 순간 `$F6` 을 바꿔 115개를 하나씩 띄웠습니다(`textlayout.lua` 의 `WIN=`). 이 프로브는 열기 뒤 `$2006`/`$2007` 로 nametable 에 쓴 칸을 모으고, 그때의 스크롤도 적습니다. 왕좌의 방은 스크롤 X 가 384화소라 nametable 칸에서 48을 빼면 화면 칸입니다.

```text
00 x 2- 7 y 2- 5 w 6 | 31 15 23 …
01 x 2- 7 y 6- 9 w 6 | 31 35 23 …
03 x 4-15 y 2-11 w12 | 62 12 …
05 x18-25 y 4-19 w 8 | 49 21 …
```

폭은 바이트 0 위 니블 × 2, x 는 바이트 0 낮은 니블 × 2, y 는 바이트 1 위 니블 × 2 였습니다. 바이트 1 의 아래 두 비트는 열 수(명령 창 2), bit2 는 셋째 바이트가 있다는 표시입니다(`16:$953C`). 높이는 레코드에 없고 항목 줄 수로 정해집니다.

첫 바이트의 위 니블이 `1` 인 짧은 레코드(`11`, `12`, `13`, `14`)는 `16:$94DB` 가 다음 창의 레코드로 넘어가며 `$03D5` 만 바꿉니다. 강제로 연 `1A`~`1C` 는 `1D` 와 같은 자리에 그려졌습니다.

## 3. 본문 바이트

`16:$9304` 가 본문을 한 바이트씩 갈래로 나눕니다. `00`~`7F` 는 창 문자열 항목, `D0`~`DF` 는 목록 시작입니다. 들여쓰기는 つよさ 창 `0B` 의 화면으로 정했습니다.

```text
 8 │　　　ちから：　　7│      AA 48
10 │　　すはやさ：　　4│      A9 49
12 │　たいりょく：　13│      A8 4A
18 │さいたいＨＰ：　27│      4D
```

`A8`+n 이 붙으면 틀 안 n+2 번째 칸, 없으면 1번째 칸에서 시작합니다. 제목도 같아서 명령 창의 `AA 38` 은 `╴コマンド` 의 `╴` 가 3번째, 글이 4번째 칸입니다. `80`~`9F` 는 항목 루틴입니다. どうする 창 `14` 는 `57 96 58 59 5A`(つかう ? みる わたす すてる)인데 화면에는 みる 가 없습니다. `C0 nn` 은 처음에 `C0` 다음 바이트를 항목으로 읽었는데, `04 … C0 05`, `12 … C0 13` 처럼 뒤 바이트가 창 번호로 보였습니다. 강제로 `04` 를 열면 `05`(주문 목록) 자리까지 그려지고, どうぐ 를 고르면 `12` 다음에 `13` 이 열렸습니다. 커서가 가리킨 동료에 맞춰 함께 여는 「곁 창」 입니다.

## 4. nametable 과 견주기

`dq4text.py rom windows --compare DIR` 은 열기마다 레코드의 x·y·w 와 nametable 의 `┌┐└` 자리를 견줍니다. 처음에는 두 가지가 틀렸습니다.

- 교회·가게의 창이 「틀을 못 찾음」 이었습니다. 열기 사이에 같은 칸을 여러 번 쓰는데, 프로브가 마지막 값만 남겨서 창을 닫을 때 되돌린 배경만 보였습니다. 칸마다 처음 값도 남기게 고쳤습니다.
- 전투 메시지 창 `3D` 는 레코드가 x2 w28 인데 틀은 x3 w26 이었습니다. 영역 끝 칸은 `00` 으로 지우고 틀을 한 칸 안쪽에 그립니다. 셋째 바이트의 bit7-6 이 `01` 인 창(`3D` `50`, `62` `40`)만 그렇고, 필드 메시지 창 `43`(`90`)은 그대로입니다.

```text
$ uv run python tools/dq4text.py rom/dq4.nes windows --compare work/n-* work/s-weapon work/s-tool work/s-church work/s-inn
…
work/s-church: 열기 5 창 41 레코드 x18 y4 w10 / nametable x18 y4 w10 h14 같음
같음 66, 다름 0
```

강제로 연 115개 가운데 틀이 나온 111개의 첫 열기가 모두 같았습니다. `0F`, `34`~`36` 은 왕좌의 방에서는 틀이 나오지 않았습니다. 장면 실험은 필드 명령 8가지, 1장 첫 전투, 바트랜드 마을(`02/00`)의 무기점·도구점·교회·여관(`warp.lua`), 타이틀입니다.

`export` 에 `dq4-window-layouts` 를 더해 창마다 자리·폭·열·본문 갈래·여는 BRK 자리를 JSON·TSV 로 씁니다. DQ5 창에 맞출 때 쓰는 입력입니다.

## 5. 폰트를 다시 올리는 곳과 x3

`BRK 08 8F`(폰트 올리기)를 다시 찾으니 앞 일지의 셋 말고 `17:$8A0E` 가 더 있었습니다. 실행을 보려고 `textforce.lua` 의 `HOOK` 으로 네 자리와 `18:$B7A3` 을 걸고 몇 장면을 돌렸습니다.

| 장면 | 돈 곳 |
| --- | --- |
| 디버그 장 고르기(`$C000`=`F7`, 교회 저장 → 리셋 → 불러오기 → 3장) | 리셋 뒤 `1A:$802E`, 134프레임 뒤 `1E:$A362`, 279프레임 뒤 `1A:$8088` |
| 1장 끝 → 2장 시작 | `1A:$8088` 두 번 |
| 1장 첫 전투 A 40번, 전원 A 연타 3000프레임 | 전투 없음, 전원은 `1A:$802E`·`$8088` |

`1E:$A362` 는 `$C000` bit3 이 0 일 때만 가는 자리라 제품판에서는 돌지 않습니다. `1D:$8E23` 은 뱅크 `1D` 함수 `01` 안이고 `12:$B4D0` 이 부릅니다. `1C:$94CD` 는 앞뒤가 데이터로 보입니다.

`x3` 의 `13`·`83`·`F3` 은 `textbrk.lua` 로 전투·장 끝·필드 보행을 기록해도 나오지 않았고, 함수 `08` 은 모두 `93` 이었습니다. 롬에서 이 꼴을 찾으면 대부분 데이터 뱅크이고, 앞뒤가 코드로 보이는 것은 `83` 의 `10:$BAE1`·`11:$BC2B` 둘뿐입니다.

## 틀렸던 것들

- `$058B` 를 대화 종류로 보고 부르는 쪽마다 값을 찾으려 했습니다. 메시지 번호의 위 바이트일 뿐이었습니다.
- `C0` 뒤 바이트를 창 문자열 항목으로 읽었습니다. 함께 여는 창의 번호입니다.
- 프로브가 칸마다 마지막 값만 남겨, 닫힌 창의 틀이 보이지 않았습니다.

## 남은 것

- 창 레코드의 `B0`~`BF`, `E0`~`FF`, `C1 nn`, 항목 루틴 `80`~`9F` 하나하나의 뜻과 목록 루틴 `D6`~`DF` 가 만드는 항목. 자리 루틴 창(`10`·`29`·`2B`·`4D`)의 자리 규칙.
- 왕좌의 방에서 틀이 안 나온 `0F`·`34`~`36`, 장면에서 열어 보지 않은 창의 쓰임.
- `BRK 08 8F` 의 `17:$8A0E`·`1D:$8E23` 이 도는 장면, `1C:$94CD` 가 데이터인지.
- `x3` 의 `83` 두 자리(`10:$BAE1`·`11:$BC2B`)가 도는 장면. `13`·`F3` 은 쓰이는 곳을 못 찾음.
