# 2026-10-24 (2): 팔레트와 셀 속성

[앞 일지](2026-10-24-dq5-map.md)에서 배치 비트스트림까지 풀고 남긴 숙제를 이어서 풀었습니다.
맵 레코드가 무엇으로 끝나는지, 팔레트가 어디 있는지, 셀 버퍼의 나머지 바이트를 무엇이 채우는지입니다.
결과는 [dq5-map-format.md](../dq5-map-format.md) 에 반영했습니다.

## 1. 팔레트는 그냥 ROM 에 있었다

그림을 칠하려고 매번 MesenCE 의 CGRAM 덤프를 쓰던 것을 없애고 싶었습니다.
먼저 CGRAM 을 16색 줄 단위로 잘라 ROM 에서 그대로 찾아봤더니, 맵이 쓰는 1~7번 줄이 모두 압축 없이 나왔습니다.

| CGRAM 줄 | ROM |
| --- | --- |
| 2·3·4 | `10:EC08`·`10:EC28`·`10:EC48` |
| 5·6·7 | `10:E628`·`10:E648`·`10:E668` |
| 1 | `10:E688` 등 네 곳 |

앞 일지의 ROM 읽기 집계에 `10:DE87` 이 맵 전환 때 `10:E628-10:EC67` 을 읽는다는 줄이 이미 있었습니다.
그 루틴(`10:DE0B`)을 실행 커버리지로 읽으니, `$BC` 로 세트 표를 찾고 → 세트별 목록에서 팔레트 번호 7개를 꺼내 →
`10:E5C8` 의 16색을 복사하는 단순한 구조였습니다. 목록이 세트마다 둘인데, 어느 쪽을 쓸지는
`JSL 21:8000` 이 `7E:075E ≥ $F0` 인지로 정합니다(이 값의 정체는 아직 모름).

Python 으로 옮겨 CGRAM 덤프와 비교했습니다.

```
work/snap2/c00600.bin set 6 alt 0 rows equal [1, 2, 3, 4, 5, 6, 7]
work/snap2/c01710.bin set 6 alt 0 rows equal [1, 2, 3, 4, 5, 6, 7]
```

이제 맵 그림은 롬만으로 그리고, 덤프로 칠한 그림과 픽셀 차이가 없습니다.

## 2. 「인물 데이터」인 줄 알았던 것

앞 일지에서 비트스트림 바로 뒤(`18:E326-`)를 `01:B8xx` 가 읽는 것을 보고 인물·이벤트 데이터라고 짐작했습니다.
리스팅을 읽어 보니 셀 버퍼의 `+0`·`+1`·`+4` 를 고치는 **속성 패스 셋**이었습니다.
셋 다 같은 니블 리더(`01:B8A8`·`01:B8DD`)와 같은 엔트리 형식을 쓰고, 고치는 비트만 다릅니다.

니블 리더는 의미를 이해하기보다 상태(`$03` 의 bit7)까지 그대로 옮기는 쪽을 택했습니다.
읽는 방식이 직관적이지 않아서(첫 니블을 바이트째 돌려주는 등) 해석하다 틀리느니 똑같이 흉내 내는 편이 확실했습니다.

## 3. 비교했더니 패스 전부터 어긋났다

패스 시작(`01:B7AC`)과 끝(`01:BA4C`)에서 WRAM 을 떠서 비교하니, 패스를 돌리기도 전에 모든 셀이 달랐습니다
(02/06 은 3,744칸 = 78×48 전부). 디코더가 끝난 뒤 패스 전에 무언가 셀마다 값을 하나 OR 하고 있었습니다.

- 셀 `+1` 을 쓰는 코드를 감시하니 `01:9414` 루프였고, `$1A6F` 를 OR 했습니다.
- 그런데 `$1A6F` 에 쓰는 코드는 감시에 걸리지 않았습니다. RAM 주소를 `00:`·`7E:`·`80:` 으로 다 걸어도 마찬가지였습니다.
- 그래서 반대로 맵 머리를 **읽는** 코드를 잡았더니(`rwatch.lua`) `01:97D0` 이 머리 9바이트를 하나씩 읽어 RAM 여기저기에 나눠 넣고 있었고,
  `+5` 의 아래 니블이 `$1A6F` 였습니다. 쓰기 감시에 안 걸린 이유는 아직 확인하지 못했습니다.

이것으로 머리 바이트 대부분의 행선지가 정해졌습니다(뜻은 몇 개 남음).

## 4. n+1 이 아니라 n+2

기본값 단계를 넣자 패스 전 비교는 0바이트가 됐지만 패스 뒤는 109바이트가 달랐습니다.
틀린 셀이 (35,7)·(35,8)·(35,9) 처럼 반복 구간의 **끝 칸 바로 다음**에 몰려 있었습니다.

```
01:B80D  LDX $09      ; 횟수
01:B80F  INX
...                   ; 한 칸 처리
01:B82F  DEX
01:B830  BPL $B81A
```

`INX` 뒤 `DEX/BPL` 이라 n+2 번 돕니다. 고친 뒤 두 맵 모두 0바이트가 됐습니다.

## 5. 레코드 경계로 346개 전부 검증

패스까지 넣으니 레코드 끝을 알 수 있게 됐고, 그게 바로 다음 맵의 시작과 맞닿는지로 모든 맵을 검사할 수 있었습니다.
게임과 직접 비교한 것은 두 맵뿐이지만, 형식을 하나라도 잘못 읽으면 경계가 어긋나므로 좋은 검사입니다.

```
Counter({1: 342, 0: 3, 'last': 1})
```

342개는 끝 다음 바이트가 정확히 다음 맵이고, 3개는 패스 3 이 반 바이트에서 끝나 리더가 한 바이트 더 넘어간 경우입니다
(패스 3 은 끝에서 니블을 맞추지 않음). 마지막 1개는 비교할 다음 맵이 없습니다.

## 6. 속성 값의 뜻 (가설)

셀 버퍼를 매 프레임 읽는 코드를 모아 보니(`rprofw.lua`) 뱅크 `$2B` 의 루틴이 인물 주변 셀의 `+0`·`+1`·`+4` 를 보고 있었습니다.
인물이 위층 뒤로 숨는지 정하는 쪽으로 보이는데, 전부 읽지는 않았습니다.

대신 값을 맵 위에 칠해 봤습니다. 모양이 너무 분명해서 가설로 적어 둡니다.

![02/07 셀 +1 아래 니블: 1 초록, 8 빨강, 9 노랑. 파란 점은 +0 bit3](../images/dq5-map-0207-attributes.webp)

- 1: 바닥. 침대·탁자도 1 이라, 가구에 막히는 것은 다른 값(블록 속성 `+4` 로 추정)이 맡는 듯합니다.
- 8: 벽.
- 9: 벽 아래 띠. 위층 벽에 가려지는 바닥.
- `+0` bit3: 문틀처럼 위층이 인물을 덮는 칸.

직접 걸어 보거나 판정 코드를 끝까지 읽어야 확정할 수 있습니다.

## 틀렸던 것들

- 비트스트림 뒤 데이터 = 인물·이벤트: 아니었다. 셀 속성 패스였고, 레코드 안에 인물 데이터는 없다.
- 셀 `+0` 은 안 씀: 기본 속성과 패스 2·3 이 쓴다.
- 반복 칸 수 n+1: `INX` 를 놓쳤다. n+2.
- RAM 쓰기 감시로 `$1A6F` 출처 찾기: 걸리지 않았다. 반대로 데이터를 읽는 쪽을 잡아 해결.
