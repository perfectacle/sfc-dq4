# 2026-10-25-17: 이민 마을 단계 전환, 얻는 물건 자리와 종류

[15 일지](2026-10-25-15-param3.md)에서 못 푼 셋을 다시 봤습니다. 이민 마을 단계는 고르는 곳과 플래그를 실측으로 찾았고, 얻는 물건은 실제로 가서 열었습니다. 가게 레코드를 고르는 코드는 이번에도 찾지 못했습니다. 결과는 [param-format.md](../docs/param-format.md) 와 [extras.md](../docs/extras.md) 에 있습니다.

## 1. 이민 마을 단계

앞에서는 ARM9 의 맵 이름 표에서 막혔습니다. 이번에는 SCRIPT 폴더에서 `ss1out` 같은 맵 이름 바이트를 찾았습니다. 나오는 파일은 `field.bin` 하나뿐이었습니다. `ndsscript.py dump` 로 보니 initialize 에 이야기 플래그 갈래(명령 `0x18`)가 다섯 겹으로 들어 있고, 갈래마다 `0x48` 명령이 `ss0out`~`ss5out` 을 필드 기호에 씁니다. 각 단계 옆의 `0x102 a b` 아래에는 다음 단계 플래그를 켜는 `0x17` 이 있었습니다.

실측은 5장 상태에서 했습니다. 단계 플래그 481·484·490·502·504 를 RAM 에서 0~5개 켜고 필드 장면으로 들어간 뒤 RAM 에서 `ssNout` 문자열을 찾았습니다. 정적 자료 밖에서는 `0x020EAEDA` 한 곳만 값이 바뀌었고, 켠 플래그 수에 따라 `ss0out`~`ss5out` 이 되었습니다.

`0x102` 는 롬 전체 SCRIPT 에서 이민 마을 파일 넷에만 나옵니다. 인자는 1·5, 5·9, 9·13, 13·17, 17·25 로 이어지는 구간입니다. 그래서 「이민자 수가 a 이상 b 미만이면 다음 단계」로 읽었습니다. 처리 루틴은 찾지 못했습니다. 시도한 것은 이렇습니다.

- 명령 번호 표: 함수 포인터 0x100개 넘게 이어지는 표를 ARM9·오버레이에서 찾았습니다. 오버레이 0 의 표는 6낱말짜리 클래스 표(83개)였습니다.
- 명령 이름 표: ARM9 `0x020C0840` 의 (번호, 이름) 표는 대사 변수(`%a`) 이름 표였습니다.
- switch 경계: `add pc` 앞에 0x177 이상과 견주는 곳을 찾았지만, 경계가 0x3E7·0x10E·0x1B1·0x1BB 인 것뿐이었습니다.

이민자 수를 담는 RAM 도 이 때문에 찾지 못했습니다.

## 2. 얻는 물건을 실제로 열기

맵 팩 `FMAP` 의 배치 `+0x2C`(조사 대상 번호)가 얻는 물건 표의 `+04`(물건 번호)와 같았습니다. caf1 은 26개가 모두 짝이 맞았습니다. 그래서 물건마다 자리와 모델 이름을 알 수 있고, 종류 바이트를 모델 이름과 견줄 수 있었습니다. `07` 보물상자, `25` 통(taru), `27` 항아리(tubo), `11` 서랍, `1C` 옷장 등이었습니다(맵 전체 통계).

화면 확인은 1장 haout 의 통(물건 1114, やくそう)으로 했습니다.

1. 주인공 자리 `0x020EC524` 를 통의 `FMAP` 좌표 남쪽으로 썼습니다. 처음에는 1.25·1.3 떨어뜨려 「足もとを 調べた」만 나왔습니다. 0.6·0.8 로 붙이자 「タルの中を のぞきこんだ。」가 떴습니다.
2. 메뉴는 X 뒤 「しらべる」(아래·오른쪽)입니다. A 만 누르면 아무것도 일어나지 않았습니다.
3. 「やくそうを みつけた！」→「手に入れた。」 뒤 RAM 을 견주자 `0x020CE26C` bit3 이 켜졌습니다. 이 물건의 열었음 플래그는 291 이고, 291 = 36 × 8 + 3 이라 플래그 배열은 `0x020CE248` 입니다.

## 3. 가게 레코드를 고르는 코드

haout 스크립트(615줄)를 `ndsscript.py dump` 로 봤지만 가게를 여는 명령은 보이지 않았습니다. 가장 많은 명령은 `0x18`·`0x4A`·`0x07`(인물 번호 하나) 순이었고, 가게 문장도 없었습니다. 가게 인물은 스크립트가 아니라 맵 인물 표 쪽에서 정해지는 것으로 보고 남겼습니다.
