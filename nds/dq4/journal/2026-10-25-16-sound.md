# 2026-10-25-16: 소리 묶음(SDAT) 풀기와 곡이 울리는 장면

NDS DQ4 의 소리 자료 `sound_data.sdat` 를 풀어 곡 50개·서곡 스트림·효과음 634개·샘플 362개를 뽑고, 게임이 곡을 고르는 함수를 찾아 장면마다 실제로 부른 곡을 기록했습니다. 결과는 [sound-format.md](../docs/sound-format.md) 에 있고, 뽑은 소리는 비공개 에셋 저장소 `nds/dq4/sound/` 에만 둡니다.

## 1. SDAT 의 목록

`SYMB`·`INFO`·`FAT`·`FILE` 네 블록을 읽으니 SEQ 52칸(0·1 은 빈 칸), SEQARC 1개(`SEQ_SE`, 안쪽 1171칸 중 634개), BANK 54개, WAVEARC 4개, PLAYER 9개, GROUP 1개, STRM 1개(`STRM_OVERTURE32_8`)였습니다. FAT 의 파일 110개가 이 수와 맞습니다.

```text
$ uv run --locked python nds/dq4/tools/ndssound.py info
[seq] 칸 52, 레코드 50
    2 SND_BGM_M02_MENUET               파일   0 뱅크   2 음량  95 플레이어 0 우선 50/50
...
[strm] 칸 1, 레코드 1
    0 STRM_OVERTURE32_8                파일 109 형식 PCM8 채널 2 32728Hz 샘플 3834883 루프 0 음량 127
```

같은 폴더의 `sound_data.sadl` 은 `#define` 755줄짜리 C 머리 파일이었고, 이름과 번호가 `SYMB` 와 하나도 빠짐없이 같았습니다. 곡 이름은 `DEBUG/soundlist.dat`(사운드 테스트 이름표)에서 일본어로 나왔습니다. `BGM, 1,序曲` 부터 `BGM,49,重要アイテム発見` 까지 SEQ 번호와 같고, 1 이 스트림입니다.

## 2. 합성

참고 구현(ghost-trick 의 `sseq_render.py`)은 음표·악기·트랙·팬·음량·템포만 다뤘습니다. 이 게임은 곡에서 음높이 휨·모듈레이션·ADSR 덮어쓰기·표현을, 효과음에서 이음·포르타멘토·휩쓸기·되풀이까지 써서 시퀀서를 새로 짰습니다. 프레임(약 191.96Hz)마다 템포 누산기로 틱을 돌리고, 음마다 엔벨로프·LFO·휩쓸기를 갱신해 (이득, 속도)를 쌓은 뒤 numpy 로 한꺼번에 그립니다. 곡 하나에 수 초입니다.

루프는 트랙이 앞자리로 건너뛰는 첫 `94` 로 찾았습니다. 처음에는 첫 트랙이 뛰는 순간 루프를 정했는데, 트랙마다 루프 길이가 다를 수 있어 모든 트랙이 루프하거나 끝날 때까지 기다려 가장 긴 루프를 고르도록 바꿨습니다. 1회차와 2회차의 음을 견주니 7곡에서 0.999~1.000 이 같았습니다. 파형으로 견주면 상관이 0~0.9 로 흩어지는데, 틱이 프레임 단위로 떨어져 회차마다 음 시작이 표본 몇 개씩 어긋나기 때문입니다.

## 3. 에뮬레이터 소리와 견주기(실패)

합성이 맞는지 보려고 desmume libretro 코어의 소리를 녹음했습니다. 곡을 고르려고 곡 시작 함수의 인자를 바꿔 끼우니(아래 4절의 훅) 힙에는 바꾼 곡의 SSEQ 가 실렸는데, 녹음은 바꾼 곡이 무엇이든 스펙트럼이 같았습니다(43Hz 근처가 가장 큼). 스펙트로그램을 그려 보니 녹음은 리듬이 보이지 않을 만큼 뭉개져 있었고 합성 쪽은 음표가 또렷했습니다. ghost-trick 이 쓴 코어 빌드도 같았습니다. 코어가 소리를 동기 모드로 내기 때문으로 보이며, 대조는 남은 것으로 둡니다.

## 4. 곡을 부르는 함수

장면 11곳(성 낮·밤, 마을 낮·밤, 던전, 탑 등)에서 RAM 을 떠 「그 장면의 곡 번호와 같은 값」을 찾으니 `0x020EAA78`·`0x02108204`·`0x02108220` 셋만 남았습니다. 이 주소를 상수로 가진 코드를 따라가 음 관리자 `0x02108200` 의 메서드와 곡 시작 `0x0208420C`(핸들, 곡), 효과음 시작 `0x02084268`(핸들, 0, 번호)을 찾았습니다.

기록에는 브레이크포인트가 없어서, 두 함수의 첫 명령을 RAM 위 빈 자리(`0x023F9000`)의 기록 루틴으로 가는 분기로 바꿨습니다. 기록 루틴은 인자와 돌아갈 주소를 고리 버퍼에 쓰고 원래 첫 명령을 실행한 뒤 돌아갑니다. ARM 명령은 손으로 인코딩해 Capstone 으로 거꾸로 풀어 확인했습니다(keystone 은 이 환경에서 불러지지 않음).

```text
    46            BGM h=0x2108210 a1=14   (cgout1 에 들어감)
   367            BGM h=0x2108210 a1=5    (1장 필드)
   811            BGM h=0x2108210 a1=30   (전투 테스트)
  1108            SE  h=0x2108250 a2=300  (명령 고르기)
  1145            SE  h=0x2108270 a2=401  (적 공격)
```

## 5. 맵·필드·전투의 곡

- 맵: 맵 정보 표(`0x020A294A`)의 `+6`·`+7` 이 (낮 곡, 밤 곡)이었습니다. 6장 상태에서 544맵을 낮으로, 밤 곡이 다른 266맵을 밤으로 들어가니 741건 중 733건이 표와 같았습니다. 처음에는 183건이 어긋났는데, 대부분 이미 마을 곡(14)이 울리고 있어 곡 함수가 요청을 내지 않은 것이었습니다. 「요청이 없으면 지금 곡을 본다」로 고쳐 셌습니다. 실측은 맵을 4조각으로 나눠 에뮬레이터 넷을 함께 돌렸습니다.
- 필드: `0x02025BF8` 이 장마다 5·7·9·12, 5·6장은 플래그와 일행 첫 인물로 고르고, 탈것이면 28·25 를 씁니다. 장 시작 세이브스테이트 6개와 탈것 칸 1·2 가 모두 코드대로였습니다. 6장의 첫 자리를 바꾼 실험은 모두 20(마차)이라 선두별 곡은 확인하지 못했습니다.
- 전투: `0x02025D68` 은 기본 30, 4장이면 11, 조우 레코드(`0x0209B774`)의 곡이 있으면 그 곡입니다. 조우 레코드 번호를 고정하고 걸어 일으킨 전투 19건이 모두 표대로였습니다.
- 스크립트: 명령 분기 표에서 `0x86`(곡)·`0x147`(곡, 필드 곡 자동 끔)·`0x62`(효과음)의 처리기를 따라가 곡 함수·효과음 함수를 부르는 것을 확인했습니다.
- 오프닝·타이틀에서는 곡 요청이 없었고, 서곡 스트림 자료가 RAM 버퍼에 차례로 실렸습니다(10초에 5.3초 자리, 30초에 25.4초 자리).

장면을 실측한 곡은 SSEQ 25개와 서곡입니다.

## 6. FC·DQ5 와 같은 장면

FC 곡은 dq4 트랙의 [dq4-sound-format.md](../../../fc/dq4/docs/dq4-sound-format.md) 가 장면별로 적어 둔 것과 맞췄습니다. FC 도 장별 필드 곡을 일행 첫 인물로 고르고 4장 전투에 ジプシー 곡을 써서, DS 와 고르는 방식이 같았습니다. FC 의 エンドール 맵 `04/07`·`04/0E` 는 FC 맵 그림으로 관중석·카지노임을 보고 DS 18·16 과 짝지었습니다. FC 맵 곡 고르기가 시간을 보지 않으므로 성·마을의 밤 곡(3·15)은 DS 에서 늘어난 것이고, ピサロ 곡(26·27·51)도 늘어났습니다. 이민 마을과 6장 맵은 새 곡 없이 기존 곡을 씁니다.

DQ5 는 [dq5-sound-format.md](../../../sfc/dq5/docs/dq5-sound-format.md) 의 장면표와 맞췄습니다(필드·배·나는 탈것·天空城·전투·여관·전원 뒤 첫 곡).

## 틀렸던 것들

- 에뮬레이터 녹음 두 개가 같다는 결과를 보고 곡 바꿔치기가 안 먹은 줄 알았습니다. 힙에 실린 SSEQ 는 바꾼 곡이었고, 녹음 자체가 뭉개져 있었습니다.
- 조우 레코드 표 포인터를 리터럴 값에서 한 번 더 따라가 0 을 읽었습니다. 리터럴이 곧 객체 주소(`0x020C51D8`)이고 표는 `+0x50` 의 값입니다.
- 6장 선두 실험에서 마차 칸을 `0x020C4EB0` 으로 보고 0 으로 묶었으나 곡이 바뀌지 않았습니다. 마차 칸이 다른 곳이거나 조건이 더 있는 것으로 보입니다.
- 인물 번호 25 를 이름 없이 두었다가, 이름 표 `b1001000` 색인 + 1 규칙으로 ピサロ 임을 확인했습니다.
