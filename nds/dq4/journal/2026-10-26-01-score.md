# 2026-10-26-01: 곡·효과음 악보를 FC 와 같은 json·txt 로

NDS 곡 50개와 효과음 634개의 악보를 FC 곡과 같은 꼴의 `NN-이름.json`(트랙별 명령·음 시간표)과 `NN-이름.txt`(사람이 읽는 덤프)로 냈습니다. DS 에만 있는 곡(ピサロ 26·27·51, 밤 곡 3·15, 17·33 등)을 SFC DQ5 의 SPC 악보로 옮길 때 FC 곡과 같은 변환기를 쓰려는 것입니다. 형식은 [sound-format.md 「악보」](../docs/sound-format.md#악보jsontxt) 에 있고, 뽑은 파일은 비공개 에셋 저장소 `nds/dq4/sound/` 에만 둡니다.

## 1. FC 의 꼴

FC 의 `fc/dq4/sound/songs/02.json` 은 최상위에 `id`·`kind`·`tempo`·`ticks_per_second`·`tempo_changes`·`loop_start`·`loop_len`·`end_tick`·`channels[]`·`timeline[]` 을 둡니다. `channels[].items[]` 는 롬 구조(되풀이·부르기)를 그대로 둔 명령 목록이고, `timeline[]` 은 드라이버를 돌려 펼친 음입니다([FC 「중간 형식」](../../../fc/dq4/docs/dq4-sound-format.md#중간-형식json)). txt 는 `곡 NN: …` 머리, `[채널] 주소` 와 `주소 바이트 명령` 줄, 끝의 음 사건입니다.

SSEQ 는 기종 채널 대신 트랙(최대 16)이 있어 `channels[]` 를 트랙마다 하나(`track0`~)로 두었습니다. FC 와 뜻이 같은 명령(`note`·`rest`·`tempo`·`jump`·`call`·`return`·`transpose`·`end`)은 같은 이름을, 나머지는 SSEQ 명령 이름(`program`·`pan`·`volume`·`expression`·`attack`~`release` 등)을 썼습니다. SSEQ 에만 있는 정보는 최상위에 더했습니다: 4분음표 48틱(`ticks_per_quarter`), SEQ 레코드의 뱅크·음량·우선·플레이어, 그 곡이 쓰는 프로그램마다 SBNK 악기 정의(구간·파형 파일·기준 음·ADSR·팬).

## 2. 명령은 시퀀서가 지난 자리에서 푼다

`items` 를 정적으로 따라 풀면 부르기(`95`)의 목적지·되풀이(`D4`/`FC`)·트랙 열기(`93`)를 모두 따라가야 합니다. 이미 MIDI·WAV 를 만드는 시퀀서가 트랙마다 지난 명령 위치를 `Track.visited` 에 모으고 있어, 그 위치를 주소 순으로 하나씩 푸는 디코더(`decode_cmd`)만 새로 짰습니다. 곡을 루프 2회까지 따라가므로 지나지 않은 명령은 없고, 명령 종류별 수가 형식 문서의 명령 표와 모두 같았습니다.

```text
rest 117419, volume 77342, note 42970, tempo 11068, call 2052, bend 921, return 813, program 513,
mod-depth 467, pan 460, expression 441, bend-range 438, note-wait 433, open-track 383, jump 302, ...
```

음의 길이는 FC 와 뜻을 맞추기 어려웠습니다. FC 의 음은 `len`(다음 음까지)과 `gate`(울리는 길이)를 가지는데, SSEQ 는 `note-wait`(`C7`)가 0 이면 음이 기다리지 않고 쉼이 시간을 넘깁니다. 곡은 모든 트랙이 0 입니다. 그래서 `items` 의 음에는 `gate` 만 두고, `timeline` 에 그때 기다린 틱을 `len` 으로 적었습니다.

```text
곡 1A: ピサロ (SND_BGM_M26_PISSARRO), SSEQ 파일 24, 뱅크 26 BANK_BGM_M26_PISSARRO, 음량 95, 플레이어 0, 트랙 0:$001C 1:$0D87 …

[track0] $001C
  001C  FE FF 01      track-alloc 01FF (트랙 0,1,2,3,4,5,6,7,8)
  001F  93 01 6B 0D 00  open-track 1 → $0D87
  …
  0047  C7 00         note-wait 0
  0049  E1 40 01      tempo 320 (255.9 틱/초)
```

## 3. 서곡은 악보가 없다

서곡(`01` 序曲)은 SSEQ 가 아니라 STRM(PCM8 스테레오 녹음)이라 악보가 없습니다. `songs/index.json` 의 `01` 에 `"score": null` 과 까닭(`scoreNote`)을 적고, 같은 곡의 FC 악보 자리(`fcScore`: `fc/dq4/sound/songs/02.json`)를 가리켰습니다. 포팅은 FC `02` 악보를 씁니다.

## 4. 악보로 MIDI 를 다시 만들어 견주기

json 만으로 곡을 옮길 수 있는지 보려고, `items` 만 읽어 트랙을 돌리는 해석기(`score_events`)를 시퀀서와 따로 짰습니다. 틱마다 열린 순서대로 트랙을 돌리고, 기다림을 하나 줄이고, 새로 연 트랙은 다음 틱부터 돌립니다. 이것으로 낸 사건을 같은 MIDI 쓰기에 넣어 `.mid` 와 견줬습니다(`scorecheck`).

```text
$ uv run --locked python nds/dq4/tools/ndssound.py scorecheck OUT
02-王宮のメヌエット: 음표 … MIDI 바이트 같음 일치
…
[songs] 50개 중 일치 50, 음표 98679
[sfx] 634개 중 일치 634, 음표 3460
```

곡 50개 모두 MIDI 바이트가 같았습니다. 음 수 98,679 는 MIDI 의 켬·끔 짝 수이고, 기록을 멈춘 틱에 켠 음 4개는 끔이 같은 틱 앞에 정렬되어 짝이 없어 두 번 셉니다. 실제 음은 98,675개입니다. 효과음은 MIDI 를 내지 않으므로 json 의 `timeline` 과 음(틱·트랙·음·세기·gate)을 견줬고 634개 모두 같았습니다.

`export` 의 `.mid`·`.sseq`·`.wav`(곡 폴더 151개, 효과음 634개)도 PR #328 때 에셋 저장소에 올린 파일과 바이트가 같았습니다. 시퀀서에 음마다 상태를 적는 줄만 더했고 소리와 사건은 바뀌지 않았습니다. `index.json` 은 악보 파일 키(`score`·`scoreText`)만 늘었고, 장면(`scenes`)은 에셋 저장소의 것을 그대로 두었습니다.

## 틀렸던 것들

- 검산용 MIDI 읽기가 처음에는 「끔」이 오면 늘 앞서 켠 음이 있다고 보고 멈췄습니다. 기록을 멈춘 틱에 켠 음은 끄는 틱이 같고, MIDI 쓰기가 같은 틱의 끔을 켬보다 앞에 두어 짝 없는 끔이 생깁니다. 짝이 없는 켬·끔을 따로 세도록 고쳤습니다.

## 남은 것

- 악보 json 을 SPC 악보로 옮기는 변환기와 DS 에만 있는 곡의 옮김. SBNK 악기를 DQ5 악기에 대응시키는 표.
- 접두 명령(`A0`~`A2`, 무작위·변수·조건)은 이 게임이 쓰지 않아 검산 해석기가 다루지 않습니다.
