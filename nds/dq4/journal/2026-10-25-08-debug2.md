# 2026-10-25-08: 조우 끄기·필드 워프·장 번호와 플래그·메시지 디버그

[첫 디버그 일지](2026-10-25-04-debug.md)에서 남긴 여섯 가지를 풀었습니다. 조우를 끄는 비트, 필드 좌표의 원본, 장 번호·이야기 플래그·인물 레코드의 RAM 배치, 메시지 디버그 장면의 조작을 찾았습니다. 6장 진입 프리셋이 검게 멈추던 것은 도구 버그였습니다. 결과는 [debug.md](../docs/debug.md) 에 있습니다.

## 1. 조우: 걸음 수가 아니라 난수

イムルへの洞くつ(프리셋 3)에서 한 걸음마다 RAM 4MB 를 남기며 걸으니 19걸음째 전투가 났습니다. 걸음마다 일정하게 변하는 값 중 `0x02110944` 가 3씩 늘어 조우 누적값처럼 보였습니다. 그런데 0 으로 고정해도 똑같이 19걸음째 전투가 났습니다. 같은 세이브스테이트에서 같은 입력이면 난수도 같아서 늘 같은 걸음에서 나는 것이었습니다.

그래서 코드로 갔습니다. 전투 테스트가 전투 준비 객체에 값을 넣는 함수(`0x0200A98C` 등)를 부르는 곳을 모으니, 오버레이 0 의 걸음 처리 끝에서 `0x0200A730` 이 나왔습니다. 그 안의 `0x0200A67C` 첫머리가 조건 다섯 개를 봅니다.

```
0200a68c: ldr r0,=0x020ce100 ; bl 0x0201c790   ; [0x020CE100] & 0x200
0200a696: ldr r0,=0x020c533c ; movs r1,#0x68 ; bl 0x0200fa58   ; 일행 중 상태 0x68
```

`0x020CE100` 은 첫 일지에서 「맵 번호」로 잘못 봤던 값이었습니다. 실제로는 맵 속성 비트이고 `0x200` 이 「조우 있음」이었습니다. 동굴에서 이 비트를 한 번 지우니 300걸음 동안 전투가 없었습니다. 필드에서는 반대로 비트를 켜니 37걸음째 전투가 났습니다.

조우 객체 `0x020C4CD8` 의 칸을 고정하는 길은 막혔습니다. `+0x10` 은 같은 프레임 안에서 `[0x020EB9A8]` 로 다시 쓰였습니다. 그 `0x020EB9A8` 을 0 으로 고정하면 조우가 사라졌지만, 이 값은 장 번호였습니다(3절). 장을 0 으로 바꿔 조우를 없앤 셈이라 쓰지 않습니다.

## 2. 필드 워프

필드 장면(`0x0E`)에서도 `0x020EC524` 가 주인공 자리처럼 움직였습니다. 하지만 써도 다음 프레임에 되돌아갔습니다. 힙에서 같은 값을 가진 칸 세 곳에 차례로 써 보니 `0x0215E4A8` 에 쓸 때 위 화면 지도와 아래 화면 땅이 함께 바뀌었습니다. 힙 주소는 세이브스테이트마다 다를 수 있어서 이 칸을 가리키는 포인터를 거꾸로 따라갔습니다.

```
0x020EC4F0 → 0x0215D950 (주인공 객체), [0x0215D950 + 0x70] = 0x0215E4A8 → x, z
```

한 걸음이 `0x3000` 이라 칸 단위로 받게 했습니다(`ndswarp.py field`).

## 3. 장 번호·이야기 플래그·인물 레코드

프리셋 레코드를 장 시작 프리셋끼리 나란히 놓으니 `+0x9B` 가 1·2·3·4·5·6 이었습니다. 적용 함수는 이 값을 `0x0202B340` 에 넘기고, 그 함수는 `0x020EB9A8` 에 씁니다. 장 시작 상태 8개에서 읽으니 서장 1, 1~6장이 1~6 이었습니다. 서장 프리셋의 `+0x9B` 도 1 입니다.

플래그 함수 `0x0201D60C` 는 `word[n >> 5] |= 1 << (n & 31)` 꼴이었습니다. `0x020CE7DC` 의 32낱말을 장 시작 상태에서 읽어, 프리셋이 켰어야 할 플래그(`param_player_flag.dat` 레코드 0~N)와 견줬습니다. 다섯 장 모두 빠진 플래그가 없었고, 남는 것은 장 시작 이벤트가 켠 것이었습니다.

일행은 `0x0200EB98` 이 「일행 객체 `+0x2D8` 의 i 번째 칸 → `0x020C5B74 + 번호 × 0x50C`」로 인물 레코드를 찾았습니다. 첫 일지의 HP 주소 `0x020C60EE` 는 1번 레코드의 `+0x6E` 였습니다. 레벨은 6장 상태의 ソロ 38·ライアン 37·アリーナ 40 이 모두 맞는 칸을 찾아 `+0x5A` 로 정했습니다.

## 4. 메시지 디버그

장면 `0x16` 의 vtable(`0x020B8F3C`) 갱신 함수 `0x0200A094` 를 읽었습니다. 패드 비트별로 메시지 번호(`+4`)를 1·10·100·…씩 바꾸고, A 로 띄웁니다. `0x020C4C94` 에 500002 를 쓰고 A 를 누르니 「フレア「あの……　お城になにか用が?」」가 떴습니다. Y 는 언어 칸 `0x020CE3E0` 을 바꿨지만 이미 띄운 문장은 그대로였습니다.

## 5. 6장 진입 프리셋 310

다시 해 보니 프리셋 310 은 입력 없이도 ロザリーヒル 화면이 정상으로 떴습니다. 검게 멈췄던 것은 첫 판 도구가 작업마다 부팅 상태로 되돌아가지 않던 버그 때문이었습니다. 그때 만든 세이브스테이트로 다시 확인했던 것이라 같은 증상이 되풀이됐습니다. 6장 시작 세이브스테이트를 310 으로 바꿨습니다.

## 틀렸던 것들

- 「`0x020CE100` 은 맵 번호」: 맵 속성 비트입니다. 지하실 `0x149` 와 바깥 `0x159` 가 달랐던 것은 속성이 달라서였습니다.
- 「`0x020D2874` 는 이벤트 요청 칸」: 값을 아홉 가지로 바꿔 두 장소에서 써 봤지만 아무 일도 없었습니다. 첫 관찰의 대화는 그 자리의 이벤트가 우연히 겹친 것으로 봅니다. `0x020D2870` 은 나무 구조를 도는 일반 용기 객체입니다.
- 「`0x02110944` 는 조우 누적값」: 0 으로 고정해도 전투가 같은 걸음에서 났습니다.
- 「`0x020EB9A8` 을 0 으로 하면 조우 끄기」: 조우는 사라지지만 장 번호를 0 으로 바꾼 것이었습니다.
- 「프리셋 310 은 검게 멈춤」: 도구 버그였습니다.
