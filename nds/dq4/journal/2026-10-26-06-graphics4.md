# 2026-10-26-06: 메모리 감시 코어로 DSSA 반투명·동작 표·LOCN·필드 지도 번호 찾기

[2026-10-25-13](2026-10-25-13-graphics3.md) 에서 남긴 그래픽 항목을 다른 길로 다시 풀었습니다. 앞 회차는 화면을 찍어 견주거나 RAM 을 고쳐 보는 데서 멈췄습니다. 이번에는 desmume 코어에 메모리 감시를 넣어, 자료를 **읽는 코드**를 먼저 찾았습니다. 결과는 [graphics-format.md](../docs/graphics-format.md) 에 넣었습니다.

- DSSA `0x4000` 은 반투명 부품이었습니다. 같은 텍셀을 `A3I5` 와 덧붙은 팔레트로 다시 묶어 그립니다.
- 셀 머리 첫 s16 이 2 이면 표지 셀이고, 프레임 표 앞 8바이트는 대기 동작 첫 프레임의 경계 상자였습니다.
- 몬스터 동작 칸은 오버레이 3 의 동작 표가 정했습니다. 칸 7(주문)·4(숨결)·2·3·12 를 화면으로 확인했습니다.
- `LOCN` 은 걷기 판정 자료가 맞았습니다. 벽은 끝점, 바닥은 높이, 트리거 면은 출입구입니다.
- 필드 지도 번호를 찾아 gotmap·yamimap 을 화면과 견주었고, 다리 기호 변형도 확인했습니다.

## 1. 메모리 감시를 넣은 코어

libretro 코어로는 중단점을 걸 수 없습니다. 그래서 같은 커밋의 desmume 소스를 작업 폴더에 복사하고, 메모리 접근마다 불리는 `CheckMemoryDebugEvent`(`MMU.h`)의 맨 앞에 한 줄을 넣었습니다.

```c
if(type!=MMU_AT_CODE && (u32)(addr - wp_lo) < wp_len) wp_hit(event | (type<<4) | (procnum<<7), addr, size, val);
```

`wp_hit` 는 `libretro.cpp` 끝에 더한 함수입니다. ARM9 의 지금 명령 주소(`instruct_adr`, Thumb 이면 +1)·주소·크기·값·LR·r3~r6 을 6만 칸 버퍼에 쌓습니다. `wp_set`·`wp_count`·`wp_data` 를 내보내 `ndsplay.Player` 의 `core` 로 부릅니다.

처음 빌드한 코어는 한 프레임에 1,700번 남짓만 잡았습니다. 주인공 좌표를 써도 0번이었습니다. 소스를 복사해 와서 `.o` 가 새것처럼 보였고, Makefile 이 헤더 의존을 따지지 않아 명령 구현 파일이 다시 컴파일되지 않은 것이었습니다. `make clean` 뒤에는 걸을 때 주인공 좌표 쓰기가 30프레임에 1,161번 잡혔습니다. 세이브스테이트는 원래 코어와 그대로 오갑니다.

역어셈블은 지난번처럼 `uvx --with capstone` 으로 했습니다. 오버레이가 실린 상태를 그대로 보려고 RAM 덤프를 읽었습니다.

## 2. DSSA `0x4000` — 반투명 부품

ほのおのせんし(m078)와 싸우는 상태에서 RAM 의 `MonsterAnimation` 팩(`0x022C7B58`)을 찾았습니다. 대기 동작 DSSA 를 감시하니 `0x020573B4` 가 기록 16바이트를 스택에 복사하고, 작은 접근 함수들을 불렀습니다.

```text
0x02056FD0  ldrb r0,[r0]        셀 번호(아래 바이트만)
0x02056FD8  ldrb r0,[r0,#1]; and #0xF   기록 종류 → 2 이면 건너뜀
0x02057028  tst #0x10            0x1000
0x0205703C  tst #0x20            0x2000
0x02057050  tst #0x40            0x4000
```

`0x4000` 을 부르는 곳은 둘이었습니다. `0x02058188` 은 비트가 켜지면 바로 돌아가고, `0x02057560` 은 비트에 따라 텍스처 설정 함수를 다르게 불렀습니다.

```text
꺼짐  0x0208481C  TEXIMAGE_PARAM = 형식(+0x20)<<26 | 주소>>3 | 크기 | 0번 투명
      0x0208489C  PLTT_BASE = 본 팔레트(+0x4C)
켜짐  0x020848C8  +0x18 이 1 이면 0x44000000(형식 1, A3I5), 2 이면 0x58000000(형식 6, A5I3)
      0x02084938  PLTT_BASE = 덧붙은 팔레트(+0x6C)
```

같은 텍셀을 반투명 형식으로 다시 읽는 것입니다. `+0x18` 은 `TextureObject` 의 「덧붙은 팔레트 묶음 수」로 적어 두었던 칸입니다. 롬의 1,506개에서 값은 0 과 1 뿐이고, 1 은 256색 199개였습니다. 지난번 78번은 이 값이 0 이라 어느 쪽도 쓰지 않습니다. 그래서 앞 부품의 설정 그대로 그려져 차이가 없었습니다.

아틀라스로도 확인했습니다. 덧붙은 팔레트가 32색보다 작은 77마리에서 `0x4000` 부품에만 쓰이는 셀은 텍셀의 98.6% 가 아래 5비트로 그 팔레트 안을 가리켰습니다. 다른 셀은 59.2% 였습니다. 위 3비트는 0~7 로 고르게 퍼져 알파로 쓰였습니다.

ブルデビル(m133)가 マヒャド 를 외우는 화면을 2프레임마다 찍었습니다. 머리 위에 하늘색 고리가 생기고 흰 빛 덩이와 빛줄기가 나옵니다. 내보내기에 `translucent_atlas` 를 넣어 그 부품을 `A3I5` 로 그리니 같은 모양이 나왔습니다. 본 팔레트로 그리면 검은 고리와 자홍 줄무늬였습니다.

## 3. 셀 머리와 프레임 표 앞 8바이트

DSSA 를 준비하는 `0x0205708C` 는 셀마다 첫 s16 을 2 와 견주었습니다. 2 이면 다음 s16(0~9)을 번호로, 그 셀 번호를 객체의 표지 칸(10개)에 적습니다. 셀 머리 값은 0 이 41,695개, 1 이 769개, 나머지가 (2, k) 꼴이었습니다.

같은 함수는 셀 뒤 주소를 프레임 표 자리로 적고, 8을 더한 곳을 (오프셋, 크기) 쌍의 시작으로 씁니다(`0x02057110`). 그 8바이트를 s16 넷으로 읽고 칸 0 첫 프레임을 조립한 상자와 견주었습니다.

```text
m050  머리 (-62, -35, 1, 39)   첫 프레임 상자 위 -62 왼 -35 아래 1 오른 40
칸 0 이 있는 155마리 모두 1픽셀 안으로 같음
```

기록의 둘째 바이트 아래 4비트도 셌습니다. 0 이 662,894개, 1 이 32,758개(모두 첫 기록), 2 가 11,026개였습니다. 셀은 가장 많아도 200개라 셀 번호는 아래 바이트로 충분합니다.

## 4. 몬스터 동작 칸 — 동작 표

처음에는 몬스터 표 `+0x12` 의 행동 여섯 칸만 바꿨습니다. ブルデビル 에게 マヒャド(16)만 쓰게 하자 주문은 외웠지만 몸은 대기 동작 그대로였습니다. 그대로 둔 표로 싸우면 같은 マヒャド 에서 칸 7 이 읽혔습니다.

칸을 고르는 코드를 따라갔습니다. 칸 7 이 읽히는 순간 팩의 칸 표를 읽은 곳은 `0x02059510`(칸이 있는지)이었습니다. 그것을 부르는 `0x020592AC` 는 칸 번호를 받아 동작을 틉니다. 이 함수를 부르는 곳은 오버레이 3(전투)에 있었습니다. 그중 `0x0211DDE0` 이 행동 번호와 「변형」 번호로 `0x0200BEFC` 를 불러 24바이트 레코드 표를 찾았습니다. 레코드 `+0x12` 가 칸입니다.

표는 오버레이 3 파일의 `+0x114DC` 에 1,123개 있습니다. 감시에 r3~r6 을 넣어 찾을 때의 인자를 보니 이렇게 갈렸습니다.

```text
그대로 둔 표   (133, 16, 1) → 레코드 있음 → 칸 7
16 만 넣은 표  (133, 16, 2), (133, 16, 0) → 레코드 없음 → 대기 그대로
```

변형 번호는 몬스터 표 `+0x28`~`+0x2D` 의 바이트였습니다. ブルデビル 은 `00 01 00 02 00 01` 이고 행동은 `71 16 71 62 71 16` 입니다. 그래서 16 은 변형 1, 62 는 변형 2 이고, 표의 레코드와 같습니다. 행동 이름은 `DEBUG/action.dat` 의 번호와 같았습니다.

행동과 변형 바이트를 함께 고정하고, 몬스터 HP 를 60000 으로 올려 6장 일행과 싸우게 했습니다. 프레임마다 팩 범위를 감시해 20번 넘게 읽힌 칸을 적었습니다.

```text
m078 ほのお小(2)          953  칸 4   「ほのおのせんしは 火の玉を はきだした！」
m302 せいけんづき(1)      562  칸 2   「チキーラは こしを ふかく おとし まっすぐに あいてを 突いた！」
m303 まわしげり(3)        562  칸 3   「チキーラは まわしげりを はなった！」
m242 メッセージ攻撃２(5)  724  칸 12  「ランプのまおうは ぷくーっと ふくれあがって …」
m307 メラゾーマ(5)        724  칸 12  「エビルプリーストは メラゾーマを となえた！」
m000 그대로               1130 칸 3   「スライムの こうげき！」
```

표 전체를 칸별로 모으면 4 는 숨결, 5 는 毒攻撃, 6 은 동료 부르기, 7 은 주문, 8 은 不思議な踊り, 13 은 痛恨입니다. 2·3·9~12 는 몬스터마다 정한 특기였습니다. 앞 회차가 행동 파일 이름으로 짝지은 `tu`·`dk`·`na`·`fo` 도 이 이름들과 맞습니다.

## 5. LOCN — 걷기 판정

`mai1f2` 의 RAM 사본(`0x022AC8B0`)을 감시하니 서 있을 때도 매 프레임 수백 번 읽혔습니다. 걷기에 쓰이지 않는다는 지난번 결론부터 의심했습니다.

파일 머리를 다시 보니 `+0x34` 부터 오프셋이 넷이 아니라 열이었습니다. 면 표, 4바이트짜리 표, 192바이트 표 여섯, 48바이트 표 둘입니다. 면 48개 × 4 = 192 라 여섯 표는 면마다 (s16 열쇠, u16 면) 쌍이고, 열쇠는 좌표의 32배였습니다. 48바이트 둘은 파일에서 모두 0 이고, 걸을 때 게임이 0~10 을 썼습니다. 머리 `+0x10` 의 「면 수 + 넷」은 면 수, 바닥, 벽, 물체 면, 트리거 수(48 = 5 + 23 + 20)였습니다.

면을 종류별로 보니 바닥 5개는 법선이 위, 벽 23개는 옆이었습니다. 물체 20개는 넷씩 묶여 `FMAP` 배치 2~6 을 둘렀고, 면 `+0x5C` 가 그 배치의 `+0x2C`(`0x0C10` 등)였습니다. 지난번에 「경계 상자」로 읽은 두 점은 정렬되어 있지 않았습니다. 벽에서는 선분의 두 끝점입니다.

그다음 RAM 사본을 고쳐 걸었습니다.

```text
벽·물체 끝점 x·z +100     왼쪽 -8.91 까지 걸어 나감(본래 -3.15 에서 막힘)
벽·물체 꼭짓점만 +100     -3.15 에서 막힘
mai1f1 바닥 y +0.2        주인공 y 0.20      -0.2 → -0.20     +0.5 → 0.00
```

`mai1f2` 의 4바이트 표는 (`0x1009`, 4) 였습니다. 면 4 는 방 가운데의 작은 바닥이고 `+0x3E` 가 `0x1009` 였습니다. 그 칸을 밟자 `mai1f1` 로 옮겨 갔고, 주인공은 `mai1f1` 의 `0x1009` 면(계단) 한가운데에 섰습니다. 번호를 0 이나 `0x100A` 로 바꾸거나 면을 옮기면 옮겨 가지 않았습니다.

## 6. 필드 지도 번호와 gotmap·yamimap

오버레이 1 의 경로 문자열 `data/field/bin/gotmap.bin` 은 함수 `0x0211F4C0` 의 상수 풀에 있었습니다. 이 함수는 번호 0·1·2 로 `worldmap`·`gotmap`·`yamimap` 을 고릅니다. 부르는 곳을 거슬러 가니 번호는 `[0x020C4EAC + 4]` 였습니다.

처음에는 `0x020C4EB0` 에 2 를 쓰고 필드를 요청했는데 평소 지도가 떴습니다. 그 주소를 감시하니 필드에 들어갈 때 `0x02123900` 이 `0x020C4EB4` 를 읽어 `0x020C4EB0` 에 덮어썼습니다. `0x020C4EB4` 에 쓰자 지도가 바뀌었습니다.

화면과 그린 지도를 견주다가 좌표 단위도 바로잡았습니다. `ndswarp.py field` 의 한 칸은 3픽셀이라 지도 칸(16픽셀)에 서려면 칸 × 16/3 을 줘야 합니다. 이 값으로 worldmap 두 곳이 0.953·0.972 였고, 이어서 gotmap 은 10곳에서 0.939~0.968, yamimap 은 0.875~0.966 이었습니다. 모두 어긋남 0 에서 가장 높았습니다.

기호 변형은 6장 상태에서 견주었습니다. 두 다리 자리 모두 그림 0(다리)이 1.0 이었습니다. 砂漠のバザー 는 이민자 수 0~8 에서 그림 4 가 맞았고, 9~17 에서는 기호가 화면에 없었습니다. 처음 점수가 0.375 로 낮았던 것은 1픽셀 어긋남 때문이었습니다. 화면에서 그림 21장을 다 찾아보니 그림 4 가 1픽셀 옆에서 1.0 이라 ±2픽셀을 찾게 했습니다.

## 틀렸던 것들

- **`0x4000` 은 평상시 화면에 차이가 없다**: 덧붙은 팔레트가 없는 78번만 봤기 때문입니다. 팔레트가 있는 몬스터에서는 반투명입니다.
- **셀 번호는 아래 12비트**: 게임은 아래 바이트만 읽고, 비트 8~11 은 기록 종류입니다.
- **몬스터 표의 행동만 바꾸면 그 동작을 강제할 수 있다**: 변형 바이트(`+0x28`~)가 맞아야 동작 표 레코드가 잡힙니다.
- **LOCN 은 걷기에 직접 쓰이지 않는다**: 바닥을 옮겨서 생긴 착각이었습니다. 벽은 끝점으로 판정합니다.
- **LOCN 면 뒤쪽은 경계 상자, `+0x34` 의 오프셋은 넷**: 경계 상자가 아니라 끝점 둘이고, 오프셋은 열입니다.
- **`0x020C4EB0` 에 쓰면 필드 지도가 바뀐다**: 필드에 들어갈 때 `0x020C4EB4` 로 덮입니다.
- **`ndswarp.py field` 의 한 칸이 지도 한 칸**: 3픽셀입니다.
- **메모리 감시 코어가 접근을 다 잡는다**: 첫 빌드는 헤더를 고친 뒤 다시 컴파일되지 않은 파일이 섞여 일부만 잡았습니다.

## 남은 것

- DSSA 셀 머리 1 인 셀, 표지 셀과 종류 2 기록의 쓰임.
- `LOCN` 정렬 열쇠 표·면별 바이트의 쓰임, 머리 `+0x1C`~`+0x33`, `0x10xx` 밖의 트리거 종류.
- `FMAP` `+0x2C` 다음 필드.
- 이민 마을 9명 이상 단계의 기호.
- 3D 효과를 일행이 주문을 쓰는 장면과 견주기.
