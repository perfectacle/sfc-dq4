# 2026-10-25-05: 그래픽의 남은 것, 에뮬레이터 화면과 맞대기

[2026-10-25-02](2026-10-25-02-graphics.md) 에서 남긴 그래픽 항목을 desmume 화면과 세이브스테이트로 풀었습니다. 그 결과를 정리합니다.

- 몬스터 부품의 좌우 뒤집기 플래그를 찾았고, 프레임 길이를 쟀습니다(1/30초).
- 몬스터 동작 칸 0·1 의 뜻을 확인했습니다.
- 필드 칸 값 → 칩 대응을 화면에서 배워 세계 지도 전체를 그렸습니다.
- `largemap.bin`·물결 패턴·덧그림의 형식을 풀었습니다.
- 3D 관절 애니메이션 BCA0 를 재생할 수 있게 했습니다.
- 맵 판정 면 `LOCN` 의 구조를 풀었습니다.
- 짝 없던 몬스터 둘의 짝을 찾았습니다.

전투 위 화면 배경은 쓰이는 곳을 찾지 못했습니다. 결과는 [graphics-format.md](../docs/graphics-format.md) 에 넣었습니다.

## 1. 세이브스테이트에서 VRAM 꺼내기

화면만으로는 레이어와 텍스처가 어디서 왔는지 알 수 없습니다. desmume 의 세이브스테이트(코어 `retro_serialize`)는 덩어리(id, 크기) 목록입니다. 덩어리 4 안이 「이름 4바이트, 원소 크기, 원소 수, 자료」 항목들이었습니다.

```text
ITCM 1×0x8000  DTCM 1×0x4000  WRAM 1×0x400000  9REG 1×0x2000
VMEM 1×0x800   OAMS 1×0x800   LCDM 1×0xA4000(뱅크 A~I)
```

이것을 읽는 `nds/dq4/tools/ndsvram.py` 를 만들었습니다. `info` 는 DISPCNT·BGnCNT·VRAMCNT 를, `bg` 는 텍스트 BG 를 그림으로 냅니다.

## 2. 세계 지도

`largemap.bin`(1MB)은 지난번에 1024 폭 선형으로 그려 줄무늬만 나왔습니다. 4·8·16·32픽셀 정사각 타일 순서로 바꿔 보니, 32×32 일 때 일러스트로 그린 세계 지도가 나왔습니다. 4096바이트짜리 `.bin` 8개도 같은 팔레트의 64×64 였습니다. 다리, 용암, 이민 마을 4단계, 세계수를 그린 덧그림입니다.

![FIELD/large/largemap.bin 을 1/4 로 줄인 것](../images/nds-gfx-largemap.webp)

필드 장면(`0x0E`)을 띄우니 아래 화면에 위에서 내려다본 타일 지도가 1:1 로 그려졌습니다. 그런데 field.tex 의 8×8 타일은 거의 맞지 않았습니다(정확히 같은 것 9개). 세이브스테이트를 보니 엔진 A 의 BG0 이 3D 였습니다. 텍스처 뱅크 A 를 찾자 field.tex 가 `0x400` 에 그대로 있었습니다. 그 바로 뒤 `0x15400` 에는 `FIELD/texture/pattern8.pack` 의 첫 항목이 있었습니다. 그래서 패턴 팩을 256 폭으로 다시 그렸습니다. `pattern8` 은 파란 물가 칩 80개의 8프레임 애니메이션이었습니다. `pattern24` 는 64×64 바다 물결 24프레임이었습니다. 지난번에 64×64 로 그려 실패한 것은 `pattern8` 쪽이었습니다.

칸 값은 화면에서 배웠습니다. 화면의 파란 부분과 WMAP 의 바다 칸을 맞대니, 칸 하나가 16픽셀이고 화면 왼쪽 위가 칸 (19, 13)일 때 97% 가 같았습니다. 그 화면의 82칸을 VRAM 텍스처의 16×16 칩과 밝기 상관으로 견줬습니다.

```text
128 → pattern8 칩 52 (0.94)   150 → 63 (0.95)   ⇒ 짝수 v → v/2 − 12
209 → field.tex 칩 56 (0.90)  305 → 144 (0.91)  421 → 260 (0.97)
```

물가 칩은 공식 하나로 맞았지만 field.tex 쪽은 오프셋이 153·161 로 달랐습니다. 이웃 값이 이웃 칩이 되는 u16 표를 arm9·오버레이·PARAM·FIELD 전부에서 찾았지만 없었습니다. 다른 화면에서도 배우려고 주인공 좌표로 보이는 `0x020EC524`(x 424, y 295)를 써 봤습니다. 매 프레임 덮여 화면이 옮겨지지 않았고, 고정(`freeze`)해도 같았습니다.

그사이 다른 세션이 필드 워프를 찾았습니다([2026-10-25-08](2026-10-25-08-debug2.md)). 주인공 객체가 가리키는 칸에 쓰면 됩니다. 처음에는 1장 상태에서 81곳을 찍었는데 모두 검은 화면이었습니다. 부팅 메뉴 상태로 바꾸자 80곳이 찍혔습니다. 보정 화면(141.33, 98.33 → 424 픽셀)에서 좌표 단위의 3배가 픽셀이고, 화면 왼쪽 위가 주인공 픽셀 − (129, 97)임을 얻었습니다. 그래서 화면마다 칸 위치를 바로 셀 수 있었습니다. 값마다 가장 많이 뽑힌 칩을 모으니 구간이 깨끗하게 나뉘었습니다.

```text
2~6 짝수 → 물가 칩 w/2−1      8~29 → field 칩 w−7
30~174 짝수 → 물가 칩 w/2−12  175~296 → field 칩 w−153
298~304 → 바다                305~ → field 칩 w−161
```

field.tex 칩 번호가 물가·바다 구간을 건너뛰며 이어지는 꼴입니다. 바다는 `pattern24` 를 64×64 로 보고 그렸더니 가로줄 무늬가 생겼습니다. 다시 보니 프레임마다 256×16 이고 왼쪽 64×16 이 바다 칩 넷이었습니다(298·300·302·304). 이 표로 그린 지도를 80개 화면과 다시 견주었습니다. 바다가 아닌 칸 4,577개는 상관 중앙값 0.941(87.4% 가 0.8 이상)이었습니다. 바다 칸은 24프레임 중 가장 맞는 것과 견주어 중앙값 0.896 이었습니다.

![FIELD/bin/worldmap.bin 을 위 표로 그린 필드 일부(가로세로 32칸)](../images/nds-gfx-world.webp)

칸 값 1052(`0x41C`)처럼 비트 10 이상이 켜진 칸이 있습니다. NDS BG 화면 항목처럼 비트 10·11 이 뒤집기일 것으로 보고 네 가지로 대 봤습니다. 그런데 모두 상관이 0 근처라 뒤집기가 아니었습니다. 관찰한 칸의 0.5% 이고, 마을·성 기호 자리로 보여 남겼습니다.

## 3. 전투 몬스터: 뒤집기 플래그와 프레임 길이

부팅 메뉴 상태에서 장면 `0x11`(전투 테스트)을 요청하고 A 를 누르자 はさみくわがた 둘이 나왔습니다. 이름 표의 몬스터 4번이고, 그림도 `m004` 였습니다. 조립한 프레임을 화면에 대 보니 일치율이 0.56 에 그쳤습니다. 8배로 키워 보니 게임 쪽은 좌우 대칭인데 우리 조립은 오른쪽 팔다리가 뒤집히지 않았습니다. 기록의 셀 번호 위 4비트를 보니 오른쪽 짝 부품에만 `0x1000` 이 켜져 있었습니다.

```text
(39, 0, -8) (40, 0, -9) | (41, 1, 6) (42, 1, 8) (43, 1, 9)    (셀, 플래그, x)
```

이것을 좌우 뒤집기로 쓰자 0.71, 세로 1픽셀을 늘리자 0.85 가 됐습니다. 남은 차이는 부품마다 3D 사각형으로 그릴 때의 반올림으로 보입니다.

![m004 대기 동작 첫 프레임. 셀 플래그를 무시한 조립(왼쪽)과 0x1000 을 좌우 뒤집기로 쓴 조립(오른쪽)](../images/nds-gfx-flip.webp)

프레임 길이는 화면을 1프레임마다 240장 찍어 쟀습니다. 몬스터 영역은 홀수 프레임에서만 바뀌었습니다(3D 를 30fps 로 그림). 대기 동작은 17프레임이고, 같은 모양이 둘·셋씩 이어 붙은 묶음 6개로 되어 있습니다. 12프레임 뒤에 화면이 맞는 묶음이 「2~4번 → 8~10번」 이었습니다. 그래서 DSSA 한 프레임이 게임 2프레임(1/30초)입니다. 지난번 WebP 는 프레임을 하나 걸러 33ms 로 둬서 두 배 빨랐습니다.

싸우기를 골라 한 턴을 찍고, 화면을 칸마다의 프레임과 맞췄습니다. 몬스터가 공격하는 동안(「はさみくわがたの こうげき!」)만 칸 1 이 가장 잘 맞았고, 나머지는 칸 0 이었습니다.

## 4. 필드 인물 확인

필드 화면의 주인공을 인물 팩 187개의 모든 프레임과 견줬습니다. `h101` 의 다섯째 장(8장짜리 팩)이 가장 잘 맞았는데 79% 였습니다. 확대해 보니 32픽셀로 잘라 옆 프레임이 섞인 것이었습니다. 불투명 열을 세니 프레임은 **24×32** 였습니다. 24픽셀로 자르자 471픽셀 중 469픽셀이 채널당 8 이내로 같았습니다.

## 5. 짝 없던 몬스터

`m053`·`m121` 은 아틀라스 마스크가 99% 같은 짝이 없어 부품만 있었습니다. 일치율 순위를 보니 `m053` → `m027` 0.937(2위 0.804), `m121` → `m097` 0.963(2위 0.623)으로 1위가 뚜렷했습니다. 부품 몇 개를 다시 그린 변종입니다. 조립하면 나무 그루터기와 박쥐 악마가 자연스럽게 나옵니다. 그래서 「0.9 이상, 2위와 0.1 차이」 로 기준을 바꿨습니다.

## 6. LOCN 과 FMAP 나머지

`LOCN` 은 `+0x34` 의 위치부터 96바이트 레코드가 머리의 첫 수만큼 있었습니다(`cbout` 241개 = `0x5AAC − 0x4C` / 96). 레코드 안 `+0x40` 이 (0, 1, 0)·(0, 0.86, −0.51) 같은 단위 벡터였습니다. 전수로 보니 맵 197개, 면 45,225개 중 45,222개가 단위 법선이었습니다. 45,192개는 `+0x10`·`+0x1C`·`+0x28` 의 세 점이 그 평면 위에 있었습니다. 판정 면 목록입니다.

`FMAP` 배치 18,182개는 `+0x2C` 이후 필드를 모델 이름과 맞대어 봤습니다. `+0x44` 는 모델 번호와 전부 같았습니다. `+0x2C` 가 0 이 아닌 것은 보물상자(`tbox`)·문·침대·항아리·통·서랍·책장 같은 조사 대상뿐이었습니다.

## 7. 3D 관절 애니메이션(BCA0)

`CHR/*.nsbca` 의 `JNT0` 은 객체마다 플래그와 트랙이었습니다. 회전은 피벗 표(6바이트)와 기저 표(10바이트)를 색인합니다. 기저의 m12 를 c4·c0·c1·c2·c3 아래 3비트를 이은 15비트로 읽자 행렬 절반이 직교가 아니었습니다. 직교 조건에서 필요한 m12 를 거꾸로 계산해 원래 값과 맞대 봤습니다.

```text
need −174   raw 0x1F52(8018)   → 8018 − 8192 = −174
need 127    raw 0x7E(126)
```

아래 13비트만 부호 있는 값이었습니다. 이렇게 고치자 `pisaro_0` 997개 중 995개, `msdr_opening_0`·`estrk_3` 은 3,000개 전부가 직교 행렬이 됐습니다. 그다음 피사로·에스타크·마스터드래곤을 앞에서 본 직교 투영으로 움직여 봤습니다. 처음에는 4개 파일이 자료 끝을 넘어 읽었습니다. 트랙 정보의 비트 29 가 fx16 표본을 뜻했는데 비트 28 만 봤기 때문입니다(346프레임 트랙의 간격 692 = 346×2).

![피사로 3D 모델을 BCA0 동작 pisaro_1 로 움직인 프레임 6장(앞에서 본 직교)](../images/nds-gfx-bca.webp)

3D 효과 17개도 같은 방식으로 읽히지만, 그리면 비어 나옵니다. 반투명 면과 재질 애니메이션(BTA0·BMA0)에 기대는 것으로 보입니다.

## 8. 전투 위 화면 배경

`ubtl*.bgc` 의 크기(8bpp 16KB)는 위 화면 엔진 B 의 BG3(8bpp, 512×256, 문자 `0x4000`)에 꼭 맞았습니다. 하지만 테스트 전투와 1장 필드의 실제 조우, 두 평원 낮 전투에서 뱅크 H 는 비어 있었습니다. VRAM 전체와 메인 RAM 에서도 ubtl 타일의 64바이트 줄은 하나도 나오지 않았습니다. 어느 전투에서 쓰는지는 남았습니다.

## 틀렸던 것들

- **인물 프레임은 32×32**: 24×32 입니다. 32 로 자르면 옆 프레임이 섞입니다.
- **DSSA 셀 번호 위 비트는 그리기와 상관없다**: `0x1000` 이 좌우 뒤집기입니다.
- **몬스터 WebP 는 한 프레임 걸러 33ms**: 게임은 모든 프레임을 1/30초씩 보입니다.
- **`largemap.bin` 은 그림이 아니다**: 32×32 타일 순서의 1024×1024 그림입니다.
- **패턴 팩은 64×64 `A3I5`**: `pattern8` 은 256 폭 8bpp 물가 칩, `pattern24` 만 64×64 8bpp 입니다.
- **기저 회전의 m12 는 15비트**: 아래 13비트입니다.
- **BCA0 트랙의 폭 비트는 28**: 데이터에서 켜지는 것은 29 입니다.
- **필드 칸은 field.tex 의 2×2 8×8 타일**: 칸 하나가 16×16 칩이고, 값 구간마다 field.tex·`pattern8`·`pattern24` 칩을 고릅니다.
- **`pattern24` 는 64×64**: 256×16 의 왼쪽 64×16 입니다.
- **칸 값 비트 10·11 은 뒤집기**: 뒤집어도 맞지 않습니다.
- **field.tex 칩 대응은 따로 있는 표**: 값 구간마다 오프셋이 다를 뿐 공식으로 풀립니다.

## 남은 것

- 필드 칸의 비트 10 이상, `WSYN`·`WCHA`·`WCMA`, `gotmap`·`yamimap`.
- `ubtl*` 을 쓰는 전투와 타일 배치.
- DSSA 플래그 `0x2000`·`0x4000`, 몬스터 동작 칸 2~13, 남은 1픽셀 차이.
- `LOCN` 머리의 나머지 수와 뒤쪽 덩어리, `FMAP` 필드를 게임에서 바꿔 확인하기.
- BTA0·BMA0 트랙과 3D 효과 재생.
