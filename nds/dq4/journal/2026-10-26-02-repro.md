# 2026-10-26-02: 에셋을 롬에서 처음부터 다시 만들기

비공개 에셋 저장소의 `nds/dq4/`(그래픽·맵 화면·소리)를 이 저장소와 두 롬만으로 다시 만들 수 있게 했습니다. 맵 화면 모음을 만드는 명령 `ndswarp.py screens` 와 전체 진입점 `ndsassets.sh` 를 더했습니다. 깨끗한 폴더에 처음부터 다시 만들어 에셋 저장소와 파일마다 맞췄습니다. 결과는 [README 「에셋 다시 만들기」](../README.md#에셋-다시-만들기)와 [debug.md](../docs/debug.md) 에 있습니다.

## 1. 무엇이 다시 만들어지지 않았나

에셋의 `SOURCE.txt` 를 보면 그래픽은 `ndsgfx.py export`·`gallery`, 소리는 `ndssound.py` 의 다섯 명령으로 만들어졌습니다. 맵 화면 `screens/`(544장)는 `README.txt` 에 「각 맵: `ndswarp.enter(p, 이름, settle=240)` 뒤 화면 저장」이라고만 적혀 있었습니다. 그 반복은 도구에 없었습니다. 세 가지를 한 번에 돌리는 진입점도 없었고, 깨끗한 상태에서 다시 돌려 맞춰 본 적도 없었습니다.

## 2. `ndswarp.py screens`

`chapters` 와 같은 길로 부팅 디버그 메뉴 → 프리셋 331(6장, 피사로가 동료) 상태를 롬에서 만듭니다. 그다음 `_list.txt` 순서로 맵마다 그 상태를 다시 읽어 `enter(p, 이름, settle=240)` 하고 `NNN-<맵>.png` 를 씁니다. 실패한 맵은 목록으로 내고, 찍은 방법은 `README.txt` 로 함께 씁니다.

`fk01` 은 6장 상태에서 스크립트가 곧 `ckout` 으로 넘깁니다([2026-10-25-09 일지](2026-10-25-09-debug3.md)). 그래서 출발 상태에서 맵에 머물지 못하면 부팅 상태에서 한 번 더 들어가게 했습니다. 이제 `fk01` 도 구름 위 天空城 화면이 나오고, 실패한 맵은 없습니다.

```
506	fk01	ok	boot
부팅 상태(전원 → 디버그 메뉴 Town Part)에서 다시 들어간 맵: fk01
어느 상태에서도 그 맵에 머물지 못한 맵: 없음
```

코어는 세이브 파일(`dq4ds.dsv`)을 시스템 폴더에 씁니다. 그 폴더가 출력 폴더였을 때는 에셋으로 갈 폴더에 `.dsv` 가 섞였습니다. 그래서 세이브스테이트와 함께 임시 폴더로 옮겼습니다.

## 3. 맵 화면이 실행마다 달랐다

처음 만든 544장을 에셋과 견주니 431장이 바이트까지 같고 113장이 달랐습니다. 다른 곳은 맵 인물의 자리, 폭포·용암 애니메이션, 화면이 스스로 움직이는 맵(`za3f3`)의 카메라 위치였습니다. 같은 명령을 한 번 더 돌린 결과와 견줘도 460장만 같았습니다. 도구가 결정적이지 않았던 것입니다.

한 프로세스 안에서는 같은 상태에서 같은 맵에 두 번 들어가면(사이에 2초 쉼) 화면 해시가 같았습니다. 프로세스를 새로 띄우면 달랐습니다. 그러니 차이는 부팅할 때 들어옵니다. desmume 의 `rtcGetTime`(`rtc.cpp`)은 `movieMode` 가 0 이면 호스트 시각을 돌려주고, 0 이 아니면 `currMovieData.rtcStart`(기본 2009-01-01) + 프레임 수를 돌려줍니다. 게임이 부팅 때 읽은 시계가 난수에 들어간다고 보고, 코어가 내보내는 `movieMode` 를 ctypes 로 3(재생 끝)으로 두었습니다.

처음에는 늘 3 으로 두었더니 세이브스테이트를 읽지 못했습니다(`cannot load`). 0 이 아니면 상태에 영상 기록(`MOVI`)이 붙고, 읽을 때 영상 GUID 를 견주다 거부합니다. 그래서 프레임을 돌리는 동안만 3 으로 두고 상태를 쓰고 읽을 때는 0 으로 돌렸습니다.

| | 같은 맵 세 개의 해시, 프로세스 1 | 프로세스 2 |
| --- | --- | --- |
| 호스트 시계 | `ddf7bb5d 788919a2 95dcec6d` | `f5c78f9f 6ca2937b 95dcec6d` |
| 시계 고정 | `84866e0d 788919a2 253b4bbd` | `84866e0d 788919a2 253b4bbd` |

고친 `screens` 를 따로 세 번 돌렸습니다(둘은 동시에, 하나는 `ndsassets.sh` 안에서). 544장이 셋 모두 바이트까지 같았습니다.

## 4. 전체 진입점 `ndsassets.sh`

`nds/dq4/tools/ndsassets.sh OUT [ASSETS]` 가 롬 SHA-1 확인 → 풀기 → 그래픽 → 맵 화면 → 소리 → 첫 페이지 → 동기화를 합니다. 소리 단계는 `export`·`scorecheck`·`scenes` 4조각(동시에)·`summary`·`gallery` 입니다. 첫 페이지(`ndsgfx.py gallery`)는 옆 폴더의 `README.txt`·`gallery/index.html` 링크를 넣으므로 마지막에 돌립니다. 동기화는 만든 단계의 폴더만 `rsync --delete` 로 맞추고, 손으로 쓴 `README.md` 는 남깁니다. 폴더마다 커밋 해시·롬 SHA-1·명령을 적은 `SOURCE.txt` 를 씁니다.

처음 돌렸을 때 소리 단계의 `scenes` 넷이 모두 죽었는데도 스크립트는 다음으로 넘어갔습니다. 원인은 둘이었습니다.

- 백그라운드로 띄운 넷을 `wait` 하나로 기다리면 실패가 전해지지 않습니다. 하나씩 `wait PID` 하도록 바꿨습니다.
- `scenes` 는 결과 json 옆에 임시 폴더를 만들고 그 안의 상태 파일을 읽습니다. 경로가 상대 경로면 `work/state/dq4ds-work/nds/...` 처럼 엉뚱한 곳을 찾습니다. 그래서 절대 경로로 넘겼습니다.

`scenes` 는 장 시작 세이브스테이트 `work/state/dq4ds-ch*.state` 를 씁니다. 그래서 그 파일이 없을 때만 `ndswarp.py chapters work/state` 로 먼저 만듭니다.

## 5. 에셋과 맞춘 결과

깨끗한 폴더 `OUT` 에 전부 만들고(약 35분), 에셋 저장소(커밋 `0761722` 이후의 `nds/dq4/`)와 파일 목록·바이트를 견줬습니다. 바이트가 다른 그림은 프레임마다 RGBA 로 풀어 픽셀을 셌습니다.

| 폴더 | 파일 | 바이트까지 같음 | 다른 것 |
| --- | --- | --- | --- |
| 그래픽 | 4,289 | 4,289 | 없음 |
| `screens/` | 544 | 431 | 113(`fk01` 은 일부러 바꿈, 112장은 인물·애니메이션) |

- 그래픽은 WebP(무손실, `method=4`)와 PNG(`optimize`) 모두 실행마다 같아서 고칠 것이 없었습니다. 파일 목록도 같았습니다(`SOURCE.txt` 만 새로 씀).
- 맵 화면의 다른 112장은 위 화면만 다른 것 27장, 아래 화면만 78장, 둘 다 7장입니다. 다른 픽셀은 전체 53,477,376개 중 316,903개(0.59%)이고 78장은 한 장의 1% 미만입니다. 에셋은 시계를 고치기 전에 찍어서 이 112장은 다시 만들 수 없습니다. 그래서 이번 결과로 바꿨습니다. 내용은 같고, `fk01` 은 나아졌으며, 이제 다시 돌리면 바이트까지 같습니다.
- 소리는 `scorecheck` 가 곡 50개(음표 98,679)·효과음 634개(음표 3,460) 모두 일치했습니다. 다른 한 줄은 6장 필드 곡(20)의 장면 설명입니다. 에셋은 「선두 7명 모두(… ミネア·マーニャ·ピサロ)」이고, 지금 `scenes` 는 선두 1·3·4·7·8·25 의 6명만 재서 「선두 6명」이 됩니다. 에셋을 만든 실행이 マーニャ(9)도 쟀던 것으로 보입니다. 소리 폴더는 그대로 두었습니다.
