# 2026-10-26-05: 행동 표, 상태 번호, 내성 값 1·2, 동료 대화의 세 값

PARAM 형식과 디버그 문서의 「남은 것」을 다시 잡았습니다. 앞 회차는 화면과 RAM 통계로 밀어붙였고, 이번에는 함수를 떼어 내어 돌리는 길을 썼습니다. 전투나 맵 장면의 RAM 4MB 를 덤프하고, 그 덤프를 unicorn 에 그대로 올려 함수 하나만 인자를 바꿔 가며 불렀습니다. 그렇게 나온 규칙을 마지막에 에뮬레이터 화면으로 맞췄습니다. 결과는 [param-format.md](../docs/param-format.md)(행동 표, 내성, 얻는 물건, 동료 대화, 가게)와 [debug.md](../docs/debug.md#상태-이상-번호)에 있습니다.

## 1. 「주문 효과 표」는 행동 표였다

앞 일지의 「`0x020A8AD0` 부근 `0x48` 바이트 레코드」는 주소를 레코드 경계로 잡지 않은 것이었습니다. 표 묶음 객체 `0x020C51D8` 의 `+0x38` 이 `0x020A8294` 를 가리키고, 여기서부터 `0x48` 바이트씩 끊으면 레코드 n 의 `+24` 가 n 입니다. 주문 n 의 이름은 `b1003000` 의 n−1 번이라, 레코드 1 이 メラ, 30 이 マホトーン, 31 이 マヌーサ, 32 가 メダパニ 입니다. 앞 판의 「マホトーン `0x1D`」는 이름 번호(n−1)를 적은 것이었습니다.

칸 뜻은 이 표를 읽는 작은 함수들로 풀었습니다. `0x020C51D8 +0x38` 을 읽고 `0x48` 을 곱하는 함수를 모으니 칸마다 하나씩 있었습니다.

```
0x020151F4  +37 → 23갈래 표 → 내성 칸(メラ 3, ギラ 2, イオ 1, …, 불 숨결 0x18, 찬 숨결 0x19 …)
0x020152D0  +43 bit4-2       → 등급
0x020154DC  +38              → 효과(4B·9B·9C 는 0x27)
0x02015388  +20, 0x0201539C +34, 0x02015374 +3A
```

몬스터 표 `+12` 의 행동 번호도 같은 번호였습니다. スライム 의 `71 260` 은 행동 71 「%a00010の こうげき！」와 260 「しかし まわりこまれてしまった！」(にげる)입니다. 아이템 표 `+0A` 도 같은 번호라, まふうじのつえ 는 336 「呪文を ふうじこめられた！」, ほほえみのつえ 는 341 「にっこり ほほえんだ。」입니다. `ndsparam.py actions` 를 더했습니다.

## 2. 상태 번호를 함수로 모으기

전투 RAM 에서 상태 칸 함수 `0x0201E888` 을 부르는 곳은 22곳뿐이었고, 대부분 상수(잠·독·마비)를 넘겼습니다. 주문 쪽은 `0x0201E494`(상태 표, 행동 번호, 인자)가 맡았습니다. 효과를 읽어 갈래 표로 칸을 고르고 `0x02035C50`(칸, 값, 인자)을 부릅니다.

이 함수를 unicorn 으로 떼어 냈습니다. 상태 표 자리에 빈 메모리를 주고, `0x02035C50`·`0x02035C98`(켜기·지우기)에 갈고리를 걸어 어느 칸에 무엇을 쓰는지만 기록했습니다. 행동 1~599 를 모두 넣었습니다.

```
28 ラリホー   set slot 0x0A        30 マホトーン set slot 0x12
31 マヌーサ   set slot 0x0B        32 メダパニ   set slot 0x14
266 おたけび  set slot 0x15        267 まぶしいひかり set slot 0x0B (값 0x1C)
554 (チキーラ 羽) set slot 0x1A    75 だいぼうぎょ set slot 0x1B (값 0x27)
106 いてつくはどう clr 0x0F 0x0E 0x18 0x0D 0x0C 0x10 0x08 0x12 0x0B 0x13 0x19
```

`0x0201E494` 가 부르는 `0x020154DC` 에도 갈고리를 걸어 효과 값을 0~`0x29` 로 바꿔 넣으니, 효과 8~`0x16`·`0x18`~`0x1A` 는 효과 값 그대로가 상태 번호였고 `0x29` 만 상태 `0x1E` 칸을 켰습니다. 효과가 `0x29` 인 행동은 표에 없었습니다. 상태 `0x1E` 는 코드가 행동 467 「時間が とまった！」일 때 직접 켰습니다(`0x0202E7AC`). 같은 자리에서 행동 466 은 잠, 468 「おそろしい うめきごえ」는 `0x15`, 97 「ふしぎなきり」는 `0x1F`, 531 「ちからを ためている」는 `0x11` 을 켰습니다. 지금 행동 번호는 `[0x020EC4A4] + 0x2C` 에서 읽습니다.

## 3. 몬스터에게 그 행동을 시키기

함수 결과를 화면으로 맞추려면 그 행동을 실제로 맞아야 합니다. 주문을 가진 인물로 메뉴를 고르는 대신, 몬스터 쪽 행동을 바꿨습니다. 4장 시작 상태(マーニャ 혼자)를 불러 RAM 의 몬스터 표에서 スライム(`0x0209DF78`)의 MP 를 99 로, 행동 여섯 칸을 모두 N 으로 쓴 뒤 저장하고, 그 상태에서 `ndswarp.py battle` 로 スライム 1마리를 불렀습니다. 첫 턴에 スライム 이 그 행동을 썼습니다. 200프레임 뒤 マーニャ 의 상태 표를 읽었습니다.

マーニャ 의 인물 레코드는 처음에 `0x020C5B74 + 9 × 0x50C` 를 잘못 셈해 엉뚱한 곳을 읽었습니다. メダパニ 전투의 덤프에서 `01 00 00 00 14 00 00 00` 을 찾아 `0x020C8B58` 을 얻었고, 거기서 칸 `0x14` 를 빼 `0x020C8A68`(레코드 9번 `0x020C88E0` + `0x188`)을 썼습니다.

```
--act 32  (メダパニ)  slot 0x14: 01 00 00 00 14 00 00 00 00 07 02 00   이름 칸 「こんらん」
--act 30  (マホトーン) slot 0x12: 01 00 00 00 12 00 00 00 00 07 04 00   이름 칸 「マホトン」
--act 31  (マヌーサ)  slot 0x0B: 01 00 00 00 0b 00 00 00 00 05 03 00   이름 칸 「マヌーサ」
--act 266 (おたけび)  slot 0x15: 01 00 00 00 15 00 00 00 00 01 05 00   「おどろき すくみあがっている！」
--act 467             slot 0x1E: 01 00 00 00 29 00 00 00 01 04 05 00   マーニャ·スライム 양쪽
--act 554             slot 0x1A(61프레임), 턴이 끝나면 꺼짐
```

이 순서를 `ndswarp.py battle … --act N` 으로 넣었습니다. 기존 인자는 그대로입니다.

## 4. 내성 값 1·2 는 확률이었다

행동 표의 내성 갈래를 칸 번호로 바꾸는 `0x020151F4` 를 부르는 곳을 따라가니, `0x020144CC`(내성 묶음, 칸, 등급)과 쌍둥이 `0x0201494C` 가 나왔습니다. 내성 묶음은 전투 몬스터 객체 `+0x168` 이고, `+4` 부터 28칸을 1바이트씩 풀어 둔 것입니다. 4장 전투 덤프에서 スライム 의 내성 비트를 풀어 만든 28바이트를 찾아 `0x02162828` 을 얻었습니다.

두 함수가 부르는 `0x0201430C`·`0x020147D4` 를 unicorn 에 올리고, 난수 함수 `0x0207EAA8` 에 갈고리를 걸어 0~999 를 하나씩 넣었습니다. 등급 0 은 내성 0·1·2·3 에서 1000·850·400·0 이었습니다. 등급 0~2·7 은 이 값보다 난수가 작아야 1000(들음), 아니면 0 입니다.

앞 판은 メラ 의 피해가 내성 1·2 에서도 12 라 「차이 없음」이라고 적었습니다. 확률이라면 맞은 경우의 피해는 그대로이고 「きかなかった」가 섞여야 합니다. 4장 マーニャ 의 전투에서 メラ 를 고르기 직전에 내성 묶음의 メラ 칸(`0x0216282E`)을 바꾸고, 난수 상태 `0x02116C20` 을 매번 다르게 써서 40번씩 쐈습니다.

```
내성 0  : きかなかった 0/40
내성 1  : きかなかった 6/40     (기대 15%)
내성 2  : きかなかった 23/40   (기대 60%)
맞았을 때 피해 8~14(행동 표 +2C~+2E 범위)
```

## 5. 동료 대화의 세 값

맵 장면 RAM 을 따로 덤프해 오버레이 0 이 실린 상태로 읽었습니다.

- 직전 대화 값을 쓰는 `0x021392EE` 는 함수 `0x02139240` 안이고, 이 함수는 스크립트 명령 `0x4A`(말을 걸면)의 처리 칸 `0x02020440` 이 부릅니다. 값은 지금 오브젝트 번호로 표 `0x020EA5DC` 에서 읽은 것입니다. 2장 맵에서 표는 `0 1 2 3 4` 였습니다.
- 최근 이벤트 값은 ARM9 대사 명령이 메시지 번호를 그대로 넣습니다. `tab1b` 의 `03 1101` 이 레코드의 1101 과 같았습니다.
- `0x020B91C8` 은 설정 함수 `0x0200BEB0` 을 부르는 곳이 모두 맵 이동이었습니다. 스크립트 명령 `0x20`(분기 `0x02020A88` → `0x020242DC` → `0x02027514`)은 인자 다섯째 낱말(입구)을 씁니다. 6장 상태에서 맵 이름을 `cbout` 으로 쓰고 이 값만 바꿔 맵을 다시 실으니, `0x1001` 은 정문 앞, `0x1005` 는 높이 3.25 의 성벽 위에 주인공이 섰습니다. 조건 12 = 4101 인 다섯 줄은 「正門を通らず このような所から」 같은 벽 구멍 대사입니다.

## 6. 얻는 물건 `2C` 와 `+17`

`2C` 레코드의 물건 번호를 맵 팩과 스크립트에서 찾으니 스크립트에만 있었습니다. 제어 오브젝트의 `initialize` 에 `02B 번호 x y z` 가 있고, 모습 `0xD7` 오브젝트가 같은 자리에 섭니다. 35줄 중 31줄이 이 꼴이었습니다. イムル 우물(maido)에서 (1.30, 0.90)에 서서 「しらべる」를 고르자 50G 가 75G 가 되었습니다.

`0x020CE358` 을 켜는 `0x0201CEFC` 는 오버레이 0 `0x0211F338` 이 부르고, 그 앞에서 레코드 `+17` bit0 을 봅니다. 레코드 수라고 적었던 `+16` 은 u8 이었고(2,722줄 모두 레코드 수와 같음), `+17` 이 따로 있었습니다. 이 64비트 배열은 맵을 옮기면 지워졌습니다.

## 7. 가게 first 18

`0x0201D2BC` 는 `0x020CE214` 가 1 이면 맵 이름 대신 키 `en` 을 만듭니다. 키 함수 `0x0200CCCC` 는 두 글자를 `c0 × 100 + c1` 로 바꿔 비교하고, `en` = 10210 이 18 입니다. unicorn 으로 `0x0201D2BC` 를 불러 `0x020CE214` 를 1 로 두니 맵 이름과 상관없이 오프셋 `0x3A8`(= 18 × `0x34`)이 나왔습니다. 품목이 FC 의 가짜 장소 그룹 `FE` 와 같습니다. 1 을 쓰는 코드는 찾지 못했습니다.

## 틀렸던 것들

- 「주문 효과 표는 `0x020A8AD0` 부근, マホトーン `0x1D`」: 표 시작은 `0x020A8294` 이고 マホトーン 은 레코드 30 입니다.
- 「몬스터 내성 값 1·2 는 피해 주문에서 차이 없음」: 피해는 그대로이고, 듣지 않을 확률이 15%·60% 가 됩니다.
- 「상태 `0x14` 는 받는 피해 증가(ルカニ 꼴)」: `0x14` 는 혼란입니다. 직접 켠 화면에서 피해가 1 → 5 로 보인 것은 혼란한 ライアン 이 자기를 친 것으로 봅니다. ルカニ 는 `0x18` 입니다.
- 「얻는 물건 `+16` 은 u16 레코드 수」: u8 이고 `+17` 이 따로 있습니다.
