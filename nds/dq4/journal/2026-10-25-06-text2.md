# 2026-10-25-06: 메시지 번호, 대사 표지, 실행 파일 문자열, 이벤트 스크립트

대사 형식의 남은 칸을 메웠습니다. MPT0 머리 `+08` 이 첫 메시지 번호라는 것을 찾아 동료 대화 표·이벤트 스크립트가 부르는 번호가 모두 맞게 됐고, `@cN@`·`%a` 표지, 대응표의 `98A8`, 실행 파일의 Shift_JIS 문자열, `SCRIPT/*.bin` 의 블록 구조, `TRANS/m278_03.dssa` 1바이트 차이를 정리했습니다. 결과는 [text-format.md](../docs/text-format.md) 와 [rom-map.md](../docs/rom-map.md) 에 있습니다.

## 1. MPT0 머리 `+08`·`+0C`

952개 파일의 `+08`·`+0C` 를 파일 이름 × 1000 을 뺀 값과 색인 번호 끝과 나란히 놓았습니다.

```
b0000000.mpt  +08-base 2    +0C-base 999   색인 [0, 1, 2, 8 …] … 997
b0001000.mpt  +08-base 1    +0C-base 534   색인 [0, 3, 4 …] … 533
```

952개 모두 첫 색인 번호가 0 이고, `+0C` − `+08` 이 마지막 색인 번호와 같았습니다. 그렇다면 `+08` 은 색인 0번의 메시지 번호입니다. 차이(`+08` − 파일 이름 × 1000)는 0~7 이 대부분이지만 38·102·503 인 파일도 있습니다(`b0506`·`b0521`·`b0538` 등 동료 대화 파일이 102).

부르는 쪽으로 확인했습니다. 동료 대화 표의 메시지 번호 7,209개는 「파일 이름 × 1000 + 색인」으로 읽으면 3,831개만 대사에 있었는데, `+08` 기준으로 읽으니 7,209개 모두 있었습니다. 3절의 이벤트 스크립트 메시지 명령도 1,493개에서 2,931개(2,932개 중)로 늘었습니다. `ndstext.py` 의 `read`·`messages` 를 이 규칙으로 고쳤습니다.

## 2. 한글판 화면과 대응표

desmume libretro 코어로 한글판 롬(`rom/dq4ds-kr.nds`)을 켜고 `ndswarp.py preset … 1 --rom rom/dq4ds-kr.nds --fs work/nds/kr` 로 1장 시작 상태를 만들었습니다. 일본판 세이브스테이트에 한글판 롬을 물리면 폰트와 대사가 이미 RAM 에 있어 일본어가 나오므로, 한글판 롬으로 전원부터 다시 만들어야 했습니다.

A 를 눌러 가며 찍은 대사 창 13장(지문 3, 대신 1, 왕 7, 여자 2)이 `ndstext.py dump work/nds/kr/…/b0000000.mpt --kr` 의 메시지 2~24 와 글자 하나까지 같았습니다.

```
2   @a@b이것은 바트랜드라는 작은 나라의\n왕궁전사 이야기。
15  @a0001  왕@b왕「요즘 아이들이\n	사라진다는 소문은\n	그대들도 들었겠지。
24  @a0003  여자@b＊「그 애는 아직 살아있어요。\n	아아 그래도 서두르지 않으면 …
```

메뉴를 열어 「도구 일람」도 보았습니다. 이것은 `overlay_0016` 의 `@どうぐいちらん` 자리를 대응표로 읽은 값과 같았습니다. 실행 파일 문자열도 대사와 같은 폰트·같은 대응으로 그려집니다.

## 3. `98A8` 은 「훔」

`98A8` 을 쓰는 대사 47곳을 대응표로 읽으면 모두 「훔쳐보는」·「훔친」·「훔치겠」처럼 「훔치다」 꼴이었습니다. 글리프를 이웃 글자와 나란히 찍어 보니 아래쪽이 「흠」(`9A13`)과 같은 네모였습니다.

```
98A8(zen12)    9A13 흠
.....#......   .....#......
.########...   .########...
...#..#.....   ...#..#.....
..#....#....   ..#....#....
...####.....   ...####.....
............   ............
##########..   ##########..
.....#......   ............
.########...   .########...
.#......#...   .#......#...
.########...   .########...
```

이 폰트의 ㅁ 받침은 위아래 줄과 양옆이 있는 네모입니다. 「훑」이면 ㄹ·ㅌ 두 받침이 보여야 합니다. 대응표를 「훔」으로 고쳤고, KS 순서(훌 < 훔 < 훗)도 그대로 지켜져 `ndskr.py check` 가 오류 0 입니다.

## 4. `@cN@`

`@a<인물 번호>` 별로 문장 끝 숫자를 모았습니다. 785명 중 773명이 한 값만 썼고, 값은 인물의 종류로 갈렸습니다. 0 은 화자 없는 지문, 1 은 アリーナ·マーニャ·ミネア·女·姫 같은 여자와 아이, 2 는 トルネコ·クリフト·王·兵士 같은 보통 남자, 3 은 ライアン·あらくれ·戦士·マスタードラゴン 처럼 굵은 목소리입니다. 영어 대사는 전부 `@c0@` 이었습니다.

그래서 목소리(글자 효과음) 종류라고 생각하고 에뮬레이터에서 바꿔 봤습니다. 왕의 대사 「모두들 편하게 듣게나」가 RAM `0x023CD504` 에 대사 파일 그대로 실려 있어, A 를 누르기 직전에 `@c2@` 의 숫자만 바꿨습니다. 같은 자리 첫 글자를 바꾸면 화면에 바로 반영되는 것도 확인했습니다.

```
@c2@  화면 해시 fc26ad c5a4ba 9e828e … 54631b  소리 893,408샘플
@c0@  화면 해시 fc26ad c5a4ba 9e828e … 54631b  소리 첫 차이 없음
@c1@  (같음)
@c3@  (같음)
@c9@  (같음)
AAAA  화면 해시 fc26ad c5a4ba 25e7f5 …        소리 211,128번째 샘플부터 다름
@b2@  화면 해시 fc26ad c5a4ba 3c9316 …        소리 211,134번째 샘플부터 다름
```

표지는 읽지만 숫자는 이 장면에서 아무것도 바꾸지 않았습니다. 숫자가 인물 종류를 나타낸다는 것까지만 적고, 무엇에 쓰는지는 남겼습니다.

## 5. `%a` 변수

일본어 대사의 `%a` 는 98가지입니다. 같은 번호를 쓰는 문장을 모두 늘어놓고 들어갈 말을 읽었습니다(`%a00090` 주인공 이름, `%a00130` 나타난 몬스터, `%a00620` 사고파는 값 등). 영어 대사는 같은 자리를 `%a01010` 처럼 앞 두 자리를 바꿔 쓰고, `%A090%Xhero%Z%B090%Xheroine%Z` 로 같은 변수의 성별에 따라 낱말을 고릅니다. 그래서 다섯 자리는 「꼴 2자리 + 변수 3자리」로 보았습니다. 표는 형식 문서에 두었습니다. 값을 채우는 코드는 찾지 않았습니다.

## 6. 실행 파일의 Shift_JIS 문자열

한글판과 다른 `arm9.bin` 자리를 보니 `@マップじょうほう`, `@エド`, `@ふ` 처럼 `@` 로 시작하고 0 으로 끝나며 4바이트 맞춘 자리에서 시작하는 문자열이 줄지어 있었습니다. `arm9.bin` 은 압축되지 않아 파일 오프셋 + `0x02000000` 이 주소입니다. 이 꼴(가나가 들고 4바이트 맞춘 자리, cp932 로 풀림)을 `arm9.bin` 과 오버레이 전부에서 찾고, 각 문자열 주소와 같은 u32 를 모든 모듈에서 찾는 `ndstext.py sjis` 를 만들었습니다.

232개가 나왔고 모두 가리키는 포인터가 있었습니다. 158개는 주소를 늘어놓은 표 안에 있었습니다. 이름 입력 글자판 표 4개(`0BEFE4` 등), 인물 이름 표(`0B2DBC`, 20개)가 큽니다. 팬패치가 바꾼 120개를 대응표로 읽으니 대부분 제대로 된 말이었지만, 「마을 일름을」, 「부시지」(メッセージ), 「발撒크＋」, 「떠난 주민 찾燕」 넷이 어긋났습니다. 「일」·「부」 코드는 대사에서 1,600번 가까이 그 음절로 쓰여 표는 맞습니다. 撒·燕 은 아예 폰트에 없는 코드입니다. 팬패치 쪽 실수로 보입니다.

처음에는 Python 의 `shift_jis` 로 풀어 `ガライ` 자리가 깨졌습니다. 팬패치는 `㌃` 같은 NEC 특수 문자 자리(`0x87xx`)에도 한글을 넣었으므로 cp932 로 풀어야 합니다.

## 7. `SCRIPT/*.bin`

`caf1.bin` 첫머리가 `script` 이름 16바이트, u32 10, `0x70`, `0x50`, 0, 그리고 (오프셋, 크기) 쌍 10개였습니다. 그 안에 `scriptgroup`·`scriptobject`·`initialize`·`execute`·`terminate` 가 같은 꼴로 들어 있었습니다. 처음에는 머리 크기를 「0x20 + N×8」로 잡아 `initialize`(N = 3, 머리 0x40)가 깨졌습니다. 표 크기가 N×8 을 16 의 배수로 올린 값이었습니다. 이 규칙으로 396개가 모두 읽혔습니다.

함수 블록의 칸 3개는 명령마다 1바이트, 명령 시작 오프셋 표, u32 코드입니다. 오프셋 표로 명령을 자르니 명령 번호마다 인자 수가 정해져 있었습니다(4개만 두 가지). 인자가 메시지 번호인 명령을 찾으려고 명령 번호·인자 자리마다 「대사에 있는 번호」 비율을 셌더니, `0x05` 의 첫 인자가 2,932개 중 2,931개로 두드러졌습니다.

```
00005 18E77 1  ; @a0005  衛兵@b＊「王さまは　この上におわします。
```

도구는 [ndsscript.py](../tools/ndsscript.py) 입니다.

## 8. `TRANS/m278_03.dssa` 의 1바이트

바뀐 곳은 파일의 마지막 바이트로, 마지막 프레임 마지막 기록의 순서 칸이었습니다(일본판 `2E`, 한글판 `00`). 그래픽을 고친 흔적이라기에는 너무 작아서 롬 안의 자리를 보았습니다. 한글판 롬은 파일을 번호 순서대로 다시 묶었고, 번호가 가장 큰 이 파일이 롬 맨 끝에 있습니다. 그 끝이 롬 파일 크기(101,176,592바이트)와 같습니다. 롬을 다시 묶고 잘라 내는 과정에서 끝 바이트가 0 이 된 것으로 보입니다.

## 틀렸던 것들

- 메시지 번호를 「파일 이름 × 1000 + 색인 번호」로 읽었습니다. 952개 중 922개 파일에서 1~503 씩 어긋났고, 동료 대화 표의 절반이 「없는 번호」로 보였던 까닭입니다. 동료 대화 표 `+1A` 가 2 이상이면 번호가 없다는 관찰도 이 때문이었습니다.
- `98A8` 을 글리프만 보고 「훑」으로 읽었습니다. 이 폰트의 ㅁ 받침 모양을 몰랐습니다.
- `@cN@` 을 목소리 효과음 종류로 보았지만, 바꿔도 소리 샘플이 같았습니다.

## 남은 것

- `@cN@` 숫자가 게임에서 바꾸는 것(보통 인물 대화, 대화 기록 화면).
- `%a` 변수 번호 → 값 표(코드), 영어 꼴 번호 `01`~`05`.
- 이벤트 스크립트의 `0x05` 밖 명령의 뜻.
- 가나 없는 한자만의 실행 파일 문자열 목록, 폰트에 없는 코드(撒·燕)가 화면에 나오는 모양.
- 이름 표 「번호」 열(색인 번호)과 아이템·몬스터 번호의 관계.
