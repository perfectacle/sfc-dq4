# 2026-10-25-13: 필드 기호·WTEX, ubtl, DSSA 플래그, LOCN, 3D 효과 재생

[2026-10-25-05](2026-10-25-05-graphics2.md) 에서 남긴 그래픽 항목을 이어서 풀었습니다. 결과는 [graphics-format.md](../docs/graphics-format.md) 에 넣었습니다.

- 필드 칸의 위 비트는 기호 자리였고, 기호 그림과 위치는 `worldmap.bin` 의 `SDAT` 덩어리에 있었습니다.
- 칸 값 → 칩 표는 같은 파일의 `WTEX` 였습니다. `WSYN`·`WCHA`·`WCMA` 도 풀었고, gotmap·yamimap 도 그렸습니다.
- `ubtl*` 은 코드가 여는 경로가 없고 전투 넷에서 실리지 않아, 쓰이지 않는 자료로 봤습니다.
- DSSA `0x2000` 은 상하 뒤집기였습니다. `0x4000` 은 평상시 화면에 차이를 만들지 않았습니다.
- 몬스터 동작 칸은 행동 파일 이름과 맞대어 대부분 짝지었습니다.
- LOCN 의 면 경계를 바로잡았지만, RAM 에서 바꿔도 걷기는 그대로였습니다.
- BTA0·BMA0 를 풀어 3D 효과 17개를 재생했습니다.

## 1. 필드 칸의 위 비트는 기호 자리

`worldmap.bin` 에서 비트 10 이상이 켜진 칸 325개를 이웃끼리 묶으니 74곳이었습니다. 2×2·3×3 덩어리이고, 아래 10비트는 거의 풀(209~212)이었습니다. 덩어리마다 3칸 아래에 워프해 화면을 찍었습니다(`ndswarp.py field`, 부팅 메뉴 상태). 그 자리에는 성·마을·동굴·다리·사당·탑·석상·세계수가 서 있었습니다. 74곳 각각에 `FIELD/symbol/symbol.pack` 21장을 대 보니 61곳이 픽셀 일치 0.95 이상이었습니다. 위 비트 번호와 그림은 대개 「그림 = 번호 − 1」 이었지만 예외(10번이 동굴과 마을 둘)가 있었습니다. 그래서 번호만으로는 그림이 정해지지 않았습니다.

`PARAM/param_map_field_symbol.dat` 은 12바이트 레코드 113개였습니다. 첫 레코드가 (10, 2, 151, 0x12E, …)이고 `DEBUG/fieldsymbol.dat` 의 10번이 「バトランド城下町＆城」, 그림 2 가 성이었습니다. 좌표를 실측 자리와 맞대니 필드 픽셀 ≈ 25.6 × 좌표 − (1207, 409) 로 잔차 중앙값이 12.6픽셀이었습니다. 1픽셀이 25.6 = 4096/160 이라, 위 화면 양피지 지도의 아이콘 좌표입니다.

정확한 자리는 `worldmap.bin` 의 덩어리에서 나왔습니다. 머리 `WMAP` 뒤를 (태그, 크기)로 걸어 보니 `WSYN`·`WCHA`·`WMAP`·`WCMA`·`WTEX`·`SDAT` 였습니다. `SDAT` 는 10바이트 레코드였고, 첫 레코드는 (0, 그림 2, 장소 19, 640, 301, 48, 48)이었습니다. 실측 61곳 모두가 「그림 왼쪽 위 = (x − 폭//2 − 1, y − 높이 − 1)」 에 1픽셀 안으로 맞았습니다.

```text
tex 9  32×32 상자  (−17, −33)     tex 2  48×48 상자  (−25, −49)
tex 4  41×32 상자  (−20, −33)     tex 11 24×40 상자  (−13, −41)
```

## 2. WTEX 가 칸 값 → 칩 표

`WTEX` 는 0xB60 바이트였습니다. 6바이트로 나누면 485개로, 지도에 나오는 칸 값의 최댓값과 같았습니다. 값 w 의 레코드는 w − 1 번째였습니다. 레코드의 플래그 8 이면 +2 의 물가 칩, 8|16 이면 바다 칩, 아니면 +4 의 field.tex 칩입니다. 지난번에 화면에서 배운 대응과 400개 값이 같았고, 다른 80개는 지도에 쓰이지 않는 홀수 값이었습니다. 그래서 렌더러를 `WTEX` 로 바꿨습니다.

다시 견주다가 화면 원점을 (128, 96)으로 바꿨더니, 땅 상관이 0.944 에서 0.516 으로 떨어졌습니다. (129, 97)이 맞았고, 기호 위치의 −1 도 이 원점 기준이었습니다.

```text
땅 4,502칸 0.944(0.8 이상 89.5%)   기호 칸 75개 0.921   바다 0.896
```

`WCHA` 의 u16 (0, 18, 8, 50, 37)은 직사각형이었고, 32×29 = 928 이 `WCMA` 의 u16 수와 같았습니다. `WCMA` 를 그 자리에 넣으면 410칸이 바뀌어 북서쪽 성이 있는 섬이 바다가 됩니다. `worldmap_scene1.bin` 의 그 자리와 똑같았습니다. scene0·2 는 기호 칸 325개만 지운 판이었습니다. `WSYN` 은 블록 수와 블록 크기(4·4·64·64, gotmap·yamimap 은 3·3·64·64)였습니다.

## 3. ubtl 은 쓰이지 않는 자료

지난번 평원 전투 두 번에서는 `ubtl*` 이 메모리에 없었습니다. 이번에는 동굴 `dab1` 에 워프한 뒤 전투 테스트를 열었고, 테스트의 배경 목록도 `btldk1` 로 바꿨습니다. 둘 다 평원 배경으로 싸웠고, ubtl 타일의 64바이트 줄은 VRAM·메인 RAM 어디에도 없었습니다. 전투 테스트는 늘 평원 배경을 쓰는 것으로 보입니다. 동굴에서 걸어서 조우하려고 조우 비트(`0x020CE100 | 0x200`)를 세우고 120걸음을 걸었지만, 전투는 일어나지 않았습니다.

그래서 코드 쪽을 봤습니다. 실행 파일과 오버레이에서 `%s` 가 든 경로 문자열은 `data/btlmap/%s.lz`, `data/chr/%s_%d.nsbca`, `data/pam/m%03d_%s.pam` 등이었습니다. `battlebg` 나 `.bgc` 형식은 없었습니다. `.bgc` 로 끝나는 문자열은 `G2D/SYSTEM` 의 둘뿐이었습니다. 이 근거로 쓰이지 않는 자료로 결론 냈습니다.

## 4. DSSA 플래그와 동작 칸

`0x2000` 은 몬스터 38번의 대기 동작에 있습니다. 전체 일치율로는 뒤집기 방식들이 0.81~0.83 으로 가려지지 않았습니다. 그래서 플래그가 붙은 부품만 따로 그려 그 픽셀만 쟀습니다.

```text
상하 뒤집기 0.577   그대로 0.320   좌우 0.283   양쪽 0.236   (12장)
```

`0x4000` 은 m078 의 불꽃, m310 의 몸 대부분에 붙어 있습니다. m078 은 덧붙은 팔레트가 없으니 팔레트는 아닙니다. 78번과 싸운 화면에서 불꽃은 다른 부품과 같은 색·순서로 불투명하게 그려졌습니다. 평상시에는 보이는 효과가 없어서 뜻은 남겼습니다.

동작 칸은 행동 파일 이름으로 짝지었습니다. `PAM/mNNN_<종류>.pam`·`CAMERA/mNNN_<종류>` 의 종류와 몬스터마다 채워진 칸을 맞대니 다음처럼 나왔습니다.

- `ju`(주문) 58마리 중 55마리가 칸 7
- `br`(숨결) 44마리 중 41마리가 칸 4
- `tu` 9마리 중 8마리가 칸 13

화면 확인은 전투 테스트로 했습니다(ホイミスライム 둘·셋, 키리키리바타). 공격은 다시 칸 1(0.93)로 맞았습니다.

남은 1픽셀 차이는 세로 배율이었습니다. 지난번 측정에서 세로만 1.02~1.05배 늘렸을 때 가장 잘 맞았습니다(29 → 30픽셀).

## 5. LOCN: 면 경계를 바로잡고 RAM 에서 바꿔 보기

mai1f2 로 워프한 뒤 RAM 에서 `LOCN` 을 찾으니 `0x022AC8B0` 에 있었습니다. 파일과 다른 곳은 경계 상자 자리와 오프셋 넷(포인터로 바뀜), 160바이트였습니다. 면 표 포인터는 머리 +0x5C 를 가리켰습니다. 파일의 `+0x34` 값 0x4C 는 `+0x10` 기준이었습니다. 그래서 면은 지난번에 본 것보다 16바이트 뒤에서 시작합니다. 면을 다시 나눠 보니 다음과 같았습니다.

- 꼭짓점 넷의 사각형
- 법선
- (−16, −16)
- 경계 상자 최솟값·최댓값

이어지는 두 덩어리는 (s16 열쇠, u16 면 번호) 쌍 목록이었습니다.

주인공 발밑 바닥 사각형 둘(법선 y 1, 경계 상자가 주인공 x·z 를 품음)을 RAM 에서 50 단위 옮기고, 따로 1.0 올려도 봤습니다. 그래도 걷는 범위(아래로 z 2.58 에서 멈춤)와 주인공 좌표가 바뀌지 않았습니다. RAM 에 있던 다른 LOCN(면 442개)에서도 같았습니다. cbout 에서는 LOCN 면이 y 3.25 인데 주인공 y 칸은 계속 0 이었습니다. 걷기 판정은 이 목록을 실행 중에 직접 읽지 않는 것으로 보입니다.

`FMAP +0x2C` 는 맵 전체에서 2,734가지였고, 490~507 의 16개만 여러 맵이 같이 씁니다. 나머지는 물체마다 하나였습니다. 맵 스크립트에서는 거의 나오지 않았고, 스크립트 물체 머리와도 맞지 않았습니다.

## 6. BTA0·BMA0 와 3D 효과

3D 효과가 비어 나온 원인은 텍스처였습니다. `effect010` 은 `hyado`(16색)와 `kemuri`(A5I3), `effect003b` 는 둘 다 A5I3 였습니다. 알파 128 미만을 버리는 규칙에 거의 다 걸렸습니다. 래스터에 반투명 섞기를 넣자 얼음 결정과 불덩이가 나왔습니다.

BTA0(`SRT0`)는 재질마다 8바이트 트랙 다섯이었습니다. 처음 보이는 `31 00 00 30 00 10 00 00` 은 49프레임·상수·배율 1.0 이었습니다. 플래그 0x10 만 켜진 트랙은 s16 표본을 가리켰고, `tama` 의 이동 T 가 0, 127, 251, … 로 늘었습니다. BMA0(`MAT0`)는 재질마다 4바이트 트랙 다섯이었습니다. 넷째까지는 상수 색이고 다섯째(알파)의 위치가 재질마다 53 = 프레임 수씩 늘어 프레임별 u8 알파였습니다. 처음에 재질 항목 앞에 2바이트가 더 있다고 보고 읽다가 항목 끝을 넘었습니다. 이동은 텍스처를 밀고 알파는 곱해, 효과 17개를 WebP 로 냈습니다.

## 틀렸던 것들

- **칸 위 비트 번호가 기호 그림을 정한다**: 그림은 `SDAT` 가 정하고, 같은 번호가 다른 그림이 되기도 합니다.
- **양피지 지도 좌표 표로 기호를 놓는다**: 1픽셀이 25.6픽셀이라 너무 거칩니다. 자리는 `SDAT` 입니다.
- **화면 원점은 주인공 − (128, 96)**: (129, 97)입니다.
- **전투 테스트는 고른 배경으로 싸운다**: 동굴에서 열어도, 배경 목록을 바꿔도 평원이었습니다.
- **DSSA `0x4000` 은 불꽃의 가산 섞기나 다른 팔레트**: 게임 화면의 불꽃은 불투명하고 색도 같았습니다.
- **LOCN 면은 `+0x34` 의 오프셋에서 시작한다**: 그 오프셋은 `+0x10` 기준이라 16바이트 뒤입니다.
- **MAT0 항목은 u16 0 뒤에 트랙**: 트랙 다섯이 바로 시작합니다.

## 남은 것

- DSSA `0x4000` 의 뜻, 셀 머리 u32, 프레임 표 첫 8바이트.
- 몬스터 동작 칸 7·4 등의 화면 확인, 칸 2·3·12.
- LOCN 의 실제 쓰임과 머리 수 넷·격자, FMAP `+0x2C` 이후를 게임에서 확인하기.
- gotmap·yamimap·기호 변형·3D 효과를 게임 화면과 견주기.
