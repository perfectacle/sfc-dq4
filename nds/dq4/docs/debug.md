# NDS DQ4 디버그 기능·RAM 지도·장면 이동

NDS 「ドラゴンクエストIV 導かれし者たち」(일본판)에 남은 개발용 기능과, 그것으로 아무 장·아무 맵에서 바로 실험을 시작하는 방법입니다. 도구는 [ndsplay.py](../tools/ndsplay.py)(desmume libretro 코어를 화면 없이 돌리며 입력·화면·세이브스테이트·RAM 읽고 쓰기)와 [ndswarp.py](../tools/ndswarp.py)(장면 이동·진행도 프리셋·장 시작 세이브스테이트)이고, 찾은 과정은 [2026-10-25-04 일지](../journal/2026-10-25-04-debug.md), [2026-10-25-08 일지](../journal/2026-10-25-08-debug2.md), [2026-10-25-09 일지](../journal/2026-10-25-09-debug3.md), [2026-10-25-12 일지](../journal/2026-10-25-12-debug4.md), [2026-10-25-14 일지](../journal/2026-10-25-14-debug5.md), [2026-10-25-20 일지](../journal/2026-10-25-20-debug6.md)·[2026-10-26-05 일지](../journal/2026-10-26-05-actions.md) 에 있습니다.

모든 「켜는 법」은 에뮬레이터 안에서 RAM 을 쓰는 것입니다. 롬 파일은 고치지 않습니다. 주소는 ARM9 주소(메인 RAM `0x02000000`~)입니다.

## 준비

desmume libretro 코어를 직접 빌드해 경로를 `DESMUME_CORE` 에 둡니다. [libretro/desmume](https://github.com/libretro/desmume) 커밋 `95b4d79` 에서 `make -C desmume/src/frontend/libretro` 로 만든 `desmume_libretro.dylib`(Linux 는 `.so`)를 씁니다. 롬은 `rom/dq4ds.nds`, 풀어 둔 파일 시스템은 `work/nds/jp`(목록·프리셋 표를 읽음)입니다.

```sh
export DESMUME_CORE=/path/to/desmume_libretro.dylib
uv run --locked python nds/dq4/tools/ndswarp.py chapters work/state     # 서장·1~6장 시작 세이브스테이트
uv run --locked python nds/dq4/tools/ndswarp.py presets 6章             # 진행도 프리셋 찾기
uv run --locked python nds/dq4/tools/ndswarp.py preset work/p 331       # 프리셋 331(산, 피사로가 동료) 상태로 시작
uv run --locked python nds/dq4/tools/ndswarp.py map work/m mlout2 --state work/state/dq4ds-ch5.state
uv run --locked python nds/dq4/tools/ndswarp.py field work/f 200 60 --state work/state/dq4ds-ch1.state   # 필드 (200, 60) 칸
uv run --locked python nds/dq4/tools/ndswarp.py map work/m dab1 --state work/state/dq4ds-ch1.state --no-encounter
uv run --locked python nds/dq4/tools/ndswarp.py battle work/b 50x3 1x2 --state work/state/dq4ds-ch1.state  # m050 3마리 + m001 2마리
uv run --locked python nds/dq4/tools/ndswarp.py map work/n maout --time 4 --state S   # 밤의 イムルの村
uv run --locked python nds/dq4/tools/ndsplay.py rom/dq4ds.nds work/t --state work/state/dq4ds-ch1.state \
  --cmd "a 5; hold left 30; peek 20c55f0 4; poke32 20c55f0 270f; press x; shot menu"
```

`ndsplay.py` 명령: `wait`·`press`·`hold`·`a`·`mash`·`touch`·`drag`·`shot`·`every`(입력·화면), `poke`·`poke32`·`freeze`·`peek`·`dump`·`until`(RAM), `save`·`load`(세이브스테이트). 자세한 꼴은 도구의 docstring 에 있습니다. 세이브스테이트는 코어의 `retro_serialize` 그대로(약 12MB)라 같은 코어 빌드에서만 읽힙니다.

## 장 시작 세이브스테이트

`ndswarp.py chapters OUT` 가 전원부터 만듭니다(세이브스테이트 입력이 필요 없음). 원래 체크아웃의 `work/state/` 에 아래 이름으로 둡니다.

| 파일 | 프리셋 | 시작 맵 | 화면 |
| --- | --- | --- | --- |
| `dq4ds-boot.state` | 없음 | `caf1` | 부팅 디버그 메뉴 「1:Town Part」. 이름 「ソロ」, 인물 없는 バトランド城 |
| `dq4ds-ch0.state` | 0 「序章」 | `mlb1a` | 서장 첫 장면(산골 마을 지하 훈련장) |
| `dq4ds-ch1.state` | 1 「１章スタート」 | `caf1` | 「第一章 王宮の戦士たち」 → 「これは バトランドという…」, 그 뒤 왕좌의 방 |
| `dq4ds-ch2.state` | 24 「２章スタート」 | `cbf2` | 「むかしむかし ある所に アリーナ姫という…」 |
| `dq4ds-ch3.state` | 59 「３章スタート」 | `mfm1f1` | 「ここは エンドールから はるか北にある…」(トルネコ 집) |
| `dq4ds-ch4.state` | 93 「４章スタート」 | `mhg1n1` | 「これから始まるお話は 父親のカタキを探し…」 |
| `dq4ds-ch5.state` | 109 「５章スタート」 | `mlm1f1` | 「エンドールから はるか東の山奥に…」 |
| `dq4ds-ch6.state` | 310 「ロザリーヒル（エンディングセーブ後）」 | `mqout` | 엔딩 뒤 ロザリーヒル, 일행 ドラン·ソロ·ライアン·アリーナ |
| `dq4ds-ch6-psaro.state` | 331 「山（ピサロ仲間にした）」 | `srout` | 피사로가 동료가 된 뒤 |

1~5장은 게임의 장 시작 연출(장 제목 → 해설 → 첫 장면)이 그대로 돕니다. 장 번호(`0x020EB9A8`)는 서장 프리셋도 1 이고(레코드 `+0x9B` 가 1), 1~6장은 1~6 입니다.

## 남은 디버그 기능

### 장면 관리자와 장면 번호

게임은 「장면(Part)」 객체를 번호로 등록해 두고 하나씩 돌립니다. 관리자는 `0x02108048` 이고 `+0x64` 가 지금 장면, `+0x68` 이 이전 장면, `+0x6C` 가 다음 장면 요청(-1 이면 없음)입니다. 요청 함수 `0x02056488` 은 `+0x6C` 에 쓰기만 하고, 장면 루프(`0x020563A0`)가 다음 틀에서 바꿉니다. 그래서 **`0x021080B4` 에 번호를 쓰면 그 장면으로 넘어갑니다**. 등록은 `0x020084AC` 에서 합니다.

| 번호 | 객체 | 장면 | 확인 |
| --- | --- | --- | --- |
| `0x00` | `0x020C45C4` | 부팅 직후(곧 `0x0C`) | 실측 |
| `0x01` | `0x020C2908` | **부팅 디버그 메뉴**: `1:Town Part`, `2:SSA Viewer Part`, `3:Message Debug Part`, 메모리 크기, `Build.07/10/20 23:45`, `Convt.06/04/27 16:44` | 실측 |
| `0x02` | `0x020C296C` | 타이틀 로고(「ERROR:MID <0>」 창이 함께 뜸) | 실측 |
| `0x03` | `0x020EB388` | 모험의 서 고르기·만들기 | 실측 |
| `0x04` | `0x0210836C` | 회사 로고 → 오프닝 | 실측 |
| `0x0B` | `0x0210837C` | 곧 `0x0C` 로 넘어감 | 실측 |
| `0x0C` | `0x020C293C` | 맵(마을·성·던전). 들어갈 때 지금 맵 이름(`0x020C4F44`)을 읽어 실음 | 실측 |
| `0x0D` | `0x020C28B8` | 전투(배경만 뜨고 적 없음. 전투 테스트가 이 장면으로 넘김) | 실측 |
| `0x0E` | `0x020C2900` | 필드(세계 지도, 위 화면에 지도) | 실측 |
| `0x0F` | `0x020C52A4` | 카지노 포커 | 실측 |
| `0x10` | `0x020EC4E8` | 빈 양피지 지도 화면 | 화면만 |
| `0x11` | `0x020C28BC` | **전투 테스트**(`Battle Menu Part`) | 실측 |
| `0x13` | `0x020ED5F4` | 엇갈림 통신(이민 마을 모으기) 대기 | 화면만 |
| `0x16` | `0x020C4C90` | **메시지 디버그**(`Message Debug Part`): バトランド城 위에 메시지 번호의 문장을 띄움. [아래](#메시지-디버그장면-0x16) | 실측 |
| `0x08` | 등록 안 됨 | `SSA Viewer Part`(메뉴 2번). 고르면 아무 장면도 돌지 않음 | 실측 |

### 부팅 디버그 메뉴(장면 `0x01`)

메뉴 표는 `0x020B8C08` 의 `0x24` 바이트 항목(+0 장면 번호, +4 이름, 장면 번호 `0x1B` 가 끝)이고, 고르면 그 장면을 요청합니다(`0x02009520`). 위·아래는 누르고 있는 동안 매 프레임 움직이므로 1프레임만 누릅니다(`press down 1 10`). 들어갈 때 맵 이름을 `caf1` 로 정하므로 「1:Town Part」는 새 게임 없이 バトランド城에 주인공 「ソロ」를 세웁니다. 인물·진행 플래그가 비어 있어 「빈 무대」로 쓸 수 있습니다(`ndswarp.py boot`).

### 전투 테스트(장면 `0x11`, `Battle Menu Part`)

위 화면에 `1.Mode : Encount`(또는 `Select`), `2.Encount Tile`, `3.Time Zone`, `4.Group`, `5.Map` 이 뜹니다. 첫 줄에서 오른쪽·왼쪽 방향키로 모드를 바꾸고, 위·아래로 값을 고르고, A 로 시작합니다(코드 읽기, `0x02008954`). `Encount` 모드에서 A 를 누르니 1장 상태에서 「スライムが あらわれた!」 전투가 지금 일행으로 시작했습니다. 맵 목록은 `data/btlmap/_list.txt` 입니다.

`Select` 모드(첫 줄에서 오른쪽)는 무리 4개에 몬스터와 마릿수를 직접 넣습니다. 객체는 `0x020C28BC` 이고, 칸은 갱신 함수 `0x02008D78` 을 읽어 정리했습니다.

| 줄 | 칸 | 오른쪽·왼쪽 |
| --- | --- | --- |
| `2.GROUP` | `+0x1C` 고른 무리(0~3) | 무리 바꾸기 |
| `3.MONSTER : m%03d` | `+0x20 + 4×무리` 몬스터 번호(0~320). 몬스터 표 번호와 같고 이름은 `ndsparam.py monsters`([param-format.md](param-format.md#몬스터-표)) | ±1, R 을 누른 채면 ±10 |
| `4.COUNT` | `+0x30 + 4×무리` 마릿수(0~8) | ±1 |
| `5.Group`·`6.Map` | 무리 목록·전투 배경 목록(`0x020C27D4`) | 앞뒤 항목 |

A 를 누르면 네 무리의 몬스터·마릿수를 전투 준비 객체로 옮기고 전투를 시작합니다. 무리 0 에 `m050` 3마리를 쓰고 A 를 누르니 「とらおとこAは みのけもよだつ おたけびを あげた!」 전투가 1장 일행으로 시작했습니다. `ndswarp.py battle OUT 50x3 --state S` 가 이 순서를 그대로 합니다.

### 메시지 디버그(장면 `0x16`)

객체 `0x020C4C90` 의 `+4`(`0x020C4C94`)가 메시지 번호(0~2,000,000)이고, A 를 누르면 그 번호의 문장을 메시지 창에 띄웁니다. 번호 500002 를 쓰고 A 를 누르니 「フレア「あの……　お城になにか用が? 夫はイムルの村と聞いたのですが。」」가 떴습니다. 처음 들어가면 번호가 0 이라 「ERROR:MID <8>」 이 뜹니다.

키는 갱신 함수 `0x0200A094` 를 읽어 정리했고, 아래 표의 번호 키와 X 는 화면·RAM 으로 확인했습니다. 500002 에서 오른쪽을 단위별로 한 번씩 누르니 `+4` 가 500003 → 500013 → 500113 → 501113 → 511113 → 611113 이 되었고, 같은 키와 왼쪽으로 500002 로 돌아왔습니다.

| 키 | 하는 일 |
| --- | --- |
| A | 지금 번호의 문장을 띄움 |
| 오른쪽·왼쪽 | 번호를 한 단위 늘리고 줄임. 함께 누른 키로 단위가 바뀜: 없음 1, B 10, R 100, R+B 1,000, L 10,000, L+B 100,000 |
| X | 창 종류(`+8`, 1~4)를 바꿈. 1·2 는 보통 메시지 창, 3 은 글자가 작은 창, 4 는 창이 뜨지 않음 |
| Y | 언어(`+0xC`, 0~5)를 바꾸고 `0x020CE3E0` 에 씀. 한 번 눌러 1 이 된 것은 실측, 이미 띄운 문장은 그대로 |
| Select | `+0x1C` 를 켜고 끔 |

### 진행도 프리셋(디버그 「フラグショップ」의 남은 반쪽)

`data/DEBUG/flagshop.dat` 은 「번호, 묶음, 이름」 347줄(「序章」, 「１章スタート」 … 「天空城（裏エンディング）」)입니다. 이 목록을 띄우던 메뉴는 롬에서 빠졌지만, 고른 번호를 적용하는 코드는 ARM9 에 남아 있습니다.

| 주소 | 하는 일 |
| --- | --- |
| `0x020B970C` | 적용 대기 프리셋 번호. 평소 -1 |
| `0x0200DD50` | 대기 번호를 쓰는 함수(부르는 곳이 롬에 없음. 빠진 메뉴가 불렀던 것) |
| `0x0200DD5C` | 대기 번호가 -1 이 아니면 적용하고 -1 로 되돌림. 부르는 곳은 ARM9 `0x0203D1A2`·`0x0203D1DC` 와 오버레이 0·1. 장면 `0x0C` 를 요청하면 적용됨(실측) |
| `0x0200D774` | 적용: 프리셋 레코드로 일행·돈 등을 쓰고(실측: 일행·돈이 바뀜) 아래 플래그 함수를 부름 |
| `0x0200CAA8` | 프리셋 레코드 찾기: `PARAM/param_player_event1`~`4.dat`(머리 4바이트 + `0x9C` 바이트 레코드, `+0` 프리셋 번호로 찾음). 레코드는 `+2` 돈(u16, 프리셋 311 이 26646 이고 메뉴도 26646G), `+0xE`~ 일행 바이트, `+0x13` 이름(UTF-8, 잘림), `+0x93` 시작 맵 이름, `+0x9B` 장 번호 |
| `0x0200D9D4` | `PARAM/param_player_flag.dat`(머리 4바이트 + 16바이트 레코드, 플래그 번호 u16 다섯 칸, `0xFFFF` 은 빈칸)으로 이야기 플래그 객체 `0x020CE7DC` 를 지우고 레코드 0~N 의 플래그를 켬 |

그래서 **`0x020B970C` 에 번호 N 을 쓰고 맵 이름에 레코드의 시작 맵을 쓴 뒤 장면 `0x0C` 를 요청하면** 그 진행도로 그 맵에 들어갑니다. 1장(1)·2장(24) 프리셋은 일행이 ライアン(HP 27, 50G)·アリーナ(HP 16, 100G)로 바뀌는 것으로, 1~5장 시작 프리셋은 장 시작 연출이 도는 것으로 확인했습니다.

### 빠진 것

- 오버레이 4·5·7·8·10~14·17~23(20개)은 32바이트짜리 0 입니다. 개발용 오버레이를 비워 둔 것으로 보입니다.
- `Debug Menu` 객체(`0x021080F4`, 항목 `0x24` 바이트를 `%d:%-10s %5d` 로 그리는 틀)는 ARM9 에 있지만, 열림 칸(`+0x68`)과 항목 표(`+0x78`)를 쓰는 코드가 없습니다. 메뉴 내용이 빠진 오버레이에 있었던 것으로 보입니다.
- `DEBUG/action.dat`(주문·특기 이름 목록), `fieldsymbol.dat`(필드 기호 → 장소 이름), `soundlist.dat`(사운드 테스트 곡명)을 여는 코드는 찾지 못했습니다.

## RAM 지도

1장 상태 등에서 값을 바꿔 화면으로 확인한 것만 적습니다.

| 주소 | 크기 | 뜻 | 확인 |
| --- | --- | --- | --- |
| `0x021080AC` | u32 | 지금 장면 번호 | 장면마다 값 |
| `0x021080B4` | u32 | 다음 장면 요청 | 쓰면 장면이 바뀜 |
| `0x020C4F44` | 문자열 16 | 지금 맵 이름(`_list.txt` 의 셋째 칸, 예 `mlout1`) | 맵을 옮기면 바뀜, 쓰고 장면 `0x0C` 를 요청하면 그 맵이 실림 |
| `0x020C4F24` | 문자열 16 | 바로 앞 맵 이름 | 실측 |
| `0x020CE100` | u32 | 지금 맵의 속성 비트. `0x200` 이 조우 있음(`0x0201C790` 이 봄) | [조우 끄기](#조우-끄기) |
| `0x020CE104` | 문자열 | 맵 이름 사본(게임 상태 객체 `0x020CE100` 의 `+4`) | 실측(쓰기는 효과 없음) |

### 상태 이상 번호

상태를 거는 길은 하나입니다. 주문·특기·몬스터 행동·도구 사용은 모두 행동 번호 하나를 갖고, 행동 표(ARM9 `0x020A8294`, `0x48` 바이트 레코드, [param-format.md](param-format.md#행동-표))의 `+38` 이 효과 종류입니다. `0x0201E494`(상태 표, 행동 번호, 인자 하나)가 `0x020154DC` 로 효과를 읽어 그 칸을 켭니다. 효과 8~`0x16`·`0x18`~`0x1A` 는 효과 값이 곧 상태 번호이고, `0x1C` 는 상태 `0x0B`, `0x27` 은 `0x1B`, `0x29` 는 `0x1E` 칸을 켭니다(칸의 `+4` 에는 효과 값이 들어감). 아래 표의 「거는 행동」은 이 함수를 unicorn 으로 따로 돌려, 행동 1~594 마다 어느 칸을 켜는지 모은 것입니다(`ndsparam.py actions`). 행동 번호 뒤 이름이 없는 것은 이름 파일에 이름이 없는 몬스터용 행동이라 첫 전투 문장으로 적었습니다.

#### 켜 본 화면

앞 판은 1장 ライアン 을 キリキリバッタ(`m001`) 1마리와 싸우게 한 뒤 상태 칸 하나를 직접 켜고 A 로 한 턴씩 넘겼습니다(0~31 모두). 위 표와 맞는 것은 `0x08` 「からだは 鉄のかたまりとなり なにものも うけつけない！」, `0x0B` 「ミス！ キリキリバッタに ダメージを あたえられない！」, `0x0C`·`0x11` 같은 공격 9 → 18, `0x13` 「もとのすがたに もどった！」, `0x1A` 「羽で あいてを とらえられない！」입니다. `0x14` 를 켰을 때 받는 피해가 1 → 5 로 보인 것은 혼란한 ライアン 이 자기를 친 것으로 보입니다. `0x15`·`0x1E` 를 켰을 때 「ミス！ ライアンは ダメージを うけない！」가 두 번 나온 것은 위 표의 뜻(겁먹음·시간 정지)과 바로 이어지지 않아, 상태 칸만 켜고 다른 칸(`+9`·`+A`)을 0 으로 둔 탓인지 확인하지 못했습니다.

맵 번호(`0x020A294A` 의 맵 정보 표, `0x2A` 바이트 항목 544개, `_list.txt` 와 같은 순서)는 RAM 에 정수로 남지 않고 이름으로만 다닙니다.

`0x020D2870` 은 나무 구조를 도는 일반 용기 객체(vtable `0x020C14E0`)이고 `+4` 의 평소 값은 -1 입니다. 값을 써도 빈 성과 1장 왕좌의 방에서 아무 일도 일어나지 않았습니다(-1·0·1·2·3·5·0x10·0x100·0x12345 를 써 보고 X·A 를 누름).

## 장면 이동(맵 워프)

`ndswarp.py map` 은 진행도를 그대로 두고 맵 이름만 바꿔 장면 `0x0C` 를 다시 요청합니다. 주인공은 맵의 기본 자리(대개 원점 근처)에 서며, 그 자리가 벽 안이면 `--x`·`--z`(칸 단위)로 옮깁니다. 산골 마을 맵 `mlm1f1`·`mlm2f1`·`mly1f1`·`mlb1b`·`mlido`·`mlout2` 와 성 `ccf1a` 로 옮겨 화면을 확인했습니다. 맵 544개 전부를 6장(프리셋 331) 상태에서 옮겨 보니 543개는 그 맵에 머물렀고, `fk01` 만 곧 `ckout` 으로 바뀌었습니다. `fk01` 은 하늘을 나는 天空城 연출 맵입니다. 부팅 상태에서 옮기면 구름 위 天空城이 그대로 보이고, 5장 상태에서는 「どこからともなく こえが きこえる……」 이벤트가 시작됩니다. 맵을 싣지 못한 것이 아니라, 그 맵의 스크립트가 조건이 맞으면 다른 맵으로 넘기는 것입니다. 조건은 **장 번호 5 이상, 이야기 플래그 431, 주인공이 てんくうの つるぎ·よろい·たて·かぶと 넷을 장비**이고, 셋 중 하나라도 빠지면 `fk01` 에 머뭅니다(부팅 상태에 6장 상태의 RAM 을 덮어써 ddmin 으로 좁힘). 이 맵으로 가는 길은 목적지 번호 `0x17`(`0x02027F98` 의 분기, `0x19` 는 `dpb8b`)입니다.

`ndswarp.py screens OUT` 이 이 모음을 만듭니다. 프리셋 331 상태를 롬에서 만들고(`--state` 로 바꿀 수 있음), 맵마다 그 상태를 다시 읽어 맵 이름을 바꾸고 장면 `0x0C` 를 요청한 뒤 240프레임 기다려 위·아래 화면을 `NNN-<맵>.png`(256x384)로 저장합니다. 그 맵에 머물지 못하면 부팅 상태에서 한 번 더 들어가므로 `fk01` 도 天空城 화면이 나옵니다. desmume 의 시계(RTC)는 호스트 시각을 따라 부팅할 때마다 맵 인물의 걸음과 물·불꽃 애니메이션이 달라집니다. 그래서 프레임을 돌리는 동안만 코어의 `movieMode` 를 3(영상 재생 끝)으로 두어 시계를 「2009-01-01 + 프레임 수」로 고정합니다. 이렇게 두 번 돌린 544장은 바이트까지 같았습니다.

문으로 들어가야 시작되는 이벤트는 워프로 건너뛰면 멈출 수 있습니다(서장 어머니 대화가 그랬음). 그럴 때는 바깥 맵에 워프한 뒤 주인공 자리를 문 앞에 써서 걸어 들어갑니다.

**벽 통과**는 따로 찾지 않았습니다. 주인공 자리(`0x020EC524`)를 쓰면 아무 칸에나 설 수 있어 같은 목적에 씁니다.

## 필드 워프

필드(장면 `0x0E`)에서 `0x020EC524` 는 매 프레임 다시 쓰이는 그리기용 사본입니다. 원본은 주인공 객체(`[0x020EC4F0]`)의 `+0x70` 이 가리키는 x·z(s32, 한 칸 `0x3000`)입니다. 힙 주소라 세이브스테이트마다 다를 수 있으므로 포인터를 따라갑니다.

`ndswarp.py field OUT X Z --state S` 는 장면 `0x0E` 를 요청한 뒤 그 칸에 씁니다. (141, 98)·(200, 60) 칸에서 위 화면 지도·아래 화면 땅이 바뀌고 거기서 다시 걸었습니다. 바다 칸에 쓰면 물 위에 섭니다. 필드는 맵 장면을 거치지 않고 들어가므로, 이 경로로 들어간 필드는 맵 속성 비트가 앞 맵 그대로이고 조우 비트가 없으면 조우도 없습니다. 필드 좌표는 `0x1000000`(= 1365⅓ 칸)마다 돌아갑니다. x 1500·1700·2000 칸, z 1600·1900 칸을 쓰면 1365⅓ 을 뺀 자리에 섰습니다. `ndswarp.py field` 는 넣은 값을 이 범위로 접습니다(-10 → 1355.33).

위 화면 지도의 주인공 표시(칼 모양)는 대략 `(58 + x/10, 11 + z/10)` 픽셀(x·z 는 칸)이었습니다. 11곳(0~397 칸)에서 표시의 흰 픽셀 중심을 재 맞췄고, 한 바퀴가 지도에서 약 136 픽셀입니다.

## 조우 끄기

걸음마다 오버레이 0(맵)·1(필드)이 조우 판정 `0x0200A730` → `0x0200A67C` 를 부릅니다. `0x0200A67C` 는 맵 속성 비트 `0x020CE100 & 0x200` 이 없으면(`0x0201C790`) 바로 돌아갑니다. 그래서 **`0x020CE100` 의 `0x200` 비트를 지우면 그 맵에서 조우가 없습니다**. 비트는 맵에 들어갈 때 다시 실리므로 맵을 옮기면 다시 지웁니다(`ndswarp.py … --no-encounter`).

| 실험(같은 출발, 좌우·상하로 걷기) | 결과 |
| --- | --- |
| イムルへの洞くつ(`dab1`, 프리셋 3), 그대로 | 27걸음째 전투 |
| 같은 곳, 비트를 한 번 지움 | 300걸음 동안 전투 없음 |
| 필드 (200, 60), 비트 없음 | 300걸음 동안 전투 없음 |
| 같은 곳, 비트를 켬 | 37걸음째 전투 |

조우 객체는 `0x020C4CD8`(`+8` 조우 칸 64, `+0x1C` 조우 단계)입니다. `+0x10`·`+0x1C` 를 매 프레임 0 으로 고정해도 전투는 막히지 않았습니다. 같은 프레임 안에서 다시 쓰이기 때문입니다.

## 남은 것

- 상태 칸 `+9`·`+A` 의 뜻(남은 턴으로 보임)과, 상태 `0x15`·`0x1E` 를 직접 켰을 때 적 공격이 빗나간 까닭.
- 행동 467(시간 정지)·468(うめきごえ)·97(ふしぎなきり)을 실제로 쓰는 몬스터·장면.
