# NDS DQ4 PARAM 표 형식

`data/data/PARAM/*.dat` 가운데 늘어난 내용([extras.md](extras.md))을 가르는 데 쓴 표입니다. 몬스터·가게·メダル·얻는 물건·동료 대화 표와, 이벤트 스크립트(`SCRIPT/<맵>.bin`)가 부르는 대사 파일을 다룹니다. 도구는 [ndsparam.py](../tools/ndsparam.py), 찾은 과정은 [2026-10-25-07 일지](../journal/2026-10-25-07-param.md)·[2026-10-25-10 일지](../journal/2026-10-25-10-param2.md)·[2026-10-25-15 일지](../journal/2026-10-25-15-param3.md)·[2026-10-25-17 일지](../journal/2026-10-25-17-param4.md)·[2026-10-25-19 일지](../journal/2026-10-25-19-param5.md)·[2026-10-25-21 일지](../journal/2026-10-25-21-param6.md) 에 있습니다. 진행도 프리셋(`param_player_event*`·`param_player_flag`)은 [debug.md](debug.md), 메시지 번호 규칙은 [text-format.md](text-format.md) 를 봅니다.

모든 PARAM 파일은 머리 4바이트 뒤에 고정 길이 레코드가 이어집니다. 머리 값은 파일 종류마다 다르고(`param_map_shop_*`·`param_map_medal` 은 `1A 00 00 00`, `param_item_*` 은 `32 BC 00 00`) 레코드 수와는 맞지 않습니다.

```sh
uv run --locked python nds/dq4/tools/ndsparam.py monsters work/nds/jp rom/dq4.nes   # DS 몬스터 표와 FC 대조
uv run --locked python nds/dq4/tools/ndsparam.py items work/nds/jp rom/dq4.nes      # 아이템 번호 대조
uv run --locked python nds/dq4/tools/ndsparam.py casino work/nds/jp rom/dq4.nes     # 카지노·メダル 경품
uv run --locked python nds/dq4/tools/ndsparam.py talk work/nds/jp 1                 # 동료 대화 조건
```

## 몬스터 표

머리 4바이트 + 60바이트 레코드 315개. 이름은 이름 표 `b1002000` 의 `+00` 번입니다.

| 위치 | 크기 | 뜻 | 근거 |
| --- | --- | --- | --- |

이름이 같은 FC 몬스터 208마리 가운데 156마리는 경험치·골드·HP·MP·공격·수비·민첩 일곱 값이 모두 같아서, 이 일곱 칸의 위치는 확정입니다. 나머지 52마리는 DS 에서 값을 고친 것입니다(뒤 「FC 와 대조」).

내성 칸은 2비트씩이고, `+2F` bit1-0 부터 FC 내성 칸 순서(`dq4data.py` 의 `RESIST_NAMES`)대로 15칸이 이어집니다. FC 몬스터와 값이 모두 같은 156마리로, FC 칸마다(`dq4data.resists()`) DS 의 모든 2비트 자리와 견줬습니다.

| `+2F` bit7-6 | デイン | 156 |
| `+30` bit1-0 | バギ | 155 |
| `+30` bit3-2 | ヒャド | 154(`+35` bit1-0 도 155) |
| `+30` bit5-4 | マヌーサ | 156 |
| `+30` bit7-6 | ラリホー | 154 |

| `+31` bit3-2 | ニフラム | 156 |
| `+31` bit5-4 | マホトラ | 156 |
| `+31` bit7-6 | マホトーン | 156 |

ギラ·ヒャド 는 차례대로 놓인 자리 말고도 `+34`·`+35` 에 같은 값이 있습니다. 같은 계열 다른 주문(DS 에서 늘어난 내성 칸)으로 보이지만 확인하지 못했습니다.

전투로 확인(4장 マーニャ 혼자, 전투 테스트로 スライム 1마리, 전투 전에 RAM 의 몬스터 표 `0x0209DF78` + `0x2F` 를 바꾸고 メラ):

| `+2F` 값 | 결과 |
| --- | --- |
| `00`·`01`·`02`·`03`·`0C`·`C0` | 「スライムに 12の ダメージ!!」 |
| `30`·`FF` | 「スライムには きかなかった!」 |

DS 의 メラ 칸은 `+2F` bit5-4 이고, 위 표의 FC メラ 칸과 같은 자리입니다. 앞 판에서 이 자리를 FC 「イオ」 칸과 짝지은 것은 FC 도구가 내성 값을 칸 순서가 아닌 필드 번호 순서로 내놓았기 때문이었고, dq4 트랙이 PR #294 에서 바로잡았습니다(`monster_fields()['resist_fields']`, `resists()`). 값 3 이 「듣지 않음」인 것은 확인했고, 1·2 의 뜻(반감 등)은 확인하지 못했습니다. 같은 전투에서 bit5-4 를 1(`10`)·2(`20`)로 두어도 メラ 는 0 일 때와 같은 12 였습니다. 값 1·2 가 피해 주문의 피해를 줄이지는 않았고, 무엇을 바꾸는지는 남은 것입니다.

## 아이템 번호

가게·メダル·얻는 물건 표의 아이템 값 n 은 이름 표 `b1000000` 의 n−1 번입니다. 1장 バトランド 가게 줄이 `(2, 30) (3, 100) (10, 200) (5, 550)` 이고, FC 같은 가게가 こんぼう 30G·どうのつるぎ 100G·いばらのむち 200G·くさりがま 550G 입니다. n−1 번 이름이 こんぼう·どうのつるぎ·せいなるナイフ·くさりがま 이므로 값이 맞습니다.

DS 와 FC 의 아이템 순서는 무기 앞쪽(FC `00`~`13`, DS 번호 = FC ID + 1)만 같고, 그 뒤는 DS 가 새 아이템을 사이사이에 끼워 넣고 도구 순서도 바꿨습니다. 옮길 때는 번호를 더해서 맞추지 말고 `items` 가 내는 대응표를 씁니다.

### 아이템 표(ARM9)

아이템 능력치는 PARAM 이 아니라 ARM9 `0x02095594` 부터 32바이트 레코드에 있습니다(아이템 n 은 `0x02095594 + 32 × (n−1)`, n = 1~161). 가게 값 58개 가운데 56개가 이 표의 값과 같은 자리를 찾아서 알았습니다. 앞 판은 레코드 시작을 16바이트 앞(`0x02095584`)으로 잡아 앞 아이템의 뒷부분을 섞어 읽었습니다.

| 위치 | 뜻 | 근거 |
| --- | --- | --- |
| `+00` | u16 값(G). 0 은 가게에서 안 팖 | 가게 표와 56/58 같음 |
| `+02` | u16 팔 값. 77개 중 68개가 값 × 3/4 | |
| `+06` | u8 강도(공격력·수비력) | FC 와 이름이 같은 장비 82개 중 74개 같음 |
| `+10` | u8 아이템 번호 n(아이템 158 만 137) | |
| `+12` | u8 종류: 0 도구, 1 무기(1~42), 2 방어구(43~106), 3~6 장신구 | 번호 구간 |
| `+14` | u16 장비할 수 있는 인물. 비트 n 이 인물 번호 n+1: 0 ソロ, 1 ソフィア, 2 ライアン, 3 アリーナ, 4 クリフト, 5 ブライ, 6 トルネコ, 7 ミネア, 8 マーニャ, 9 ピサロ | 비트 0~8 이 FC 장비 표(인물 8명, 주인공은 ソロ·ソフィア 둘)와 82개 중 78~82개 같음. 비트 9 는 まかいの 장비 4종이 이 비트만 가져 ピサロ 로 봄 |
| `+04`·`+08`~`+0E`·`+13`·`+16`~`+1E` | 모름. `+1C` 는 `0x020CAExx` 꼴 주소 | |

장비 비트를 찾은 방법: ARM9·오버레이의 모든 자리·간격(1~32바이트)·비트에 대해, DS 번호 순으로 그 비트를 모아 FC 인물별 장비 가능 여부와 맞는 수를 셌습니다. 간격 32, 위 자리에서만 9개 비트가 각각 FC 인물 하나와 78개 이상 맞았습니다. 새 장비 수치와 장비 인물은 [extras.md](extras.md#새-장비-수치) 에 있습니다.

## 가게 표

게임이 쓰는 가게 표는 ARM9 안에 있습니다(nds-text2 실측). first 는 `0x020945F8` 부터 19개로 PARAM 파일과 같습니다. second 는 `0x02099A30` 부터 36개입니다. PARAM 파일은 30개이고, 레코드 6 의 여관 값만 다릅니다(ARM9 4G, PARAM 5G). 레코드 30(`mr`)과 31~35(이민 마을 `ss1`~`ss5`)는 ARM9 에만 있습니다. `ndsparam.py shops` 는 ARM9 표를 읽습니다.

### 레코드 고르기

nds-text2 가 코드를 읽고 함수를 돌려 찾았습니다. 자세한 근거는 [script-format.md](script-format.md#가게) 에 있습니다.

- 표: `0x020CE3EC` 가 0 이면 first, 1 이면 second 입니다(장 번호가 4 보다 크면 1). 표 주소는 `0x020CE3F0`·`0x020CE3F4` 에 있고, 표 묶음 객체 `0x020C51D8` 의 `+0x84`·`+0x88` 에도 있습니다.
- 레코드: `0x0201D2BC` 가 지금 맵 이름 앞 두 글자로 키를 만듭니다(이민 마을 `ss` 는 셋째 글자까지). `0x0200CCCC`(first)·`0x0200CB10`(second)가 그 키를 레코드 번호로 바꾸고, 목록에 없는 맵은 0번입니다.
- 맵 → 레코드(`ndsparam.py` 의 `SHOP_MAPS`):
  - first: `ma` 1, `mb` 2, `mc` 3, `md` 4, `me` 5, `sb` 6, `hc` 7, `cc` 8, `tb` 9, `mf` 10, `mg` 11, `cd` 12, `mh` 13, `mi` 14, `ce` 15, `mj` 16, `mk` 17.
  - second: `hc` 1 … `mr` 30, `ss1`~`ss5` 31~35.

이 방식은 화면과 맞았습니다. 1장 haout(`ha` 는 목록에 없어 0번)의 무기점 주인(스크립트 물체 `(-3.46, 10.55)`, 명령 `98 2`) 앞에서 말을 걸자 first 0 의 품목이 나왔습니다. maout(`ma` = 1)의 같은 명령에서는 first 1(どうのつるぎ … てつのやり)이 나왔습니다.

FC 장소와의 대조(`shops JPROOT FCROM`): 가게가 있는 ARM9 레코드 43개 가운데 25개가 어느 FC 장소와 품목이 완전히 같고, 그중 22개는 여관 값도 같습니다(예: first 0 = `02/00` バトランド, first 7 = `04/00` エンドール). 앞 판의 「39개 중 29개」는 여관 값을 견주지 않고 센 잘못된 수였습니다.

### 실측

진행도 프리셋 1~346 을 하나씩 적용하고 시작 맵에서 「はなす」를 골라, 통과 목록과 그 직전 RAM 4MB 를 모았습니다. 일행과 말할 수 있었던 곳은 280곳입니다. 위 규칙을 RAM 덤프에 그대로 적용한 흉내(우선순위, 플래그 세 벌, 아이템, 변장, 일행 칸, 들은 목록, 6장 → 5장)는 280곳 모두에서 통과 목록이 같았습니다. 이전 판의 「통과하지 않은 줄 1,027줄을 통과로 잘못 냄」은 우선순위와 일행 조건을 몰랐기 때문입니다.

RAM 을 바꿔 직접 확인한 것:

- 프리셋 12(古井戸): 최근 이벤트 값 목록에 `0x3EF` 를 넣자(`0x020ED308`, 수 1) `+00` = 1007 인 레코드 64·65 만 남음(우선순위 7 이 13 보다 앞섬).
- 프리셋 13(caf1, 낮): 시간대 `0x020CE1B4` 를 1(아침)로 두자 밤 문장(500031·500033)만 남음. 古井戸(시간 0 레코드뿐)는 그대로.
- 프리셋 13: 직전 대화 값 `0x020ED33C` 를 0·1·2·6·7·9 로 두자 `+1C` 가 그 값인 레코드(우선순위 6)가 뽑힘.
- 프리셋 12 에서 「はなす」를 되풀이하자 들은 문장 목록이 501027 → 501025 → 501033 으로 늘고, 그때마다 그 문장이 통과 목록에서 빠졌습니다. 말한 횟수(`+1A8`)가 3 이 된 뒤에는 통과 목록이 비었습니다. 고르는 순서는 난수라 같은 세이브스테이트에서도 실행마다 같다는 보장은 없습니다(이번 실행은 501027 부터).
- 프리셋 16(湖の塔 지하)에 최근 이벤트 값 1101 을 넣고 말하자 레코드 160(`+1A` = 211)이 나왔습니다. 「えぐえぐっ…」「でも もう助かったんだよね…」 두 줄 뒤 はい/いいえ 를 물었고, はい 면 501406, いいえ 면 501407 이 떴습니다.
- 프리셋 94(4장)에서 `mhout` 으로 옮기고 직전 대화 값을 4 로 두자 레코드 104(`+1A` = 18203, マーニャ)만 통과했습니다. 통과 항목의 `+14` 가 8(ミネア)이었고, 화면에는 マーニャ 두 줄과 ミネア 한 줄, 모두 세 줄이 떴습니다.
- 앞 일지에서 「고른 메시지 번호」로 읽은 `0x020ED2B4` 는 들은 문장 목록의 첫 칸이었습니다. 처음 말한 직후에는 두 값이 같아 화면 대조가 맞았습니다.

## 이벤트 스크립트가 부르는 대사

`SCRIPT/<맵>.bin` 의 4바이트 정렬 u32 가운데 대사 파일 번호 범위(MPT0 머리 `+08`~`+0C`)에 드는 값을 파일별로 세면, 맵과 대사 파일이 이어집니다(`scripts`). 명령 형식을 풀지 않은 근사치이지만, 6장·이민 마을처럼 대사 파일이 장소별로 나뉜 곳은 장소를 바로 알려 줍니다. 결과는 [extras.md](extras.md#6장-맵과-이벤트) 에 있습니다.

## FC 와 대조

`items`·`monsters` 는 이름(히라가나·가타카나, 작은 가나 차이 무시)으로 먼저 짝을 찾고, 이름이 없으면 가게 값(아이템)이나 경험치·HP·공격·수비(몬스터)가 같은 것을 찾습니다. FC 폰트에 작은 가나가 없어 FC 이름은 `イエテイ` 처럼 적혀 있으므로, [glossary-table.md](glossary-table.md) 의 「FC 에 같은 이름 없음」 가운데 몬스터 5개(イエティ·アークバッファロー·フェイスボール·フェアリードラゴン·ガーディアン)는 표기 차이일 뿐입니다.

## 남은 것

- 동료 대화: 직전 대화 값·최근 이벤트 값·`0x020B91C8` 를 쓰는 쪽의 뜻. 플래그 B·C 는 맵 안 임시 플래그로 확인했고, 스크립트 명령 `0x17`·`0x18` 의 종류 1·2 가 켜고 봄.
- 얻는 물건: `FMAP` 에 짝이 없는 종류(`2C` 등)가 놓이는 자리, `+15` 플래그(`0x020CE358`).
- 몬스터 내성 값 1·2 의 효과(피해 주문 メラ 에서는 차이 없음), `+28`~`+2E`·`+36`~`+3B`, 행동 번호 체계.
- 가게: 맵 키 목록에 없는 레코드(first 18)의 쓰임.

| 객체 `+0x8C`·`+0x90` | `0x02140900`·`0x0214124C`(오버레이 0), `0x0215A77C`·`0x0215B0C8`(오버레이 1) | `map_common_param`·`map_field_symbol` | 같음. 맵·필드 오버레이가 자기 객체에 넣음(`0x0213ED0C`·`0x02129628`) |

`param_map_common_list` 는 사본도 이름도 없어 게임이 쓰지 않는 것으로 봅니다. 레코드 1,010개가 [얻는 물건 표](#얻는-물건-표)와 같은 24바이트 꼴(머리 값도 `32 BC 00 00` 으로 같음)이고, 물건 번호 3000~4801 이 모두 맵별 `param_item_*` 에 있습니다. 899개는 맵별 파일의 레코드와 바이트가 같고, 111개는 `+12` 열었음 플래그 번호만 다릅니다. 맵별 파일을 모은 개발용 목록으로 보입니다.

같은 형식의 파일은 머리 값이 같습니다. `param_item_*`·`map_common_list` `0xBC32`, `map_tile*`·`seatile`·`gottile`·`yamitile` `0x18C`, `param_player_talk*` `0x0E7C60`, `param_player_event*` `0xEA9C` 입니다. 레코드 수와는 맞지 않아 형식 표지로 봅니다.

### 조우 구역

필드 구역 지도는 FC 와 같은 16×16 칸 지도입니다. 값이 없는 칸은 `FF` 이고, FC 에서 구역이 있던 바다 칸 상당수도 `FF` 입니다([FC 조우 표](../../../fc/dq4/docs/dq4-encounter-format.md#필드-구역-지도)). 칸은 필드 좌표 x·z(fx32)의 위 4비트(`>> 20`)이고, 값은 FC 구역 번호 그대로입니다.

| 파일 | 크기 | 쓰는 곳 | FC 와 견주기 |
| --- | --- | --- | --- |
| `map_tile1` | 16×16 | 1·2·4장 | FC 1·2·4장 지도(`18:$A4BD`). 둘 다 값이 있는 66칸 중 64칸이 같음 |
| `map_tile2` | 16×16 | 3장 | FC 3장 지도(8줄). 둘 다 값이 있는 23칸이 모두 같고, 아래 8줄은 `FF` |
| `map_tile3` | 16×16 | 5·6장 | FC 5장 지도의 bit5-0. 둘 다 값이 있는 183칸 중 177칸이 같음 |
| `map_seatile` | 16×16, 값 0~3 | 지도 값이 `FF` 인 칸과 바다 위 | FC 5장 지도 bit7-6(네 바다)과 256칸 중 251칸이 같음 |
| `map_gottile` | 4×4, 위 줄 `35`·나머지 `34` | 필드 1 | FC 「필드 1 은 Y < 0C 이면 구역 35, 아니면 34」 |
| `map_yamitile` | 3×3, 모두 `36` | 闇の世界 | FC 필드 3 구역 36 |

고르는 코드는 `0x0200A8C4`(Thumb)입니다. 장 번호(객체 `+0x10`)로 표를 고르고(1·2·4 → tile1, 3 → tile2, 5·6 → tile3, 0 은 없음), 값이 `FF` 이거나 객체 `+4` 가 1 이면 seatile 을 읽습니다. 폭은 `0x0208A6A0`~`0x0208A6DC` 의 상수(16·4·3)입니다. FC 는 배 위 구역이 늘 `00` 이었지만([FC 조우 표](../../../fc/dq4/docs/dq4-encounter-format.md#배)), DS 는 네 바다를 구역 0~3 으로 씁니다.

실측: 1·3·5장 세이브스테이트에서 필드의 칸 10곳씩(무작위)에 주인공을 두고 조우 레코드 번호 `0x020C4CE0` 을 읽었습니다. 30곳 중 24곳이 위 규칙(지도 값, `FF` 면 seatile)과 같았고, 나머지 6곳(1장 1, 5장 5)은 지도 값이 있는데도 seatile 값이 나왔습니다. 그 칸이 바다라 객체 `+4` 가 켜진 것으로 보지만, 칸의 지형은 확인하지 않았습니다.

- `map_floor` `+21`~`+26` 중 조우(`0x200`)·조명(`0x1`) 말고 맵 속성 비트의 뜻. 맵 종류별 통계만 봤습니다.
