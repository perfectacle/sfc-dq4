# NDS DQ4 이벤트 스크립트

`data/data/SCRIPT/<맵 이름>.bin`(396개)은 맵마다 하나 있는 이벤트 스크립트입니다. 맵에 놓이는 인물, 말을 걸었을 때의 대사, 연출, 맵 이동, 전투, 이야기 깃발을 모두 이 파일이 정합니다. 도구는 [ndsscript.py](../tools/ndsscript.py)이고, 찾은 과정은 [2026-10-25-11 일지](../journal/2026-10-25-11-script.md)에 있습니다.

```sh
uv run --locked python nds/dq4/tools/ndsscript.py tree work/nds/jp/data/data/SCRIPT/caf1.bin
uv run --locked python nds/dq4/tools/ndsscript.py dump work/nds/jp/data/data/SCRIPT/ev03.bin work/nds/jp
uv run --locked python nds/dq4/tools/ndsscript.py ops work/nds/jp/arm9.bin work/nds/jp/data/data/SCRIPT
```

주소는 ARM9 주소입니다. `arm9.bin` 은 압축되지 않아 파일 오프셋 + `0x02000000` 이 주소이고, `0x0211D540` 부터는 마을 장면에서 실리는 `overlay_0000` 입니다.

## 블록

모든 층이 같은 블록 꼴입니다.

| 위치 | 뜻 |
| --- | --- |
| `+00` | 이름 16바이트(`script`, `scriptgroup`, `scriptobject`, `initialize`, `execute`, `terminate`) |
| `+10` | 칸 수 N |
| `+14` | 머리 크기 = 0x20 + 표 크기 |
| `+18` | 표 크기 = N × 8 을 16 의 배수로 올림 |
| `+1C` | 0 |
| `+20` | 칸마다 (오프셋, 크기) u32 쌍. 오프셋은 블록 시작 + 머리 크기 기준 |

`script` 는 칸이 10개(`za1f1.bin` 만 7개)이고 칸마다 `scriptgroup` 하나입니다. `scriptgroup` 은 `scriptobject` 를 1~43개 가집니다. **칸 번호는 장 번호입니다.** 마을 장면을 준비하는 코드(`overlay_0000` `0x0212E734`)가 장 번호 `[0x020EB9A4 + 4]`(`0x020EB9A8`)를 `0x0201EFF4` 에 넘기고, 이 함수는 6 을 5 로 바꿔 둔 뒤 `SCRIPT/<맵 이름>.bin` 을 읽어 그 칸의 `scriptgroup` 하나만 해석기에 싣습니다(`0x0205A8B8` → `0x0207D8C0`). 1~5장은 칸 1~5, 6장은 칸 5 입니다. `caf1` 의 인물이 칸 1(1장)과 칸 5(5·6장)에 모여 있는 것도 이 때문입니다.

| 칸 | 실리는 때 | 명령이 있는 파일 |
| --- | --- | --- |
| 0 | 장 번호 0. 서장 세이브스테이트도 장 번호가 1 이라 본 적 없음 | 11 |
| 1~4 | 1~4장(서장 포함 1) | 168·58·51·49 |
| 5 | 5장과 6장 | 367 |
| 6~9 | 실리지 않음(호출자가 하나뿐이고 6 은 5 로 바뀜). 칸 6 에는 6장 대사(152xxx·155xxx)가 있으나 쓰이지 않는 자료로 보임 | 123·3·3·14 |

확인: 장 시작 세이브스테이트 8개(서장·1~6장·6장 ピサロ)에서 RAM 의 함수 문맥이 가리키는 그룹이 서장·1장 1, 2~5장 2~5, 6장 둘 다 5 였습니다.

확인: 396개 파일 전부 이 규칙대로 읽힙니다(오브젝트 7,592개, 함수 22,776개, 명령 55,478개).

### 오브젝트

`scriptobject` 는 칸 4개입니다. 0x30바이트 머리, `initialize`(맵에 들어올 때), `execute`(맵에 있는 동안), `terminate`(맵을 나갈 때) 함수입니다(함수 이름의 뜻은 이름과 쓰임에서 짐작).

| 머리 위치 | 뜻 |
| --- | --- |
| `+04` | 인물 모습 번호. 대부분 `CHR/hNNN.pack` 번호와 겹침(174가지 중 158가지가 있는 팩 번호) |
| `+08` | 방향 0~3 |
| `+0C`·`+10`·`+14` | x·y·z(s32, 4.12 고정소수, 4096 = 1.0) |

모습 번호는 대사의 화자 이름과 맞습니다. 메시지를 부르는 오브젝트의 모습별 화자를 세면 `0x00` 男 114, `0x01` 女 77, `0x03` おばさん 135, `0x05` 老人 105, `0x0F` 兵士 174, `0x11` 衛兵 75 처럼 한 가지 이름으로 몰립니다. 대사 `@a` 인물 번호와의 관계는 [text-format.md](text-format.md#인물-번호-a)에 있습니다.

### 함수

함수 블록은 칸 3개입니다.

1. 명령마다 깊이 1바이트.
2. 명령 시작 오프셋 u32 표. 명령 수 + 1 개이고 마지막 값이 코드 크기입니다(비어 있지 않은 함수 5,673개 모두).
3. 코드. 명령은 u32 하나(아래 16비트 명령 번호, 위 16비트 상태 비트)와 그 뒤 번호마다 정해진 수의 u32 인자입니다. 명령 번호마다 인자 수가 하나로 정해져 있고, `0x0A`·`0x0B`·`0x0E`·`0x36` 만 두 가지입니다.

## 실행

### 깊이와 조건

깊이 바이트가 명령을 나무로 묶습니다. 어떤 명령 뒤에 깊이가 하나 큰 명령들이 오면 그것이 자식이고, 명령이 참을 돌려줄 때만 자식을 실행합니다. 조건 명령(`0x18` 등)은 결과를 돌려주고, 일반 명령은 언제나 참을 돌려주므로 자식을 그대로 이어서 실행합니다. 나무를 만드는 쪽은 `0x0205A3A8`·`0x0205A3DC`·`0x0205A418`(노드 5바이트: 깊이, 부모, 첫 자식, 다음 형제), 명령 하나를 실행하는 쪽은 `0x0205A2B0` 입니다(코드 읽기).

실측: 1장 왕좌의 방(`caf1`)에서 왕에게 말을 거는 자리는 아래 꼴입니다. 부모 조건 `0x18 2 7 1` 을 다른 조건(`0x18 2 7 0`, `0x19 1`·`0x19 3`)으로 RAM 에서 바꾸니, 조건이 참이면 이 대사(메시지 28~30)가 나오고 거짓이면 다른 가지의 대사가 나왔습니다.

```
018 깃발이면: 맵[7]=1
  04A 말을 걸면
    006 대사 목록(마을): 28 29 30
```

이야기 연출은 대부분 「맵 깃발 N 이면 → 명령들 → 깃발 N 끄기, 깃발 N+1 켜기」를 여러 오브젝트에 나눠 적은 상태 기계입니다. 한 오브젝트가 깃발을 넘기면 다음 차례의 오브젝트가 이어받습니다([6장 이벤트](#6장-이벤트)).

### 명령 번호와 처리 함수

명령 함수 `0x0201FDA8` 이 명령 번호(u16)를 읽어 `0x0201FDC0` 의 `addls pc, pc, r2, lsl #2` 로 분기표에 들어갑니다. 분기표는 `0x0201FDC4`(범위 밖 번호가 가는 기본 칸) 뒤 `0x0201FDC8` 부터 명령 0~`0x177` 의 ARM `b` 명령 0x178칸입니다(`ndsscript.py ops`). 처리 칸은 거의 모두 「상태 비트 검사 → 인자 주소(명령 + 4)를 넘겨 함수 호출 → 결과를 참·거짓으로」 꼴입니다.

- 쓰이는 명령 번호는 306가지입니다. 28가지는 기본 칸으로 가는 빈 번호이고 스크립트에 나오지 않습니다.
- 처리 칸이 부르는 것은 Thumb 함수 226칸, ARM 함수 11칸, 여러 프레임에 걸치는 객체 108칸입니다(나머지 33칸은 기본 칸·공통 끝). 함수는 ARM9 안에 있거나 마을 오버레이 `overlay_0000`(`0x0213xxxx`, 마을 장면에서만 실림)에 있습니다. 객체는 `0x02023290` 이 객체의 시작·갱신·끝났나·끝 함수를 차례로 부릅니다.

### 상태 비트

명령 낱말의 위 16비트는 파일에서 0·1·3 이고, 실행 중에 같은 바이트(`+2`)를 게임이 고쳐 씁니다(코드 읽기).

| 비트 | 뜻 |
| --- | --- |
| `0x01` | 여러 프레임 명령. 처음 실행 때 `0x10` 을 켜고 시작 함수를 부르며, 끝나면 `0x40` 을 켬. 일반 명령도 이 비트가 있으면 `0x40` 이 켜진 뒤에는 다시 실행하지 않음(`0x0201FD80`) |
| `0x02` | 되풀이. 나무 걷기(`0x02059A58`)가 형제 목록의 마지막 명령을 끝냈을 때 그 명령의 `0x02` 를 보고(`0x0205A368`), 켜져 있으면 목록 처음으로 돌아가 형제 모두의 `0x10`·`0x40` 을 지움(`0x0205A318`). 그래서 한 번만 도는 명령들이 다음에 부모가 참이 되면 다시 돔 |
| `0x10`·`0x40` | 실행 중 상태. 함수를 다시 시작할 때 `0x0205A318` 이 지움 |

파일의 상태 비트는 `execute` 의 연출 명령에 주로 붙습니다(`0x17` 은 0 이 1,585번, 1 이 3,820번, 3 이 1,104번). `0x02` 는 늘 `0x01` 과 함께(값 3) 붙고, 1,664개 중 1,662개가 형제 목록의 마지막 명령이며 모두 `execute` 에 있습니다. 연출의 끝 `017.3 깃발 쓰기: 맵[n]=0` 이 대표입니다.

실측(`caf1`, 아래 「확인 방법」의 주입): 형제 목록 마지막 자리에 `0x13 1 0`(돈 1 더하기)을 상태 1 로 넣으면 60프레임 동안 한 번, 상태 3 으로 넣으면 56번 더해졌습니다.

`0x01` 이 켜진 명령은 끝난 뒤(`0x40`)에는 처리 함수를 부르지 않고 참을 돌려줍니다(`0x0201FD80` 이 0 을 돌려주면 처리 칸이 기본값 참으로 끝남). 그래서 상태 1 인 조건 명령은 처음 한 번만 검사하고, 그 뒤로는 거짓이었어도 자식을 실행합니다(실측: `18 2 50 1` 을 상태 0 으로 넣으면 자식이 돌지 않고, 상태 1 로 넣으면 다음 프레임부터 자식이 돎).

## 깃발

`0x17`(쓰기)·`0x18`(검사)의 첫 인자가 깃발 종류, 둘째가 번호, 셋째가 값입니다. 종류마다 1024비트 배열이고, 비트 위치는 `[(번호 >> 5) × 4]` 낱말의 `번호 & 31` 비트입니다(`0x0201D644` 읽기, `0x0201D60C`·`0x0201D628` 켜기·끄기).

| 종류 | 배열 | 쓰임 |
| --- | --- | --- |
| 0 | `0x020CE7DC` | 이야기 깃발. 진행도 프리셋이 이 배열을 채움([debug.md](debug.md)). 6장 단계 깃발 `0x1A4`(6장 시작)·`0x1AA`·`0x1AB`·`0x1AF`(ピサロ 동료)를 장 시작 세이브스테이트에서 읽어 확인 |
| 1 | `0x020CE75C` | 장소 깃발. 맵 이름 앞 두 글자가 바뀌는 이동에서만 지워짐. 같은 마을·성·던전(같은 머리글자)의 층·건물 사이를 오가는 동안 남음. 장 시작 세이브스테이트 8개에서 모두 0(쓰기 482번, 검사 821번) |
| 2 | `0x020CE6DC` | 맵 깃발. 맵에 들어갈 때마다 지워짐 |

종류 0 의 번호 `0x2A` 미만을 켤 때는 다른 표(`0x020321D4`)에도 적습니다(코드 읽기, 뜻 모름).

종류 1·2 를 지우는 곳은 마을 장면 준비(`0x0212E8D0`)입니다. 종류 2 는 언제나 `0x0201D660` 으로 지우고, 종류 1 은 `0x0200B8E0(0x020C4EAC)` 가 0 이 아닐 때만 지웁니다. 이 함수는 앞 맵 이름(`[0x020C4EAC + 0x78]`)과 지금 맵 이름(`+0x98`, 곧 `0x020C4F44`)의 첫 두 글자를 견줘 같으면 0 을 돌려줍니다.

실측: `caf1` 에서 종류 1·2 의 첫 낱말을 `0xF0F0` 으로 쓰고 맵 이동 명령 `0x1F` 를 주입했습니다. `caf2b`·`caout`·`ca1f1` 로 가면 종류 1 이 남고 종류 2 가 0, `cbout`·`ccout` 으로 가면 둘 다 0 이었습니다. `ndswarp.py map` 처럼 맵 이름을 직접 써서 옮기면 앞 맵 이름이 바뀌지 않아 이 비교를 볼 수 없습니다.

## 명령

### 확인 방법

1장 왕좌의 방에서 왕에게 말을 걸기 직전에, 왕의 대사 명령 자리(`06 1C 1D 1E 0 0 0 0 0`, 9낱말)를 시험할 명령으로 RAM 에서 덮어쓰고 A 를 눌렀습니다. 명령마다 스크립트에서 가장 많이 쓰인 인자 그대로 넣고, 20·80·200 프레임 뒤 화면과 깃발 배열·맵 이름·장면 번호·주인공 자리·돈을 비교했습니다. 인자가 9낱말을 넘는 `0x00`·`0x1F` 를 뺀 304가지를 돌렸고, 에뮬레이터가 멈춘 것은 없었습니다.

이 방법으로 보이는 것은 「이 장면에서 한 번 실행했을 때 눈에 띄는 변화」뿐입니다. 다른 오브젝트·조건이 있어야 하는 명령은 변화가 없어 뜻을 정하지 못했습니다.

말을 걸 인물이 없는 곳에서는 다른 방법을 씁니다. 해석기는 명령을 실행할 때마다 RAM 의 오프셋 표를 읽습니다(`0x0205A2B0` 이 `[객체 + 0x2AC]` 의 오프셋과 `[객체 + 0x2B0]` 의 코드 시작을 더함). 그래서 `execute` 의 맨 위 명령 하나의 오프셋 칸을 빈 RAM(`0x0236B000`)을 가리키게 고치고, 그 자리에 상태 비트 1 을 켠 명령을 두면 맵에서 저절로 한 번 실행됩니다. 이 방법으로 필드(5장 상태, 필드 칸 (100, 100))와 이민 마을(`ss1out`)에서 같은 304가지를 다시 돌렸고, 상태 바이트에 끝남 비트(`0x40`)가 켜질 때까지의 프레임으로 기다리는 명령의 길이도 쟀습니다.

이번에는 같은 방법을 넓혀 썼습니다.

- **RAM 전체 비교**: 1장 왕좌의 방(`caf1`)에서 조작할 수 있게 된 상태로, 제어 오브젝트(그룹 1 오브젝트 0) `execute` 의 맨 위 명령을 쓰인 306가지로 하나씩 바꿔 240프레임 돌린 뒤 4MB 메인 RAM 을 기준 실행(해 없는 깃발 쓰기)과 비교했습니다. 15% 넘는 명령에서 함께 바뀐 곳(인물 움직임 등)은 뺐습니다. 맵 비트·시간대·장 번호·일행 값처럼 이름이 붙은 RAM 이 바뀐 것은 따로 값을 넣어 다시 쟀습니다.
- **조건**: 맨 위 명령 자리에 조건을 상태 0 으로, 그 자식 자리(깊이 1)에 맵 깃발 `0x50` 쓰기를 넣으면, 조건이 참일 때만 깃발이 켜집니다. `18 2 50 1`(거짓)·`18 2 50 0`(참)으로 틀을 확인한 뒤, RAM 값을 바꿔 가며 조건 명령의 참·거짓을 쟀습니다.
- **인물 명령**: 인물 오브젝트의 `execute` 에 넣어야 그 인물에게 듣습니다. `caf1` 오브젝트 6(병사, 모습 `0x11`)의 `execute` 맨 위에 넣고 30프레임 뒤 아래 화면을 기준과 비교했습니다.
- **처리 함수 읽기**: 분기표 칸마다 처리 함수(객체면 vtable 의 시작·갱신·끝났나·끝)를 capstone 으로 읽어, 부르는 함수와 리터럴 RAM 주소를 뽑았습니다. 부르는 함수 대부분은 싱글턴을 돌려주는 함수(정적 지역 초기화 꼴)라 그 싱글턴으로 묶었습니다: 인물 관리자 `0x0214D5D0`(`0x0213433C`), 주인공 `0x0214B728`(`0x0212EEA0`), 카메라 `0x0214CEE4`(`0x02132098`), 창 관리자 `0x0214D188`(`0x021336F8`), 맵 관리자 `0x0215B428`(`0x02135A78`). 객체 명령의 객체는 BSS 에 있는 C++ 객체라 vtable 은 RAM 에서 읽었습니다.

### 전투 안

전투 중에는 맵 스크립트가 돌지 않습니다. `caf1` 에서 `78 1 0` 으로 전투를 연 뒤(장면 `0x0D`), 그리고 `ndswarp.py battle` 의 전투 테스트에서, 주입 칸을 `0x13`(돈 더하기, 상태 1)으로 바꾸고 120~180프레임을 돌렸지만 상태 바이트가 `0x01` 그대로였고 돈도 그대로였습니다. 스크립트 파일과 함수 문맥은 RAM 에 남아 있습니다. 전투 중 `0x0211D540` 에는 마을 오버레이 0 대신 오버레이 3 이(`0x02166CA0` 에는 16 대신 15), 실려 있어 `0x0213xxxx` 의 처리 함수도 없습니다. 전투 안에서만 뜻이 있는 명령은 없고, 전투와 이어지는 것은 전투를 여는 `0x78`·`0x10E`·`0x164`, 조우 객체를 고치는 `0x3E`, 전투 뒤 값을 보는 `0x41` 입니다.

### 명령 표

분기표가 있는 번호 347가지(처리 없는 28가지와 `0x01` 제외)를 처리 함수가 부르는 함수·읽고 쓰는 RAM 으로 나눴습니다. `ndsscript.py ops` 가 같은 분류 열을 찍습니다. 근거: **실측** 주입 실험·RAM 실험, **코드** 처리 함수를 끝까지 읽음, **스크립트** 쓰인 자리와 인자에서 읽음, **분류** 처리 함수가 부르는 대상만 읽어 묶음(뜻은 정하지 않음). 「인자」 는 스크립트에서 본 인자 수입니다.

인물 쪽 명령은 모두 「지금 실행 중인 오브젝트」의 인물에게 듣습니다(`0x020234D4` 가 함수 문맥의 오브젝트 번호를 돌려주고, 인물 관리자 `+4` 의 배열에서 그 번호의 인물 객체를 꺼냄). 인물 객체(vtable `0x02144B08`)는 `+0x164` 의 인물 그림 객체(`0x02048xxx`)에 일을 넘기고, 그림 객체의 `+0xC8` 비트(1 보이기, 4·0x10·0x40·0x100)를 켜고 끕니다.

### 가게

`0x98` 의 인자는 가게 종류입니다. 1장 왕좌의 방에서 인자 0~`0x1C` 를 하나씩 넣어 첫 대사를 봤습니다.

| 인자 | 가게 | 인자 | 가게 |
| --- | --- | --- | --- |
| 0 | 여관 | 8 | 무기점(둘째. 레코드 칸 26~31, 밤 무기점) |
| 1 | 교회 | 9 | 방어구점(둘째. 칸 32~37) |
| 2 | 무기점(칸 0~5) | `0xA` | 도구점(둘째. 칸 38~43) |
| 3 | 방어구점(칸 6~11) | `0xB` | 코인 교환소(둘째. 칸 44~49) |
| 4 | 도구점(칸 12~17) | `0xC` | 카지노 코인 판매 |
| 5 | 코인 교환소(칸 18~23, 경품) | `0xF` | 격투장 |
| 6 | 여관(둘째. 칸 24~25 의 값) | `0x11` | メダル王 |
| 7 | 교회(둘째) | `0x10` | 은행(「1000ゴールド単位」) |
| | | `0x12` | 약초 사고팔기(「やくそう ですね」) |
| | | `0x13`·`0x18` | 팔기 목록 |
| | | `0x16` | アリーナ 약초 대사(「アリーナ姫は やくそうを 持っていない」) |
| | | `0x17` | 인질로 맡길 동료 고르기 |
| | | `0x19` | 장 이름 「序章」만 뜸 |
| | | `0x1A` | 모험의 서에 기록 |
| | | `0x1B` | 카지노 장면 `0x0F`, 코인이 없다는 대사 |
| | | `0x1C` | 무기를 사러 온 손님(3장 무기점 일, `mfw1f1` 에서 9번) |

`0x10`~`0x1C` 는 5장 상태로 `hcy1b1` 에 들어가 돈을 50000G 로 하고 주입해 봤습니다(1장 왕좌의 방 결과와 겹치는 것은 같음). `0xD`·`0xE`·`0x14` 는 두 곳 모두 화면이 검게 남고, `0x15` 는 바로 끝났습니다. 스크립트에 쓰인 인자는 0~6, 8~`0xC`, `0x10`, `0x11`, `0x1C` 뿐이라, 반응이 없는 넷은 어떤 스크립트도 쓰지 않습니다. 칸 번호는 [param-format.md](param-format.md) 의 가게 레코드 칸이고, 「둘째」 가게의 칸은 아래 코드에서 읽었습니다.

가게 레코드는 맵 이름으로 고릅니다(코드 읽기, 함수는 unicorn 으로 실행해 표를 뽑음).

1. 표: `0x020CE3EC` 가 0 이면 first, 1 이면 second 표(장 번호가 4 보다 크면 1). 표 주소 `0x020CE3F0`·`0x020CE3F4` 는 `arm9.bin` 안의 `0x020945F8`·`0x02099A30` 을 가리킵니다(실측). first 는 `PARAM/param_map_shop_first.dat` 와 바이트가 같고, second 는 레코드가 36개로 PARAM 파일(30개)보다 6개 많고 레코드 6 의 여관 값 하나가 다릅니다. 게임은 `arm9.bin` 의 표를 씁니다.
2. 레코드 번호: `0x0201D2BC` 가 지금 맵 이름(`0x020CE104`) 앞 두 글자로 키(첫 글자 × 100 + 둘째 글자, `ss` 로 시작하면 셋째 글자까지)를 만들고, `0x0200CCCC`(first)·`0x0200CB10`(second)가 레코드 × 52 로 바꿉니다. 목록에 없는 맵은 레코드 0 입니다. `[0x020CE214]` 가 1 이면 맵 이름 대신 `en` 을 키로 씁니다. `en` 은 first 의 레코드 18(여관 10G, 도구점 `0x6F`~`0x72` 4가지, 무기·방어구 없음), second 의 레코드 0 입니다(unicorn 으로 두 함수를 실행).

| 표 | 맵 머리글자 → 레코드 |
| --- | --- |
| first | `ma` 1, `mb` 2, `mc` 3, `md` 4, `me` 5, `sb` 6, `hc` 7, `cc` 8, `tb` 9, `mf` 10, `mg` 11, `cd` 12, `mh` 13, `mi` 14, `ce` 15, `mj` 16, `mk` 17, `en` 18, 나머지 0 |
| second | `hc` 1, `sb` 2, `cd` 3, `mf` 4, `se` 5, `mm` 6, `mn` 7, `mo` 8, `cg` 9, `mj` 10, `mk` 11, `mi` 12, `mh` 13, `hh` 14, `mb` 15, `mc` 16, `md` 17, `tb` 18, `ma` 19, `ha` 20, `mq` 21, `mp` 22, `ci` 23, `td` 24, `sh` 25, `ms` 26, `ck` 27, `sm` 28, `dp` 29, `mr` 30, `ss1`~`ss5` 31~35, 나머지 0 |

3. 칸: 레코드는 4바이트 칸 52개(칸 0 여관 값, 칸 1 교회, 칸 2~ 가 품목 0~)이고, 종류 0~11 이 칸 시작 +0·+1·+2·+8·+`0xE`·+`0x14`·+`0x1A`·+`0x1B`·+`0x1C`·+`0x22`·+`0x28`·+`0x2E` 로 갑니다(`0x0201D2BC` 끝의 분기). 품목은 `0x0201D4FC`, 값은 `0x0201D524` 가 읽습니다.

확인: 1장 왕좌의 방(`caf1`)에서 맵 이름 칸 `0x020CE104` 를 바꾸고 무기점을 열었습니다. `caf1` 은 레코드 0 의 こんぼう·どうのつるぎ·せいなるナイフ·くさりがま 4개, `mbf1` 은 레코드 2 의 앞 3개, `ccf1` 은 무기 칸이 빈 레코드 8 이라 빈 목록이 나왔습니다. 세 레코드의 무기 칸과 같습니다. `maout`(イムル)의 무기점 주인에게 직접 말을 걸면 first 1 의 품목이 나온다는 실측([param-format.md](param-format.md))도 `ma` → 1 과 맞습니다.

## 6장 이벤트

6장 맵의 스크립트를 위 명령으로 읽은 것입니다. 단계 깃발은 이야기 깃발(종류 0)이고, 맵 깃발은 그 맵 안의 연출 차례입니다. 6장 상태 세이브스테이트(프리셋 310·331)의 깃발 값은 「깃발」 절에 적었습니다.

### 6장 단계 깃발

| 깃발 | 켜는 곳 | 뜻(스크립트 읽기) |
| --- | --- | --- |
| `0x1A4` | `ckout`(天空城 밖) `terminate` 의 「`0x182` 이 1 이고 `0x10 106A` 일 때」, `mlb1a`(산골 마을 지하) | 6장 시작. 프리셋 310 에서 1 |
| `0x1AA` | `tdf5`(世界樹 꼭대기) | 世界樹の花 를 얻음으로 보임 |
| `0x1AB` | `mqout`(ロザリーヒル) | ロザリー 에게 꽃을 쓴 뒤로 보임. `srout` 의 가지가 이 깃발로 5장 결전(0) / 6장(1)으로 갈림 |
| `0x1AD` | `srout`(山) | 쓰러진 デスピサロ 앞 → 회상(`ev03`)으로 |
| `0x1AE` | `ev03` | 회상이 끝나 山 으로 돌아옴 |
| `0x1AF` | `srout` | ピサロ 가 동료가 됨. 프리셋 331 에서 1 |

### 山(`srout`)

`srout` 은 5장 결전과 6장 합류를 한 파일에 담습니다. 6장 쪽 차례입니다.

1. 이야기 `0x1AB`=1, `0x1AE`=0: 자리 조건으로 보이는 `0x0A` 가 맵 깃발 `0x14` 를 켬 → 조작 잠금, 주인공 걷기, `0xB6`(카메라), 목소리 지정 `3 3 3 3 3 1`, 「デスピサロ「ぐはあ…」」(메시지 154003~) 6쪽.
2. 맵 깃발 `0x15`: デスピサロ(모습 `0x87`)가 보이고 걸어와 「ぐ…ぐ…」(154013~) 뒤 효과음, 화면 어둡게, 이야기 `0x1AD`=1, `ev03` 으로 맵 이동.
3. `ev03` 에서 돌아온 뒤(이야기 `0x1AE`=1): 맵 깃발 `0x2C` → `0x2D` → … `0x31` 을 오브젝트 사이에서 넘기며 ピサロ「…………！」(154069~), 「世界樹の花……」(154074~), 「……人間たちよ。」(154075~) 뒤 `0x142`, `0x64 4 18`(오브젝트 4 의 인물을 숨기고 인물 `0x18` 을 일행에 넣음), 마지막에 이야기 `0x1AF`=1(동료).

5장 쪽(이야기 `0x1AB`=0)은 デスピサロ「ぐはあ」(129003~) 뒤 `0x10E 1 B9 4 2 A 2` 전투, デスピサロ（完全体）(129021~)입니다.

### 꿈과 회상(`ev03`)

ロザリー·ピサロ 장면 두 개를 한 맵에 담습니다. `initialize` 가 이야기 `0x1AD` 로 갈라, 0 이면 5장 イムル 여관 꿈(대사 `b0118`, 맵 깃발 1~`0xC`), 1 이면 6장 회상(대사 `b0154`, 세피아 화면 `0xC9` 와 맵 깃발 `0x14`~`0x1D`)을 놓습니다. 오브젝트 9개가 맵 깃발을 넘겨받습니다.

1. 맵 깃발 1~6: 사내들(모습 `0x12`·`0x0B`·`0x0C`)이 ロザリー 를 몰아붙임. 「さあ 泣け！」(118509~), 효과음 403, 「う… うう……。」.
2. 맵 깃발 7: ピサロ(모습 `0x7F`)가 y 6 → 2 → 1.2 로 내려와 「ロザリー！」(118518), 맵 깃발 `8`·`9`·`0xA`·`0x64` 를 한꺼번에 켬 → 인간들이 밀려남(`0x2E`), 화면 색 `0xA8 1F 1F 1F 28 489`, 효과음 555.
3. 맵 깃발 `0x0B`·`0x0C`: ピサロ·ロザリー 대화(118531~), 화면 어둡게 뒤 이야기 `0x15A`=1·`0x15B`=0, `may1f1`(イムル 여관)로 맵 이동.
4. 맵 깃발 `0x14`~`0x1D`(6장 회상 쪽): ロザリー 를 쫓는 사내(모습 `0x43`)가 두리번거림(`0x4E` 를 0·3·2·1 로), 「!」(`0x51 C9`), 「う…うわああっ！！」(`0x15`, 60프레임), ピサロ 가 다시 내려와 「あぶないところだったな。」(154039), 대화 뒤 이야기 `0x1AE`=1, `srout` 으로 돌아감.

### ゴットサイド 아래 お楽しみダンジョン(`dpout`, `dpb*`)

`dpout` 은 오브젝트 53개, 명령 2,217개로 6장 스크립트 중 가장 큽니다. ニワトリ(메시지 146xxx)와 エッグラ·チキーラ 가 있고, 대결은 `0x10E` 로 엽니다.

- 첫 대결: 묻는 대사 뒤 `0x99`(예·아니오), 효과음 1147, 「エッグラとチキーラ「…」」(146588), `0x10E 1 F3 1 1 1A7 0`.
- 다시 붙기: 이야기 깃발 `0x1B1`~`0x1B7` 을 차례로 검사해 `0x10E 1 F3 n 1 1B0 0` 의 셋째 인자 n 을 2~8 로 고름. 이긴 횟수에 따라 상대가 세지는 7전으로 보입니다.
- 이야기 깃발 `0x1A7`~`0x1A9`, `0x1B0`~`0x1B8`, `0x1E0`, `0x1F8` 을 검사하고, `0x1A7`~`0x1A9`·`0x1B0`~`0x1B8` 을 씀.

`dp` 로 시작하는 맵 29개 중 스크립트가 있는 것은 10개입니다. `dpb1a` 는 `msout`(ゴットサイド)으로 나가는 맵 이동 하나, `dpb5a`·`dpb5ido` 는 老人 의 우물 선물(이야기 `0x1A5`·`0x1A6`), `dpb7c` 는 くさった死体·灯台タイガー 대사, `dpb8a` 는 이야기 `0x1C1` 켜기, `dpb8c` 는 スライム 신부 안내(이야기 `0x29`), `dpb8b` 는 農夫 대사입니다.

## 남은 것

- 「분류」만 한 명령 173가지의 뜻. 처리 함수가 부르는 대상(인물 관리자·주인공·카메라·맵 관리자·일행 함수 등)까지만 읽었고, `caf1` 주입의 RAM 전체 비교에서 이름 붙은 RAM 이 바뀌지 않았습니다. 6장 연출에 많이 쓰이는 인물 이동 객체(`0x2C`~`0x33`·`0x4B`·`0x4C`·`0x5B`), 카메라 객체(`0x24`·`0x29`·`0xB4`·`0xB6`), 주인공 줄(`0xA6`·`0xB0`), 대사 창 객체 `0x142` 가 먼저입니다. 화면 연출이라 인자를 바꿔 가며 같은 오브젝트에 주입해 화면을 비교해야 합니다.
- 인물 그림 객체 `+0xC8` 의 비트 4·`0x10`·`0x40`·`0x100` 과 인물 객체 `+0x38` 의 비트 8·`0x20`·`0x100`·`0x400` 이 화면에서 무엇을 바꾸는지. 그 비트를 읽는 코드를 찾지 못했고, 병사 주입에서는 `0x34`·`0x53`·`0x54` 만 그림이 조금 바뀌었습니다.
- `0x16` 이 보는 인물 표 `0x020C52D4` 의 비트 `0x10000`(일행 인물은 `0x1100`), `0x14` 가 쓰는 `0x020C55F8`, `0x41` 이 보는 `0x020EA39C` 가 무슨 값인지.
- 칸 0 이 실리는 때(장 번호 0 인 상태를 보지 못함)와 칸 6~9 의 자료가 쓰이는지.
- `0x98` 인자 `0xD`·`0xE`·`0x14`·`0x15`. `caf1`·`hcy1b1` 두 곳에서 반응이 없고 스크립트도 쓰지 않습니다.
- `0x020CE214` 를 1 로 쓰는 곳, 곧 가게 키 `en`(first 레코드 18)을 쓰는 장면. 리터럴 `0x020CE200`·`0x020CE214` 와 오프셋 `0x14`·`0x114` 저장을 찾았지만 읽는 곳 둘뿐이었고, 장 시작 세이브스테이트 8개에서 모두 0 입니다.
