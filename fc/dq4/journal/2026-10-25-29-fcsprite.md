# 2026-10-25-29: 원작 필드 인물·몬스터 그림 뽑기

SFC 쪽에서 스프라이트를 새로 그릴 때 옆에 놓고 볼 원작 그림을 롬에서 뽑았습니다. 필드 인물·일행·탈것은 그림 번호마다 4방향 × 걸음 2프레임, 전투 몬스터는 195종 전부를 PNG(1배·8배)와 색 번호 행렬로 내고, 한 페이지로 묶어 이름·번호와 함께 봅니다. 형식은 [dq4-fcsprite-format.md](../../dq4-fcsprite-format.md) 에 있습니다.

## 1. 출발점

[대화 스크립트 일지](2026-10-25-28-talk3.md) 까지 알려진 것은 인물 레코드의 그림 번호, 그 번호를 맵의 그림 표 `$6E5E` 에 넣는 `1C:$9A37`, 새 번호를 BRK `04 87`(뱅크 `08` 함수 4)로 읽는다는 것이었습니다. 함수 4 는 `08:$85D3` 입니다.

```
08:$85F2  $0E = 번호 × 24 → 포인터 $8649 의 워드($979B) 를 더함
08:$8621  LDY #$08 → $864B 를 8번: $80C4(3바이트 읽기) → $80D5(타일 주소) → $8340(타일 번호) → $83BD(CHR 로 복사)
```

`$80C4`·`$80D5` 는 [블록 일지](2026-10-25-16-block.md)에서 푼 블록 모양 레코드와 같은 루틴이고, `$09` = 2 일 때 스프라이트 쪽 갈래(`$8132`)를 탑니다. 레코드 3바이트 × 8 = 블록 8개, 블록은 16×16 의 타일 4장입니다. 갈래를 그대로 옮기니 뱅크 비트(`0D`·`0E`), 모양별 오프셋 표(`$A1D0`), 바이트 1 위 4비트의 좌우 반전, 바이트 2 아래 2비트의 팔레트가 나왔습니다. 결과는 `$7200` + 칸 × 64 에 (타일 번호, 속성) 4쌍씩 쌓입니다(`$82B0`, 포인터 `$833E`).

## 2. 왕좌의 방에서 첫 비교

1장 왕좌의 방 세이브스테이트를 덤프해 `$6E5E` 칸 8개를 흉내 낸 결과와 견줬습니다. 같은 주소를 다시 올리지 않는 규칙(`$8254`, 목록 `$7700`)까지 넣으니 첫 번에 모두 맞았습니다.

```
13 slot4 tab OK chr bad 0 / 12
11 slot5 tab OK chr bad 0 / 20
...
0F slotB tab OK chr bad 0 / 20
party slot 0 matches ['0x6', '0x4e']
```

일행 칸 0 은 그림 번호를 모르니 표 108개 전부를 넣어 보고 같은 것을 찾았습니다. 라이안이 `06`, 2~5장 시작 덤프에서 アリーナ `07`, トルネコ `05`, マーニャ·ミネア `03`·`02`, 주인공 `00` 이었습니다. 직업 이름 순서인 인물 레코드 번호와 같습니다([dq4-save-format.md](../../dq4-save-format.md)). 일행이 없는 칸 1~3 은 늘 `0E`(관)였습니다.

## 3. 돌려 그리기

그림 번호 bit7 이 켜진 인물이 있는 맵(`00/01`, `0A/00`)으로 워프하니 bit7 인 칸만 `$7200` 이 어긋났습니다. `$859B` 가 bit7 을 `$7A` 로 떼어 두고, `$7A` 가 켜져 있으면 레코드 4 하나로 8블록을 만들면서 블록 쌍마다 타일 자리(`$8981`)·반전 비트(`$82D2`)·그림(`$89C9`)을 90°씩 돌립니다. 처음 옮긴 코드는 `C0` 은 맞고 `9C`·`96`·`B7` 이 틀렸는데, 반전 비트를 옮기는 순서를 잘못 적은 것이었습니다(아래 「틀렸던 것들」). 고친 뒤 다섯 가지가 모두 맞았습니다. 그림으로 보면 쓰러진 사람처럼 눕힌 모습입니다.

## 4. 방향과 걸음

블록 j 가 어느 방향인지는 `$7200` 을 읽는 곳을 찾아 정했습니다. 읽기 감시에 `0F:$D878` 하나만 걸렸습니다.

```
0F:$D7F9  LDA $7000,X / ... / AND #$03 → $D869
0F:$D869  ASL ×4, $0526 bit7 이면 +8 → ($7200+칸×64),Y 에서 8바이트
```

블록 = (`$7000` 아래 2비트) × 2 + (`$0526` bit7)이고, 모든 인물이 `$0526` 하나로 같이 걷습니다. 필드에서 주인공을 네 방향으로 걷게 하니 `$7000` = `40`·`41`·`42`·`43` 일 때 블록 0·2·4·6 이었습니다. 0 위, 1 오른쪽, 2 아래, 3 왼쪽입니다.

화면 비교(`check-field`)는 OAM 2×2 묶음의 타일·속성으로 칸과 블록을 찾아, 덤프 CHR 로 그린 16×16 과 롬으로 그린 블록을 픽셀로 견주고, 그 칸을 쓰는 인물의 `$7000` 과 블록 번호도 견줍니다.

## 5. 필드의 탈것

필드 덤프에서는 칸 4 가 `$6E5E` 와 맞지 않았습니다. 필드에서는 `$6E5E` 에 앞 맵의 값이 남아 있고, 칸 4~D 는 `1E:$9799` 가 `1E:$97AE` 의 10개를 차례로 올립니다. 표 `09` 말, `0A` 마차, `0B` 배, `0C` 기구입니다(그림을 보고 붙인 이름).

## 6. 워프 33곳

인물 레코드의 그림 번호를 가장 많이 덮도록 맵을 골라 [워프 도구](../../dq4-warp.md)로 들어가 400프레임 뒤에 덤프했습니다. 들어오는 출구가 없는 맵은 `dq4warp.sh` 가 자리를 못 정해, 첫 인물 둘레에서 지나갈 수 있는 칸을 골라 주었습니다. 디버그 「シナリオ」 창의 B(8명 일행, [dq4-save-format.md](../../dq4-save-format.md))로 クリフト 도 확인했습니다.

```
덤프 43개 중 42개 모두 같음
groups 131 px 33536/33536 dir 100/100 chr 6182/6183
그림 번호 105가지, 돌려 그리기 19가지, 표 82개
```

다른 1개는 4장 시작 세이브스테이트의 칸 5(그림 `3A`)로, `$7200` 이 모두 빈 타일 `78` 이었습니다. 쓰는 인물 넷이 모두 숨은 인물입니다. 맵을 새로 읽으면 이 칸이 생기지 않아 원인은 못 찾았습니다.

## 7. 몬스터 그림은 압축

첫 전투 덤프를 보니 몬스터는 BG 타일(`8D` 부터)이었습니다. 타일 16바이트를 PRG 에서 그대로 찾으니 일부만 뱅크 `06` 에 있고 나머지는 없었습니다. 압축이 있다는 뜻입니다.

원하는 몬스터와 싸우려고 [tools/lua/fc/spritebattle.lua](../../../tools/lua/fc/spritebattle.lua) 를 만들었습니다. 조우 판정 `18:$9D06` 을 메모리상 `CLC`/`RTS` 로 바꿔 걸음마다 전투가 나게 하고, 전투 시작 `18:$A11A` 에서 무리 칸 `$6E45`~`$6E4C` 를 덮습니다. 읽기 기록에서 뱅크 `06` 을 읽는 것은 모두 `$C7E1`(17바이트 복사)이었고, 그것을 부르는 곳의 스택이 뱅크 `14` 의 `$9F82` 를 가리켰습니다.

```
A=06 src=8ED6 stk=81 9F 18 D0 ... 0507=14
```

실행 커버리지로 뱅크 `14` 리스팅을 만들어 읽었습니다. `$812F` 가 무리마다 `$9F0C` 로 ID → 그림 번호(`14:$B2D5`), `$9FA9` 가 그림 레코드 5바이트(`14:$A019`), `$9F26` 이 데이터 뱅크, `$9712` 가 타일 풀기, `$9783` 이 BG·OBJ 패턴으로 올리기, `$98F5` 가 배치입니다. 타일은 「배치 몇 개 + 그림」 이고, 그림은 16비트 마스크로 0 인 바이트를 빼는 단순한 압축이었습니다. 이 규칙으로 그림 194개를 다 읽으면 데이터 71가지 사이의 경계 67곳 중 66곳에서 끝이 같은 뱅크의 다음 데이터 시작과 맞았습니다. 남은 한 곳은 `06:$9D2F`~`$9D34` 6바이트를 어느 그림도 읽지 않는 자리입니다.

## 8. 화면과 맞추기

`check-monster` 는 nametable·attribute·BG 팔레트·OAM 으로 화면 픽셀의 NES 색을 만들고, 롬으로 그린 그림을 8픽셀 단위로 옮겨 가며 가장 많이 맞는 자리를 찾습니다. スライム 은 처음부터 맞았고, おおみみず 는 OBJ 하나만 9픽셀이 어긋났습니다. OBJ x 가 `FF` 였는데 화면은 그림 왼쪽보다 1픽셀 앞이었습니다. OAM x = (x + 왼쪽 열 × 8) & `FF` 라 그림 기준으로는 부호 있는 바이트입니다. エスターク 는 그림이 두 줄 위(nametable 8행)에 있었습니다. 고친 뒤:

```
덤프 20개 중 20개 모두 같음
몬스터 26종, 그림 26가지, 픽셀 22164/22164
```

여러 무리가 같이 나올 때 게임은 팔레트를 화면 4칸에 나눠 넣지만(`$0444`·`$0448`), NES 색으로 견주면 무리 수와 상관없이 같습니다. さまようよろい·じごくのよろい·キラーアーマー·サイモン·ピサロナイト 는 같은 데이터(761픽셀)에 팔레트만 다릅니다. 그림 194개의 데이터는 71가지입니다.

## 9. 열람

`sheet` 가 필드 그림 143개(표 108개 + 쓰이는 돌려 그리기 35개)와 몬스터 195종을 `work/dq4-fcsprite/index.html` 한 페이지에 모읍니다. 필드 그림에는 쓰는 맵 수와 맵 번호를 붙이고, `who N` 은 그 그림을 쓰는 인물을 맵·낮밤·진행 목록·슬롯·자리·대화 번호로 찍습니다. 인물 레코드 → 그림 번호는 `tools/dq4talk.py` 의 `sprite`(같은 날 들어온 `looks` 명령의 함수)를 그대로 씁니다. 그림 `11`(병사)이 183명, `C0` 이 4명으로 `looks` 와 같습니다.

```
$ uv run --locked python tools/dq4fcsprite.py rom/dq4.nes who C0
그림 번호 C0 → 표 40r 돌려 그리기: 인물 4명
  00/01 낮 슬롯  8 (16,05) 그림 C0 대화 008
```

## 틀렸던 것들

- 돌려 그리기의 반전 비트: `$82D2` 를 「새 타일 0 = 옛 타일 1」 로 읽었습니다. 실제로는 타일 자리(`$8981`)와 같이 새 [0, 1, 2, 3] = 옛 [2, 0, 3, 1] 입니다. `C0` 처럼 반전 비트가 없는 그림은 틀린 코드로도 맞아서 바로 드러나지 않았습니다.
- 방향 비교가 처음에 9번 어긋났습니다. 물결 그림(`2C`)처럼 블록 여러 개가 같은 그림이면 마지막 블록만 보고 있었고, 걷는 인물(`$7000` bit7)은 OAM 을 만든 뒤 방향이 바뀌어 있었습니다. 둘을 고치자 어긋남이 없어졌습니다.
- OBJ 자리를 부호 없는 바이트로, BG 0행을 모든 그림에서 nametable 10행으로 두었습니다(위 8절).
- 오른쪽으로 20프레임 걸은 덤프는 맵에 들어가던 중이라 칸 4 가 비어 있었습니다. 6프레임으로 다시 찍었습니다.
