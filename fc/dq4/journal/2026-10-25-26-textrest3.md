# 2026-10-25-26: 포팅용 기호 텍스트 내보내기와 モシャス

대사 2633개, 창 문자열, 이름 목록 7종을 SFC 쪽으로 옮길 수 있게 「기호 텍스트」로 내보내는 `fc/dq4/tools/dq4text.py rom export` 를 만들었습니다. 기호를 다시 바이트로 바꾸면 원래 바이트와 모두 같은지, 6비트 부호가 롬 비트열과 같은지도 검사합니다. 앞 일지에서 남긴 `もどき` 비트는 주문 `モシャス`(행동 `27`)가 켠다는 것을 전투에서 확인했습니다. 결과는 [dq4-text-format.md](../docs/dq4-text-format.md#포팅용-기호-텍스트) 와 [dq4-rom-map.md](../docs/dq4-rom-map.md) 에 있습니다.

## 1. 무엇을 내보낼까

SFC DQ5 엔진에 대사를 넣을 때 필요한 것은 글자와 제어의 뜻입니다. FC 의 6비트 압축이나 사전 단어 선택은 필요 없습니다. 그래서 메시지마다 세 겹을 같이 둡니다.

| 겹 | 내용 | 쓰임 |
| --- | --- | --- |
| `codes` | 롬의 6비트 부호(끝 `39` 까지) | 롬과 맞춰 보기 |
| `bytes` | 사전을 편 글자 바이트 | 기준 원문 |
| `sym` | 글자는 유니코드, 제어는 `{LINE}` 같은 기호 | SFC 제어 코드로 바꾸는 입력 |

기호는 처리기 뜻대로 붙였습니다. `FB` 는 `{WAIT}`, `FC` 는 `{LINE}`, `F9` 는 `{END}` 같은 식입니다. 치환 제어 `F2 F3 F5 F6 F7` 은 인자를 메시지 안이 아니라 RAM `$F9` 부터 하나씩 꺼냅니다. 꺼내는 순번 `$5B` 를 누가 0 으로 두는지 찾았습니다.

```text
16:8028  20 56 86 JSR $8656   ; 시작 위치
16:802B  20 96 85 JSR $8596   ; ↓
16:8596  a9 00    LDA #$00
16:8598  8d 51 05 STA $0551
16:859B  85 5b    STA $5B     ; 인자 칸 순번
```

메시지를 찍을 때마다 0 이 되므로, 칸 번호는 메시지 안에서 치환 기호의 순번과 같습니다. 그래서 `{NAME:0}`, `{ITEM:1}` 처럼 칸을 적었습니다. `EE` 는 다른 제어와 달리 인자가 메시지 안 다음 바이트라 `{SOUND:1A}` 로 씁니다.

```text
0002	00	$800F	1	{NAME:0}は　どうぐを　もっていない{END}	True	True
060A	02	$930A	3	そなたの　かつやくを　きたいしているぞ。{LINE}ライアンよ{END}	True	True
```

## 2. 탁점이 두 가지

처음에는 탁점 `3D` + 글자를 합친 글자 하나로 쓰고, 되돌릴 때 유니코드 분해로 다시 나누었습니다. 이렇게 하면 `ド` 가 문제입니다. 롬에는 `ド` 타일(`65`)이 따로 있고, `3D` + `ト`(`4E`)로도 씁니다. 둘 다 `ド` 로 쓰면 되돌릴 수 없습니다. 같은 일이 타일 `66`~`69`(`じだどぶ`)에도 있습니다.

롬에서 세어 봤습니다.

| 글자 | 타일 | 탁점 |
| --- | --- | --- |
| `ド` | 메시지 719번, 이름 116번 | 메시지 181번, 이름 47번 |
| `じ` `だ` `ど` `ぶ` | 창 문자열 6번(`だ`·`ど`) | 메시지 수천 번 |

처음 규칙(겹치면 탁점 쪽을 `{3D}` 로 남김)으로 돌리니 `{3D}とうぐ` 같은 줄이 1660줄이었습니다. 많이 쓰는 쪽을 맨 글자로 두었습니다. `ド` 는 타일, `3D 4E` 는 `{3D}ト`, 타일 `66`~`69` 는 `{66}`~`{69}` 입니다. 이렇게 하면 `{3D}` 는 메시지 163줄, `{66}`~`{69}` 는 창 문자열 6곳으로 줄어듭니다. 화면에 나오는 대로 읽을 사람을 위해 `text` 열에는 합친 글자를 그대로 둡니다.

## 3. 왕복 검사

`export --check` 는 세 가지를 봅니다.

1. `sym` 을 바이트로 되돌린 것이 `bytes` 와 같다.
2. `codes` 를 풀면 `bytes` 가 된다.
3. `codes` 를 6비트씩 이어 붙인 비트열이 시작 자리부터의 롬 바이트와 같다.

3번에서 처음에 거의 모든 메시지가 틀렸습니다. 시작 단계 p 만큼 부호 p 개를 앞에 채워 맞추려 했는데, 단계 2·3 이면 채운 비트가 8비트를 넘어 바이트 경계가 밀립니다. 단계 p 의 첫 부호는 시작 바이트에서 `6p mod 8` 비트 뒤(bit7·1·3·5)에서 시작하므로 그만큼만 채우고, 바이트마다 부호가 쓴 비트만 비교하게 고쳤습니다.

```text
$ uv run python fc/dq4/tools/dq4text.py rom/dq4.nes export --check
메시지 2633개, 창 문자열 109개, 이름 434개: 다른 것 0개
```

검사가 틀린 것을 잡는지도 봤습니다. 메시지 하나의 `sym` 에 `{LINE}` 을 더하고, 다른 메시지의 부호 한 비트를 바꾸고, 창 문자열의 `{CALL:02}` 를 `{INS:02}` 로, 이름 하나에 `ド` 를 더하니 네 행 모두 「다름」 이 나왔습니다.

창 문자열은 `80` 이상 바이트를 `{CALL:nn}`(루틴 항목)과 `{INS:nn}`(문자열 항목 끼우기)으로 나눕니다. 되돌릴 때 그 항목이 정말 루틴인지 문자열인지도 확인합니다. 이름은 [dq4-data-format.md](../docs/dq4-data-format.md#이름-목록) 의 7종(뒤의 몬스터 목록은 같은 포인터라 뺌)에서 0번 빈 이름을 뺀 434개입니다.

출력은 `work/text/` 에 JSON(`legend` + `rows`)과 TSV 로 씁니다. 원문이 저작권 텍스트라 저장소에는 도구만 둡니다.

## 4. もどき 비트를 켜는 것

`F6` 이 `もどき` 를 붙이는 비트는 `BRK 29 C3 0C`(명령 `29` = 비트 검사)로 봅니다. 같은 꼴로 명령만 다른 호출을 롬에서 찾았습니다.

```text
11:$9DDE 00 2a c3 0c
11:$B114 00 2b c3 0c
```

`11:$9DDE` 가 든 루틴은 `11:$9DA4` 에서 시작하고, 이 주소는 `11:$A448` 에 있습니다. 앞뒤를 보면 `11:$A3FA` 부터 루틴 주소 표이고, `11:$8C78` 이 `BRK 03 1F` 가 돌려준 번호 × 2 로 이 표에서 뜁니다. `$A448` 은 첨자 `27` 이고, 주문 `27` 은 `モシャス` 입니다. 첨자 `00`~`12` 가 모두 `11:$9AD2`, `13`·`14` 가 `11:$9AFC` 인 것도 주문 표(`メラ`~`ミナデイン` 이 공격 주문, `ザキ`·`ザラキ`)와 맞습니다.

`textmodoki.lua` 로 확인했습니다. 1장 첫 전투(몬스터 2마리) 세이브스테이트에서 A 로 공격만 하며, `11:$8C85`(번호가 A 에 있는 자리)에서 번호를 기록했습니다. 바꾸지 않으면 번호는 `7F`(전투 시작)와 `43`(공격)뿐입니다. `FORCE=27` 로 모두 `27` 로 바꿨습니다.

```text
158 msg 004C F9=C0
163 action A=43 -> 27
187 hook 11:9DDE
187 w 727A=D0 pc=A993
```

몬스터 칸 0 이 행동한 프레임에 `11:$9DDE` 가 돌고 `$727A`(칸 0 레코드 바이트 6)가 `D0`, 곧 bit4 가 켜졌습니다. 칸 1 도 같았고, 끝 화면의 몬스터 목록 창은 `ライアンもどき — 1ひき` 두 줄, 몬스터 그림은 ライアン 모양이었습니다. ライアン 의 행동을 `27` 로 바꾼 차례에는 `11:$9DDE` 가 돌지 않았습니다.

어느 몬스터가 `モシャス` 를 쓰는지는 아직입니다. 몬스터 레코드 바이트 9-14 의 행동 번호가 이 표의 첨자와 다릅니다. はさみくわがた 의 레코드는 `32 47 32 47 47 32` 인데 실행 중 번호는 `43` 이었습니다. 레코드에 `27` 이 있는 몬스터는 べホマスライム 하나라, 레코드 번호를 그대로 첨자로 읽으면 안 됩니다.

## 5. 패드 2 를 롬 지도에

[dq4-rom-map.md](../docs/dq4-rom-map.md) 에 패드 읽기를 적었습니다. 패드 2 는 `$C8FF` 의 `LDA $4016,X`(X=1, 곧 `$4017`)로 읽어 `$15` 에 두고, `$4017` 을 절대 주소로 읽는 명령은 없습니다. `$15` 를 읽는 곳 `$CAD8` 은 `AND #$03` 다음 `JMP $CAEA` 가 바로 `LDA $0584` 를 해서 값을 버립니다. 실측은 [dq4-debug.md](../docs/dq4-debug.md#패드-2-흔적) 에 있어 링크만 걸었습니다. 롬 지도에는 「`$4017` 읽기가 없다」 는 문장이 처음부터 없었으므로, 고친 것이 아니라 빠진 내용을 더한 것입니다.

## 틀렸던 것들

- 탁점 + 글자를 언제나 합친 글자로 쓰면 되돌릴 수 있다고 봤습니다. 롬에는 `ド` 같은 탁점 글자 타일이 따로 있어 같은 글자가 두 가지로 쓰입니다.
- 메시지 시작 단계 p 를 「부호 p 개 앞 채우기」 로 맞췄습니다. 실제로는 시작 바이트 안에서 `6p mod 8` 비트 뒤입니다.
- 몬스터 레코드의 행동 번호를 행동 표 첨자로 읽으면 べホマスライム 이 `モシャス` 를 쓰는 셈이 됩니다. 실행 중 번호와 레코드 번호는 다릅니다.

## 남은 것

- `モシャス`(행동 `27`)를 쓰는 몬스터. 몬스터 레코드 행동 번호와 실행 중 행동 번호를 잇는 곳. `もどき` 비트를 끄는 `11:$B114` 가 도는 장면.
- 자동 `＊「` 가 실제로 붙는 메시지 목록(`$058B` 를 정하는 쪽).
- 창마다 위치·크기·항목 목록을 정하는 곳, 루틴 항목 하나하나가 찍는 값.
- `BRK 08 8F` 의 다른 자리 `1C:$94CD`, `1D:$8E23`, `1E:$A362` 가 실행되는 장면.
- `x3` 의 `13`, `83`, `F3` 을 실행 중에 보지 못함.
