# 2026-10-25-20: 투기장 전투 테스트·효과 오류 보고와 SRAM 재현성

앞 일지([2026-10-25-14](2026-10-25-14-debug.md))에서 남긴 것 셋을 풀었습니다. MesenCE 테스트러너가 `Saves/dq4.sav` 를 불러온다는 의심은 사실이었습니다. 다만 전원을 켜는 실험만 영향을 받아서, `dq4state.sh` 의 첫 단계에 SRAM 을 고정하는 스크립트를 끼웠습니다. 디버그 스위치 `$C000`=`00` 으로 엔도르 투기장에 들어가니 시합 직전에 전투 테스트 창이 떴고, 고친 무리로 시합이 시작됐습니다. `10:$81B9` 는 주문·도구 효과 처리가 실패했을 때 부른 뱅크와 효과 번호를 찍는 개발용 오류 보고였습니다. 결과는 [dq4-debug.md](../../dq4-debug.md) 에 있습니다.

## 1. `Saves/dq4.sav` 는 정말 불러오나

MesenCE 설정 폴더의 `Saves/` 에 `dq4.sav`(8KB)가 있었고, 몇 분마다 고친 시각이 바뀌었습니다. 같은 롬을 쓰는 실험이 동시에 여럿 돌면서 이 파일 하나를 같이 쓰고 있었습니다. 이 파일을 고쳐 시험하면 남의 실험을 흔들게 됩니다. 그래서 롬을 `work/` 에 다른 이름(`dq4probeA.nes`)으로 복사해, 그 이름의 `.sav` 로 시험했습니다.

```text
.sav 를 5A 로 채움       → 2프레임째 SRAM 8KB 전부 5A
.sav 없음               → 전부 00, 끝나면 dq4probeA.sav 가 생김
.sav 5A / 00 + throne.mss → 불러온 뒤 SRAM 이 둘 다 같음(md5 ec20d972…)
```

불러오는 것도, 끝날 때 다시 쓰는 것도 사실입니다. 다만 세이브스테이트를 불러오면 SRAM 도 세이브스테이트 것으로 바뀝니다. 그러니 영향을 받는 것은 전원을 켜서 시작하는 실험뿐입니다. `dq4state.sh` 의 첫 단계(전원 → 이름 입력)가 여기에 해당합니다. 모험의 서가 든 지금 `dq4.sav` 를 복사해 같은 입력을 주자, 이름 입력 화면 대신 이어하기로 가서 오프닝 대사(「おうきゅうせんしの ものがたり。」)가 나왔습니다.

## 2. SRAM 을 고정하기

`.sav` 를 지우거나 덮는 방법은 남의 실험과 부딪칩니다. 그래서 Lua 에서 SRAM 을 덮기로 했습니다. `tools/lua/fc/debugsram.lua` 는 스크립트를 읽는 시점, 곧 첫 프레임 전에 `nesSaveRam` 8KB 를 `00`(또는 `SRAM` 파일)으로 채운 뒤 다른 드라이버를 돌립니다. `5A` 파일을 둔 채 끼우자 1프레임째 SRAM 이 전부 `00` 이었고, 이름 입력 화면이 `.sav` 가 없을 때와 바이트까지 같았습니다.

`dq4state.sh` 의 첫 단계를 `debugsram.lua` → `mkstate.lua` 로 바꿨습니다. `STATE_DIR` 을 더해 `work/state` 를 덮지 않고 따로 만들게 했습니다. 두 번 만드는 사이에 다른 실험이 `dq4.sav` 를 바꿨는데도 세이브스테이트 4개와 그림 3장이 바이트까지 같았습니다.

그런데 새로 만든 것은 지금 `work/state` 의 것과 달랐습니다.

```text
throne    RAM 352바이트, SRAM 850바이트 다름
battle    끝 무리 01 01 (おおみみず 하나·スライム 하나), 주석은 「おおみみず 둘」
SRAM $6D8C~  예전 FF, 새로 00
이름      예전 「あああ」, 새로 「ああ」
```

예전 세이브스테이트는 무언가 든 `.sav` 로 만든 것입니다. 이름 입력에 A 를 하나 더 넣어 「あああ」로 맞춰 봤지만, 대사 타이밍이 밀려 필드 단계에서 성 앞(맵 `0A`)을 벗어나지 못했습니다. 그래서 입력은 그대로 두고 스크립트 주석을 새 결과에 맞췄습니다. `work/state` 를 새것으로 바꿀지는 정하지 않았습니다(남은 것).

## 3. 투기장 찾기

`18:$ABA9` 는 `18:$A81B` 고리 안에 있습니다. 고리 앞 `18:$A813` 이 뱅크 18 함수 표의 `14` 번이고, 롬에서 `BRK 14 8F` 는 `15:$AAA5` 한 곳뿐이었습니다. `dq4talk.py` 로 모든 맵의 인물 스크립트를 풀어 `call 15:AAA5` 를 찾았습니다. 엔도르 지하 `04/01` 의 (08,0A) 인물(대화 `048`)이었고, 그 옆 인물은 「ここは ポーカーのテーブルです。」 입니다. 메시지 `0480`·`0489` 를 찍는 `BRK 80 4B`·`BRK 89 4B` 도 고리 첫머리에 있었습니다.

코인은 내기 코드가 `$62AD`~`$62AF` 를 읽는 것을 보고, 워프할 때 `SET="62AD=E80300"`(1000)으로 넣었습니다. 1매를 걸자 999 로 줄어서 맞았습니다.

## 4. 투기장의 전투 테스트 창

`probe/trace.lua` 는 CPU 주소로 걸려서 다른 뱅크의 같은 주소까지 잡습니다(뒤 5절의 `$81B9` 는 뱅크 08 에서 400번 걸림). 그래서 PRG 오프셋이 맞을 때만 적는 `tools/lua/fc/debugtrap.lua` 를 만들었습니다. `debugpad.lua`(`ROMPATCH`)와 `warp.lua` 를 묶어 왕좌의 방에서 `04/01` (08,0B) 로 가서, 위를 보고 말을 걸었습니다.

```text
메시지 0480 → 0489 → 몬스터·배율 표(スライム 5.3, キリキリバッタ 4.7, はさみくわがた 3.8, スライムベス 4.0)
→ スライム 에 1매 → 「では しあいを ごらんください。」 → 「FIGHT!」
21 62BA9 … 6E45=00 6E46=01 6E47=03 6E48=05 6E49=01 6E4A=01 6E4B=01 6E4C=01
```

제품판은 `$ABA9` 와 `$ABB1` 이 같은 프레임에 지나가고 바로 시합이 시작됐습니다. `00` 이면 「FIGHT!」 뒤 화면이 검게 멈췄습니다. 팔레트가 모두 `0F` 였을 뿐이고, 네임테이블에는 「― 1ひき」 네 줄과 「おわり」 창이 있었습니다. 보이지 않아도 입력은 먹었습니다.

- 아래 4번 + A(「おわり」): 82프레임 뒤 `$ABB1`, 원래 네 마리로 시합.
- 첫 줄 A → 목록 아래 2번 → A → 마릿수 위 2번 → A → 「おわり」: `$6E45`=`04`, `$6E49`=`02`. 시합 화면에 슬라임이 둘 나왔습니다. 몬스터 `04` 는 이름이 スライム 인 다른 항목(HP 40)입니다.

앞 일지에서 조우 판정 자리에 창을 억지로 넣었을 때는 「おわり」 뒤 전투로 넘어가지 않았습니다. 투기장은 창 뒤에 `$72E9`=`80` 과 `BRK 28 0F` 로 시합을 따로 엽니다. 디버그판 투기장은 고른 몬스터끼리 싸움을 붙여 보는 테스트 도구였던 셈입니다.

## 5. `10:$81B9`

`10:$81B9` 앞뒤를 읽었습니다. 처리기 표 `10:$9E67` 을 효과 번호 `$6E0B` 로 찾는 `10:$8221` 이 조건이 맞지 않으면(`$831E` 가 C=0) `JMP $81B9` 로 갑니다. 표에는 목적지 고르기 `47` = `$9513` 도 있어서 뱅크 10 이 주문·도구 효과 처리임을 알 수 있습니다. `$81B9` 는 제품판에서 `CLC; RTS` 일 뿐입니다. `00` 이면 메시지 `01CA`·`01CD`·`01CE`·`01CF` 를 찍는데, 풀어 보니 「まん。」「ばんく [F8]。」「ふあんく [F8]。」「P1 [F8]です。」였습니다. 숫자 자리에는 `$0517`·`$6E0B`·`$6E` 가 들어갑니다.

1장 첫 전투를 `00` 으로 A 를 눌러 가며 1360프레임 돌렸지만, `debugtrap.lua` 로 PRG `401B9` 는 한 번도 걸리지 않았습니다. 그래서 `10:$8221` 을 `JMP $81B9` 로 바꿔(`ROMPATCH="40221=4CB981"`) 모든 효과를 이 출구로 보냈습니다.

```text
34 401B9 … 6E0B=2D 006E=00 0517=11
창: 「まん」 → 「ばんく 17。」 → 「ふあんく 45。」 → 「P1 0です。」
```

`$11`=17, `$2D`=45 라서 값은 10진입니다. 처리기가 없는 효과를 부르면 어느 뱅크에서 몇 번 효과를 불렀는지 보여 주던 개발용 오류 보고입니다.

## 틀렸던 것들

- 앞 일지는 `10:$81B9` 가 「`11[14]` 앞부분과 같은 준비」를 한다고 봤습니다. `$6BDD` bit7 을 켜는 것은 같지만, 하는 일은 전투 테스트가 아니라 오류 보고였습니다.
- `dq4state.sh` 주석의 「あああ」·「おおみみず 둘」은 비어 있지 않은 `.sav` 로 만든 결과였습니다. 같은 입력을 빈 SRAM 으로 주면 「ああ」·「おおみみず 하나·スライム 하나」가 됩니다.

## 남은 것

- 투기장 테스트 창의 몬스터 목록 순서(셋째 칸이 몬스터 `04` 였음)와 마릿수 범위. 일행 전투에서 고른 무리와 싸우는 길은 아직 없음.
- `10:$81B9` 에 정상 진행으로 닿는 경우. 처리기 14곳의 `JMP $81B9` 조건과 `10:$831E` 의 `$6BDE` bit7 조건.
- `work/state` 의 1장 세이브스테이트를 새 `dq4state.sh` 결과로 바꿀지. 바꾸면 그것을 출발점으로 쓴 실험 문서의 숫자를 다시 확인해야 함.
