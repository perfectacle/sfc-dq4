# 2026-10-25-39: 원작 그림 2차 — 필드 가장자리, 팔레트 순환, 장 제목·엔딩, 장소 이름

[30 일지](2026-10-25-30-fcgfx.md)에서 남긴 것들을 풀었습니다. 필드 디코더가 게임이 읽는 가장자리 칸까지 풀도록 고치고, 정체를 몰랐던 필드 2 가 쓰이지 않는 빈 자리이며 진짜 넷째 필드는 `$65` = 3 인 闇の世界라는 것을 찾았습니다. 화면이 어긋나던 필드 3·`3B/00` 폭포는 팔레트 순환이었고, `04/07` 투기장은 들어오자마자 주인공이 걸어 올라가는 스크롤 중의 화면이었습니다. 장 끝·장 제목·엔딩 장면을 뜨고, ルーラ 목적지 표로 장소 이름을 더 붙였습니다. 결과는 [dq4-field-format.md](../docs/dq4-field-format.md) 와 [dq4-fcgfx.md](../docs/dq4-fcgfx.md) 에 있습니다.

## 1. 가장자리에서 나던 IndexError

`dq4field.decode` 는 줄을 폭에서 잘라 두는데, 게임의 범위 검사 `0F:$D2AA` 는 좌표에서 3 을 뺀 값을 폭과 비교합니다. 게임이 읽는 칸은 X = 3 ~ 폭+2 이고 0~2 는 늘 0 입니다. 잘린 격자로는 오른쪽·아래 가장자리 세 칸을 못 읽어서, 렌더러가 줄을 따로 풀어 쓰고 있었습니다.

고치는 김에 `$D259` 를 그대로 따르는 `cell` 을 만들었습니다. X 가 40~7F·C0~FF 이면 기준점에서 거꾸로 읽는 `$D37E` 까지 8비트 셈으로 옮겼고, `decode` 는 줄 0 ~ 높이+2, 칸 0 ~ 폭+2 를 `cell` 로 채웁니다. 앞에서부터 푼 예전 줄과 견주니 필드 0·1 은 모두 같았습니다.

```
0 253 253 diff 0 / 62500
1 64 64 diff 0 / 3721
```

## 2. 필드 2 와 필드 3

필드 3 의 폭·높이를 읽는 자리 `$D2D6+3`·`$D2D9+3` 은 표 밖이었습니다. 표는 `FA 3D 2A` / `FA 3D 36` 세 개뿐이고, 필드 3 은 필드 0 의 높이 `FA` 와 다음 루틴의 코드 바이트 `A4` 를 폭·높이로 씁니다. 그런데 입구 도착 레코드에는 필드 3 이 11곳이나 있었습니다.

줄 레코드 포인터가 앞 줄 바로 뒤를 잇는지 따라가 보니 필드 3 은 54줄, 줄마다 정확히 62칸이었습니다. 62칸으로 끊어 그리자 250칸으로 그렸을 때 네 번 되풀이되던 석상이 하나의 섬이 됐습니다. 필드 1 은 64×64(61+3)였습니다.

```
field 1 break at row 64 ptr 3D3F expected ABAC
field 3 break at row 54 ptr 00A2 expected AED0
field 2 break at row 1 ptr 39DD expected FABC
```

필드 2 는 줄 레코드 표 `0B:$8004` 가 가리키는 `$BE22` 의 첫 줄이 고정 뱅크 `$FAA5`, 둘째 줄이 `$39DD`(PPU 레지스터 거울)를 가리킵니다. `$65` 를 쓰는 코드를 모두 찾으니 표에서 오는 값은 0·1·3, 상수는 0·1 뿐이라 필드 2 로 갈 길이 없습니다. 워프로 넣은 화면이 그림과 달랐던 것은 롬 밖을 읽어서입니다. 렌더러는 이제 필드 0·1·3 만 그립니다.

가장자리로 워프해 화면과 견주었습니다(스프라이트를 끈 덤프).

```
work/v/f0e2b/: 필드 0(팔레트 0단계) 맵 종류 00  비교 61440 픽셀 중 0 다름(뺀 것 0)
work/v/f1e2/: 필드 1(팔레트 1단계) 맵 종류 00  비교 61440 픽셀 중 0 다름(뺀 것 0)
work/v/f3e2/: 필드 3(팔레트 2단계) 맵 종류 00  비교 61440 픽셀 중 8344 다름(뺀 것 0), 처음 (224, 0)
```

필드 3 (3A,32) 는 화면이 줄 데이터 밖을 보여 줍니다. Y ≥ 36 은 줄 레코드가 RAM 을 가리키고, X = 40 한 줄만 다른 것은 화면 줄을 그리는 `0F:$EB9D` 가 `$D27F` 로 세 칸씩 읽기 때문입니다. 첫 칸만 범위 검사와 기준점 고르기를 하고 나머지 둘은 앞으로 이어 읽어서, 데이터 밖에서는 `$D259` 와 값이 달라집니다.

`fieldlookup.lua` 로 필드 0·1·3 에서 걸으며 기록한 `$D259` 호출 269번도 `cell` 과 모두 같았습니다.

## 3. 필드의 물결과 용암

가장자리 덤프 넷은 롬 팔레트로 그리면 61440 픽셀이 전부 다르고 덤프 팔레트로 그리면 0 이었습니다. 화면이 거의 물이라 물 색만 바뀐 것입니다. 필드 3 에서 `$05FC`~`$060B` 쓰기를 지켜보았습니다.

```
05FC-060B pc=8B6E prg=74B6E first=12 n=18 addr=05FE val=0C
05FC-060B pc=8BA4 prg=74BA4 first=12 n=18 addr=0606 val=26
```

`1D:$8B1E` 가 `$3C`&0F 가 0F 인 프레임, 곧 16프레임마다 모든 필드에서 `$05FE`·`$05FF` 를 맞바꾸고, 필드 3 이면 `$0606`~`$0608` 을 돌립니다. 처음에 이 순서대로 돌려도 21090 픽셀이 남았는데, PPU 에 쓰는 순서가 `$0606`, `$0608`, `$0607` 로 RAM 과 달랐습니다. RAM 은 `06 16 26`, 덤프 팔레트는 `06 26 16` 이었습니다. 이 순서를 넣고 나니 남은 228 픽셀은 블록 `01` 이 난수로 `19`(반짝임)가 된 칸이었습니다. 둘 중 하나와 같으면 같은 것으로 세자 도착 2·18·34·50·66프레임 뒤의 덤프가 모두 0 다름이었습니다.

## 4. 폭포는 팔레트, 투기장은 걷는 중

`3B/00` 은 30 일지에서 타일 그림이 흐르는 것으로 봤지만, 프레임 20~120 동안 PPU 쓰기는 `$3F00` 대 팔레트뿐이었고 MMC1 CHR 뱅크도 그대로였습니다. 같은 `1D:$8B4A` 가 맵 종류 `18` 이면 4프레임마다 팔레트 2 의 색 셋을 돌리고, 16프레임마다 팔레트 1 의 두 색을 맞바꿉니다. 돌리는 횟수를 바꿔 가며 견주니 두 번 돌린 것이 0 이었습니다.

```
0 0 40384
1 0 40384
2 0 0
```

화면 덤프가 메모리보다 한 프레임 늦으니, 한 번 덜 돌린 것이 세 단계로 돌아 두 번 돌린 것과 같습니다. 도착 2·6·10·14·22·30프레임 뒤 여섯 덤프가 모두 0 다름이었습니다.

`04/07` 은 (0F,0B)에 내려도 덤프 때 `$45` 가 `0A` 였고 `$0509` 가 프레임마다 1 씩 줄고 있었습니다. 들어오면 주인공이 (0F,09)까지 걸어 올라갑니다. 덤프의 nametable 로 맞춘 스크롤은 237 로, RAM 의 235 보다 두 프레임 늦었습니다. 걸음이 끝난 60·150프레임 뒤의 덤프는 관중 애니메이션 블록을 빼고 0 다름이었습니다. 렌더러가 블록을 nametable 에 놓을 때 스크롤을 8로 나누던 것을 16 격자로 고쳤습니다(스크롤 중에도 블록 자리는 16픽셀 격자).

맵 종류 50가지를 다시 하나씩 워프해 보니 49가지가 0 이었고, `2B` 의 `30/00` 은 들어오자마자 대화 창이 떠서 같은 종류의 `33/01` 로 0 을 확인했습니다.

## 5. 장 끝·장 제목·엔딩

[dq4-save-format.md](../docs/dq4-save-format.md#장-끝) 의 장 끝 조건 플래그를 `SET` 으로 쓰고 그 맵으로 워프한 뒤, 60프레임마다 A 를 누르며 덤프했습니다. 장 끝 메시지 → 「第一章 王宮の戦士たち 完」 → 모험의 서 기록 → 「第二章 おてんば姫の冒険」 차례였고, 2~4장 끝도 같았습니다. 덤프 nametable 로 그린 화면은 여덟 장면 모두 0 다름입니다. 제목 상자의 타일은 plane 0 이 `1A:$8CA8` + 8×타일 번호의 1비트 그림과 모두 같았습니다. 제목의 한자도 여기 있습니다.

엔딩은 2장 세이브스테이트에서 5장 끝 조건을 쓰고 `2D/00` 으로 워프해, 테스트러너가 결과를 남기는 길이인 1만 프레임씩 네 번 이어 200프레임마다 떴습니다. 바다 위 天空城이 동트며 밝아지는 장면, 구름 위 天空城과 열기구, 각 마을, 스태프 롤, 「The End」 가 나왔습니다. 바다 장면은 아래 물결이 덤프 nametable 과 4652 픽셀 달라, 줄마다 스크롤을 바꾸는 것으로 보입니다.

## 6. ルーラ 목적지 표로 장소 이름

`$65` 를 쓰는 곳을 찾다가 `1E:$AE59` 가 레코드 표에서 필드 번호를 읽는 것을 봤습니다. `1E:$AE19` 가 목적지 번호를 받아 `1E:$AF00` + 7×번호 를 읽고, 바이트 0 bit7 로 필드·맵을 가릅니다. 번호 순서가 장소 이름표 28개와 같아서, 필드 자리를 입구 표와 맞추니 26개가 입구와 1칸, りバーサイド 가 2칸이었습니다.

```
00 キングレオ      필드 0 (40,A7) → 그룹 00
01 てんくうじょう    맵 2D/00 (0C,07)
18 ゴットサイド     필드 1 (20,1D) → 그룹 1A
1B きぼうのほこら    필드 3 (23,2B) → 그룹 26
```

대사로 붙인 이름과 둘 다 있는 그룹 20개가 모두 같았고, 대사에 「ここは」 가 없던 8개 그룹(ボンモール, ガーデンブルグ 등)에 새로 이름이 붙었습니다. 대사 쪽도 「ここは X」의 X 가 장소 이름씨로 끝나는 것(サラン, きこりのいえ, エルフのさと 등)과 「このとう」「このどうくつ」 같은 갈래 말까지 넓혀, 73개 그룹 중 43개에 이름이 붙었습니다(28 ルーラ, 4 대사의 이름표 이름, 5 대사 구절, 6 갈래 말).
