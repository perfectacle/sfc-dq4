# 2026-10-25-45: デスピサロ 형태와 남은 필드 그림

[첫 스프라이트 일지](2026-10-25-29-fcsprite.md)에서 쓸 수 없다고 남겨 둔 デスピサロ 를 형태 8가지 모두 롬에서 그렸습니다. 첫 그림의 타일 규칙 두 가지와 형태 루틴이 부르는 부품 함수를 풀어 시뮬레이터로 옮겼고, 전투를 강제로 일으켜 형태마다 화면 덤프와 픽셀을 견주었습니다. 함께 여자 勇者·ブライ 를 화면으로 확인하고, 이벤트가 바꾸는 그림·4장 시작의 빈 칸·주문 연출을 정리했습니다. 결과는 [dq4-fcsprite-format.md](../docs/dq4-fcsprite-format.md) 의 「デスピサロ 형태」「이벤트가 바꾸는 그림」 절에 있습니다.

## 1. 형태 번호 찾기

`14:$812F` 는 그림 번호 `AE`·`BC` 를 따로 다룹니다. 같은 뱅크에서 `CMP #$AE` 를 따라가니 `14:$8303` 이 `$6E7E` 를 `07` 과 견주었습니다. 뱅크마다 `$6E7E` 를 찾으면 전투 시작 때 0 으로 두는 `12:$8092`, 하나씩 올리는 `11:$9202`·`$9228`, 그리고 `14:$A3F4` 가 나옵니다.

```
14:A3F4  LDA $6E7E / ASL / TAX / LDA $A40D,X ... JSR $8364
14:A40D  1B A4 6A A4 99 A4 D0 A4 7F A6 36 A7 88 A8   ; 형태 루틴 7개
```

## 2. 전투를 강제로 일으켜 형태 넘기기

[spritebattle.lua](../tools/lua/spritebattle.lua) 와 같은 방법(조우 판정을 메모리에서 바꾸고 전투 시작 `18:$A11A` 에서 무리를 덮음)으로 [spriteboss.lua](../tools/lua/spriteboss.lua) 를 만들었습니다. 전투가 시작되면 적 HP(`$7274` + 14n + 10)를 1 로 눌러 두고 A 를 눌러 공격하고, `$6E7E` 가 바뀌면 입력을 멈추고 400프레임 뒤에 덤프합니다. 처음에는 디버그 B 세이브스테이트가 마을 집 안이라 조우가 나지 않아, 필드 0 (67,67)로 워프한 상태에서 출발했습니다.

```
start frame=26 mon=AE:1
frame=968 form=01 ... frame=10152 form=07
dump f7 frame=10552 form=07
```

롬에서 뽑은 그림은 비공개 에셋에만 두므로 여기에는 싣지 않습니다. 형태 0~3 은 금색이고 칼 두 자루 → 한 자루 → 없음 → 팔 없음, 4~7 은 초록이고 머리 → 팔 → 아래 → 위 머리 순서로 부품이 붙습니다.

## 3. 첫 그림: 161타일의 두 규칙

예전 디코더는 레코드의 161타일을 모두 「배치 + 그림」으로 읽어 56번째부터 엉뚱한 배치가 나왔습니다. 추적(`CALLS="14:969C,14:9712"`)에서 게임은 161타일을 다 읽고 `$B861` 에서 끝났는데 디코더는 `$BA64` 였습니다. `$969C` 를 읽으니 デスピサロ 일 때 남은 타일 수 `$D1` 이 `6A` 보다 작으면 `$29` 를 켜고, `$9712`·`$9783` 은 `$29` 가 켜져 있으면 머리 바이트 뒤의 자리 바이트를 읽지 않습니다. 이 규칙을 넣자 끝이 `$B861` 이 됐습니다. 그 뒤 105타일은 자리 없이 OBJ 패턴에만 올라가는 형태 부품입니다.

그래도 형태 0 덤프와 31픽셀이 달랐습니다. 화면 OAM 은 13개인데 디코더는 15개를 놓았고, `14:$9852` 가 デスピサロ 일 때 놓을 타일 수를 `36`(54)으로 줄이고 있었습니다.

## 4. 부품 함수

형태 루틴이 부르는 함수를 `CALLS` 로 모두 기록했습니다. 표에서 읽는 함수가 대부분입니다.

```
896 00 14:A3F4 ...            ; 형태 0 → 1
897 00 14:B100 X=00           ; CHR 부품 0: 07:$B196 의 타일 6장을 OBJ 타일 EE~ 로
902 00 14:AC1A X=00           ; OBJ 부품 0
902 00 14:AE7C ...            ; OBJ 타일 2~7 지우기
966 00 14:AA43 X=00           ; BG 부품 0
```

`$B100`(CHR), `$AA43`(BG 칸), `$AC1A`(OAM), `$AE7C`·`$AE80`(타일 지우기·드러내기)을 옮기고 기록한 순서대로 재생하니 형태 1~6 이 바로 모두 맞았습니다. 형태 7 은 OAM 칸 8·9 를 직접 옮기는 `$A9FD` 와, 칸마다 BG 팔레트 3 을 주는 `$A8BF` 루프를 더해야 했습니다. 형태 0 → 1 의 속성 쓰기(`$A42A`, `$23E0`~ = `05`)를 행 16·17 까지 넣자 아래 두 줄도 맞았습니다.

```
form 0: 같음 2692/2692 ... form 6: 같음 2888/2888
form 7: 같음 4050/4058
```

형태 7 의 8픽셀은 겹친 스프라이트의 앞뒤였습니다. 같은 실행을 402프레임 뒤에 덤프하면 모두 같았고, 스크린샷과도 색이 하나씩 대응했습니다. 프레임마다 OAM 칸 배정이 바뀌어(`$C78C`, `$0513`) 앞뒤가 번갈아 나옵니다. 난수가 달라 진행이 다른 401프레임 실행에서도 형태 0~6 이 모두 같았습니다.

도구에서는 기록을 반복만 묶어 형태마다 한 줄(`BOSS_STEPS`)로 두고, 각 기호의 뜻과 데이터는 롬 표에서 읽습니다. `boss` 명령이 형태 여덟 장을 같은 상자(106×91)로 내고, `check-boss` 가 덤프와 견줍니다.

## 5. 여자 勇者와 ブライ

디버그 B 일행(8명)은 걷는 넷이 `80 81 82 83` 이라 ブライ 가 화면에 나오지 않습니다. `$616A`~ 를 `80 84 82 83` 으로 바꾸고 워프해도 일행 칸은 그대로였습니다. 워프 중에는 `1E:$9648`(일행 칸 다시 올리기)이 돌지 않았고, 전투를 하나 치르고 필드로 돌아올 때 돌았습니다.

```
760 00 1E:9648 ...
  칸 1 그림 04(표 04) $7200 같음, CHR 27/27
  화면 OAM 묶음 6개, 픽셀 1536/1536 같음
```

여자 勇者는 도착 뒤 `$615C` = `01` 만 쓰고 같은 방법으로 확인했습니다. `08:$859B` 는 `$62A5` bit7 도 보지만, 일행 칸은 `1E:$966C` 가 고른 값을 번호 바꿈 없이 `08:$8676` 에 넘기므로 `$615C` bit0 만으로 표 `08` 이 됐습니다.

## 6. 이벤트가 바꾸는 그림과 4장 시작의 빈 칸

BRK `0D 87` 은 `08:$8668` 이고 일행 칸 로더와 몸통이 같습니다. 54곳 중 상수로 정해지는 표는 `01 02 03 04 06 12 15 1E 24 3B 3D 4C 53 83` 이었습니다. `changes` 명령이 목록을 냅니다.

4장 시작 칸 5 의 `78 00`×32 를 찾으려고 상수 `78` 을 찾았지만 관계가 없었고, 그 맵에 다시 들어가는 워프는 장면이 걷지 못하는 상태라 실패했습니다. 세 번째로 그 상태에서 장면을 진행하며 `$7240`~`$727F` 쓰기를 감시하니 287프레임에 보통 로더 `08:$82B0` 이 다른 그림을 올렸습니다. 보통 로더가 32칸을 한 타일로 채우려면 블록 8개가 모두 같은 타일 주소여야 해서 표를 모두 뒤졌고, 표 `53` 이 빈 타일 한 장짜리였습니다. 64바이트와 CHR 이 표 `53` 과 같습니다.

## 7. 주문 연출

디버그 B 일행이 キングスライム 둘과 4000프레임 싸우는 동안(みんながんばれ) `となえた` 메시지가 나왔지만, OAM 의 (타일, 속성) 조합은 필드 일행·빈 것·왕관 부품 다섯 가지뿐이었습니다. 주문 연출은 OBJ 를 쓰지 않습니다.

## 틀렸던 것들

- 「デスピサロ 는 팔레트를 그림 레코드가 아닌 곳에서 받는다」: 팔레트 순번이 목록보다 컸던 것은 자리 없는 타일을 자리 있는 것처럼 읽어 머리 바이트가 어긋났기 때문이었습니다. 팔레트는 레코드 것을 씁니다(칸 배정만 다름).
- 프로브의 `CALLS` 를 `cpu >= 0xC000 and nil or ...` 로 써서 고정 뱅크 주소가 하나도 걸리지 않았습니다. Lua 의 `and/or` 는 가운데 값이 `nil` 이면 뒤 값을 돌려줍니다.
- 전투 뒤 필드 덤프에서 일행 칸 표가 몇 바이트씩 어긋났는데, 프로브가 전투가 끝난 뒤에도 적 HP(`$727E`…)를 눌러 필드 그림 표 `$7200` 을 덮은 것이었습니다. `HPFRAMES` 로 누르는 기간을 줄였습니다.
- 여자 勇者 덤프를 `check-field` 가 표 `00` 으로 적었습니다. 표 `08` 은 `$7200` 배치가 표 `00` 과 같아 배치만으로는 못 가르므로, CHR 까지 맞는 표를 고르게 고쳤습니다.

## 남은 것

- `BOSS_STEPS` 는 형태 루틴을 명령 단위로 옮긴 것이 아니라 실측 호출 순서입니다.
- 4장 시작 칸 5 에 표 `53` 을 올린 곳이 A = `53` 인 네 곳 중 어디인지.
- `$62A5` bit7 의 뜻, 탈것 칸 표 `0D`·`58`~`60` 과 へんげのつえ 표를 쓰는 장면.
- 몬스터 공격·피격 때의 BG 바꾸기.
