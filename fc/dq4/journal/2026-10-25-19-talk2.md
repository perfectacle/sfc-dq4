# 2026-10-25-19: 대화 조건·밤 인물·호출 문장

[앞 일지](2026-10-25-09-talk.md)에서 풀지 못하고 프로브 기록에 기대던 조건 넷(`03`·`11`·`13`·`1E`)의 뜻을 뱅크 10 의 일행 루틴에서 읽고, RAM 으로 일행·소지품·장을 만들어 확인했습니다. 이제 `compare` 는 기록을 빌리지 않고 예측합니다. 서비스 0·4·5, 밤의 대화 번호, 이야기 진행에 따라 바뀌는 인물 목록, 인물 레코드의 그림 번호와 움직임 바이트, 호출 문장 126곳의 갈래도 정리했습니다. 결과는 [dq4-script-format.md](../docs/dq4-script-format.md) 에 있습니다.

## 1. 조건 넷은 뱅크 10 의 일행 루틴

조건 `03` 은 `BRK 63 63 40`, `13` 은 `BRK 63 73`, `11` 은 `BRK 66 73`, `1E` 는 `BRK 29 73` 을 부릅니다. `b2` 아래 4비트가 `3` 인 특수 형식이라 뱅크 10 함수 6·7 인데, 함수 표를 보니 둘 다 `10:$810B` 였습니다.

```
10:810B  86 6e    STX $6E
10:810D  85 6f    STA $6F
...
10:8116  a5 76    LDA $76        ; b1
10:8118  8d 0b 6e STA $6E0B
10:811C  a5 77    LDA $77        ; b2
10:811E  c9 73    CMP #$73       ; 73 이면 셋째 바이트 없음
```

`b1` 은 `$6E0B` 로 가서 `10:$9E67` 의 처리기 표를 고릅니다. `63` 은 일행에서 인물 번호를 찾고, `42` 는 그 자리의 상태(레코드 바이트 0 bit7 이 꺼지면 1), `66` 은 소지품 8칸에서 아이템을 찾고, `29` 는 성별입니다. 스크립트에서 이 조건 뒤에 오는 대사를 모아 보니 뜻이 맞았습니다.

```
00B 03 06 | then 0A3D おお　ライアン！ よくぞ　もどった！
01D 13 07 | then 07AC なんと　ひめさまが……！ おいたわしや……。 | else 07AE これは　ひめさま。
089 1E    | then 0902 そなたの　かつやくを　きたいしているぞ！ | else 0903 そなたのような　わかいむすめ　には
```

`03` 은 「걷는 일행에 인물 n 이 살아 있음」, `13` 은 「인물 n 이 죽어 있음」, `11` 은 「아이템 n 을 가짐」, `1E` 는 「선두가 남자」 로 보였습니다. 인물 번호는 [저장 데이터 일지](2026-10-25-11-event.md)의 레코드 번호(0 주인공 ~ 7 アりーナ)와 같습니다.

## 2. 한 인물 앞에서 아무 스크립트나

이 조건들은 다른 장·다른 맵의 인물에게 걸려 있어, 맵마다 찾아가서는 확인할 수가 없습니다. 그래서 `talk.lua` 에 `TID` 를 더했습니다. 갈래 직전(`15:$9942`)에 `$00`/`$01` 을 바꾸면 왕좌의 방 왕에게 말을 걸어도 아무 대화 번호의 스크립트가 돕니다. 말이 끝나면 A 로 명령 창이 열리고 다시 A 로 「はなす」 가 되므로, A 를 거듭 누르면 목록의 대화 번호를 차례로 돌립니다. `SET` 으로 첫 말 걸기 직전에 일행·레코드·장을 씁니다.

```
96 talk 1A 1 22
97 tid 089
94 msg 0901
454 cond 1
454 msg 0902
```

조건 넷이 든 스크립트 중 호출·서비스 문장이 없는 37개를, 장 5가지 × 일행 4가지로 돌렸습니다.

| 일행 | `SET` |
| --- | --- |
| 1장 그대로(ライアン) | `615A` 만 |
| 주인공·アりーナ·ミネア·マーニャ, 소지품 12가지 | `616A=80878283`, 레코드 바이트 0 = `80` |
| 같은 일행, アりーナ·ミネア 의 바이트 0 = `00`, マーニャ 는 HP 0 | |
| 여자 주인공·トルネコ·クリフト·ブライ | `615C=01` |

조건마다 참·거짓이 모두 나왔고(`03 09` 와 `13 03` 은 거짓만), 말 걸기 2382번(대화 번호를 바꾼 것 740번) 중 다름이 없었습니다. HP 를 0 으로 한 マーニャ는 `13 03` 이 거짓이라, 「죽음」 은 HP 가 아니라 레코드 바이트 0 bit7 입니다.

## 3. 마차와 5장

`13` 은 5장(`$615A` ≥ 4)에서만 `BRK 6A 73` 을 더 부릅니다. 마차(`$6172`~, `$618E` = `20`)에 죽은 アりーナ를 두고 4장·5장으로 돌렸습니다.

| 장 | アりーナ 자리 | `13 07` | `03 07` |
| --- | --- | --- | --- |
| 4장 | 마차, 죽음 | 참(`07AC`) | |
| 5장 | 마차, 죽음 | 거짓(`07AE`) | 거짓(`09CD`) |
| 5장 | 걷는 일행, 죽음 | 참(`07AC`) | |

1~4장은 마차의 인물도 세고, 5장은 걷는 일행만 셉니다. 이 실험(마차 넷, 말 걸기 276번)도 다름이 없었습니다. `03` 은 셋째 바이트 `40` 이 마차 쪽 찾기를 막아 장과 상관없이 걷는 일행만입니다. `11` 은 5장에서도 마차 アりーナ의 아이템 `1E` 로 참이었습니다. 마차를 셀지는 `10:$8498` 이 `$618E` 와 마차의 맵을 보고 정하는데, 실측한 값은 `00`·`20` 뿐이라 그 밖은 디코더가 「?」 로 둡니다.

예전에 기록대로 따랐던 5장 왕좌의 방 3명도 다시 돌렸습니다. 워프로 5장 왕좌의 방을 새로 읽고 `SLOT` 을 06~1A 차례로 주니 78번 모두 같았고, 기록을 빌린 조건은 0번이었습니다.

## 4. 서비스 0·4·5

대화 번호를 `000`·`004` 로 바꿔 왕에게 말을 걸었습니다.

```
97 tid 004
97 svc 04
104 msg 0238      ＊「ここは　もちものと　おかねの あずかりじょです。
...
97 tid 000
97 svc 00
104 msg 021B      ＊「そなたが　ここにきたのも カミの　おみちびき。
```

4 는 맡기는 곳, 0 은 교회입니다. 5 는 02/00·05/01 의 신부에게 말을 걸어 교회(`021B` → 기록 `0229`)였습니다. `$9CBF` 가 4·6·1·3·2 만 따로 보고 나머지를 모두 교회로 보내서 0 과 5 가 같습니다. 서비스 4 를 쓰는 인물은 04/00 의 ネネ(대화 `075`) 하나이고, 5장에 카운터 너머에서 말을 걸 때만입니다. 1장에는 그 자리에 아무도 없어 대화 번호를 바꿔 확인했습니다.

## 5. 밤

`1C:$96FC` 는 슬롯 번호만큼 레코드를 세면서 지금 시간에 나오지 않는 레코드를 건너뜁니다(`1C:$9798`: 낮은 F bit4, 밤은 F bit3). 밤의 대화 번호는 `1C:$975A` 에서, F bit1 이 꺼져 있으면 머리 뒤에 덧붙은 바이트를 씁니다.

```
1C:9780  a0 01    LDY #$01
1C:9782  20 4e 99 JSR $994E      ; 바이트 1
1C:9785  29 03    AND #$03       ; 위 2비트
1C:9789  a0 08    LDY #$08       ; F bit0 이 켜져 있으면 7
1C:9792  20 4e 99 JSR $994E
1C:9795  85 00    STA $00        ; 아래 8비트
```

워프 도구의 `SET="62ED=90"` 으로 밤을 만들고 왕좌의 방(02/01)과 04/00 을 새로 읽어 밤 인물에게 `SLOT` 으로 말을 걸었습니다.

```
02/01 밤 슬롯 06 대화 17A: 기록 0519 / 예측 0519 → 같음
04/00 밤 슬롯 0A 대화 1A3: 기록 0542 / 예측 0542 → 같음
```

02/01 9명, 04/00 10명이 모두 같았습니다. 04/00 은 처음에 슬롯 07(여관 주인)에게 「はい」 로 묵어 버려 아침이 되는 바람에 순서를 바꿔 다시 돌렸습니다. 밤의 X·Y 도 덧붙은 바이트에서 오는데(`1C:$9907`), 진입 때 덤프의 인물 표와 19명 중 18명이 같았고 한 명은 걸어서 한 칸 옮겨 있었습니다.

## 6. 그림 번호와 바이트 2

`1C:$99B3` 을 따라가니 바이트 3 위 6비트와 바이트 0 bit7 로 만든 값에 `0F` 를 더해 그림 표 `$6E5E` 에 넣고, 인물 표 `$6FE0` 에 그 칸 번호 + 4 를 둡니다. 바이트 2 의 니블은 `1C:$9A74` 가 인물 표 `$7040` 의 위 4비트로 넣습니다(낮 위, 밤 아래 니블). 덤프 7개의 93명을 맞추니 그림 번호는 모두 같고, 움직임은 8 미만 73명 중 72명이 같았습니다. 다른 한 명은 1장 세이브스테이트의 슬롯 6 인데, 같은 맵을 워프로 새로 읽으면 맞습니다.

```
02/01 슬롯 0C (0E,12) $6FE0 05  OAM 타일 83 84 85 팔레트 3
02/01 슬롯 11 (11,12) $6FE0 05  OAM 타일 78 79 7A 팔레트 3
```

같은 칸(그림 `11`)을 쓰는 병사 둘은 같은 팔레트와 같은 타일 구역에서 방향만 다른 그림으로 그려졌습니다.

## 7. 호출 문장

호출 문장이 부르는 루틴 100개를, 안에서 무엇을 부르는지로 나눴습니다(`fc/dq4/tools/dq4talk.py calls`). 가장 많은 것은 BRK `07 CF`, 뱅크 1C 함수 07(`1C:$AD5F`)로, A 번째 포인터(`1C:$BF74`)로 점프하는 이벤트 표입니다. `talk.lua` 에 이벤트·특수 전투 진입을 찍게 하고 몇 개를 돌렸습니다.

```
97 tid 016
104 msg 079C      いのちしらずなやつめ！
207 ev1C 00
207 battle 05
```

| 루틴 | 대화 | 결과 |
| --- | --- | --- |
| `$9D57`(이벤트 `00`) | `016` | 특수 전투 `05` |
| `$AC20`(이벤트 `14`) | `0C6` | 특수 전투 `0E` |
| `$AB7D`(이벤트 `15`) | `0AE` | 일행 `86` → `86 84`(ブライ) |
| `$AB8D` | `0B1` | 소지품 `7E` → `7B`(パデキアのたね) |
| `$A6A4` | `088` | `$62ED` `90` → `28`, 자리 (0E,05) 로 맵을 다시 읽음 |
| `$A4B7` | `0C9` | 슬롯 8 의 `$7040` `41` → `11`, 그 뒤 제자리 |

## 8. 이야기 진행에 따른 인물 목록

맵 형식 문서에 「밤·이벤트용 대체 목록」 으로 적혀 있던 `1C:$9D0E` 를 따라가니 코드가 아니라 포인터였고, 그 끝 `1C:$9D10` 에 6바이트 줄 56개가 있었습니다. 맵에 들어갈 때 `1C:$9CC1` 이 줄마다 (그룹, 순번, 마스크, 플래그 번호, 목록 주소)를 보고, 플래그가 켜진 첫 줄의 뱅크 1C 목록을 씁니다. 밤은 5절처럼 레코드의 F 비트로 가르고, 이 표는 장이 끝났는지(`$6282`) 같은 진행 플래그로 가릅니다.

```
02/01 flag 08&80 $6283 list 1C:8184 n=12
04/00 flag 07&10 $6282 list 1C:8ACE n=16
12/00 flag 07&10 $6282 list 1C:9142 n=18
```

워프의 `SET` 으로 플래그를 켜고 들어가 인물 표를 덤프했습니다. 02/01·02/00·04/00·12/00 모두 인물 수가 그 목록과 같았고, 02/01 은 12명의 자리가 모두 같았습니다. 줄을 고른 뒤 `1C:$9C6F` 가 다시 무르는 경우가 있어, `$6282` bit4 를 같이 켠 02/01 은 보통 목록 21명으로 돌아왔습니다. 04/00 은 5장 목록으로 12명에게 말을 걸어 메시지가 모두 같았습니다. 이 목록까지 넣으니 맵 인물의 대화 번호가 861가지가 되었고, 스크립트 346개가 모두 어느 인물에게서 쓰였습니다.

## 9. 3A/04

`1C:$96CE` 는 장소가 3A/04 일 때만 `$64` 를 03 으로 바꿉니다. 처음에는 3A/03 의 목록에서 대화 번호를 꺼내는 것으로 읽었습니다. 그런데 레코드를 세는 `1C:$96FC` 는 맵에 들어갈 때 정한 목록 포인터 `$3A`/`$3B` 만 보고 `$64` 는 읽지 않습니다. 3A/04 슬롯 6 은 대화 `008`(→ `02F0`)이었지만, 3A/03 의 첫 레코드도 `008` 이라 둘을 가르지 못했습니다. 바꾸는 까닭은 남은 것입니다.

## 틀렸던 것들

- `SET` 을 처음에는 말 걸 때마다 썼습니다. パデキア 스크립트가 바꾼 소지품을 다음 말 걸기에서 다시 `7E` 로 덮어 「아이템이 안 바뀐다」 고 잘못 볼 뻔했습니다. 첫 말 걸기에만 쓰게 바꾸고 조건 실험을 모두 다시 돌렸습니다.
- 「죽음」 을 HP 0 으로 짐작했는데, HP 를 0 으로 둔 인물은 살아 있는 것으로 나왔습니다. 처리기 `42` 는 레코드 바이트 0 bit7 만 봅니다.
- 5장 왕좌의 방에서 왕 바로 아래(10,0E)로 위를 보게 워프했더니 「だれもいない」 만 나왔습니다. 까닭은 확인하지 않고, 아래쪽 병사 앞(11,11)으로 옮겨 `SLOT` 으로 돌렸습니다.
- `1C:$96CE` 의 3A/04 를 「다른 목록에서 대화 번호를 찾는다」 고 디코더에 넣었다가 뺐습니다. 목록 포인터는 맵에 들어갈 때 이미 정해져 있습니다.
- `1C:$9D0E` 를 밤 목록으로 짐작했는데, 진행 플래그로 고르는 목록 표였습니다.
- 이벤트 목록을 확인하려고 워프 직후(도착 10프레임 뒤) 덤프했더니 인물 표가 예전 그대로였습니다. 인물 표는 화면이 밝아진 뒤에 채워져서, 300프레임 기다려 다시 덤프했습니다.
- `$7040` = `11` 을 「인물이 사라짐」 으로 짐작했습니다. 실제로는 움직임 니블 1(제자리)이고, 값을 바꾼 인물은 그 자리에 그대로 있었습니다.

## 남은 것

- 마차를 셀지 정하는 `$618E` 의 다른 값(아래 3비트, bit7)과 마차의 맵 `$618F` 를 만든 실측. 손님(인물 번호 8·9) 조건.
- 이벤트 표 `1C:$BF74` 의 번호마다 하는 일(실측은 `00`·`14`·`15`), 맵 이벤트 `1D:$B74D` 의 표, 이벤트 번호를 A 로 받는 14곳.
- 움직임 니블 0~7 의 뜻(1 = 제자리 말고는 모름)과 8 이상의 공용 값.
- 그림 번호와 CHR 그림의 대응(뱅크 08 함수 04 가 읽는 곳).
- `1C:$96CE` 가 3A/04 에서 `$64` 를 바꾸는 까닭.
- 이벤트 목록을 무르는 `1C:$9C6F` 의 `$62A5`·`$6287`·`$6295` 갈래.
