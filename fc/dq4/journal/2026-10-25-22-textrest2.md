# 2026-10-25-22: 남은 제어 바이트·창 문자열·폰트 올리기·BRK 길이

[13 일지](2026-10-25-13-textrest.md) 의 「남은 것」 을 차례로 풀었습니다. 메시지에 없는 제어 바이트를 가짜 바이트로 띄우고, 창 문자열 안의 `80` 이상 바이트, 폰트를 CHR 로 올리는 루틴, BRK 특수 형식의 실제 길이, 뱅크 `06`·`07` 을 확인했습니다. 전투 창(24칸)을 읽는 디코더도 고쳤습니다. 결과는 [dq4-text-format.md](../../dq4-text-format.md), [dq4-bank-format.md](../../dq4-bank-format.md), [dq4-rom-map.md](../../dq4-rom-map.md) 에 있습니다.

## 1. 메시지에 없는 제어 바이트 띄우기

`F0`, `F2`, `F3`, `FA`, `FD` 는 롬 메시지 2633개에 한 번도 나오지 않습니다. 메시지를 고쳐 넣을 수는 없으니, 메시지에서 한 바이트를 꺼내는 `16:$803F` 가 돌아가는 RTS(`16:$808D`)에서 A 와 `$57` 을 원하는 값으로 바꿨습니다. `textforce.lua` 에 `FAKE="0B 0C 0D F0 0E 0F FF"` 꼴로 넣었습니다. 왕에게 말을 걸 때 나오는 `060A` 의 첫 바이트들이 이것으로 바뀝니다.

처음에는 `0B 0C F0 0D 0E FF` 로 했는데 `F0` 도 `FC` 도 줄을 바꾸지 않았습니다. 앞 일지에서 본 들여쓰기 탓입니다. 왕의 대사는 자동 `＊「` 가 붙어 들여쓰기 칸 `$55` 가 2 이고, `あい` 두 글자를 찍으면 커서가 2 라 줄바꿈이 그냥 지나갑니다. 세 글자로 늘려 다시 했습니다.

```
F0: あいう / 　　えお   cur=04 line=03
FC: あいう / 　　えお   cur=04 line=03
FA: あいう             cur=02 line=03
FF: あいう             cur=03 line=01
```

`F0` 은 `FC` 와 같았습니다. `FA` 는 줄을 바꾸고 끝나 뒤 바이트를 찍지 않았고, `FF` 는 줄을 바꾸지 않고 끝났습니다. `FD` 는 `あい` 에서 멈췄다가 278프레임에 A 를 누르자 283프레임에 둘째 줄 `うえ` 가 나왔습니다. 같은 자리의 `FB` 는 줄을 바꾸지 않고 기다린 뒤 첫 줄 앞을 덮어썼습니다(`うい`).

`F3` 에 주문 2 를 주니 `メラゾー` 가 나왔습니다. 주문 이름에서 마지막 글자를 뺍니다. `F2` 는 `$00/$01` 이 가리키는 이름을 찍는데, 이 포인터는 처리기가 정하지 않습니다. `textforce.lua` 의 `AT` 로 `F2` 처리기 들머리(`16:$82C3`)에서 `$00/$01` 에 아이템 1 의 이름 자리 `0B:$B1F7` 을 썼습니다.

```
FAKE="F2 00 F7 FF" ARGS=F9=55,FA=02 AT=82C3:00=F7,01=B1
→ こんぼう　どうのつるぎ
```

`F2` 가 인자 `$F9` 를 하나 건너뛰었기 때문에 다음 `F7` 이 `$FA`(아이템 2 `どうのつるぎ`)를 가져갔습니다.

## 2. もどき

`F6` 처리기는 몬스터 이름을 찾기 전에 `BRK 29 C3 0C` 를 부르고, carry 가 켜지면 동료 이름에 `もどき` 를 붙입니다. 이 BRK 동안 읽히는 RAM 을 적었습니다.

```
rd 6E59=29 pc=A34D     ← b1(명령 29)
rd 0082=8C pc=A957     ← 셋째 바이트 0C | 80
rd 727A=C0 pc=A971     ← AND ($84),Y, $84/$85 = $7274, Y = 6
```

`0C` 의 아래 3비트가 비트 번호(4), 나머지가 바이트 순번입니다. 몬스터 칸 0 의 전투 레코드 `$7274` 바이트 6 의 bit4 를 봅니다. 전투 세이브스테이트에서 `$727A` 를 `D0` 으로 두고 `001F` 를 띄웠습니다.

```
しかし　ライアンもどきは　ねむっている！
ライアンもどきに　9のダメージ！
```

몬스터 목록 창도 `ライアンもどき — 1ひき` 로 바뀌었습니다. 뒤에 `Ａ`~`Ｈ` 는 붙지 않습니다. 어느 몬스터가 이 비트를 켜는지는 아직 모릅니다.

## 3. 전투 창을 읽는 디코더

전투 창 줄 버퍼를 24칸으로 읽으려고 버퍼를 다시 보니, 버퍼는 3줄이 아니라 4줄(`$C0` 바이트)이었습니다. 글자 칸 = `$0552 × $54 + $0551`(`16:$85B3`)이고 `$0552` 는 1·3·5·7 입니다. 폭 `$54` 로 바꾸자 24칸 줄의 탁점 자리가 맞았습니다.

그런데 전투 덤프를 메시지와 비교하니 여전히 틀린 탁점이 나왔습니다. 버퍼 쓰기를 기록해 보니 원인이 보였습니다.

```
101 w 06B2=3D pc=8327 52=20 0552=01   ← ライアンの　こうげき！ 의 げ(8칸)
281 w 06AE=3D pc=8327 52=1C 0552=01   ← おおみみずの　こうげき！ 의 ず(4칸)
281 w 06B3=3D pc=8327 52=21 0552=01   ← 같은 문장의 げ(9칸)
```

전투는 메시지마다 버퍼를 지우지 않고 첫 줄부터 덮어씁니다. 8칸의 탁점은 그대로 남습니다. 화면은 메시지마다 창을 지우고 글자마다 nametable 에 바로 찍으므로(글자 행 `$0552 + 13`, 열 `$53`) 문제가 보이지 않습니다. 그래서 전투 덤프는 nametable 에서 읽게 했습니다. 걷다 만난 전투 5턴을 10프레임마다 덤프해 비교했습니다.

```
ok 99 lines 196 bad 0 empty 70 {'nametable': 99}
```

창이 보이는 99개가 모두 맞았고, 같은 99개를 버퍼로 읽으면 33개가 달랐습니다. 비교하려면 치환(`F6` 이름, `F8` 숫자)을 아무 글자와 맞추고, 한 창에 차례로 나온 메시지 여럿을 이어 붙여야 했습니다. `--compare` 에 `004C,0016,…` 처럼 번호를 여럿 받게 했습니다. 24칸 줄이 있는 `0050`·`0193`·`01E5` 도 전투에서 띄워 맞는 것을 봤습니다.

필드 쪽도 다시 확인하다 하나를 더 고쳤습니다. 대사가 끝나 다른 창이 열리면 `$54` 가 `0F` 로 바뀌어 폭을 잘못 읽습니다. 필드는 22칸으로 고정하고, 자동 `＊「`(`$058B ≥ 5`)도 넣어 비교하게 했습니다. 왕에게 두 번 말을 건 덤프 71개가 `060A` 와 맞았습니다.

## 4. 창 문자열 표

`16:$A572` 를 읽는 코드는 `16:$97D8` 이었습니다. 그룹 번호 `$03D6` 으로 `$A578`·`$A674` 중 하나를 고르고, 항목 번호 × 2 를 `16:$A576` 의 `70`·`14` 와 비교합니다. 작으면 그 포인터로 뛰고(루틴), 크면 문자열로 찍습니다. 그룹 0 의 항목 `00`~`37` 은 코드였습니다.

문자열 안의 `80` 이상 바이트는 `16:$97B0` 이 같은 그룹의 항목 `b & 7F` 로 풉니다. `textwin.lua` 로 이 두 곳을 기록하며 つよさ 창을 열었습니다.

```
149 top g=0 n=44
149 ref g=0 b=84 code     ← せいべつ：[84]
169 top g=0 n=4F
169 ref g=0 b=D4 str      ← [D4] = 항목 54 こうげきカ
169 ref g=0 b=90 code     ← ：[90]
```

화면에는 `せいべつ：おとこ`, `こうげき力：19` 가 나왔습니다(`カ`(`44`) 타일이 力 처럼 생겼습니다). `tools/dq4text.py rom windows` 로 표를 풀고, 기록에 나온 항목을 같은 때의 nametable 에서 찾았습니다. 필드 명령 창, つよさ 창, 전투 명령 창·몬스터 목록, 타이틀 메뉴에서 문자열 35개가 탁점 자리까지 같았습니다. 그룹 1 은 타이틀의 모험의 서 메뉴와 5장 전투의 `たたかう`·`いれかえ` 같은 문구였습니다.

## 5. 폰트를 올리는 루틴

앞 일지는 부팅 160프레임까지만 CHR 쓰기를 봤습니다. 이번에는 전원에서 2500프레임까지 `textfont.lua` 를 돌렸습니다.

```
5   chr=10B0 val=00 pc=8573 prg=68573 0507=1A
52  chr=10B0 val=20 pc=B7D6 prg=637D6 0507=18
154 chr=10B0 val=00 pc=8280 prg=68280 0507=1A
223 chr=10B0 val=20 pc=B7D6 prg=637D6 0507=18
```

`18:$B7D6` 은 `STA $2007` 이고, 들머리는 뱅크 `18` 함수 `08`(`18:$B7A3`)입니다. `$2006` 에 `$1000` 을 쓰고, 타일 `00` 에 0 을, 이어서 `$B848` 부터 140타일을 8바이트 + 0 8바이트씩 씁니다. 쓴 값 `20 FC 20 3C 66 AA 92 64` 는 `18:$B898`(글자 `0B` あ)과 같습니다. 읽기는 `0F:$C888` 의 `LDA ($00,X)` 로, PRG 읽기 콜백에 `18:$B848`~`$BCA7` 1120바이트로 잡혔습니다.

이 함수를 부르는 BRK 는 `1A:$802E`, `1A:$8088` 의 `BRK 08 8F` 였습니다. 처음에 `b2` 를 `1F` 로 셈해 롬에서 찾지 못했는데, 뱅크 `18` 은 `b2 >> 4 = 1` 에 bit3 을 더해 `8F` 입니다. 전원 직후 한 번, 타이틀 그림이 BG 를 지운 뒤 한 번 올리고, 그 뒤 왕좌의 방 대화·つよさ 창·성 앞에서 필드로 나가기·필드 보행과 전투 들어가기에서는 `$1000`~`$18CF` 에 한 번도 쓰지 않았습니다.

글자에서 화면까지의 사슬은 이렇습니다.

```
글자 바이트 g → BG 타일 g → CHR $1000 + 16g ← 18:$B840 + 8g (8바이트, 둘째 평면 0)
```

전투에 들어가면 BG 타일 `8D` 부터 몬스터 그림이 올라갑니다(아래 7절). 한글 글자를 FC 쪽에서 늘린다면 이 자리를 몬스터 그림과 나눠 써야 합니다.

## 6. BRK 호출을 모두 잡기

`textbrk.lua` 를 만들었습니다. BRK 처리기 `$C408` 에서 스택의 복귀 주소로 호출 위치를 알아내고, BRK 직전과 같은 스택 높이에서 BRK+1~+6 중 어디가 처음 실행되는지로 실제 길이를 잽니다. 장 시작 세이브스테이트 다섯 개, 왕좌의 방, 성 앞, 필드 보행과 전투, 전원 직후에서 돌렸습니다.

```
1365 prg=487D1 message 009
1445 prg=48825 message 00C
288  prg=7A354 flag-set 6291 was=00 mask=80
643  prg=7A399 flag-set 6288 was=00 mask=40
643  prg=7A620 flag-test 6288 was=40 mask=40
725  prg=7A41B flag-clear 6288 was=40 mask=BF
```

메시지 형식은 전투 끝(`12:$87D1` 등)과 4장 시작(`1D:$AB7D`)에서 잡혔고, 같은 프레임에 `16:$8656` 이 같은 번호로 들어갔습니다. 플래그 켜기는 장 시작 처리(`1E:$A354`)에서, 끄기는 `1E:$A41B` 등에서 잡혀 뒤 검사에서 값이 바뀐 것을 봤습니다. 모두 BRK+4 로 돌아왔습니다.

`x3` 형식은 호출 위치 191곳의 실제 복귀 자리를 얻었습니다. `dq4bank.py` 의 규칙으로 계산한 길이와 191곳 모두 같습니다.

## 7. 뱅크 06·07

두 뱅크는 다섯 장면에서 실행도 읽기도 없었습니다. 필드에서 걷다 전투에 들어가는 장면에서 PRG 읽기를 뱅크까지 적으니 나왔습니다.

```
pc=3C7EC b07 n=204  range=08000-0803F frames=387-387
pc=3C7EC b06 n=3092 range=08E63-0AE2E frames=389-403
```

`0F:$C7E1` 은 A 가 정한 뱅크에서 17바이트를 `$0108` 에 읽어 오는 루틴이고, 부른 곳은 `14:$9F7F` 였습니다. 같은 프레임들에 CHR `$18D0`~`$1B9F`(BG 타일 `8D`~`B9`)가 써졌고, 이 전투의 몬스터는 はさみくわがた(ID `03`) 하나였습니다. 뱅크 `06`·`07` 은 압축된 전투 몬스터 그림으로 보고, 압축 형식은 남겼습니다.

## 틀렸던 것들

- `x3` 의 길이를 「함수 번호가 홀수면 BRK+3」 으로 적었는데, `93`(함수 `09`)은 41곳 모두 BRK+4 였습니다. 함수 `08`·`09` 는 `$77` 이 `93` 이면 한 바이트, 아니면 두 바이트를 더 읽습니다.
- 창 줄 버퍼를 3줄·22칸 고정으로 읽었습니다. 4줄이고 폭은 `$54` 이며, 전투는 버퍼보다 nametable 이 맞습니다.
- 폰트 함수의 BRK 를 `08 1F` 로 찾았습니다. 뱅크 `18` 의 `b2` 는 `8F` 입니다.
- 창 문자열 표의 `80` 이상을 「창 명령」 이라 불렀는데, 같은 표의 다른 항목(루틴·문자열)을 부르는 바이트였습니다.

## 남은 것

- `もどき` 비트를 켜는 몬스터·주문.
- 창마다 위치·크기·항목 목록을 정하는 곳, 루틴 항목 하나하나가 찍는 값.
- `BRK 08 8F` 의 다른 자리 `1C:$94CD`, `1D:$8E23`, `1E:$A362` 가 실행되는 장면. 필드·마을 그림이 BG 타일 `8D` 이상의 어디를 쓰는지.
- `x3` 의 `13`, `83`, `F3` 을 실행 중에 보지 못함.
- 뱅크 `06`·`07` 의 압축 형식과 몬스터마다의 자리.
