# DQ4(FC) 맵 블록·타일·팔레트·통행

마을·던전 맵과 필드는 16×16 픽셀 블록 32개(맵 종류마다 다름)로 그립니다. 이 문서는 블록 번호가 8×8 타일 4개·팔레트·통행 속성으로 바뀌는 과정, 타일 그림을 어디서 CHR-RAM 으로 올리는지, 걸을 때 통행과 지형 효과를 어떻게 정하는지 정리합니다. 디코더는 [fc/dq4/tools/dq4block.py](../tools/dq4block.py), 실험 과정은 [2026-10-25-16 일지](../journal/2026-10-25-16-block.md) 에 있습니다. 맵 해제(`$7800`)는 [dq4-map-format.md](dq4-map-format.md), 필드 타일 번호는 [dq4-field-format.md](dq4-field-format.md) 를 따릅니다.

주소 표기는 `뱅크:$주소` 이고, 근거 표시가 없는 것은 MesenCE 덤프와 디코더 결과가 같음을 확인한 것입니다. 「코드 읽기」 는 리스팅만 읽고 실험으로 확인하지 않은 것입니다.

## 블록 정의 표

`08:$80B3` 의 포인터(`$8ADB`)부터 맵 종류마다 64바이트, 블록 0~1F 마다 2바이트 `a b` 입니다(`08:$8055`).

| 바이트 | 비트 | 뜻 |
| --- | --- | --- |
| `a` | 7-5 | 종류(`$6F20`). 그늘 바꾸기가 씀(아래). 0 이 아니면 맵에 안 쓰여도 올림 |
| `a` | 4-3 | 팔레트(`$76C0`) |
| `a` | 2-0 | 모양 레코드 번호 상위 3비트. `7` 이면 블록 없음(아무것도 올리지 않음) |
| `b` | 7-0 | 모양 레코드 번호 하위 8비트 |

블록 정의 `00 17` 은 `$615A`(장 − 1, 1장이 0)가 1(2장)이 아니면 `00 12` 로 바뀝니다. 2(3장)일 때는 `$6286` bit4 가 켜져 있어야 바뀝니다(`08:$808E`, 코드 읽기. 1장 세이브스테이트(`$615A`=`00`)에서 필드의 블록 16 이 `00 12` 로 올라간 것은 확인).

블록 20·21 은 지금 주인공이 서 있는 구역과 다른 구역의 칸을 그리는 데 씁니다(아래 「구역」). `08:$853E` 가 맵 종류 t 로 `08:$8AA2` 표에서 2비트(바이트 t>>2, 위 비트부터)를 골라, `08:$8AAF`+선택×4 의 2바이트 정의 두 개를 블록 20·21 로 올립니다. 필드(맵 종류 `00`)는 올리지 않습니다.

### 모양 레코드

`08:$8235` 의 포인터(`$A80D`) + 번호×3 의 3바이트입니다(`08:$80D5`).

| 바이트 | 뜻 |
| --- | --- |
| 0 | CHR 번호 하위 8비트 |
| 1 | bit7-4 모양(0~F), bit2 그림 뱅크(0 이면 `0C`, 1 이면 `0D`. 모양 E 는 보지 않음), bit1-0 CHR 번호 상위 2비트 |
| 2 | 속성(`$6F40`). 아래 「통행」 |

모양 0~D: 첫 타일 주소 = (`08:$8229`+2×뱅크비트 의 워드) + CHR 번호×16. 뱅크 `0C` 는 `$8000`, `0D` 는 `$7F01` 이 기준입니다. 나머지 세 타일은 `08:$8237` 의 포인터(`$A1BB`)+모양×3 의 부호 있는 바이트 세 개만큼 앞 타일에서 16바이트 단위로 떨어진 주소입니다. 모양 F: `08:$8225` 의 포인터(`$A28D`)+CHR 번호×8 에 타일 주소 네 개가 그대로 있습니다(`08:$81C6`).

모양 E(`08:$81E8`): `08:$8227` 의 포인터(`$AEB7`)+CHR 번호×2 의 주소부터 이어진 4타일이고, 그림 뱅크는 `0C` + `$76`(= `11`) = `1D` 입니다(`08:$83D9`). 타일 애니메이션의 그림이 있는 뱅크이고, 롬에서 모양 E 를 쓰는 블록은 애니메이션 블록 전부(첫 프레임 그림을 그대로 올림)와 맵 종류 `0F` 의 블록 1F(`1D:$891E` 의 물, 애니메이션 없음)입니다.

타일 순서는 왼위, 오른위, 왼아래, 오른아래입니다.

### 타일 그림 올리기

그림은 PRG 뱅크 `0C`·`0D` 에 압축 없이 2bpp 16바이트 타일로 있습니다. `08:$83BD` 가 `0F:$C7E1` 로 그 뱅크를 끼워 16바이트를 PPU 로 복사합니다. 타일 번호는 `8D` 부터 차례로 붙습니다(`08:$84FF`).

- 같은 그림 주소는 다시 올리지 않고 먼저 올린 번호를 씁니다(`08:$823D`, 주소 목록 `$7700`).
- 맵(종류 `00` 이 아님)에서 종류 비트도 속성(아래 7비트)도 없는 블록은 맵(`$7800`)이나 바깥 블록 `$0520` 으로 쓰였을 때만 올립니다(`08:$8487`, 쓰인 블록 표시는 `1E:$A046` 이 `$6E5E` 에).
- 맵 종류 `1E` 가 아니면, 블록 번호가 가장 작은 「안 쓰인 블록」 칸에 정의 `18 11` 을 타일 번호 `FC`~`FF` 로 올립니다(`08:$8710`). 종류 비트가 있는 블록은 쓰인 것으로 칩니다.
- 같은 주소 찾기는 뱅크를 보지 않고 주소 2바이트만 비교합니다. 애니메이션 블록에 따로 정한 예외는 없습니다. 모양 E 블록은 뱅크 `1D` 의 블록마다 다른 주소라 찾아도 걸리지 않고, 그래서 늘 이어진 새 타일 4개를 받습니다.

필드(맵 종류 `00`)도 같은 루틴으로 올리고, 블록 32개를 모두 올립니다.

### 타일 애니메이션

`1D:$802A` 가 맵 종류로 `1D:$8096` 목록을 찾습니다. 목록의 bit7 이 켜진 값마다 무리 번호가 하나씩 늘고, 아래 7비트가 맵 종류입니다(`2D` / `2C` / `0E` / `01`·`06`·`08`·`10`). 칸 8개마다 블록 번호(`1D:$8096` 안의 순번 × 8 + 칸, `1D:$80A6`)와 그림 원본 주소(무리 × 16 + 칸 × 2, `1D:$80DE`, 0 이면 빈 칸)가 있습니다. 프레임마다 `1D:$8C52` 가 그 블록의 첫 타일부터 이어진 4타일(64바이트)을 뱅크 `1D` 의 그림으로 덮어씁니다.

| 맵 종류 | 블록 | 그림 |
| --- | --- | --- |
| `2D` | 0E 0F 10 11 12 13 14 1F | `1D:$811E`~`$849E` |
| `2C` | 0D 0E 19 1B | `1D:$851E`·`$859E`·`$861E`·`$869E` |
| `0E` | 14 | `1D:$871E` |
| `01` | 0B | `1D:$891E`~ |
| `06` | 10 | `1D:$891E`~ |
| `08` | 14 | `1D:$891E`~ |
| `10` | 1C | `1D:$891E`~ |

이 블록들은 모두 모양 E 라 블록 표를 올릴 때 이미 뱅크 `1D` 의 첫 프레임 그림을 받습니다(위 「모양 레코드」). 맵 종류마다 하나씩, 블록 표를 올린 직후(`08:$853B`)의 CHR 을 떠서 견주니 모양 E 블록을 올린 맵 종류 7가지(`2D`·`0E`·`01`·`06`·`08`·`10`·`0F`)의 뱅크 `1D` 타일 56개가 모두 디코더와 같았습니다. `2C` 는 고른 맵(`15/02`)에 그 블록이 쓰이지 않아 올리지 않았습니다.

처리 코드(코드 읽기): 고정 뱅크 `0F:$C9FC` 가 프레임마다 `BRK 00 DF`(`1D` 함수 0, `1D:$8B1E`)를 부릅니다. `$3E` 가 0 이 아니고 걷기 상태 `$0584` 가 2 이상이면 쉬고, 아니면 프레임 카운터 `$3C` 의 아래 4비트가 홀수일 때 `0F`→칸 0, `0D`→칸 1, …, `01`→칸 7 을 맡습니다(`1D:$8B2F`). 맵(`$28` ≠ 0, `18` 이 아님)이면 `1D:$8C52` 가 그 칸이 `$0569` 의 비트(bit7 이 칸 0)에 켜져 있을 때 원본 `$0572`/`$057A` + (`$3C` & `$0583`)×4 에서 64바이트를 칸의 첫 타일 `$056A`(블록 표 올릴 때 `1D:$802A` 가 `$7600` 에서 가져옴)부터 PPU 로 보냅니다. 그래서 칸 하나는 16프레임마다 바뀌고, 무리마다 값은 이렇습니다(`1D:$809E`·`$80A2`).

| 무리(맵 종류) | `$0569` | `$0583` | 프레임 |
| --- | --- | --- | --- |
| `2D` | `FF` | `10` | 2장, 16프레임마다 |
| `2C` | `1B` | `10` | 2장 |
| `0E` | `08` | `70` | 8장 |
| `01` `06` `08` `10` | `AA` | `10` | 2장 |

같은 함수가 팔레트도 돌립니다(`1D:$8B4A`). 필드(`$28` = 0)는 `$3C` & `0F` = `0F` 일 때마다 BG 팔레트 0 의 색 2·3(`$05FE`·`$05FF`)을 맞바꾸고, `$65` = 3 이면 팔레트 3 의 색 1~3(`$0606`~`$0608`)도 한 칸씩 돌립니다. 맵 종류 `18` 은 타일 대신 4프레임마다 팔레트 2 의 색 1~3(`$0603`~`$0605`)을, 16프레임마다 팔레트 1 의 색 1·2(`$0600`·`$0601`)를 돌립니다. 필드 0 세이브스테이트에서 `$05FE` 를 쓰는 곳이 `1D:$8B6E` 하나이고 16프레임마다 `12`↔`21` 로 바뀌는 것, 맵 종류 `18`(`3B/00`) 덤프의 팔레트 2 가 롬 값 `21 11 01` 을 돌린 `11 01 21` 인 것은 실측입니다. `$629A` bit7 이면 스크롤을 무작위로 흔듭니다(`1D:$8CE6`). `$3C` & 7 = 7 일 때 난수(`0F:$C891`)로 X·Y 마다 `1D:$8D1D` 의 짝(`00 00`·`01 FF`·`02 FE`·`04 FC`) 하나를 골라 `$0508`·`$0509` 에 앞 값을 더하고, 다음 프레임에 뒤 값을 더해 되돌립니다. 그래서 0·1·2·4픽셀 어긋난 화면이 한 프레임씩 끼어듭니다.

실측(`12/00`, 맵 종류 `0E`): 블록 14 의 원본 주소 `$02`/`$03` 을 `1D:$8C7D` 에서 찍으니 `$3C` = `07`·`17`·…·`77` 에서 `$871E`·`$875E`·`$879E`·`$87DE`·`$881E`·`$885E`·`$889E`·`$88DE` 로 차례로 넘어가고 `87` 에서 `$871E` 로 돌아왔습니다. 8장을 16프레임씩, 128프레임에 한 바퀴입니다. 흔들기는 맵에 들어갈 때 `08:$B6BD` 가 bit7 을 끄므로 들어온 뒤 `$629A` = `80` 을 써서 봤습니다. `1D:$8CF3` 이 약 10프레임마다 돌고 `$0508`/`$0509` 가 (+1, 0)·(+2, +1)·(+1, +2)·(0, +2) 처럼 바뀐 뒤 다음 프레임에 `80`/`00` 으로 돌아왔습니다.

## 맵 칸 → 화면

### 그늘 바꾸기

`1E:$9F47` 은 맵을 푼 뒤 칸마다, 블록 종류(`$6F20` 아래 3비트)가 1~3 인 칸의 아래 칸이 종류 0 이면 그 칸을 종류 5~7(= 1~3 + 4)인 블록으로 바꿉니다. 아래 칸이 다른 구역이면 맵 종류에 따라 다르게 정합니다(`1E:$A016`·`$A01C` 표). 디코더 `shade()` 가 같은 결과를 냅니다(확인한 모든 맵에서 `$7800` 0 바이트 다름).

### 맵 밖과 구역

- 맵 밖 칸은 바깥 블록 `$0520`(맵 헤더)입니다. `$0550` bit7 이 켜진 맵은 `0F:$D469`(X&7)·`$D471`(Y&7) 무늬로 `$0520` 과 `$0582`(`08:$8A92`+맵 종류, 종류 `0F` 미만만)를 섞습니다(`0F:$D44C`).
- 칸의 위 3비트는 구역입니다. 주인공 칸의 구역(`$46` = `$7140` 위 3비트)과 다른 칸은 블록 20(주인공이 구역 0) 또는 21 로 그립니다. 집 안에 들어가면 밖이 검게 가려지는 것이 이것입니다. `$07BA` 가 4 이면 바깥 블록은 구역과 상관없이 그립니다(`0F:$D4E6`).

### nametable

세로 미러링이라 nametable 두 장이 가로로 붙어 64×30 타일입니다. 화면 왼쪽 위 칸이 맵 좌표 (`$7C`, `$7B`), 스크롤이 X = (`$0505` bit0)×256 + `$0508`, Y = `$0509` 일 때, 화면의 (i, j) 번째 블록(16×15)은 nametable 의 (X/8 + 2i, Y/8 + 2j)(64·30 으로 나눈 나머지)에 2×2 타일로 들어가고 attribute 는 그 블록의 팔레트입니다(`0F:$EB23`). 블록 없음(`a`&7 = 7)인 블록은 타일 `00`(빈 타일)이라 attribute 는 이전 맵의 값이 남아도 보이지 않습니다.

## 팔레트

BG 팔레트 4개의 색 0 은 모두 `0F`(`$05FC`)이고, 색 1~3 의 12바이트를 `$05FD`~ 에 씁니다.

맵(`0E:$802B`):

1. 밤이면 1, 아니면 0. 밤은 `$62ED` ≥ `78`.
2. `0E:$BBB1`(그룹, `FF` 끝)·`$BBD3`(순번, `FF` 는 아무 순번)에 지금 장소가 있으면 그 순번 i 에 따라: i < 0E 이면 맵 종류 대신 `0E:$BBC5`+i 를 씀, i = 0E 이면 `$6293` bit4 일 때 `36`, i = 0F·10 이면 밤으로 침, 11 이상이면 낮으로 침. `$65` 가 3 이면 밤으로 침(`0E:$BB55`).
3. 세트 번호 = `0E:$BBE6`+(맵 종류×2 + 밤).
4. `0E:$BC68`+세트×4 의 4바이트가 팔레트마다 색 묶음 번호, 색 묶음은 `0E:$BD40`+번호×3 의 3바이트.

필드(`1E:$A296`): 시각 `$62ED` 를 `1E:$A2DB` 의 경계 8개(`00 78 7C 80 84 C0 C4 C8`)와 비교한 순번 x 로 `1E:$A2E3`+12x 의 12바이트를 그대로 씁니다. `$65` 가 3 이면 x = 8.

### せかいじゅのは

속성 `33` 은 世界樹(그룹 `2F` 의 맵 넷, 블록 1C·1D)의 칸입니다. 발밑이 `33` 일 때 「しらべる」를 하면 `1E:$B423` 이 「〜は　あしもとを　しらべた。」(02A7) 뒤에 둘을 봅니다. `BRK 3A 0F`(`10:$A312`)는 `$616A` 목록에서 bit7 이 켜진 인물(번호 0~7) 가운데 누군가의 소지품(레코드 `$13`~`$1A`)에 `57` 이 있으면 C=1 이고, `1E:$BC20` 은 ふくろ(`$61DA`~)를 봅니다. 둘 다 없으면 `57` 을 줍니다(`1E:$B5A3`). 하나라도 있으면 「なんと　せかいじゅのはを　みつけた！」(0298) 뒤 「しかし　せかいじゅのはは　ぬけなかった！」(04C6)로 끝납니다. 칸 자리는 보지 않으므로 `33` 칸 어디서나 같습니다.

실측(1장 일행, 라이안 소지품 `82 A6 FF …`): `2F/03` (02,04) 에서 두 번 「しらべる」 → 첫 번째는 `$B434` 를 지나 소지품 셋째 칸에 `57`, 두 번째는 `$B43B`. 라이안 소지품에 `57` 을 넣고 하면 첫 번째부터 `$B43B`. `2F/00` (0A,04) 도 첫 번째에 받았습니다. ふくろ 는 `$61DB` 부터 `FF` 앞까지의 아이템 목록이고(개수 = `15:$B3B2`, 최대 128), `1E:$BC20` 은 끝에서부터 `$61DA`+개수 ~ `$61DB` 를 봅니다. ふくろ 에 `57 FF` 를 넣고 「しらべる」 하니 `1E:$BC32`(찾음) 뒤 `$B43B` 로 가 받지 못했고, 비운 대조 실행은 `$BC30` 뒤 `$B434` 로 가 라이안 소지품 셋째 칸에 `57` 이 들어갔습니다.

값이 `FF` 가 아니면(그룹 `47`·`45`) 그 값 n 이 `1E:$8A24` 의 5바이트 레코드(구역, 폭, 높이, `$7800` 주소)를 고릅니다. 떠날 때 `1E:$8A0D` 가 그 사각형 칸들의 위 3비트를 구역 `80` 으로 바꾸고(`1E:$8A68`·`$8A9A`), 내린 뒤 `1E:$8A48` 이 `1E:$8A42`+n 의 구역(`60 40 20 20 20 20`)으로 바꾸며 주인공의 구역 `$46` 도 그 값으로 둡니다. 사각형은 모두 6×5 이고, 목적지 칸을 둘러싼 리프트 바닥입니다(`47/00` 의 n=0 은 (1B,01)~, n=1 은 (27,01)~, `45/04` 의 n=2 는 (22,15)~, `45/06` 의 n=3 은 (05,0B)~, `45/05` 의 n=4 는 (19,0F)~, `45/07` 의 n=5 는 (06,01)~). 리프트를 타는 동안 바닥을 다른 구역으로 떼어 그리고, 내리면 도착한 곳의 구역에 붙이는 것으로 봅니다. 디코더 `lift_rects()`.

실측: `47/00` (2B,04) 에서 위로 (2B,03) 을 밟자 `$7F` = `00` 으로 `1E:$8A0D`·`$8A68` 을 지나 (1F,03) 에 섰고, 끝 덤프에서 n=0 사각형 30칸의 구역이 모두 3, `$46` = `60` 이었습니다. 타는 동안 `80` 으로 바뀌는 것은 코드 읽기입니다.

### 출구 칸 연결

출구 표 `$05A0`([dq4-map-format.md](dq4-map-format.md#출구-표-05a0))에 없는 출구, 곧 계단·旅の扉·리프트 칸의 목적지는 `08:$B22E`(BRK `08` 함수 `0A`)가 정합니다. 계단 등(`06`~`09`·`25`·`26`·`0C`)은 `1E:$9100` 이, 旅の扉(`0A`)는 연출 뒤 `1B:$A118` 이 부릅니다. 걸음마다 먼저 도는 `1B:$8014` 가 `$05A0` 의 칸을 처리하므로 두 경로는 겹치지 않습니다(맵 279개에서 두 표에 다 있는 칸 0).

1. **고정 표** `08:$B681`(`08:$B323`): 9바이트 = 그룹, 순번, x, y → 그룹, 순번, x, y, 방향. 6항목, `FF` 끝.
2. **칸 순번**(`08:$B4ED`): 맵 버퍼 `$7800` 을 줄마다 왼쪽부터 읽어, 속성 아래 7비트가 `08:$B675` 의 목록(`08 09 26 25 0F 0A 06`)에 드는 칸을 셉니다. 지금 칸 앞까지 센 수가 이 칸의 순번 i 입니다.
3. **연결 표** `08:$B974` 의 포인터(`$B976`, `08:$B246`): 그룹마다 그룹 바이트, 레코드들, `FF`. 레코드 첫 바이트 bit7 이 그 순번(맵)의 마지막 레코드이고, bit6-5 가 종류, bit4-0 이 목적지 순번입니다. 맵 순번 k 의 목록까지 건너뛴 뒤 레코드 i 개를 건너뜁니다. 목록 끝을 보지 않아서 레코드보다 칸이 많으면 다음 맵의 레코드를 읽습니다.

| bit6-5 | 길이 | 바이트 | 목적지 |
| --- | --- | --- | --- |
| `0` | 1 | `k` | 필드. 이 그룹의 필드 입구(`0E:$BE69` 의 첫 항목) 좌표, 필드 번호는 도착 표 `08:$B7F9` 의 bit6-5(`08:$B06A`). `41` 의 (0E,30) 은 (8D,1F), `42` 의 (1F,02) 는 (84,5A)(`08:$B2EC`) |
| `1` | 3 | `k` n g | 그룹 g 의 순번 k, 그 맵에서 센 n 번째 칸 |
| `2` | 2 | `40` g | 그룹 g 에 필드에서 들어갈 때의 도착 자리(`08:$AF13`). 하나뿐인데(`2D/00` 의 0번) 고정 표가 먼저 잡음 |
| `3` | 2 | `k` n | 같은 그룹의 순번 k, n 번째 칸 |

4. **목적지 바꾸기**(`08:$B397`): 목적지가 `3D/01` 이고 `$62AA` bit7 → `3D/02`, n 이 1~3 이면 n+1. `40/01`·n 0·bit5 → `40/02`. `45/04`·n 0 또는 4·bit4 → `45/06`(n 4 는 5). `45/05`·n 2·bit1 → `45/07` n 3. `42/01`·bit3 → `42/00`. `19/00` 이고 밤 → `19/01`. `15/03` 이고 낮 → `15/02`. `34/03` 이고 `$6295` bit0 이 꺼짐 → `34/02` n 0. `14/00`·`$62AA` bit0 → `14/02` n 0. 목적지 그룹 `18` 은 `$6280` bit1 이면 `18/01` (00,0F)(`08:$AF51`, 필드에서 들어갈 때). 실측은 아래 「목적지 바꾸기 실측」.
5. 목적지 맵을 푼 뒤 `08:$B554` 가 같은 방법으로 n 번째 칸을 찾아 `$44`/`$45` 에 둡니다. 도착 방향은 그 칸의 속성으로 정합니다(`08:$B59F`): `08` 왼쪽, `09` 오른쪽, `25`·`26` 위, `0F`·`0A` 아래.

롬 전체(디코더 `exit_links()`, `links` 명령): 센 칸 555개(`08` 262, `09` 249, `0F` 14, `25` 11, `0A` 9, `26` 9, `06` 1) 가운데 528개가 맵, 21개가 필드, 4개가 고정 표, 2개(`09/07`·`0D/02` 의 (06,1D))는 레코드가 없습니다(아래). 연결 표의 레코드는 73그룹 584개(종류 3 516, 0 52, 1 15, 2 1)입니다. 칸이 없는 맵에도 레코드가 하나씩 있습니다(목록의 끝 표시).

#### 레코드가 없는 칸

`09/07`·`0D/02` 는 `13/01` 과 맵 데이터가 같은 11×35 맵입니다. 아래쪽 방(계단 (06,1D))은 벽으로 닫혀 있고, 위쪽 도착 칸 (07,07)에서 칠해 보면 47칸만 닿아 이 계단에 걸어서 갈 수 없습니다. 그 방으로 들어오는 연결 레코드도 출구 표 `$05A0` 항목도 없습니다. `13/01` 에서는 같은 계단이 `13/00` 으로 이어집니다.

순번 1 의 레코드 자리는 그 그룹 표의 끝 `FF` 입니다. `FF` 를 종류 3(같은 그룹)·순번 `1F` 로, 다음 그룹 바이트를 n 으로 읽습니다. 디코더는 이 칸을 `invalid` 로 표시합니다. 워프로 (06,1E)에 세워 위로 한 걸음 밟으면 `09/07` 은 없는 맵 `09/1F` (19,49)(초록 무늬로 찬 화면, 맵 종류 `0E`)에 섰고, `0D/02` 는 게임이 처음부터 다시 시작해 타이틀 화면으로 돌아갔습니다. 걸어서 못 가는 자리라 게임에서는 생기지 않습니다.

#### `$07BA`

### 문과 열쇠

문은 막힌 칸(bit7)이고 아래 7비트가 `14`~`23` 입니다. `1E:$B3C8` 의 16바이트가 4개씩 잠금 단계를 나눕니다(`1E:$B36E`).

| --- | --- | --- |
| 0 | `14` `18` `1C` `20` | 열쇠 없이 |
| 1 | `15` `19` `1D` `21` | とうぞくのカギ(`71`) 이상 |
| 2 | `16` `1A` `1E` `22` | まほうのカギ(`72`) 이상 |
| 3 | `17` `1B` `1F` `23` | さいごのカギ(`73`) |

같은 줄의 네 값(열)은 문 모양이고 `08:$8796`(BRK `08` 함수 `12`)이 연 뒤 바꿀 블록을 고릅니다. 롬에 쓰인 문은 모양 0 의 `94`·`95`·`96`·`97`(한 칸), 모양 2 의 `9C`·`9D`, 모양 3 의 `A0`·`A2`(2×2)입니다. 모양 1(`18`~`1B`)은 쓰이지 않습니다.

- 모양 0(`14`~`17`): 선 칸과 문 너머 칸(선 칸에서 두 칸 앞)의 블록 정의에서 모양 레코드 번호(`a` 아래 2비트, `b`)를 `08:$882A` 의 목록(`074 035 042 078 031 01A 01C 013`, `FFFF` 끝)에서 찾아(`08:$880E`), 앞쪽에 있는 블록을 문 칸에 씁니다. 같거나 둘 다 없으면 선 칸의 블록입니다. 디코더 `door_open()`. 실측: `00/00` (07,08), `01/02` (04,07), `03/00` (17,07), `07/00` (1A,19), `08/02` (05,0A), `04/0E` (08,02) 에서 さいごのカギ(`73`)를 쥐고 「とびら」 → 6곳 모두 예측한 블록(넷은 문 너머 칸의 블록)이 `$7800` 과 `$6C0C` 항목에 들어감. 앞서 본 `02/01` (03,0C) 의 `07` 도 같음.
- 모양 2(`9C`·`9D`, `08:$8855`): 선 칸에서 앞 칸과 그 옆(위·아래로 열면 왼쪽 칸, 왼쪽·오른쪽으로 열면 위 칸)의 속성이 같은지로 문의 왼쪽 위 칸을 정하고, 문을 지나 한 칸 더 간 칸 하나의 값(`$53`)을 고릅니다. 위·왼쪽·오른쪽으로 열면 문의 왼쪽 열·위 줄 너머 칸이고, 아래로 열 때만 오른쪽 열 너머 칸입니다(`08:$88E5` 가 `$06` 대신 `$04` 에 한 번 더 써서). `1E:$835D` → `$8392` 가 네 칸에 그 값의 블록(아래 5비트)만 쓰고 칸의 구역은 그대로 둡니다(`1E:$9E92`). `$6C0C` 항목은 문의 오른쪽 아래 칸 주소, 순번|`80`, 고른 값(구역 포함)입니다. 디코더 `door_open_2x2()`.
  실측(さいごのカギ를 쥐고 「とびら」): `30/02` 의 문 (18,0E)~ 를 왼쪽에서 열면 `06`, 오른쪽에서 열면 항목 값 `46`·칸 `06`. `36/01` (0A,06) 위로 `14`. 너머 칸을 메모리에서 서로 다른 블록으로 바꿔 두고 연 다섯 번(`3C/00` 위·아래, `33/01` 오른쪽 두 자리·왼쪽)도 모두 예측한 칸의 블록이었습니다(`3C/00` 아래로: 왼쪽 너머 `07`·오른쪽 너머 `11` 가운데 `11`). 항목 주소 `$7A6B`(`3C/00` 문의 (2F,0B))·`$7850`(`33/01` 의 (08,06))이 오른쪽 아래 칸입니다. 앞 판의 「`41`(구역 2)」는 문 위의 벽 칸에 서서 연 결과이고, 「왼쪽 위 칸 주소」는 틀렸습니다.
- 모양 3(`A0`·`A2`, `08:$88FE`): 문 칸과 같은 속성을 가진 블록을 `$6F40` 에서 앞에서부터 찾아 첫째를 `$0540`, 셋째를 `$0541` 에 두고 A=1 로 돌아옵니다. 그러면 `1E:$8383` 이 소리(`BRK A9 FB`) 뒤 성문 연출 `1B:$8706`(`BRK 03 BF`, 맵 종류 `32` 면 X=2)을 부릅니다. 연출이 블록 `$0540`·+1 의 속성을 `80`, `$0541`·+1 을 `24` 로 바꾸므로(`1B:$885F`~`$886D`) 아래 줄로 지나갈 수 있고, 그 너머는 출구 표 `$05A0` 의 칸입니다. `$7800` 과 `$6C0C` 은 바뀌지 않아, 다시 들어오면 닫혀 있습니다. 실측: 「とびら」로 `04/00` (17,0A)·`0D/00` (08,0B)·`46/00` (13,09)·`3C/08` (04,04)의 `A0`, `00/00` (0F,0F)의 `A2` 가 모두 열리고, 위로 두 걸음에 `04/02`·`0D/01`·`46/03`·`3C/07`·`00/01` 로 들어갔습니다. `00/00` 의 `A2` 는 잠금 2 라 열쇠 없이는 0361, とうぞくのカギ로는 0360 이고 まほうのカギ부터 열렸습니다. 앞 판의 「열리지 않음」은 연출을 기다리지 않고 `$6C0C`·`$7800` 만 본 것이었습니다.

- 「とびら」(명령 창 7번째, `1E:$B2A6`): 앞 칸이 문이면 잠금 0 은 바로 엽니다. 아니면 일행이 가진 가장 센 열쇠(`1E:$B3B7` 가 `73`→`71` 순으로 `BRK 66 73`)의 순번이 잠금−1 이상이면 엽니다. 열쇠가 없으면 「かぎを　もっていない。」(0361), 모자라면 「かぎが　あわない。」(0360). 문이 아니면 「ここには　とびらがない。」(035E), 속성 `AC` 는 「この　とびらは　ひらきそうにない。」(03F2), 그룹 `3F` 의 `B0` 은 「がんじょうそうな　とびらだが　3にんで　おせば　こわせそうだ！」(03EC). 4장(`$615A`=3, 1장이 0)에서는 잠금 2 문(`16`·`1A`·`1E`·`22`) 앞에서 `BRK 63 63 03`(A=`09`)으로 オーりン(인물 번호 `09`, [dq4-script-format.md](dq4-script-format.md#인물-번호))이 일행에 있는지 봅니다(`1E:$B381`). 셋째 바이트 `03` 은 `$6E0A` 의 bit0(레코드 바이트 0 bit7, 살아 있음)·bit1(바이트 0 bit6 이 꺼짐) 조건이고 bit6·bit7 이 꺼져 있어 걷는 자리와 마차 자리를 다 셉니다(`10:$8254`·`$826D`·`$829B`). 있으면 창 `52`(가게·여관과 같은 메시지 창)를 열어(`BRK 07 6F 52`) 「カギが　かかっている！ ▼ しかし　オーりンが　カギを　こじあけた。」(03A5) 뒤 열쇠 없이 여는 경로(`1E:$B32A`)로 갑니다.

  실측(1장 일행, `04/02` (06,0D)의 `96` 앞, 도착 뒤 `$615A` = `03`, 레코드 9 `$610F` 바이트 0·5 를 써서 손님 オーりン으로): 걷는 둘째 자리(`$616B` = `89`, `$610F` = `80`, `$6114` = `C6`)는 C=1 로 `$B3A2` 를 지나 문이 열렸고 `$6C0C` = `79 72 02 69`. 마차 자리(`$618E` = `20`, `$6172` = `89`)도 같았습니다. 바이트 0 이 `00`(죽음)이면 C=0, オーりン이 없으면 C=0 으로 열쇠 검사(`1E:$B3B7`)로 갔고, `$615A` = `02` 면 이 검사를 건너뛰었습니다.
- 열쇠를 「どうぐ」로 쓰면 `12:$A78A` → `1E:$8346` 이 같은 일을 합니다(`$6279` = 쓴 열쇠, `1E:$B33B`, 코드 읽기).
- 연 문은 `$6C0C` 의 4바이트 목록(최대 40개, `FF` 끝)에 남습니다: `$7800` 버퍼 주소 상위·하위, 순번(bit7 이면 2×2 문), 바꾼 블록. 맵을 그릴 때 `1E:$A0B3` 이 칸을 돌며 속성 `14`~`23`(문) 칸만 골라 `1E:$A0D6` 에서 주소·지금 순번이 같은 항목을 다시 씁니다(코드 읽기). 그룹은 적지 않습니다.
- 목록을 지우는 곳: `1E:$A615` 가 `$6C0C`~`$6CAB`(160바이트)를 `FF` 로 채웁니다. 맵에서 필드로 나갈 때(`1E:$930E`)와 게임을 시작할 때(`0F:$C97A` 의 `BRK 22 EF` → `1E:$A3BA`)가 부릅니다. 실측: 문을 연 `02/01` 에서 필드로 나가자 `1E:$A619` 가 써서 목록이 비었고, 전원을 켜 새로 시작한 실행에서도 493프레임째(1장 이야기 글이 뜬 뒤)에 160바이트를 썼습니다. 이벤트 `1D:$AEAE`·`$B379` 는 첫 바이트만 `FF` 로 씁니다(코드 읽기).
- 불러오기도 지웁니다. 성 앞마당에서 `$6C0C` 에 항목 하나(`79 83 01 07`)를 넣고 교회에서 저장, 리셋해 「ぼうけんのしょ」를 불러오자 `12:$AC47` 이 칸을 복사한 뒤 같은 프레임에 `1E:$A3A1`(저장한 자리로) → `0F:$C97A` → `1E:$A3BA` → `$A615` 가 160바이트를 `FF` 로 썼습니다. 그 실행에서 목록을 쓴 곳은 이것 하나였습니다. 세 번째 호출 자리 `1E:$A45B` 는 `1E:$A3BA` 뒤 갈래에서 `$628A` bit2 가 켜져 있을 때 bit2 를 끄고 bit1 을 켠 다음 목록을 다시 지우고 `1E:$84B6` 으로 갑니다(`1E:$A3FC`·`$A453`, 코드 읽기).
- 지우지 않는 곳: 같은 그룹 안(`02/01` → `02/02`), 맵에서 다른 그룹의 맵으로(`02/01` → `0E/00`, 출구 표 `$05A0` 경로) 옮겨도 목록이 `79 83 01 07` 로 남았습니다(실측). 그룹을 적지 않으므로 다른 그룹의 같은 순번·같은 주소에 문 칸이 있으면 그 문도 열려 그려질 수 있습니다(코드 읽기, 롬에 그런 자리가 있는지는 확인 안 함).

왕좌의 방 `02/01` 의 문(03,0C)(`95`)에서 확인했습니다. 열쇠 없이 「とびら」 → 0361. `$60CA` 에 `71` 을 넣고 「とびら」 → `$6C0C` = `79 83 01 07`(주소 `$7983` = (03,0C), 블록 `07`), 그 칸을 지나 (03,0D) 로 들어감. 위층 `02/02` 에 다녀와도 목록이 남고, 돌아오자 `$7983` 이 롬 값 `0C` 로 풀린 뒤 곧 `07` 로 다시 쓰였습니다.

### 따로 읽는 곳이 없는 막힌 값

## 기계가 읽는 지도

`json` 명령이 맵 279개·필드 3개(0·1·3)를 JSON 하나로 내보냅니다(기본 `work/dq4block.json`, 약 1.5MB, 커밋하지 않음).

| 키 | 내용 |
| --- | --- |
| `effects` | 속성 값(16진 문자열) → `terrain()` 결과(`walk`, `ship`, `effect`, `hp`, `dir`, `door{lock, shape, opens}`(`opens` 는 `cell`·`beyond_2x2`·`gate`), 속성 `33` 의 `item`, `talk_over`, `facing`) |
| `keys` | 열쇠 아이템 `71 72 73` |
| `maps[]` | `group`, `index`, `type`(맵 종류), `w`, `h`, `outside`(바깥 블록), `props`(블록 0~1F 의 속성, 없는 블록은 null), `cells`(줄마다 16진 문자열, 그늘 바꾸기 뒤 `$7800` = 위 3비트 구역 + 블록), `falls`(떨어지는 칸마다 `fall()` 결과, 방향은 아래로 침) |
| `fields[]` | `field`, `w`, `h`, `props`, `cells`(블록 번호) |
| `maps[].exits` | 출구 칸마다 `exit_links()`: `x`, `y`, `prop`, `ord`(칸 순번), `to`(맵이면 `group`·`index`·`n`·`x`·`y`·`dir`, 필드면 `field`·`x`·`y`, 고정 표면 `fixed`, 레코드가 모자란 첫 칸은 `invalid` 와 게임이 읽는 없는 맵 순번 `1F`·n). 목적지 바꾸기는 플래그 0·낮으로 계산 |
| `fall_table`, `lifts`, `lift_rects`, `pots`, `signs` | 위 표들. `signs[].at` 은 그 좌표에 `A8` 칸이 있는 맵 |
| `exit_kinds`, `exit_fixed`, `exit_table` | 출구 칸으로 세는 속성 값, 고정 표, 그룹마다 순번별 레코드 |

장소별 속성 고치기(`08:$8A2A`)는 `props` 에 들어가 있고, 성문 연출·연 문처럼 나중에 바뀌는 칸은 들어 있지 않습니다.

## 디코더

```sh
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes defs 0D          # 맵 종류 0D 의 블록 정의·애니메이션·낮 팔레트
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes 02 01            # 맵 02/01 의 통행 지도(텍스트)
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes 02 01 --nt       # 맵 전체의 nametable 타일 번호
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes 02 01 --png      # work/dq4block-02_01.png (확인용, 커밋 금지)
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes field 0 --png    # 필드 0
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes props            # 속성 값별 뜻·맵 수·칸 수(--maps 는 맵마다)
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes compare work/x   # seq.lua·warp.lua 의 end.* 덤프와 비교
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes effects 3C 01    # 맵의 속성 값마다 뜻·칸 수, 떨어지는 칸의 목적지
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes tables           # 속성 값마다 terrain(), 떨어지기·리프트·タンス/つぼ·팻말 표
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes links 1E 00      # 출구 칸마다 목적지(G K 를 빼면 모든 맵)
uv run python fc/dq4/tools/dq4block.py rom/dq4.nes json             # work/dq4block.json
```

통행 지도 글자: `.` 속성 `00`, `#` `80`, `~` `83`, 그 밖의 막힌 값은 소문자(맵마다 작은 값부터 `a`, `b`…), 지나가는 값은 `1`~`F`·`10` 부터 `G`…. 끝 줄에 글자마다 속성 값과 뜻을 적습니다. PNG 의 색은 NES 색을 근사한 것입니다.

## 확인

`compare` 는 덤프의 `$7600`·`$76C0`·`$6F20`·`$6F40`, CHR-RAM `$1000`~, BG 팔레트, `$7800`, 화면 16×15 블록의 nametable·attribute 를 디코더와 비교합니다.

| 덤프 | 맵 종류 | 결과 |
| --- | --- | --- |
| 1장 왕좌의 방·위층·성 앞 집 안(걸어서) | `0D`·`09`·`0A` | 모두 0 다름(성 앞은 성문 연출이 바꾼 블록 4개와 그 타일 16개만 다름) |
| 필드 0 | `00` | 모두 0 다름 |
| 워프로 맵 종류 48가지(`00` 제외 전부)마다 맵 하나 | `01`~`32` | 블록 표·팔레트·`$7800` 은 성 앞(`02/00`, 성문 연출)만 빼고 0 다름. CHR 은 `33/03`(종류 `0F`)의 블록 1F 타일 4개만 다름. nametable 은 34가지가 0 다름, 나머지는 상태 창·대화 창이 덮은 자리만 다름. 성 앞만 크게 달랐던 것은 덤프가 일렀기 때문: `WAIT=120`(도착 61프레임 뒤)에는 `$7C`/`$7B` 가 아직 왕좌의 방 값 (08,0F)이고 914타일 다름, `WAIT=200` 에서는 (0A,03)으로 0 다름 |
| 모양 E 를 고친 디코더로, 맵 종류 50가지마다 워프해 300프레임 뒤 | `01`~`32` | 블록 표·CHR(애니메이션 타일 뺌)·`$7800` 모두 0 다름(`33/03` 의 블록 1F 포함). 팔레트는 `18` 만 다름(팔레트 돌리기) |
| 같은 50가지, 블록 표를 올린 직후 `08:$853B`(`blockload.lua`) | `01`~`32` | CHR 0 다름, 뱅크 `1D` 타일 56개 0 다름, `$7600` 은 아직 올리지 않은 빈 칸 블록(FC~FF) 하나만 다름 |

걷기: 맵 8개(왕좌의 방, 마을 `0E/00`, 동굴 `34/00`·`3C/01`, 탑 `2C/00`, 성 `01/00`, `45/00`, 필드 0)에서 네 방향으로 200프레임씩 걸어 멈춘 자리를 통행 지도로 예측한 자리와 비교했습니다(32번). 속성 bit7 인 칸 앞에서 멈춘 23번은 모두 예측과 같았습니다. 나머지는 인물에 막힌 것(3), 맵 가장자리나 출구 표로 다른 맵에 나간 것(5: `3C/01` 의 오른쪽 끝 (21,04) 에서 한 걸음 더 가자 `3C/00` (02,14) 로), 미끄러지는 바닥에서 밀려난 것(1: `3C/01` 에서 왼쪽으로 걷다 `13` 을 밟자 (19,04) → (19,0C). `13`(왼쪽)에서 (15,04) 의 `12`(아래)로 이어진 길)입니다. 맵 밖 칸은 바깥 블록이 막혀 있어도 가장자리를 넘으면 필드로 나갑니다(`1E:$9155`).

## 남은 것

- 맵 종류 `2C` 의 블록 1B 는 올릴 때 `1D:$851E`, 애니메이션 원본은 `1D:$869E` 로 다름(덤프로 보지 않음). 맵 종류 `0E` 밖의 무리(`2D`·`2C`·`01` 등)의 프레임 순서는 같은 식의 코드 읽기.
