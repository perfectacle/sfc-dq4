# DQ4(FC) 디버그 스위치와 숨은 개발 기능

FC DQ4(일본판 Rev A)에 남은 개발용 기능과, 그것을 찾은 방법(실행 커버리지로 미실행 코드 모으기)을 정리합니다. 도구는 [fc/dq4/tools/dq4debug.py](../tools/dq4debug.py)(미실행 코드·후보 찾기), [fc/dq4/tools/lua/debugpad.lua](../tools/lua/debugpad.lua)(롬 바이트 덮어쓰기·패드 2 흉내), [fc/dq4/tools/lua/debugreads.lua](../tools/lua/debugreads.lua)(`$C000` 을 읽는 명령 모으기), [fc/dq4/tools/lua/debugtrap.lua](../tools/lua/debugtrap.lua)(PRG 오프셋으로 실행 잡기), [fc/dq4/tools/lua/debugsram.lua](../tools/lua/debugsram.lua)(전원을 켜기 전 SRAM 고정)이고, 과정은 [2026-10-25-14 일지](../journal/2026-10-25-14-debug.md) 와 [2026-10-25-20 일지](../journal/2026-10-25-20-debug2.md) 에 있습니다. 주소 표기는 [dq4-ram-format.md](dq4-ram-format.md), BRK 형식은 [dq4-bank-format.md](dq4-bank-format.md) 를 따릅니다.

이 문서의 「켜는 법」은 모두 테스트러너 안에서 PRG ROM **메모리**를 바꾸는 것입니다. 롬 파일은 고치지 않습니다.

## 장 고르기(「シナリオ」 창)

가장 쓸모 있는 디버그 기능입니다. `$C000` bit3 을 0(`F7`)으로 두면 장을 시작하기 직전 `1E:$A35B` 가 「シナリオ 1 2 3 4 5」 창을 띄워 1~5장 어디서나 시작할 수 있습니다. 창의 조작, B 의 특수 시작, 장 시작 세이브스테이트 `work/state/dq4-ch{1..5}-start.mss` 를 만드는 명령은 [dq4-save-format.md 「디버그 장 고르기」](dq4-save-format.md#디버그-장-고르기) 가 정본입니다. 이 문서에서는 같은 바이트의 다른 비트를 다룹니다.

## 디버그 스위치 `$C000`

고정 영역의 첫 바이트 `$C000`(PRG 오프셋 `3C000`·`7C000`, 고정 뱅크 `0F`·`1F` 둘 다)은 코드가 아니라 스위치 바이트입니다. 제품판 값은 `FF` 이고, **비트가 0 이면 그 기능이 켜집니다**. 바로 뒤 `$C001` 부터는 `JMP` 표입니다.

롬 전체에서 `LDA/BIT/LDY $C000` 꼴은 뱅크 `17` 을 빼면 12곳(고정 뱅크 두 벌 포함)이고, 아래가 그 전부입니다. 뱅크 `17` 의 `AD 00 C0`·`AC 00 C0` 8곳은 데이터 뱅크(그룹 표)의 우연한 바이트로 봅니다(그 뱅크는 한 번도 실행되지 않음). **bit0·bit1·bit2 를 보는 코드는 없습니다.**

`debugreads.lua` 로 PRG `3C000`·`7C000` 의 읽기를 모두 잡아 봤습니다. 부팅(새 게임 시작까지), 왕좌의 방 대화·걷기, 필드 조우 → 전투, 첫 전투, 2~5장 시작 세이브스테이트에서 걷고 A 누르기, 모두 9장면입니다. 읽은 명령은 `0F:$CE9C`·`$CFB1`·`$D08E`(걸음)과 `1F:$A35B`(부팅, 1회)뿐이었습니다. 색인 읽기나 다른 꼴로 `$C000` 을 읽는 곳(`?` 로 찍힘)은 없었습니다. 표의 나머지 읽는 곳은 이 장면들에서 돌지 않는 루틴(특수 전투, 투기장, 목적지 고르기) 안에 있습니다.

비트 0·1·2·4·5 를 하나씩 0 으로 바꾼 롬(`FE`·`FD`·`FB`·`EF`·`DF`)으로 필드 조우 → 전투 입력을 재생했습니다. 끝 RAM 2KB 와 WRAM 8KB 가 제품판과 바이트까지 같았습니다. 같은 입력에서 `BF` 는 전투가 나지 않아(`$6E49` 1 → 0) 덮어쓰기가 먹는 것은 확인했습니다.

| 비트(켤 값) | 읽는 곳 | 켜면 | 근거 |
| --- | --- | --- | --- |
| bit7(`7F`) | `0F/1F:$CFB1`, `$D08E`(맵 걸음) | 패드 1 B 를 누르고 걸으면 바닥 검사(`$6F40,X` → `$0594`)를 건너뛰어 **벽을 지나감** | 실측 |
| bit6(`BF`) | `0F/1F:$CE9C`(걸음 끝) | 걸음마다 부르는 조우 판정(`BRK 00 8F` = `18:$9BE6`)을 **Start 를 누를 때만** 부름. 곧 인카운트 끄기 | 실측 |
| bit6(`BF`) | `11:$BF02`(함수 `11[14]` 안) | 몬스터 무리 4칸을 고르는 **전투 테스트 창**을 띄움 | 창은 실측, 정상 진입 경로는 아래 |
| bit5(`DF`) | `18:$A1F8`(특수 전투 `18[01]`) | `$6E44` bit6 을 켜는 줄을 건너뜀. 그런데 바로 앞 `ORA #$C0` 이 이미 bit6 을 켜므로 차이가 없음 | 코드 읽기 |
| bit4(`EF`) | `10:$9513`(뱅크 10 처리기 표 `10:$9EF3` 의 항목) | ルーラ·キメラのつばさ 의 「どこへ」 목록에 가 본 마을 비트(`$6165`~`$6169`)와 상관없이 모든 마을이 마을 레코드 번호 순(`$AF00`+7×번호: キングレオ, てんくうじょう, サントハイム, バトランド …)으로 뜨고, 고른 순번을 그대로 `$72` 에 씀. 1장 필드에서 비트를 모두 00 으로 두고 키메라의 날개를 써 1~4번째를 고르자 레코드 00~03 자리(필드 0 (40,A7), 맵 2D/00 (0C,07), 필드 0 (27,4A), 필드 0 (A4,2F))에 섬. 제품판(`FF`)은 같은 상태에서 목록이 비어 있음. 제품판 목록 규칙은 [dq4-save-format.md](dq4-save-format.md) | 확인 |
| bit3(`F7`) | `1E:$A35B`(장 시작 전) | 「シナリオ」 장 고르기 창 | [dq4-save-format.md](dq4-save-format.md#디버그-장-고르기) 에서 실측 |
| 바이트 전체가 `00` | `18:$ABA9`(투기장 `18[14]`) | 투기장 시합 직전에 **전투 테스트 창**(`BRK 14 1F` = `11[14]`)을 띄워 싸울 무리를 바꿈. 「おわり」 뒤 고른 무리로 시합이 시작됨 | [실측](#투기장에서-전투-테스트-창) |
| 바이트 전체가 `00` | `10:$81B9`(뱅크 10 효과 처리의 실패 출구) | 효과가 처리되지 않고 끝날 때 「まん」「ばんく 17。」「ふあんく 45。」「P1 0です。」처럼 부른 뱅크·효과 번호·인자를 10진으로 찍는 **개발용 오류 보고** | [실측(억지로 부름)](#1081b9-효과-처리-실패-보고) |

### 실험에 쓰는 법

분석 실험을 쉽게 하는 쓰임새입니다.

| 하려는 것 | 켤 값 | 함께 쓸 것 |
| --- | --- | --- |
| 다른 장의 마을·던전을 처음부터 보기 | `F7` | 장 시작 세이브스테이트 `dq4-ch{1..5}-start.mss` 를 `STATE` 로 |
| 맵의 아무 칸에나 가기(벽·물·카운터 너머) | `7F`, B 를 누른 채 걷기(`SEQ="left+b:200"`) | [warp.lua](dq4-warp.md) 로 맵에 들어간 뒤. 카운터 너머 인물, 막힌 방, 보물 칸 |
| 전투 없이 오래 걷기 | `BF` | 필드·던전 자동 보행, 맵 전환·입구 실측. 조우가 필요한 순간만 Start 를 같이 누름 |
| 정해진 무리와 싸우기 | `00` | 엔도르 투기장(맵 `04/01`, (08,0A) 인물)에서 내기를 걸면 시합 전에 전투 테스트 창이 뜸. [아래](#투기장에서-전투-테스트-창). 일행이 싸우는 전투는 아님(투기장 시합) |
| 빨리 걷기 | `$CADC`=`F0 0C EA` + `PAD2=02` | 아래 「패드 2 흔적」 |

`debugpad.lua` 는 입력 드라이버 앞에 끼우는 스크립트라 `DRIVER` 를 바꾸면 무엇이든 묶을 수 있습니다. 다른 프로브(`cover`·`trace` 등)와 묶으려면 그 프로브의 `DRIVER` 로 `debugpad.lua` 를 주고 실제 드라이버는 `PAD_DRIVER` 로 줍니다. 워프와 묶으면 이렇습니다(실측: 제품판은 (11,09) 그대로, `7F` 는 x=`06` 까지).

```sh
DRIVER=$PWD/fc/dq4/tools/lua/warp.lua MAP=04/00 X=11 Y=09 SEQ="left+b:200" TAIL=30 \
  ROMPATCH="3C000=7F;7C000=7F" SHOT_DIR=$PWD/work/wp \
  "$MESENCE" --testrunner --nes.ramPowerOnState=AllZeros "$PWD/rom/dq4.nes" "$PWD/fc/dq4/tools/lua/debugpad.lua"
cat work/wp/warp.txt    # 「끝」 줄의 44= 가 도착 x 에서 줄어 있음
```

`debugpad.txt`(`LOGW`)는 `MAXF` 를 줬을 때 `MAXF-1` 프레임에 씁니다. 워프처럼 드라이버가 먼저 멈추면 `MAXF` 를 그보다 짧게 줍니다.

### 전원을 켜는 실험과 `Saves/dq4.sav`

MesenCE 테스트러너는 롬 파일 이름으로 설정 폴더의 `Saves/<롬 이름>.sav`(macOS 는 사용자 `Library/Application Support/MesenCE/Saves/`)를 배터리 RAM 으로 불러오고, 끝날 때 그 파일에 다시 씁니다. `rom/dq4.nes` 를 쓰는 모든 실험이 `Saves/dq4.sav` 하나를 같이 쓰므로, 동시에 도는 다른 실험이 그 내용을 계속 바꿉니다.

| 실험 | 결과 |
| --- | --- |
| 롬을 다른 이름(`dq4probeA.nes`)으로 복사하고 `Saves/dq4probeA.sav` 를 `5A` 로 채운 뒤 2프레임째 SRAM 덤프 | 8KB 전부 `5A`. 파일이 없으면 전부 `00`이고, 끝나면 그 이름의 `.sav` 가 생김 |
| 같은 `.sav` 를 `5A`·`00` 으로 두고 `dq4-ch1-throne.mss` 를 불러온 뒤 SRAM 덤프 | 둘이 바이트까지 같음. 세이브스테이트가 SRAM 도 바꿈 |
| `dq4state.sh` 의 첫 단계(전원 켜기 → 이름 입력) 입력을 `.sav` 없이, 그리고 모험의 서가 든 `dq4.sav` 사본으로 | 없으면 이름 입력 화면(「ああ」), 사본이면 같은 입력이 이어하기로 가서 오프닝 대사 화면 |

그래서 **세이브스테이트에서 시작하는 실험은 `.sav` 에 영향을 받지 않고, 전원을 켜서 시작하는 실험만 받습니다.** 전원을 켜는 실험은 `debugsram.lua` 를 앞에 끼워 SRAM 을 고정합니다. 스크립트를 읽는 때가 첫 프레임 전이라 리셋 루틴이 SRAM 을 읽기 전에 덮입니다(실측: 위 `5A` 파일을 둔 채 끼우면 1프레임째 SRAM 이 전부 `00`).

```sh
SRAM_DRIVER=$LIBDIR/mkstate.lua SAVEAT=750 MAXF=760 SEQ="..." SHOT_DIR=$d \
  "$MESENCE" --testrunner --nes.ramPowerOnState=AllZeros "$PWD/rom/dq4.nes" "$PWD/fc/dq4/tools/lua/debugsram.lua"
# SRAM=파일 을 주면 00 대신 그 8KB 를 채움
```

`fc/dq4/tools/dq4state.sh` 는 첫 단계를 이렇게 돌립니다. 바뀐 스크립트로 두 번 다시 만들었을 때(그 사이 `Saves/dq4.sav` 는 다른 실험이 바꿈) 세이브스테이트 4개와 그림 3장이 바이트까지 같았습니다. `STATE_DIR` 로 출력 폴더를 바꿀 수 있어 기존 `work/state` 를 덮지 않고 시험할 수 있습니다. 다만 지금 `work/state` 에 있는 1장 세이브스테이트는 이전 `.sav` 로 만든 것이라 새로 만든 것과 다릅니다. 이름이 「あああ」(새로는 「ああ」)이고, SRAM `$6D8C`~ 에 `FF` 가 남아 있으며(새로는 `00`), 첫 전투가 「おおみみず 둘」(새로는 おおみみず 하나·スライム 하나)입니다. 이름 입력에 A 를 하나 더 넣어 「あああ」로 맞추면 대사 타이밍이 밀려 필드 단계에서 성 앞을 벗어나지 못했습니다.

### 켜는 법

`debugpad.lua` 를 입력 드라이버 앞에 끼워 `ROMPATCH` 로 두 벌을 같이 바꿉니다(세이브스테이트를 불러온 뒤인 3프레임째에 씀).

```sh
export MESENCE=/path/to/Mesen LIBDIR=$(uv run krpatch fc lua)
d=$PWD/work/wallpass; mkdir -p $d
DRIVER=$LIBDIR/seq.lua STATE=$PWD/work/state/dq4-ch1-courtyard.mss SEQ="left+b:300" TAIL=2000 EVERY=0 MAXF=400 \
  ROMPATCH="3C000=7F;7C000=7F" LOGW=0044,0045 SHOT_DIR=$d \
  "$MESENCE" --testrunner --nes.ramPowerOnState=AllZeros "$PWD/rom/dq4.nes" "$PWD/fc/dq4/tools/lua/debugpad.lua"
cat $d/debugpad.txt     # 값이 바뀐 프레임마다 "프레임 0044=.. 0045=.."
```

여러 기능을 함께 켜려면 비트를 같이 지웁니다(예: bit7+bit6 = `3F`, 전부 = `00`).

### 실측

| 실험 | 출발 | 입력 | 결과 |
| --- | --- | --- | --- |
| bit7 벽 통과 | `dq4-ch1-courtyard.mss`, (12,0A) | 왼쪽 300프레임 | 제품판·`7F` 만·B 만: 모두 (12,0A) 에서 움직이지 않음. `7F` + B: 16프레임마다 한 칸씩 x=`00` 까지 18칸 |
| bit6 인카운트 | `dq4-ch1-field.mss` | 위아래 왕복(`dq4state.sh` 의 전투 입력) 1600프레임 | 제품판: 374프레임에 전투(`$6E49`=`01`). `BF`: 약 93걸음 동안 전투 없음. `BF` + Start 를 누르며 걷기: 230프레임에 전투 |
| bit6 전투 테스트 창 | `dq4-ch1-courtyard.mss` | `0F/1F:$CEAE` 의 `BRK 00 8F` 를 `BRK 14 1F` 로 바꾸고 `BF` + Start 로 한 걸음 | 「― ひき」 네 줄과 「おわり」 창 → A 로 몬스터 목록(スライム, いたずらもぐら …) → 마릿수 창(`00`) → 첫 칸 「スライム ― 2ひき」, `$6E45`=`00`·`$6E49`=`02`. 「おわり」 뒤 화면이 어두워진 채 전투로 넘어가지 않음(조우 판정 자리에 억지로 넣었으므로) |

### 투기장에서 전투 테스트 창

투기장은 엔도르 지하 `04/01` 의 (08,0A) 인물(대화 번호 `048`)입니다. 그 스크립트가 `15:$AAA5` 에서 `BRK 14 8F`(`18[14]` = `18:$A813`)를 부릅니다. `18[14]` 의 고리는 이렇게 돕니다.

| 주소 | 하는 일 |
| --- | --- |
| `18:$A818` | 메시지 `0480`(「かくとうじょうは こちら！」) |
| `18:$A81B` | 메시지 `0489`(「つぎのしあいの モンスターと ばいりつは これです。」) |
| `18:$A840` | 시합 무리 고르기. 몬스터 `$6E45`~`$6E48`, 마릿수 `$6E49`~ 에 씀(실측). 장 `$615A`·`$62D5` 로 표를 고르는 것은 코드 읽기 |
| `18:$A8D4`, `$ABF6` | 걸 몬스터와 매수(`0481`). 코인은 `$62AD`~`$62AF`(3바이트), 건 매수 `$6E82`~`$6E85` |
| `18:$AB98` | 「FIGHT!」 화면 뒤 `$6E44`=0, **`$ABA9` 에서 `$C000` 이 `00` 이면 `BRK 14 1F`(전투 테스트 창)**, 그다음 `$72E9`=`80` 과 `BRK 28 0F` 로 시합 |
| `18:$AA11` | 결과 |

실측은 1장 왕좌의 방 세이브스테이트에서 `warp.lua` 로 `04/01` (08,0B) 에 들어가 코인을 넣고(`SET="62AD=E80300"`, 1000) 말을 걸었습니다. `debugtrap.lua` 로 `18:$ABA9`(PRG `62BA9`)와 그 뒤 `$ABB1`(`62BB1`)을 잡았습니다.

```sh
TRAP=62BA9,62BB1 LOG=6E45,6E46,6E47,6E48,6E49 TRAP_DRIVER=$PWD/fc/dq4/tools/lua/debugpad.lua \
  PAD_DRIVER=$PWD/fc/dq4/tools/lua/warp.lua ROMPATCH="3C000=00;7C000=00" STATE=$PWD/work/state/dq4-ch1-throne.mss \
  MAP=04/01 X=08 Y=0B DIR=0 SET="62AD=E80300" SEQ="a:4,wait:30,a:4,wait:120" TAIL=60 SHOT_DIR=$d \

```

| 경우 | 결과 |
| --- | --- |
| 제품판(`FF`) | `$ABA9` 와 `$ABB1` 이 같은 프레임. 창 없이 スライム·キリキリバッタ·はさみくわがた·スライムベス 각 1마리(`$6E45`~ `00 01 03 05`, `$6E49`~ `01 01 01 01`) 시합 |
| `00`, 창에서 바로 「おわり」 | 「FIGHT!」 뒤 팔레트가 모두 `0F` 인 검은 화면에 창이 뜸(네임테이블에는 네 줄과 「おわり」가 있음). 아래 4번 + A 로 「おわり」 → 82프레임 뒤 `$ABB1`, 같은 네 마리로 시합 |
| `00`, 첫 줄을 고친 뒤 「おわり」 | A → 목록에서 아래 2번 → A → 마릿수에서 위 2번 → A 로 첫 줄이 `$6E45`=`04`(이름 スライム, HP 40 짜리 다른 항목)·`$6E49`=`02`. 「おわり」 뒤 슬라임 둘 + 나머지 셋으로 시합 |

곧 `$C000`=`00` 이면 투기장이 **원하는 몬스터 무리끼리 싸움을 붙이는 전투 테스트**가 됩니다. 창이 검은 화면에 뜨는 것은 「FIGHT!」 화면이 팔레트를 꺼 둔 채 부르기 때문으로 보입니다(창은 보이지 않아도 입력은 먹음). 앞 절의 조우 판정 자리(`$CEAD`)에 억지로 넣으면 전투로 넘어가지 않았는데, 투기장은 창 뒤에 시합을 여는 `BRK 28 0F` 가 따로 있어서 넘어갑니다.

### `10:$81B9` 효과 처리 실패 보고

뱅크 10 은 주문·도구 효과 처리입니다. BRK 특수 형식 `x3`([dq4-bank-format.md](dq4-bank-format.md#특수-형식))이 `$76`~`$78` 을 두고 뱅크 10 함수를 부르면, `10:$815F` 가 효과 번호 `$6E0B` 로 처리기 표 `10:$9E67` 을 찾아(`10:$8221`) 부릅니다. 처리기 표에는 `47` = `$9513`(bit4 가 읽는 목적지 고르기)도 있습니다. 조건이 맞지 않을 때(`10:$831E` 가 C=0) `10:$8223` 대신 `JMP $81B9` 로 가고, 처리기 14곳도 끝에서 같은 곳으로 갑니다.

`10:$81B9` 는 제품판에서 `CLC; RTS` 로 「처리 안 됨」만 돌려줍니다. `$C000`=`00` 이면 그 전에 `$6BDD` bit7 을 켜고 메시지를 찍습니다.

| 순서 | 코드 | 찍는 것 |
| --- | --- | --- |
| 1 | `BRK 07 6F`(`16[07]`), `BRK CA 1B` | 메시지 `01CA`(「まん。」) |
| 2 | `BRK 12 FB` | 소리 `12` |
| 3 | `$FD` = 들어올 때의 `$0517`, `BRK CD 1B` | `01CD` 「ばんく [F8]。」 = 부른 쪽 뱅크 |
| 4 | `$FD` = `$6E0B`, `BRK CE 1B` | `01CE` 「ふあんく [F8]。」 = 효과 번호 |
| 5 | `$FD` = `$6E`, `BRK CF 1B` | `01CF` 「P1 [F8]です。」 = 첫 인자(행동하는 사람 번호로 보임) |

곧 개발 중에 처리기가 없는 효과를 부르면 어디서 무엇을 불렀는지 알려 주던 **오류 보고**입니다. 「まん」은 앞의 무언가에 이어 붙던 말(「すみません」 같은)의 꼬리로 보이지만 메시지 `01CA` 자체가 「まん。」입니다.

실측: 정상 진행에서는 이 출구를 한 번도 못 봤습니다(앞 절 18장면 커버리지, `$C000`=`00` 으로 1장 첫 전투 A 연타 1360프레임에서 `debugtrap.lua` 로 PRG `401B9` 0회). 그래서 `10:$8221` 을 `JMP $81B9`(`ROMPATCH="40221=4CB981"`)로 바꿔 첫 효과부터 이 출구로 보냈습니다. 첫 전투 명령 창에서 A 를 누른 직후의 첫 효과(`$6E0B`=`2D`, `$6E`=`00`, `$0517`=`11`)에서 창에 「まん」 → 「ばんく 17。」 → 「ふあんく 45。」 → 「P1 0です。」가 차례로 찍혔습니다(값은 10진, `$11`=17, `$2D`=45). 같은 실험에서 `$6E0B` 는 `2A`·`46`·`3C` 도 지나갔습니다.

## 패드 2 흔적

패드 읽기 `0F/1F:$C8EC` 는 패드 1 을 `$14`, 패드 2 를 `$15` 에 둡니다(bit0 A, 1 B, 2 Select, 3 Start, 4 위, 5 아래, 6 왼쪽, 7 오른쪽; `$CB1A` 방향 표 `10 80 20 40` 과 맞음). 패드 2 는 `$C8FF` 의 `LDA $4016,X` 가 X=1 일 때 읽습니다(곧 `$4017`). 절대 주소로 `$4017` 을 읽는 명령은 없고, `1F:$F090` 은 APU 프레임 카운터로 쓰기만 합니다. `$CBAA` 의 `LDA $4016` 은 스트로브 직후 첫 읽기 값(패드 1 의 A 비트와 그 위 확장 비트)을 `$0529` 에 OR 로 모읍니다(코드 읽기).

`$15` 를 읽는 코드는 롬 전체에서 `0F/1F:$CAD8` 한 곳입니다. 걸음 시작마다 돕니다.

```text
0F:CAD8  a5 15    LDA $15        ; 패드 2
0F:CADA  29 03    AND #$03       ; A·B
0F:CADC  4c ea ca JMP $CAEA      ; A 를 버리고 $0584 를 다시 읽음
0F:CADF  8d 84 05 STA $0584      ; ← 아무 데서도 오지 않음
0F:CAE2  a9 20    LDA #$20
0F:CAE4  8d 85 05 STA $0585
0F:CAE7  4c 34 d2 JMP $D234      ; 패드 읽기
```

`$0584` 는 걷기 상태입니다(보통 `01`, 바닥 종류 `$10`~`$13` 의 미끄러지는 바닥이면 `02`). `$CA21` 이 `$CA3C+$0584` 의 가면(`0F`·`07`·`0F`)으로 걸음 간격을 정합니다. 그러니 `$CADF` 는 패드 2 의 A·B 를 걷기 상태로 쓰던 자리이고, 지금은 `JMP` 로 막혀 있습니다.

`$CADC` 를 `F0 0C EA`(`BEQ $CAEA; NOP`)로 바꿔 패드 2 값이 `$CADF` 로 가게 하면(원래 분기 꼴은 알 수 없어 이렇게 되살린 것입니다):

| 패드 2 | `$0584` | 한 칸 걷는 데 |
| --- | --- | --- |
| 없음 | `01` | 16프레임 |
| A | `01` | 16프레임 |
| B | `02` | 8프레임(두 배 빠름, 맵·필드 모두) |
| A+B | `03` | 16프레임 |

덮어쓰지 않은 제품판에서 패드 2 B 를 눌러도 16프레임 그대로였습니다.

MesenCE 테스트러너에서 `emu.setInput(입력, 1)` 은 포트 번호와 상관없이 패드 1 로 들어갔습니다(MesenCE 설정의 포트 2 가 `None`, 명령줄 `--nes.port2.type` 도 효과 없음). 그래서 `debugpad.lua` 는 패드 읽기가 패드 2 를 다 읽고 돌아가는 `$C90B`(X=1)에서 `$15` 를 `PAD2` 값으로 덮습니다. `$15` 를 읽는 곳이 하나뿐이라 패드 2 를 누른 것과 같습니다.

## 미실행 코드 찾기

`dq4debug.py` 는 `probe/cover.lua` 기록 여러 개를 합쳐, 실행된 명령에서 갈 수 있는 곳(조건 분기의 다른 쪽, `JMP`·`JSR` 대상, `BRK` 뱅크 호출 대상과 BRK+3)을 따라가 한 번도 실행되지 않은 명령을 덩어리로 모읍니다. `$C000` 이상은 출발 뱅크의 256KB 절반의 고정 뱅크(`0F`/`1F`)로, 고정 영역에서 `$8000` 대로 가는 `JSR` 은 뱅크를 몰라 따라가지 않습니다.

```sh
C=$(ls work/cov/*/cover.txt)
uv run python fc/dq4/tools/dq4debug.py rom/dq4.nes unrun $C   # 덩어리: 시작, 바이트, 명령 수, ?(따라가다 잘못된 명령), 들어오는 곳
uv run python fc/dq4/tools/dq4debug.py rom/dq4.nes find $C    # 패드 2·$4017·$C000 읽기, 패드와 여러 비트 비교
uv run python fc/dq4/tools/dq4debug.py rom/dq4.nes brk $C     # BRK 함수 표에서 닿는 코드의 BRK 가 부르지 않고 실행도 안 된 항목
```

18장면에서 모았습니다: 전원 켜기 3000프레임(타이틀), 이름 입력, 오프닝 대사, 왕좌의 방 명령 창 8칸 전부·대화·무작위 걷기, 성 앞 → 필드, 필드 걷기, 전투(싸우기·다른 명령), 필드에서 조우 → 전투, 워프로 맵 6곳(`04/00`·`0B/00`·`0E/00`·`1B/00`·`2B/00`·`45/00`)·필드 2곳의 무작위 걷기와 말 걸기.

| 값 | 수 |
| --- | --- |
| 실행된 명령 | 28579개(56947바이트) |
| 실행된 뱅크(오프셋 수) | `08` 1156, `0B` 29, `0E` 88, `0F` 4704, `10` 2991, `11` 2118, `12` 1519, `13` 140, `14` 2099, `15` 334, `16` 4015, `18` 977, `19` 48, `1A` 1309, `1B` 244, `1C` 637, `1D` 520, `1E` 1914, `1F` 3737 |
| 실행 안 된 뱅크 | `00`~`07`, `09`, `0A`, `0C`, `0D`, `17` |
| 닿는데 실행 안 된 코드 | 18068명령, 35847바이트, 덩어리 1065개 |
| 그중 큰 것 | `0F:$CEC4` 4543바이트(맵 바닥 종류 처리에서 여러 뱅크로 가는 BRK 를 따라 이어진 것), `12:$84AA` 1718바이트, `11:$88C1` 1316바이트, `15:$9CC3` 899바이트(대화 스크립트 쪽) |

`find` 가 낸 후보는 `0F/1F:$CAD8`(패드 2) 두 곳과 `$C000` 읽기 9곳이 전부였습니다. 커버리지로 닿지 않는 `10:$9513`·`18:$A1F8`·`18:$ABA9` 는 롬 바이트 검색(`AD 00 C0` 꼴)으로 찾았습니다. 「실행 안 됨」은 이 18장면 기준이고, 엔딩·카지노·배·마차처럼 들르지 않은 장면의 코드도 섞여 있습니다.

## 남은 것

- 투기장 테스트 창의 몬스터 목록 순서(목록 셋째 칸이 몬스터 `04` 였음)와 마릿수 창의 범위. 일행 전투로 고른 무리와 싸우는 길은 아직 없음(조우 판정 자리에 넣으면 전투로 넘어가지 않음).
- `10:$9EF3` 처리기 표가 어느 명령의 표인지.
- `10:$81B9` 에 정상 진행으로 닿는 경우(어떤 효과·조건에서 처리기가 「처리 안 됨」을 내는지). 처리기 14곳의 `JMP $81B9` 조건과 `10:$831E` 의 `$6BDE` bit7 조건.
- `work/state` 의 1장 세이브스테이트를 새 `dq4state.sh` 결과로 바꿀지(지금 것은 이전 `.sav` 로 만든 것이라 이름·첫 전투가 다름). 바꾸면 그것을 출발점으로 쓴 실험 문서의 숫자를 다시 확인해야 함.
- 패드 2 흔적의 원래 분기 꼴(`$CADC` 에 무엇이 있었는지)은 알 수 없음. 되살린 꼴에서 A(`01`)·A+B(`03`)가 무엇을 뜻했는지.
- 고정 뱅크 `0F` 에서 `$8000` 대로 가는 `JSR` 을 뱅크까지 따라가면 미실행 목록이 더 정확해짐(지금은 따라가지 않음).
